## Context

On the stream-json interactive path a **new session is a fresh spawn with a new session id**, not a typed
`/clear` (that is the terminal/PTY-path mechanism). The production pieces are already built and
unit-tested: `Pool.RotateForNewSession` (#1125, mints a fresh id, re-keys the pool, rebinds the
conversation, persists), `(*streamsup.Runner).RestartFresh` (#1124, rotates the runner id and re-spawns
fresh), and `startFreshRunner`'s type-switch dispatch that wires them together for the stream runner
(#1125). #1141 proved one `send_message` drains on the stream path; #1136 proved an interrupt stops a
running turn. This spec proves the **next** behaviour on that path — `new_session` rotates the id and
restarts the bound runner fresh, with **no `/clear`** — live, end-to-end, against the fakeclaude
stream-json harness.

This is the stream twin of `TestRelayV2_NewSessionRotatesOnDisk` (the PTY new_session e2e). The PTY test
asserts the fsnotify watcher follows claude's self-rotated `<uuid>.jsonl` into the registry; the stream
test asserts the **daemon-minted** rotation lands directly (no watcher, no `/clear`).

## Design

One test: **`TestRelayV2_StreamNewSessionRotatesAndRestartsFresh`** (build tag `e2e`, package `e2e`).

### Constants / setup (mirror the #1141 send test)

- `initialUUID = "11111111-1111-4111-8111-111111111111"` (bootstrap), `knownConvID =
  "22222222-2222-4222-8222-222222222222"`, two distinct turn texts (`e2e-1137-user:one`,
  `e2e-1137-user:two`) with matching echo needles.
- `home := shortHome(t)`; pair `phone-a`; decode payload + server static pubkey.
- `seedBoundConversation(t, home, knownConvID, initialUUID)` — binds `knownConvID` → the bootstrap
  (`initialUUID`). **Load-bearing twice:** it stamps the id alignment that makes M1's pre-rotation drain
  pass (sink tag == active == `initialUUID`), and its cursor-stamp (via the M1 `send_message`) is what lets
  `new_session` resolve to the bound runner (#1125 routing prerequisite).
- `stdinLog := filepath.Join(t.TempDir(), "fakeclaude-stdin.log")`.
- `fr := fakerelay.New(relayTestLogger())`; `regPath := filepath.Join(home, ".pyry", "test",
  "sessions.json")`.
- `h := StartStreamInteractiveWithRelay(t, home, initialUUID, fr.URL()+"/v2/server",
  "PYRY_FAKE_CLAUDE_STDIN_LOG="+stdinLog)` — the extra env flows to the daemon's process env and is
  inherited by **both** the bootstrap child and the fresh post-rotation child (both append to the one log;
  see the fake change).
- `serverID`; `waitBinaryHello`; `fakephone.Dial`; `driveHandshakeToOpenDaemonInteractive` (interactive —
  the capability `handleNewSession` and the structured stream both require).

### Ordered milestones (these ARE the acceptance criteria)

- **M1 — pre-rotation baseline (child live; AC-1 precondition).** `send_message` #1 (`knownConvID`, text
  `…one`) → await its sealed ack → drain until an `assistant_delta` whose `Text` contains the `…one` echo
  (`ConversationID == knownConvID`). This is the #1141 send test verbatim; it proves the child is live and
  the **pre-rotation** turn drains to the phone (the drain gate passes because tag == active ==
  `initialUUID`). Then assert the baseline `waitForBootstrapID(t, regPath, initialUUID, …)` (non-vacuity
  for M2).

- **new_session actuation (AC-1).** Bounded re-send loop: `sendNewSessionFrame(t, phoneA, sendA, reqID++)`
  every ~250 ms until M2 observes the rotation, capped ~10 s. `new_session` is fire-and-forget and drops
  silently on a detached session, so re-send exactly as `relay_v2_new_session_test.go:191-208` does. After
  M1 the child is live, so the first frame should actuate; the loop is defensive against timing.

- **M2 — rotation on disk (AC-2, "session id rotates" + "restarts fresh").**
  `post := waitForBootstrapIDChange(t, regPath, initialUUID, 10*time.Second)`. Assert
  `uuidStemPattern.MatchString(post.ID)` and `post.LastActiveAt.After(pre.LastActiveAt)` (the exact shape
  the PTY test uses). **This on-disk rotation is a strong proof of the whole mechanism, not just the pool
  write:** `startFreshRunner`'s stream arm is a *single* path — `newID, _ := rotate(oldID);
  v.RestartFresh(string(newID))` (`main.go:1345-1351`) — so a persisted rotation `initialUUID → newID`
  (from `RotateForNewSession`'s `saveLocked`) implies `RestartFresh(newID)` was invoked immediately after
  with the same id. Registry rotated ⟹ the bound runner restarted fresh under `newID`.

- **M3 — client observes the rotation (AC-2, "the client observes …").** Drain phone envelopes (mirror
  `nextEnv`) until a `protocol.TypeSessionTransition` whose `SessionTransitionPayload` has `Reason ==
  "clear"`, `NewSessionID == post.ID`, `PreviousSessionID == initialUUID`, `ConversationID ==
  knownConvID`. This frame is broadcast to every interactive conn on `notifyTransition(ReasonClear)` — the
  phone-side, different-fabric observable of the fresh-session break, carrying the daemon-minted new id.
  Use a generous deadline and tolerate interleaved broadcasts.

- **M4 — the post-rotation session serves a subsequent turn (AC-2, "…serving a subsequent turn").**
  `send_message` #2 (`knownConvID` — now rebound to `post.ID`, text `…two`) → await its ack. The ack
  proves the **rotated** session accepts a subsequent turn: `Route` resolves `knownConvID` →
  `CurrentSessionID == post.ID` → `Pool.Lookup(post.ID)` HIT (the pool was re-keyed to `post.ID`). Then
  poll the stdin log until it contains the `…two` bytes — the **fresh child received and is serving** the
  subsequent turn (the daemon's inbound queue retries `WriteUserTurn` until the fresh child is stdin-ready,
  so a generous ~20 s deadline absorbs the fresh spawn).
  **Do NOT drain a phone-side `assistant_delta` for turn #2** — it is dropped at the stream drain gate.
  See § *The post-rotation drain divergence* and § Open questions. The stdin-log delivery proof is the
  achievable "serving" observable and keeps this ticket test-only.

- **M5 — no `/clear` on the stream path (AC-3).** Read the full stdin log. Assert it (a) **contains** a
  user-turn marker (e.g. the `…one` needle, or the substring `"type":"user"`) — non-vacuity, proving the
  log actually captured stdin — and (b) **never contains** `/clear`. On the stream path `new_session` is a
  process re-spawn (`RestartFresh`), never a keystroke, so no child ever receives `/clear`. (Poll briefly
  for (a) to close the cross-process write-visibility window, then assert (b) on the same bytes.)

- **AC-4:** `relay_v2_new_session_test.go` is untouched. **AC-5:** `make e2e` green with the new spec.

### The fakeclaude change (stream-path stdin tee)

The stream-json branch (`main()` ~line 447) currently does `runStreamJSON(os.Stdin, os.Stdout,
honorInterrupt)` and returns — it reads stdin directly and logs nothing (the `startStdinReader` log path is
a *different* reader used only by the PTY/TUI modes below). Add, gated on `PYRY_FAKE_CLAUDE_STDIN_LOG`
being set:

- Open the log file with the **same flags** the PTY path uses: `os.OpenFile(logPath,
  os.O_WRONLY|os.O_APPEND|os.O_CREATE, 0o600)` (append, so the bootstrap child and the fresh child both
  accumulate into one log; `fatalf` on error, matching `startStdinReader`).
- Wrap it in a tiny sync-on-write `io.Writer` (Write → `f.Write` then `f.Sync`, mirroring the PTY reader's
  per-write `Sync` at `:1025-1032`) and pass `io.TeeReader(os.Stdin, thatWriter)` to `runStreamJSON`
  instead of `os.Stdin`.
- Keep `runStreamJSON`'s signature unchanged — the tee lives at the call site, so `main.go:448`'s siblings
  (#1136 interrupt mode) and the #1140 `runStreamJSON` unit test are untouched.

Contract: **additive and off by default.** With `PYRY_FAKE_CLAUDE_STDIN_LOG` unset the branch is
byte-identical to today (the #1141/#1136 stream tests set no such env). Every stdin byte the daemon writes
to the stream child — user-turn envelopes, interrupt control_requests — is teed; none is `/clear`, which is
the point of AC-3.

Document the env's stream-path meaning in the `main.go` package-doc block that already lists
`PYRY_FAKE_CLAUDE_STDIN_LOG` (a one-line addition: "In stream-json mode the same var tees the stream
child's stdin to the file").

### Why the observables are what they are

- **Rotation is daemon-minted, not fake-minted.** The ticket note "the fake must mint a fresh session id
  on restart so the rotation is observable" describes the **PTY** pattern (the fake self-rotates
  `<uuid>.jsonl` on `/clear`, and the watcher follows it). On the **stream** path `RotateForNewSession`
  mints the id (`NewID()`), re-keys the pool, and `saveLocked`s it directly — the fake plays no part in the
  id. So **no fakeclaude session-id change is needed**: the stream fake keeps its cosmetic `"fake-stream"`
  literal (the parser never decodes `session_id`). The observable is the on-disk registry (M2) plus the
  phone-side `session_transition` (M3).

- **The pre-rotation turn drains to the phone; the post-rotation turn is proven at the fake boundary.**
  This asymmetry is not a test shortcut — it is the current behaviour of the opt-in stream path (see
  next §). M1 uses the drain; M4 uses the stdin log.

### The post-rotation drain divergence (load-bearing — read before designing M4)

The stream turn-drain gate forwards an event only when the producing runner's sink tag equals the active
conversation's bound session id (`stream_turn_drain.go:126-136`; `env.sessionID != active → drop`). Two
facts collide after a rotation:

- The sink tag is fixed at **runner construction**: `sink.sinkFor(cfg.SessionID)`
  (`streamsup_runner.go:94`) captures `initialUUID` once, and `RestartFresh` re-spawns the child **in
  place** — it never rebuilds the runner, Parser, or sink. So the bootstrap runner's events stay tagged
  `initialUUID` forever.
- `RotateForNewSession → notifyTransition(ReasonClear) → rebindConversation`
  (`transition.go:57-88,113-142`) sets `conv.CurrentSessionID = newID`. So
  `boundSessionIDForActive` (`relay.go:427-437`) returns `newID` after the rotation.

⇒ For a turn issued **after** the rotation, `env.sessionID (initialUUID) != active (newID)`, so its
`assistant_delta`/`turn_end` are dropped at the gate and never reach the phone. This is why M4 does not
drain a phone-side delta. It is a **latent gap in the opt-in, still-under-construction stream path**,
surfaced for the first time by driving a turn after a stream rotation; it is a *separate concern* from
`new_session` routing (which this ticket proves works) and is **out of scope** here (test-only). See
§ Open questions for the recommended follow-up. **Do not "fix" it by asserting a delta — the test will
hang at M4.**

## Concurrency model

Same as every `relay_v2_*` sibling: the test goroutine is the **sole reader** of the phone conn and the
sole writer of `sendA`-sealed frames. Drain loops (`nextEnv`) read serially with per-milestone deadlines;
the daemon and fake run as real processes. No goroutines are spawned by the test. The stdin-log poll is a
plain bounded `os.ReadFile` loop. The fake's tee runs on `main()`'s single goroutine (no shared state), so
`-race` stays clean by construction (as `runStreamJSON` already is).

## Error handling / failure modes (make each `t.Fatal` self-diagnosing)

- **M1 delta never arrives** → child never came up or the pre-rotation drain broke (most likely a UUID
  mismatch between `seedBootstrapRegistry`/`seedBoundConversation`) — reuse #1141's diagnostic wording.
- **M2 never rotates** (`waitForBootstrapIDChange` times out) → `new_session` did not actuate: the frame
  dropped on a detached session, the `streamRunner.RestartFresh` forwarder is missing (silent-inert —
  #1125's classic failure), or the cursor was never stamped. Dump `mustReadFile(t, regPath)`.
- **M3 no `session_transition`** → the transition emitter did not broadcast the clear, or the resolver
  couldn't map `newID` → conversation. Distinguish from M2 (M2 green + M3 red ⟹ emitter/resolver, not
  rotation).
- **M4 stdin log never gains `…two`** → the fresh child never received the subsequent turn (delivery never
  reached it, or the rotated session didn't re-spawn). Include the ack-received / not-received state and
  the log contents in the message.
- **M5 `/clear` present** → the stream arm mis-routed to the PTY `/clear` path (a `startFreshRunner`
  type-switch regression). **M5 `…one`/`"type":"user"` absent** → the tee is not wired or the env didn't
  reach the child (guards M5 against a vacuous pass on an empty log).

## Open questions

1. **Post-rotation phone-side streaming (the drain divergence) — recommend a follow-up production ticket.**
   Under `interactive_runner: "stream-json"`, assistant output for any turn **after** a `new_session` (or
   any future stream rotation) is dropped at the turn-drain gate because the runner's sink keeps its
   construction-time tag while the conversation rebinds to the new id (see § *The post-rotation drain
   divergence*). For a remote-interactive feature this is a real functional gap, not just a test
   inconvenience — after `new_session` the user keeps chatting and would see nothing. It is a *separate*
   concern from this ticket (which proves rotation + fresh-restart + no-`/clear`) and is deliberately left
   out of a test-only ticket. **Recommendation:** file a production ticket to re-tag the runner's drain
   sink on `RestartFresh` (or make the drain gate match via the conversation's `SessionHistory`, which
   already carries the pre-rotation id — cf. `relay.go:821`). When that lands, M4 can be upgraded to a
   phone-side `assistant_delta` drain and the fake-boundary proof demoted to belt-and-suspenders. Flagging
   for PO/documentation triage; not blocking #1137.

2. **Whether M3 (`session_transition`) should be mandatory or belt-and-suspenders.** It is the cleanest
   phone-side "client observes" signal and I've specced it as a required milestone. If it proves flaky
   under interleaving (it shouldn't — the interrupt test drains multi-type frames the same way), it can be
   softened to best-effort while M2 (disk) + M4 (ack + stdin log) still cover AC-2. Developer's call at
   implementation time; default to keeping M3 required.
