## Context

The daemon obtains the model list at child spawn (#1839), retains it per session (#1840), maps it to the wire (#1848) and emits it on the live interactive turn lane (#1849). A client that attaches *after* the `initialize` exchange gets none of it: the emitter returns early while the conversation cursor is empty, the event is droppable under `droppableCap`, and `forwardEnvelope`'s `last_event_id` dedup is a reconnect mechanism with no fresh-connect backfill. #1863 landed the relay-side answer — `V2SessionConfig.RetainedModelLists`, drained by `reconcileModelLists` from `handleNoiseInit`'s interactive-open tail — and wired it to nothing.

**This ticket supplies the daemon-side producer that fills that seam, and nothing else.** The payload is #1857's `resolveBoundModelList` verbatim; the mapping is #1848's; the retention is #1840's. The only new behaviour is *enumeration* — turning a conversation-keyed resolver into a set, because a `V2Session` carries no conversation id and there is nothing to key on at connect time.

**No ADR.** This is the third instance of an already-recorded pattern (connect-time reconcile, Mode B), not a new decision — #1863's write-up in `docs/knowledge/features/v2-session-manager.md` already carries the design rationale, and this ticket only fills the closure it names. The documentation phase updates that section (its closing line still says the seam ships nil and names #1864 as the wirer).

## Design

### The adapter

One new unexported function in `cmd/pyry/session_model_list.go`, directly below `resolveBoundModelList`:

```go
// retainedModelLists adapts the conversation-keyed resolver to the relay
// connect-time reconcile seam (#1863): one marshal-ready ModelListPayload per
// conversation whose bound session currently holds a list.
func retainedModelLists(convReg *conversations.Registry, pool *sessions.Pool) func() []protocol.ModelListPayload
```

Behaviour, in ten lines of body: call `convReg.List()` with **no filter**, allocate `make([]protocol.ModelListPayload, 0, len(convs))`, call `resolveBoundModelList(convReg, pool, string(c.ID))` for each row, append only when the comma-ok is `true`, return the slice. That is the entire function. No new imports — `session_model_list.go` already imports `conversations`, `protocol` and `sessions`.

Five properties the doc comment must state, because each one is a decision a later reader would otherwise re-litigate:

1. **The comma-ok is the only filter.** The adapter reads no field of `Conversation` other than `ID`, and never inspects a payload it is about to append. Every refusal rule stays inside the resolver, which is where #1857 put them; a second spelling here would be a second place the rule is decided.
2. **The double lookup is deliberate.** `List()` already hands back each `Conversation` — including `CurrentSessionID` — and the adapter throws that away and lets the resolver `Get` the row again. The alternative (reading `CurrentSessionID` off the listed row and calling `Pool.Lookup` directly) forks the empty-`CurrentSessionID` guard, which is the #678 isolation enforcement point: `Pool.Lookup("")` returns the *bootstrap* session, so a fork that drifted would hand an unbound conversation the shared bootstrap child's menu under its own id. The cost is one extra registry scan per row; the registry holds tens of rows and this runs once per connect.
3. **Enumerate-all, unfiltered.** See "Archived conversations contribute" below.
4. **A pure read.** It mints nothing, retires nothing, mutates no daemon state, and takes no logger — the resolver's `MUST NOT grow one` rule extends to the adapter for the same #833 reason. There is nothing a "why did this conversation not contribute" line could carry except the caller's id or the model values themselves.
5. **Order is `List()`'s order** (registry insertion order) and is *not* a contract. `reconcileModelLists` sends one envelope per payload and the client correlates on `conversation_id`. Tests index by `ConversationID`, never by position.

### Archived conversations contribute

`List()` with no filter returns archived rows, and `Registry.SetArchived` writes exactly one field — it does **not** unbind `CurrentSessionID`. So an archived conversation whose bound session still holds a list **does** produce a payload. That is the intended behaviour: the reconcile asserts current control truth and the client decides what to show. State it in the doc comment and pin it with a test, so that neither adding nor omitting `ListFilter{IsArchived: ...}` can happen by accident later.

### The bootstrap session contributes nothing, by construction

`CurrentSessionID` is written only at conversation mint (`handlers.CreateConversation`) and rebound on rotation (`Registry.RebindSession`). The pool's bootstrap session has no conversation record and therefore never appears in `List()`. `protocol.ModelListPayload` is conversation-scoped and a bootstrap session has no conversation id to stamp, so there is nothing to send for it. **Do not reach for a `""`-is-bootstrap convention** — that is the exact hazard `resolveBoundModelList`'s empty-`CurrentSessionID` guard exists to close.

### Why this is not a one-line copy of `outstandingQueues`

`outstandingQueues(w.queue)` is buildable inside `startRelayV2` only because `relay.go` imports `internal/msgqueue`. `relay.go` deliberately does **not** import `internal/sessions`, and the `runSettings` field's own comment says so in as many words: the closure is built at `main.go` "so the `internal/sessions` dependency stays at the composition root". The adapter needs a `*sessions.Pool`, so it follows `runSettings`, not `outstandingQueues` — three files, not two:

| File | Change |
|---|---|
| `cmd/pyry/session_model_list.go` | the `retainedModelLists` adapter (above) |
| `cmd/pyry/relay.go` | a `retainedModelLists func() []protocol.ModelListPayload` field on `relayWiring` (documented like `runSettings`: what it is, why it is built at `main.go`, what nil means), plus one line in the `relay.V2SessionConfig` literal in `startRelayV2`, sited next to `OutstandingQueues` |
| `cmd/pyry/main.go` | one entry in the `relayWiring` literal in `runSupervisor`: `retainedModelLists: retainedModelLists(convReg, pool),`, next to `runSettings` |

The field type is `func() []protocol.ModelListPayload` — primitive-typed, `protocol` is already imported in `relay.go`, so no new import there either.

**Assign the field straight through: `RetainedModelLists: w.retainedModelLists`.** Do not wrap it in a closure inside `startRelayV2`. A wrapper would be non-nil even when the field is nil, which silently defeats the seam's `nil ⇒ no reconcile` contract — every existing `relayWiring` literal in tests and the foreground/v1 path leaves the field nil and must stay byte-identical to today.

### Data flow

```
handleNoiseInit (interactive open, relay Run goroutine)
  └─ (*V2SessionManager).reconcileModelLists
       └─ cfg.RetainedModelLists()            ← the seam
            └─ retainedModelLists closure     ← this ticket
                 ├─ conversations.Registry.List()        (all rows, incl. archived)
                 └─ resolveBoundModelList per row        (#1857)
                      ├─ Registry.Get → CurrentSessionID guard
                      ├─ Pool.Lookup → Session.Runner()
                      ├─ type-assert ModelList() (turnevent)
                      └─ turnbridge.MapEvent → protocol.ModelListPayload
```

## Concurrency model

No goroutine is created and none is joined. The closure runs **synchronously on the relay manager's Run goroutine**, called from `reconcileModelLists` inside `handleNoiseInit`'s tail, so it must not block: everything it touches is a leaf acquisition held for the length of a map or slice read.

Lock behaviour is inherited from the resolver and stays additive-free:

- `Registry.List` takes the registry mutex and releases it before the loop begins. Each `resolveBoundModelList` then takes it again in `Get`. **The per-row lookups are never nested inside `List`'s scope** — the loop iterates a *copy*, which is precisely why `List` returns one. Do not restructure into `Registry.Update`/a callback that holds the registry lock across the pool lookup; that would add a registry→pool lock edge the daemon does not have today, and `Registry.Update`'s own doc forbids re-entering the registry from inside it.
- The pool `RLock` and the retention hold's leaf mutex are taken and released inside each resolver call, sequentially, never nested.
- The enumeration is a snapshot-of-snapshots, not an atomic one. A conversation created, deleted, rebound or rotated between `List()` and its own `Get` resolves either to the menu of the session bound a moment ago, or to a refusal — the benign TOCTOU the resolver documents, unchanged by enumerating. A model list is a property of one child's `initialize` reply; a rotation's fresh child reports its own. **No re-read, no retry, no re-list.**

Cost is O(rows²) registry comparisons — each `Get` is a linear scan — plus one deep copy of each contributing session's retained list, once per interactive handshake and never per turn. At the sizes this daemon carries (tens to hundreds of rows) that is microseconds. **State the complexity in the adapter's doc comment**, because the registry only grows: auto-archive sets a flag rather than deleting, and archived rows are deliberately enumerated. It is not fixed here — the clean fix is an id-keyed `Registry.Get`, in another package — and it must not be "fixed" by reading `CurrentSessionID` off the listed row, which trades a performance concern for a security regression (§ Design, property 2). See § Security review [Network & I/O].

## Error handling

The adapter has **no error path of its own and adds no reject branch.** Every refusal is `resolveBoundModelList`'s comma-ok, and the response to `false` is `continue`. Specifically:

| Situation | Where refused | Adapter's response |
|---|---|---|
| Bound session holds no retained list | resolver, at the hold | skip the row |
| Conversation bound to no session (`CurrentSessionID == ""`) | resolver, first guard | skip the row |
| Bound session no longer in the pool | resolver, `Pool.Lookup` error (discarded) | skip the row |
| Runner does not implement `ModelList` (PTY / non-stream runner) | resolver, type assertion | skip the row |
| Registry empty, or no row contributes | — | return the empty slice |
| Unknown conversation id | resolver's first guard — **unreachable from here** | n/a: every id came out of `List()` |

The unknown-conversation arm needs **no test and no second guard**. Building a fixture for it means constructing a state the production path cannot produce.

An empty return is correct and complete: `reconcileModelLists` returns without sending when `len(retained) == 0`. Returning the non-nil zero-length slice (from `make(..., 0, len(convs))`) matches `outstandingQueues`; nil would behave identically, since this slice never marshals — the relay iterates it and marshals each element.

**An empty menu is never presented as a real one.** The resolver never answers `true` with an empty `Models` (`turnevent.ModelList.Models` is documented "Never empty", and every arm that could produce one refuses instead), and the adapter appends only on `true`. Do not add a `len(payload.Models) > 0` check in the adapter — it would be a second, weaker spelling of a rule the resolver already owns, and no test could redden it.

## Testing strategy

All in `cmd/pyry/session_model_list_test.go`, using the fixtures already there. No new fixture type; `sentinelModelList`'s conspicuous `ZZ…ZZ` values are what make the log negative meaningful.

Scenarios (bullet-pointed; the developer writes them in this package's table-driven idiom):

- **AC 1 — one contributing conversation yields exactly one payload.** A pool from `newModelListTestPool`, one session armed with `sentinelModelList("…")`, one registry row bound to it. Assert `len(got) == 1`, `got[0].ConversationID` is that conversation's id, and `assertPayloadCarries(t, got[0], armed)` — entries in claude's order, all six `ModelOption` fields, `DroppedModels` carried through rather than recomputed.
- **AC 2 — each refusal contributes nothing and raises nothing.** One registry holding, alongside one contributing row: a row bound to a session that holds no list (armed with nothing), a row with `CurrentSessionID: ""`, and a row bound to `"session-not-in-pool"`. Assert exactly one payload comes back, that it is the contributing one, and that no payload has empty `Models`. Building all four rows into **one** registry is the point — it pins that a refusal skips its own row rather than aborting the enumeration or contaminating a sibling's payload.
- **AC 2 — nothing to send at all.** An empty registry, and a registry whose only rows all refuse: `len(got) == 0` both times, no panic.
- **Archived rows contribute.** A row with `IsArchived: true` (set on the `conversations.Conversation` literal passed to `Create` — no need to go through `SetArchived`) bound to a session holding a list contributes its payload. This is the sole red for a mutant that adds `ListFilter{IsArchived: &f}`.
- **Multiple conversations are not crossed.** Two sessions (`pool.BootstrapID()` plus one from `pool.Create` under `runPoolReady`), armed with two differently-tagged sentinel lists, two bound rows. Index the result by `ConversationID` and assert each carries its own session's menu. Mirrors `TestResolveBoundModelList_IsolatesConversations` at the enumerator level; it is the pin a shared buffer, an off-by-one, or a loop-variable capture cannot pass.
- **AC 3 — the enumerator logs nothing.** Mirror `TestResolveBoundModelList_LogsNothing`: build the pool *before* swapping `slog.SetDefault` to a buffer, run the enumeration over a registry containing both a contributing row and the refusing rows, assert the buffer is empty, then assert no `ResolvedModel` / `Value` / `DisplayName` / effort level from any returned payload appears in it. Must not call `t.Parallel` — `slog.SetDefault` is process-global.

**What is deliberately not tested, and why** (so a reviewer does not read it as an omission):

- **The struct-literal hop** — `relayWiring.retainedModelLists` reaching `V2SessionConfig.RetainedModelLists`. `startRelayV2` needs a live `*relay.Connection`, a device registry and a static key, so there is no cheap unit seam; `OutstandingModals` and `OutstandingQueues` are unpinned in exactly the same way and for the same reason. **#1868 is the end-to-end proof** and is blocked on this ticket. Review the two lines by eye instead.
- **The unknown-conversation arm** — unreachable from this entry point (see § Error handling).
- **`turnbridge.MapEvent`'s mapping** — owned and pinned by #1848; `assertPayloadCarries` compares against the source event rather than re-tabling it.

## Security review

**Verdict:** PASS

**Findings:**

- **[Trust boundaries]** No findings. The boundary sits **upstream and downstream of this ticket, never inside it**. The adapter takes *no argument at all*: there is no parameter for network data to arrive on. Every conversation id it hands the resolver came out of `Registry.List()`, and those ids are **server-minted** — `handlers.CreateConversation` builds each row's `ID` from `conversations.NewID()`, never from the request — so nothing this path stamps into `ModelListPayload.ConversationID` is client-authored text. The untrusted content (claude-authored model names, effort levels) crosses into the daemon far upstream at #1839/#1840 and is carried opaquely here: the adapter reads no string field of any payload and branches on nothing but the resolver's comma-ok. `resolveBoundModelList`'s untrusted-id rules stay enforced where they are; this entry point simply cannot reach the arm they guard.
- **[Tokens, secrets, credentials]** Not applicable, and specifically so: `ModelListPayload` carries no token, nonce or answer credential (contrast `ModalShownPayload`'s answerability, which is why #877's reconcile had to prove it mints nothing). The adapter mints nothing, so there is no lifecycle, rotation or revocation surface to address. The one adjacent secret — the binary's static key — is loaded in `startRelayV2` and never reaches this closure.
- **[File operations]** Not applicable. No path is constructed, joined, stat'd or opened. `Registry.List` and `Pool.Lookup` are in-memory reads; nothing on this path writes to disk, so there is no mode, symlink, TOCTOU-on-path or atomic-write question. This is worth stating rather than skipping because the resolver's SECURITY note explicitly forbids joining `convID` into a path — the adapter inherits that prohibition and has no path to join it into.
- **[Subprocess / external command execution]** Not applicable. Nothing here spawns, signals or configures a child; the pool session's runner is only *type-asserted for a read method*, never actuated (contrast `activeInterrupter` / `activeSessionStarter`, which reach the same runners to act on them).
- **[Cryptographic primitives]** Not applicable. No randomness, no comparison against a secret, no key material. The frames built from these payloads are sealed by the existing Noise transport downstream; this ticket adds no crypto decision.
- **[Network & I/O]** **SHOULD FIX — noted, not gated: the enumeration is O(rows²) work on the relay manager's shared Run goroutine, and the conversation registry grows monotonically.** Each `resolveBoundModelList` re-`Get`s its row, and `Registry.Get` is a linear scan, so N registry rows cost N scans. Auto-archive sets a flag rather than deleting, and archived rows are deliberately enumerated (§ Design), so N never shrinks on its own. At the sizes this daemon carries (tens to hundreds of rows) the cost is sub-millisecond and invisible; at thousands it becomes a per-handshake stall on the goroutine that dispatches for *every* conn, which is head-of-line blocking rather than a leak. Not fixed here, deliberately: the only clean fix is an id-keyed index inside `internal/conversations` — a fourth production file in another package, against a `size:s` ticket — and the alternative (reading `CurrentSessionID` off the listed row to skip the second lookup) forks the #678 empty-id guard, which is a real security regression traded for a performance one. **Action: the developer states the complexity in the adapter's doc comment** so the cost is visible to whoever hits it, and the fix, if ever needed, lands at `Registry.Get`. No failure has been observed; both sibling reconciles ship enumerations on the same goroutine.
- **[Network & I/O]** OUT OF SCOPE — **nothing bounds the payload *count***. The seam's SECURITY note delegates every bound upstream "explicitly including not on how many payloads are returned", but the bounds it cites (`ModelListPayload.DroppedModels` on the aggregate, `ModelOption.TruncatedFields` per entry, frozen by #1704/#1705/#1812) bound content *within* one payload, and `Pool.ActiveCap` defaults to `0` (uncapped). The count is therefore one payload per conversation holding a list, re-sent per interactive handshake — amplification available to an already-paired device that mints many conversations. **Decision: no cap here**, for three reasons: (a) a cap here is a second place the limit is decided, the exact hazard the seam's note names, and the two could disagree silently; (b) truncating a *control snapshot* degrades badly — the client renders a menu that is wrong rather than merely short, with no way to tell; (c) no failure has been observed, and `outstandingQueues` / `modalbridge.Registry.Snapshot` ship the identical unbounded-count shape today. If it ever needs bounding, the home is `create_conversation` / `Pool.ActiveCap`, where the mint happens — not a read adapter, which would hide the growth rather than bound it. No ticket filed; file one only on an observed failure.
- **[Error messages, logs, telemetry]** No findings, enforced structurally. `retainedModelLists` takes **no logger** and must never grow one — the resolver's stated #833 rule, inherited: the only thing a "why did this row not contribute" line could add is a conversation id or the model values themselves. It also produces no error to wrap: every refusal is a `continue`. AC 3's test pins the regression shape that structure cannot (someone reaching for package-level `slog` / `slog.Default()`), using `sentinelModelList`'s conspicuous `ZZ…ZZ` values so the negative cannot be satisfied by an unrelated substring. The relay side is already bound by `reconcileModelLists`' own note (its marshal branch deliberately withholds `err`, because `encoding/json` quotes the offending bytes).
- **[Concurrency]** No findings, but three properties must survive into the code and are stated in § Concurrency model: (a) **no new lock edge** — the per-row `Get` runs *outside* `List`'s scope because the loop iterates the copy `List` returns; restructuring through `Registry.Update` or any registry-held callback would both add a registry→pool edge and deadlock against `Update`'s own no-re-entry rule; (b) **no shared mutable state escapes** — `List` returns a copy, `sessionModelHold.ModelList` hands back a per-call deep copy, and `turnbridge.MapEvent` allocates a fresh outer slice, so two concurrent enumerations for two connecting conns never share a backing array and the relay can marshal one while another enumerates; (c) **no goroutine is created**, so there is nothing to leak and nothing to join at shutdown — the closure is a synchronous call on a goroutine whose lifecycle the manager already owns. The `List`→`Get` window is the benign TOCTOU the resolver documents; a row deleted or rebound inside it resolves or refuses, and both are correct.
- **[Threat model alignment]** No findings on the mechanism; one documentation consequence, already owned. `docs/protocol-mobile.md` § Security model's relevant threats are all discharged by gates that exist before this code runs: a passive observer sees only Noise-sealed frames; an unpaired or revoked device never reaches `handleNoiseInit`'s success tail (device-token validation and `Registry.Reload` at handshake, #782); a non-interactive conn is withheld by `!s.interactive`. The one property this ticket makes newly true is that a connecting paired device receives the model menu of **every** conversation the daemon holds, not only the ones it created. That is consistent with pyrycode's stated multi-device model (paired devices share one daemon's control truth) and strictly less sensitive than what `OutstandingQueues` already enumerates daemon-wide (the user's queued message *text*), so it is accepted rather than gated — but it is named here rather than inherited silently, because no per-device conversation ACL exists at any seam and a future ticket adding one must know this path enumerates across it. Separately, merging this makes three passages of `docs/protocol-mobile.md` false in the client-facing direction; that correction is **OUT OF SCOPE** and needs a sibling slice blocked by this ticket (§ Out of scope) — PO has flagged it for filing twice.
