## Context

`pyry agent-run` on the headless stream path has never been measured with a command still running at trailer time. The ptyrunner reading is #1337's, taken live on 2026-08-06 against claude 2.1.220: **pyry declared the turn finished while the command it launched was still running**, on `run-running-at-trailer` / `admit-proof`, carried by pyry's own reap log.

That evidence class does not exist here. `streamrunner.Run` reaps only inside `cmd.Cancel`, which its own comment says never fires on a clean exit, so **a healthy run on this path writes no reap log at all**. `terminal_reason` is pyry's invention and claude's own `result` line carries no such key, so the trailer gate reads `gate-absent-reason-owes-none` rather than certifying a reason. And claude exits before the observation window, so any parentage-based view of the command goes blind — and blind reads exactly like a negative verdict.

What stands in its place is the pinned-pid sighting route: #1439's certified ordering, #1440's predicate, wired into the classifier's `gate-absent-reason-owes-none` arm by #1446 and separated into its three void cases by #1447/#1448. Its answer, `run-alive-at-sighting-by-ordering`, establishes that the command was still running **when the trailer was sighted on pyry's stdout** — a strictly weaker claim than #1337's aliveness-at-declared-finish, because no terminal reason is certified on this path and so no declared-finished instant exists. That gap is a finding to report, not a shortfall to close by wording.

Every instrument is shipped. Ten offline blockers landed it: the staging delta (#1349), the predicate (#1352), the arm (#1437, #1444, #1448), the gate's runner-path reading (#1452), and the gather's two route inputs and their byte sweeps (#1453, #1456, #1457, #1459, #1463). All are CLOSED. **This ticket supplies readings and adds no instrument.**

### The one design decision this spec makes

`finGatherInputs.Ordering` exists (#1462) and **no live caller can fill it.** `trailCertifyOrdering` needs `trailerSighted`; the only thing that sights a trailer is `trailWaitForTrailer`, and both of its non-test call sites report the sighting *after* the call the premise would have to be passed to. Recovering the premise with an earlier `trailWaitForTrailer` degrades the gather's own observation to `trailBoundFromStart` — a discriminator whose own doc says it bounds nothing — and that degraded observation is the one that fills the published `BoundFrom`, the `Staleness` and the gate. #1462's spec named this circularity and left it as "design work for a ticket that does not exist yet".

**The resolution is to certify AFTER the gather and to fill `trailRunReadings.Ordering`, never `finGatherInputs.Ordering`.** § 4 states it and argues it. This routes *around* the circularity rather than resolving it: the input field stays unfillable, its prohibition stands unchanged, and no shipped doc goes stale.

## Design

### 1. One new file, and its identifiers

`internal/e2e/realclaude/finding_stream_exit_path_probe_test.go`, `//go:build e2e_realclaude`.

Prefix `finStream`, verified free at `HEAD` with `git grep -o -h -E 'finStream[A-Za-z0-9_]*' -- '*.go'` → **0**; controls run with the same recipe: `finExit` → 35 (a prefix known to be present), `trailOrder` → 171, an absent prefix → 0. Re-run and record all three in the commit message: a grep that silently matched nothing reads exactly like a free prefix.

Two constants, **this file's own literals, derived from nothing**:

```go
const finStreamExitEnableEnv = "PYRY_PROBE_STREAM_EXIT_PATH"
const finStreamExitPyryExitDeadline = 120 * time.Second
```

- The env name is free against the seven shipped `PYRY_PROBE_*` names, and is deliberately **not** `PYRY_PROBE_EXIT_PATH_STREAM`: a name carrying another gate's name as a prefix makes a grep for either report both. Two gates, not one — an operator must be able to spend one live turn on one path without spending two.
- The deadline is a separate literal and **not** a reuse of `finExitPyryExitDeadline`, whose doc calls itself that file's own constant. Same value, same asymmetry argument (too short manufactures a `run-void-pyry-did-not-exit` on a healthy run and costs an operator round-trip; too long costs wall-clock on a run that already failed) — and separate so re-tuning one path cannot silently move the other. Same doctrine `finLiveStageStreamEnvDelta` follows against `finLiveStageEnvDelta`. Its doc must additionally name the one leg that is genuinely path-specific: pyry's own `cmd.Wait` on claude blocks on a pipe here rather than on process exit alone, bounded by `streamrunner`'s `WaitDelay` — see § Error handling.

### 2. The header comment — what it must argue, and what it must NOT copy

Follow the sibling's shape, **re-derive its content**. The sibling's central section argues that the reap log is the evidence and point-in-time reads are systematically late. On this path that argument is not merely different, it is inverted, and copying it across would ship a false claim. Required sections:

1. **What it is.** The headless `PYRY_USE_STREAMJSON=1` path and only that path; #1337 owns the ptyrunner default. Name that the two paths do not write the same trailer and do not present the same process tree at trailer time.
2. **It composes and publishes; it derives nothing.** `finLiveRunStage` → `finGatherReadings` → `trailCertifyOrdering` → `finExitClassify` → `finRecordBuild` → `finWriteArtifacts`. Every outcome consumed as returned.
3. **Why the sighting route is the evidence, and why the reap log is structurally absent.** `streamrunner.Run` reaps only inside `cmd.Cancel`; a clean exit therefore writes no reap line, so the attribution leg is *empty by construction* rather than merely late — it is not a weaker version of #1337's evidence, it is a different one. State that the substitute is the ordering argument, and state the ordering explicitly: **the trailer's appearance on pyry's stdout precedes pyry's exit, which precedes the pinned-pid re-read.** The rig's *poll* is later than all three and that is not a defect — the premise is that the trailer WAS sighted, and bytes reach the buffer only while pyry is alive, so a trailer found in the buffer after pyry exited was necessarily written before pyry exited.
4. **What this path's evidence cannot say.** No terminal reason is certified here, so there is no declared-finished instant, so `run-running-at-trailer` is not reachable and must not be approximated in prose. The strongest available claim is about the trailer's SIGHTING.
5. **Captured-bytes discipline.** Artifacts go into a public issue. **No `ps -E`, no `-Eww`, anywhere** — those dump `CLAUDE_CODE_OAUTH_TOKEN` and `ANTHROPIC_API_KEY`; `pinReadState`'s pid-pinned lookup is `pid=,ppid=,stat=` by construction and is the only `ps` this file reaches. The raw trailer line is unreachable by the shape of the gather's third return, not by discipline. Name every value the log channel carries and why each is safe (§ 7).
6. **It asserts almost nothing.** One `t.Fatalf` of its own (`os.MkdirTemp`). The three abort paths inherited from `finLiveRunStage` are named, not re-guarded.
7. **One skip gate, not two.** The reach probe's second gate is not copied, for the reason `finLiveRunStage`'s SITE A already records: this run's delta names `PYRY_USE_STREAMJSON` explicitly, so the ambient loses either way. The observed-path reading is the real guard and is strictly stronger than an env check.
8. **What this file ships offline.** One trap, § 5. `go vet` and `staticcheck` under `make check` run *without* `-tags e2e_realclaude` and analyse nothing here; `make e2e-realclaude` is the gate.

The header may be shorter than the sibling's. Do not re-argue anything a shipped symbol's own doc already argues — cite the symbol.

### 4. The body — `finStreamExitRunProbe(t *testing.T, artifactDir string)`

**The order is load-bearing at four points.** Straight-line, no early return, no disposition of its own.

1. **Stage.** `h := finLiveRunStage(t, finLiveStageStreamEnvDelta())`. Everything after this runs with the FIFO write end **still held**: `holdProbeFIFO` releases only in the `t.Cleanup` it registers itself, which by construction runs after this body returns. This rig registers no cleanup at all, so it cannot disturb the driver's LIFO ordering. This is an inversion of the neighbouring `background_reach_probe_test.go` precedent, which releases the FIFO first — say so, so a reader does not read it as a copy.

2. **Wait for pyry's own exit — in the body, never in a cleanup.** A receive on `h.PyryExited` against `finStreamExitPyryExitDeadline`; `exitCode` starts at `pinExitStatusUnknown` and **the read of `h.ExitStatus` sits inside the receive arm**. That channel's close is the only happens-before edge with the driver's `cmd.Wait` goroutine; any shape that evaluates the field outside the arm — hoisting it, or passing it to a helper alongside the bool — is a data race `go test -race` will flag. There is deliberately no such helper. The timeout arm leaves `pinExitStatusUnknown` in place, which is what keeps a non-exiting run from publishing `exit_code: 0`.

3. **The claude-still-alive reading**, `pinReadState(h.ClaudePID).Verdict` and nothing else — never a raw `ps` column, because this value crosses the gather unvalidated, is republished as `claude_state` and is quoted into a published Detail. Taken here, after the exit wait.

   **Its meaning is re-derived for this path and is not the sibling's.** On ptyrunner the expected value is `no-such-process` because `sess.Close()` SIGTERMed claude, and the reading is blind to the reap window. Here claude exits *on its own* after writing its `result` line, before pyry returns — so the reading is expected to be `no-such-process` for a different reason, and what it decides is **whether any parentage-based view of the command could have been informative at all**. It is a race, which is exactly why it is recorded per run rather than assumed. It is corroboration and never the finding.

4. **The pinned-pid re-read.** A **second** `pinReadState` call and never a reuse of step 3's: that one is over `h.ClaudePID`, naming claude itself; this one's pid comes from the during-turn pinned set. Same instant, different pid — a reuse reads correct and answers about the wrong process.

   ```go
   var pinnedPid pinStateOutcome
   if len(h.Pin.PGIDs) > 0 {
       pinnedPid = pinReadState(h.Pin.PGIDs[0])
   }
   ```

   The first entry, for the reason the gather's field doc gives: `finLivePinReduce` projects one entry per FIFO-matched row with duplicates deliberately intact, so a healthy run's set is two entries naming one detached group. **An empty set takes no read at all** — `pinReadState(0)` answers `pinStateInstrumentFailed` and so claims an instrument ran, where the zero `pinStateOutcome` carries `Verdict ""`, a shape the route's pid-read-failed reason already names. No dedupe, no cardinality assertion — that is the staging gate's count arm's business.

   This discharges AC2's three sub-clauses structurally: the pid was pinned during the turn while the command was still reachable, matched on the FIFO path in the full argv by the driver's own scan; the re-check is a lookup **for that pid alone** and requires no descendant relationship; and `pinReadState`'s closed set separates `pinStateRunning` from `pinStateExitedNotReaped`, because `ps` lists a zombie as a row. **`probeHasCommand` is not used** — it matches on `filepath.Base(argv[0])`, so the held command records as `cat`, and it is scoped to descendants, the one scoping guaranteed to fail here.

5. **One `finGatherReadings` call**, with `Ordering` left unfilled and a comment saying why (§ 4a). The other fields exactly as the sibling fills them, each keeping its argument:
   - `Stdout: h.Stdout` — the live buffer; `Bytes()` returns a copy under a mutex.
   - `Needles: []string{h.FIFOPath}` — **the FIFO path alone**, never the driver's two-needle list: this gather has no `finLivePinReduce`, so the claude needle would put claude's own row into the classifier's match-count arms and into the published liveness list.
   - `Stderr: h.Stderr.Bytes()` — read after the exit wait. On this path it is expected to carry **no reap line**, and that is the point rather than a defect.
   - `Pinned: h.Pin.PGIDs` — already `[]int`; nothing is converted here.
   - `PyryExited`, `ClaudeState` — as measured.
   - `RunnerPath: tdnRunnerFromArgv(h.Pin.ClaudeCommand)` — **reduced at the call site and never inside the gather**, because the argv is verbatim and this value is republished as `runner_path`. Never `reachRunnerPathFromArgv`: it keys on `--append-system-prompt-file`, which both builders emit, so it would label a correctly-wired stream run `ptyrunner`. An empty `ClaudeCommand` is admissible and lands on the shipped `indeterminate` answer — ambiguity, never a wrong-path claim. **This is the reading that makes `trailGateAbsentOwesNone` reachable at all**, and it is the same reading the record's `runner_from_argv` is built from, so record and gate cannot disagree (AC4).
   - `PinnedPid: pinnedPid` — crosses whole.

#### 4a. The ordering, certified after the gather

```go
readings.Ordering = finStreamCertifyOrdering(sighting.State, pyryExited)
```

Placed **immediately after the gather and strictly before `finExitClassify`**. The comment must carry four things, and each is load-bearing:

- **Which field this is.** It fills `trailRunReadings.Ordering`. `finGatherInputs.Ordering` is left at its zero and **must stay** that way: that field's own doc says no live caller fills it and none may be added, and this ticket does not add one. The circularity it names is real and is routed around here, not resolved — a reader following this ticket must not conclude the input field became fillable.
- **Why after and not before.** The `trailerSighted` premise is only knowable from the gather's own third return. Recovering it with an earlier `trailWaitForTrailer` would degrade the gather's own observation to `trailBoundFromStart` — the discriminator whose doc says it bounds nothing — and that degraded observation is what fills the published `BoundFrom`, `Staleness` and the gate. A mis-report, not a cost.
- **Why this is a fill and not a re-derivation.** The gather left the field zero because it could not be given the input; nothing is overwritten, nothing the gather decided is re-decided, and the value comes from `trailCertifyOrdering`'s own output — the field's one admissible producer — and never from a `trailOrderResult` literal.
- **Why the ordering premise is satisfied even though the poll is last.** Bytes reach `h.Stdout` only while pyry is alive, so a trailer the gather finds after pyry exited was written before pyry exited: trailer → pyry's exit → the pinned-pid read, in that order, and the read at step 4 happening earlier in *program* order than the poll changes none of it.

#### 4b. Classify, build, write

`finExitClassify(h.Staging, readings)` — **reused from the sibling file, not copied.** Staging is decided first; a run that failed to stage is never passed to the classifier, because an unstaged run's post-trailer scan still parses a healthy process table, matches nothing, and would reach an ANSWER about a run in which no command ever existed.

`finRecordBuild` exactly as the sibling calls it: `Rows: h.Pin.Rows` (the during-turn pin, never a second scan), `Liveness: readings.Liveness`, `Attribution: attribution`, `Trailer: finTrailerBuild(outcome, sighting)` (from the gather's third return, never a second `trailWaitForTrailer`), `RunnerFromEnv: reachRunnerPathFromEnv(h.EnvDelta)` — the real delta, so this reads this run rather than the operator's shell — `ClaudeCommand: h.Pin.ClaudeCommand` whole and unexamined, `ClaudeVersion: h.ClaudeVersion`. Then `finWriteArtifacts(t, artifactDir, rec)`.

The same argv is therefore reduced twice — once at the gather's call site and once inside the builder — and the two are deliberately not hoisted into one, for the reason the sibling records: `tdnRunnerFromArgv` is pure over the string, so they agree by construction, and sharing would mean changing one of two shipped signatures.

### 5. The one offline trap

The composition is live-only, so the file ships exactly one offline test — over the only decision this file introduces:

```go
func finStreamCertifyOrdering(sightingState string, pyryExited bool) trailOrderResult
```

It returns `trailCertifyOrdering(sightingState == trailSeen, pyryExited, true)`.

**The parameter is the scan state and never a `finSighting`** — the same narrow-the-parameter enforcement `trailCertifyOrdering`'s own doc makes for its three bools: a `finSighting` carries `TerminalReason`, `StopReason`, `Subtype` and `KeyNames`, none of which this decision needs and none of which a denylist would catch.

**The `true` is structural and is not a guess.** `holdProbeFIFO` keeps the write end, hands back a receive-only channel with no release path of its own, and closes its release channel only in the `t.Cleanup` it registers itself; this rig registers no cleanup; therefore the wait in the body is held for its whole duration by construction. `trailCertifyOrdering`'s doc sanctions exactly this: "a caller passing `holdHeld=true` is asserting something it can know." The doc comment must also name the consequence of getting it wrong, because that is the threat #1462's security review left open: a probe that *guessed* it would publish `run-alive-at-sighting-by-ordering` on a run where the hold was released, and a released hold means the pinned pid could have been retired and reissued between the two instants — so the artifact would name a process it cannot show is the same one.

`TestFinStreamCertifyOrderingMapsThePremises` — a table over the three shipped scan states × the two exit outcomes, as bullet-pointed scenarios; the developer writes them in the package's table idiom:

- `trailSeen` + exited → `trailOrderCertified`
- `trailSeen` + not exited → `trailOrderVoidNoExit`
- `trailAbsent` + exited → `trailOrderVoidUnsighted`
- `trailAbsent` + not exited → `trailOrderVoidUnsighted` (sighting outranks exit)
- `trailAborted` + exited → `trailOrderVoidUnsighted`
- `trailAborted` + not exited → `trailOrderVoidUnsighted`

Plus one assertion over all six rows: **no row answers `trailOrderVoidUnheld`**, stated in the test's own prose as what pins the third argument. That single clause is what makes the trap discriminating rather than decorative — it goes red on a `false`, and the table goes red on a swapped premise pair or on a `sightingState != ""` test in place of the `== trailSeen` one.

The record publishes neither the gate value, the classifier Detail, the staging result, nor the ordering, so those reach an operator through `t.Logf` — which keeps the two proven artifact files exactly as the shipped writer produces them rather than growing a second file-writing surface no sweep covers.

4. **Pyry's exit** — `exited_within_<deadline>`, the recorded `exit_code`, and which of the three exit notes applies (exited cleanly / did not exit / exited with no clean code, a shape a signalled process also produces). Name `run.json`'s `trailer_keys` as the auditable evidence — the names claude emitted, names only, never values.

State the path-specific asymmetry against #1337: there the post-trailer scan found 0 matches because the reap had already killed the group, and here nothing reaps on a clean exit, **so a match is the predicted reading rather than an anomaly**. Where the classifier was consulted, name `classified.Route` and `classified.RouteReason` — the evidence-route fields are what keep this answer apart from #1337's.
7. **The finding, in one sentence**, keyed on the classifier's value. Counts, closed-set values and `terminal_reason` only — never `stop_reason`, which is model-influenced and carried uncapped by design, and never any sub-record's Detail. Three arms:
   - **not consulted** → NO CLAIM IS MADE; the run did not stage (naming the staging value), so no reading here is about a held command.
   - **`trailOutcomeAliveAtSightingByOrdering`** → the finding: **the command was still running when the trailer was sighted on pyry's stdout.** It must then state, in the same breath, all three of AC3's clauses: that the exit code alone does not separate a completed run from a terminated one (both exit 0, and since #1388 a complete result trailer additionally discards claude's non-zero status); that what carried it was **the certified ordering of the three instants and the pinned-pid re-read, not a trailer field**; and that **no declared-finished instant exists on this path**, so the stronger aliveness-at-declared-finish claim #1337 made is unavailable here — recorded as absent, never restated in weaker words.

## Concurrency model

No goroutine is created here. One is inherited: the driver's `cmd.Wait` goroutine, which writes `h.ExitStatus` and then closes `h.PyryExited`. That close is the only happens-before edge; the exit-status read sits inside the receive arm for that reason and for no other. `h.Pin` is written before the handle is returned and is never touched again, so reading `h.Pin.PGIDs` above the select would be early rather than racy — it is nonetheless taken after the wait, because the route's claim is about a pid re-read at an instant later than pyry's exit.

Shutdown: this rig registers no `t.Cleanup`. The driver registers its defence-in-depth SIGKILL **before** `holdProbeFIFO`, so LIFO releases the FIFO first and pyry gets a real chance to exit on its own. Do not disturb that order; inverting it has no symptom and yields a green run in which the rig, not pyry, produced the exit.

`go test -race` must pass on the package with `-tags e2e_realclaude`.

## Error handling

Failure modes are **recorded, not raised** — a probe that turns an unexpected reading into a red test loses the reading. One `t.Fatalf` of this file's own: `os.MkdirTemp`. Three abort paths are inherited from `finLiveRunStage` and are not re-guarded: pyry never spawning a claude child, no `system/init` session id, and `ReadJSONL`'s fatal on an unreadable transcript.

Two path-specific hazards to expect and to record rather than to repair:

- **`ExitStatus` may be non-zero on a correct, complete run.** `streamrunner` sets `cmd.Stdout` to a non-`*os.File` writer, so `os/exec` creates a pipe and pyry's own `cmd.Wait` on claude blocks until every dup of claude's stdout write end is closed — including any held by the detached Bash group. It is bounded by `WaitDelay`; if it fires, `Run` returns the wait error and `runAgentRun` maps it to a non-zero exit. `PyryExited` still closes, and well inside this file's deadline. **Whether it fires is not decidable offline and this run is the first measurement.** If the recorded `exit_code` is non-zero on an otherwise healthy run, that is this reading, not a defect — record it and say which mechanism it is consistent with. It changes no verdict: the discriminator is the trailer and the ordering, never the exit status.
- **A `terminal_reason` present on this path** means pyry's idle-stall watchdog fired and synthesised the trailer. The gate answers `trailGatePresentOwesNone` and the classifier `run-void-reason-not-owed-by-path`. Not a finding about the exit path; record it as a run to re-take.

**Findings:**

- **[Trust boundaries]** No new boundary. Every untrusted input crosses a shipped reduction before this rig sees it: model-controlled transcript bytes are reduced by `finLiveAssembleStaging` inside the driver; the trailer is reduced to `finSighting`'s scalars plus bounded key names inside the gather, which withholds both `trailScanResult.Line` and the `*resultTrailer` by the shape of its third return; ambient argv is reduced by `tdnRunnerFromArgv` at the call site and by `finRecordBuild` internally. - **[Tokens, secrets, credentials] MUST-NOT-REGRESS, held structurally.** The realistic leak is an operator's `CLAUDE_CODE_OAUTH_TOKEN` / `ANTHROPIC_API_KEY` reaching a public issue through a process-table read. `ps -E` and `-Eww` are forbidden by the header and appear nowhere; `pinReadState`'s columns are `pid=,ppid=,stat=` by construction; the pinned-pid re-read is a lookup for one known pid and is not a reason to persist a full-table command column. The log channel is enumerated field-by-field in § 7 and every value on it either has a passing byte sweep or is an int / closed-set constant. The `%v`-on-a-struct prohibition is stated because that is the concrete mechanism by which `h.Pin.Rows`' verbatim argv would print from a line reading as ordinary debug formatting.

The residual is that the artifacts persist until the operator removes them — accepted, since their whole purpose is to be pasted, and their content is what the byte sweeps constrain.
