## Context

`BeginRotation` arms the gate; `setStdin` disarms it for **any** child that binds. The arm is generation-stamped (`rotateGen`) so a losing rotation's `abort` cannot clear a winner's arm, but nothing stamps the release side. Between the arm and the rotation's own `RestartFresh` sits all of `Pool.RotateForNewSession` — mint, re-key, register, an fsync'd atomic write, then the `session_transition{clear}` fan-out. Any child that binds inside that gap ends a window it has no relationship to, and `RestartFresh` then kills it. A turn accepted on the strength of the already-fired clear is written into that child, msgqueue reads the successful write as a commit, drops the head, and the turn is gone silently — #1330's loss reached through a different door.

The obvious fix — disarm only when this spawn consumed `rotatePending` (`beginSpawn`'s `forceFirst`) — is a **one-shot token** and fails AC 2: `beginSpawn` consumes `rotatePending` unconditionally, so a successor spawn that dies during setup (`spawnAndWait` returning `started == false`, `setStdin` never reached) spends the authorisation, and every later child binds unauthorised. The gate wedges permanently and the conversation refuses every turn until some unrelated later rotation. The design below uses a **monotonic threshold** instead, which every later spawn satisfies and no spawn consumes.

This work does not warrant an ADR: it corrects the release half of the mechanism ADR-less #1330 introduced, and the package overview already carries that mechanism's prose.

## Design

### The rule

> A binding child may disarm the gate **only if its spawn was set up after a `RestartFresh` that landed after the standing arm was placed.**

Two pieces of state express it, one under each existing mutex, plus a per-spawn snapshot threaded from setup to bind.

| State | Mutex | Meaning |
|---|---|---|
| `freshSeq uint64` | `restartMu` | Monotonic count of `RestartFresh` rotations that have landed. Process-local; never persisted, serialised or logged. |
| `armFreshSeq uint64` | `mu` | The `freshSeq` value observed when the **standing** arm was placed. Meaningful only while `rotating` is true. |
| `freshSeq` (per spawn, a value) | — | Snapshot taken in `beginSpawn`'s existing `restartMu` section, threaded to `setStdin`. |

`setStdin` disarms iff `spawnFreshSeq > armFreshSeq` — strictly greater, so a spawn set up before the arm's partner `RestartFresh` reads equal and is refused.

Both new fields join the charter of the mutex that already guards their sibling. `mu`'s statement — "which child, if any, may receive a turn" — covers `armFreshSeq` exactly, and it must be written in the **same acquisition** that sets `rotating = true`, or a bind landing between them would compare against a retired arm's threshold. `restartMu`'s "one acquisition per spawn setup" (#1481) is preserved: the snapshot is a read inside the section that already exists, not a new one.

### Signature changes (five call sites, all in-package)

- `beginSpawn(ctx, firstRun) (iterCtx, cancel, args, forceFirst, freshSeq)` — one more named return. Callers: `Run`, plus `TestRunner_BeginSpawn_FirstSpawnResumesExistingTranscript` and `TestRunner_RestartFresh_EmptyIDIsNoOp`, which absorb it with `, _`.
- `spawnAndWait(ctx, args, freshSeq)` — one more parameter, passed straight through. One caller: `Run`.
- `setStdin(w, freshSeq)` — one more parameter, the authorisation input. One caller: `spawnAndWait`.

No exported signature changes, so `streamRunner`, `sessions.Runner` and `beginRotationOrNoop` are untouched.

### Behaviour, method by method

- **`RestartFresh`** — `freshSeq++` inside its existing `restartMu` section, alongside `sessionID` and `rotatePending`. The empty-id early return stays above the section and therefore does **not** bump (§ Error handling).
- **`beginSpawn`** — reads `freshSeq` into the returned value inside its existing section. Nothing new is consumed or cleared.
- **`BeginRotation`** — reads the current `freshSeq` under `restartMu`, **then** takes `mu` and sets `rotating`, `rotateGen++` and `armFreshSeq` together. Two leaf acquisitions, **sequential and never nested**; the read must come first (§ Concurrency).
- **`setStdin`** — publishes the handle unconditionally; clears `rotating` only when authorised.
- **`takeStdin`**, **`turnTarget`**, **`WriteUserTurn`**, the `abort` closure — unchanged. `abort` stays `rotateGen`-stamped and leaves `armFreshSeq` alone; a stale threshold behind a disarmed gate is inert, and the next arm overwrites it.

### Why the snapshot is taken at spawn **setup**, not at bind

Reading `freshSeq` inside `setStdin` instead would be a different, wrong rule. The crash-respawn's `beginSpawn` runs before `RestartFresh` but its `setStdin` can run after: it would then read the bumped value, disarm, and be killed moments later by the very `RestartFresh` that bumped it. AC 1's wording — "a spawn set up *before* that rotation's `RestartFresh` landed" — is a statement about setup time, and only a snapshot taken in `beginSpawn` can carry it.

### Rejected alternatives

- **Gate on `forceFirst`.** Fails AC 2 (one-shot token; see § Context).
- **Move `rotating` under `restartMu`** so the arm and the counter share one acquisition. Reopens #1330: `turnTarget` must answer "gated?" and "which stdin?" under one lock, and `stdin` cannot leave `mu`.
- **`freshSeq` as an `atomic.Uint64`,** so `BeginRotation` needs no `restartMu`. Rejected: correctness would then rest on real-time ordering between an unsynchronised load and a mutex-protected store, which Go's memory model does not promise. `restartMu` gives a genuine happens-before for one extra leaf acquisition.
- **Re-read `freshSeq` after arming and re-stamp under the arm's own generation,** closing the residual window in § Concurrency. Declined per evidence-based fix selection: it adds a retry loop for a few-instruction residue of a gap that has never been observed even in its current, far wider form.

## Concurrency model

No new goroutines, no new channels, no change to the shutdown sequence.

**Lock discipline.** `mu` and `restartMu` are both leaves and **no path in this package holds two of them at once** — that invariant is what makes the ordering safe, and the fix must not break it. `BeginRotation` becomes the second method (after `WriteUserTurn` → `turnTarget` then `liveSessionID`) that takes both, sequentially. Its doc comment currently claims "one leaf-mutex acquisition"; update it to say two, taken in order and never nested, and say why the `restartMu` read comes first. There is no lock-order cycle today because nothing nests; record in that same doc that if nesting ever becomes unavoidable the order is `restartMu` → `mu`, matching the sequence this method establishes, so a future `mu` → `restartMu` nesting is recognisable as the inversion it would be.

**Why the ordering works (AC 1).** `RestartFresh`'s bump and `beginSpawn`'s snapshot happen in sections of the *same* mutex, so they are totally ordered with the `rotatePending` handoff — there is no skew window between them:

- Spawn's section **before** `RestartFresh`'s → snapshot equals `armFreshSeq` → refused. This is the filed crash/backoff respawn, and equally a `Restart`-driven respawn (`Restart` and `SetSpawnArgs` never bump).
- Spawn's section **after** `RestartFresh`'s → snapshot is strictly greater → authorised. This is the successor, and every spawn after it.

**Why the arm reads before it arms.** `armFreshSeq` and `rotating` are published in one `mu` acquisition, so no bind can observe an armed gate carrying a previous arm's threshold. Arming first and reading second would open exactly that window.

**Residual window, and it must be documented honestly.** Between `BeginRotation`'s `restartMu` read and its `mu` acquisition, a *different* frame's `RestartFresh` could land **and** a spawn could take its snapshot; that spawn's later bind would then clear the arm being placed. Closing it would require holding both mutexes at once, which the two-mutex charter forbids. It is unreachable from a single `new_session` frame — `startFreshRunner` calls `BeginRotation` and `RestartFresh` in program order on one goroutine — so it needs two concurrent frames interleaving inside a few instructions. The documented two-frame gap in its *stated* shape ("frame 1's respawn is still pending when frame 2 arms") **is** closed: frame 2's arm reads the already-bumped counter, so frame 1's successor snapshot is not strictly greater and cannot disarm it.

**No new TOCTOU.** The check and the mutation (`if authorised { r.rotating = false }`) are the same `mu` acquisition that publishes `stdin`.

## Error handling

- **Successor spawn fails during setup** (`StdinPipe` / `cmd.Start`, `started == false`). `setStdin` never runs, and nothing was consumed: `freshSeq` still exceeds `armFreshSeq`, so the next child to bind disarms. AC 2 holds by construction. Note that `rotatePending` *is* spent by that failed spawn — existing #1481 behaviour, and precisely why the authorisation must not ride on `forceFirst`.
- **`rotate()` fails.** Unchanged: `startFreshRunner` runs the `rotateGen`-stamped `abort`, which clears the arm and cannot clear a later one.
- **`RestartFresh("")`.** The early return stays above the `restartMu` section, so no bump: `freshSeq` counts rotations that landed, not calls made. Reachability: `startFreshRunner` calls `RestartFresh` only with `rotate()`'s success value, and `RotateForNewSession` returns `("", err)` on every failure path and a `NewID()`-minted id otherwise, so no production path pairs an arm with an empty-id call. Bumping anyway would authorise a spawn that succeeds no rotation — AC 1's own failure shape — so the conservative side is the correct one. If a pool bug ever mints an empty id, the arm outlives it until the next rotation; that is a pool-layer defect and belongs there.
- **Counter overflow.** `uint64`, monotonic, process-local. Not a reachable concern; state it in the field doc as `rotateGen`'s doc already does.
- **`rotate()` that never returns.** An arm whose partner `RestartFresh` never lands — `RotateForNewSession` blocked forever inside `saveLocked`'s fsync on a wedged filesystem, so neither the bump nor `abort` ever runs — leaves the gate armed, where today an unrelated respawn would drop it. That unearned release is the defect this ticket removes, so the change is deliberate: turns are then **refused retryably** (`ErrNoLiveChild`, msgqueue re-attempts against its 2 m give-up and surfaces a visible failure) instead of being written into a doomed child and silently dropped. Refusal is the safer failure, and the trigger is a wedged rotation that has not completed — outside AC 2's "once the rotation has completed".
- **No new log records, and none inside `setStdin`.** The gated-refusal record in `WriteUserTurn` is unchanged: still `Info`, still naming only the event and the runner's own session id. Do not log `freshSeq`, `armFreshSeq`, payload bytes or `conversationID`. Explicitly do **not** add a record explaining a refused disarm inside `setStdin` — it holds `mu`, so a slow handler would block the Run goroutine under a leaf mutex (the hazard `WriteUserTurn`'s own comment describes for the mirror case), and a `Debug` record anywhere in the daemon's stderr defeats #1330's e2e AC-1 instrument guard. If the release path needs a diagnostic, it belongs above the acquisition in `spawnAndWait`, at `Info`.

## Testing strategy

All rows live in `internal/streamsup/runner_test.go`, run under `go test -race`, and use only the existing harness. No `time.Sleep` calibrated against the window — every wait is a happens-before edge (`waitSpawn` receives fire from `onSpawn`, which runs *after* `setStdin`, so a receive means "the gate's release point has run for that child").

**Vacuity guard, mandatory in every row.** `WriteUserTurn` returns `ErrNoLiveChild` for both refusals — gated, and no child bound — so a row asserting only `errors.Is(err, ErrNoLiveChild)` passes under the mutant whenever no child happens to be live. Assert through `turnTarget`'s `gated` return, as `TestRunner_BeginRotation_AbortIsGenerationStamped` does.

### Row (a) + Row (b) — one run, two subtests

One test function, one `echo_lines` runner via `runInBackground`, two sequential `t.Run` subtests. Subtests are load-bearing rather than cosmetic: under the mutant row (a) must fail while row (b) still executes and passes, which is exactly the per-row evidence AC 4 asks for and which a single flat function cannot produce.

Setup (outside the subtests): `helperRunCfg(t, "echo_lines", …)`, an `onSpawn` that does a non-blocking send on a buffered `spawned` channel, `waitSpawn` for the first spawn, then `r.BeginRotation()`. `echo_lines` stays alive until it is killed, so no respawn can race the arm — the arm is strictly before any later `beginSpawn`.

- **(a) "an unauthorised bind leaves the gate armed"** — `r.Restart(nil)` kills child 1 and (hint in hand) relaunches with no backoff; `waitSpawn` for child 2. Then assert, in order:
  - `r.Stdin() != nil` — a child is demonstrably bound, so nothing below can collapse into the pre-existing no-live-child refusal.
  - `_, gated := r.turnTarget()` reports `gated` — the discriminator, and the assertion the mutant reddens.
  - `r.WriteUserTurn(ctx, "c1", []byte("gate-probe-armed"))` returns `ErrNoLiveChild` — the caller-visible contract.

  This row is AC 1's `Restart`-driven clause as well as AC 3(a).

- **(b) "the successor bind drops the gate"** — continues the same run: `r.RestartFresh(rotatedSessionID)`, `waitSpawn` for child 3, then assert `r.WriteUserTurn(ctx, "c1", []byte("gate-probe-fresh"))` returns nil and `waitForContains(out, "gate-probe-fresh")`. Add `strings.Count(out, "READY") == 3` **after** that wait — three children existed, the first two are dead, so the echo can only be the successor's. That is the "observably lands in the successor child" evidence.

- **Parent-level, after both subtests:** `out` must not contain `gate-probe-armed`. Place it here, not inside (a): the bytes-never-reached-a-child assertion needs a happens-after edge, and (b)'s successful `waitForContains` supplies a deterministic one — child 2's `cmd.Wait` returned before child 3 spawned, and `Wait` returns only after its stdout copier drained. Putting it inside row (b) would redden (b) under the mutant and break AC 4's green-on-both requirement; a `time.Sleep` settle inside (a) would trade determinism for nothing.

### Row (a2) — the filed crash/backoff respawn

A separate compact function, `crash` mode with `BackoffInitial`/`BackoffMax` in the low milliseconds. **Arm inside `onSpawn` under a `sync.Once`** (the shape `TestRunner_RestartFresh_RotatesThenResumesNewID` uses for `RestartFresh`) — not from the test goroutine after `waitSpawn`. With `crash` the child is gone in 20 ms, so a test-goroutine arm can land after the respawn already bound, and the row would then assert on a bind that predates the arm: green on both trees, proving nothing. Arming inside the first spawn's `onSpawn` puts the arm strictly before child 2's `beginSpawn` by program order on the Run goroutine.

Then `waitSpawn` twice (first spawn, crash respawn) and assert `turnTarget` reports `gated`. Do **not** assert `r.Stdin() != nil` here — the crash child may already be gone, and `gated` is non-vacuous on its own: under the mutant child 2's `setStdin` cleared `rotating` before the second `waitSpawn` returned, so the read is deterministic in both directions.

### Discrimination evidence (AC 4) — run both trees, record both

Mutant: in `setStdin`, replace the authorised clear with the unconditional `r.rotating = false`. The `freshSeq` parameter then goes unused, which is legal for a Go parameter, so the mutant is a one-line edit that still compiles.

Run it with an overlay — no worktree writes, so the shipped tree is never dirtied:

## AC 5 — routed to the documentation phase, not the developer

AC 5 asks for three corrections in `docs/knowledge/features/streamsup-package.md`. **That file is not a developer deliverable on this pipeline** — the documentation phase is its sole writer, and the developer's worktree may mutate only code, tests and this spec. Folding a knowledge-doc edit into the implementation budget is a named budget-exhaustion failure (#471, #478). It also avoids a merge conflict: in-flight `feature/1504` already touches this same file, and the documentation phase runs serially on merged `main` where `feature/1482` never will.

So the developer writes none of it. The documentation phase applies the following, and each site must state the shipped rule **and** why it is load-bearing:

1. **The *"Known accepted gap, not fixed … the release side is not generation-aware"* paragraph** — do not delete it; **correct** it. The release side is now authorised: `setStdin` clears `rotating` only for a spawn set up after a `RestartFresh` that landed after the standing arm, carried by a monotonic `freshSeq` snapshot rather than a one-shot token (a token would wedge the gate when the successor spawn dies in setup). The two-frame interleaving the paragraph describes **is** closed in its stated shape, because frame 2's arm captures the already-bumped counter. Say plainly what is **not** closed: the few-instruction window inside `BeginRotation` between its `restartMu` read and its `mu` acquisition, unreachable from a single frame, left open because closing it would require holding both leaf mutexes at once.
2. **The sentence "`setStdin` clears `rotating` in the same acquisition that publishes the new handle"** — still one acquisition, but the clear is now conditional on the spawn's authorisation. Keep the `takeStdin` contrast; it is unchanged.
3. **The bullet "On spawn: `setStdin(stdin)` publishes the new handle"** under "Held-open stdin" — now `setStdin(stdin, freshSeq)`; the handle is published unconditionally and the gate is released only when that spawn is the rotation's successor or later.

## Open questions

1. **Naming.** `freshSeq` / `armFreshSeq` are the spec's names. If the developer finds something that reads better beside `rotateGen` and `rotatePending`, rename freely — the semantics are the contract, not the identifiers. Keep them distinct from `rotateGen`, which stamps arms and is a different axis.
2. **`beginSpawn`'s fifth return value.** Kept as a plain named return for the smallest diff and because it keeps #1481's single-acquisition read visible at the call site. If it reads badly, a small `spawnInputs` struct is an acceptable substitute — but do not move the snapshot out of the existing `restartMu` section to get it.
3. **The residual `BeginRotation` window** is deliberately left open (§ Concurrency). If evidence of a two-frame loss ever appears, the fix is a re-read-and-re-stamp under the arm's own `rotateGen`; that is a new ticket, not a widening of this one.

## Security review

**Verdict:** PASS

**Findings:**

- **[Trust boundaries]** No MUST FIX. The boundary — relay-delivered payload bytes → which child process receives them — stays exactly where #1330 put it, in `turnTarget`'s single `mu` acquisition, and this change only narrows who may end a refusal. Payload bytes never reach the authorisation: `freshSeq` and `armFreshSeq` are process-local counters minted by `RestartFresh` calls, never derived from, compared against, or influenced by wire data. A remote `new_session` frame does drive the counter (via `startFreshRunner`), but only after `beginRotationOrNoop` has already placed that frame's own arm, and the arm reads the counter *before* its partner bump — so a frame can never invalidate its own arm.
- **[Concurrency]** SHOULD FIX, addressed in the spec rather than deferred: the design adds a second mutex to `BeginRotation`, which previously took one. Addressed three ways in § Concurrency — the acquisitions are sequential and never nested, the `restartMu` read is specified to come *before* the `mu` arm (arming first would publish `rotating` beside a retired arm's threshold, a real disarm-by-stale-comparison bug), and the doc must record `restartMu` → `mu` as the order should nesting ever be introduced. The check-and-mutate in `setStdin` is one acquisition, so no TOCTOU is added. Both counters are mutex-guarded and every row runs under `-race`.
- **[Concurrency — residual]** ACCEPTED, documented, never worse than today. The window between `BeginRotation`'s counter read and its arm cannot be closed without holding both leaf mutexes at once. Its worst outcome is precisely the pre-fix behaviour for one interleaving, it is unreachable from a single `new_session` frame (`startFreshRunner` calls both in program order on one goroutine), and it needs two concurrent frames to interleave inside a few instructions. AC 5's doc correction is required to state it rather than claim a clean close.
- **[Availability / denial of service]** ACCEPTED, stated in § Error handling. Authorising the disarm removes an unearned release valve: an arm whose partner `RestartFresh` never lands now holds. The reachable trigger is a `rotate()` wedged in `saveLocked`'s fsync — a rotation that has not completed — and the resulting failure is a retryable `ErrNoLiveChild` that msgqueue surfaces, not the silent payload loss the valve currently trades for. A `new_session` flood can keep the gate armed, but that is unchanged by this fix (every `BeginRotation` re-arms today too) and each arm is still released by its own successor.
- **[Error messages, logs, telemetry]** SHOULD FIX, folded into § Error handling. The obvious developer instinct — log the refused disarm inside `setStdin` — is barred twice over: it holds `mu`, so a slow `slog` handler stalls the Run goroutine under a leaf mutex, and a `Debug` record anywhere in the daemon's stderr defeats #1330's e2e AC-1 instrument guard. Neither counter may be logged; the unchanged gated-refusal record in `WriteUserTurn` still names only the event and the runner's own session id, never `conversationID` and never payload bytes.
- **[Network & I/O]** No findings. No new network surface, no reads, no size caps to set. The refusal keeps returning the existing `ErrNoLiveChild` rather than a new sentinel, so `TestRelayV2_StreamNewSessionRotatesAndRestartsFresh`'s contract check — stream `WriteUserTurn` returns only `ErrNoLiveChild`, `turncommit.ErrDropped` or nil — still holds. A new error value would have broken it silently.
- **[Subprocess / external command execution]** No findings by construction: argv is untouched. `buildArgs` and `useCreateForm` are not modified, and the spec forbids relocating the transcript probe or the argv assembly back under `restartMu` (#1630's leaf-mutex rule) or moving the new snapshot out of `beginSpawn`'s existing section (#1481's single-acquisition rule). The kill path — `cmd.Cancel`, the descendant-group reap, `WaitDelay` — is unchanged.
- **[File operations]** N/A with reason: the design adds no path construction, no `os.Stat`, no writes and no permissions decision. The only filesystem touch in the package remains `transcript.StatByID` behind `useCreateForm`, which this ticket does not modify — including its `ValidStem`-before-join property, which is what keeps a non-canonical id from becoming an arbitrary-path existence oracle.
- **[Tokens, secrets, credentials]** N/A with reason: no tokens, keys or credentials exist in this design. `freshSeq`/`armFreshSeq` are process-local monotonic counters — never persisted, serialised, transmitted or logged, per the field docs the fix must write, matching `rotateGen`'s existing statement.
- **[Cryptographic primitives]** N/A with reason: no randomness is security-relevant here, so neither `crypto/rand` nor `math/rand` enters the design. The counters are compared only against a value the same process captured under a mutex; they are not nonces, not authentication material, and not guessable-by-an-adversary in any sense that matters, since no external caller can supply one.
- **[Threat model alignment]** `docs/protocol-mobile.md` § Security model, § Threats: the relevant threat is a turn's payload reaching the wrong session's child. This gate is that control and the fix strengthens it without touching the payload path — no new parsing, no new buffers, no new bytes retained. Explicitly out of scope and unchanged here: authentication of the `new_session` frame itself (Noise_IK plus device identity, upstream of this package) and rate-limiting inbound `new_session` frames. Neither is regressed by this change; both are pre-existing surfaces owned elsewhere.
