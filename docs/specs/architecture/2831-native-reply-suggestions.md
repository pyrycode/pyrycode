## Context

Native suggestions are generated by claude after `result` when spawned with `--prompt-suggestions`. #2829 parses them, #2830 reconciles them on connect; nothing produces or emits state. This slice adds the producer. No decision record needed.

## Design

**Spawn flag.** `buildArgs(base, create, sessionID, promptSuggestions bool)` appends `--prompt-suggestions` after `--replay-user-messages` when true. `beginSpawn` computes it as `!promptSuggestionsDisabled(append(os.Environ(), env...))`, where the helper reads the last `CLAUDE_CODE_ENABLE_PROMPT_SUGGESTION=` entry and returns true only for `false`.

**State owner** — new `cmd/pyry/reply_suggestion.go`, type `replySuggestions`, one per daemon, built in `startRelayV2` only when a stream sink exists. One leaf `sync.Mutex` over `map[convID]*replySuggestionConv`:

- published state: `revision uint64`, `published bool`, `text *string`, `sessionID string`
- eligibility: `delivered` (non-empty delivered user text since the last TurnEnd), `assistant` (main-agent text in the current turn), `invalidated` (since current turn start), `eligible` (last TurnEnd qualified and nothing since invalidated it).

Methods (all nil-safe, none pushes under the lock):

- `noteDelivered(convID, text)` — msgqueue OnDelivered path.
- `turnStarted(convID)` — emitter, when `startTurnIfNeeded` opens a turn: reset the turn flags, then clear.
- `noteAssistantText(convID)` — emitter TextChunk with `ParentToolCallID == ""` and non-empty text.
- `turnEnded(convID, success)` — emitter TurnEnd arm; `eligible = success && delivered && assistant && !invalidated`; consumes `delivered`.
- `suggest(convID, text)` — emitter `PromptSuggestion` arm; only when eligible: consume eligibility, store text with the conversation's current session id, revision++, mark dirty. Otherwise nothing.
- `invalidate(convID)` — accepted send, send-now, `/clear`, reset/eviction transition, exit/teardown close. Existing entries only: `invalidated = true`, `eligible = false`; if text is held, set it nil, revision++, mark dirty.
- `current()` — the `ReplySuggestions` seam: one payload per published conversation that still exists (via `sessionFor`), sorted by conversation id; deleted conversations are pruned there.
- `Run(ctx)` — publisher goroutine. Woken through a 1-buffered channel, takes the dirty set, snapshots each conversation's *current* payload under the lock, then pushes to every interactive conn from `ActiveConns`. Coalescing to current state means a wake can never lose a clear, and the relay's per-conn revision guard drops anything overtaken.

The broadcast leaves `EventID` nil: suggestion state is control state, never ring or history. Session id comes from `sessionFor(convID) (string, bool)` over the registry's `CurrentSessionID`.

**Wiring.** The OnDelivered hook is fixed in `main.go` before the relay leg, so `main.go` mints the owner (stream path only) and hands it on `relayWiring.suggestions`; `deliveredFuncs` gains `suggestions.noteDelivered`. `startRelayV2` sets its broadcaster and resolver, starts `Run`, assigns `emitter.suggestions`, wires `ReplySuggestions: suggestions.current` (nil seam without a sink), wraps the `SendMessage` enqueuer and resetter and `QueueSender` in small adapters that invalidate on acceptance only (`EnqueueSent != 0`, `SendNow == true`, `/clear` reaching `StartNewSession`), and wraps `w.transitions` so the composed observer also invalidates the transition's conversation. `sessions.Runner` is untouched.

## Concurrency model

Writers: drain goroutine (emitter hooks), relay handler goroutines (accept adapters), msgqueue drain (noteDelivered), pool transition observer. Reader: relay Run (`current`). All go through the one leaf mutex; the only push happens on the owner's own `Run` goroutine with no lock held, so no path round-trips through relay Run while holding anything. `Run` exits on ctx cancel; the wake channel is never closed.

## Error handling

Push errors are logged at Debug with conn id and conversation id only. Marshal cannot fail (strings, uint64, *string); defensive Debug without payload. Suggestion text is never logged anywhere.

## Testing strategy

- `runner_test.go`: existing argv tables gain the flag; a table for `promptSuggestionsDisabled` (unset, `true`, `false`, last entry wins).
- `reply_suggestion_test.go`: the eligibility table (success/fail outcome, error flag, non-end_turn reason, missing user text, missing main text, subagent-only text, invalidated mid-turn), set and clear revisions, clear after each trigger with `current()` returning null, delete pruning, other conversation untouched, `Run` fans out to interactive conns only.
- Fake-daemon e2e (`internal/e2e/relay_v2_stream_reply_suggestion_test.go`): replay fragment with assistant text, `result` success and a `prompt_suggestion` line; two interactive phones both see the set; a second send from phone A clears on both; phone C connecting afterwards receives null; a second conversation's state stays absent.

## Security review

**Verdict:** PASS

**Findings:**

- [Trust boundaries] No findings. The one boundary for the suggestion text is `decodePromptSuggestion` in `internal/streamsup` (#2829): single-line, non-blank UTF-8, at most 1024 bytes. Downstream it is carried verbatim and only as `ReplySuggestionPayload.SuggestedReply`. Attribution is by the producing session's conversation (`conversationForSession` in the drain, passed to `HandleFor`), never the active cursor, so one conversation's suggestion cannot be stamped onto another. The frame goes through `Push` and so through `forwardEnvelope`, where `withheldFromConn` and `replySuggestionStale` apply as for the reconcile. The daemon never sends the text to claude itself: only an explicit client send does.
- [Tokens] No findings. Nothing secret is created or read. `promptSuggestionsDisabled` compares one env value against the literal `false` and logs nothing; `accountTokenEnv` is untouched.
- [File operations] No findings. State is daemon memory only; nothing is written to disk.
- [Subprocesses] No findings. `buildArgs` adds one constant flag; no caller-controlled value reaches argv, and the inherited environment is unchanged. Operators can opt out with `CLAUDE_CODE_ENABLE_PROMPT_SUGGESTION=false` or claude's own settings. Whether every supported claude accepts the flag is what the `needs-real-claude` gate proves.
- [Cryptography] No findings. Revisions are ordering counters, not secrets; frames are sealed by the existing Noise transport.
- [Network and I/O] No findings. One frame is at most about 1.2 KB. The publish rate is bounded: one set per eligible turn and one clear per held suggestion, so repeated sends from a client cannot amplify (`clearLocked` publishes only while text is held), and `Run` coalesces a burst to each conversation's current state. Memory is one small entry per conversation that delivered or ran a turn; `current` forgets deleted conversations.
- [Errors, logs, telemetry] No findings. The text is never logged: `Run` logs event, conn id, conversation id and Push's transport error only; the live test logs only its length.
- [Concurrency] SHOULD FIX, fixed in the build: resetting `invalidated` at turn start lets an accept that arrives after the child opened the next turn, but before the drain saw it, be erased, so that turn could publish while a newer message waits. The reset moves to the next queued (non-send-now) delivery, which always follows its own accept; see Revisions. Otherwise one leaf mutex, the registry read behind `sessionFor` always taken with it released, no push under it, and `Run` exits on ctx with its cleanup waiting.
- [Threat model] No findings against `docs/protocol-mobile.md` § Security model: paired, end-to-end encrypted conns only, and the same interactive gate as every v2 event frame. A prompt-injected suggestion is still inert text the user must choose to send.

## Revisions

- 2026-10-05, from the security review run after the plan commit (the `security-sensitive` label was missed at plan time): `turnStarted` no longer resets `invalidated`. `noteDelivered` resets it, but not for a send-now delivery, which joins the turn its accept invalidated. Contract: an accepted send invalidates every turn up to the next queued delivery, so an accept racing the drain's view of a turn start is not lost. `turnStarted` still clears a held suggestion and the turn's text and eligibility flags.
- 2026-10-05: `current` reads the registry with the mutex released, through `resolver` and `forget`, so the mutex stays a leaf. `sessionFor` is installed by `bindSessions` under the mutex.
- 2026-10-05: the owner is minted in `main.go` (stream path), as the Wiring paragraph says, not in `startRelayV2`; `startRelayV2` binds and starts it. The open question on live suggestion cadence is settled by the `needs-real-claude` gate, which runs the live test with a six-turn budget.
- 2026-10-05, from the fake-daemon test going red on a rerun: msgqueue's OnDelivered is not ordered against the stream. For a stream claude it acknowledges placement on the queue's goroutine, often after the turn's `result` and sometimes after the `prompt_suggestion`. So eligibility no longer needs the delivery before `TurnEnd`. `turnEnded` records `turnOK` (success, main-agent text, not invalidated) and credits any delivery already seen as `userOK`. A delivery confirmed after the turn ended, before the next turn starts, credits that turn. A suggestion that arrives while only `userOK` is missing waits in `pending` and is published by that confirmation. Every invalidation and every turn start drops `pending`. The set conditions are unchanged; only their arrival order is now free.
- 2026-10-05, from the real-claude gate failing `TestInteractiveStream_NativeReplySuggestionSetThenClear`: turn 1 drew no suggestion, the 30-second wait for one timed out a fakephone read, and coder/websocket closes the conn when a read's context expires, so turn 2's send hit a closed conn. Test-only fix: one reader goroutine owns every phone read with a single long deadline, and the turn and suggestion waits time out on its channel. No product contract changes.
- 2026-10-05, from the real-claude gate failing `TestInteractiveStream_NativeReplySuggestionSetThenClear` a second time (six turns, no suggestion). Two causes. First, a daemon bug: from a conversation's second turn on, the accept that queued the turn's message sets the sticky `invalidated`, and only that message's delivery confirmation resets it. For a stream child that confirmation lands after the `result`, so `turnEnded` folded `invalidated` into `turnOK` and dropped every later turn. The fake-daemon test missed it because its only accept hits a conversation the owner has not seen yet. New contract: a per-turn `turnHit`, reset at turn start, records invalidations inside the drain's view of the turn and is what `turnEnded` folds. The sticky `invalidated` is read at publication instead: a suggestion that meets it waits in `pending`, and the next queued delivery confirmation, which resets it, publishes the suggestion if the user text is credited. An accept with no delivery to follow before the next turn start still leaves the turn unpublished. Second, the live prompts: a probe of claude 2.1.280 showed that it emits a suggestion on nearly every turn after the first for coding steps with an obvious follow-up, and its suggestion prompt stays silent when the next step is not obvious. The garden prompts each ended on an open question to the user, so the live test now drives small coding steps.
