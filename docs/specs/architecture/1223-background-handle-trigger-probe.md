## Premise corrections

Two statements in the ticket body are wrong or path-dependent. Neither invalidates
the ticket; both change how the probe is staged, so they are settled here rather
than at a live-run cost.

### 1. `agent-run` does **not** use `-p` on its default path

The body says *"Under `-p`, which is what `agent-run` uses, background tasks end
shortly after the run's final result."* The default path is **ptyrunner**: claude
is spawned in an interactive TUI with argv `--session-id --settings
--permission-mode dontAsk --append-system-prompt-file --model --effort`
(`internal/agentrun/ptyrunner/runner.go:616-625`), reached whenever
`PYRY_USE_STREAMJSON != "1"` (`cmd/pyry/agent_run.go:266`). The headless
stream-json path (`--input-format/--output-format stream-json --verbose`,
i.e. the `-p`-shaped one) is the opt-in legacy rollback.

Consequences for this spec:

- The documented `-p` background-task lifecycle does not necessarily describe the
  default path. **Do not rely on it for timing.** The design below removes the
  dependence entirely (§ Mechanism).
- Every record must name which path the rep ran under. #1224–#1227 read this.
- If the levers do not fire on the ptyrunner path, the streamrunner path is a
  first-class second attempt (§ Fallback row), and a divergence between the two is
  itself a finding for AC2, not a footnote.

### 2. The env-plumbing "open design question" is already answered

The body flags *"how the probe gets them into claude's environment is an open
design question for the architect."* It is settled by reading two lines:

- `ptyrunner`: `if cfg.Env != nil { cmd.Env = append(os.Environ(), cfg.Env...) }`
  (`runner.go:297-299`). Production leaves `cfg.Env` nil, so `cmd.Env` stays nil and
  `os/exec` gives the child **pyry's own environment verbatim**.
- `tuidriver.EnsureClaudeEnv(cmd)` (`runner.go:300`) only materialises `cmd.Env` from
  `os.Environ()` when nil and overrides `TERM`. It does not filter, allowlist, or
  clobber anything else.
- `streamrunner` has the identical shape (`streamrunner/runner.go:179`).

**Therefore: setting a variable on the `pyry agent-run` process is sufficient.** No
production change, no new flag, no forwarding list. The probe sets it via `cmd.Env`
on the pyry subprocess and it lands in claude's environment on both paths.

This is a claim about the code, not about claude. Whether claude *honours*
`BASH_DEFAULT_TIMEOUT_MS` in TUI mode is exactly what the probe measures — and
§ Env-arrival control makes "the variable never reached claude" separable from
"claude ignored it" without spending a turn.

## Mechanism

The whole probe rests on one inversion, ported from #1219's fixture design: **the
test owns the window in which the command is in flight, and claude only waits on
it.** Everything else is bookkeeping.

```
test:   mkfifo <workdir>/probe-hold
test:   goroutine → open(fifo, O_WRONLY)     [blocks: no reader yet]
claude: Bash → cat <workdir>/probe-hold      [blocks: no writer yet]
        ↓ both opens complete at the same instant — a rendezvous
test:   holds the write end, never writes    → cat blocks in read() indefinitely
test:   Close()  (t.Cleanup ONLY)            → cat sees EOF and exits
```

Three properties fall out, and each maps to an AC:

1. **The command cannot complete on its own.** So if a `tool_result` matching the
   Bash `tool_use` appears while the test still holds the write end, the only
   explanation is claude ending the call itself. That is the *fired* signal for
   AC1/AC2 — a **structural** discriminator, not a match against claude's prose.
   Matching prose is the treadmill #563 and #1219 both fell off; do not do it.
2. **The backgrounded process stays alive for as long as the test wants.** So AC5's
   `ps` snapshot has **zero timing race**: the test takes it synchronously at the
   instant it observes the `tool_result`, with pyry still running and `cat` still
   blocked. No poller, no ring buffer, no post-hoc window selection.
3. **The window's start is race-free.** The blocking `open(O_WRONLY)` returns the
   instant `cat` starts — no 100 ms poll lag. (That lag is what lost #1219's race
   against a 5 s model-chosen timeout.)

### Non-negotiable: the write end never leaves the helper

`holdProbeFIFO` returns a rendezvous signal, **never the `*os.File`**. The only
release is its own `t.Cleanup`, which by construction runs after the subtest body.
If the caller could close early, `cat` would exit on its own and every
`did-not-fire` rep would be misclassified as `fired` — a silent false positive on
the ticket's central question.

### Command choice, and what is *not* load-bearing

`cat <fifo>` is used because: it is not `sleep`-leading (the body records that
Claude Code never auto-backgrounds a `sleep`-leading command — a different
mechanism from #563's standalone-`sleep` refusal); it is the exact command whose
2026-07-28 observation gave the no-model-`timeout` branch this probe targets; and it
is a single, `ps`-visible leaf process.

**Not load-bearing:** the neutral command name and the neutral FIFO name
(`probe-hold`, no `.fifo` suffix). They only reduce a cue that might prompt the model
to attach a defensive timeout. Properties 1–3 hold regardless. Do not read them as
"pick a command claude won't bound" — that is the treadmill this shape exists to end.
For the same reason **no prompt carries a timeout nudge**: steering the model is the
lever the ticket explicitly ruled out.

## Design

One new file: `internal/e2e/realclaude/background_trigger_probe_test.go`,
`//go:build e2e_realclaude`. No other file is created or modified.

### Opt-in gate

`make e2e-realclaude` runs the whole package glob (`Makefile:57`), so an ungated
probe would burn ~9 live turns on every `make preship`. Gate it:

```go
// Skips unless PYRY_PROBE_BACKGROUND_TRIGGER=1. This is an evidence probe,
// not a regression gate — a SKIP here is the normal preship outcome and
// carries no signal about pyry's behaviour.
```

The skip message must say all three things: that this is a probe and not a gate,
the env var that enables it, and the row-by-row `-run` recipe. A future reader
seeing a green `make e2e-realclaude` must not conclude the probe passed.

### Row table

Each row differs only in the environment handed to `pyry agent-run` and (for one
row) the prompt. `reps` is 3 only where AC3 needs it.

| row | extra env on the pyry process | why | reps |
|---|---|---|---|
| `default-only` | `BASH_DEFAULT_TIMEOUT_MS=5000` | L1 — the no-model-`timeout` branch, the one that broke determinism on 2026-07-28 | 3 |
| `max-only` | `BASH_MAX_TIMEOUT_MS=5000` | L2 in isolation. Against a command the model does **not** bound, the ceiling should not apply — a *did-not-fire* here is the attribution evidence AC2 asks for, not a failure | 1 |
| `both` | both, `=5000` | the body's primary candidate: covers the branch where the model sets no timeout (default applies) **and** where it sets one (clamped to the ceiling) | 3 |
| `disabled` | both, plus `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` | the body's free negative control. If the lever fires above and this suppresses it, timeout-expiry is confirmed as the mechanism | 1 |
| `run-in-background` | none; prompt asks for `run_in_background: true` | AC4's comparison target. Not a determinism candidate — the model fills this parameter in | 1 |

Nine live turns. **Run row by row** (`-run 'TestRealClaude_BackgroundHandleTrigger/<row>'`),
not as one invocation — a whole-table run can exceed both the `go test` default
timeout and a single tool call's budget.

There is no `baseline` (no-env) row: AC4 explicitly permits the quoted 2026-07-27
transcript as the expiry-path baseline and says reproducing the coin flip afresh is
not required.

### Per-rep sequence

Each rep is its own `t.Run` subtest, so it gets its own `t.TempDir()`, its own
`t.Setenv`, and its own `t.Cleanup` — reps must not share a HOME or a FIFO.

1. `WithWorktreeAuthenticated(t)` → `workdir` (also the pinned HOME).
2. `mkfifo <workdir>/probe-hold`; `holdProbeFIFO` starts the blocking-open goroutine.
3. Write `prompt.txt` / `system.txt`; spawn `pyry agent-run` **asynchronously**
   (`cmd.Start`, `Setpgid: true`) with the row's env appended to `os.Environ()`.
4. Defense-in-depth `t.Cleanup`: `syscall.Kill(-pyryPid, SIGKILL)`. ESRCH is benign.
5. Wait for the rendezvous (bounded). Timeout ⇒ record `command-never-ran`; the rep
   is inconclusive, **not** a test failure.
6. Recover `sessionID` from pyry's stdout via `parseInitSessionID`.
7. Poll the session JSONL for the Bash `tool_use`, then for a `tool_result` whose
   `tool_use_id` matches. Bounded (see § Timing constants).
8. **On observing the `tool_result`, synchronously and in this order:**
   a. `ps -axo pid=,ppid=,pgid=` — retain the **verbatim** output (AC5) and parse
      pyry's descendant subtree from that same snapshot.
   b. liveness probe on pyry (`Signal(syscall.Signal(0))`) — records whether the
      snapshot was genuinely taken before `pyry agent-run` returned (AC5's
      "during the turn" requirement, self-evidenced rather than assumed).
   c. claude's env read (§ Env-arrival control).
   d. `os.ReadDir(workdir)` listing (AC5).
9. Release happens only in `t.Cleanup`: close the write end → `cat` sees EOF → the
   call completes → the turn ends → pyry exits. This is also the teardown path for
   `did-not-fire` reps.

### Classification

Three-valued, derived from artifacts the rep already produced. No prose matching.

- **`fired-background`** — a matching `tool_result` appeared while the FIFO write
  end was still held, **and** the `cat` process is present in the `ps` snapshot as
  a descendant of pyry. The command was moved aside, not killed.
- **`fired-other`** — matching `tool_result` present, but `cat` is absent from the
  snapshot. Claude bounded the call and the command did not survive. Record it
  verbatim; draw no conclusion.
- **`did-not-fire`** — no matching `tool_result` within the deadline.

`command-never-ran` is a fourth, separate outcome for step 5's timeout — the model
did not issue the Bash call at all. It is not evidence about the lever.

The same `ps` snapshot serves the classifier **and** AC5's raw readout. One exec,
two jobs.

### Env-arrival control (different fabric)

The largest confound on a total-null outcome is *"the variable never reached
claude"*, which looks identical to *"claude ignored it"*. Separate them without
spending a turn and without going through the model:

- **Primary (model-free):** at step 8c, read the claude child's environment from
  the OS (`ps -Eww -p <claudePid>`, or `ps eww -p <claudePid>`) and extract **only**
  the three lever variable names and their values. Whether the variable arrived is
  then an OS-level fact, independent of anything claude chose to do.
- **Fallback (only if the OS read is blocked or empty):** a one-turn row whose
  prompt is `Use the Bash tool to run \`printenv BASH_DEFAULT_TIMEOUT_MS\`. Do
  nothing else.` and which records the `tool_result` text. Model-mediated, hence the
  fallback rather than the primary.

**Redaction is mandatory.** These artifacts get pasted into a public issue. Extract
the three named variables by name; **never** dump the full environment —
`CLAUDE_CODE_OAUTH_TOKEN` and `ANTHROPIC_API_KEY` live in it. Same rule for pyry's
stdout/stderr captures: `truncate` them and skim before pasting. The workdir listing
is **names only** — note that `workdir == HOME` under `WithWorktreeAuthenticated`,
so the listing will show `.claude/` and `.claude.json`; list them, never their
contents.

### Fallback row (conditional, not part of the default matrix)

Only if `default-only` and `both` both come back `did-not-fire` on the ptyrunner
path: re-run `both` with `PYRY_USE_STREAMJSON=1` also set on the pyry process, which
selects the headless stream-json path (`cmd/pyry/agent_run.go:266`). A lever that
fires there but not under the TUI is a first-class AC2 finding — record it as such.

### Timing constants

Name them; do not inline. All are generous multiples of the 5 s lever so a slow
turn is never misread as a lever failure.

| constant | value | rationale |
|---|---|---|
| rendezvous deadline | 60 s | covers TUI spawn + idle + prompt delivery + the model reaching the Bash call |
| `tool_use`-on-disk deadline | 30 s after rendezvous | the envelope lags the subprocess by a couple of seconds |
| `tool_result` deadline | 45 s after `tool_use` | 9× the 5 s lever; expiry means `did-not-fire`, not "too slow" |
| JSONL poll interval | 200 ms | |
| `--max-turns` | 6 | the turn must **complete** (claude receives the result and replies), so leave headroom; mirrors the `--max-turns=6` in `spawnPyryAgentRun` |

A `did-not-fire` rep therefore costs ~2 min (it waits out the deadline, then
releases). A `fired` rep costs ~30 s.

### Evidence artifacts

Write per-rep artifacts to a directory that **survives the test** —
`os.MkdirTemp("", "pyry-1223-probe-*")`, path emitted via `t.Logf`. Not `t.TempDir()`:
that is removed at test end and the developer needs the files afterwards to compose
the issue comments.

Per rep, capture: claude version (`resolveClaudeBin` + `--version`), row name, the
exact env delta, the runner path, pyry/claude pids, the classification, the
**verbatim** `tool_use` and `tool_result` JSONL lines (raw bytes, unreformatted —
AC1 says verbatim), whether `input.timeout` was present on the `tool_use` and its
value, the verbatim `ps` snapshot, the pyry-liveness result, the redacted lever-env
readout, the workdir listing, and the session JSONL path.

`input.timeout` is **diagnostic, never dispositive** — it tells you *which* branch a
rep exercised (model-set vs default-applied). Dump it; do not classify on it.

### What this probe asserts

Almost nothing. It is an evidence collector, not a regression gate.

- `t.Fatalf` **only** on structural failure: pyry won't build, `mkfifo` fails, pyry
  never spawns a claude child, no `system/init` session id on stdout.
- Everything else — `did-not-fire`, `command-never-ran`, reps disagreeing — is
  `t.Logf`'d into the record. Per AC3, a lever that fires intermittently is
  *reported* as non-deterministic; it is not a red test.

## Concurrency model

Deliberately minimal — one goroutine.

- **The FIFO-hold goroutine.** Blocks in `os.OpenFile(path, os.O_WRONLY, 0)`, then
  closes a `chan struct{}` to signal the rendezvous. A **closed channel**, not a
  buffered send: the signal may be awaited by more than one receiver (the body and,
  potentially, a cleanup assertion), and a buffered send deadlocks the second waiter.
  The `*os.File` stays inside the helper; `t.Cleanup` closes it.
- **`cmd.Wait` goroutine** (only if the design needs a non-blocking exit observation).
  Prefer the `Signal(0)` liveness probe at step 8b — it needs no goroutine at all.
- **stdout buffer.** `os/exec` writes the child's streams from a copier goroutine
  while the test reads them mid-run, so the buffer must be mutex-guarded.
  `syncBuffer` in `sigterm_mid_tool_use_test.go` is exactly this — but that file is
  being rewritten (§ Branch hygiene), so define a probe-local equivalent (~15 LOC).
  The duplication is deliberate and cheap; note it in a comment.
- No parallelism. `t.Setenv` forbids `t.Parallel()`, and live claude runs share one
  usage window.

**`t.Cleanup` ordering is LIFO** — the defense-in-depth `Kill(-pyryPid)` must be
registered *before* `holdProbeFIFO`, so the FIFO release runs first and pyry gets
the chance to exit cleanly.

## Error handling

| failure | handling |
|---|---|
| `mkfifo` / build / spawn fails | `t.Fatalf` — structural, the rep cannot run |
| no `system/init` session id within deadline | `t.Fatalf` — nothing downstream is observable |
| rendezvous never fires | record `command-never-ran`, release, continue to the next rep |
| `tool_use` never lands on disk | record `command-never-ran` with the distinguishing note that the rendezvous *did* fire; continue |
| no matching `tool_result` within deadline | record `did-not-fire` — the expected outcome for several rows |
| `ps -Eww` blocked/empty | record it, fall back to the `printenv` row (§ Env-arrival control) |
| pyry already exited at snapshot time | record `snapshot-window-missed` on that rep; AC5 is unmet for it, and that is a stated fact, not a silent gap |
| reps within a row disagree | record the per-rep classifications and report the row as **non-deterministic** (AC3) |

## Testing strategy

This ticket's artifact *is* a test, so "testing strategy" means: how does the
developer know the probe itself works before trusting its output?

- **Rendezvous self-check** (credential-free, no live claude, runs in seconds):
  create a FIFO, call the hold helper, `exec` a local `cat <fifo>` in place of
  claude, assert the rendezvous signal fires; then assert `cat` is *still alive*
  after a short wait (proving the hold is real), and that it exits once the cleanup
  release runs. This is the "did the release work" seam — register the assertion
  cleanup **before** the helper that registers the release, so LIFO puts the
  assertion after it. Without this check, a hold bug turns every `did-not-fire` into
  a false `fired`.
- **`ps`-parse self-check** (credential-free): feed a synthetic three-column
  `pid ppid pgid` fixture through the descendant walk and assert the expected
  subtree. Mirrors `internal/agentrun/reap_test.go`'s shape.
- **Live rows**: run one row at a time; read the artifact directory; compose the
  issue comments from the verbatim captures.

Both self-checks must run under `go test -tags e2e_realclaude -run '<name>' -v`
without credentials, and their names should make that obvious. They are the only
part of this file that is deterministic.

## Scope discipline

**Hard iteration cap.** The ticket rules out prompt-steering as a lever. So if the
env rows do not fire, the correct next step is the § Fallback row (streamrunner
path) — and after that, **record the null and stop**. Do not iterate on prompt
wording, do not try a fourth command, do not lower the timeout values hunting for a
threshold. A null outcome is an explicitly sanctioned deliverable of this ticket
(AC2), and prompt iteration is the treadmill #563 and #1219 already paid for twice.

**No conclusions.** This ticket records readouts. Statements about reaping, orphan
survival, turn accounting or workdir hygiene belong to #1224–#1227, which read this
evidence. If the probe surfaces something startling in those areas, put it in the
issue comment as an observation with the raw artifact attached — not as a finding,
and not as a code change.

## Open questions

- **Does the interactive TUI honour `BASH_*_TIMEOUT_MS` at all?** The docs describe
  them as Claude Code client settings without qualifying the mode. § Env-arrival
  control makes "did not arrive" separable from "arrived and was ignored", so
  whichever way it lands, the record is unambiguous. Unresolvable without the run —
  that is the ticket.
- **Does `BASH_MAX_TIMEOUT_MS` alone bound a call the model did not bound?** The
  docs say it caps what the model *can* set, which reads as inapplicable when the
  model sets nothing. The `max-only` row measures this rather than assuming it; a
  `did-not-fire` there is the evidence for AC2's per-lever attribution and for the
  body's "neither alone covers both branches" claim.
- **Does the `run_in_background` comparison need its own FIFO?** Probably yes (the
  handle should stay live for the process-tree comparison), but if the model returns
  a handle for a trivially-completing command the comparison still works on the
  `tool_result` text and JSONL surfaces. Decide at implementation time from what the
  first run shows; do not spend extra live turns settling it in advance.
