## Context

`TestRelayV2_StreamNewSessionRotatesAndRestartsFresh` fails intermittently at M4. #1273 made the record self-describing: elapsed stamps, the stdin log's size at ack #2 versus at expiry, a failure-time registry re-read. Its own closing note names what it still cannot do — separate *"delivery stalled inside the seam"* from *"the fresh child never spawned"*, because a frozen stdin log is consistent with both.

The daemon already emits the discriminator. On the error-return arm the drain logs a **Warn** every second (`queue.go:607`, `defaultRetryInterval = 1s`); across a 20 s dead window that is ~20 lines, with no give-up possible (`defaultGiveUpAfter = 2m`). The test just never captures it. `h.Stderr` is right there, mutex-guarded, documented for mid-test polling.

**The negative reading is the delicate half, and it is why this is a design and not a one-liner.** Zero Warns does **not** mean the daemon never tried. Three states are silent at the daemon's Info level:

1. parked in `Activate` — bounded by `inboundActivateTimeout` = 30 s;
2. parked in the mid-turn hold — bounded by `streamTurnHoldTimeout` = 15 min;
3. **actively retrying at the same 1 s cadence** under the pending/hold branch (`queue.go:587`), which logs at **Debug**, deliberately content-free so a legitimate hold never spams the operator log — and the harness starts `pyry` without `-pyry-verbose`, so the level is `slog.LevelInfo` and those lines never appear.

State 3 is the trap: it is *looping* — the exact behaviour the Warn count is meant to detect — and it is invisible. So the record must say **"not the error-return arm"**, never **"the daemon never tried"**. In this fixture state 3 cannot occur (the fake claude raises `ErrTrustModalPending` only under `Readiness{TrustModal:true}`, which this test does not configure) — but that is a fixture property, not a property of the record, so the legend states the honest general reading rather than the locally-true strong one.

## Design

Everything below is package-private, inside `internal/e2e/relay_v2_stream_new_session_test.go`. No production code, no new files, no exported identifiers. Names verified free in package `e2e`.

### D1 — The window boundary is a byte offset into `h.Stderr` (AC-1)

Beside the existing `ackTwoBytes` capture (line 383), record the daemon log's length at the same moment:

```go
ackTwoLogLen := len(h.Stderr.Bytes())
```

Why an offset and not a timestamp: `safeBuffer` is **append-only**. Its entire method set is `Write` / `String` / `Bytes` (`auto_attach.go:79-101`); there is no `Reset`, no `Read`, and nothing in the harness resets it. So byte *N* means the same byte for the life of the test, and `snapshot[ackTwoLogLen:]` is exactly "what the daemon logged after ack #2" — no clock, no parsing, no format coupling.

Two disciplines the surrounding code already imposes, both of which this capture must honour:

- **Same instrument at both ends.** The file's 370-381 comment explains why `ackTwoBytes` and `logBytes` both use `os.ReadFile + len` rather than mixing in an `os.Stat`: a concurrently-appended file makes a mixed-instrument delta unattributable. Same rule here — both ends read `h.Stderr.Bytes()`. `len(h.Stderr.Bytes())` copies the buffer just to measure it; that is a few KB and it is the correct trade for instrument consistency. Do **not** add a `Len()` method to `safeBuffer` — that is a different file, outside this ticket's scope.
- **Nothing fatal on the failure path.** `h.Stderr.Bytes()` takes no `*testing.T` and cannot fail; the renderer below is a pure function over bytes. The path stays free of `t.Fatal*`-ing helpers, as the 421-423 comment requires.

One honesty note to carry into the code comment: `os/exec`'s stderr-copy goroutine is asynchronous, so a line written microseconds before the snapshot may not be in the buffer yet. Against a 20 s window at a 1 s cadence this cannot change any reading, but the record should not pretend the boundary is exact to the microsecond.

### D2 — One pure renderer owns every honesty obligation (AC-1, AC-2, AC-3)

```go
// daemonLogWindow renders the daemon log bytes written after `since` — the
// window between ack #2 and the M4 poll's expiry. Pure over its arguments:
// no *testing.T, no I/O, no clock. Never returns "".
func daemonLogWindow(snapshot []byte, since, budget int) string
```

Two package-level constants beside it:

- `daemonLogBudget = 8 << 10` — the byte cap the M4 call site passes. Sized against the modelled arm: ~20 Warn lines at ~250 B each ≈ 5 KB, so the expected failure renders complete, and elision is reserved for a genuinely chatty run. `budget` is a parameter, not a hard-coded read of the const, so the table test can drive elision on small fixtures instead of an 8 KiB one.
- `msgqueueRetryWarn = "msgqueue: delivery failed, will retry"` — the literal from `queue.go:607`.

The function returns a header line followed (in the two measured cases) by the excerpt. Four arms, exhaustive over the argument space:

| Arm | Condition | Rendering |
|---|---|---|
| **unmeasurable** | `since < 0 \|\| since > len(snapshot)` | `<unmeasurable: the ack #2 offset N exceeds the M-byte snapshot; the window boundary cannot be applied>` — the buffer is append-only, so this is unreachable in practice; it exists so a broken instrument can never render as a measurement. |
| **empty** | window length 0 | `<empty: the daemon logged nothing between ack #2 and expiry>` — never a blank line, never `""`. |
| **complete** | `0 < len ≤ budget` | header + the whole window verbatim. |
| **elided** | `len > budget` | header + first `budget/2` bytes + `… [K bytes elided from the middle] …` + last `budget/2` bytes. |

The header, in all measured arms, states three things: the window's **total** byte count (not the kept count — that is the honesty AC-2 asks for), the count of retry Warns, and which arm rendered it, e.g.

```
daemon log, ack #2 → expiry: 20144 bytes, 19 retry Warns matching "msgqueue: delivery failed, will retry"
  (bounded: showing the first 4096 and last 4096 bytes, 11952 bytes elided from the middle)
```

Three design points behind that shape:

**The Warn count is the primary datum; the excerpt is corroboration.** `bytes.Count(window, []byte(msgqueueRetryWarn))` answers AC-1's question — "readable directly off the failure instead of inferred" — as a number, and it survives elision, which a hand-count of the excerpt does not. The header **names the literal it matched**, so a reader whose count is 0 can see the needle and check it against `queue.go` rather than trusting a silent 0. That is the same posture as `regNowID`'s sentinel: the instrument reports itself.

**Head *and* tail, not head alone.** The realistic over-budget case is an unexpectedly chatty run, where onset (did retries begin at all?) and end (what was the last thing the daemon said?) are both load-bearing. Head-only elision could bury either. The cut is byte-based, not line-aligned — the header says "bytes" and means it; do not spend code aligning to newlines.

**Elision is stated in bytes elided, not "truncated".** AC-2's two failure modes are symmetric: a long run must not bury the record, and a short one must not *look* truncated. The complete arm therefore says nothing about eliding, and the elided arm gives the exact count.

### D3 — Message ordering: computed verdicts before the static legend (AC-1)

The M4 `t.Fatalf` grows to five ordered parts:

1. **Headline** — unchanged.
2. **Computed readings** — ack #2 received, the stdin-log size pair with its read errors, the registry id pair. Unchanged from #1273.
3. **The daemon window** — `daemonLogWindow(h.Stderr.Bytes(), ackTwoLogLen, daemonLogBudget)`, its header carrying the counts, then the excerpt.
4. **The static legend** — how to read the window. Verbatim intent:

   > ~1 retry Warn/s (`defaultRetryInterval` 1 s) ⟹ the drain was in the **error-return arm**: `DeliverFunc` returned non-nil, the head stayed queued, and the fresh child never became writable. No give-up is possible inside this window (`defaultGiveUpAfter` 2 m). **Zero retry Warns ⟹ the drain was NOT in that arm — it does NOT mean the daemon never attempted delivery.** Three states are silent at the daemon's Info level: parked in `Activate` (bounded by `inboundActivateTimeout`, 30 s), parked in the mid-turn hold (`streamTurnHoldTimeout`, 15 min), or **retrying at the same 1 s cadence under the pending/hold branch**, which logs at Debug so a legitimate hold never spams the operator log.

5. **`log=%q`** — the stdin log, unchanged, still last.

Ordering rationale (the ticket's optional process note, taken up because it costs nothing): this failure's output has now been pasted into a ticket twice with the tail cut off. Putting every computed value ahead of the static prose means a cut paste loses only text that is readable in the source anyway. The legend must stay in the message rather than migrating to a code comment — a triager reading CI output does not have the source open.

The legend is static text; keep it as one `+`-joined literal block in the format string, not as `%s` of a package-level const. It is read at exactly one site.

### D4 — Diagnostic-only (AC-4)

No new deadline, no change to `turnTwoDeadline` (20 s) or any other duration, no retry wrapper, no `t.Skip`, no `t.Parallel`. The test fails on the first occurrence, as before. Verification commands in § Testing strategy.

### D5 — Correcting the deadline-pin comment (lines 388-397)

The existing prose says the drain *"BLOCKS inside the delivery seam waiting for claude to go idle (#704) **with no periodic retry**, so a missed wake-up is an **unbounded** stall."* Both clauses are false: a 1 s ladder exists on the error arm, and both parked states are bounded (30 s / 15 min).

**Do not paste the ticket's own replacement phrasing.** The ticket offers *"20 s, 60 s and 300 s all sit below both silent bounds (30 s / 15 min), so all three really are the same red"* — which is itself wrong: 60 s and 300 s both **exceed** the 30 s `inboundActivateTimeout`, so an `Activate` park stops being silent well before either. Correcting one wrong justification by writing another is worse than leaving it. Write only what is true:

- The error arm **does** re-attempt, every `defaultRetryInterval` (1 s), abandoning the head after `defaultGiveUpAfter` (2 m).
- The parked waits are **bounded, not unbounded** — `inboundActivateTimeout` 30 s, `streamTurnHoldTimeout` 15 min — but silent at Info level for the whole of *this* 20 s window, which sits below both.
- Raising the deadline still cannot fix the failure, and the reason is the outcome, not the silence: past 15 min a wedged hold gives up and surfaces a typed `session_error`, and everything shorter simply spends longer inside the same stall. 20 s, 60 s and 300 s are all red. What changes with a longer deadline is only how much evidence accrues — and capturing the log is the cheap way to get that evidence without paying the wall-clock.
- The no-retry-wrapper half of the comment stays as written; it is correct (#1168 / PR #1169).

Keep it to roughly the length it is now. This is a correction, not an expansion.

## Concurrency model

No goroutines are added. One shared object is read from the test goroutine: `h.Stderr`, written concurrently by `os/exec`'s stderr-copy goroutine and guarded by `safeBuffer.mu`. `Bytes()` returns a copy under the lock, so the snapshot is safe to retain and index. Both reads (offset capture, failure-time snapshot) are ordinary `Bytes()` calls. The suite runs under `-race`; nothing here introduces an unguarded read.

## Error handling

| Failure mode | Rendering |
|---|---|
| Daemon logged nothing in the window | `<empty: …>` sentinel. Never a blank rendering — that would read as "the daemon logged nothing", which is a *finding*, not an *absence of data*, and only the sentinel makes the difference visible. |
| Offset exceeds the snapshot | `<unmeasurable: …>` sentinel naming both numbers. Unreachable while `safeBuffer` stays append-only; it is the guard that makes that assumption checkable rather than implicit. |
| `msgqueue`'s Warn literal drifts | The count reads 0 while the excerpt still shows the lines. The header prints the literal it matched, so the discrepancy is visible in the same breath. Accepted over pinning the string in production. |
| Window over budget | Elided arm, exact byte count stated, both ends kept. |

Nothing on this path can call `t.Fatal*`: `h.Stderr.Bytes()` cannot fail and `daemonLogWindow` takes no `*testing.T`. A fatal fired while building `t.Fatalf`'s arguments pre-empts the whole deliverable — #1273 established this by name and it is why `readBootstrapIfPresent` exists.

**Redaction posture, unchanged.** `msgqueue` never logs `head.text`, and the daemon's Info level carries no phone content by design. This change attaches Info-level daemon output only; it does not raise the level (see below) and adds nothing new to what the record prints.

**`-pyry-verbose` stays off.** Enabling it to surface the Debug-level hold line would change the daemon's logging under test and widen what the record prints, for an arm this fixture cannot produce. AC-5's perturbation is pinned to the Warn-emitting arm precisely so the non-vacuity proof never depends on a level change.

## Testing strategy

### T1 — Table test for the renderer (covers AC-2 and AC-3 without a live repro)

`daemonLogWindow` is pure over `(snapshot, since, budget)`, so its four arms are provable offline in the same file, in this package's table-driven idiom. Scenarios, as behaviour — not as pre-written test code:

- **empty window** — `since == len(snapshot)`: renders the `<empty: …>` sentinel; assert the result is non-empty and contains `empty`. This is AC-3's contract check. It is *not* a manufactured live failure — the ticket forbids inventing a fixture that stalls with zero output, not testing the renderer's own contract.
- **offset past the end** — `since > len(snapshot)`: renders `<unmeasurable: …>` carrying both numbers.
- **negative offset** — same sentinel arm; guards against a future caller passing a computed offset.
- **complete window under budget** — the whole window appears verbatim; the header states the total byte count; the rendering says nothing about eliding.
- **over-budget window** — first and last fragments both present, the elided-byte count is exactly `total − budget`, and the header states the total (not the kept count). Drive this with a small `budget` and a synthetic snapshot; do not build an 8 KiB fixture.
- **Warn counting** — a snapshot carrying *k* copies of the literal, with one copy placed **before** `since`: the count reports *k − 1*, proving the count is scoped to the window and not to the whole buffer. Include one case with zero occurrences and a non-empty window (the "daemon logged, but not retries" reading).

Assert on substrings and computed numbers, not on the full rendered string — a whole-output golden would turn every wording tweak into a test edit.

### T2 — The unperturbed run still passes

```
go test -tags e2e -race -count=1 -run 'TestRelayV2_StreamNewSessionRotatesAndRestartsFresh|TestDaemonLogWindow' ./internal/e2e/
```

Then `make e2e` once before proposing, for the whole tagged package.

### T3 — AC-5: non-vacuity on an induced failure

**The perturbation.** Force the error-return arm — the arm that emits the Warns. A deliberately *blocking* seam emits nothing by construction and proves nothing about capture, so it is not an acceptable substitute. Insert at the very top of `newInboundDeliver`'s returned closure (`cmd/pyry/main.go:1626`), before `resolve`:

```go
if strings.Contains(string(payload), "e2e-1137-user:two") {
    return errors.New("e2e-1296 induced delivery failure")
}
```

Why this shape:

- `strings` and `errors` are already imported in `main.go`; `bytes` is not. Using `strings` keeps the perturbation to **one hunk with no import change**, so the revert cannot leave a stray import behind.

- It is **scoped to turn #2**. M1 sends `…user:one` and must still drain end-to-end, or the run never reaches M4.
- A plain error is **not** `ErrTrustModalPending`, so `q.pending(err)` is false and the drain takes the Warn arm — one Warn per second, ~19-20 across the window, no give-up (2 m ≫ 20 s).
- **ack #2 still lands.** The handler acks on *enqueue*, before any delivery attempt (`send_message.go:94-97, 191`), so `gotAck2` is true and the M4 branch — not the earlier ack-wait `t.Fatal` — is what fires.
- The daemon is a separately built binary; `ensurePyryBuilt` rebuilds from source, so the edit takes effect. **Check `PYRY_E2E_BIN` is unset** — set, it short-circuits to a prebuilt binary and the perturbation silently does nothing (a false negative that reads as a real result).

**What the perturbed run must show**, checked against the printed failure message:

1. the daemon window is **non-empty** and its retry-Warn count is **≥ 1** (expect ~19-20);
2. it contains at least one line emitted **after** ack #2 — the Warns themselves are that evidence;
3. it does **not** contain daemon output already present at ack #2. Concrete needle: `pyrycode starting` (`main.go:1080`) is logged once, at daemon startup, long before ack #2. It must **not** appear in the window. Offset-slicing off `len == 0` would trivially pass every other check while failing this one, which is exactly why AC-5 names it.

Record the observed Warn count and the absence of `pyrycode starting` in the PR body — that is the demonstrated proof AC-5 asks for, in place of an argument.

**Then revert the perturbation** and re-run T2 before proposing. The diff must contain no `cmd/pyry` change; confirm with `git diff --name-only origin/main...HEAD` → exactly the test file and this spec.

## What this record will and will not decide

**Will:** separate *"the drain retried and was refused"* (≈20 Warns) from *"the drain was not in the error-return arm"* (0 Warns) — the pair #1273 left fused. Under this fixture, 0 Warns narrows to *parked in `Activate` or the mid-turn hold*, because the third silent state (pending/hold retry) requires `Readiness{TrustModal:true}`, which this test never configures.

**Will not:** distinguish the two parked states from each other — both are silent at Info level for the whole window, and separating them needs either `-pyry-verbose` (rejected above) or a production-side observable. Nor does it decide *"the fresh child never spawned"* on its own: `streamsup` logs `spawning claude` / `claude exited` / `restarting after backoff` at Info (`runner.go:473, 504, 529`), so those lines will appear in the window **if they happen** — real evidence, but their absence is weak, since a child that spawned before ack #2 logs nothing afterwards. That remains a next-ticket concern (process liveness at failure time), and #1298 may be the same stall via the straggler-re-mark hypothesis.
