# Ticket #1381 — Map claude's `background_tasks_changed` roster subtype to a size-bounded daemon event

Third and last child of #1378's `system` subtype family, after #1380 (`task_started`, scalar) and #1382 (`task_updated`, scalar). This one's payload is an **array** — the family's first aggregate variant — which forces a second, genuinely new bound dimension neither scalar sibling needed.

## Implementation

- **`turnevent.BackgroundTaskRoster` / `turnevent.BackgroundTask`** (`internal/turnevent/event.go`) — two new types, placed right after `BackgroundTaskUpdated`. `BackgroundTask` is the roster's element type (`TaskID`, `TaskType`, `Description`, `TruncatedFields`) and carries no `Event` marker — it isn't one. `BackgroundTaskRoster` (`Tasks []BackgroundTask`, `DroppedTasks int`) is the event: `Tasks` is `nil` for an empty or claude-omitted roster (an empty roster is still emitted — it says nothing is alive), truncated from the tail when over cap; `DroppedTasks` is the count-dimension cut report, `0` when nothing dropped, `len(Tasks)+DroppedTasks` recovers claude's true count. No top-level `TruncatedFields` on this variant — each dimension reports at the level where it happens: text cuts ride the entry, the count cut rides the event.
- **Named `Roster`, not `Changed`, deliberately.** claude's `background_tasks_changed` names the trigger; the payload is a snapshot of everything alive. A `…Changed` name invites a consumer to read it as a delta, and reading a snapshot as a delta is one short step from inferring a finish the daemon has never observed — the name is the first line of the no-synthesized-finish rule's defense, the doc comment the second.
- **Dispatch** — one new arm, appended after `task_updated`: `case "background_tasks_changed": return p.emitBackgroundTaskRoster(line)`. Nothing else in `consumeLine` changes; `system` stays on `ignoredLineTypes`, so `TestParser_IgnoredLineTypesIsTheMeasuredSet`'s pin on `{system, rate_limit_event}` stays green untouched.
- **`systemBackgroundTasksLine` / `systemBackgroundTaskEntry`** — new decode targets. `Tasks []systemBackgroundTaskEntry`; each entry `TaskID`/`TaskType`/`Description string`, exactly the capture's three per-entry keys and nothing invented — no `tool_use_id`, no `patch` (the scalar siblings carry those because their *lines* do). `uuid` and `session_id` are absent from the decode target itself, a stronger guarantee than the test sweep: a field never declared cannot leak.
- **`emitBackgroundTaskRoster`** — peer of `emitBackgroundTaskUpdated`, same structural choices for the same reasons: decodes the **top-level** `line` bytes only (never nested — what keeps a whole roster unforgeable out of claude's own tool output, which matters more here than on either sibling since this is the one event that claims what is *alive*); undecodable payload → content-free `Debug` naming the subtype keyword only, no event, `return true`; the **count** bound runs before the loop (tail truncation, claude's order preserved, no ranking invented); the **text** bound runs per entry via the same `bound` closure shape both siblings use, declared inside the loop so `cut` is per-entry.
- **Two new cap constants**, beside the existing four: `maxTaskRosterEntries = 8` (the count dimension — no precedent in this package; 8× the one observed entry, chosen to land the worst case on a clean 8 KiB) and `maxTaskRosterDescription = 512` (a *smaller* budget than `maxTaskDescription`'s 4096 for the same field, because this is the one field in the family whose budget is multiplied by a count claude chooses, and because the authoritative full-length copy already crossed the wire on the `BackgroundTaskStarted` this entry's `task_id` joins back to). Worst case one entry: 256+256+512 = 1024 bytes; worst case one event: 8×1024 = 8192 bytes = 12.5% of the 65519-byte v2 envelope, exactly half of `maxUnrecognizedRaw`'s 16 KiB.
- **The family's single-worst-case doctrine forced a decision, not an inheritance.** `maxTaskPatch`'s doc states the doctrine (`BackgroundTaskUpdated`'s worst case chosen deliberately in line with `BackgroundTaskStarted`'s so the family has ONE number a reader can hold). Reusing the scalar caps here puts one roster entry at 4608 bytes — only a *one-entry* roster (not a roster) matches the scalar pair, and 14 entries would consume 98.5% of the envelope. Resolved as one worst case per **shape**, not per variant: scalar ≤ ~4.9 KB, roster ≤ 8 KiB — written into `maxTaskRosterEntries`'s doc; `maxTaskPatch`'s sentence is left unedited, since it still correctly describes the scalar pair.
- **No terminal/finish event synthesized (AC3).** The capturing probe never observed a task finishing, so a task's disappearance from a later roster — the only available finish signal — is not inferred into an event. Enforced structurally by the parser staying turn-stateless: no field added to `Parser`, no cross-line state, each line maps independently, so there is nothing to diff successive rosters against even if a future change wanted to.
- Field mapping and cap arithmetic built from the same committed capture #1380/#1382 used (`internal/e2e/realclaude/testdata/dropped_lines_v2.1.220.json`, `dropped_lines[12]`), read through the existing `capturedSystemLine` reader (no second reader written). The capture's 212-byte, one-entry roster proves the field mapping and nothing about either bound — both bounds are proven by lines synthesized to exceed them, which AC1 explicitly permits (no invented field *structure*, only invented array contents).

## Patterns established

- **An aggregate event needs a second, independent bound dimension a scalar event never does, and the two dimensions report at different levels.** Text truncation is a property of one entry (rides `TruncatedFields` on that entry); count truncation is a property of the whole collection (rides a field on the event itself, `DroppedTasks`, not folded into a name-only top-level `TruncatedFields{"tasks"}` that would lose *how many* were cut). Reusable whenever a future event carries a claude-controlled-length collection.
- **A family-wide "one worst case" doctrine written for scalar variants does not survive an aggregate variant unexamined**, and the fix is not to force a fit or silently abandon the doctrine — it's to state what dimension the doctrine was actually protecting (legibility: one number a reader can hold) and qualify it precisely (one number per *shape*). The qualification lives at the new constant; the old sentence is left alone because it remains true for what it describes.
- **A reflection drop-sweep written for a scalar event's top-level string fields visits nothing on an aggregate one.** `BackgroundTaskRoster` has zero top-level string fields — every carried value lives inside `[]BackgroundTask` — so a sweep that doesn't descend into a slice-of-struct field passes in silence, asserting nothing. The fix is a literal floor sized to what a correct descending sweep *must* visit (`1 entry × 3 string fields × 2 dropped keys = 6`), not a route-derived expression — #1382 already established that route-derived floors silently weaken when route count and string-field count diverge; here they don't even align in kind (one is per-event, the other per-entry).
- **A field carried once elsewhere and multiplied by a claude-chosen count earns a smaller unit budget than its single-instance sibling**, independent of the observed size — the multiplication is the argument, not thrift, and it composes with "the full-length copy is recoverable via the join key" to bound the actual harm of the smaller cap.
- **"Build the field mapping from the capture" and "the bound needs a synthesized line" are not in tension** when the rule is read as scoped to structure: a synthesized line that reuses the capture's exact key set but varies array contents or field lengths invents no field claude doesn't send. This is the same distinction #1382 drew for `Patch`'s internal shape, generalized to array length here.

## Lessons learned

(From the PR body — developer's notes, lightly trimmed.)

- A reflection drop-sweep over an aggregate event visits zero fields and passes in silence. `BackgroundTaskRoster` has no top-level string fields — every carried value lives inside `[]BackgroundTask` — so the sibling tests' top-level sweep would have asserted literally nothing while reading as a full drop proof. The literal floor (1 entry × 3 string fields × 2 dropped keys = 6) is what catches "the reflection never descended," and it is load-bearing here in a way it was not for either scalar sibling.
- The family's single-worst-case doctrine (`maxTaskPatch`'s comment) cannot survive an aggregate variant unexamined. An aggregate cannot share a scalar's worst case unless its cardinality is 1, and a one-entry roster is not a roster. Resolved as one worst case per shape rather than per variant — scalar ≤ ~4.9 KB, roster ≤ 8 KiB — written into `maxTaskRosterEntries`'s doc; `maxTaskPatch`'s sentence is left unedited because it still describes the scalar pair accurately.
- A multiplied field earns a smaller unit budget than the same field carried once. `maxTaskRosterDescription` (512) is deliberately below `maxTaskDescription` (4096) for the same text: in a roster the description is a label in a list whose length claude chooses, and its authoritative full-length copy already crossed the wire on the `BackgroundTaskStarted` the entry's `task_id` joins back to.
- The "no content in logs" rule has a count-shaped hole that string-sweeping cannot close. No entry count can be searched for reliably, so the security test asserts the exact record set instead (exactly one record, the drop, carrying the subtype keyword only) — which forbids a count attr on any path rather than hoping to grep one.
