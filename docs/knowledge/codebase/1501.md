# Ticket #1501 — `-count=1` on the four opt-in e2e recipes

`e2e-realclaude`, `e2e-liverelay`, `e2e-install` and `e2e-update` each build
their binary under test with a **subprocess** `go build`
(`ensurePyryBuilt`/`ensureRelayBuilt` in `internal/e2e`,
`internal/e2e/realclaude`, `internal/e2e/liverelay`; the two build sites in
`cmd/pyry/update_e2e_test.go`). A child process's file reads never enter the
test binary's cache key, so an edit confined to `cmd/pyry`,
`internal/brokenpyry`, or the sibling relay checkout left the key unchanged
and `go test` replayed the previous `ok` without spawning anything — a third
false-green mode alongside the two `docs/release-tooling.md` already
documented for the live-claude suite (no credentials, build failure). `make
e2e` already carried `-race -count=1`; this ticket copies only the
`-count=1` half onto the other four opt-in recipes. `make test` (line 49) is
untouched — it's untagged and reaches none of the nine subprocess build
sites, and its cache is load-bearing inside `make check`.

PR [#1562](https://github.com/pyrycode/pyrycode/pull/1562). Spec:
[`docs/specs/architecture/1501-count1-opt-in-e2e-recipes.md`](../../specs/architecture/1501-count-1-opt-in-e2e-recipes.md).
One code-review round, PASS with one non-blocking NIT.

## Implementation

- Four one-line `Makefile` edits — `-count=1` added after `-tags` on
  `e2e-realclaude`, `e2e-liverelay`, `e2e-install`, `e2e-update`. No `-race`,
  no scope change, no other flag on any of the four lines.
- One shared comment block placed above `.PHONY: e2e-realclaude` (the first
  affected recipe in file order) naming all four recipes, the subprocess-build
  mechanism, and why `test` above is deliberately excluded. A single block was
  chosen over four separate ones so a reader about to delete the flag from any
  one of the four recipes greps `-count=1` and lands on the canonical
  explanation — verified in code review to actually work, since the block's
  own text contains that string.
- No Go source changed; QA's `make check` gates (vet, race tests, staticcheck,
  substrate-guard, fake-daemon `e2e`) were unaffected and stayed green.

## Patterns established

- **A cache-replay defect needs a real on-disk edit and revert to reproduce —
  `go test -overlay=<json>` does not work for this class of question.** The
  overlay path is itself part of the command line, so it changes the cache
  key and forces a miss regardless of whether the fix under test is present.
  The house mutation-testing technique of running `go test
  -overlay=<abs-path json>` to RED-proof a logic change with no worktree
  writes doesn't transfer to cache questions — those need a real on-disk
  edit and a real revert.
- **A count-based non-vacuity check needs `-v` to be reachable.** `grep -c
  '^=== RUN'` only works if the recipe under test actually emits `=== RUN`
  lines; a bare `go test` without `-v` doesn't, so the pass condition would be
  vacuously unsatisfiable through the unmodified recipe. `GOFLAGS=-v` supplies
  it externally without editing the recipe, but since `-v` is itself one of
  Go's cacheable flags, both compared runs must use the same setting or the
  comparison isn't apples-to-apples.
- **`defaultSiblingRelayRepo` resolves relative to the compile-time source
  path, which breaks under a dispatcher worktree.** In
  `.pyrycode-worktrees/<branch>/`, `../pyrycode-relay` doesn't exist and the
  suite skips loud rather than running. Point `PYRY_RELAY_REPO` at the
  *canonical* repo root instead: `dirname "$(git rev-parse
  --path-format=absolute --git-common-dir)"`, then `../pyrycode-relay` from
  there.

## Lessons learned

**From the PR body's own "Lessons learned" section** (developer), confirmed
independently by code review's own repro:

- **`(cached)` is not the only replay tell — the durations are.** A cached
  verbose run reprints the prior run's exact per-test timing verbatim (e.g.
  `(2.31s)` identical on both runs), while two genuine executions differ
  (`2.36s` / `2.27s`). Useful for reading a log after the fact when the
  `(cached)` marker itself might be stripped or missed.
- **The spec's pass condition needs both halves checked, not just the
  absence of `(cached)`.** `-count=1` makes "no `(cached)` in the log" true
  even for a suite that skipped every test — the same count-not-exit-code
  trap `docs/release-tooling.md` already documents for the live-claude suite,
  arriving at a second site. `grep -c '^=== RUN'` being nonzero *and equal*
  across both runs is the check that actually discriminates.
- **Guard a revert with `trap … EXIT`, not `set -e`.** `set -e` skips the
  revert step when an intermediate command in the repro fails, leaving the
  probe edit (a comment appended to `cmd/pyry/relay.go`) in the tree.
