# Ticket #1168 — wire the approval-tool flags onto the interactive stream-json spawn

The interactive stream-json runner spawned claude with no permission-approval flags at all — not
`--permission-prompt-tool`/`--mcp-config`, not even `--dangerously-skip-permissions`. On a non-yolo
permission-bearing turn claude had no daemon approval tool to call, `permbridge` recorded no pending
request, and no `modal_shown` ever fanned to the phone: a fail-open gap found live on 2026-07-22 running
the T9 gate specs against real claude, which left `TestInteractiveStreamModalResolution` (#1154) red on
`main` and blocked #1083 (T9 cutover). #1106 had already built the two primitives this needed
(`permissionArgs`/`writeMCPApproveConfig`) but only wired them onto `pyry agent-run`'s stream spawn,
explicitly deferring the interactive-daemon live-wiring downstream. This ticket lays that wire.

Full design writeup: [`specs/architecture/1168-interactive-stream-permission-arg-wiring.md`](../../specs/architecture/1168-interactive-stream-permission-arg-wiring.md).

## Implementation

- `cmd/pyry/streamsup_runner.go` — new pure helper `withApprovalArgs(args []string, mcpApprovePath string) []string`: if `slices.Contains(args, "--dangerously-skip-permissions")` returns `args` unchanged (yolo — the flag is already present; no duplicate, no injection); otherwise `append(slices.Clone(args), permissionArgs(false, mcpApprovePath)...)`. `newStreamRunnerFactory(sink *streamTurnSink, mcpApprovePath string) sessions.RunnerFactory` gained the second param and its closure calls `scfg.Args = withApprovalArgs(scfg.Args, mcpApprovePath)` immediately after `mapStreamsupConfig` (which stays pure — the injection is a runtime concern one layer up, same rationale as the existing `Stdout` install). This is the **sole** stream-path-specific spawn-construction site and covers both the bootstrap runner and per-conversation runners, so a per-conversation stream session can't silently bypass the approval gate.
- `cmd/pyry/main.go` — `selectInteractiveRunner(cfg, logger)` gained a third `mcpApprovePath string` param, threaded to `newStreamRunnerFactory`. `runSupervisor` writes the `--mcp-config` file once at startup via `writeMCPApproveConfig(resolveExecutable(), socketPath)`, gated on `cfg.InteractiveRunner == "stream-json"` — the same string the runner-selection switch keys on, so the factory is never built with an empty path. Fail-closed: a write error wraps and aborts daemon startup rather than letting a non-yolo session spawn with `--mcp-config ""`. `defer os.Remove(mcpApprovePath)` removes it at daemon shutdown (content is daemon-global — `(pyry binary, control socket)` — identical across every session and respawn, so per-daemon lifecycle is correct, not per-spawn).
- Yolo signal: read `--dangerously-skip-permissions` off the spawn's own args, per-spawn, rather than plumbing a separate boolean. Both yolo entry points funnel through that one flag — the operator's bootstrap pass-through and `internal/sessions.claudeSettingsArgs`'s per-session-YOLO append — so probing the args is robust to both and evaluated fresh at every spawn.
- Tests: `cmd/pyry/streamsup_runner_test.go` extended with `TestWithApprovalArgs` (yolo-row unchanged / non-yolo-row = input + exact `permissionArgs(false, path)` tail / non-mutation via clone) plus a factory-construction row asserting the four injected flags appear (non-yolo) or don't (yolo, flag present exactly once). `cmd/pyry/interactive_runner_test.go`'s four `selectInteractiveRunner` subtests updated to the three-arg signature (`""` in tests — nil-factory-on-pty, shared-sink-instance, and loud-error-on-garbage assertions unchanged).

## Patterns established

- **Read the yolo bit off the live spawn's own args instead of threading a separate boolean.** `--dangerously-skip-permissions`'s presence is the single deterministic signal for "is this spawn yolo", checked at the point of construction rather than carried as a second parameter that could drift from what the args vector actually says. Reusable whenever a downstream construction site needs to know an upstream toggle that's already expressed as a flag on the same argv it's building.
- **Daemon-global config, written once, removed at shutdown — not per-spawn.** When a generated file's content depends only on daemon-lifetime constants (binary path, socket path), write it once at startup gated fail-closed, and let every spawn share the path by reference. Per-spawn regeneration would be pure waste; per-spawn removal would race a still-running child reading it.
- **Injecting in the factory closure, not the pure mapper.** `mapStreamsupConfig` stays a fully-inspectable pure function; anything that depends on daemon state external to the `supervisor.Config` being mapped (here, `mcpApprovePath`) belongs one layer up, in the closure that calls the mapper — same rationale #1098 used for installing `Stdout`.

## Security review

Code review: **PASS**, no findings. Verified: blast radius contained (every call site of both changed signatures updated — 5 for `selectInteractiveRunner`, 3 for `newStreamRunnerFactory`); the yolo probe is sound because both spawn paths bake `claudeSettingsArgs` before `stripSessionIDFlags` runs (which only drops `--session-id`/`--resume`), so the skip-permissions flag always survives to where `withApprovalArgs` reads it; config-file lifecycle is correct (fail-closed write, `defer os.Remove` after the blocking pool/supervisor drain returns); AC5 (PTY argv byte-equivalent) holds **structurally** — the injection is gated on `"stream-json"` and the PTY path resolves a nil factory, so it cannot reach this code, not merely by convention. Architect's spec security review (self-review, PASS): fail-closed startup posture, `--strict-mcp-config` closes the shadow-server hazard, socket value is the daemon's own `resolveSocketPath` result (correct daemon, not a stale/default one), no independent bypass introduced alongside the pre-existing yolo flag, no secrets in the written config (mode 0600, pyry-bin + socket-path only). `make e2e-realclaude` ran clean (skip-path in the no-login dispatch env); the live green run of `TestInteractiveStreamModalResolution` was the author's 2026-07-22 finding that motivated this ticket.
