# Ticket #1411 — Prove a healthy run emits no usage-limit frame, at both test tiers

Closes the loop #1404/#1405/#1410 opened: `emitRateLimit`'s three-rung gate (parser-tier only until now)
had never been proven to hold end-to-end — parser → `turnbridge.MapEvent` → the interactive v2 emitter →
an encrypted frame on a connected client. #1410 made that proof reachable by giving the mapper a case for
the variant; before it, any wire-level assertion here would have been vacuously green. This ticket adds
the two tiers that are not substitutes for each other: a hermetic pair that feeds the exact captured bytes,
and a live standing sentinel that watches what claude sends today. No production code. PR
[#1413](https://github.com/pyrycode/pyrycode/pull/1413).

## Implementation

- **`internal/e2e/internal/fakeclaude/main.go`** — a new value-carrying rider,
  `PYRY_FAKE_CLAUDE_STREAM_RATE_LIMIT` (`envStreamRateLimit`), default-off. Unlike the boolean
  `envStreamBogus`, the value **is** the fed line's `rate_limit_info.status` — the gate's sole
  discriminator — so the benign case and its non-benign control are provably on one path, differing in
  exactly one string. `runStreamJSON` grew a fifth parameter (`rateLimitStatus string`) rather than reading
  the env itself, keeping it a pure I/O seam; a five-positional-parameter signature was flagged and
  accepted rather than collapsed into a `streamRiders` struct — refactoring three existing call sites for
  no behaviour change would have fought Simplicity First. `writeRateLimitEvent` writes one top-level
  `rate_limit_event` line **before** the reply, transcribing all six keys of the captured
  `rate_limit_info` object (`dropped_lines_v2.1.220.json`) — not just the three
  `streamsup.rateLimitInfo` decodes — with `status` substituted for the caller's value. `uuid`/`session_id`
  are the fake's own synthetic constants, not the capture's templated placeholders, and neither is in the
  parser's decode target. Empty status ⟹ rider off ⟹ byte-identical output; the parser's third rung (absent
  or empty `rate_limit_info`) is therefore unreachable through this seam by construction and stays
  parser-tier, as prescribed.
- **`internal/e2e/internal/fakeclaude/stream_detect_test.go`** — two new unit tests mirroring the bogus
  rider's pair: `TestRunStreamJSON_RateLimitRider` is table-driven over the two statuses the hermetic e2e
  drives (`"allowed"`, `"e2e-not-allowed"`), pinning that the two cases differ **only** in `status` and that
  the object's other five keys, `uuid`, and `session_id` are identical across both rows — the cheapest tier
  at which "the knob's value is the gate's sole discriminator" is checkable.
  `TestRunStreamJSON_RateLimitRiderOffIsByteIdentical` pins default-off. Existing calls to `runStreamJSON`
  (10 call sites total, at the sizing ceiling) each took a new trailing `""`.
- **`internal/e2e/relay_v2_stream_rate_limit_test.go`** (new, `//go:build e2e`) — one shared
  `driveRateLimitTurn` helper plus two tests, lifting the drive shape from
  `relay_v2_stream_unrecognized_test.go` (pair → UUID double-seed → fakerelay → daemon → phone dial →
  interactive handshake → seal-send → drain-until-`turn_end`). The helper asserts none of the ACs itself —
  it `t.Fatalf`s only on transport/decode faults, returning with `sawTurnEnd == false` on the 30s drain
  deadline — so the milestone assertions in the tests stay live values, not dead code shadowed by a helper
  that already fataled.
  - `TestRelayV2_StreamRateLimitBenignReachesNoPhone` (AC-1): drives `"allowed"`. Asserts, **in order**, the
    reply arrived (`sawEcho`) and the turn closed (`sawTurnEnd`) — both fatal — then `len(rateLimited) == 0`
    and `unrecognized == 0`. The milestone-first ordering is prescribed: a zero read off an incomplete run
    proves nothing.
  - `TestRelayV2_StreamRateLimitNonBenignReachesPhone` (AC-2): drives `"e2e-not-allowed"`, same path, same
    helper. Asserts exactly one frame, with `ConversationID`/`Status`/`LimitType`/`ResetsAt` matching the fed
    values and `TruncatedFields == nil` (not `[]` — `RateLimitedPayload` has no nil→`[]` `MarshalJSON`, so
    this distinguishes "nothing was cut" from a positive empty list on the wire, for the first time through a
    real daemon rather than a unit test).
  - **Why AC-2 exists, not just AC-1**: a zero-assertion does not prove its own input arrived. The reply's
    milestones (`sawEcho`, `sawTurnEnd`) prove the *reply* flowed, not that the *fed line* reached
    `emitRateLimit`. Three bugs would leave AC-1 green for the wrong reason — a misspelled rider env var, a
    malformed `"type"` routing the line to the unrecognized lane instead, or the line being dropped before
    the parser — and AC-2's non-benign control kills all three by demanding exactly one frame on the same
    path. Both tests also assert `unrecognized == 0`, turning the second bug into an immediate diagnosis
    rather than an inference.
  - The interactive handshake (not a bare/non-interactive one) is load-bearing: `rate_limited` is
    capability-gated, so a non-interactive phone would see zero frames in *both* tests, making AC-1
    vacuously green. AC-2 is what would have caught that, too.
- **`internal/e2e/realclaude/interactive_stream_liveness_test.go`** (AC-3) — one new
  `case protocol.TypeRateLimited:` in `drainForCompletedTurn`, beside the existing
  `TypeUnrecognizedMessage` sentinel, inherited by all six live stream specs with no per-spec opt-in.
  `t.Fatalf` unconditionally (no conversation filter — a usage limit is account-scoped), printing `Status`,
  `LimitType`, `ResetsAt`, `TruncatedFields`, `ConversationID` and naming both readings: a limit genuinely in
  force on the account (not a bug — re-run after the window resets), or `streamsup.benignRateLimitStatus`
  ("allowed") having gone stale against a claude that renamed or recapitalised the value. Zero production
  logging is touched; the printed fields are a test failure message in an opt-in, locally-run suite, not the
  daemon's operational log that `emitRateLimit`'s own doc forbids payload data from reaching.
- **`docs/knowledge/features/protocol-package.md:1219`** (AC-4) — the one evergreen sentence naming the live
  sentinel as "#1411, still open" now names both proof tiers in past tense. No other evergreen site made
  the claim (swept at f9ae5ab); frozen specs and per-ticket `codebase/` records are historical and were left
  alone.

## Patterns established

- **A zero-assertion needs a control that shares the feed path and differs only in the gate's
  discriminator.** Inverting a positive-count template (`len(unrecognized) != 2`) to a zero-assertion
  silently drops the template's self-proving arrival property — a fed line that never arrives makes a
  positive count wrong, but leaves a zero-count green. The reply's own completion milestones (an assistant
  delta, a turn end) do not substitute; they prove the reply flowed, not that the fed input reached the
  point under test. The fix generalizes beyond this ticket: whenever a hermetic test asserts "the gate
  produced nothing," pair it with a twin driven on the identical path that differs in exactly the one byte
  or field the gate branches on, and demand a positive count from that twin.
- **A value-carrying env knob, not a boolean, keeps two divergent test cases provably on one path.** Where
  a boolean rider (`envStreamBogus`) is sufficient when there's one on/off behaviour to prove, a rider whose
  two required cases differ only in a single field's value should carry that value directly
  (`PYRY_FAKE_CLAUDE_STREAM_RATE_LIMIT=<status>`) rather than being expanded into two booleans or two env
  vars — the latter would let the two cases drift apart in everything except the field the test cares about.
- **`GOFLAGS=-overlay=<path>` reaches child `go build` processes; a bare `-overlay` on the outer `go test`
  does not**, per the PR's own lessons-learned (below). Relevant to any future mutation-discrimination check
  against this e2e harness, since it spawns `fakeclaude` and `pyry` as separate `go build` artifacts.

## Lessons learned

From the PR body's own "Lessons learned" section (developer, verbatim):

- A nested `go build` does not inherit `-overlay`; `GOFLAGS` does. The e2e harness builds fakeclaude and
  `pyry` in child `go build` processes, so a plain `-overlay` on the outer `go test` mutates only the test
  binary — a mutation of the fake or the daemon silently applies to nothing and the run reads as a false
  green. Passing `GOFLAGS=-overlay=<abs-path>` in the environment reaches the children. Any mutation check
  against a spawned-subprocess harness needs this, or it discriminates nothing.
- Inverting a positive template to a zero-assertion silently drops the template's arrival proof (see
  Patterns established above for the generalized form). The recovered proof is a control differing only in
  the gate's discriminator — which is also why the rider's knob carries a value rather than a boolean.

Discrimination checks (six `go overlay` mutations, no worktree writes) all went RED on the intended
assertion per the PR's testing table; the load-bearing row is the rider's env var misspelled at the test
end, which left the benign (zero-assertion) test green and only the non-benign control catching it
(`got 0, want exactly 1`) — the exact vacuity AC-2 exists to rule out.
