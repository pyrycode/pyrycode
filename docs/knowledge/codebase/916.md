# Ticket #916 — default `transport.Config.WriteTimeout` when unset

Reliability-review fix (2026-07-10, question 5: "a silent default that hides a mistake"). A
zero-value `Config.WriteTimeout` made `sendPump` wrap every write in an already-expired context
(`context.WithTimeout(ctx, 0)`), so every `conn.Write` failed instantly with deadline-exceeded,
`serve` tore the conn down, and the client entered a permanent connect-disconnect loop. The logs
(`transport: connected` then instantly `transport: disconnected`) read as a network fault, not a
config mistake — expensive to misdiagnose. The sole production caller
(`internal/relay/connection.go:130`) already passes `10 * time.Second`, so this only bit a new
consumer or a test that omitted the field.

## Implementation

- **New `defaultWriteTimeout = 10 * time.Second` constant** in `internal/transport/wssclient.go`,
  deliberately kept outside the existing `// Wire-spec constants` block — it's a local send-I/O
  bound, not a `docs/protocol-mobile.md`-derived cadence value. Kept numerically in sync with the
  production caller by comment convention, not by a shared symbol (matching the existing posture
  for the wire-spec constants — no enforcement, no observed drift).
- **`New`** now defaults a non-positive `WriteTimeout` to `defaultWriteTimeout`, inserted right after
  the existing `Logger == nil` panic and before the `Client` struct literal — mirrors the sibling
  defaulting posture already used for ping/pong/backoff cadence knobs. `<= 0` (not `== 0`) so a
  negative duration is also treated as unset. Mutates the local `cfg` before it's copied into
  `c.cfg`, so the default is observable on the constructed `Client`, not just applied per-write.
- **Fix lives in `New`, not `sendPump`** — defaulting once in the constructor keeps the value fixed
  and inspectable; defaulting at the `sendPump` call site would re-evaluate per frame and leave
  `c.cfg.WriteTimeout` reading `0` to any inspector.
- **`Config.WriteTimeout` doc comment** promoted from the struct-level comment to a field-level one,
  stating both the existing "not an inactivity timeout" contract and the new unset-defaults-to-10s
  behavior.
- **`internal/relay/connection.go:130`'s explicit `10 * time.Second`** was deliberately left
  untouched — the two 10s values are intentional and independent (package default = safety net for
  unset configs; production caller = explicit and self-documenting). Coupling the caller to the
  package default was out of scope.

## Tests

- `TestNew_DefaultsWriteTimeout` (table-driven, white-box `package transport`): unset (`0`) → `10s`,
  negative (`-1`) → `10s`, positive (`3s`) → preserved unchanged. Asserts directly on
  `c.cfg.WriteTimeout`, no network.
- `TestNew_UnsetWriteTimeout_SendSucceedsEndToEnd`: drives a real send over the existing
  `newTestRelay` seam with `WriteTimeout` deliberately omitted from `Config`. Non-vacuity: under the
  pre-fix bug, the zero `WriteTimeout` would make `sendPump`'s first `Write` fail instantly, the conn
  would drop, and no echo would ever return — a successful round-trip is a genuine regression catch,
  not a tautology.

## Patterns established

- Config-knob defaulting belongs in the constructor (`New`), applied once by mutating the local
  `cfg` before the struct literal — not at the read call site. This is now the third knob family
  (ping/pong, backoff, and now `WriteTimeout`) following this shape; treat it as the standing
  convention for any future optional-looking `transport.Config` field.
- `<= 0` over `== 0` for duration-defaulting guards, so a caller's negative value (a plausible typo,
  e.g. a missing digit turning `10s` into `-10s`... unlikely, but a sign-flip elsewhere) doesn't slip
  through as "unset but non-zero."
