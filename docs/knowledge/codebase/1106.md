# Ticket #1106 — streamsup spawn-arg injection: non-YOLO permission-prompt-tool + mcp-config, YOLO skip-permissions

The enforce-vs-skip switch for the whole Streamrunner Interactive permission bridge (#1079 → #1103–#1106). `buildStreamRunnerClaudeArgs` (`cmd/pyry/agent_run.go`) used to unconditionally inject `--dangerously-skip-permissions`. This ticket makes that injection conditional on a `yolo bool` and adds the non-YOLO branch: the `--permission-prompt-tool mcp__pyry_approve__approve --mcp-config <path> --strict-mcp-config --permission-mode default` args the T1 spike (#1075) proved route every tool use through `pyry mcp-approve` (#1105) and, behind it, the daemon's `permbridge` approval registry (#1103/#1104). Split from #1079; blocked by #1105 (merged).

Full design writeup: [`specs/architecture/1106-streamsup-permission-arg-injection.md`](../../specs/architecture/1106-streamsup-permission-arg-injection.md).

## Implementation

- `cmd/pyry/mcp_config.go` (new, 127 lines) — two runner-agnostic units, deliberately taking no `agentRunArgs` so the downstream `streamsup` live-wiring can call them directly:
  - `permissionArgs(yolo bool, mcpConfigPath string) []string` — the security-load-bearing switch. `yolo=true` → exactly `["--dangerously-skip-permissions"]`. `yolo=false` → exactly `["--permission-prompt-tool", approveToolRef, "--mcp-config", mcpConfigPath, "--strict-mcp-config", "--permission-mode", "default"]`. `approveToolRef = fmt.Sprintf("mcp__%s__%s", mcpServerName, approveToolName)` is derived from the `pyry mcp-approve` subcommand's own constants (`cmd/pyry/mcp_approve.go`, #1105) so the tool reference cannot drift from what that subcommand advertises. `--strict-mcp-config` is non-negotiable in the non-YOLO arm: without it, a `.mcp.json` planted in the workdir could register a fake/shadowing `pyry_approve` server and silently defeat enforcement.
  - `renderMCPApproveConfig(pyryBin, socketPath string) ([]byte, error)` / `writeMCPApproveConfig(pyryBin, socketPath string) (string, error)` — generate the `--mcp-config` JSON (`{"mcpServers":{"pyry_approve":{"command":<pyryBin>,"args":["mcp-approve","-pyry-socket",<socketPath>]}}}`) and write it to a per-spawn `os.CreateTemp("", "pyry-mcp-approve-*.json")` tmp file (mode 0600, mirrors `internal/agentrun/settings.writeSettings`). **Fail-closed:** an empty `pyryBin` or `socketPath` returns an error and nil bytes — this function can never emit a bare `["mcp-approve"]`, which would resolve to the *default*-named daemon instance's socket (wrong daemon, silent enforcement failure — the AC-4 hazard the ticket exists to close). The socket sits as the first token after `mcp-approve` in the args vector, exactly where `splitClientFlags` (`main.go:336-358`) peels `-pyry-*` value-flags off the front.
- `cmd/pyry/agent_run.go` — `buildStreamRunnerClaudeArgs` signature changed to `(parsed agentRunArgs, yolo bool, mcpConfigPath string) []string`; the hardcoded `--dangerously-skip-permissions` element is replaced by a spread of `permissionArgs(yolo, mcpConfigPath)` in the same argv slot (after `--verbose`, before `--append-system-prompt-file`). The sole production caller, `runAgentRunStreamRunner` (the legacy `PYRY_USE_STREAMJSON=1` path), passes `(parsed, true, "")` — byte-for-byte unchanged emitted argv.
- Tests (`cmd/pyry/mcp_config_test.go`, new, 185 lines; `agent_run_test.go` extended): exact-slice pins for both `permissionArgs` arms, a drift guard asserting `approveToolRef == "mcp__"+mcpServerName+"__"+approveToolName`, `renderMCPApproveConfig` content + fail-closed-on-empty-input cases, `writeMCPApproveConfig` on-disk byte-equality against `renderMCPApproveConfig`'s output, and `TestBuildStreamRunnerClaudeArgs_Shape` extended with a non-YOLO row alongside the unchanged YOLO golden row.

## Patterns established

- **Runner-agnostic switch, single production caller today.** `permissionArgs`/`renderMCPApproveConfig`/`writeMCPApproveConfig` take no `agentRunArgs` and know nothing about `streamrunner` vs `streamsup` — `buildStreamRunnerClaudeArgs` is just the first consumer to thread the toggle through. The downstream `streamsup` live-wiring (not yet landed) is expected to call these two units directly rather than duplicating them.
- **Fail-closed-by-construction beats a documented caller contract.** The empty-`socketPath`/`pyryBin` guard in `renderMCPApproveConfig` is deterministic code enforcing the AC-4 invariant (never emit a config that resolves to the wrong daemon), not a convention the caller is trusted to honor — belt-and-suspenders where the safety net is different fabric from the stochastic "caller passes the right socket" rule.

## Lessons learned

- **Byte-equality between a generated file and its render function needs `f.Write`, not `json.NewEncoder(f).Encode`.** `internal/agentrun/settings.writeSettings`'s recipe (`os.CreateTemp` → `json.NewEncoder(f).Encode` → `Close`) was the natural template to mirror, but the encoder appends a trailing `\n` — that would make `writeMCPApproveConfig`'s on-disk bytes diverge from `renderMCPApproveConfig`'s returned bytes, breaking the byte-equality test asserting the two match. `writeMCPApproveConfig` uses `f.Write(b)` on the pre-marshaled bytes instead. Worth checking this any time a new writer is templated off an `Encode`-based one and the test asserts byte-for-byte parity with a separate render step.

## Security review

Code review: **PASS**, one NIT (`approveToolRef` could be a compile-time `const string` concatenation instead of an init-time `var fmt.Sprintf` — both operands are untyped string constants; the existing `TestApproveToolRef_DriftGuard` pin makes the current `var` form equally safe, so left as-is). Architect's spec security review (self-review, PASS) is on record in the spec doc — see AC-3/AC-4 coverage there. `make e2e-realclaude` gate passed.

Downstream note carried forward (not a finding, not gating): when the non-YOLO branch is wired to a live spawn, the caller must choose `--allowed-tools` carefully — allowlisted tools bypass the approval-prompt tool by design, so an overly broad allowlist narrows the enforcement gate even with `permissionArgs(false, ...)` wired correctly. That's the live-wiring caller's contract, out of scope here.
