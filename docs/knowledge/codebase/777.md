# Ticket #777 — pace the v2 mid-turn-reconnect replay (one event per Run pass)

The v2 session manager is single-goroutine — "the loop is the lock" — which makes the
Noise `CipherState` single-writer invariant structural (`s.send.Encrypt` and the re-key
swap all happen on the one `Run` dispatch goroutine). That posture is correct **only while
every per-conn op is bounded-small**, and one was not: `replayMissed` (#647) served a
mid-turn-reconnect replay by sealing and forwarding the **entire** retained ring tail (up
to `MaxEventsPerConversation = 1024` events) **inline in a single Run pass**. A phone
reconnecting with a stale `last_event_id` could therefore monopolise `Run` for the whole
batch — no other connection's delivery, inbound frames, wakes, or snapshot requests were
serviced until the replay finished. A latent fairness/latency cliff (fine at today's
scale, filed from the 2026-07-03 Cross-Repo Code Review). This ticket **paces** the replay
to forward one frame per Run pass, mirroring the existing `drainOnce` push-drain precedent,
so the reschedule changes only *when* frames are forwarded (interleaved with the select),
never *where* (still `s.send.Encrypt` on `Run`) — the seal single-writer invariant is
untouched. `security-sensitive`; spec-stage security review verdict **PASS**.

## Implementation

One production file changes (~160 net LOC), additive — no new file, no new package, no new
exported surface, no signature change, no new goroutine topology. The mechanism reuses the
**existing** cap-1-channel + non-blocking-send + re-signal pump idiom (`drainCh`/`drainOnce`,
#610) and the shared `forwardEnvelope` seal-and-forward path.

| File | Change |
|---|---|
| `internal/relay/v2session.go` | **The paced replay drain.** Two new Run-owned fields: `V2Session.replayQueue []eventring.Event` (the not-yet-forwarded replay tail; nil/empty ⇒ no replay in flight) and `V2SessionManager.replayCh chan struct{}` (cap-1, initialised beside `drainCh` in `NewV2SessionManager`). One new `Run` select arm `case <-m.replayCh: m.drainReplayOnce(runCtx)`. `replayMissed`'s inline `for _, ev := range events` loop replaced by *store-and-signal*: keep the ring read + gap→`emitResync` + the #663 `min(afterID, newest)` clamp inline, then (if the tail is non-empty) `s.replayQueue = events` + a non-blocking send on `m.replayCh`; return. New method `drainReplayOnce` (structural copy of `drainOnce` over `m.sessions`, no `pushMu`): scan for the first session with a non-empty tail, pop the head, `forwardEnvelope` it, advance `s.replayThrough = ev.ID` on success. `drainOnce` gains a **gate**: it snapshots the set of replay-pending conn-ids from `m.sessions` *before* taking `pushMu`, then skips those conns when selecting a live envelope to pop (and when computing `more`). `closeWith` nils `s.replayQueue` beside the timer nils. |

### Why a dedicated replay queue, not the existing push queue

The ticket floated two mechanisms — (a) feed replay events through the existing per-conn
push queue so `drainOnce` interleaves them, or (b) a dedicated per-conn replay cursor the
Run loop advances one frame per pass. **The architect chose (b), forced by two hard facts:**

1. **Drop policy would gap the replay.** The push queue is bounded at `pushQueueCap = 256`
   with a drop-oldest-delta policy; a replay batch is up to `MaxEventsPerConversation = 1024`
   events — 4× the cap. Routing it through the push queue would silently evict the oldest
   queued replay deltas → exactly the "partial, gap-ful replay" AC #2 forbids. The dedicated
   `replayQueue` is bounded only by what `ring.After` already materialised, so there is no
   drop and no gap.
2. **The trailing watermark can't share the guarded path with a pre-set watermark.**
   `forwardEnvelope`'s dedup guard drops any envelope with `*EventID <= s.replayThrough`.
   Replay works only because `replayThrough` *trails one event behind* the frame being
   forwarded. If replay frames flowed through the push path with `replayThrough` pre-set to
   `newest`, the guard would drop every one. Per-event advancement needs a dedicated drain
   that owns the advance step.

### Data flow (mid-turn reconnect of conn A while a turn streams live)

```
handleNoiseInit(A) success tail  [Run pass N]
  ├─ A → V2StateOpen, push queue created, A now enumerable
  └─ replayMissed(A, afterID): ring.After → events
        gap?  → emitResync, return                 (unchanged path, never touches the queue)
        else  → replayThrough = min(afterID, newest)   (#663 clamp)
                len(events)==0 → return             (caught up: the clamp is all the work)
                A.replayQueue = events; signal replayCh; return
  Run returns to its select ───────────────────────────────────────────►

[pass N+1..]  a fair select interleaves:
  replayCh → drainReplayOnce: forward ONE (e_k), replayThrough=k, re-signal replayCh
  Frames   → conn B's noise_init serviced   ◄── B not blocked (AC #1)
  replayCh → forward e_{k+1} … (one per pass) …
  drainCh  → A's live events?  GATED (A.replayQueue non-empty) → skip, stay buffered
  …
  replayCh → forward the last frame; A.replayQueue empty; replayThrough=newest
             → signal drainCh
  drainCh  → A's buffered live events now drain, in order, all id > newest  (AC #2)
```

## Patterns established

- **A dedicated cap-1-channel pump per unbounded per-conn op — the `drainOnce` precedent,
  applied a second time.** #610 built `Push` → per-session `pushQueue` → `drainCh` (cap-1,
  non-blocking send) → `drainOnce` (pop **one**, forward, re-signal if more) precisely so a
  slow send can't re-block the single Run loop. #777 mirrors it exactly for replay:
  `replayMissed` stores the tail + signals `replayCh` (cap-1), and `drainReplayOnce` forwards
  one frame per pass + re-signals while any session still has a tail. The queue lives on the
  session; the channel carries `struct{}` (wakeup only, references no session, spawns no
  goroutine), so one cap-1 channel covers concurrent multi-conn replays. When a per-conn op
  is unbounded, the fix is *pace it through a one-per-pass drain*, not move it off `Run` —
  the latter would dismantle the single-owner `CipherState` invariant.
- **Ordering is now preserved by a gate, not by inline completion.** #647 guaranteed
  "replay precedes live" structurally — the whole replay finished inline before `Run`
  returned to service `drainCh`. Paced replay makes that false, so the guarantee is
  re-established by two composed, *deterministic* facts (belt-and-suspenders, both fabrics
  code): (1) `replayMissed` populates `replayQueue` on Run pass N, *before* `Run` returns to
  its select — and a conn only becomes visible to the off-Run live emitter via `ActiveConns`
  (which funnels onto `Run`, serviced no earlier than pass N+1), so no live event can enter
  A's push queue before its `replayQueue` is populated; (2) the new `drainOnce` **gate**
  holds A's push queue un-drained while `A.replayQueue` is non-empty. Result: replay ids
  (all ≤ `newest`, ascending) reach the wire before live ids (all > `newest`). The
  `replayThrough` guard remains the belt for any straggler live dupe with id ≤ `newest`.
- **Read the gate set outside `pushMu`; skip inside it.** `drainOnce` snapshots the
  replay-pending conn-ids from `m.sessions` *before* taking `pushMu`, then skips them inside
  the existing `pushMu`-guarded scan. `m.sessions` and `replayQueue` are Run-owned and
  `drainOnce` runs on `Run`, so the read needs no lock — and keeping it outside `pushMu`
  preserves that lock's "guards only `m.queues`, taken alone" invariant.
- **The re-signal on the forward-error path is load-bearing, not defensive.** When
  `forwardEnvelope` errors mid-replay (session vanished / seal failure), the errored conn's
  tail is abandoned (`replayQueue = nil`, matching the old inline loop's early `return`) —
  but the "any session still has a tail?" re-signal scan **still runs**. The single cap-1
  `replayCh` drives *every* conn's pump, so skipping the re-signal on the error path would
  strand a *different* session's still-pending replay.
- **Seal single-writer preserved, not weakened (AC #3).** Every replay frame is still sealed
  by `s.send.Encrypt` inside `forwardEnvelope` on the `Run` goroutine; pacing changes only
  the interleaving of forwards with the select. Two forwards for one conn are never
  concurrent (both on `Run`), so the Noise send-nonce sequence stays monotonic exactly as in
  the inline loop. A re-key swap landing between two paced forwards composes correctly —
  `forwardEnvelope` reads `s.send` at execution time, so each frame seals fully under the
  current key (whole-old or whole-new, never torn). Each event is popped once and forwarded
  once; on error the tail is abandoned, never retried — no double-seal / nonce-reuse path.

## Lessons learned

- **The pre-existing replay tests passed only by a timing coincidence, not a guarantee.**
  `waitConnOpen`'s 2 ms poll gap gave `Run` enough idle time to drain a small *inline*
  replay before the poll observed the conn — so "conn enumerable ⇒ replay forwarded"
  happened to hold. Paced replay makes that false (the tail drains over passes *after* the
  conn appears), so the harness (`reconnectScenario`) had to switch from `waitConnOpen` +
  immediate `snapshot()` to polling `waitForEnvelopes(t, rec, wantEnvs)` for the final frame
  count. The existing replay tests assert *final forwarded content* (ids/order/payloads),
  which is unchanged — only the wait mechanism moved. (Lifted from the PR's Lessons-learned
  section.)
- **`drainReplayOnce`'s `replayCh` re-signal must run on both the success and the
  forward-error path.** Abandoning the errored conn's tail without re-signalling would
  strand a *different* session's still-pending replay, because the single cap-1 channel
  drives all conns' pumps. (Lifted from the PR's Lessons-learned section; see the "load-
  bearing" pattern above.)

## Out of scope (deferred)

- **Cross-conn fairness under a reconnect storm.** Map-random selection across `m.sessions`
  is fair in expectation (matches `drainOnce`). If a many-conn simultaneous-large-replay
  pattern is ever *observed* to starve a conn, a round-robin cursor could replace map-random
  — the same latent concern `drainOnce` already carries. Deferred per Evidence-Based Fix
  Selection.
- **A separate `replayQueue` cap.** The tail is already bounded by ring retention
  (≤ `MaxEventsPerConversation = 1024`); a second cap would only reintroduce the drop/gap
  risk that motivated *not* using the push queue. Left uncapped by design.
- **Re-key / handshake head-of-line blocking (~100µs) and the snapshot render (≤4KB
  buffer).** Bounded-small, accepted per spec #453 — explicitly *not* touched. This ticket
  paced the one **unbounded** op only; it is not a per-connection-goroutine rewrite of the
  manager (that would dismantle the documented single-owner `CipherState` invariant).

## Testing

All new/changed tests live in `internal/relay/v2session_replay_test.go` (same package,
stdlib only, `-race`-clean). The harness rework (switching `reconnectScenario` to
`waitForEnvelopes`) came first; the existing #647/#663 replay tests stayed green after the
swap since they assert final forwarded content, not open-instant snapshots. Two new
same-package helpers support deterministic direct-drive tests: `offlineHandshake` (a
manager-less paired handshake yielding the responder `send` + initiator `recv` CipherStates,
so an open session can be injected and `drainReplayOnce`/`drainOnce` called on the test
goroutine) and `newInjectManager` (a manager with `Run` **not** started).

- `TestV2Session_Reconnect_Paced_OnePerRunPass` (**core #777 invariant**) — one
  `drainReplayOnce` pass forwards exactly ONE replay frame, leaves the rest queued, and
  advances `replayThrough` by a single event. Driven single-goroutine (no `Run`), the
  watermark-guard-test pattern.
- `TestV2Session_Reconnect_LiveGated_DrainOnceSkipsReplayingConn` (**AC #2 gate**) — while a
  conn has a non-empty `replayQueue`, `drainOnce` must NOT pop its buffered live events; once
  the tail drains, `drainOnce` releases them, so wire order is replay ids (ascending) then
  the live id. Direct `drainOnce`/`drainReplayOnce` calls, no timing.
- `TestV2Session_Reconnect_LargeReplay_DoesNotBlockOtherConn` (**AC #1 fairness**) — conn A
  reconnects with a ~200-event tail; while it drains, conn B's `noise_init` is fed on
  `Frames`. Asserts B's `noise_resp` lands *before* A's final replay frame in the recorder's
  ordered snapshot. Under a fair select, "B serviced only after all of A" has probability
  ≈ 2⁻²⁰⁰ — deterministic in practice (noted in a comment).
- `TestV2Session_Reconnect_LiveInterleave_OrderedAfterReplay` (**AC #2 end-to-end**) — a
  live event pushed to A as its replay drains reaches the wire AFTER every replay frame,
  never interleaved. Exercises the real `Run` select + `drainOnce` gate + `drainCh`
  re-signal. The ordering assertion holds regardless of whether the live push lands before
  the tail fully drains, so it never false-fails on timing.
- `TestV2Session_Reconnect_PacedReplay_Race` (**AC #3 race**) — a paced replay draining
  concurrently with off-`Run` live `Push`es to the same conn AND a second conn's handshake:
  no data race, no send-nonce violation. Proves `replayQueue`/`replayThrough` are never
  touched off `Run` and every `s.send.Encrypt` stays serialised on `Run`.
