# Ticket #994 — auto-continue claude's Settings Warning startup dialog + log it

Split from #988's design doc (issue only, not a shipped ticket). Observed live 2026-07-15: the operator's daemon wedged **every** UI-created conversation on claude's informational Settings Warning startup dialog — a malformed `.claude/settings.json` in the workdir made claude stop at startup with `Settings Warning … 1. Continue / 2. Fix with Claude / 3. Exit and fix manually`, and every queued turn parked forever in the silent `msgqueue` retry loop. The fix auto-answers Continue (claude's own default) and logs it locally, instead of wedging or forwarding it as a remote modal.

## Implementation

One new file + a small `supervisor.go` wiring change, entirely inside `internal/supervisor`:

- `internal/supervisor/settings_warning.go` (new): `waitReadyAutoContinue(ctx, waitReadyDeps) error` — composes **in front of** the existing `readyForDelivery` trust gate (#1013), not in place of it. It calls `d.waitReady(ctx)`; if the error is a `*tuidriver.UnexpectedModalError` **and** the content co-signal `isSettingsWarning()` is true, it logs a `slog.Warn` (`workdir` field), sends `keystrokeFn(sess, keyAnswer, "1")`, polls for the dialog to clear (`settingsWarningDismissed`, bounded by `settingsWarningDismissTimeout`/`settingsWarningDismissPoll`, ~2s/150ms, mirroring tui-driver's `DefaultAnswerConfirmTimeout`), then re-gates readiness **once** (no recursion). Every other outcome — ctx error, `*ProcessExitedError`, `ErrTrustModalPending`, or any other unexpected modal — passes through unchanged, preserving fail-loud.
  - `detectSettingsWarning(sess *tuidriver.Session) bool` is the sole claude-screen literal pyrycode holds outside tui-driver (`settingsWarningAnchor = "Settings Warning"`), justified in-file: it's consulted only *after* tui-driver has already structurally confirmed a blocking selection dialog (#224), so it's a content co-signal layered on a trusted structural one, not a standalone screen-scrape — `cmd/substrate-guard` stays green because tui-driver owns no `ModalClass` for this dialog.
- `internal/supervisor/supervisor.go`: new `settingsWarningFn func(sess *tuidriver.Session) bool` field on `Supervisor` (same set-once-in-`New`, immutable-post-`New`, test-overridable seam as `keystrokeFn`), wired to `detectSettingsWarning` in `New`. Both `deliverViaSession` call sites (the direct nil-`ResolveTranscript` path and the growth-confirm closure) now route through `waitReadyAutoContinue(ctx, s.readyDeps(sess))` instead of calling `readyForDelivery` directly.
- `internal/supervisor/settings_warning_test.go` (new): seam-level tests only — happy path (auto-continue → ready → turn proceeds), other-unexpected-modal passthrough, non-modal-error passthrough, first-`waitReady`-nil passthrough, keystroke-error wrap, stuck-dialog-after-answer, log assertion, and `readyDeps`/`New` wiring. No live claude, no screen literals in tests (the anchor stays in production `settings_warning.go`).

**Deviation from spec, developer-flagged as an improvement:** the spec said to wrap `sess.WaitReady` directly, but by the time this landed the merged #1013 sibling had already routed both `deliverViaSession` call sites through `readyForDelivery(ctx, sess.WaitReady)` (the trust-modal gate). `readyDeps.waitReady` wraps `readyForDelivery`, not raw `WaitReady`, so the two gates stack cleanly: `ErrTrustModalPending` (a sentinel, not an `*UnexpectedModalError`) misses the `errors.As` check and passes through unchanged, keeping #1013's fail-loud/forward behavior intact, while the Settings Warning's `*UnexpectedModalError{Class: ModalClassUnknown}` propagates through `readyForDelivery` unwrapped and is caught. Code review (PASS) verified this composition explicitly — see Lessons learned.

## Patterns established

- **Compose a new gate over a merged sibling's seam, don't duplicate or bypass it.** When a spec is written against an in-flight call site and a sibling ticket changes that call site first, wrap the sibling's function rather than the raw primitive it replaced — `errors.As`/`errors.Is` naturally discriminate which gate should fire. See [[dev-compose-new-gate-over-merged-sibling-when-spec-callsites-stale]].
- **Content co-signal layered on a trusted structural signal, consulted only after the structural signal already fired.** `detectSettingsWarning` is never called standalone — only after `errors.As` has already confirmed `*tuidriver.UnexpectedModalError`. This is the same "belt-and-suspenders of different fabric, across the layer boundary" shape as other anchor-consulted-after-structural-confirmation designs in this codebase, and it's why a pyrycode-owned screen literal doesn't trip `cmd/substrate-guard`.
- **Bounded auto-continue, no recursion.** The gate re-gates readiness exactly once after answering — a second unexpected modal after Continue surfaces its own error rather than looping. Keeps the retry/give-up semantics owned entirely by the caller (`msgqueue`), not duplicated inside the gate.

## Lessons learned

From the PR body: the spec's "wrap the two `sess.WaitReady` call sites" instruction predated the #1013 trust-modal sibling landing on those same call sites. The clean composition is to have the new gate's `waitReady` seam wrap `readyForDelivery` — a pending trust modal returns `ErrTrustModalPending` (not an `*UnexpectedModalError`), so it passes through `waitReadyAutoContinue` unchanged and stays fail-loud, while the Settings Warning's `*UnexpectedModalError` (returned unwrapped by `readyForDelivery`) is still caught by `errors.As`. The two gates stack without either duplicating the other's logic — worth checking, on any ticket whose spec cites a call site by name, whether a sibling has since changed what that call site actually calls.
