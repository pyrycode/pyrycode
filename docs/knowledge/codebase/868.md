# Ticket #868 — serialize `conversations.Registry.Save` with a dedicated save mutex

`Registry.Save` held `r.mu` only long enough to copy the in-memory snapshot, then ran temp-write → fsync → rename **unlocked**. Three goroutines call `Save` concurrently in production (the v2 manager's create/rename handlers, the auto-archive sweep loop, the `/clear` rebind observer), so two overlapping saves could interleave and let an **older** snapshot's rename land last — clobbering a newer one on disk. The file self-heals on the next `Save`, but a daemon restart before that durably loses the mutation: a phone-created conversation vanishes, or a `/clear` rebind reverts to a retired session id.

## Implementation

- **New `saveMu sync.Mutex` field on `Registry`** (`internal/conversations/registry.go`), acquired at the top of `Save` and released via `defer`, held across the *entire* snapshot→encode→fsync→rename sequence. Deliberately separate from the pre-existing `mu` (which still guards `conversations` for reads/mutations) — this is what preserves read/mutate concurrency during the slow disk write, unlike `internal/sessions`'s `Pool.saveLocked`, which serializes under the state lock itself.
- **Lock order is one-directional: `saveMu → mu`, never the reverse.** `Save` takes `saveMu`, then briefly takes `mu` for the snapshot copy and releases before any I/O. No mutator or reader ever touches `saveMu`. This makes the classic AB/BA deadlock structurally impossible — confirmed by `-race`.
- Taking the snapshot **inside** `saveMu` (not just adding the mutex around the outer call) is the load-bearing part: it forces snapshot-acquire order to equal rename order, so the last `Save` to acquire `saveMu` always renders the most complete state, regardless of how fsync/rename timing shuffles without it.
- The rest of the atomic-write recipe (0600 temp file, fsync, rename-as-commit, pre-existing target untouched on failure) is untouched — the entire production change is one field + two lines (`Lock` + `defer Unlock`).

## Patterns established

- **This is the conversations-specific fix; `internal/devices.Registry.Save` has the same latent bug and was explicitly left alone.** [ADR 020](../decisions/020-devices-registry-snapshot-then-write.md) documents devices' snapshot-then-write pattern and its "later rename wins" rationale for concurrent `Save`s — but "later rename wins" only guarantees no torn write, not no lost update, which is exactly the gap #868 closes for conversations. Per the ticket's tech notes and PROJECT-MEMORY's "duplicate until a fifth registry forces extraction" rule, devices is intentionally out of scope here; if devices ever grows a second concurrent `Save` caller (today it has only the single-goroutine `pyry pair` / `pyry pair revoke` CLI paths), the same `saveMu` shape applies directly.
- **Dedicated save mutex, held across the full I/O sequence with the snapshot taken inside it, is now the fix-of-record for this lost-update class** — same lock-hygiene family as [#866](866.md) (guarding `Session.id` across two structurally different reader populations), scoped here to "guarantee snapshot order == rename order" instead of "guarantee a consistent read."

## Testing

`TestRegistry_SaveConcurrentNoLostUpdate` (`internal/conversations/registry_test.go`): 15 iterations × 24 goroutines, each goroutine `Create`s a unique conversation and *immediately* `Save`s (no mutate-all-then-save-all barrier — see Lessons learned). After all goroutines return, `Load` must show all 24 records; asserted under `-race`.

## Lessons learned

- **The non-vacuity hinge for this test class is interleaved mutate-then-save per goroutine, not a mutate-all-then-save-all barrier.** A barrier makes every `Save` snapshot the identical full state, so nothing can ever clobber anything and the test passes even on unfixed code — silently proving nothing. Confirmed the guard is real by watching it fail on pre-fix code first (iteration 0 landed only 8 of 24 records on disk).
