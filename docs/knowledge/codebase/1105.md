# Ticket #1105 — `pyry mcp-approve`: MCP stdio approve server forwarding over the control socket

The tool host claude actually talks to for the Streamrunner Interactive permission bridge. A non-YOLO headless claude spawned with `--permission-prompt-tool mcp__pyry_approve__approve` synchronously calls the registered `approve` MCP tool for every non-allowlisted tool use and blocks on its allow/deny JSON. `pyry mcp-approve` is that MCP stdio server: it forwards each call to the daemon over the merged `mcp.approve` control-socket verb (#1104) and returns the daemon's verdict as the tool result. Split from #1079; blocked by #1104 (merged).

Full design writeup: [`specs/architecture/1105-mcp-approve-subcommand.md`](../../specs/architecture/1105-mcp-approve-subcommand.md). ## Implementation

- `internal/control/client.go`: `Approve(ctx, socketPath, req ApprovePayload) (*ApproveResult, error)` — a ~25-line sibling of `Rekey`, sending `Request{Verb: VerbMCPApprove, Approve: &req}` through the shared `request` helper. Doc-comment pins the load-bearing contract: callers must pass a ctx with a deadline ≥ the daemon's approval window, since `request` installs that deadline as the conn read deadline (patient read) while the dial itself still fails fast (≤`dialRetryBudget`≈1.5s) on an unreachable socket. No `ErrorCode` mapping — any error (dial/transport/decode, `resp.Error`, empty `resp.Approve`) is returned verbatim because the caller fail-closes to deny regardless of cause.
- `cmd/pyry/mcp_approve.go` (new, 295 lines): `runMCPApprove(args)` mirrors `runACP` — `parseClientFlags` resolves the socket, `signal.NotifyContext(SIGTERM, SIGINT)`, a **stderr-only** slog logger (stdout is exclusively the MCP JSON-RPC frame stream), then `serveACP(ctx, os.Stdin, os.Stdout, logger, s.register)`. Reuses the protocol-neutral `acp.Transport`/`serveACP` loop verbatim rather than re-deriving the parked-Read-on-non-pollable-stdin machinery.
  - `approveServer{socketPath, timeout, log}` — read-only after construction, no shared mutable state.
  - `register` binds `initialize` / `tools/list` / `tools/call`; `notifications/initialized` needs no handler (dropped silently by `dispatchNotification`).
  - `initialize` echoes the client's `protocolVersion` when present, falls back to `defaultMCPProtocolVersion = "2025-06-18"` otherwise; returns `capabilities.tools:{}` + `serverInfo.name = "pyry_approve"` (load-bearing — forms `mcp__pyry_approve__approve`).
  - `tools/list` advertises exactly one tool, `"approve"` (also load-bearing — the tool-reference suffix), with an advisory `inputSchema`.
  - `tools/call` is the fail-closed core (`toolsCall`): unmarshal `{name, arguments}` → reject non-`"approve"` names → unmarshal `arguments` into `control.ApprovePayload` (`input` stays `json.RawMessage`, never parsed) → `control.Approve` with `cctx = context.WithTimeout(ctx, mcpApprovalTimeout + mcpApproveClientMargin)` → map the result. **Every terminus returns `(mcpToolResult{isError:false}, nil)`** — never a JSON-RPC error, never a hang. The only verdict the subcommand self-originates is `deny` (via `denyResult`, pinned to `permbridge.BehaviorDeny`); `allow` reaches claude solely by marshaling the daemon's `resp.Approve` verbatim (`updatedInput` byte-preserved).
  - `mcpApproveClientMargin = 30 * time.Second` — added to `mcpApprovalTimeout` so the daemon's own approval timer fires first (its informative timeout-deny passes through) rather than the client's generic read-deadline error. Inert until #1106 wires `--permission-prompt-tool` in production.
  - Logging discipline: `logVerdict` emits only `tool_use_id` + `behavior`, on every branch including the pre-parse deny paths — raw `params`/`arguments`/`input` bytes are never logged (adversarial, potentially secret-bearing model input).
- `cmd/pyry/main.go`: `case "mcp-approve": return runMCPApprove(os.Args[2:])` in `run()`, plus one `printHelp` line.
- `cmd/pyry/mcp_approve_test.go` (new, 395 lines): a fake control-socket peer (`net.Listen("unix", ...)` decoding one `control.Request`, encoding a canned `control.Response`) drives `TestMCPApprove_Initialize` (version echo + fallback), `_ToolsList`, `_AllowRoundTrip` / `_DenyRoundTrip` (byte-exact golden JSON per the T1 contract), `_SocketUnreachable_Deny` / `_DaemonError_Deny` (fail-closed), `_MalformedOrUnknown_Deny` (no crash), `_MalformedInput_NoByteLeak` (logging discipline), and `TestControlApprove_UndeadlinedCtxReturns` (no-hang deadline property).

## Patterns established

- **Fail-closed MCP tool host template.** `runMCPApprove`/`approveServer` is the second `cmd/pyry` subcommand (after `pyry acp`, #756) to reuse `serveACP` for a *different* JSON-RPC dialect over the same neutral `acp.Transport` — confirming the transport is genuinely protocol-agnostic, not ACP-specific despite its package name. Any future stdio JSON-RPC tool host should start from this pairing (`parseClientFlags` → `signal.NotifyContext` → stderr logger → `serveACP`) rather than hand-rolling framing.
- **Self-originate-only-deny, allow-only-passthrough.** The structural invariant that makes this subcommand safe to expose to adversarial model input: it has *no code path* that constructs an allow verdict. Every deny is a fixed-constant `denyResult(reason)`; the sole allow path is marshaling the daemon's trusted `resp.Approve` verbatim. Worth reusing verbatim in #1106 or any future adapter that stands between an untrusted model surface and a trusted daemon decision.
- **`isError` always `false`, even for internal-error denies** — a deny is a *successful* tool result claude must honor; flagging it as an MCP error risks claude discarding the content and mishandling the turn. Applies to any future MCP tool that encodes a business-logic rejection rather than a protocol fault.

## Lessons learned

- **`t.Cleanup` runs LIFO — a fake-peer test helper that gates its own teardown on a separately-signalled channel can self-deadlock.** A fake control-socket peer registered `ln.Close()` + `wg.Wait()` inside its own cleanup; because `t.Cleanup` unwinds LIFO, `wg.Wait()` blocked before a later-registered release signal ever fired. Fix: have a blocking peer drain the connection (`io.Copy` until the client closes it on its own read-deadline) instead of depending on cleanup-ordering between two separately registered `t.Cleanup` calls. Reusable whenever a test spins up a peer goroutine and needs deterministic teardown — prefer "the client's own timeout/close unblocks the peer" over "a second cleanup hook signals the peer," since cleanup order across independent `t.Cleanup` registrations is LIFO, not dependency-graph-aware.
