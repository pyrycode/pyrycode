# Ticket #1218 — Compare the two runners over the alphabet the parser actually maps

`TestPtyRunnerVsStreamRunner_StructuralEquivalence` (`internal/e2e/realclaude/ptyrunner_byte_equivalence_test.go`) was RED on `main`: the streamrunner side carries ~10 `system/thinking_tokens` lines per turn, the ptyrunner side carries none, and the pre-#1218 shape comparison treated that as a mismatch. `internal/streamsup`'s shipped parser ignores the whole `system` family by design (it's claude's catch-all namespace and highest-rate emitter — see `ignoredLineTypes` in `internal/streamsup/parser.go`), so the test was failing on exactly the lines production deliberately drops. The equivalence being asserted was real; the alphabet it asserted over was stale. Test-only change, no production code (the ticket's explicit "do not fix by changing what either runner emits" holds).

## Implementation

- **A third table, `parserIgnoredTypes`, mirrors `streamsup.ignoredLineTypes` and is consulted by `shapeFilterTypes` only.** The pre-existing `shapeFilterTypes()` unioned `expectedStreamRunnerOnly.Events` and `expectedPtyRunnerOnly.Events` — tables documented as "one runner emits it, the other doesn't" and also read by `additiveDriftViolations` (the SET check). `system` is not one-sided (both runners emit `system/init`), so adding it to either table would have been a factually false entry that also silently pre-authorised a future genuinely one-sided `system` divergence. `parserIgnoredTypes = {system, rate_limit_event}` answers a different question — "does the shipped parser map anything from this type?" — and only `shapeFilterTypes` reads it; `additiveDriftViolations` is untouched, so it keeps seeing every `system` line on both sides and still fires if one runner ever stops emitting `system/init` while the other keeps emitting it.
- **`rate_limit_event` is carried in two tables on purpose, not by accident.** It's already in `expectedStreamRunnerOnly.Events` (streamrunner-only, from #506) *and* now in `parserIgnoredTypes` (parser-ignored). Both facts are independently true and each table answers a different question; set union is idempotent so the filter is unaffected either way.
- **Four `compareShapes` guards rewritten for the post-filter intersection (3 shapes/side: `assistant, assistant, result/success`).** The two minimum-length floors (`want >= 4 (init+user+assistant+result)`) became `want >= 2 (assistant+result)` — `>= 3` was deliberately avoided because the two-assistant split (thinking message + text message) is claude-version-dependent, so pinning it would pin a version artifact rather than a structural guarantee. The two index-0 guards (`stream[0] == (system,init)`) became `stream[0].Type != "assistant"` — the post-filter sequence now opens with model output, not init.
- **`checkInit` (`:499`/`:500`) is untouched.** It walks raw bytes independently of `extractShapes`/the shape sequence, so field-level init coverage (cwd/model/session_id/tools) is unaffected by dropping `system` from the sequence comparison.
- **The positional "init arrives first" claim isn't lost by dropping the index-0 guards** — it's pinned more strongly elsewhere and none of it needed a live claude to confirm: `internal/agentrun/ptyrunner/runner_test.go:148-168` asserts ptyrunner's raw stdout `lines[0]` decodes to `(system,init)`; `cmd/pyry/agent_run_test.go:671-688` asserts `system/init` precedes every `assistant`; `streamjson.New` (`internal/agentrun/streamjson/emitter.go:110-146`) writes the init envelope before returning the emitter, so nothing can structurally precede it; and on the streamrunner side the position was never pyrycode's claim to make — streamrunner is a byte-exact passthrough of claude's own stdout.
- **Incidental fix, out of #1218's design but required for the AC5 live PASS: three claude-2.1.220 result-trailer fields allowlisted** (`time_to_request_ms`, `ttft_stream_ms`, `fast_mode_disabled_reason`, added to `expectedStreamRunnerOnly.ResultTrailerFields`). `compareShapes` used to `t.Fatalf` on the `system` mismatch before the additive-drift loop ever ran, so a claude version bump that added these fields stayed masked. Fixing the sequence comparison unmasked the SET check reaching the result trailer for the first time. Safe by construction rather than judgement — ptyrunner's trailer is a fixed Go struct (`internal/agentrun/streamjson/emitter.go`, `type trailer`) that structurally cannot emit a field claude adds API-side — and each is a sibling of a field the #503 audit already classified API-only (`duration_api_ms`, `ttft_ms`, `fast_mode_state`).
- **Three new fixture-driven tests, all under the existing `e2e_realclaude` tag, none needing claude or network:** `TestExtractShapes_FiltersParserIgnoredTypes` (the filter drops exactly `system`/`rate_limit_event`, preserves order, leaves an unlisted type like `assistant` alone); two new sub-tests inside `TestAdditiveDriftAssertion_SelfCheck` (`system_one_sided_streamrunner`, `system_one_sided_ptyrunner`) that pin the AC2 guarantee the existing self-check's `intersectionBaseline` fixture couldn't provide (it carries `system/init` on both sides, so it stayed green regardless of which table a wrong fix touched); and `TestParserIgnoredTypesMatchesStreamsupParser`, which drives a real `streamsup.NewParser` per member of `parserIgnoredTypes` with a representative line and asserts zero emitted events — guards the dangerous direction (a member that the parser actually maps, which would silently drop a meaningful envelope from the comparison).
- **AC5 confirmed live, twice.** Code review ran `make e2e-realclaude` against live claude 2.1.220 and observed a genuine red-on-`main` / green-on-branch pair in the same session (`main` at `062024b`: `structural mismatch: shape lengths differ: streamrunner=8 ptyrunner=4`; branch: PASS, 3 shapes/side). The PR body's own AC5 run shows the same shape: pre-filter streamrunner carries `system/init` + 4×`system/thinking_tokens` + 2×`assistant` + `rate_limit_event` + `result/success` (10 lines) against ptyrunner's `system/init` + 4 local housekeeping envelopes (`mode`, `permission-mode`, `file-history-snapshot`, `user`) + 4×`attachment` + 2×`assistant` + `result/success` (12 lines); post-filter both collapse to `[assistant, assistant, result/success]`.

## Patterns established

- **A shared source of truth can be load-bearing for two different questions — split it when one caller needs a third answer the other two callers must not see.** `shapeFilterTypes` and `additiveDriftViolations` both read the two one-sided allowlists (`expectedStreamRunnerOnly`/`expectedPtyRunnerOnly`); the tempting one-line fix (add `system` to a table) would have silently disabled the SET check for the whole family, because both consumers share the table. Introducing a third table scoped to the one consumer that needed the new answer — while leaving the other consumer reading only the original two — is what keeps the SET check's guarantee intact. The `parserIgnoredTypes` doc comment states explicitly which of the two questions it answers and which caller reads it, so a future reader doesn't merge it back into the allowlists "for consistency."
- **A `t.Fatalf` guard early in a test masks every assertion downstream, including ones failing for unrelated reasons.** This test had been RED on a stale sequence alphabet long enough that a separate result-trailer staleness (three new claude 2.1.220 fields) accumulated behind the fatal, invisible until the sequence fix went green. When a long-RED gate finally passes, budget for a second failure to surface immediately — fixing the first defect is what makes the second one observable, not what causes it.
- **Pin a durable structural floor, not the observed count, when the observed count is a version artifact.** The post-filter intersection is `[assistant, assistant, result]`, but the two-assistant split is claude-version-dependent (a thinking message plus a text message). The floor guard is `>= 2` rather than `>= 3` for exactly this reason — a higher floor would have pinned a claude-version behaviour as a structural guarantee.

## Lessons learned

From the PR body and code review (PR #1220, PASS with 0 MUST / 3 NIT):

- **Comment precision on "fully policed."** The `parserIgnoredTypes` doc comment claims a member "stays fully policed by `additiveDriftViolations`." Code review's NIT: `additiveDriftViolations` is *type*-grained (`extractEventTypeSet` decodes only `type`), while the sequence check this PR removes `system` from was `(type,subtype)`-grained. Sufficient today only because ptyrunner's sole `system` subtype is `init`, so a one-sided loss of it does drop `system` from that side's type set and does fire — but if ptyrunner ever gains a second `system/*` subtype, a one-sided loss of `system/init` specifically would go undetected by the SET check while still being silently dropped from the sequence. Not a design defect (the wholesale family drop is exactly what the ticket asked for) but a precision gap in the comment, left as-is per NIT severity.
- **A dated audit doc is a point-in-time record, not a maintained mirror — don't chase it.** `docs/audits/2026-05-23-ptyrunner-streamrunner-byte-equivalence.md:60` says the allowlist "enumerates 1 event + 7 result-trailer fields"; this ticket takes it to 10. Code review flagged it but explicitly did not request a fix: the file's sibling claim ("0 ptyrunner-only emissions") was already false on `main` since #562, and its own line citations were already stale. The project's revealed standard is that dated audits are historical snapshots, not living docs — left untouched here for the same reason.
- **A mirror needs a pointer from both directions, not just the direction that was built.** `internal/streamsup/parser_test.go:436`'s `TestParser_IgnoredLineTypesIsTheMeasuredSet` is the file a contributor edits to grow `ignoredLineTypes` — but nothing there points back at `parserIgnoredTypes` in the realclaude package. `TestParserIgnoredTypesMatchesStreamsupParser` (this ticket) guards the mirror from the copy's side; the source side has no equivalent nudge. Flagged as a NIT, not fixed in this PR — worth a one-line comment addition if `parser_test.go` is next touched.
