# Ticket #1404 — Map `rate_limit_event` to a bounded `turnevent.RateLimited`

`rate_limit_event` leaves `ignoredLineTypes` (now down to `{"system": true}`) and
gains its own arm in `internal/streamsup`'s `consumeLine` main switch, mapping to
a new bounded `turnevent.RateLimited`. Fifth mapping in the family #1380 opened,
and the first that is **not** a `system` subtype. PR
[#1408](https://github.com/pyrycode/pyrycode/pull/1408), code review **PASS** (1
SHOULD FIX, below the merge threshold). Carrying the event to a mobile/ACP client
is **not** in scope — that's the protocol shape and turnbridge mapping, #1405.

## Implementation

- **The substance is the gate, not the mapping.** claude reports the usage-limit
  window **once per run** whatever its state — `status` reads `"allowed"` in all
  three captures on record (claude 2.1.158, 2.1.199, 2.1.220), i.e. every run
  that produced one hit no limit at all. A 1:1 translation would fire on every
  healthy turn. `emitRateLimit`'s gate has three rungs, all decided and stated at
  the code:
  1. `status == benignRateLimitStatus` ("allowed") → silence.
  2. `status` non-empty and not the benign value → one `RateLimited`. The
     recommended posture from the architect spec, confirmed rather than
     overturned: the failure direction is the safe one — an unrecognised status
     surfaces and a human looks, rather than a real limit vanishing.
  3. `rate_limit_info` absent, present-but-empty, or the line fails to decode →
     silence. This is the decision AC2 case (c) asked for: the naive "emit
     unless status is allowed" reading is rejected because an absent container
     answered with "emit" turns a future container rename into a per-run noise
     row on **every** healthy run forever, while answering with silence produces
     only a false negative on a condition that has never fired once in three
     captures. The cost — a container rename goes undetected by any automatic
     test — is stated at the code rather than hidden; the live drop census is
     the named backstop.
- `turnevent.RateLimited{Status, LimitType, ResetsAt int64, TruncatedFields
  []string}`. `Status`/`LimitType` are claude-authored strings, bounded at
  construction by a new `maxRateLimitField` (256 — ~28× the observed 7–9 byte
  values, deliberately wide because the value set beyond the one benign status
  is unmeasured). `ResetsAt` is claude's unix-seconds integer, passed through
  **unbounded and unvalidated in both directions** — not `time.Time` (converting
  would invent a claim the bytes don't make), and a consumer must not assume it
  lies in the future *or* in a sane range at all. `session_id`/`uuid` are absent
  from the decode target itself (the family's #1380 precedent), and so are the
  payload's four `overage*` keys — two of which are **measured
  version-variable** across the three captures (`overageResetsAt` only on
  2.1.158, `overageDisabledReason` only on 2.1.199/2.1.220).
- The variant is a **report, never a control input** — its doc states that
  nothing in the daemon may key a behaviour (backoff, throttle, retry, turn
  suspension, reconnect delay) on it. Every field crosses the subprocess trust
  boundary as claude-authored data; the only consumer today is display (#1405).
- New decode target `rateLimitEventLine{ Info rateLimitInfo }`, the family's
  first **nested** target — claude carries this payload one level down, under
  `rate_limit_info`. The container is a plain struct, not a pointer: absence and
  a present-but-empty object are treated identically (both leave `Status` empty,
  which the gate reads as "no report was made"), so a pointer would buy a
  distinction nothing acts on.
- `ignoredLineTypes` shrinks to its one remaining member, `{"system": true}`;
  `TestParser_IgnoredLineTypesIsTheMeasuredSet` updated to match — untagged, so
  it's the first thing that goes red on a plain `make check`. The `sl.Type ==
  "system"` guard at the drop branch is **kept**, not deleted, with its stated
  reason re-justified: it no longer exists "because of `rate_limit_event`" (that
  member is gone) but scopes the subtype match to `system` **by construction**,
  so a future list member carrying a colliding subtype name can't reach the
  wrong emitter.
- `cmd/pyry/interactive_turn_v2.go`'s `eventKind` gained a fifth mapped arm,
  `turnevent.RateLimited → "rate_limited"` — name only, no field content, for
  the same reason `ThinkingProgress`'s arm exists: without it the other three
  call sites (`acp_turn_stream.go`, `stream_turn_busy.go`,
  `stream_turn_drain.go`) would log `"unknown"` for a variant the daemon
  recognises.
- `cmd/pyry/stream_turn_busy.go`'s opener whitelist needed **no code change** —
  `RateLimited` lands in `observe`'s `default` arm, correctly, because a usage
  limit is orthogonal to turn lifecycle. The comment that predicted this day
  ("rate_limit_event … is exactly the line that becomes an `ApiRetry` the day
  someone wires it") is rewritten in the past tense as a discharged prediction,
  and its stale cite (`parser.go:158-163`) is repointed — see § Lessons learned
  for why the spec's own replacement cite was also wrong.
- **Realclaude mirror (build tag `e2e_realclaude`), second commit.**
  `parserIgnoredTypes` loses its `"rate_limit_event"` entry;
  `expectedStreamRunnerOnly.Events` **keeps** its entry unchanged (different
  table, different claim — ptyrunner's structural inability to emit an
  API-stream event, independent of whether the parser maps the line). A third
  edit the ticket body didn't name but the architect spec flagged:
  `parserIgnoredTypeFixtures`'s matching entry, forced by
  `TestParserIgnoredTypesMatchesStreamsupParser`'s orphan-fixture check. The
  `dropped_line_capture_test.go` row at the captured `{"type":"rate_limit_event"}`
  line keeps its `wantDrop: true` verdict (rung 3 is silence) — only its `why:`
  string changes, since `dropcapClassify` derives the verdict from the shipped
  parser rather than declaring it.
- Eight Go source comments corrected to state the line is mapped, not dropped
  (AC5); six left untouched because they stay true (the parser's census row,
  the watchdog's "activity only" note, a historical quote, a line inventory,
  and two `ptyrunner_byte_equivalence_test.go` sites); one deleted along with
  its orphaned fixture entry, its fact relocated onto the table that still
  makes the claim.

## Patterns established

- **A once-per-run status report needs a gate with an explicit absent-container
  decision, not just a benign-value decision.** Two rungs, not one: what to do
  on the measured-benign value is the obvious half: what to do when the
  decode target simply has nothing in it is the one a naive implementation
  falls into rather than chooses — and it's the one that determines whether a
  future upstream rename fails loud (a noise row, self-correcting) or quiet (a
  silently vanished feature, self-correcting the other way, into invisibility).
  Chosen here for the loud failure, matching `ignoredLineTypes`' own doctrine.
- **A nested decode target's container is a plain struct, not a pointer, when
  absence and empty-but-present are the same downstream decision.** Mirrors
  `systemThinkingTokensLine`'s `int` over `*int` argument, extended to a struct.
- **`TruncatedFields` order is asserted by call order, not literal order** —
  sequential `bound()` statements rather than a composite literal, so the order
  a reader sees is the order the contract promises, and a `go test -overlay`
  mutant swapping the two calls has exactly one row that can catch it.

## Lessons learned

From the PR body's own "Lessons learned" section (developer, verbatim):

> **The realclaude mirror cannot catch its own drift for this type, and the
> AC4 edit is statement-correctness rather than test-forced.** Measured with
> two overlay mutants: restoring `parserIgnoredTypes["rate_limit_event"]`
> *alone* goes RED (the member-has-no-fixture check), but restoring the entry
> **and** its fixture leaves the whole tagged suite **green**. The only
> fixture the mirror ever had for the type is the bare
> `{"type":"rate_limit_event"}` line, a rung-3 line that emits zero either
> way, so the mirror's "does the parser map this?" pin cannot discriminate. A
> future re-add of the false entry would pass. No mechanism shipped (no
> observed failure, and the spec's "do not relocate the fixture" reasoning
> holds — the mirror makes no claim about the type any more), but the gap is
> real and worth knowing before someone reads that green as evidence.
>
> **The spec's `parser.go:282-285` cite target was pre-change.** The ticket
> asked for `stream_turn_busy.go`'s stale `parser.go:158-163` cite to be
> repointed at `:282-285`, but this change adds ~100 lines of constants and
> prose above the list, so the literal ships at `:384-386`. Writing the
> spec's number verbatim would have replaced one stale cite with another on
> the same commit.
>
> **Restoring `rate_limit_event` to `ignoredLineTypes` is behaviourally
> inert**, contrary to the spec's mutation table, which expected rung 2 to go
> RED alongside AC3's pin. The `case "rate_limit_event"` arm is matched
> before the `default` branch ever consults the map, so only the pin catches
> it — which is the correct division of labour, but the pin is the *sole*
> detector rather than one of two.
>
> **A row's silence can be accidental rather than principled, and moving it
> is the honest fix.** `TestParser_IgnoredLineTypesStaySilent`'s
> `rate_limit_event` row stayed green only because its payload's container
> key is `rate_limit` rather than claude's `rate_limit_info` — nothing to do
> with the ignored list its table is named for. Following #1385's precedent
> it moved verbatim into the rung-3 test, where the same silence holds for a
> visible, newly decided reason and the logged `reason` is asserted too.

Code review's own verification, worth keeping alongside the above:

- Mutation-matrix — the spec's own table, all 8 rows RED at the named row via
  `go test -overlay` (no worktree writes), baseline green first: benign
  constant, all four rung-3 rows, the cap rows, the `bound()`-order row (sole
  RED), `ResetsAt` not copied, the reverted-to-`ignoredLineTypes` mutant
  (both AC3's pin **and** rung 2), and the drop site given a `"status",
  rl.Info.Status` attribute (caught by the content-free-log sweep).
- AC5 counted per site independently (`git grep rate_limit_event -- '*.go'`,
  every hit classified): 8 corrected, 6 left alone, 1 deleted with its
  fixture — matched the spec's own count exactly.
- One SHOULD FIX, not blocking: the new `eventKind` arm
  (`interactive_turn_v2.go`) has no test, breaking the family's own unbroken
  precedent (#1380/#1381 got a live/unknown test, #1385 got
  `TestInteractiveTurnEmitterV2_ThinkingProgressEventKindNamesTheVariant`).
  Verified by mutation that both `return "unknown"` (arm behaviourally absent)
  and `return "rate_limited:" + ev.(turnevent.RateLimited).Status` (the
  content-free claim in the arm's own comment, unenforced) leave the entire
  suite green. Not fixed in this PR (below merge threshold); flagged for
  #1405, which touches this surface anyway.
- Confirmed the blast-radius question the diff itself doesn't show:
  `dropcapCensus` (built from *dropped* lines) still counts a healthy run's
  `rate_limit_event` correctly — rung 1 is still a drop, just for a different
  reason than list membership — so mapping the type cannot silently zero
  `RateLimitEventObserved`.
