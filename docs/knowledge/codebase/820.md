# Ticket #820 — `rename_conversation` v2 wire message + daemon handler

Adds the missing rename verb both paired clients need (mobile stubbed it
locally, desktop was building its Rename dialog against it): a protocol type
constant, a two-field request payload, and a daemon handler wired at both
relay dispatch sites. Every other primitive the verb needs already
existed — the reply type (`conversation_updated`), the registry setter
(`Registry.Update`), the not-found code, and `list_conversations` surfacing —
so this shipped as a thin vertical slice cloning `create_conversation`'s
handler shape, not a new primitive.

## Implementation

Five production files, ~150 LOC total, none of them new packages:

- `internal/protocol/codes.go` — `TypeRenameConversation = "rename_conversation"`,
  in the Conversations cluster.
- `internal/protocol/conversations_write.go` — `RenameConversationPayload{ConversationID, Name string}`.
  Deliberately **not** a reuse of `PromoteConversationPayload` — promote also
  carries a required `Cwd`, which a rename neither has nor means.
- `internal/protocol/envelope.go` — `TypeRenameConversation: true` in
  `v1TypeSet`. It's a `dispatch.Route` request/reply verb like
  `create_conversation` / `promote_conversation`, not a v2-control frame
  intercepted before `dispatch.Route` (contrast `new_session` /
  `set_session_settings` / `interrupt` in `v2OnlyTypes`) — the ticket title's
  "v2 wire message" refers to the encrypted v2 *transport* it rides, not the
  v1/v2 *type partition*, which is about dispatch mechanism.
- `internal/relay/handlers/rename_conversation.go` (new, ~90 LOC) —
  `RenameConversation(reg ConversationRenamer, registryPath string, logger *slog.Logger) dispatch.Handler`.
  Flow: decode → empty-title guard (`strings.TrimSpace(p.Name) == ""`, runs
  *before* `Update` so a blank rename leaves the stored name untouched) →
  `Registry.Update` (single locked callback both sets `Name` and snapshots the
  `ConversationUpdatedPayload` — no find-then-read TOCTOU, no second lock) →
  not-found on an `Update` miss → eager best-effort `Save` → `c.Reply`. `LastUsedAt`
  is **not bumped** — rename is a metadata edit, not a "use", mirroring
  `Registry.Promote` (which touches only `IsPromoted` + `Name`) and keeping
  `list_conversations` ordering stable.
- `cmd/pyry/relay.go` — two `d.Register`/`Handlers[...]` lines, adjacent to
  `TypeCreateConversation`, both reusing `resolveConversationsRegistryPath(instanceName)`.

`ConversationRenamer` is the consumer-declared minimal interface
(`Update` + `Save`) `*conversations.Registry` satisfies structurally, same
pattern as `ConversationCreator` (#666) and `TurnWriter`/`SessionRouter`/`Enqueuer`
in the same handlers package — see [features/relay-package.md](../features/relay-package.md).

All three reject branches (`protocol.malformed` decode, `protocol.malformed`
empty-name, `conversation.not_found`) reply with a fixed static string, never
attacker-controlled bytes (title, id, decode error). The title is user
content and is never logged; only `conn_id` / `conversation_id` (a non-secret
registry key) appear in structured log fields — same discipline as
`create_conversation`.

## Testing

- `internal/relay/handlers/rename_conversation_test.go` — table-driven:
  success (reply shape, `in_reply_to` correlation, registry row updated,
  `LastUsedAt` unchanged via `time.Time.Equal`), persistence-survives-reload

`go test -race ./...`, `go vet ./...`, `go build ./cmd/pyry` all pass.

## Out of scope

- **Live fan-out to other connected clients.** Like the other write verbs,
  this replies only to the requester; other clients pick up the new title on
  their next `list_conversations`. A live broadcast is a separate concern for
  a future ticket.
- **Title length cap.** Neither `create_conversation` nor `Promote` caps
  `Name` length today and no oversized-title failure has been observed
  (evidence-based deferral). If ever wanted, it belongs on the registry
  primitive so every write verb inherits it, not on this one handler.
