# #1131 — Nil-safe modal keystroker for stream mode

**Size:** XS (spec'd S). Security-sensitive (fail-closed permission gate). 2 production files
(`cmd/pyry/modal_resolve_v2.go` +36, `cmd/pyry/relay.go` +14/-4) + 1 test file
(`cmd/pyry/modal_resolve_v2_test.go` +145). `internal/relay` untouched. Not blocked by any open
ticket; blocks #1081 (the config toggle that makes stream mode selectable).

## What shipped

The **fourth and final** typed-nil `w.sup` reader in `relay.NewV2SessionManager`'s
`V2SessionConfig` guarded, completing the sibling set: `screenSnapshotterOrNil` (#1101),
`activeInterrupter` (#1121), `activeSessionStarter` (#1125).

`newModalResolverV2(modalReg, w.sup, logger)` (`cmd/pyry/relay.go:454`) passed the bootstrap
`*supervisor.Supervisor` directly as the modal keystroker. On the stream-json bootstrap path
`Session.Supervisor()` returns a **typed-nil** pointer (#1077); `ResolveCancel`/`ResolveTimeout`
call `kb.SendEsc()` **unconditionally**, so a remote `modal_cancel` (or deny-on-timeout) for an
outstanding stream-json approval dereferenced the nil receiver inside `sendModalKey`
(`internal/supervisor/modal.go:97`, locks `s.sessMu` before any nil check) → daemon panic.

Two new symbols in `cmd/pyry/modal_resolve_v2.go`, beside the `modalKeystroker` interface:

- **`noopKeystroker`** — a zero-size struct implementing `modalKeystroker` with three tolerated
  no-ops (`SendEsc`/`Answer`/`AcceptTrust` all return `nil`). The stream-json bootstrap's
  keystroker: there is no PTY to dismiss a modal on, since a stream-json approval is a
  permbridge-parked completer resolved through the verdict arm
  (`streamApprovalBridge.ResolveStream`, #1080), not an on-screen PTY modal.
- **`modalKeystrokerOrNoop(sup *supervisor.Supervisor) modalKeystroker`** — the composition-root
  guard. Takes the **concrete** pointer (not the interface) so `== nil` runs before boxing; `nil`
  maps to `noopKeystroker{}`, a live supervisor passes straight through unchanged.

One production wiring change, `cmd/pyry/relay.go:461`:

```go
modalResolver := newModalResolverV2(modalReg, modalKeystrokerOrNoop(w.sup), logger)
```

## Why a no-op, not a bound-runner re-route (unlike #1121/#1125)

Interrupt and new_session were re-routed off `w.sup` to the **active bound runner** because those
verbs must reach the conversation's own runner. Modal cancel/timeout is a **PTY-modal dismissal**
keystroke — in stream mode there is no on-screen modal to dismiss, so the semantically correct
stream-mode keystroker is *nothing*, not a re-route. This is also why the return shape differs
from `screenSnapshotterOrNil`: that guard returns a genuine **nil** interface (the consumer,
`handleRequestSnapshot`, has a nil-check arm). The modal resolver has no nil-`kb` arm — `SendEsc()`
is called unconditionally — so a genuine nil interface would panic just the same as the boxed
typed-nil. The guard must return a **non-nil, callable** no-op instead.

## Fail-closed proof (security-sensitive)

- **Cannot resolve to allow:** the only path that resolves a permbridge completer to allow is
  `streamApprovalBridge.ResolveStream(modalID, allow=true, …)`, reached only from
  `ResolveAnswer`'s verdict arm after the `MayAnswerRemotePermission` +
  `AuthorizeRemotePermission` gate. `ResolveCancel`/`ResolveTimeout` never reference
  `streamApprovals`, and `noopKeystroker` never touches the permbridge — verified by reading
  `ResolveCancel`, `ResolveTimeout`, and `ResolveStream` end-to-end (architect + code-review both
  did this independently).
- **Stays denied, not un-denied:** consuming the modalbridge entry in `ResolveCancel` doesn't touch
  the permbridge completer; its own #1103 deny-on-timeout is the deterministic fail-closed
  backstop. `retire`'s early return on an already-consumed modal prevents a double-dismissal
  without un-denying. Belt-and-suspenders with different fabric: the safety net is a deterministic
  timer, not another stochastic keystroke.
- **PTY path byte-identical:** a non-nil `w.sup` passes straight through; the existing
  `fakeKeystroker`-based happy-path suite is untouched.

## Patterns established

- **Not every typed-nil guard has the same return shape.** `screenSnapshotterOrNil` (#1101) returns
  a genuine nil because its consumer has a nil-check arm; `modalKeystrokerOrNoop` must return a
  non-nil no-op because its consumer calls the interface method unconditionally. Before writing a
  new `xOrY` guard for a typed-nil `w.sup` seam, read the consumer's call site first — the presence
  or absence of a nil-check arm decides whether "nil" or "no-op" is the fail-safe value.
- **Sibling-seam scope discipline holds across the whole guard family.** Code review confirmed the
  other raw-`w.sup` readers (`relay.go:479` usage-resolve, `:667-669` turn/modal streams) are
  pre-existing, untouched, and belong to #1081's blocked-by stream-gating audit — not a regression
  in this PR. Same "sibling seams out of scope" pattern #1101 established.

## Lessons learned

From the PR body (#1132):

- The nil-safe return shape differs from `screenSnapshotterOrNil` by design: a **non-nil** no-op
  keystroker, not a genuine nil interface. The resolver has no nil-`kb` arm, so a genuine nil
  interface would panic on the unconditional `SendEsc()` just as a boxed typed-nil would — the
  guard must return something callable. (This was anticipated in the spec, not discovered during
  implementation — flagged here because it's the one detail most likely to be gotten wrong if this
  pattern is copied for a future seam without reading the consumer first.)
