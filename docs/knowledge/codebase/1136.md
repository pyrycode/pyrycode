# Ticket #1136 — Stream e2e: per-conversation interrupt honoured under `interactive_runner:"stream-json"`

Proves, live and end-to-end, that a phone-originated interrupt is honoured **per
conversation** on the stream-json interactive path. The production interrupt
primitive (`(*streamsup.Runner).Interrupt()`, #1120) and its per-conversation
routing (`activeInterrupter` → `resolveBoundRunner`, #1121) were already built and
security-reviewed; nothing about them changes here. What was missing was a fake
that could stay genuinely mid-turn long enough for an interrupt to land, and the one
spec that drives the whole chain together. Rides the harness helper from #1141
(`StartStreamInteractiveWithRelay`) and the fakeclaude stream-json mode from #1140.

## Implementation

- **Fakeclaude interrupt rider** (`internal/e2e/internal/fakeclaude/main.go`):
  `PYRY_FAKE_CLAUDE_STREAM_INTERRUPT` (default-off), read once at the `envStreamJSON`
  gate and passed into `runStreamJSON` as a new `honorInterrupt bool` param — the
  function itself stays env-free. In interrupt mode a user turn gets the assistant
  echo line **only** (`writeAssistantEcho`, the result is withheld so the turn stays
  in flight), and an interrupt `control_request` (matched by the new
  `interruptControlRequest`, which mirrors `streamsup.controlRequest`'s wire shape)
  gets `writeInterruptedResult` — a `result{subtype:"error_during_execution"}` line.
  `writeStreamResponse` was split into `writeAssistantEcho` + the trailing
  `result{success}` line so the default (mode-off) path stays byte-identical for the
  #1141 send rider and the sibling new_session/queue riders. Full design + rationale
  now lives in [features/fakeclaude-binary.md § Interrupt mode](../features/fakeclaude-binary-stream-json-mode.md#interrupt-mode-honorinterrupt-1136).
- **Fakeclaude unit tests** (`stream_detect_test.go`, extended): drive the mode
  through the **real** `streamsup.Parser` (the #1140 different-fabric discipline) —
  an in-flight user turn maps to one `TextChunk` and no `TurnEnd`; an interrupt
  `control_request` maps to one `TurnEnd{Reason: TurnEndReasonCancelled}`; the full
  sequence in order. The 3 pre-existing `runStreamJSON` call sites gained `, false`.
- **The e2e spec** (`internal/e2e/relay_v2_stream_interrupt_test.go`, new,
  `//go:build e2e`): `TestRelayV2_StreamInterruptStopsRunningTurn`. Mints a
  conversation over the wire (`create_conversation` → `conversation_created`) rather
  than binding to the bootstrap session — the minted conversation gets its **own**
  stream runner and its own fakeclaude child (inheriting the daemon's env, so
  interrupt mode is live on it too). Drives one `send_message`, awaits the ack, then
  drains to an `assistant_delta` (M1 — proves the turn is running), sends a
  payload-less `interrupt` frame, then drains to a `turn_end` with
  `ConversationID == convB && StopReason == "cancelled"` (M2 — proves the interrupt
  reached that conversation's own bound runner, not the bootstrap).

## Why the observable is `StopReason`, not a turn-state value

There is no distinct "interrupted" turn-state — the taxonomy is only
`thinking`/`responding`/`idle`. The interrupt signal is carried by `turn_end`'s
`StopReason`: `error_during_execution` → `streamsup.Parser`'s `resultTurnEndReason`
→ `TurnEndReasonCancelled` → `turnbridge.MapEvent` → `TurnEndPayload{StopReason:
"cancelled"}`. This is strictly stronger than the PTY sibling
(`relay_v2_interrupt_test.go`), which only asserts *that* a `turn_end` arrived — the
tui-driver's event kind can't distinguish an interrupt-stop from a clean end, but
the stream parser can, so this spec asserts the stronger claim.

## What AC3 (isolation) proves, and what it deliberately doesn't

Minting the target conversation — rather than binding it to the bootstrap session,
as #1141's send test does — is what makes this exercise #1121's routing at all. Had
the target been bootstrap-bound, `resolveBoundRunner` would return the bootstrap
runner regardless of whether routing was correct, indistinguishable from the
pre-#1121 bug (interrupt always hits bootstrap). Under that bug the interrupt would
land on the idle bootstrap child → no `turn_end` ever → the test times out; correct
routing produces `turn_end{cancelled, convB}`. So M2 **is** the live isolation proof
for the routing target.

A phone-observable "second concurrent conversation is untouched" negative was
deliberately **not** added: `startStreamTurnDrainV2` drops any non-active session's
events before the emitter (`cmd/pyry/stream_turn_drain.go`), so a leaked event on an
unwatched conversation is indistinguishable from a correctly-isolated one at the
phone — such a test would observe nothing and add flake surface for no signal.
Runner-level cross-conversation isolation is proven deterministically instead by
#1121's unit tests (`cmd/pyry/interrupt_routing_test.go`): the bound runner is
interrupted exactly once, a separate bootstrap fake zero times. That's the
belt-and-suspenders pair — different fabric, not a re-derivation.

## Patterns established

- **Withheld-result as an "in-flight turn" primitive for the stream fake.** Prior
  fakeclaude modes model timing via polling/triggers on the PTY/TUI surface
  (idle-trigger, Esc-ends-turn). The stream path has no such surface — this ticket's
  contribution is the analogous idea for stream-json: skip the `result` line so the
  parser never emits `TurnEnd`, and the turn is genuinely open until something else
  (here, the interrupt) closes it. Reusable by any future stream e2e that needs a
  turn to still be running when it acts.
- **Splitting a response-writer along its "is the turn still open" seam.**
  `writeStreamResponse` → `writeAssistantEcho` + inline result, so a rider mode can
  reuse the unconditional half (the echo) and substitute the conditional half (the
  terminator). Verified structurally by the #1141 send rider staying green, not
  just by re-diffing the bytes (see Lessons learned).
- **Minting a conversation as the isolation-proof shape**, not binding it to
  bootstrap. Mirrors `relay_v2_modal_perconv_test.go`'s mint dance; this is its first
  use on the stream-json path (see Open questions below — it worked on first try, no
  fallback needed).

## Lessons learned

From the PR body (developer-flagged):

> Splitting `writeStreamResponse` into `writeAssistantEcho` + result made the "keep
> the turn in flight" mode a one-line branch while leaving the default path
> byte-identical — verified structurally by the #1141 send rider staying green, not
> just by re-reading the bytes.

Additional note from the architect spec's open question: this was the first e2e
spec to mint a conversation (`create_conversation`) under
`interactive_runner:"stream-json"` rather than reusing the bootstrap-bound session.
The minted child came up via `newStreamRunnerFactory` and passed on the first try —
the pool-minting flow was already shipped and unit-tested (#1109/#1125) and proven
live on PTY, so this was expected, but it was still the first live confirmation on
the stream path specifically. No fallback to a bootstrap-bound target was needed.
