# Ticket #1318 — Raise the stream harness daemon to Debug and count the pending/hold marker in M4's window

[#1296](1296.md) attached a daemon-log window to M4's failure record so a recurrence of
`TestRelayV2_StreamNewSessionRotatesAndRestartsFresh` could separate "the drain retried and
was refused" from "the drain was not in the error-return arm." Its first live capture
(2026-08-04, during QA of PR #1317 / #1313) rendered `<empty:` — and that emptiness turned out
not to decide anything: at the daemon's default `LevelInfo`, a *parked* delivery and a drain
*looping* once a second in `msgqueue`'s pending/hold branch (which logs at `Debug`,
deliberately, "a long legitimate wait must not spam the operator log") are indistinguishable.
The headline discriminator #1296 shipped was not one. This ticket fixes the instrument, not
the stall — diagnosing/reproducing/fixing the underlying stall stays with
[#1298](https://github.com/pyrycode/pyrycode/issues/1298), which is still open.

## Implementation

- **`internal/e2e/harness.go`** — `StartStreamInteractiveWithRelay` now appends `-pyry-verbose`
  to its `extraFlags` unconditionally, for all six stream-spec callers. `-pyry-verbose` is
  pyry's existing lever (`cmd/pyry/main.go`): its only effect is flipping the stderr handler
  from `LevelInfo` to `LevelDebug`, no behavioural branch keys off it. Applied file-wide rather
  than gated behind a parameter — a bool would cost six call-site edits and leave two harness
  variants, forcing a reader of a captured daemon log to first work out which variant produced
  it. Verified blast-radius (documented in the doc comment): no `internal/e2e` test other than
  this one reads `h.Stderr` content; `realclaude`'s `e2e_realclaude`-tagged specs don't call
  this constructor at all.
- **`internal/e2e/relay_v2_stream_new_session_test.go`**:
  - `msgqueueHoldDebug` — a new file-level const, copied verbatim from `internal/msgqueue/queue.go`'s
    `Debug` hold line, following the same precedent `msgqueueRetryWarn` already set (duplicated
    rather than exported — exporting an operator-facing log string turns it into an API; a
    count of `0` beside a visibly-populated excerpt is the accepted drift guard). Named with
    the level baked in (`...HoldDebug`, mirroring `...RetryWarn`) because the level is exactly
    what makes the two counts' readings differ.
  - `daemonDebugLevel = "level=DEBUG"` — `slog`'s `TextHandler` rendering of a Debug record's
    level field, verified against a live handler rather than assumed.
  - `daemonLogWindow`'s header gained a second window-scoped count: `pending/holds: %d
    (matching %q)`, computed with `bytes.Count` exactly like the existing retry-Warn count.
    Both sentinel arms (`<unmeasurable:`, `<empty:`) still return before the header is built,
    so neither count can leak past them — pinned by extending both arms' `notWant` lists.
  - An **AC-1 instrument guard** placed after M4's success log and before M5 (not a new
    milestone): polls `h.Stderr.Bytes()` for `daemonDebugLevel` for up to 5s at 50ms, `t.Fatalf`
    naming two possible readings of an absence — the harness's `-pyry-verbose` isn't reaching
    the handler, or the drain stopped dropping post-rotation events at the active-session gate
    (which would mean the file's own header divergence analysis, `:62-72`, is stale). This
    guard runs **only on a green M4** by construction (the earlier `t.Fatalf` exits first on
    red) — deliberately, since it is a regression guard that keeps the level flip honest on
    every passing run so the rare red run's record can be trusted.
  - `daemonLogBudget`'s doc comment: the old sizing arithmetic (~20 Warns × ~250B ≈ 5KB,
    computed against an `Info`-level window) is marked **retired**, not silently left standing.
    The constant itself (`8 << 10`) is unchanged — no over-budget `Debug` window has been
    observed, and moving it would be a defense against an unobserved failure mode.
  - M4's "how to read that window" prose was replaced (see "What this record will and will not
    decide" below for the content) and `TestDaemonLogWindow` gained 3 new table cases (marker
    present → non-zero count; window-scoping; both markers present → both counts independent)
    plus `pending/holds` added to existing cases' `want`/`notWant`.

## Patterns established

- **Raise the harness's log level, not the production call site, when a test needs a
  deliberately-quiet log line.** The daemon's `Debug` placement at the `msgqueue` hold site is
  intentional operator-facing behavior; the fix belongs on the harness side using the
  production binary's own existing flag (`-pyry-verbose`), never by bumping the call site's
  level to serve one test.
- **A count's name should encode the precondition that makes it meaningful.** `msgqueueHoldDebug`
  (not `msgqueuePendingHold`) bakes in the log level because the level is exactly what makes
  the `pending/holds` count a measurement (`Debug` harness) vs. a permanently-suppressed `0`
  (`Info` harness, the old default) — the name is a standing reminder of that dependency.
  Paired with an **instrument guard that only fires on green**: when a count depends on a
  precondition (log level, a flag, a build tag), a guard placed after the assertion that
  consumes it — running only on the path where the count would otherwise go unnoticed as
  silently degraded — re-proves the precondition on every passing run instead of trusting it.
- **A count kept at the expected value of `0` is a contract check, not dead weight**, when the
  branch it counts is structurally unreachable on the harness in question (traced through the
  concrete classifier wiring, not asserted) — a future non-zero reading is itself the finding.

## Lessons learned

From the PR body's own **Lessons learned** section
([PR #1319](https://github.com/pyrycode/pyrycode/pull/1319)):

> **A silent-state list can name a branch its own wiring forbids.** M4's inherited prose called
> the pending/hold retry one of three states silent at Info, but on this harness that arm is
> structurally unreachable: `cmd/pyry` wires exactly one `Pending` classifier
> (`errors.Is(err, supervisor.ErrTrustModalPending)`), whose only production producer is the PTY
> delivery gate, while this harness runs `stream-json`, whose `WriteUserTurn` returns only
> `ErrNoLiveChild`/`ErrDropped`/nil. Suppressed-level and unreachable look identical in a log —
> trace the gate before believing a state is merely invisible. The count is kept as a contract
> check, which is why it is worth having at `0`.
>
> Verify a "verified against a live handler" claim yourself. Both matched literals
> (`level=DEBUG`, and the hold message surviving `TextHandler`'s `msg=` quoting) were re-derived
> by rendering real records through `slog` rather than inherited — cheap, and the whole ticket
> exists to clean up prose that shipped wrong numbers.
>
> A retired sizing model must be marked retired, not silently left standing. `daemonLogBudget`'s
> doc arithmetic was computed against an Info-level window; the number stays (no over-budget
> window has been observed) but the model is now explicitly withdrawn, so a future reader
> cannot mistake it for current.
>
> A guard that only runs on green is the right shape for an instrument. The AC-1 check never
> fires on a red M4 — the `t.Fatalf` exits first. That is deliberate: it is a regression guard,
> so every green run re-proves the level flip and the rare red run's record can be trusted when
> it arrives.

**Live AC-1 observation** (from the PR body): two `Debug` records captured on a green run, both
the predicted post-rotation drop —

```
level=DEBUG msg="relay: stream-turn drop; not active session" event=stream_turn.not_active kind=text_chunk session_id=11111111-...
level=DEBUG msg="relay: stream-turn drop; not active session" event=stream_turn.not_active kind=turn_end   session_id=11111111-...
```

**Non-vacuity was proven by mutation, not just assertion** — mutated copies run via `go
test -overlay` against the worktree. Every mutation tried (removing `-pyry-verbose`; dropping
the new count from the header; matching it against `msgqueueRetryWarn` instead of its own
literal; scoping it to the whole buffer instead of the window; letting it leak past a sentinel
arm) went RED. Notably, removing `-pyry-verbose` alone reddened the *AC-1 guard*, which is
itself an empirical confirmation of the ticket's founding premise — the hold arm really is
invisible at `Info`.

## What this record will and will not decide

**Will:** map the count pair to `msgqueue`'s two drain arms — `retry Warns > 0` is the
error-return arm (non-`Pending` `DeliverFunc` error, ~1 Warn/s, no give-up possible inside this
20s window); `pending/holds > 0` is the hold arm (a `Pending`-classified error, give-up streak
reset, same 1s cadence). Both non-zero means the drain moved between arms inside the window.

**Will not, even now:** distinguish the two remaining silent states from each other or from one
another — parked in `Activate` (bounded by `inboundActivateTimeout`, 30s, which
`newInboundDeliver` does not log around) and parked in the mid-turn hold
(`streamTurnHoldTimeout`, 15m, whose whole `waitIdleForDelivery` → `WaitIdle` chain is silent at
every level). Both counts landing at `0` narrows the field to exactly these two states but does
not decide between them — no log level makes either one visible. Deciding *that* pair, and the
stall itself, remains [#1298](https://github.com/pyrycode/pyrycode/issues/1298)'s to close.
