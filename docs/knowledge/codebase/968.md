# Ticket #968 — smoke test the daemon against a real `pyrycode-relay`

Every relay e2e test ran against the in-process `fakerelay`; the deployed
relay server (`pyrycode/pyrycode-relay`) had only ever been proven by hand.
This ticket adds a single opt-in `e2e_liverelay` test that drives a full
round-trip — device identity → WS connect → Noise IK handshake →
`list_conversations` — against a **real** `pyrycode-relay` binary spawned
hermetically on a loopback listener. Zero production code changed: one new
test package, one Makefile target, one doc edit.

## Deviation from spec

The architecture spec (`docs/specs/architecture/968-liverelay-smoke-test.md`)
proposed a **dial-retry loop** to close the daemon-registers-then-phone-dials
race (`fakerelay.WaitBinary`'s real-relay analog). The developer verified
against the relay source that this doesn't work: `ClientHandler` *accepts*
the `/v1/client` WebSocket upgrade first and only then closes with WS 4404 if
no binary is bound — so `fakephone.Dial` succeeds regardless of registration
state, and a dial-retry loop can't detect readiness at all. The shipped
implementation polls `/healthz`'s `connected_binaries` field instead — the
relay's own authoritative registration signal, and (unlike `/v1/*`)
**not** rate-limited, avoiding the risk of the dial-retry approach exhausting
the per-IP burst limiter. Code review verified this against the relay source
independently and confirmed it as correct and strictly better than the
spec's proposal. Same intent, corrected mechanism.

## Patterns established

- **A real dependency's readiness signal beats a client-side retry loop when
  the two disagree.** The spec inferred the readiness contract from the
  fakerelay analog (`WaitBinary`) without re-deriving it against the real
  server's actual accept-then-reject handshake shape; the correct fix
  surfaced only by reading the target server's source directly. When porting
  a test harness onto a **different implementation** of the same interface,
  verify the new implementation's actual protocol behavior rather than
  assuming the old fake's hook has a drop-in equivalent.
- **Loopback-bind-only is a MUST-FIX baked into the design, not a review
  finding to defer.** The architecture spec called this out explicitly in
  its own security review (§ Security review, Subprocess execution) — the
  ephemeral plaintext relay must bind `127.0.0.1` and never `0.0.0.0`/bare
  `:port`, load-bearing enough to be called out in a code comment, not just
  the spec prose.

## Lessons learned

- The real relay's `/v1/client` handler accepts-then-4404s an unbound
  server-id; a phone dial is not a binary-registration probe on this server
  (it is on `fakerelay`, which is why the spec's dial-retry proposal, ported
  from that assumption, didn't hold). `/healthz.connected_binaries`
  (unauthenticated, un-rate-limited) is the correct registration signal for
  the real relay.
- The default `../pyrycode-relay` sibling-repo derivation (via
  `runtime.Caller` → repo root) is correct for an operator's normal checkout
  but resolves wrong when the test runs inside a git worktree (this
  documentation pass itself ran from
  `.pyrycode-worktrees/documentation-968/`, one level deeper than a plain
  clone). `PYRY_RELAY_REPO` is the override for worktree/CI runs — code
  review verified the round-trip green with
  `PYRY_RELAY_REPO=<sibling path>`.
