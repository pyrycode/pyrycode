# Ticket #1337 — Probe: does `pyry agent-run` reach its normal exit path while a backgrounded command still runs? (ptyrunner default, live)

The reading half of the two-part instrument family #1340 started. claude
auto-backgrounds a Bash command once `BASH_DEFAULT_TIMEOUT_MS` expires and
can then complete the turn normally — final assistant message,
`emitter.Close()` trailer write, exit — while that command is still a
descendant of pyry. Nobody had measured whether pyry's own declared
completion on the ptyrunner default therefore lags the work the turn
described. This ticket is the live entry point: it takes #1340's staged
handle, waits for pyry's own exit with the rendezvous FIFO still held,
reads pyry's reap log as the primary evidence (a point-in-time liveness
check is systematically late — see below), and publishes the result
through the shipped composition. It derives nothing the prior four blockers
(#1338, #1340, #1342, #1343) already shipped.

New file: `internal/e2e/realclaude/finding_exit_path_probe_test.go`
(`//go:build e2e_realclaude`, 517 lines), plus one field
(`ExitStatus int`) added to `finLiveRunHandle` in
`internal/e2e/realclaude/finding_live_run_test.go` (#1340's file). No other
production or test code touched.

## Implementation

- **The exit-code gap this ticket closes.** #1340's driver goroutine
  discarded `cmd.Wait()`'s result (`_ = cmd.Wait()`) and `cmd` was
  function-local, so no consumer holding only `PyryPID` could recover pyry's
  exit status — a second `Wait` on an already-reaped child returns `ECHILD`.
  `finLiveRunHandle.ExitStatus` closes that gap: written by the same
  goroutine **strictly before** `close(pyryExited)` (the only happens-before
  edge a consumer has), and initialised to `pinExitStatusUnknown` in the
  driver's composite literal rather than left at the `int` zero — `0` is
  documented elsewhere as *a real successful exit*
  (`finRecordRun.ExitCode`, `finding_run_record_test.go:126-135`), so an
  unwritten field would misreport a run that never exited as a clean one.
- **The read sits inside the receive arm, and that is structural, not a
  style choice.** The probe body's `select` reads `h.ExitStatus` only in the
  `case <-h.PyryExited:` branch. There is deliberately no
  `finExitObservedCode(exited bool, status int)` helper — any shape that
  evaluates the field outside the receive (hoisting it above the `select`,
  passing it to a helper alongside the bool) reads it concurrently with the
  driver's goroutine and is a data race `go test -race` catches. `-1` is not
  uniquely "did not exit" (a signalled process reports the same value); the
  probe's log line states which of the two applies, from whether its own
  wait completed — the distinction stays the consumer's to make, per
  `finRecordRun.ExitCode`'s own doc.
- **Staging is decided before the classifier is consulted, made structural
  by `finExitClassify(staging finOutcomeResult, readings trailRunReadings)
  (string, trailRunOutcome, bool)`.** On any staging value other than
  `finOutcomeReadyToClassify` it returns the staging value and the **zero**
  `trailRunOutcome` (`Value == ""`) with `consulted=false`, never calling
  `trailClassifyRun` at all. This is not tidiness: on an unstaged run the
  post-trailer argv scan still runs over a healthy process table, parses
  rows and matches nothing — which would reach the classifier's
  `trailOutcomeNoRowMatched` fall-through, one of its three real answers,
  published about a run in which no command ever existed.
  `finTrailerBuild`'s first parameter is a bare `string` fed from either
  closed set (the classifier's eleven or the staging tier's seven)
  precisely so the pass-through needs no adapter.
- **The primary evidence is pyry's own reap log, not a point-in-time
  read.** `ptyrunner.Run`'s teardown order (`runner.go:479-485`) writes the
  trailer at `emitter.Close()` **before** the reap and before
  `sess.Close()`'s SIGTERM, so a group named in `ReapDescendantGroups`'s log
  (which logs only groups it actually killed, skipping any already gone)
  was alive when the reaper ran — strictly after the trailer write. A
  liveness read taken at *observation* time (up to one `probePollInterval`,
  200ms, after the write, with the reap finishing in one `ps` exec) is a
  systematic false negative on this question. The claude-still-alive read
  (`pinReadState(h.ClaudePID).Verdict`) and the per-pid post-trailer reads
  are recorded as corroboration only — the claude read is **known blind**
  (the reap runs between the trailer and claude's SIGTERM, so in that
  window the command is dead-by-reap while claude still reads alive) and
  the per-pid reads are **known late** — and neither overrides an
  attribution.
- **Composition consumed as returned, four load-bearing choices that would
  otherwise have compiled cleanly but wrongly:** `Needles` is the FIFO path
  **alone** (not the driver's two-needle list — the gather has no
  `finLivePinReduce`-style separation, so adding the claude needle would
  pollute the classifier's match-count arms); `Pinned` is `h.Pin.PGIDs`
  directly (already `[]int`, no `[]reachProc → .PGID` conversion site);
  `Rows` in `finRecordBuild` is the **during-turn** pin (`h.Pin.Rows`), never
  a second post-trailer scan (the gather returns only counts and per-pid
  liveness, never its matches); `Trailer` is built from the gather's
  **third return** (`finSighting`), never a second `trailWaitForTrailer`
  call (which would match on its first poll and report
  `trailBoundFromStart` — a mis-report, not a cost).
- **The publication channel for the fifth criterion is `t.Logf`, not a new
  artifact field.** `finRecordRun` carries only the trailer sub-record's
  outcome string; the classifier's `Detail`/`ClaudeState`/`LivenessSummary`/
  match counts and the staging result reach no artifact field. Both are
  logged via `json.Marshal` or field-by-field rendering — **never `%v` on a
  struct or slice**, which is the concrete mechanism that would otherwise
  print an unredacted argv row from an ordinary-looking debug line. The
  finding sentence itself names only counts, closed-set values, and
  `terminal_reason`; it never quotes `stop_reason` (model-influenced,
  carried uncapped by design) or any sub-record's `Detail`.
- **Captured-bytes discipline**: no `ps -E`/`-Eww` anywhere; the only `ps`
  the file reaches is `pinReadState`'s pid-pinned `pid=,ppid=,stat=` lookup.
  `h.Pin.Rows` and `h.Pin.ClaudeCommand` (verbatim argv) cross into
  `finRecordBuild` unexamined and unformatted.
- **One `t.Fatalf`** of the file's own (`os.MkdirTemp` failure). Three abort
  paths are inherited from `finLiveRunStage` and not re-guarded: no claude
  child spawned, no session id, `ReadJSONL`'s parse fatal.
- **One skip gate** (`PYRY_PROBE_EXIT_PATH`), following
  `background_reach_probe_test.go`'s `reachEnableEnv` shape. The reach
  probe's second gate (`PYRY_USE_STREAMJSON=1` env check) is deliberately
  **not** copied — an earlier revision of this ticket mandated it and that
  mandate was withdrawn in the final spec: this run's own env delta names
  `PYRY_USE_STREAMJSON=0` explicitly and `os/exec` resolves the later value,
  so the delta wins over the operator's shell regardless; copying the gate
  would skip a run that would have been correct. The observed-path reading
  (`RunnerFromEnv` vs. `ClaudeCommand`'s argv-derived label, computed inside
  `finRecordBuild`) is the real guard and is strictly stronger.

## Tests

`TestFinExitClassifyConsultsTheClassifierOnlyOnThePassThrough` — the one
offline-drivable decision this ticket introduces. Table-driven, 8 rows: one
per staging failure value ranged from `finOutcomeValues()` (not
hand-listed, so a future seventh value arrives without an edit), each
paired with `trailRunProofReadings()` deliberately — a wrongly-consulted
classifier answers `trailOutcomeRunningAtTrailer` over those readings,
loudly distinguishable from the expected staging pass-through — plus two
pass-through rows (`trailRunProofReadings()` and `trailRunWellFormed()`,
the well-formed row asserted against `trailClassifyRun`'s own live output
rather than a hand-pinned value, so the row pins the pass-through and does
not re-assert the classifier's own table). Both fixtures come from the
shipped constructors, never hand-built, since a hand-built
`trailRunReadings` is exactly what the classifier's C1–C9 contract block
exists to reject.

RED was established by mutation via `go test -overlay=<abs-path json>` (no
worktree writes, no commit to revert) rather than by argument: observed
failing-subtest counts matched the spec's predicted mutant × row table
exactly — consult-unconditionally 6/8, never-consult 2/8,
outcome-discarded-after-consult 6/8, `consulted` inverted 8/8, gated on the
wrong constant 3/8.

`go test -race -tags e2e_realclaude ./internal/e2e/realclaude/` and
`go vet ./...` pass. `make e2e-realclaude` at review time: the live entry
point (`TestRealClaude_ExitPathWhileCommandRuns`) **skipped** — the
dispatch/review environment has no Claude login — which is the documented,
expected outcome for a `needs-real-claude` ticket, not evidence about

## Patterns established

- **A handle field written by a background goroutine needs its
  happens-before edge documented at the field itself, not only at the call
  site that reads it.** `ExitStatus`'s doc names `PyryExited`'s close as the
  sole edge specifically because the natural-looking consumer shape —
  hoist the value, pass it to a small helper alongside a bool — reads
  outside the receive arm and races. Stating the edge in the field's own
  comment, and refusing the helper that would make the race easy to write,
  is the reusable shape for any future handle field a background goroutine
  populates.
- **A gate-then-consult composition (staging tier → classifier) is made
  structural by returning the zero value of the downstream type on the
  gated-off path, keyed on a package constant deliberately not equal to the
  zero value** (`finOutcomeReadyToClassify`). The zero-`trailRunOutcome`
  return (`Value == ""`, rejected by `trailIsRunOutcome`) is what lets an
  offline trap distinguish "correctly not consulted" from "consulted, then
  the answer was silently dropped" — both would otherwise look identical to
  a caller checking only the returned outcome string.
- **When a record type has no field for a value the evidence needs
  (here: the classifier's full outcome, the staging result), the fallback
  publication channel is `t.Logf` with a hard rule on rendering** —
  `json.Marshal` or field-by-field only, never `%v` on a struct or slice —
  rather than widening the artifact schema for a probe-specific need. Keeps
  the two proven artifact-writing paths (`finWriteArtifacts`'s `run.json`/
  `run.md`) exactly as their own byte sweeps already cover them.
- **Corroboration that is known-blind or known-late is recorded
  explicitly as such and never allowed to override the primary
  attribution.** The claude-still-alive read here is *expected* to
  disagree with the reap-log attribution on a healthy run precisely because
  it is blind to the case the probe exists to catch; stating that
  explicitly is what keeps a future reader from "fixing" the code to make
  the corroboration agree.

## Lessons learned

(From PR #1347's body, and the code-review comment on PR #1347.)

- **`go test -overlay=<abs-path json>` is the cheap way to prove a trap
  discriminates.** Each mutant runs from a scratchpad copy with no worktree
  writes and no commit to revert; the observed per-mutant subtest counts
  either match a spec's predicted table exactly or name the row that
  doesn't. Worth reaching for whenever a spec supplies a mutant-by-row
  table.
- **Initialising an unwritten value to a safe sentinel and making the
  access race-free are two different fixes, and it's easy to do only the
  first.** `pinExitStatusUnknown` fixes what an unwritten `ExitStatus`
  *reads as*; it does nothing about a read that races the writer. Both were
  needed here, and the doc says so at the field rather than assuming a
  reader infers it.
- **`gofmt -l internal/e2e/realclaude/` is dirty on `main` for three files
  unrelated to any given change** (`permission_protocol_spike_test.go`,
  `resilience_test.go`, `tool_loop_test.go` as of this ticket). Filter
  `gofmt -l` output to the PR's own diff before reading it as a finding —
  already captured project-wide in memory as
  `code-review-realclaude-baseline-noise`.
- **Code review SHOULD FIX (non-blocking, not yet applied): four line
  citations into `finding_live_run_test.go` went stale within the same PR
  that shifted them.** This PR's own `+37`/`+27`/`+24`-line insertions into
  that file (the `ExitStatus` field and its doc) moved every anchor the new
  probe file cited into it, and the gap matched the shift exactly — PR-
  created staleness, not inherited debt. The harmful one
  (`finding_exit_path_probe_test.go:70`, citing `:331-341` for the two
  inherited abort paths) now lands on the `promptPath`/`systemPath`
  `os.WriteFile` fatals instead, so a reader following it would wrongly
  conclude those writes are the abort paths needing no guard, and that the
  claude-child/session-id fatals still need one. The other three
  (`:90`→`:242-246` streamjson conclusion, `:123`→`:277-300` SIGKILL
  cleanup, `:265`→`:411-416` two-needle scan) are the same class, lower
  severity. **Still present as of this writing** (verified: `:70`, `:90`,
  `:123`, `:265` still cite the pre-edit line numbers) — below the
  review's 3-finding blocking threshold, explicitly left for "the next
  touch." Re-derive all four against the post-edit file whenever this file
  is next edited. General lesson: a same-PR edit to a file that a sibling
  new file cites by line number stales those citations by construction —
  worth a self-check (`rg` the cited ranges after any such edit) before
  requesting review, matching the project's standing citation-staleness
  pattern (see `code-review-attribute-a-stale-cite-by-gap-size` in agent
  memory).
- **Code review NIT (pre-existing from #1340, not this ticket): the header
  comment's "the two `t.Fatalf`'s ... and they are the only ones" claim in
  `finding_live_run_test.go:227` undercounts** — the file holds four
  (`:333`, `:337`, `:370`, `:376` at review time). Flagged only so it isn't
  misattributed to this PR; out of scope here, already logged as a lesson
  in [`codebase/1340.md`](1340.md).
