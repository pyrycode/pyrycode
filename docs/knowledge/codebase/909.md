# Ticket #909 — v2 `dispatchAppFrame` drains handler replies concurrently with `Route`

Reliability-review finding: `dispatchAppFrame` ran `dispatch.Route` synchronously on the v2 session manager's single `Run` goroutine and drained the per-frame `outbound` channel (capacity `handlerOutboundBuf = 8`) only *after* `Route` returned. A handler emitting more than 8 reply envelopes in one invocation filled the channel and blocked forever inside `Conn.Send` — and because `Route` ran on `Run`, the *entire* v2 session manager wedged for every connection until daemon restart. Latent, not live: today's three handlers (`send_message`, `list_conversations`, `register_push_token`) each emit exactly one reply. `security-sensitive` because the fix restructures goroutine ownership around the AEAD-seal path (`s.send.Encrypt`) on the internet-exposed encrypted surface. See [`features/v2-session-manager.md`](../features/v2-session-manager.md) § `noise_msg` in `V2StateOpen` for the updated data-flow narrative.

## Implementation

- **One production file, `internal/relay/v2session.go`** (+111/-34 net across the diff). No new exported types, no signature change on `dispatchAppFrame`, `handlerOutboundBuf` unchanged at 8.
- **`dispatch.Route` now runs on a short-lived per-frame goroutine.** `dispatchAppFrame` spawns `go func() { defer close(routeDone); dispatch.Route(...) }()` and the `Run` goroutine enters a loop selecting on `<-outbound` (seal-and-forward each reply as it arrives) and `<-routeDone` (drain any residual buffered replies non-blockingly, then return). A handler emitting 16 replies (2× `handlerOutboundBuf`) can no longer fill the channel — `Run` is draining it continuously while `Route` runs.
- **`forwardAppReply(s *V2Session, reply protocol.RoutingEnvelope)` is the extracted seal-and-forward body** — `s.send.Encrypt` → `marshalInnerFrameV2(TypeNoiseMsg, ...)` → `m.send`. Pure extraction of the prior inline loop body (same two WARN messages, same drop-on-seal/marshal-error posture); both select arms call it. Its doc comment states the load-bearing invariant: **MUST run only on the `Run` goroutine** — never from inside the spawned closure.
- **`s.send.Encrypt` never left `Run`.** The spawned goroutine runs only `dispatch.Route` → handler → `conn.Send` (JSON marshal + channel push — no AEAD). This is the property the `security-sensitive` label gates; code review confirmed `forwardAppReply`'s only two call sites are both `Run`-side select arms.
- **`ctx.Done()` is deliberately not a third select arm.** The handler already observes cancellation through `Conn.Send`'s own `ctx.Done()` arm (ctx is the manager's `runCtx`), so a shutdown drives the handler to return → `Route` returns → `routeDone` fires naturally. A third ctx arm risked orphaning the still-running `Route` goroutine or dropping ordered replies mid-stream.
- **FIFO preserved structurally, not by convention.** Single sender (the handler, off-`Run`) + single receiver (`Run`) over the buffered `outbound` channel ⇒ Go's channel semantics guarantee order end to end. `forwardAppReply` runs strictly sequentially on `Run`.
- **The `outbound` channel is still never closed** (#446) — a handler that forks a goroutine retaining `*dispatch.Conn` and sends after `dispatchAppFrame` returns still writes into a leaked-but-capacity-bounded channel the GC reclaims; closing here would panic such a sender. This property is orthogonal to the concurrent-drain change and survives verbatim.
- **New test file `internal/relay/v2session_appframe_test.go`** (+198 LOC) rather than an edit to the 175 KB `v2session_test.go`, reusing existing package helpers (`driveToOpen`, `sealAppFrame`, `decryptAppFrame`, `v2Recorder`, `waitForOutboundCount`):
  - `TestV2Session_OpenState_ProlificHandler_NoDeadlock` — a handler emitting 16 replies completes without wedging the manager; a second frame on the same conn is still serviced afterward. Fails (times out) against the pre-fix drain-after-Route code; passes after.
  - `TestV2Session_OpenState_ProlificHandler_EmissionOrder` — decrypts all 16 sealed replies via the phone-side `initRecv` (which decrypts strictly in send-counter order) and asserts indices `0..15` in order — doubles as a send-counter-integrity check, since a reordered or dropped seal surfaces as an AEAD authentication failure, not a silent gap.
  - AC #3 (seal stays on `Run`) is pinned by `-race` across both tests, not a separate fixture — an off-`Run` seal or concurrent CipherState touch would fire the race detector and break the ordered-decrypt assertion.

## Patterns established

- **Interleave-drain over accumulate-then-seal.** The architect's spec named two shapes: (a) an off-`Run` drainer buffers replies into a slice, `Run` seals after joining; (b) run `Route` on a goroutine, `Run` interleaves draining with waiting for it. (b) shipped — bounded memory (no unbounded accumulation for a prolific handler) and fewer lines, at the cost of `forwardAppReply` running once per reply instead of once per batch. Generalises: when a producer-consumer rendezvous needs to move off a single-owner goroutine but the *sink* operation (the seal) must stay on it, interleave-drain-as-you-go beats buffer-then-flush unless the sink genuinely needs batch context.
- **Extract the single-owner-sensitive body into a named, doc-commented method before making its call site concurrent.** `forwardAppReply`'s doc comment isn't decorative — it's the artifact code review checked call sites against. When a fix introduces a new goroutine near existing single-owner state, give the single-owner operation its own named function with an explicit "MUST run only on X" comment; it turns "verify no cross-goroutine access" from a diff-wide reasoning exercise into a two-call-site grep.

## Lessons learned

- **flynn/noise's `CipherState.Decrypt` advances an internal receive counter — you cannot decrypt reply N in isolation.** A test asserting FIFO order by decrypting sealed replies must decrypt them in send order; skipping ahead to reply N surfaces as `chacha20poly1305: message authentication failed`, not a wrong-order result. This is *why* the emission-order test doubles as a send-counter-integrity check under `-race` (per the spec's design) — the AEAD counter discipline forces the test to prove ordering as a side effect of being able to decrypt at all.
- **Two evergreen-doc callouts about this deadlock predated the fix and needed correcting, not just adding to.** `features/v2-session-manager.md` had two verbatim descriptions of the pre-909 behavior — `StreamBundle`'s doc comment ("handlerOutboundBuf = 8, deadlocks on >8 sends from a handler") and its prose mirror explaining why bundles route around the reply channel — both stated a deadlock trigger that no longer exists post-fix. Reflexively appending a "#909 fixed this" footnote without touching the original sentence would leave a doc that reads as self-contradictory. When a ticket falsifies a previously-true statement elsewhere in the knowledge base, find and rewrite that statement — don't just add a new one nearby.

## Out of scope (deferred)

- **Head-of-line blocking from a slow/hung handler.** `Run` still blocks its whole dispatch loop for the duration of `dispatch.Route` (the two-arm select has no other work to do while waiting) — a handler that's merely *slow*, not prolific, still stalls every `conn_id`. #909 fixed the reply-*count* deadlock, not this reply-*latency* stall. Tracked as the pre-existing "per-conn fan-out for handler dispatch" follow-up in [`features/v2-session-manager.md`](../features/v2-session-manager.md) § Out of scope — the priority concern before flipping `cmd/pyry/relay.go`'s production cutover to v2.
- **Shrinking `handlerOutboundBuf`.** Considered and rejected in the spec: a larger buffer still reduces `conn.Send`/`Run` rendezvous churn for the common 1-few-reply case. The fix removes the *correctness dependence* on the buffer's size, not the buffer's value.
