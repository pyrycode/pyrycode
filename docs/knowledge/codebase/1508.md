# Ticket #1508 — `sanitizeName` must never return `.` or `..`

`sanitizeName` (`cmd/pyry/main.go`) is the only path-traversal defence in front of five per-instance path resolvers (`resolveRegistryPath`, `resolveConversationsRegistryPath`, `resolveDevicesPath`, `resolveServerIDPath`, `resolveSocketPath`). Its allowlist permitted `.`, so the literal names `.` and `..` survived the transform unchanged and reached `filepath.Join` as live path components: `PYRY_NAME=.` collapsed the per-instance directory away (state landing beside `config.json` in `~/.pyry`), and `PYRY_NAME=..` put `sessions.json`, `conversations.json`, `devices.json` and `server-id` directly in `$HOME`. `resolveSocketPath` was never affected — it concatenates a `.sock` suffix rather than joining the name as a directory component.

## Implementation

- The fix is a switch on the **built result**, not the input, appended after the existing empty-input guard: `"."` → `"._"`, `".."` → `".._"`. This mirrors what the transform already does to `"./x"` → `"._x"` and `"../x"` → `".._x"` (the separator becomes `_`), and checking the output rather than the input keeps the postcondition holding even if the allowlist changes later.
- New doc comment on `sanitizeName` states the postcondition explicitly: the result is non-empty, holds no path separator, and is never `"."` or `".."`, so `filepath.Join(dir, sanitizeName(name), file)` always yields `dir/<one-component>/file`. Cites `TestSanitizeName` and `assertInsideInstanceDir`'s callers by symbol, not by line (repo convention — `make cite-guard`).
- No resolver, call site, or `keys.LoadOrCreate` accept/reject outcome changes. `validDaemonName` (`internal/keys`) still rejects `._` and `.._` — both still contain `.` — so the write-before-reject ordering in `runPair` is unaffected; only *where* the pre-rejection write lands changes (now inside a correctly contained instance directory instead of `$HOME`).
- Orphaned state from a pre-fix `PYRY_NAME=.`/`..` run is left in place deliberately — no migration, no cleanup, no warning log. See the architecture spec's § Design for the reasoning.

## Patterns established

- **Shared containment assertion, `assertInsideInstanceDir` (`cmd/pyry/args_test.go`)**: asserts `filepath.Rel(home/.pyry, got)` has exactly two components and the first is neither `"."` nor `".."`. Two clauses, each the sole detector of one hostile input — `.` is caught only by the component-count check (`filepath.Join` cleans `.` away, so a naive `rel == ".." || strings.HasPrefix(rel, "../")` check is blind to it), `..` only by the first-component check. Confirmed by mutation in code review: dropping either clause lets exactly one hostile name through green. Reuse this helper — don't hand-roll a containment check — for any future per-instance path resolver.
- **Guard the built result, not the input**, when a transform's allowlist could plausibly grow: it's the durable form of a postcondition and survives allowlist changes that individually re-introduce a dangerous output.
- **`t.Setenv` vs `t.Parallel`**: the AC-3 socket pin (`TestResolveSocketPath_DotNamesStayInPyryDir`) was added as a non-parallel *sibling* test rather than a subtest of the existing parallel `TestResolveSocketPath`, because `t.Setenv` panics inside a parallel test and mutating `$HOME` during the parallel phase would race every other parallel subtest reading it. The four registry-style resolver tests already follow this shape for the same reason.

## Lessons learned

- A containment check of the shape `rel == ".." || strings.HasPrefix(rel, "../")` is blind to a bare `.`: `filepath.Join` cleans the `.` away, so the result stays provably inside the parent while the intended one-level-deeper subdirectory silently vanishes. Containment and *depth* are separate properties — a test asserting only the former passes on a path one level too shallow. Asserting the component count plus the first component's identity catches both escapes; either clause alone catches just one. (From the PR's own "Lessons learned" section.)
- Code review additionally fuzzed the full postcondition directly (non-empty, separator-free, never `.`/`..`, and `filepath.Join(dir, out, file)` always exactly `dir/<one-component>/file`) — 3,075,188 executions, zero counterexamples — and swept `codegraph_callers sanitizeName` for consumers beyond the five named resolvers, finding `runPairDefault` and `startRelayV2`; both still refuse `._`/`.._` via `keys.LoadOrCreate` identically to how they refused `.`/`..` pre-fix. Worth the extra sweep whenever a path-building helper's blast radius is claimed rather than enumerated.
