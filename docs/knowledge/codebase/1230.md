# Ticket #1230 — Is a backgrounded Bash command inside the reaper's descendant-BFS reach?

Adds `internal/e2e/realclaude/background_reach_probe_test.go`, an opt-in live probe
(`PYRY_PROBE_BACKGROUND_REACH=1`) plus three credential-free self-checks that answer the
predictive half of "does claude's timeout-triggered backgrounding leak a process past
`agentrun.ReapDescendantGroups`": is a backgrounded Bash command still a transitive child
of claude's pid, and would its process group survive the reaper's three exclusions. One
during-turn snapshot, no teardown — the confirmatory half (does it actually die, and by
whose hand) is #1231's. Zero production files changed; the deliverable is the observation.
**Answer, from the 2026-07-30 live run: yes reachable, and the group survives all three
exclusions** — see § The answer.

## Implementation

- **Content-first identification, never subtree-first (AC1).** `reachScanArgv` execs one
  full-table `ps -axww -o pid=,ppid=,pgid=,command=` and hands the bytes to
  `reachMatchArgvRows`, which matches the run's FIFO path and session UUID against **full
  command lines across the whole process table** — never a base name, never restricted to
  a subtree walked down from a known root. This is the mechanism the ticket exists to add:
  #1223's `probeAnnotateCommands` reduces argv to `filepath.Base(fields[1])` and only
  annotates pids it already found by walking down from pyry, so it structurally cannot see
  a re-parented survivor. `-ww` is load-bearing — without it macOS truncates the command
  column to terminal width and silently drops the argv tail holding the FIFO path,
  reproducing that exact defect with no visible symptom.
- **Three-valued match outcome, established before any reachability claim.** `matched`
  (background handle present in `toolUseResult.backgroundTaskId` AND ≥1 argv row hit) /
  `trigger-never-fired` (no handle — inconclusive, re-run) / `fired-no-row-matched` (handle
  present, zero rows — a finding in its own right, never collapsed into "not reachable").
  The handle is read from the `tool_result` envelope, never `input.timeout` (#1223 observed
  it absent 10/10).
- **Root pinned content-first, then checked against the rig's positional guess (AC2).**
  The rig's `probeWaitForDirectChild` picks claude's pid **positionally** — pyry's first
  direct child, no content check. This ticket pins it independently by matching the run's
  `--session-id <uuid>` against claude's argv (`ptyrunner/runner.go:618`), then records
  whether the two agree. Because both reachability reads are rooted at claude's pid, a
  mis-identified root would make them agree and both be wrong — agreement never validates
  the root, only content does.
- **Two reachability reads off one integer snapshot (AC2).** `reachChainUp` walks the ppid
  chain **up** from each matched pid to claude's pid (cycle-guarded, mirroring production's
  `seen`); `probeDescendantsFromPS` (#1223's, already self-checked, unedited) BFS's **down**
  from claude's pid using production's exact parse/walk. Disagreement is recorded as an
  **instrument fault**, never a finding — the design refuses to report a "leak" off two
  reads that don't corroborate each other.
- **Exclusion arithmetic, with the real integers (AC3).** Reproduces `reap.go:52`'s three
  comparisons (`pgid <= 1`, caller's own group, `pgid == rootPid`) against the held pgid,
  the reaper's own pgid (read from the **`pyry agent-run`** process's row in the integer
  snapshot, not the test binary's), claude's pid, and claude's pgid — and separately
  records whether `pgid == pid` actually holds for claude, since `reap.go:45-47`'s
  group-leader claim is asserted in a comment, not tested, anywhere in production.
- **Redaction is structural (`security-sensitive`, earned by this ticket, not inherited
  from #1223).** The raw argv table never leaves `reachScanArgv`'s one stack frame; no
  `-E`/`-e`-with-environment/`eww` anywhere in the file (`ps -E`/`eww` would dump every
  process's environment, including `CLAUDE_CODE_OAUTH_TOKEN`); needles matched in Go,
  never handed to a shell; each retained command capped at 512 bytes **after** matching
  (capping before would make a needle past the cap invisible — an instrument limit
  misreported as `fired-no-row-matched`); only the integer-column snapshot is persisted
  verbatim — that's what reaches the public comment.
- **Reuses #1223's rig verbatim; no edits to `background_trigger_probe_test.go`.** Every
  new symbol is `reach`-prefixed to avoid a same-package redeclare against the concurrent
  `feature/1219` branch and the sibling #1231.
- Final size: 1461 lines (three self-checks — `TestReachMatchArgvRows`,
  `TestReachChainUp`, `TestReachBackgroundHandle` — plus the live test), against the
  spec's ~590 LOC projection. In family with sibling `background_trigger_probe_test.go`
  (1312 lines); the projection was low, not the file bloated.

## The answer

Run by hand 2026-07-30, claude 2.1.220, model `claude-haiku-4-5`, ptyrunner path
(corroborated two ways: `PYRY_USE_STREAMJSON` cleared, and claude's own argv carries
`--append-system-prompt-file`, a flag only the terminal path emits).

**The backgrounded command IS a transitive child of claude's pid, and its process group
survives all three reaper exclusions.**

```
pid=99630 ppid=99624 pgid=99624   (cat, held on the FIFO)
pid=99624 ppid=99233 pgid=99624   (zsh -c wrapper — its own group leader)
pid=99233 ppid=99198 pgid=99233   (claude)
```

reaper's own pgid (read from `pyry agent-run`'s row) = 99198; claude pid/pgid = 99233/99233
(`pgid == pid` **holds** on this run, validating `reap.go:45-47`'s claim). Held pgid 99624
survives `<= 1`, survives `== 99198`, survives `== 99233` → would land in the reaper's kill
set. Up-walk and down-BFS agreed.

**Disposition:** reachable, would be targeted — no follow-up ticket for a reachability gap.
Stated plainly per the AC: this establishes only that the reaper **would** target the
group; whether it actually dies, and by whose hand, is #1231's question, not answered here.

**One flag carried forward to #1231:** the group that would be killed is the **zsh
wrapper's**, not `cat`'s own — `cat` is only in the kill set by inheriting the wrapper's
pgid. If `cat` is ever re-parented or moved to its own group, this arithmetic changes.

Full envelopes and the verbatim integer-column snapshot are on the issue:
[live probe result](https://github.com/pyrycode/pyrycode/issues/1230) (final comment,
2026-07-30).

## Patterns established

- **Content-first identification for a reachability probe means matching full argv
  against a run-unique needle across the *whole* process table, never walking down from a
  known root.** A subtree-first search can never detect the exact failure mode
  (re-parenting out of the subtree) the probe exists to catch — it would report the leak
  case as merely "absent." Reach for this whenever a probe's job is to prove a negative
  about reachability, not just to annotate what a cheaper walk already found.
- **Two "independent" reads sharing an unvalidated root make agreement worthless as
  proof.** If both reads are rooted at the same pid and that pid is wrong, they agree and
  are both wrong. Pin the root itself content-first (a unique, unforgeable value in the
  target's own argv — here, `--session-id <uuid>`) and record whether it agrees with a
  cheaper positional guess, rather than trusting agreement alone.
- **A match outcome with a "not found" arm needs three values, not two, whenever "not
  found" is ambiguous between "never ran," "ran and is now gone," and "matcher is
  broken."** Collapsing to a boolean turns the second case into a false positive for the
  first, or worse, into the alarming verdict the probe was designed to catch.
- **Gate downstream arithmetic on the load-bearing snapshot's own error status, placed
  structurally after the parts of the record that don't depend on it.** A partial read
  (context-timeout truncation on a loaded machine) can make two otherwise-independent
  reads spuriously agree — the gate has to sit where it disqualifies exactly the
  arithmetic that depends on the bytes, not before or it mislabels findings that don't.

## Lessons learned

From the PR body (#1232), round-1 code review (1 MUST FIX / 1 SHOULD FIX / 4 NIT), and
round-2 review (PASS, 0 MUST FIX / 1 SHOULD FIX / 2 NIT):

- **A probe's content-first identification can depend on a routing decision that drifts
  underneath it — check the routing at the gate, not in the record.** Root pinning here
  depends on `--session-id` appearing in claude's argv, which only the ptyrunner path
  emits; `PYRY_USE_STREAMJSON=1` (live in the dispatch environment) routes to
  streamrunner instead, where claude mints its own session id and the needle can never
  match. Without a gate, the run would burn a live turn to reach a guaranteed
  root-disagreement. Fixed with an explicit `t.Skipf` naming the corrected
  `env -u PYRY_USE_STREAMJSON …` command. Same drift #1223 hit from the other side (its
  streamrunner-fallback gate assumption silently stopped holding).
- **A record struct gaining a slice field stops being `==`-comparable, and a
  synthetic-tree self-check copied from a sibling test won't catch that at review time —
  only the compiler does, at build time.** `reachProc` grew `Needles []string`; the
  tempting fix (compare `%+v` string reprs) would have quietly started comparing the
  512-byte-capped `Command` field too. Worth checking before reusing
  `TestProbeDescendantsFromPS_SyntheticTree`'s assertion shape on a type that has since
  grown a slice.
- **The redaction cap must be applied after matching, not before.** Capping first makes
  a needle sitting past 512 bytes invisible — which reads as `fired-no-row-matched`, a
  *finding* in AC1's vocabulary, rather than as an instrument limit. Over-retaining is a
  redaction problem; under-matching is a false finding — the two failure directions are
  not symmetric, and only one of them corrupts the observation.
- **Reading the same pid's pgid off two different `ps` snapshots (integer-column vs.
  argv) can disagree — name which one is authoritative rather than silently preferring
  one.** Fixed twice: once for claude's pgid at implementation time, and again (SHOULD
  FIX, round 1) for the held pgid, which had been taken from the argv snapshot while
  every other exclusion-arithmetic integer came from the integer snapshot. Both now read
  from the integer snapshot — the frame AC4 publishes verbatim — with divergence
  `note()`d rather than resolved silently.
- **`ps -axww -o pid=,ppid=,pgid=,command=` is the portable four-column form** (verified
  darwin 25.5). `-ww` is not hygiene — see § Implementation.
- **A snapshot's own read error has to gate everything computed from it, and the gate's
  placement matters (round-1 MUST FIX).** `rec.PSError` was recorded but never
  consulted; `probeProcessSnapshot` returns partial stdout *alongside* its error on a 5 s
  context timeout (a loaded machine is the expected condition here, not the exotic one),
  so a cut table that drops an intermediate hop while keeping the held row makes the
  up-walk and down-BFS spuriously **agree** on "not reachable" — passing the skew check
  and publishing a false leak claim from an instrument that half-ran. Fixed by gating
  *after* the match-outcome switch rather than inside it: the match question is answered
  by the argv `ps` alone, so a failed integer snapshot must neither relabel a true
  `matched` nor suppress a true `fired-no-row-matched` finding, only disqualify the
  reachability half. Code review round 2 verified the asymmetry this rests on:
  `reachScanArgv` discards partial output on error while `probeProcessSnapshot` doesn't,
  so the two `ps` calls genuinely warrant different gating.
- **A zero-length artifact reads as "never got that far," which is a different claim
  from "the read failed."** `writeReachArtifacts` skipped writing `reach.ps.txt` when
  `rec.rawPS` was empty; fixed to write an explanatory placeholder naming `ps_error` and
  the disposition instead of leaving the artifact silently absent.
- **A boolean field with finding-semantics needs the same "never measured" caveat every
  sibling field in the same record gets — it doesn't travel automatically.** Round-2
  SHOULD FIX (shipped unfixed, under the 3-finding merge threshold): `claude_pgid_equals_pid`
  and `up_and_down_reads_agree` publish `false` on runs that never measured them, and AC3
  treats that first boolean as a finding. The `ClaudeRow` field got exactly this caveat
  this round; it didn't propagate to its siblings.
- **A QA-reported "regression" in a full-suite `-race` run can be a load-sensitive flake
  in an unrelated package — verify the causal link before trusting the label.** A
  `TestRelayV2_StreamNewSessionRotatesAndRestartsFresh` failure surfaced on a run that
  changed zero production files and one test file in a package not even compiled under
  the failing test's build tag (`go list -tags e2e` excludes `realclaude`). Baseline
  comparison + isolation reruns confirmed no causal link; the mechanism (an M2
  actuation-loop race against in-flight re-rotation) was characterized but is out of
  this ticket's scope to fix.
