# Ticket #1492 — cancel the daemon ctx before the joins that need it cancelled

Filed from the 2026-08-16 full-repo code review. `runSupervisor` (`cmd/pyry/main.go`) never
cancelled the daemon ctx on an error exit, which left two joins blocking forever on
goroutines whose only exit is `<-ctx.Done()`. Operator-visible symptom: starting a second
`pyry` against a live daemon's socket hung silently instead of printing "another pyry
instance is already running" — the diagnostic `ctrl.Listen`'s split-from-`Serve` design
exists to surface.

## Implementation

Two sites in `runSupervisor`, both ordering-only fixes — no goroutines added or removed,
no new exported symbols:

- **Site 1 — the deferred relay cleanup.** `defer relayCleanup()` (registered after `defer
  cancelCause(nil)`, so it ran *before* that cancel per defer LIFO) is now `defer func() {
  cancelCause(nil); relayCleanup() }()`. `relayCleanup` joins three producer drains
  (`startSessionTransitionStreamV2`, `startQueueStateStreamV2`, `startSessionErrorStreamV2`)
  that are each a bare `<-done` over a `Run` loop selecting only on `ctx.Done()` — wired
  unconditionally whenever the relay leg is enabled (the default), independent of
  runner mode. `ctrl.Listen()`'s `ErrInstanceRunning` return is today's one reachable
  error return between `startRelay` and the end of `runSupervisor`.
- **Site 2 — the `<-qDone` join.** `cancelCause(nil)` is now called immediately after
  `runErr := pool.Run(ctx)`, before `ctrl.Close()` / `<-ctrlDone` / `<-qDone`.
  `Pool.Run`'s `return g.Wait()` can return an early non-ctx error (`g`'s ctx is derived
  from the daemon ctx; cancelling `gctx` does not cancel it), and `msgqueue.Queue.Run`
  blocks on `<-ctx.Done()` before joining its own drains — so the `<-qDone` receive could
  never complete on that path.

Both new `cancelCause(nil)` calls are no-ops on every path that reaches them today
(signal, `pyry stop`, a fatal 4409 already cancels ctx first) — `context.WithCancelCause`
is first-cause-wins, so a 4409 cause already recorded by `startRelay`'s `conn.Wait()`
classifier survives both calls and `fatalCause` still reports it.

New test: `TestE2E_Startup_SecondInstanceExitsNonZero` in `internal/e2e/startup_test.go`.
Starts a daemon with the relay leg pointed at `wss://127.0.0.1:1/v2/server` (a URL that
passes scheme validation, is unbindable without root, and — because `relay.Connect` never
dials synchronously — fully wires the producer goroutines and the deferred cleanup while
staying hermetic), then starts a second process against the same socket via
`StartExpectingFailureIn`. Asserts non-zero exit, `another pyry instance is already
running` on stderr, and that the live daemon survives (`status` still exits 0).

Site 2 has no live repro — nothing in the daemon today makes `pool.Run` return an early
non-ctx error (`Pool.supervise`'s `ErrPoolNotRunning` return is unreachable from `Pool.Run`
per the ticket's correction to its own filed body). It was verified with a throwaway
errgroup-member mutant (`M1492-early-pool-error`: sleep 3s, then return an error) built via
`go build -overlay` against both trees — unpatched hangs past an external timeout, patched
exits non-zero at ~5s with `pyry: supervisor: M1492: forced early pool.Run error` on
stderr — not shipped as a test, since a permanently-vacuous e2e would be worse than none.

## Patterns established

- **Compose the unblocking cancel into the cleanup defer, not a second adjacent
  `defer cancelCause(nil)`.** The ordering that makes two adjacent defers correct
  (register the cancel *after* the cleanup so LIFO runs it *before*) reads backwards and
  invites a future edit to "fix" it into the wrong order. One closure stating
  `cancelCause` then the cleanup, in source order, is self-evidently correct without
  relying on the reader tracking LIFO.
- **`context.WithCancelCause`'s first-cause-wins lets a bare `cancelCause(nil)` be
  inserted as a structural safety net without a nil-check guard.** Both new call sites are
  unconditional; they're no-ops whenever a real cause is already recorded, and they're the
  fix precisely when nothing has cancelled yet. No caller needs to ask "was this already
  cancelled?" first.
- **A deferred cleanup that joins ctx-only goroutines must itself cancel ctx before it
  joins — cancel-then-join, not join-then-hope-something-else-cancelled-it.** The
  producers' own shape (`<-done` over a `Run` loop selecting only on `ctx.Done()`) was
  correct all along; the bug was purely in the caller's ordering relative to defer LIFO.
  Don't add close-the-input-channel or timeout escapes to a drain goroutine as a defense
  for a caller ordering bug — fix the ordering.

## Lessons learned

- The ticket's filed body named "supervise-bootstrap failure" as a second path through the
  deferred cleanup; it's unreachable (`Pool.supervise` only ever returns
  `ErrPoolNotRunning`, and `runGroup` is set immediately above the call). The real second
  path — an early non-ctx error out of `pool.Run`'s `g.Wait()` — wedges at a different site
  (the `<-qDone` join) *before* the deferred cleanups are even reached, so it needed its
  own fix rather than falling out of the site-1 change. Worth re-deriving a ticket's own
  causal chain rather than trusting a filed "second path" claim verbatim, even when the
  first path it names checks out.
- `ensurePyryBuilt` (`internal/e2e/harness.go`) shells out to its own `go build`, so a
  `-overlay` passed to `go test` never reaches the daemon binary the harness spawns.
  `PYRY_E2E_BIN` is the seam that does — needed for both the AC-2 red-on-unpatched-tree
  verification and the AC-3 mutant runs.
- `relay.Connect` only fails synchronously on config errors (bad scheme, missing identity,
  missing device registry); the dial itself runs in a launched goroutine. A `wss://` URL
  nothing can ever answer (`127.0.0.1:1`) therefore still gets the relay leg fully wired —
  producers running, cleanup registered — making the deferred-cleanup deadlock reachable
  with no fakerelay and no network.

## Testing

`go test -race ./cmd/pyry/...` and `-tags e2e -race ./internal/e2e/...`, `go vet ./...`,
`make cite-guard`; QA ran the full-module race gate (`make check` — green, `make build` —
green). Code review: PASS, no findings beyond the QA gate pass. `TestRelay_4409_PersistentExitsNonZero`
and `TestRelay_4409` (AC-4, the fatal-cause-survives property) ran unmodified and stayed
green — the first-cause-wins guarantee is a property of `context.WithCancelCause` itself,
not new code, so this is the pin, not a fresh proof.
