# Ticket #1243 — An interrupted PTY turn reports `turn_end` with reason `cancelled`

Closes the gap [#1191](https://github.com/pyrycode/pyrycode/issues/1191)'s live
gate found and [#1229](https://github.com/pyrycode/pyrycode/issues/1229) split
out: on the PTY/JSONL path, `EventKindJsonlEndOfTurn` (`internal/turnbridge/mapper.go`)
is the only source of `turn_end`, and it fires only on a clean
`stop_reason=="end_turn"` — so an interrupted turn (claude cancels in ~65 ms and
records it, but with `stop_reason: "tool_use"` on its last assistant entry)
produced no `turn_end` at all, and the client's Stop affordance hung until its
own 120 s timeout. `internal/streamsup/parser.go` already reported the same
user action on the stream-json path as `TurnEndReasonCancelled`; the two
surfaces now agree. Spec: `docs/specs/architecture/1243-interrupt-turn-end-cancelled.md`.
PR: [#1246](https://github.com/pyrycode/pyrycode/pull/1246). Size S — one new
branch + three unexported helpers in `internal/turnbridge/mapper.go`, no
production files elsewhere, no taxonomy change (`TurnEndReasonCancelled`
already existed).

See [features/turnbridge-package.md](../features/turnbridge-package.md) for
the mapper's full contract (updated by this ticket) and
[codebase/1191.md](1191.md) for the live-gate diagnosis this fix resolves.

## Implementation

- **The discriminator is a conjunction of two independent signals**, not one.
  "Did an interruption happen?" has only a prose answer — claude emits no
  structural field that's true for both observed shapes (`toolUseResult.interrupted`
  lives on the *`tool_result`* entry, so it can't see the no-tool-in-flight case
  at all, and all tracked occurrences are `false` anyway). "Who wrote this
  entry?" is answered structurally: `userAuthored(e)` checks only for the
  *presence* of the top-level `permissionMode` key (`_, ok := e.Raw["permissionMode"]`),
  never its value. `isInterruptMarker` requires `!userAuthored(e) &&
  strings.HasPrefix(strings.TrimSpace(userText(e)), interruptMarkerSentinel)` —
  the authorship gate runs first because it's a map lookup, so a genuine
  prompt's body (which can run to tens of KB) is never concatenated by `userText`.
- **`interruptMarkerSentinel = "[Request interrupted by user"` is a prefix, not
  an exact string** — it covers both observed variants (`…user]` on claude
  2.1.128, `…user for tool use]` on 2.1.220, live daemon-log evidence in the
  issue) and any future suffix claude adds, with no code change. This is the
  entire prose-treadmill surface (#563, #1219 paid this same cost before).
- **Branch order is load-bearing, not incidental.** The new check sits in
  `mapEntry`'s `case "user"`, *after* the existing `ParseToolResult` branch —
  so any entry carrying a `tool_result` block is matched and returned before
  the marker check runs. This is what keeps attacker-controlled tool output
  (a fetched page, a `cat`ted file) from ever reaching the prose matcher, even
  when that output quotes the marker verbatim.
- **The evidence for the authorship gate was re-censused at spec time**, not
  just inherited from the ticket's own (deliberately conservative) count: 3
  tracked full transcripts (2 claude versions, 3 sessions) show `permissionMode`
  present on all 3 genuine prompts and absent on all 34 claude-authored `user`
  entries (33 `tool_result`, 1 marker); a 60-session live scan of
  `~/.claude/projects` added 60 more prompts (present) and 8 `isMeta` skill
  injections (absent) with zero counterexamples in either direction. Content
  shape (string vs. text-block array) was measured and **rejected** as a
  discriminator: 30 of 60 live prompts arrive as block arrays, the same shape
  as the marker.
- **Test builder gap.** `mapper_test.go`'s existing `entry()` helper marshals
  only `{type, message}` and leaves `Raw` nil — it cannot express a top-level
  sibling field at all. A second builder, `entryFromLine(t, line)`, mirrors
  tui-driver's `parseEntry`/`parseMessage` byte-for-byte (`Raw`/`RawLine`
  always set, typed `Message` populated only when `message` is a JSON object)
  so it can drive fixtures built from real JSONL lines. `entry()`'s 13 existing
  call sites are untouched.
- **Fixture provenance has exactly two arms, no third.** Every fixture is a
  `const` backtick string labelled either **(a) verbatim** (quoted byte-for-byte
  from `internal/agentrun/jsonl/testdata/no_end_turn.jsonl`, cited `path:line`)
  or **(b) derived** (a named base line with a named span substituted). The
  2.1.220 tool-use marker, the `is_error:true` tool_result, and the forged
  prompt have no raw counterpart anywhere in the repo — the first because the
  live rig deletes its temp `HOME` on every exit path, the other two because
  they can't occur naturally — so all three are arm (b), and the AC5 clause
  this satisfies exists specifically to forbid presenting a constructed line as
  captured.
- **7 new table rows** in `TestMapEvent` (`internal/turnbridge/mapper_test.go`):
  2 are the fix itself (RED on `main`, green after — no tool in flight, tool in
  flight); 5 are directional guards that are green on both sides by design,
  each pinned to a specific wrong-discriminator direction (error-flag-only,
  prose-only, authorship-only, marker-checked-before-`tool_result`, and — added
  during implementation, see Lessons — marker text riding a *mixed* entry's
  text block alongside a `tool_result` block).

## Patterns established

- **A conjunction discriminator needs its two halves named and independently
  evidenced**, not blended into one "looks safe" rule. This spec's § Evidence
  table (prompt vs. tool_result vs. marker, in-repo counts + a reproducible
  live-scan script) is what turns "we think claude always writes
  `permissionMode` on prompts" into a checked claim with a stated sample size —
  worth the same treatment the next time a mapper keys behavior off transcript
  shape rather than an explicit event kind.
- **A forged/adversarial fixture must differ from the genuine article only
  along the dimension the discriminator reads.** `forgedPromptLine` is
  `markerLine` plus exactly one key (`permissionMode`) — verified as a
  key/value-set diff, not eyeballed. A forge fixture that also differs in some
  incidental sibling (e.g. plain-string vs. block-array content) would pass the
  test for the wrong reason while the real forge (an attachment-bearing prompt
  quoting the marker) still worked.
- **Splice derived fixtures byte-preservingly; don't round-trip through
  `json.Marshal`.** Every arm-(b) fixture is its real base line with one JSON
  value span replaced in place. A `json.Unmarshal` → mutate → `json.Marshal`
  round-trip silently renormalises escaping (an em-dash came back re-escaped
  on the first attempt at the tool-output fixture) — a derived fixture stops
  being "differs from its base only where documented" the moment it's been
  reserialized.

## Lessons learned

- **A guard row's directional claim is a measurement, not a reading of the
  code — mutation-check it.** The spec asserted `toolResultMarkerLine` (tool
  output quoting the marker) would go red if the marker check ran before
  `ParseToolResult`, and treated that as pinning the branch order. Mutation-
  checking all four wrong-discriminator directions found this one doesn't
  hold: the marker in that fixture rides the `tool_result` block's `content`
  payload, and `userText` only ever reads `text`-typed blocks — so the prose
  matcher never sees it regardless of branch order. Branch order was in fact
  unpinned by the planned test set. Fixed by adding
  `toolResultPlusMarkerTextLine` — one entry carrying both a `tool_result`
  block and a separate marker `text` block — the only input shape where branch
  order is actually what stands between tool output and the matcher.
  Generalizable: when a test is claimed to pin property X, mutate X and watch
  that specific row go red; two independent defenses (here: branch order *and*
  `userText`'s block-type filter) can make a row pass for a reason other than
  the one being claimed for it.

## Deliberately not built here

- **`permissionMode` upgrade tripwire.** Nothing fails loudly if a future
  claude version stops writing the field on prompt entries — the authorship
  gate would then read every entry as claude-authored, and a prompt quoting
  the marker verbatim could forge its own turn end again (the design's one
  fail-*open* direction; every other failure mode here is fail-safe). Left as
  an open question for its own ticket, since it needs a fixture-refresh
  mechanism this repo doesn't have yet.
- **The live gate** (`pyrycode-desktop`'s `real-claude-interrupt.spec.ts` with
  `interactiveRunner: 'pty'`) is operator-run only — it cannot run in this
  worktree or in CI. Reported as not-run in the PR; needs a build of this
  branch run by an operator.
- **[#1244](https://github.com/pyrycode/pyrycode/issues/1244)**, the fake-tier
  PTY oracle that locks this behavior in against regression, was blocked on
  this ticket landing (it needed `cancelled` to actually be assertable on this
  path) and is unblocked now.

## Security note

`internal/turnbridge`'s feature doc previously stated the package carries no
`security-sensitive` label in either direction — the producer maps trusted
local claude output, no trust decision or capability enforcement lives there.
This ticket adds the first one: `userAuthored` is a genuine authorship trust
decision (is this transcript entry claude's or the client's, echoed back
through the session), made in the inbound mapper for the first time. It's
narrow — a single boolean map-lookup gating whether prose can end a turn, no
capability grant, and downstream carries only a `Reason` string, no
transcript-derived bytes — so the package-level label is unaffected, but
`turnbridge-package.md`'s `## Not security-sensitive` section now names the
carve-out explicitly rather than reading as an unqualified blanket claim. See
the architecture spec's § Security review for the full trust-boundary
analysis (verdict PASS, two accepted-risk SHOULD-FIXes: a local `isMeta`-shaped
false positive, and the `permissionMode` fail-open direction above).
