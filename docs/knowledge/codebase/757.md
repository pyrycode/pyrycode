# Ticket #757 — `internal/acp`: outbound-request primitive (agent→client call, id-correlated)

Makes the `internal/acp` transport **bidirectional**. Besides answering host
requests (the inbound floor built by [#755](https://github.com/pyrycode/pyrycode/issues/755)),
the agent can now issue its *own* JSON-RPC request to the client and block for
the id-correlated response — `Transport.Call`. This is the transport primitive
the later handler tickets need: `session/request_permission` (T8's permission
proxy) and the held `session/prompt` return path (T7) both issue outbound calls,
now without reopening the read loop.

This ticket adds **only the outbound direction**: id generation, a pending-call
registry, the blocking `Call`, and routing of inbound *response* lines to their
waiters. It drives no claude, registers no real ACP method, and has **zero
consumers** until T7/T8 — **the unit tests are the contract.**

Split from #746, blocked by #755 (merged), sub-issue of epic
[#600](https://github.com/pyrycode/pyrycode/issues/600).
Spec: [`docs/specs/architecture/757-acp-outbound-request.md`](../../specs/architecture/757-acp-outbound-request.md).
Evergreen feature doc: [`features/acp-package.md`](../features/acp-package.md#outbound-request-primitive-transportcall-757).
Not security-sensitive — a transport mechanism (id correlation + a pending-call
registry) that makes no trust/dispatch/gate decision; the outbound call is
agent-initiated and the response comes from the same client the transport
already serves.

## Implementation

Purely additive to one existing package: **2 production files modified**
(`acp.go`, `jsonrpc.go`), 0 new files, **0 new exported types** (reuses the
existing `*Error`), **one new exported method** (`Call`). ~80 production LOC.
Blast radius nil — `Call` has zero call sites; the sole consumer
`cmd/pyry/acp.go` registers no handlers and never calls it.

- **`internal/acp/jsonrpc.go`** — two new **unexported** types:
  - `request` — the outbound agent→client JSON-RPC 2.0 frame
    (`{jsonrpc, id, method, params}`); `Params` is `omitempty` so a nil param
    is dropped from the wire. `ID` is a JSON number from the transport's own
    counter.
  - `callResult` — the value delivered to a blocked `Call`. Exactly one of
    `result json.RawMessage` / `err *Error` is meaningful per response.
- **`internal/acp/acp.go`** — three new `Transport` fields + `Call` + `reclaim`
  + `routeResponse`, and a one-line change to `handleLine`'s response-frame case
  (the #755 log-and-drop becomes `t.routeResponse(&msg)`).

### The pending-call registry — first cross-goroutine transport state

#755's transport was single-goroutine and lock-free by design (one read-loop
goroutine dispatching handlers serially inline; the handler map is
write-once-before-Serve). This ticket breaks that: the `pending` registry is
**written by the caller's goroutine** (in `Call`) and **read/deleted by the
read-loop goroutine** (in `routeResponse`). The synchronisation that makes that
safe is the real cost of this ticket, and is why AC-2 demands `-race`.

```go
nextID    atomic.Uint64              // Add(1) ⇒ 1,2,3,… never 0. Lock-free id gen.
pendingMu sync.Mutex                 // guards pending. Leaf lock.
pending   map[uint64]chan callResult // id ⇒ waiter's cap-1 channel
```

`nextID` is atomic (no lock for id generation); `pendingMu` guards `pending` at
all three access sites. **No lock nesting** — `pendingMu` and `writeMu` are
never held simultaneously (`Call` takes/releases `pendingMu`, then separately
takes `writeMu` via `writeMessage`; `routeResponse` takes only `pendingMu`).

### `Call` — the blocking outbound primitive (exported)

`Call(ctx, method string, params any) (json.RawMessage, error)`. Ordering is
load-bearing (documented at the call site):

1. **Marshal `params` first** — before touching shared state. A marshal failure
   returns immediately, so no id is burned into a dangling slot. `nil` params →
   the field is omitted from the wire.
2. `id := nextID.Add(1)`.
3. **Register the waiter before writing** — `ch := make(chan callResult, 1)`;
   under `pendingMu`, `pending[id] = ch`. Registering before the write closes
   the race where a fast response arrives before the waiter exists.
4. `writeMessage(request{...})` — reuses the `writeMu` seam **unchanged**. On
   write error: `reclaim(id)` + return the wrapped error.
5. `select { <-ctx.Done(): reclaim(id), return ctx.Err(); r := <-ch: return
   r.result / r.err }`.

`Call` MUST be issued from a goroutine other than the one running `Serve` —
inbound handlers dispatch inline on the read loop, so a `Call` that blocked that
loop would deadlock (only the read loop reads the response `Call` awaits). This
is documented in `Call`'s doc comment; the tests honour it; the handler
re-entrancy question (T8) is a deferred consumer concern.

### `routeResponse` — deliver a response to its waiter (unexported)

Runs on the read-loop goroutine; **must never block**:

1. Decode the id (`json.Unmarshal(msg.ID, &id)`). Non-numeric / out-of-range →
   unknown id → log Debug + drop.
2. Under `pendingMu`: lookup `ch`, and `delete` if present.
3. `!ok` → unknown or already-reclaimed id (the normal fate of a cancelled
   call's late response) → log Debug + drop. Debug, not Warn, to avoid log spam
   and match the #755 drop precedent.
4. Build `callResult`: an error frame decodes `rpcError` → `&Error{...}` (a
   malformed error object synthesises `&Error{CodeInternalError, "malformed
   error response"}` — deterministic, never blocks); a success frame sets
   `result = msg.Result` (may be JSON null).
5. `ch <- r` — the **cap-1 buffer guarantees this send returns immediately**,
   even if the waiter was already reclaimed.

## Patterns established

- **Cap-1 waiter channel keeps the read loop live.** Exactly one response exists
  per id, so a cap-1 buffer always has room and `routeResponse`'s send returns
  immediately — whether the waiter is still blocked, has been reclaimed
  (cancellation), or the id was unknown (which never reaches the send). This is
  the correctness core behind AC-3's "no goroutine or pending-slot leak": the
  read loop is never stalled by an absent or slow waiter.
- **Idempotent `reclaim` resolves every cancel-vs-deliver ordering.** Both the
  cancellation-`delete` and the delivery-`lookup+delete` run under `pendingMu`.
  Whichever wins: if the read loop delivers first, the caller's cancel-path
  `delete` is a no-op and the buffered value is GC'd unread (dropped); if the
  caller reclaims first, the read loop's lookup misses → unknown-id drop. No
  double-delivery, no leak, either order.
- **Register the waiter before the write.** Putting `pending[id] = ch` before
  `writeMessage` closes the fast-response race — a response can never arrive
  before its slot exists.
- **Marshal params before burning an id.** A marshal failure returns before any
  id or slot is allocated, so a caller bug never leaves a dangling registry
  entry.
- **A redundant leaf mutex becomes load-bearing exactly when its documented
  future arrives.** #755 installed `writeMu` as a redundant-but-named seam ("the
  seam #757's outbound-request writer shares"). This ticket makes it genuinely
  load-bearing (a `Call` and an inbound reply can now race on `w`) with **no
  change to the write path** — the field comment was updated from future-tense
  to present-tense, nothing else.
- **Reuse the existing `*Error` rather than add an exported type.** The mapped
  error response returns the same `*Error` handlers already return, holding the
  package's exported surface at #755's three types (the sizing lever survives).
- **`json.RawMessage` needs no defensive copy across goroutines.**
  `json.RawMessage.UnmarshalJSON` copies its input into a fresh backing array,
  so `msg.Result` is already independent of the reused `bufio.Scanner` buffer
  and is safe to hand to the caller goroutine — `-race` confirms.

## Lessons learned

- **The single-shot `run` harness cannot drive an outbound call.** #755's
  `run`/`runErr` harness feeds the whole input via `strings.NewReader`, runs
  `Serve` to EOF, then parses output — but an outbound `Call` needs a response
  written *after* its request is observed on the writer. The outbound tests add
  a **`liveTransport` harness**: `Serve` runs on its own goroutine over paired
  `io.Pipe`s; the test reads request frames off the writer to learn the
  generated id, then feeds a matching response on the reader. `Call` is issued
  from a spawned goroutine and its outcome collected over a channel, so
  `t.Fatalf` only ever runs on the test goroutine.
- **A bare `bytes.Buffer` diagnostics sink is a `-race` failure once `Serve`
  runs on its own goroutine.** `Serve` writes log records while the test reads
  them, so the sink must be synchronised. The harness wraps it in a
  mutex-guarded `syncBuffer` (the `bytes.Buffer`-under-`-race` gotcha recorded in
  `docs/lessons.md`).

## Out of scope (deferred)

- **Serve-exit does not drain pending waiters.** If `Serve` returns (EOF/error)
  while a `Call` is blocked and its `ctx` never fires, the call blocks until the
  ctx does. Consumers (T7/T8) always pass a session-lifetime context, so there
  is no observed need for the transport to fail-fast pending calls on `Serve`
  return. If a later ticket needs it, the read loop can range over `pending` and
  deliver a sentinel error on exit — additive, no wire change.
- **Handler re-entrancy (T8).** Whether an inbound handler may itself issue a
  blocking `Call` (it runs inline on the read loop, which would then be blocked
  on a response only that same loop can read → deadlock) is a **consumer-ticket**
  concern. This ticket documents the "call from a different goroutine"
  constraint in `Call`'s doc comment and its tests honour it; it does not
  enforce it.
- **Id wraparound.** `uint64` from `nextID` will not wrap in any realistic
  session; no reuse guard is warranted (evidence-based — no observed failure).
