# #1505 — Bound control-class push-queue growth with a retained-bytes ceiling

**Spec:** `docs/specs/architecture/1505-push-queue-byte-ceiling.md`
**Size:** S · `security-sensitive`
**Files:** `internal/relay/v2session_modal.go`, `internal/relay/v2session.go`, `internal/relay/v2session_test.go`, `internal/relay/v2session_debugbundle_test.go`, `docs/protocol-mobile.md`

## What shipped

`pushQueue.enqueue`'s soft-overflow branch — the one that admits a control-class envelope past `pushQueueCap` (256) — previously had no ceiling at all. Two production paths could grow it unboundedly: the #874 transport-down hold parking `drainOnce` while the #632 interactive emitter keeps pushing never-droppable `tool_result`/`tool_use`/`turn_state`/`turn_end` during a multi-minute relay outage mid-turn, and a single oversized `request_debug_bundle` archive (`debugbundle.Assemble` caps nothing). Both previously grew until the 15-minute idle sweep finally freed the queue.

`pushQueue` now tracks retained payload bytes (`bytes int`, `Σ len(item.env.Payload)`) and latches a one-way `overflowed bool` when an envelope would push that sum past `pushQueueByteCeiling` (32 MiB). The ceiling check lives in exactly one place — the soft-overflow branch — because the other two drop-policy branches structurally cap `len(items) <= pushQueueCap`, whose maximum retained bytes (`256 × 65519 B ≈ 16 MiB`) can never reach a ceiling set at ~2× that. The latch signals the Run goroutine via a new `pushOverflow chan string` (mirrors `modalTimeout`'s shape exactly), which tears the session down via `handlePushOverflow` at a new close code, `StatusQueueOverflow` (4413), with a **nil** frame — nothing is sealed onto a transport that may be exactly what's down, avoiding the #912 nonce-gap hazard. The producer-facing `Push` contract is unchanged: it still returns `nil` promptly on a ceiling trip, and a subsequent push to the torn-down conn gets the pre-existing `ErrConnNotFound`.

Full design rationale, the off-Run→Run signal shape, the deliberate no-recheck-before-teardown decision, and the bundle-path outcome all live in the architecture spec and are mirrored into [`features/v2-session-manager.md` § Push-queue byte ceiling](../features/v2-session-manager.md#push-queue-byte-ceiling-1505--pushqueuebytes--pushqueuebyteceiling--handlepushoverflow) — that section is the durable reference; this file covers only what's specific to how the ticket landed.

## Patterns established

- **Off-Run→Run signal for a condition detected inside a leaf-locked hold: mirror the existing `chan string` idiom (`modalTimeout`), don't invent a new one.** `pushOverflow` is byte-for-byte the same shape — same buffer size (`wakeBufferSize`), same non-blocking send discipline for `Push` (which, unlike `armIdleTimer`'s timer callback, runs on the *producer's* goroutine and must never block) — and a plain new arm in `Run`'s select. When a future ticket needs another off-Run condition to trigger a Run-owned action, this is the template to copy, not `armIdleTimer`'s blocking-send shape (that one is fine specifically because it runs on a throwaway `time.AfterFunc` goroutine, not a producer's).
- **Level-triggered signal, edge-triggered log.** A latch that's never cleared re-drives its own signal on every subsequent producer call (so a dropped send from a full buffer self-heals), while the accompanying `Warn` fires only on the level's rising edge (`justTripped := overflowed && !before`, captured under the same lock as the level read) so an operator sees exactly one line per session regardless of how many pushes follow. Worth reusing anywhere a latch condition needs both "don't lose the signal" and "don't spam the log."
- **A close-teardown path that may fire while the transport is down should seal nothing.** `closeWith(ctx, s, StatusQueueOverflow, nil)` — nil frame — is deliberate, not an oversight: sealing an error envelope here would burn a Noise send-nonce for a frame that can't arrive on a down transport, gapping the phone's recv nonce (the #912 failure class, where a transport outage got mislabelled as a crypto failure). The idle sweep (#774) already set this precedent; this ticket is the second data point that any teardown reachable during a down-transport window should default to `nil`.

## Lessons learned

- **A doc comment that names "what bounds this" is a maintenance liability if the cited mechanism doesn't actually bound the axis in question — write the derivation, not just the citation.** The original soft-overflow comment named #911's in-flight gate as what keeps the branch bounded; #911 only bounds the *retry* axis for debug bundles and says nothing about a single large bundle or the #874 transport-down path. The fix here wasn't just adding a ceiling — it was rewriting the comment to state the actual reachability paths and, for the new constant, writing the numeric derivation (why 32 MiB, not just "a big number") directly in the doc comment so a future reader doesn't have to reconstruct it from a spec that may no longer be handy.
- **When a constant's safety property depends on a relationship to another constant (`pushQueueByteCeiling` ~2× `pushQueueCap × maxEnvelopePayload`), say so in the doc comment on both sides.** The derivation is what makes "the ceiling can never trip below the nominal count cap" a structural guarantee that survives an independent future bump to either constant, rather than an invariant that silently breaks the first time someone changes `pushQueueCap` without re-deriving the ceiling. Test coverage (`TestPushQueue_Enqueue_ByteCeilingBoundary`) pins the boundary value but can't pin *why* 32 MiB was chosen — that has to live in prose.
