# Ticket #1402 — Map the three background-task events in `acpbridge.MapUpdate`

Wires the three `MapUpdate` arms #1401 left declared but unreferenced —
`BackgroundTaskStarted`, `BackgroundTaskUpdated`, `BackgroundTaskRoster` — so a
desktop ACP client can finally see claude's background-task lifecycle and
separate a turn that ended with work still running from a genuine finish
(#1240's symptom). PR [#1407](https://github.com/pyrycode/pyrycode/pull/1407),
code review PASS (1 SHOULD FIX, 2 NITs, below the 3-finding merge threshold).
Does **not** make the events arrive: `turnbridge.mapEvent` has no
background-task arm on the ACP lane yet, so no producer emits them until #1400.

## Implementation

- Three new `case` arms in `internal/acpbridge/outbound.go`'s `MapUpdate`
  switch, placed after `ToolUpdate` and before `TurnEnd`. Every arm is a flat
  field copy; every claude-derived string crosses **verbatim** (the producer,
  `streamsup`, already bounds each one at construction — `maxTaskFieldID`,
  `maxTaskDescription`, `maxTaskPatch`, `maxTaskRosterDescription`,
  `maxTaskRosterEntries`). `msgID` is `""` on all three (none of the neutral
  events carries a `MessageID`), and no session/conversation identifier is
  added — on ACP that's `sessionUpdateParams.SessionID`, the consumer's field.
- New helper `mapBackgroundTasks(tasks []turnevent.BackgroundTask)
  []BackgroundTask`, mirroring `mapLocations`: `nil` in, `nil` out. Returning
  `nil` for an empty roster is a **contract**, not convenience —
  `BackgroundTaskRoster.MarshalJSON` (#1401) owns the nil → `[]`
  normalisation, and a `[]BackgroundTask{}` built in the arm would be
  byte-indistinguishable from the correct mapper on the wire.
- Six comment sites corrected to state the post-arm counts (`turnevent.Event`
  is a sealed 14-variant sum — `event.go`'s own doc comment enumerates only
  13, omitting `PermissionRequest`, whose marker sits in `permission.go`):
  `MapUpdate`'s doc, the `default:` arm, the extension-discriminant `const`
  block's closing sentence, and two sites in `cmd/pyry/acp_turn_stream.go`
  (`Handle`'s doc + the `!ok` branch, now documented as a **live** drop path —
  `ApiRetry`/`Compacting` reach it on every API retry and every compaction).
  `outbound_test.go`'s `TestBackgroundTaskPayloadWireShape` doc corrected too.
  No behaviour change at any of the six.
- Test rows: three new `TestMapUpdate` cases (AC 1's field-carriage proof, all
  fixture values distinct/non-zero), four new `TestMapUpdate_WireShape` rows
  (three variants + an empty-roster byte golden), and a new
  `TestMapUpdate_EmptyRosterForwardsNilTasks` — the value-rung assertion the
  byte golden structurally cannot make, since `MarshalJSON`'s normalisation
  sits downstream of both a correct and an incorrect mapper.
- ADR 027 divergence 7's gating decision (AC 4) landed with the architect spec
  commit (`6b5f030`), ahead of this note: **emit unconditionally, no gate in
  `acpbridge`** — there's nothing to gate on (ACP ignores `clientCapabilities`
  by design), the package is contractually stateless, and no host has been
  observed rejecting an extension discriminant. Documented in
  [decisions/027-acp-mapping.md § divergence 7](../decisions/027-acp-mapping.md).

## Patterns established

- **Count a sealed sum by its markers, not by the interface's doc comment.**
  `grep 'isTurnEvent()'` package-wide is the check for `turnevent.Event`'s
  true member count; the type's own doc comment enumeration had drifted stale
  (missing `PermissionRequest`) and both of the ticket body's "corrected"
  counts inherited that drift, landing one low. Verified independently by
  code review via the same grep.
- **A `MarshalJSON` normaliser makes one property byte-unreachable, and that
  property needs its own value-level assertion.** When a wire-level
  normalisation (nil → `[]`) is owned by a type's `MarshalJSON`, an upstream
  mapper that pre-allocates the "correct-looking" empty value is
  byte-identical to the correct one and passes every golden. Pair the byte
  golden with a value-level test that reads the mapper's actual return before
  marshalling; code review mutation-tested this via `go test -overlay` and
  confirmed the value-rung test is the sole detector for that specific
  mutant.

## Lessons learned

From the PR body's own "Lessons learned" section (developer, verbatim):

> **Count a sealed sum by its markers, not by the interface's doc comment.**
> `turnevent.Event`'s own doc at `event.go:23-33` enumerates 13 variants, but
> `PermissionRequest`'s marker sits in the sibling `permission.go:75` — 14 in
> total. Both counts the ticket body supplied as corrections were one low as
> a result. `grep 'isTurnEvent()'` across the package is the check; the doc
> comment is not a source. (`event.go:33`'s enumeration is still stale —
> worth a follow-up against `internal/turnevent`.)
>
> **A `MarshalJSON` normaliser makes one property byte-unreachable.** With
> `BackgroundTaskRoster.MarshalJSON` folding nil → `[]`, an arm that
> pre-allocates `[]BackgroundTask{}` is byte-identical to the correct one and
> passes every wire-shape golden. The empty-roster case therefore needs two
> assertions with different subjects: bytes (`"tasks":[]` through the
> mapper's return path) and value (`Tasks` is nil).
> `TestMapUpdate_EmptyRosterForwardsNilTasks` carries an explicit warning not
> to "fix" it by writing `[]BackgroundTask{}` into a `wantUpdate` literal —
> `reflect.DeepEqual` distinguishes the two, so co-corrupting row and arm
> goes green with the property gone.
>
> **Codegraph's `callers` missed a live call site.** `codegraph_callers
> MapUpdate` returned only the two test functions, omitting
> `acpTurnStream.Handle` in `cmd/pyry`; grep found all three. Worth a second
> check before trusting an empty/short caller list as a blast-radius bound.

Code review's own verification, worth keeping alongside the above:

- Independently re-derived every count in every new comment (grepped
  `isTurnEvent()` markers package-wide: 13 in `event.go` + `PermissionRequest`
  in `permission.go` = 14) and confirmed all correct, including the two the
  ticket body got one low.
- Mutation-tested the empty-roster property with five mutants via
  `go test -overlay` (no worktree writes). The one that matters: a
  `mapBackgroundTasks` mutant returning `[]BackgroundTask{}` for an empty
  input left the byte golden **green** and was caught **only** by
  `TestMapUpdate_EmptyRosterForwardsNilTasks` — empirical confirmation that
  the two-rung test design is not redundant.
- One SHOULD FIX, not blocking: a new block comment in `outbound_test.go`
  claimed fixture values don't repeat "across rows or **across the other
  tests in this file**" — they do repeat between `TestMapUpdate` and
  `TestMapUpdate_WireShape` (deliberately; both drive the same subject). The
  property that actually held — no repeat against `TestBackgroundTaskPayloadWireShape`'s
  values — was correct; only the stated scope of the claim was too broad. Not
  fixed in this PR (below merge threshold); worth a one-word narrowing
  whenever `outbound_test.go` is next touched.
