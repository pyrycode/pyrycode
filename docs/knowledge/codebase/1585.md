# Ticket #1585 — Report a named session's persisted settings, not only the bootstrap's

`internal/sessions.Pool` was asymmetric: `UpdateSettings(id, …)` could change any session's
model/effort/YOLO by id, but the only read path, `DefaultSettings()`, exposed the bootstrap's
settings alone — `Session.settings` is unexported, `Lookup(id)` hands back no accessor for it,
and `SessionInfo` (from `List()`) doesn't carry it either. This adds the missing read half:
`Pool.SettingsFor(id SessionID) (SessionSettings, error)`. Split from #1577; wires no consumer.

## Implementation

- `internal/sessions/pool.go`: one new exported method, placed immediately after
  `DefaultSettings`. Body is four lines — `p.mu.RLock()` + `defer RUnlock()`, a
  `p.sessions[id]` lookup, `ErrSessionNotFound` on a miss, `(sess.settings, nil)` on a hit.
  Pure insertion: `DefaultSettings`, both its non-test callers (`cmd/pyry`'s
  `snapshotSettings` closure, `Pool.mintSettings`), and every existing settings test file are
  byte-identical after this ticket (verified structurally — `git diff main..HEAD` removes zero
  lines across the branch).
- The empty id is **not** special-cased to the bootstrap. It falls out of the absence of a
  branch (a plain `p.sessions[""]` miss), the same way `UpdateSettings` gets it — not `Lookup`'s
  `""` → bootstrap convention. Read and write now agree on what `""` means.
- No delegation in either direction between `SettingsFor` and `DefaultSettings`: two exported
  methods each taking `p.mu.RLock()` in one call chain self-deadlocks once a writer queues
  between the acquisitions (`RWMutex` isn't reentrant). `SettingsFor(p.BootstrapID())` is also
  not a substitute for `DefaultSettings()` — it's two acquisitions with a `RotateID` window
  between them, so it can read a session that stopped being the bootstrap in the interval.
  `DefaultSettings` resolves `p.bootstrap` and reads `settings` atomically under one acquisition
  and stays the only atomic way to ask for the bootstrap's settings.
- Error returned bare (`ErrSessionNotFound`, unwrapped) — not `fmt.Errorf("...%q...", id, ...)`
  — so a hostile or malformed id is never reflected into a log line or wire frame a future
  consumer builds from the error. Deliberate divergence from `ambiguousError`, which does echo
  ids, but only ones already resident in the pool.
- No `ValidID` gate: unlike `writeMCPSettings` (#1518), the id here names no file and never
  leaves the map lookup, so a malformed id is already a correct miss.

See `docs/specs/architecture/1585-per-session-settings-read.md` for the full design rationale,
including the architect's self-review security pass (PASS, 9/9 categories; the one live finding
— a read-modify-write hazard on `YOLO` for a future consumer — is mitigated via docstring, not
code, since no such consumer exists yet).

## Patterns established

- **Two exported same-lock accessors on `Pool` must stay independent, never delegate.** This is
  now the second time the "`...Locked` helper if truly shared, never call-one-exported-method-
  from-another" rule shows up in this file (`mintSettings`'s docstring records the same hazard
  for `DefaultSettings`). `SettingsFor` reaffirms it rather than reconciling the two into a
  shared exported entry point — the near-duplication is intentional and was explicitly called
  out to reviewers as not-a-simplification-target.
- **Id-keyed reads that only touch a map need no `ValidID` gate**, even on a security-sensitive
  ticket — contrast `writeMCPSettings`, which needs one because its id *becomes a path*. The
  distinguishing question for a new id-keyed accessor: does the id leave the map lookup?
- **Bare sentinel errors over ids already known to be resident vs. ids from an untrusted
  caller.** `ambiguousError` may echo an id because the pool already knows it exists;
  `SettingsFor` must not, because its id is exactly the thing being validated by the lookup.

## Lessons learned

(from the PR body's own "Lessons learned" section)

- The AC-4 deadlock test row (concurrent `SettingsFor` vs. concurrent `UpdateSettings` under
  `-race`) is invisible to every value assertion — a re-entrant-`RLock` mutant only shows up as
  a test timeout. Verifying it as RED needs an explicit `-timeout` on the mutant run; the
  default 10-minute Go test timeout would otherwise read as a hang rather than a proven result.
- `-overlay` mutants for a "reads the wrong thing" defect want two shapes, not one. A broad
  mutant (swap every `p.sessions[id]` read for `p.sessions[p.bootstrap]`) reddens five rows at
  once and proves nothing about which row is load-bearing. A narrow mutant that keeps
  not-found semantics intact and only misroutes a *known non-bootstrap* id isolates the
  ticket's central test (`PerSessionNotBootstrap`) as its sole RED — confirmed in code review
  by re-running both mutant shapes independently.
