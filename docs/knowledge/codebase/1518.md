# Ticket #1518 — write the per-session `--settings` file under the daemon data dir

`writeMCPSettings` (#943) wrote the per-session `--settings <path>` file into `os.TempDir()`, while its own doc comment said the file "must outlive every respawn" — a daemon running for days has that file age-reaped by an OS temp-dir cleaner out from under a live session, and the next backoff restart or idle-evict reactivation re-execs `spawnBase` pointing `--settings` at a missing path (the #943 MCP-enablement modal wedge returns, or the child fails to boot into permanent respawn backoff). This ticket relocates the file to the daemon's own data directory and closes the orphan-on-error gap that relocation makes permanent instead of reaped.

## Implementation

- `writeMCPSettings` (`internal/sessions/settings.go`) signature changed to `func writeMCPSettings(registryPath string, id SessionID) (string, error)`. Two branches, selected by `registryPath`:
  - `registryPath == ""` (persistence disabled, `Pool.dataDir()` reports `""`) — unchanged `os.TempDir()` behaviour, random `pyry-session-settings-*.json` name, `0600`. The branch the 17 `internal/sessions` test files with no `RegistryPath` still take.
  - `registryPath != ""` — target is `<abs(dir(registryPath))>/session-settings/<id>.json`, mirroring the `archived-sessions/` precedent (`disposeJSONLLocked`). `session-settings/` is created on demand at `0700` (`os.MkdirAll`) — needed at cold start because the data dir is otherwise created only by `saveRegistryLocked`, which hasn't necessarily run yet when `Pool.New` writes the bootstrap file.
- The write is atomic on both branches: `os.CreateTemp` in the target dir (pattern `.settings-*.json.tmp` on the data-dir branch, so a SIGKILL-orphaned scratch file is never mistaken for a real settings file and a `*.json` glob counts sessions exactly) → encode → `Sync` → `Close` → `Rename` into the final name, `defer os.Remove(tmp)` as a no-op once renamed. Same recipe as `saveRegistryLocked`. Two reasons this matters that didn't exist under `os.CreateTemp`'s random names: deterministic naming means two same-id `materialise` callers can now write the same path concurrently (rename hands a live child either the complete old or complete new file, never a truncated one), and `os.Rename` replaces a symlink at the destination instead of writing through it.
- `id` is gated on `ValidID` on the data-dir branch only (not the persistence-disabled branch, which tests feed hand-made ids). `pickBootstrap` decodes a warm-start id straight out of the registry file with no shape check anywhere upstream; after this change that string names a file, so an unvalidated `"../x"` would place the write outside the data dir. A malformed id is now a hard error, matching `loadRegistry`'s existing "malformed file is a hard error" posture.
- Naming the file `<id>.json` rather than a random suffix is what makes AC #4 (on-disk count bounded by session count, not restart count) hold **by construction** — a warm-start restart against the same registry overwrites its own bootstrap file instead of accumulating a new one, with no sweeper. A startup sweep for files orphaned by a previous SIGKILLed process stays explicitly out of scope.
- Both write sites (`Pool.New` bootstrap at `pool.go`, `buildSession` minted) now guard with a `defer`-and-success-flag: `built := false; defer func() { if !built { _ = os.Remove(settingsPath) } }()`, `built = true` set immediately before the successful return. This covers every error return between the write and success — `Pool.New`'s `newRunner` failure (named in the filing) *and* its `saveLocked` failure (found during spec review, not named in the filing); `buildSession`'s `newRunner` failure. The defer shape means a future error return added to either function is covered without anyone having to remember to add a removal — this ticket exists because that reminder was missed twice at the original #943 call sites.
- `CreateIn`'s `saveLocked`-failure rollback (discards a freshly built, freshly `NewID`-minted session) also now removes `sess.settingsPath` — beyond the filed AC #5 but the same argument: the id is never reused, so in the data dir that orphan is otherwise permanent and unbounded across retries.
- `materialise`'s discard branches (same-id race loser, `saveLocked` rollback, `ErrPoolNotRunning` rollback) **deliberately do not** remove the file — see Lessons learned below.
- `Pool.Remove`'s and `Pool.Run`'s teardown comments ("a leaked tempfile in os.TempDir is harmless") are rewritten: in the data dir a leaked file is permanent, and these removals are what keeps AC #4's bound honest rather than an incidental cleanup.

## Patterns established

- **Deterministic, id-derived filenames replace a sweeper.** Where a random per-process name would need a periodic reconciliation pass to bound growth, naming the file after the entity it belongs to (session id) makes "at most one file per live entity" a structural property of every write, not an invariant a background job has to maintain. Same shape as `archived-sessions/<uuid>.jsonl`.
- **Relocating state out of a reaped directory turns an accidental GC into a real leak — ship the leak's fix in the same change.** The OS temp reaper was quietly bounding orphan growth for #943; moving the file to a non-reaped directory without also closing every error-path orphan would have knowingly shipped an unbounded leak. AC #4 (bounded growth) and AC #5 (error-path cleanup) shipped together as one ticket rather than sequenced, because splitting them would have had a real gap between "state relocated" and "leak closed."

## Lessons learned

- **Deterministic names turn two call sites' error-path cleanup from independent decisions into one that must be evaluated per site, including the sites that must refuse it.** `materialise`'s same-id race loser now builds a settings file at the *same path* the eventual winner's live `spawnBase` references (both derive `<id>.json` from the same id). Symmetrizing `CreateIn`'s new cleanup onto `materialise`'s discard branches — the natural-looking move — would delete a live session's settings file out from under it and reopen the #943 modal wedge. The asymmetry is intentional and is called out with an inline comment at the race-loser branch precisely so it doesn't read as an oversight to the next person who diffs the two functions side by side.
- **A fix that closes one gap can surface a second, identically-shaped one nearby that the filing didn't name.** The ticket named `buildSession`'s `newRunner` failure as needing cleanup; `Pool.New` turned out to have *two* error returns after its write (`newRunner` and `saveLocked`), and `CreateIn` had a third orphan site one level up the call stack. Sweeping the full function for every `return ..., err` between a write and its success — not just the error path the filing pointed at — is what caught the other two before they became a second version of this same ticket.
