# Ticket #1139 — Stream e2e: permission round-trip proves the fail-closed gate

Live, end-to-end proof of the stream-json permission mechanism under
`interactive_runner:"stream-json"` — the final leg of the streamrunner permission
work. Every piece (`permbridge` #1103, `mcp.approve` #1104, `streamApprovalBridge`
#1080, `modalbridge` #716, the stream keystroker guard #1131) was already built and
unit-tested; this is the first time they run **together, live**, against a spawned
fakeclaude, across three cases: allow, deny, and — the load-bearing one — timeout
denies (fail-closed).

## Implementation

- `internal/e2e/relay_v2_stream_modal_test.go` (new, `//go:build e2e`) —
  `TestRelayV2_StreamModalPermissionRoundTrip`, table-driven over `{allow, deny,
  timeout}`. Per case: pair `--allow-remote-permissions` → `seedBoundConversation` →
  `StartStreamInteractiveWithRelay` with the approve rider envs → write the daemon's
  real control socket path into a file the fake reads lazily → `send_message` → await
  ack → await `modal_shown` (asserts `Class=="permission"`, the fixed 4 option IDs,
  non-empty `ModalID`, `ConversationID==knownConvID`) → answer with `modal_answer`
  (or send nothing, the timeout case) → drain until both an `assistant_delta`
  carrying the verdict needle **and** a corroborating `modal_dismissed{Outcome,
  Source}` land, while asserting the case's `forbidNeedles` never appear.
- `internal/e2e/internal/fakeclaude/main.go` — new approve rider
  (`PYRY_FAKE_CLAUDE_STREAM_APPROVE` + `PYRY_FAKE_CLAUDE_APPROVE_SOCKET_FILE`,
  default-off, mutually exclusive with the interrupt rider). `runStreamJSONApprove`
  originates one `control.Approve` call per user turn (blocking until the daemon
  answers) and reflects the verdict into a distinct needle
  (`approve-allow`/`approve-deny`/`approve-error`) via `writeVerdictResponse`.
  `runStreamJSON`'s signature is untouched — the send/interrupt/queue-drain siblings
  stay byte-identical. Full detail:
  [features/fakeclaude-binary.md § Approve rider](../features/fakeclaude-binary.md#approve-rider-pyry_fake_claude_stream_approve-1139).
- `internal/e2e/internal/fakeclaude/approve_test.go` (new, untagged unit test) —
  `writeVerdictResponse` verified through the **real** `streamsup.Parser`
  (`parseEmitted`, different fabric); a needle-distinctness guard asserts the three
  verdict needles are pairwise non-substring-confusable (the property the e2e's
  `strings.Contains` discrimination depends on).
- `cmd/pyry/main.go` — new `approvalTimeout()` env seam:
  `PYRY_APPROVAL_TIMEOUT` (`time.ParseDuration`), falling back to the existing
  `mcpApprovalTimeout` (2 min) when unset/unparseable. The one call site
  (`ctrl.SetApprovalRegistry(approvals, mcpApprovalTimeout)`) swaps to
  `approvalTimeout()`; `permbridge`'s deny-on-deadline logic is untouched — only the
  timer's duration is tunable, and production behaviour is byte-identical with the
  env absent. `cmd/pyry/approval_timeout_test.go` covers empty/invalid/short/generous.
  Full detail: [features/control-plane.md § Wiring](../features/control-plane.md).

## The one architectural fact that shaped the design

`internal/streamsup.buildArgs` does not inject `--permission-prompt-tool` /
`--mcp-config` — that pair is wired only by `cmd/pyry/agent_run.go`'s `pyry agent-run`
batch verb (#1106). So under `interactive_runner:"stream-json"`, real claude
currently would not spawn `pyry mcp-approve` at all. Fakeclaude therefore can't
originate an approval "the way real claude would" — instead it calls the exact same
client `pyry mcp-approve` calls, `control.Approve(ctx, socket, ApprovePayload{…})`,
directly. This drives the identical daemon-side surface named as production-under-
test and sidesteps the wiring gap without papering over it. See *Open production
follow-up* below.

## Fail-closed proof (the load-bearing case)

The timeout case sets `PYRY_APPROVAL_TIMEOUT=2s` on the daemon while the fake blocks
on `control.Approve` with a fixed 30s ctx (`approveDialTimeout`) — a 15× margin. So
the deny the fake receives is the **daemon's own** `permbridge.time.AfterFunc` timer
firing, not a fake self-timeout that would mask it. Three distinct needles make the
proof airtight:

| Case | fake receives | needle | corroborating `modal_dismissed` |
|---|---|---|---|
| allow | daemon verdict `allow` | `approve-allow` | `Outcome=allow_once, Source=remote` |
| deny | daemon verdict `deny` | `approve-deny` | `Outcome=reject_once, Source=remote` |
| timeout | daemon verdict `deny` (permbridge timer) | `approve-deny` | `Outcome=denied_timeout, Source=timeout` |

`approve-error` (a client-side `control.Approve` failure) must never appear in a
green run — the test forbids it explicitly in every case, so a fail-open regression,
a hang, or a masked client error all go red loudly rather than false-passing.

## Patterns established

- **Originate via the same client the production consumer uses, when the production
  wiring that would drive the fake naturally isn't there yet.** Rather than building
  a parallel or partial mock of the missing `--permission-prompt-tool` spawn path,
  the fake calls `control.Approve` directly — the identical call
  `pyry mcp-approve` makes — so the e2e proves the real daemon surface without
  depending on unrelated, still-open wiring.
- **Socket-in-a-file for a post-spawn-only value.** When a rider needs a value only
  known after the daemon spawns (a random per-run socket path), carry a *file path*
  in the env (known pre-spawn) and have the test write the real value into that file
  after startup; the fake reads it lazily at first use. Same idiom as the existing
  `PYRY_FAKE_CLAUDE_*_TRIGGER` files, extended from presence-signal to value-carrier.
- **Distinct fail-closed-vs-error needles, not just allow-vs-deny.** A binary
  allow/deny needle pair can't distinguish "the daemon denied" from "the client gave
  up and defaulted to deny" — and the second can mask a real production bug (e.g. an
  inverted timeout margin). Tagging the client-side failure with its own needle and
  asserting it never appears makes that class of false-pass structurally impossible.
- **Timer-duration-only env seam.** `approvalTimeout()` overrides *only* the
  `time.Duration` argument to an otherwise-untouched call
  (`SetApprovalRegistry`) — the deny-on-deadline logic itself is not touched, so a
  test can compress a real production timer to seconds without constructing a
  parallel/fake timer path.

## Lessons learned

- Confirmed from the PR body and code review: nothing broke or surprised during
  implementation — the design's `## Security review` (architect self-review, PASS)
  and the code-review PASS both landed clean on the first pass. The one NIT (below)
  was flagged as an explicit out-of-scope production gap, not a fix-here finding.

## Open production follow-ups (not fixed here)

- **Interactive stream runner doesn't wire `--permission-prompt-tool`/`--mcp-config`.**
  Named above — under `interactive_runner:"stream-json"`, real claude currently
  cannot route tool uses through the daemon approval registry at all. This e2e
  proves the daemon-side surface is correct and ready; wiring the interactive stream
  runner to spawn with the permission-prompt-tool + mcp-config pair is a separate,
  not-yet-filed production ticket.
- **`cmd/pyry/mcp_approve.go`'s client read-deadline margin doesn't track the env
  override** (code review NIT, `mcp_approve.go:82`): `pyry mcp-approve`'s ctx
  deadline is still `mcpApprovalTimeout + mcpApproveClientMargin`, not
  `approvalTimeout() + mcpApproveClientMargin`. A `PYRY_APPROVAL_TIMEOUT` set
  *longer* than ~2m30s would make the batch `agent-run` approval client give up
  before the daemon's window elapses — fail-closed (denies earlier), and inert until
  the above wiring gap is closed (nothing calls this path under the interactive
  runner yet). Fold into the same follow-up ticket.
