# Ticket #822 — `delete_conversation` v2 wire message

Adds the missing hard-delete verb both paired clients need (mobile stubbed the
Delete action locally, desktop is building its Channel Info **Delete** button
against it): a protocol type pair, a two-field payload family, and a daemon
handler wired at both relay dispatch sites. **Permanent** delete — the
reversible path is archive/unarchive (#880/#881, a distinct verb operating on
a durable soft-state flag). This verb clones `rename_conversation`'s (#820)
shape and reuses the existing terminal removal primitive
(`conversations.Registry.Delete`, previously only called by `Sweep`), so no
new registry field or schema change was needed.

## Implementation

Five production files, ~365 total LOC, none of them new packages:

- `internal/protocol/codes.go` — `TypeDeleteConversation = "delete_conversation"`
  (phone → binary request) and `TypeConversationDeleted = "conversation_deleted"`
  (binary → phone reply), in the Conversations cluster after
  `TypeRenameConversation`.
- `internal/protocol/conversations_write.go` —
  `DeleteConversationPayload{ConversationID string}` (one required field, no
  pointers, mirrors `RenameConversationPayload`/`PromoteConversationPayload`)
  and `ConversationDeletedPayload{ID string}` (the ack; deliberately **not**
  a `ConversationUpdatedPayload` reuse — the record no longer exists
  post-delete, so there's no row to project `name`/`cwd`/`last_used_at` from).
- `internal/protocol/envelope.go` — both constants added to `v1TypeSet`. It's
  a `dispatch.Route` request/reply verb like `create_conversation`/
  `rename_conversation`, not a v2-control frame intercepted before
  `dispatch.Route` — the ticket title's "v2 wire message" names the encrypted
  v2 *transport*, not the v1/v2 *type partition*.
- `internal/protocol/compat_test.go` — both types added to all three
  enumerations (`TestIsV1Compatible`, `TestV1TypeSet_CoversAllExportedTypeConstants`,
  `TestTypeConstants_V1V2Partition`); hardcoded v1-type count bumped 17 → 19.
- `internal/relay/handlers/delete_conversation.go` (new, ~105 LOC) —
  `DeleteConversation(reg ConversationDeleter, registryPath string, logger *slog.Logger) dispatch.Handler`.
  Flow: decode → `reg.Delete(id)` (exact-match registry-key removal; a miss
  is `conversation.not_found` with no state change — idempotent-on-miss, AC
  #4) → eager best-effort `reg.Save` (durability best-effort, mirrors
  create/rename) → `c.Reply(conversation_deleted, {id})`.
- `cmd/pyry/relay.go` — two lines mirroring create/rename, reusing
  `resolveConversationsRegistryPath(instanceName)` and `convReg`: the v1
  `d.Register` block and the v2 `Handlers` map.

`ConversationDeleter` is the consumer-declared minimal interface (`Delete` +
`Save`) `*conversations.Registry` satisfies structurally, same pattern as
`ConversationRenamer` (#820) / `ConversationCreator` (#666) — see
[features/relay-package.md](../features/relay-package.md).

`list_conversations` reads the live registry, so a hard-deleted row
disappears from its results for free (AC #3) — no consumer-side change, no
new read verb.

### Security-sensitive divergence from the rename template

This ticket carries `security-sensitive`. The one deliberate divergence from
`rename_conversation`'s malformed-branch logging: **the malformed branch logs
`conn_id` only** — never the decode `err` and never `conversation_id`. Go's
`json.Unmarshal` errors (`*json.SyntaxError`) can embed offending input bytes,
and a decode failure leaves the struct at most partially populated, so
`p.ConversationID` may hold raw attacker bytes on that path. Copy-pasting
rename's `"err", err` log call here would leak payload bytes into the daemon
log, violating AC #5. The not_found and success branches still log
`conversation_id` as a structured slog field (by then it's a proven-real
registry key, or never reached the wire) — same posture as rename/create.

Both reject branches (`protocol.malformed`, `conversation.not_found`) reply
with a fixed static string; no attacker-controlled bytes (the supplied id, a
decode-error fragment) ever reach the wire.

## Testing

- `internal/relay/handlers/delete_conversation_test.go` — clones
  `rename_conversation_test.go`'s harness (`dispatch.NewTestConn`,
  `conversations.Load`+`reg.Create` seed on a `t.TempDir()` path, `recv`
  helper). Covers: success + `in_reply_to` correlation + registry row gone +
  fresh `conversations.Load` of the same path confirms persisted removal (AC
  #1 restart-survival); `list_conversations` omits the deleted id (AC #3);
  not-found (registry byte-unchanged, no id echo); idempotent-on-miss
  (delete a seeded id, re-send same id, second reply is
  `conversation.not_found`); malformed payload (`protocol.malformed`, static
  message, and — via a slog test handler — the malformed log record carries
  no `err`/`conversation_id` field).
- `internal/protocol/conversations_write_test.go` —
  `TestDeleteConversationPayload_RoundTrip` / `TestConversationDeletedPayload_RoundTrip`
  against new `testdata/delete_conversation.json` / `conversation_deleted.json`.

`go test -race ./...`, `go vet ./...` pass; `go build ./cmd/pyry` clean.

## Lessons learned

- **A security-sensitive verb cloned from a non-security sibling must audit
  the sibling's *daemon-side log calls*, not just its wire strings.**
  `rename_conversation`'s malformed branch logs `"err", err` and
  `conversation_id` — both leak attacker payload bytes on a decode failure
  (Go json decode errors can embed offending input; a failed decode leaves
  the struct partially populated). Auditing only the wire-facing error
  message (which was already static in the template) would have missed
  this — the leak is in the *log line*, not the reply. Guarded here by a
  JSON-slog capture test asserting the malformed record carries no
  `err`/`conversation_id` key, which would fail on a naive copy-paste of the
  template's log call.

## Out of scope

- **Live fan-out to other connected clients.** Like the other write verbs,
  this replies only to the requester; other clients pick up the removal on
  their next `list_conversations`. A live broadcast is a separate concern for
  a future ticket.
- **Reconciling hard-delete with auto-archive `Sweep`.** `Sweep` already
  calls `Registry.Delete` for idle-timeout auto-archival; this ticket adds a
  second, unrelated caller (a phone-initiated explicit delete). The two
  call sites share the primitive but not a code path — no interaction to
  reconcile.
