# Ticket #1487 — Conversations bound to minted sessions survive a daemon restart

A conversation bound to a per-conversation-minted session was permanently dead after a daemon restart: `Pool.New` materialises only the bootstrap from `sessions.json`, so `sessionRouter.resolve` got `ErrSessionNotFound` for the dropped id and `send_message` rejected with a retryable `server.binary_offline` before any enqueue. This closes the deferral named by spec #833 and scoped out of #685/#696 (see [conversation-session-binding.md § Restart scope](../features/conversation-session-binding.md#edge-cases--limitations)).

## Implementation

- **`internal/sessions/get_or_create.go`** — `GetOrCreateIn`'s body (`ValidID` → `buildSession` → register-under-`p.mu` → `saveLocked` → skip-set → `runGroup` guard → `g.Go(sess.Run)`) is factored into an unexported `materialise(id, label, spawnDir) (*Session, took bool, error)`. `GetOrCreateIn` now calls `materialise` then `Activate`, but **only on the register path** — the take path (`took == true`) still returns without activating, exactly as before.
- **`internal/sessions/revive.go`** (new) — `Pool.Revive(id, label, spawnDir) (*Session, error)` calls `materialise` and returns without ever calling `Activate`. Deliberately takes **no `context.Context`**: that absence is the API contract that `Revive` never spawns and never blocks. A revived session lands at `stateEvicted` with an open `activeCh` / closed `evictedCh` — byte-identical to an idle-evicted session — so it respawns through the pool's existing lazy-respawn path on the next `Activate`. `materialise` passes `SessionSettings{}` on both callers, which for `Revive` is load-bearing: a phone-persisted `yolo: true` does not survive a restart (see [ADR 035](../decisions/035-lazy-revive-not-registry-rehydrate.md)).
- **`cmd/pyry/main.go`** — `sessionRouter.resolve` catches `Lookup`'s `ErrSessionNotFound` and calls a new `sessionRouter.revive(id, conversationID, conv.Cwd)`, which re-runs `resolveSpawnDir` — the same validator `sessionMinter.Create` uses at mint time, not a cached decision — before calling `Pool.Revive`. A rejected `Cwd` (escapes `$HOME`, including via a symlinked ancestor of a not-yet-existing path, #696) returns wrapping `handlers.ErrSpawnDirRejected` before any pool state is touched. The empty-`CurrentSessionID` guard still fires before `Lookup`, so an unbound conversation can never reach the revive branch.

Direction chosen: lazy revive in `resolve`, sourcing the spawn directory from the *conversations* registry's `Cwd` (already `$HOME`-confined and persisted since #685/#696). The rejected alternative — rehydrating `sessions.json` at `Pool.New` — would have needed a new `registryEntry` cwd field (a schema change the ticket red-lined) because a minted session's `spawnDir` is not persisted on the sessions side. Full rationale, the two-directions comparison, and the accepted residues are in [ADR 035](../decisions/035-lazy-revive-not-registry-rehydrate.md).

## Patterns established

- **`materialise` as a shared register-without-activate core.** Any future caller that needs "put this session back in the pool without spawning claude" (e.g. a future startup-reconciliation pass) should route through `materialise`/`Revive` rather than duplicating the register/persist/skip-set/schedule sequence.
- **Re-validate, don't trust, a persisted path at a new spawn site.** `sessionRouter.revive` re-runs the full `resolveSpawnDir` check rather than trusting `conv.Cwd` as already-validated, because a path valid at mint time can become a `$HOME` escape before the value is next used. Any future code that spawns a claude child from a persisted-but-stale path should follow the same re-validate-at-use pattern rather than caching a mint-time verdict.
- **An absent `context.Context` as an API-level non-blocking signal.** `Pool.Revive` has no `ctx` parameter specifically so callers (and readers) can tell at the signature that it cannot spawn or block — useful precedent for other "register only, don't activate" primitives.

## Lessons learned

- **Extracting a shared core can silently un-pin a contract that was previously structural.** `GetOrCreateIn`'s "the take path returns *without* activating" was enforced by an inline early return — impossible to violate. Turning it into a `took` flag out of the shared `materialise` core made it violable, and mutating `return existing, true` → `return existing, false` survived the **entire** `internal/sessions` package: every existing take-path test targets an already-*active* session, where a stray `Activate` is just a no-op LRU touch. The pin needed a registered-but-never-activated fixture, which only `Revive` itself can produce. When a refactor converts a structural invariant into a runtime branch, mutate that branch before assuming the inherited tests still cover it.
- **A warm-start test needs the erasure asserted, not just the revival.** Asserting only "the entry is on disk after the resolve" passes vacuously, because `Pool.New` does not rewrite `sessions.json` on a warm start — the entry is still there from the previous daemon's write. The test forces a state-changing persist *before* the touch and asserts the entry is **gone**, then resolves and asserts it is back. Without that middle rung, the AC #2 assertion ("the next persist still contains the entry") is inherited from the old pool's write rather than proved by the revive.
