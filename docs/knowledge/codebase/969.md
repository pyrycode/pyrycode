# Ticket #969 — `make e2e-install` / `make e2e-update` targets for the orphaned opt-in suites

Two real, maintained e2e suites — the install round-trip
(`internal/e2e/install_{darwin,linux}_test.go`, tag `e2e_install`) and the
full `pyry update` flow (`cmd/pyry/update_e2e_test.go`, tag `e2e_update`) —
were reachable only by hand-typed build tags, with no named way to run them
on purpose. This ticket adds two `.PHONY` Makefile targets and a doc section,
following the `e2e-realclaude`/`e2e-liverelay` template from
[[968]]. Zero production Go files touched.

## Implementation

`a441067`, +69/−0 across `Makefile` and `docs/release-tooling.md`. Matched
the architecture spec (`docs/specs/architecture/969-e2e-install-update-make-targets.md`)
exactly — no deviation.

- **`Makefile`** — `e2e-install` runs `go test -tags e2e_install
  ./internal/e2e/...` (the darwin/linux build tags on the test files mean
  only the host platform's install test compiles under this one invocation);
  `e2e-update` runs `go test -tags e2e_update ./cmd/pyry/...` (that suite is
  `package main`, so it's scoped to `cmd/pyry`, not `internal/e2e`). Both
  inserted after `e2e-liverelay` and before the `preship` block; `check` and
  `preship` untouched, and the existing `:31-33` header note documenting the
  deliberate exclusion was left as-is.
- **`docs/release-tooling.md`** — new "Install & update e2e suites" section
  after the #968 "Live-relay smoke test" section: one subsection per target
  with the `make` invocation, the underlying `go test -tags` command, when to
  run it, and its actual footprint.
- **Footprint written per-suite, not copy-pasted from the AC wording.** The
  spec flagged that AC2/AC4's phrase "mutates the real user launchd/systemd
  domain" is true for `e2e-install` (`launchctl bootstrap` /
  `systemctl --user`) and **false** for `e2e-update` (hermetic under a temp
  HOME — spawns/restarts a real daemon but nothing outside the temp dir). Both
  the Makefile comments and the doc section state each suite's real footprint
  rather than reusing one warning for both.

## Patterns established

- **A target that only runs an existing, unchanged opt-in suite is XS and
  not `security-sensitive`**, even when the suite it runs drives
  signature-verify/install/daemon-restart machinery — there's no new design
  surface, just a named entry point onto code that already existed and was
  already reviewed. Consistent with [[968]]'s "pass-through" precedent, but
  without even the 968 nuance of a deferred security-sensitive branch: #969
  has no such branch, so it's a clean not-sec XS.
- **Two sibling `.PHONY` targets built from one template collapse to one
  ticket**, not two — same shape, same doc section, same review pass.
