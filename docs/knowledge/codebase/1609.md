# Ticket #1609 — expose one conversation-keyed run-configuration seam

Split from #1587. Blocked-by #1608 (landed, `bd64f5b`). `relay.V2SessionConfig` reported run configuration through three bootstrap-scoped seams — `SnapshotSettings`, `SnapshotUsage`, `BootstrapSessionID` — none of which took a conversation, and whose agreement ("all three describe the same session") was a warning in a doc comment rather than a property of any type. This ticket adds the conversation-keyed replacement, `RunConfigFor`, and wires it. It changes no reported value and consults nothing new: nothing reads the new seam yet, so every `session_settings`/`screen_snapshot` reply stays byte-identical. Making `request_session_settings` read it, and retiring `BootstrapSessionID`, is #1610.

## Implementation

- **`internal/relay/v2session_seams.go`** — new `RunConfig` struct (`SessionID`, `Model`, `Effort`, `YOLO`, `UsedTokens`, `WindowTokens`, all primitives) and new `V2SessionConfig.RunConfigFor func(conversationID string) (RunConfig, bool)` field. Comma-ok, not an in-struct flag: `false` means the conversation is not addressable and every field of the returned `RunConfig` is zero, which a caller must not read; `true` with an empty `Model`/`Effort` is a real answer ("inherited daemon default"), the same meaning `SnapshotSettings` already carries. The paragraph in `BootstrapSessionID`'s doc that said all three seams "move together" when the decision was revisited is amended: it now names `RunConfigFor` as the actual replacement and states the three keep their current readers/wiring/values until #1610.
- **`cmd/pyry/main.go`** — `resolveBoundRunSettings(convReg *conversations.Registry, pool sessionSettingsReader, convID string) (boundRunSettings, bool)`, the settings half, at the composition root. `boundRunSettings{sessionID, model, effort, yolo}` is a named struct (not a 4-tuple) so three adjacent same-typed strings can't transpose silently. `sessionSettingsReader` is a one-method interface (`SettingsFor`) declared consumer-side; `*sessions.Pool` satisfies it with no adapter. Behaviour: `convReg.Get` miss or `CurrentSessionID == ""` ⇒ `(zero, false)` **before the pool is touched** — the refusal is inherited verbatim from `resolveBoundSession`, not re-derived, because `Pool.Lookup("")` resolves to the **bootstrap** session (#678 isolation). Otherwise a single `pool.SettingsFor(id)` call: its sentinel error (session no longer held, e.g. idle-evicted) ⇒ `(zero, false)`; success ⇒ the resolved id plus its settings. One acquisition, not resolve-then-read, is the design: `SettingsFor` answers "does the pool hold this id" and "what are its settings" under one `RLock`, closing the idle-eviction window a two-call shape would open between resolving the id and reading its settings. `SettingsFor` deliberately has no `""`-is-bootstrap special case, so the fall-through-to-bootstrap failure mode has no expression in this path at all — a second, structural guarantee stacked on the `CurrentSessionID` guard. `SettingsFor`'s error is discarded, not wrapped: `convID` never reaches a log line or an error string, and the resolver takes no logger. `Pool.DefaultSettings` and `resolveBoundSession` are unmodified.
- **`cmd/pyry/relay.go`** — new `relayWiring.runSettings func(convID string) (boundRunSettings, bool)` field (bound at `runSupervisor` in main.go to `resolveBoundRunSettings(convReg, pool, convID)`), and `runConfigFor(resolve, usage) func(convID string) (relay.RunConfig, bool)`, the composer at the wiring point. `resolve == nil` ⇒ returns `nil` at **build time**, before any closure exists — the #1608 `bootstrapSnapshotUsage` structural-nil pattern. The returned closure calls `resolve(convID)` first; on `false` it returns `(relay.RunConfig{}, false)` and calls `usage` **not at all**; on `true` it builds the `RunConfig` and calls `usage(b.sessionID)` — the *resolved session id*, never the caller's conversation id — only if `usage != nil`. `usage == nil` deliberately does **not** collapse the whole seam to nil (unlike `bootstrapSnapshotUsage`, which needs both halves to report anything): a resolved conversation still reports its own id and settings with the context figures at zero, because an unwired usage half degrades two integers, not resolvability. `startRelayV2` calls `snapshotUsageFor(w.claudeSessionsDir)` a **second time** (a fresh, stateless closure) rather than reusing the existing `bootstrapSnapshotUsage` binding, which is fixed to the bootstrap id and would report the bootstrap's occupancy for every conversation. `RunConfigFor: runConfig` is wired into the `V2SessionConfig` literal; the three existing seams (`SnapshotSettings`, `SnapshotUsage`, `BootstrapSessionID`) are untouched.
- **`cmd/pyry/run_config_test.go`** (new) — table-driven tests over a call-recording `sessionSettingsReader` double and a real `*sessions.Pool` (via `newRouterTestPool`), plus composition tests over a stub resolver and a recording usage func. Every unresolvable row asserts both the zero return *and* the exact sequence of pool/usage calls made — zero calls for empty/unknown/unbound conversation ids, exactly one call (the dangling session id, never `""`) for a pool-evicted binding.

## Patterns established

- **A comma-ok return, not an in-struct flag, when the zero value is already a real answer.** `RunConfig`'s zero value (empty model/effort, `yolo:false`, zero tokens) is indistinguishable from a genuinely resolved all-defaults session, so "not addressable" cannot live inside the struct — it has to be the second return value, checked before the struct is read at all.
- **Collapse two related reads into one acquisition when their disagreement is the exact hazard being guarded against.** `resolveBoundRunSettings` reads via `pool.SettingsFor(id)` alone rather than `Lookup` then `SettingsFor`, because a two-call shape opens a window (idle eviction) in which the reported id and the reported settings could describe different sessions — the precise invariant the seam exists to guarantee. Building on the read that has no `""`-is-bootstrap convention (rather than `Lookup`, which has one) removes an entire failure class structurally instead of guarding against it.
- **A call-recording test double, not just a return-value assertion, when "the pool must not be touched" is part of the contract.** Return values alone can't distinguish a refusal from a resolved-but-all-defaults session; only counting/recording the ids a double was asked for can prove a rejected path never reached `pool.SettingsFor("")` — the string that `Pool.Lookup` (not `SettingsFor`) would resolve to the bootstrap.
- **A composer that consults its second dependency only after the first succeeds, and only with the first's *output* — never the caller's raw input.** `runConfigFor`'s closure calls `usage` with the *resolved* session id, never the conversation id it was called with, so an unresolvable conversation reaches no transcript path at all. This is the structural form of "an unresolvable conversation addresses nothing."
- **Two closures over the same nil-optional dependency don't need to share a nil-ness rule.** `bootstrapSnapshotUsage` collapses to nil when either half is unwired because both are required to report anything; `runConfigFor` keeps working with a nil `usage` because resolvability and occupancy are independent facts about a conversation. Copying a neighboring nil-collapse rule by pattern-matching shape rather than re-deriving the actual dependency relationship is exactly the mistake the design doc calls out by name.

## Lessons learned

From the PR body:

- A recorded-call assertion needs `%q`, not `%v`, when the recorded value is a slice of ids: `[]string{""}` renders under `%v` as `[]`, so a mutant that asks the pool for the empty id produces a failure message ("asked for `[]`, want `[]`") that reads like a passing run. The mutation-verification run is what surfaced this — the assertion itself was correct; only its failure report was unreadable enough to hide a real red.
- The naming question the spec left open (whether `RunConfig`/`RunConfigFor` needed disambiguation from the neighboring `V2SessionConfig`) resolved as proposed — no collision, no rename needed. staticcheck was clean on the set-but-unread exported field as anticipated, so no construction test was required to keep the gate green.
