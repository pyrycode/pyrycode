# Ticket #1340 — Probe rig: the live staging driver for one `pyry agent-run` turn and its handle

The part of this instrument family that genuinely needs a live process. A live
probe of `pyry agent-run` splits into a deterministic **staging** half (did
the model issue the command, did the trigger fire, did the FIFO rendezvous
complete, did the during-turn process pin match) and a **reading** half (what
the trailer says, and whether the held command was alive when it was
written) that only a real claude can answer. Everything a fixture can reach
for the staging half had already shipped in three blockers — the pin
reduction (#1338), the staged command/prompt/FIFO-name/env-delta
declarations (#1342), and the eight-field record assembly (#1343). This
ticket ships the one thing none of them could: `finLiveRunStage`, which
spawns pyry, holds the rendezvous FIFO, drives the turn to the instant a
process pin is meaningful, takes that pin, and hands the pin plus the rig's
own facts to the shipped assembly — returning a handle carrying the run's
live facts and the staging tier's verdict, *as the gate returned it*.

New file only: `internal/e2e/realclaude/finding_live_run_test.go`
(`//go:build e2e_realclaude`, 446 lines). No existing file edited, no
production code. **Ships no test** — its only exercise is compilation and
`go test`'s vet subset under `make e2e-realclaude`; the live consumer is
#1337, which is where `needs-real-claude` sits.

## Implementation

- **`finLiveRunHandle`** — returned as a **pointer**, deliberately: the
  pyry-exit kill cleanup is registered before pyry's pid exists, so its
  closure has to read a field written later (`h.PyryPID`), the same shape
  `background_reach_probe_test.go`'s `rec.PyryPID` uses. Ten fields:
  `PyryPID`, `ClaudePID`, `PyryExited <-chan struct{}` (receive-only, closed
  by the `cmd.Wait` goroutine), `Stdout`/`Stderr *probeSyncBuffer` (**never**
  `[]byte` — both the reap log and the trailer land after this driver
  returns, so a snapshot would be taken strictly too early), `FIFOPath`,
  `EnvDelta`, `ClaudeVersion`, `Pin finLivePinReading` (crosses **whole**,
  never flattened — flattening would re-declare four values that already
  have one declaration and invite a second producer for `RowCount`), and
  `Staging finOutcomeResult` (`finLiveAssembleStaging`'s return **as
  returned**). **No JSON tags**, inheriting `finLivePinReading`'s and
  `finOutcomeStaging`'s "input only, never published" posture — `Pin.Rows`
  and `Pin.ClaudeCommand` are verbatim argv off the ambient process table.
- **`finLiveRunStage(t *testing.T) *finLiveRunHandle`** — no parameters
  beyond `t`; establishes its own credentialed worktree via
  `WithWorktreeAuthenticated` as the first statement, so a machine without
  credentials skips before anything is created. **Straight-line body, no
  early return, no disposition of its own** — every staging failure it could
  branch on already has a rank-ordered arm in `finOutcomeStagingGate`
  (identity → trigger → rendezvous → pin-scan-errored → count → pass-through),
  so the driver fills facts and hands them over rather than deciding which
  failure to report.
- **Cleanup order is the contract.** The pyry-exit kill cleanup is registered
  *before* `holdProbeFIFO`, so LIFO releases the FIFO first (giving pyry a
  real chance to finish the turn and exit on its own) and the kill is
  defence-in-depth rather than the thing that produced the exit — inverting
  this order produces a run that is clean-looking (green, handle populated)
  while the rig, not pyry, produced the exit, with no symptom. Copied
  verbatim, including the `h.PyryPID <= 0` guard with its `// LOAD-BEARING`
  comment, from `background_reach_probe_test.go:355-374` (not the
  comment-less copy at `background_trigger_probe_test.go:438-453`).
- **The driver takes the `tool_use`/`tool_result` wait itself, before
  pinning**, even though `finLiveAssembleStaging` also waits internally.
  The assembly's wait happens *after* the pin (it takes pin counts as
  inputs), so a driver reasoning "the assembly does the waiting" would pin
  before the `cat` exists, match 0 or 1 rows, and fire the gate's count arm
  on a correctly staged run — one live claude turn spent finding out. See
  the ordering-hazard pattern below under Patterns established.
- **The pin is one `ps` scan carrying both needles** (`fifoPath` and
  `tdnClaudeNeedle`) with two exclusions (the test binary's own pid, pyry's
  pid), handed to `finLivePinReduce` **unchanged** — the driver does not
  filter, count or dedupe it, and forwards `finLivePinWantRows` as the want,
  never `scan.MatchCount` (3 on a healthy run) and never `len(Pin.PGIDs)` (1
  on a healthy run).
- **No budget-fired run is staged.** `spawnProbePyry`'s existing
  `--max-turns=6` leaves headroom for the turn to *complete*; a budget-fired
  run's exit code can't distinguish outcomes (the `Terminate` hook cancels
  the run context and `Run` returns `nil` exactly as on normal completion)
  and its `Terminate` hook reaps *before* the trailer is written.
- **Captured-bytes discipline**: no `ps -E`/`-Eww` anywhere (the driver's one
  scan is `ps -axww -o pid=,ppid=,pgid=,command=`, no environment column);
  matched rows and claude's argv cross the handle only as the already-capped
  `reachProc.Command`; the file formats no `Detail` and writes no artifact.
- **Two `t.Fatalf`s**, both rig faults with no named home in the gate:
  `probeWaitForDirectChild` returning 0 (pyry never spawned claude) and
  `probeWaitForSessionID` returning `""` (would otherwise cause the gate to
  misreport `stage-no-bash-call` for a run the model was never asked to
  make). Both carry a deadline and pyry's own truncated stderr, nothing from
  the process table.

## Patterns established

- **A driver's body stays straight-line when every failure it could detect
  already has a named, rank-ordered arm downstream.** The alternative —
  branching early on, say, a rendezvous miss — saves at most one deadline of
  wall clock on a run that already lost a live turn, at the cost of a code
  path exercisable only live. Fill facts, hand them to the gate, let rank
  order pick the story.
- **When a callee takes a value as an input but performs its own logically
  prior wait *internally*, the caller cannot treat the callee's wait as a
  substitute for its own** if the caller has an action (here, taking the
  pin) that must happen strictly before the callee is invoked. The callee's
  wait fires too late to matter to the caller's own ordering requirement.
  This shape — a helper waiting for a prerequisite that the caller also
  needs settled *before* calling the helper — is worth naming explicitly in
  a design doc rather than left to be inferred from "the helper already
  waits for that."
- **Cleanup registration order (kill-before-hold, so LIFO releases the hold
  first) is now a three-instance pattern in this package**
  (`background_reach_probe_test.go`, `background_trigger_probe_test.go`,
  this file) and should be copied verbatim, comment included, by any future
  rig that pairs a resource hold with a defence-in-depth kill — inverting it
  produces a run indistinguishable from a correct one except in what it
  measures.

## Lessons learned

(From the PR body; see PR #1346, and code review comment on PR #1346.)

- **A file whose whole job is to *forbid* a captured-bytes channel trips its
  own grep for that channel.** The only `ps -E` occurrence in this file is
  the prohibition comment naming it. A sweep for a forbidden flag has to ask
  whether the hit sits beside the pin that forbids it, not just whether it
  matched.
- **Code review SHOULD FIX (non-blocking): a counted doc claim
  ("the two `t.Fatalf`s... and they are the only ones") was false against
  the shipped file** — two more `t.Fatalf`s exist for the prompt/system
  file-write pair, copied as plumbing from the reach precedent
  (`background_reach_probe_test.go:378-385`). Both unlisted messages are
  safe in substance (a `t.TempDir()`-rooted path plus an OS error, nothing
  from the process table), so this was a documentation-accuracy gap rather
  than a leak — but an exhaustiveness claim a reader can falsify by grepping
  the same file is exactly the failure class this file family exists to
  avoid. The architecture spec inherited the same imprecision (§ Error
  handling said "two ... and they are the only ones" while § Design step 7
  separately mandated copying a block containing two more), so this was the
  spec's own gap reaching the code rather than a deviation from it. **Lesson
  for future specs in this family: `rg -c 't.Fatalf'` the shipped file before
  writing a counted claim about it, never rely on an enumeration written
  before the precedent-copy step was drafted.**
- **Code review NIT: a citation pointed at the doc paragraph asserting a
  property rather than the body implementing it** (`finding_live_run_test.go:170`
  cited `finding_live_assembly_test.go:228-231`, the doc; the implementing
  body is at `:277-289`). The property held either way — only the
  line-range pointer was off by a section.
