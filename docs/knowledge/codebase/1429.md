# #1429 — Trailer family's passthrough cites now name the tee-parse block

**Size:** XS. Zero production files. Five 7-for-7 in-place string replacements
across two files.

## What shipped

Four cites in `internal/e2e/realclaude/trailer_terminal_reason_test.go`
(`:28`, `:97`, `:232`, `:242`) and one in
`docs/knowledge/features/e2e-realclaude.md:1104` named
`streamrunner/runner.go:170-176` — the `childCtx`/`cancelChild` cancellation
block — as the reason streamrunner passes claude's bytes through unchanged.
The actual passthrough is the tee-parse at `runner.go:177-179`
(`parser := newStreamParser(cfg.Stdout, nil)`). Two of the four Go sites sit
inside **published** `Detail` strings reaching a probe record a human
reviews; a third (`:97`) was the load-bearing *reason* cited for
`trailReasonPresentOwesNone`'s claim limit, so an argument was resting on a
citation to unrelated code.

All five edits are the same 7-character substring swap (`170-176` →
`177-179`), scoped by a single `replace_all` to
`trailer_terminal_reason_test.go` plus one doc-line edit, so every hunk is an
in-place `-N +N` — no line inserted or deleted, no Detail byte count moved
(pinned at 269 and 395 bytes, confirmed unchanged pre/post). The sibling file
`trailer_admissibility_test.go` (`:126`, `:1212`) already carried the correct
form; this ticket brings the family into agreement with its own precedent.

Full design: `docs/specs/architecture/1429-trailer-passthrough-cites-name-tee-parse.md`.

## Verification shape (worth reusing)

- **Byte-length pins need arm identity logged alongside them.** `len(Detail)`
  alone can't distinguish "the streamrunner arm still produces 269 bytes"
  from "the input stopped reducing to `streamrunner` and a different arm
  coincidentally produced 269". Both the developer's `go test -overlay`
  measurement and code review's independent re-measurement logged the arm's
  `Value` (`reason-absent-on-owes-none-path` / `reason-present-on-owes-none-path`)
  next to the byte count, making the measurement self-witnessing.
- **A cap check (`reachCapCommand`, 512-byte truncation marker) is not a
  substitute for a length pin.** These Details sit 243 and 117 bytes under
  the cap, so the cap assertion stays green through a 7-for-8, a 7-for-20, or
  a wholesale reflow — it can't detect the length-neutrality this ticket
  cared about. See [[po-1429-a-cap-check-is-not-a-neutrality-check]].
- **Per-hunk `git diff -U0` parity, not whole-file line-count parity, is what
  proves cite targets weren't displaced.** Whole-file parity permits a `+2`
  here against a `-2` there while shifting everything between; six inbound
  cites from `trailer_admissibility_test.go` point into this file, so an
  in-place-only diff (every hunk `-N +N`) was required, not just an unchanged
  total.

## Patterns established

**A repo-wide residual sweep pinned in an AC/spec, for a string the ticket's
own build artifact must quote, goes stale the moment that artifact lands.**
The spec's § Residual (and the AC) predicted the post-change sweep for
`runner.go:170-176` would return exactly 7 lines across two classes. It
actually returned 15: the 1429 spec itself (`docs/specs/architecture/1429-*.md`)
quotes the stale string 8 times to describe the defect it fixes, and that
spec landed *after* the 7-line prediction was written. The developer flagged
the deviation explicitly in the PR rather than editing the landed spec to
match (repo convention: a `spec:` commit is never amended after landing), and
code review agreed this was correct — the class-level claim ("only
`docs/specs/architecture/` build artifacts and `codebase/1366.md` remain")
held exactly; only the per-file line-count enumeration was short by the
spec's own artifact.

**Takeaway for future ACs:** when an acceptance criterion pins a repo-wide
sweep count for a string that the ticket's own spec/PR must quote to describe
the defect, pin the sweep by **class** (which files may still match, and
why) rather than by total count. The class claim survives the spec's own
commit landing; a total does not.

## Known residual, deliberately out of scope

Code review (NIT, not actioned here) found the same cite-drift pattern in
`internal/e2e/realclaude/finding_live_run_test.go`, in a form this ticket's
qualified `runner.go:170-176` sweep can't see — cites naming `:172-176`,
`:176`, and `:174` for behavior that's actually at `:177-179`, `:183`, and
`:181` respectively (5 sites: `:315`, `:402`, `:524`, `:543`, `:549`). All
predate this PR and none is displaced by it. Left for a future ticket in this
same family (#1366, #1373, #1414, #1417, #1419, #1420, #1426, #1427, #1429).

## Lessons learned

- A spec that must quote the exact string it's correcting, in order to
  describe the defect, becomes part of that string's own post-change
  residual — any AC pinning a total count for that sweep is measuring a
  moving target once the spec commits.
- Logging a byte-length measurement's discriminating identity (which
  code path produced it) alongside the length turns a fragile single-number
  pin into a self-witnessing one, at no extra cost.
