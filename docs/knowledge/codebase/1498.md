# Ticket #1498 — `pyry update` refuses a non-pinned downgrade

`doUpdate` installed whatever `/releases/latest` advertised whenever it differed from the running version — including a version *older* than what's running. The compare switch (`cmd/pyry/update.go`) only exited on a dev build, a compare error, or `Same`; `update.Newer` (current newer than latest — the rollback direction) fell through to download → verify → replace → restart. The #776 signature gate can't catch this: an older genuine release was validly signed when it shipped, so a yanked release or a stolen GitHub publishing token rolled the daemon back silently. This closes that gap with one guard on the non-pinned path; `--version <tag>` stays the sanctioned, unguarded downgrade route.

## Implementation

- One guard in `doUpdate` (`cmd/pyry/update.go`), between the `o.checkOnly` early return and the `AssetName` call: `if o.pinVersion == "" && cmp == update.Newer { return fmt.Errorf(...) }`. Both halves are load-bearing — dropping the pin check would break `--version <older-tag>`; hoisting the guard above the `checkOnly` return would make `pyry update --check` exit non-zero against a rolled-back latest, which `docs/release-tooling.md`'s release checklist depends on staying 0.
- Error message follows the file's existing `update: <step>: …` unsentineled-string convention (step name `refuse downgrade`), and names the sanctioned escape hatch verbatim so an operator can copy-paste it: `update: refuse downgrade: latest release v0.9.0 is older than the running version 0.12.0; run 'pyry update --version v0.9.0' to downgrade intentionally`. No new sentinel — matches the house pattern in this file, and nothing needs `errors.Is` on it.
- Error-only; no extra `==>` line to `o.out`. The two version lines have already printed by the time the guard runs.
- Two new tests in `cmd/pyry/update_test.go`: `TestUpdate_UnpinnedDowngradeRefused` (AC 1/2 — asserts a request-recording server saw zero asset requests, proving the refusal fires before any fetch, not just before `replace`/`runRestart`) and `TestUpdate_CheckOnlyOlderLatest` (AC 4 — `--check` against an older latest still prints both version lines and exits 0). Both use a new `newDowngradeReleaseServer` constructor (parallel to `newFakeReleaseServer`, which has four happy-path callers to keep clean) whose catch-all handler *records* the requested path and 500s rather than calling `t.Fatalf` — the handler runs on an `httptest` goroutine, where `Fatalf`'s `runtime.Goexit` would kill the handler and surface a misleading transport error instead of the real assertion failure.
- Zero existing tests modified: `TestUpdate_PinVersion`, `TestUpdate_AlreadyAtLatest`, `TestUpdate_DevBuildSkips`, `TestUpdate_Success` all stay green untouched — diff is 146 insertions, 0 deletions.
- `docs/knowledge/features/pyry-update-command.md` — flow steps, error-contract table, and tests table updated by this documentation pass (the architecture spec explicitly reserved that edit for the doc phase; the developer did not touch the file).

## Patterns established

- **Record-and-500, not `t.Fatalf`, for `httptest` catch-all handlers.** When a negative assertion needs to prove "no request of this shape happened" rather than "this specific seam wasn't called," and the assertion must survive on a non-test goroutine, record under a mutex (or atomic) and assert after the driving call returns. The `t.Fatalf`-sentinel idiom stays correct for seams invoked on the test goroutine itself (`replace`, `runRestart`).
- **Guard placement relative to a `--check`/dry-run early return is a testable ordering property, not a style call.** `TestUpdate_CheckOnlyOlderLatest` is the test that reddens if the guard drifts above `o.checkOnly`'s return — worth a dedicated test whenever a new guard is added near an existing early-exit boundary.

## Lessons learned

- The new test's request-recording server is what actually carries AC 1, not the `t.Fatalf` sentinels on `replace`/`runRestart`. Run against the unguarded (pre-fix) tree, `TestUpdate_UnpinnedDowngradeRefused` failed on the recorded-path assertion — the tarball fetch had already happened — while the `replace`/`runRestart` sentinels were never reached (the 500 response aborts the flow before either seam is invoked). A guard accidentally placed *after* `AssetName` would have passed a sentinel-only test outright. When an AC forbids a category of *network activity* rather than pinning a specific downstream *effect*, sentinel seams on `replace`/`runRestart` sit too far downstream to catch a misplacement — the assertion needs to sit at the point closest to what's actually forbidden.
- Code review independently re-derived rather than trusted two of the ticket's central claims — `CompareVersions`'s polarity, and the `e2e_update`-tagged suite's immunity (all five `updateOptions` literals in `update_e2e_test.go` serve `v999.0.0` against `currentVersion: "0.0.1"`, so `CompareVersions` always returns `Older` and the new guard never fires there) — and ran the tagged suite directly (19 tests, all green, counted from `=== RUN`) rather than accepting the spec's assertion about it, since `make check` cannot see that build-tagged package at all.
