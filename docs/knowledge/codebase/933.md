# Ticket #933 — fix the deep RacingSendError close-status-loss flake

Test-only fix for `TestFatalCloseCodes_HaltsReconnect_RacingSendError`, the deeper flake shape #523 explicitly filed-and-deferred (`Connect returned context deadline exceeded`, distinct from #523's already-fixed `did not return before ctx deadline` test-budget race). It surfaced on a developer's real `make check` on 2026-07-11, meeting #523's documented re-open condition. PR #944.

## Implementation

### `internal/transport/wssclient_test.go` (+10/-8 LOC, no production change)

Root cause was in the test's relay helper, not scheduling. `racingCloseRelay`'s drain goroutine (`newRacingCloseRelay`, `wssclient_test.go:863-935`) used to **echo** client frames back with `conn.Write` while the same goroutine's caller concurrently called `conn.Close`, which itself writes the close frame. Two writers on one `coder/websocket` conn is a protocol violation the library doesn't guard against; about 1% of the time it corrupted the frame stream and reset the connection before the client's `recvPump` read the peer's 4409 close, so no slot of `serve`'s `errs[]` carried a close status. `serve` returned a non-fatal error, `Connect` reconnect-looped the single-shot 410 relay, and the test's 15s ctx deadline fired — the `context deadline exceeded` shape.

**Fix:** the relay now reads and discards instead of echoing (`wssclient_test.go:899-911`). Draining the client's writes — which is all the relay needs, to keep `sendPump` Writes actually blocking rather than piling up in the OS TCP buffer — only requires the `Read`; the echo-back `Write` was pure hazard, not load-bearing.

## Patterns established

- **The spec's hypothesised lever was falsified by measurement, and that's a PASS, not a deviation.** The architecture doc modeled this as goroutine-starvation-bound (`recvPump` losing the scheduler race to an unthrottled busy-Send loop) and prescribed `runtime.Gosched()` or a light inter-send throttle in the test's busy-Send loop as the fix. Per the diagnose-first protocol's own mandate ("confirm the lever moves the metric before coding"), the developer measured first: `Gosched()` moved the rate 2/200 → 2/200 (no effect), and a `closeFrameGrace` 50→250ms bump moved it 2/500 → 1/200 (no effect, re-confirming #523's inherited evidence). Both were abandoned per-spec instead of shipped anyway. The `sendPump "broken pipe"` signature correlating with every failure pointed at the actual cause — a concurrent-writer bug in the test relay, not scheduler contention. See [[code-review-diagnose-first-can-falsify-architect-lever]] and [[architect-933-deep-flake-starvation-bound-lever]].
- **Read-and-discard beats throttling as a fix shape when the root cause is a concurrency-contract violation.** The shipped fix is deterministic (aligns the relay with `coder/websocket`'s one-reader/one-writer contract — Read + Close is supported, Write + Close is not) rather than probabilistic (reducing starvation odds without eliminating the race). When a flake's root cause turns out to be "two goroutines mutate/write the same handle concurrently," look for the redundant writer before reaching for scheduling knobs.
- **A stress-matrix diagnose-first protocol pays off even when its own hypothesis is wrong.** The protocol's value isn't "get the model right the first time" — it's forcing measurement before code exists, so a wrong model gets discarded cheaply (one ratchet sweep) instead of shipping a band-aid that doesn't move the metric. This is the second ticket in the #290/#523/#933 chain where a ratcheted candidate came back flat and was abandoned per-protocol.

## Lessons learned

### An architect's causal model is a hypothesis, not a mandate — the spec's own protocol says so

The spec was explicit that the starvation model was "the developer's *starting hypothesis*, to be confirmed by Phase-2 instrumentation — not a licence to skip Phase 1," and that Phase 2's two candidate fixes were to be measured, not assumed. The developer followed that instruction to the letter: measured both prescribed levers, found them flat, and let the `broken pipe` correlation in the logs redirect the investigation to the actual defect (in the relay helper the spec had otherwise treated as a read-only fixture). The code review confirmed this is the intended outcome of a diagnose-first spec, not a scope deviation: the fix stayed in-scope (test-only, AC4), was measured (AC1/AC2/AC3 all independently reconfirmed), and the anti-vacuous gate still held (reverted-`serve` still fails 19/20 at `-race -count=20`). Future specs in this chain should keep stating hypotheses as falsifiable, and future developers should keep measuring before coding — this is the mechanism, not a one-off.

### A pre-existing docstring can go stale when the mechanism it describes is removed

Code review flagged (non-blocking SHOULD FIX, still open post-merge) that `racingCloseRelay`'s struct godoc at `wssclient_test.go:863` still reads "echoes incoming frames to keep sendPump writes draining," which contradicts both the new code and the new inline comment three lines below it explaining why echo-back was removed. The PR shipped anyway since it was a single non-blocking nit. Worth a follow-up one-line fix if anyone is next in this file — the docstring is the first thing a future reader of `racingCloseRelay` sees.
