# Ticket #1226 — Probe: what does pyry do with the output file a backgrounded Bash command writes?

Offline probe, split off #1223's measured trigger. When claude's Bash timeout expires it
backgrounds the command and writes its output to
`/tmp/claude-<uid>/<encoded-cwd>/<session-id>/tasks/<backgroundTaskId>.output` — a location
#1223 already measured and confirmed lies **outside** the session workdir. This ticket asked
whether any pyry component enumerates, reads, or removes that file (a trust question — untrusted
command output crossing into pyry from an undeclared input) or whether anything removes it (an
accumulation question). **Zero production code, zero test code** — the deliverable is a GitHub
comment ([full record](https://github.com/pyrycode/pyrycode/issues/1226#issuecomment-5112926132))
plus this doc. No follow-up ticket was filed.

## Verdict

**No consumer.** No pyry component under `internal/` or `cmd/` constructs, enumerates, reads, or
removes `/tmp/claude-<uid>/…/tasks/<id>.output`, in production code. Every search (four axes for
enumeration/read, three for content-derived paths, one for removal) fired its mandated
known-positive control, so each negative is earned rather than a broken search read as a finding:

- Enumeration control: `debugbundle.newestRecording` (`internal/debugbundle/bundle.go:135`)
- Content-derived-path control: `transcript.GuardProbedPath` (`internal/transcript/transcript.go:111`)
- Removal control: `pruneOldRecordings` (`internal/agentrun/ptyrunner/runner.go:706`)

The one component that comes close — `transcript.Newest` (`internal/transcript/transcript.go:151`)
— reads filenames from claude's **sessions** dir, a different tree, and validates each through
`sessionFileStem` before use. `GuardProbedPath` would reject a `tasks/<id>.output` path on **both**
of its clauses independently: the resolved parent dir isn't `canonicalDir`
(`transcript.go:116`), and `bjh1j6tle.output` fails the `.jsonl`-suffix check in
`sessionFileStem` before `ValidStem` is even reached (`transcript.go:55-57`). The rejection is
stat-free — `EvalSymlinks` falls back to `filepath.Clean` on error, so it holds whether or not the
file exists on the machine running the check.

## Findings worth carrying forward

- **pyry is two facts short of this path, not structurally unable to reach it.** `encodeWorkdir`
  (`internal/sessions/reconcile.go:28`, `[^A-Za-z0-9]` → `-`) applied to #1223's recorded
  resolved cwd reproduces the observed `tasks/` slug byte-for-byte, `_`→`-` mapping included.
  pyry already owns a byte-exact encoder for the hard middle path component and already computes
  `os.Getuid()` elsewhere (`cmd/pyry/update.go:130`); it just never joins `/tmp/claude-<uid>` +
  the encoded cwd + `tasks/<backgroundTaskId>.output`. So "pyry doesn't know this file exists" is
  a claim about current behavior, not about what a future reader would have to build — a
  follow-up that wanted to read the file would need no new path machinery.
- **macOS 26.5.1 dropped `periodic(8)` entirely — `/tmp` sweeping is now an always-on launchd
  daemon with no enable-gate.** There is no `/etc/periodic`, no `/etc/defaults/periodic.conf`.
  `/tmp` cleanup moved into `com.apple.tmp_cleaner`
  (`/System/Library/LaunchDaemons/com.apple.tmp_cleaner.plist` →
  `/usr/libexec/tmp_cleaner`), running daily at midnight via `StartCalendarInterval`, with the
  historical `daily_clean_tmps_*` variables inlined and no `_enable` toggle to check. Policy:
  files removed when atime **and** mtime **and** ctime all exceed 3 days; directories removed
  only when empty *and* 3-days-stale. This corrects the standing assumption (previously carried
  as a `periodic.conf`/`daily_clean_tmps_enable` default-`NO` prediction) that `/tmp` might not
  be swept on macOS — it is, unconditionally, as of this OS version. Observed on this host: 437
  `.output` files / 14.4 MB, zero older than the 3-day threshold, versus 359 other files in the
  same tree that do survive past it — the write-once-so-all-three-timestamps-age-together
  asymmetry that makes the sweep `observed` rather than merely `documented`. Steady state is
  **bounded accumulation** (~3–4 rolling days), not unbounded growth. Linux was not verified on
  a live host; `systemd-tmpfiles` / `tmpfiles.d(5)` is the documented-only analogue, and many
  distros mount `/tmp` as tmpfs regardless.
- **claude's own removal behavior splits into two questions with different answers.** "Removes
  at session exit" is `observed: no` — 437 `.output` files persist across 407 ended session
  directories spanning four days; only the OS sweep bounds them. "Removes at task completion"
  stays `undetermined-offline` — the filesystem can't distinguish a completed task from one
  abandoned when its session died. A live run would need to watch a single `.output` file across
  task completion, session exit, and a `SIGKILL`ed claude; because the OS sweep is 3-day-scale,
  any disappearance seen within the same live session is attributable to claude, not the OS.
- **The `/tmp/claude-<uid>` directory is `drwx------` (0700)**, inside the sticky world-writable
  `/private/tmp` — another local user cannot read backgrounded command output. Free observation
  from the OS-arm inspection (spec's Open Question 2); posture is correct, nothing to file.

## Lessons learned

From the PR body (#1238) and code review (PASS, 0 MUST FIX / 1 SHOULD FIX / 2 NIT):

- **A record citing "value X from envelope Y" needs to confirm X and Y are the *same* envelope
  before combining fields across a multi-envelope record.** The spec pointed AC1's `$TMPDIR`
  evidence at the `probe-hold` path in the recorded `tool_use` input, but that envelope was a
  different rep from the `tool_result` being decomposed (different `tool_use_id`, different
  tempdir suffix) — using it would have silently turned a single-sample derivation into a
  cross-sample one. The `tool_result`'s own `cwd` field carried the same fact from the *same*
  envelope; the fix was re-pointing the citation, not re-deriving the conclusion.
- **A "historically defaults to X" caveat can be overtaken by the platform removing the
  mechanism entirely, not just changing the default.** The architect flagged
  `daily_clean_tmps_enable` (historically `NO`) as the likely place this probe would overturn the
  ticket body's premise. On macOS 26.5.1 the whole `periodic(8)` system is gone, replaced by an
  always-on daemon with no gate to check — the prediction inverted in a way "check the default"
  wouldn't have anticipated. Read the mechanism on the actual host rather than reasoning from a
  historical default, especially when the platform version is recent.
- **A shell-loop count and a purpose-built tool disagreed 40×** (`ls -A`-based empty-dir loop:
  402; `find -type d -empty`: 11). The `find` figure was authoritative and is the only one cited
  in the record. Cross-check a cheap ad hoc count with a second tool before it feeds a published
  claim — code review independently re-derived the true figures (883 project-slug dirs / 110
  empty at depth 1; 739 empty at depth 3) and flagged that the shipped "407 session directories
  (11 empty)" line actually counted depth-1 encoded-cwd project slugs, not session directories,
  contradicting the record's own AC1 decomposition table. The verdict was unaffected, but it's a
  reminder that a count crossing multiple directory-tree depths needs the depth stated, not just
  the number.
- **Conjunctive sweep predicates (`-atime ∧ -mtime ∧ -ctime`) produce a discriminating signal for
  free.** Because `tmp_cleaner` requires all three timestamps stale together, write-once files
  age out uniformly while re-read files in the same tree are spared. That asymmetry (0 `.output`
  files past the threshold vs. 359 other files past it) is what turned "the OS sweeps it" from
  `documented` into `observed` — worth remembering as a pattern for verifying a sweep policy is
  actually active rather than just configured.
