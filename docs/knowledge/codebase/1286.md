# Ticket #1286 — Render the run record into a pasteable artifact and prove it leaks no captured bytes

Adds `internal/e2e/realclaude/finding_artifact_write_test.go` (966 lines,
purely additive, offline, `e2e_realclaude` build tag). #1291's `finRecordRun`
was already clean; this ticket closes a different gap — the record was never
**rendered**, and `writeReachArtifacts` (`background_reach_probe_test.go:823`,
the shape this writer follows) shows what rendering can get wrong: it
marshals a clean `reach.json` and then writes `rec.rawPS` — the verbatim
process table, full argv included — into `reach.ps.txt` beside it. The
record's safety property does not transfer to the directory by itself; this
ticket is the enforcing proof that it does here. Split from #1278; blocked by
#1290 and #1291 (both merged).

## Implementation

- **`finWriteArtifacts(t, dir, rec finRecordRun)`** — the whole boundary is
  the signature. It takes the built record and nothing else: no `*reachRecord`,
  no raw process-table bytes, no second `[]byte` parameter. `finRecordRun` has
  no unexported field and no field able to hold captured bytes, so there is
  nothing raw in the writer's reach to write out — `finRecordProc`'s doctrine
  (#1291) applied one layer further out. Writes exactly two files, `run.json`
  (`json.MarshalIndent`, trailing newline) and `run.md` (the safety claim, the
  same bytes fenced, one summary line built from derived scalars of `rec`
  alone — never a `%v` on an input struct), both mode `0o600`. Errors follow
  `writeReachArtifacts`: a marshal failure is `t.Errorf` and returns: a write
  failure names the path and *continues* to the next file — a lost artifact
  is loud but does not abort the remaining writes.

- **`finWriteSafetyClaim`** is a package constant, not a literal repeated in
  the writer and the test, so the two can't drift. `run.md` must *not*
  contain `operator-review-before-paste` or `OPERATOR-REVIEW` — the record
  has no field that needs marking for review, and explaining the absent
  caveat in the caveat's own words would train a reader to look for a field
  that isn't there. That explanation lives in the writer's doc comment and in
  the test, neither of which is written into the artifact — scoping the rule
  by *layer* rather than "anywhere in the file" is #1280's lesson, applied
  here to a note instead of a record.

- **`finWriteInputs()` — one fixture, always planted.** Every input field is
  filled (all `omitempty` targets non-zero, for AC1's census), and
  `trailNeedle` (#1290/#1291's shipped 42-byte plant) is planted only in the
  inputs the pipeline **reduces or drops**: a matched row's `Command`, the
  claude argv the runner-agreement read consumes, a trailer scan's `Line`
  (via `finWritePlantedTrailerScan`, pad `0`, see below), and a reap
  outcome's captured stderr (`finWritePlantedReapLog`). The inputs the record
  carries **whole by design** — `Liveness`, `Attribution`, `Trailer` (both
  embedded sub-records), `RunnerFromEnv`, `ClaudeVersion` — carry no plant;
  a needle there would go red against a *correct* build, since those fields
  are supposed to reach the artifact intact. The `Liveness` fixture is
  hand-built (not drawn from `pinReadState`, which execs `ps`, forbidden in
  this file) with a non-empty, rig-authored `ToolStderr` — non-empty so
  `omitempty` renders the key for the census, rig-authored because the field
  is carried whole and a needle there would be a plant in the wrong place.

- **The trailer plant lands *inside* the cap, and the shipped comment on
  `trailNeedle` is wrong about where it lands.** `trailNeedle`'s own comment
  (`result_trailer_observation_test.go:297-300`) says it is "placed PAST the
  cap". Measured against `trailPaddedTrailer(0)` at this ticket's base
  commit, that is not what happens: the line renders 385 bytes and the
  needle ends at byte 146 — inside `reachCapCommand`'s 512-byte cap — so
  `trailScan` records it into `Line` intact. `finWriteTrailerPad = 0` uses
  exactly that: a needle planted *past* the cap never reaches `Line` in the
  first place, so its absence downstream would prove nothing about whether
  the line is carried (a green assertion about nothing) — #1290 AC4
  established the same plant position for the same reason. **That stale
  comment was not corrected** (it lives in a sibling's file, out of this
  ticket's scope); a future reader trusting the comment over the measurement
  will plant in the wrong place. Worth a follow-up issue.

- **AC2's mandated mutations, applied and reverted, per the spec:** M1
  interpolated `in.Rows[0].Command` inside `finRecordBuild`'s Detail format
  (not appended after `trailDetail` returns — inside the format is where
  `reachCapCommand`'s cap actually applies, so the per-Detail headroom
  assertion is what catches it) and observed RED naming both `run.json` and
  `run.md`. M2 temporarily widened `finWriteArtifacts` to accept
  `finRecordInputs` and write a third file, `run.notes.txt`, containing
  `fmt.Sprintf("evidence: %s", in.ClaudeCommand)` — a miniature
  `reach.ps.txt` — and observed RED naming that file. The key `evidence`
  deliberately matches none of AC3's forbidden-substring list, so the pass
  couldn't have been resting on key names. Both mutations were reverted; the
  writer ships taking `finRecordRun` alone.

- **Four tests, one per AC, all offline** (`go test -race -tags
  e2e_realclaude -run '^TestFinWrite' -v ./internal/e2e/realclaude/`):
  - `TestFinWriteArtifactRendersEveryDeclaredField` (AC1) — set-equality
    census between the record's declared fields and the artifact's rendered
    keys, reported in both directions (missing vs. extra). See **Patterns
    established** below — this test shipped with a MUST FIX.
  - `TestFinWriteArtifactsCarryNoCapturedBytes` (AC2) — four-channel
    non-vacuity precondition (each plant channel checked before the build,
    the trailer channel checked both for needle presence *and* in-cap
    landing), the two embedded sub-records asserted clean before the build
    (carried forward from `finding_run_record_test.go:996-1014`), per-Detail
    headroom (`reachMaxCommandBytes - len(detail) >= len(trailNeedle)`,
    i.e. every Detail under 470 bytes, asserted on what was *written* —
    #1284's shipped defect was catching this on what was *built* instead),
    then the sweep itself over every file `finWriteReadDir` returns, never a
    hard-coded two-name list.
  - `TestFinWriteArtifactCarriesNoCapturedByteShapedKey` (AC3) — recursive
    forbidden-substring key scan (`command, args, comm, argv, line, stderr,
    result, raw`) with two exact-key exemptions, each independently justified:
    `tool_stderr` (shipped, permitted, carried whole on `pinStateOutcome`,
    per #1281's exact-key-not-prefix rule) and `runner_from_argv` (names the
    *reading*, not the argv — every arm of `tdnRunnerFromArgv` returns one of
    three constants, so no input byte reaches the value; AC2's claude-argv
    plant channel is the enforcing proof of that closed set). Both exemptions
    carry a non-vacuity check that the exempted key is actually present in
    the observed set.
  - `TestFinWriteArtifactPublishesNoVerbatimModelOutput` (AC4) — three
    subtests: a structural reflection check that `resultTrailer` has no
    `result`-tagged field (stated in prose in three places pre-#1286,
    checked nowhere until now); a behavioural check that the four decoded
    trailer scalars cross verbatim into `run.json` while the needle beside
    them in the same fixture does not; and a `run.md` content check for the
    safety claim's presence and the caveat phrase's absence.

## Patterns established

- **Compare structural censuses by JSON *path*, not by bare key name, the
  moment more than one type in the family can render the same field name.**
  Code review's MUST FIX on this ticket: the first cut of AC1's census
  (`finWriteDeclaredKeys`/`finWriteObservedKeys`) flattened to bare names.
  Four of the family's 32 names are shared across types — `detail` across
  five, `pid`/`ppid`/`pgid` across two each — so a dropped nested field could
  vanish from the artifact while some *other* type's same-named field kept
  the census green. Concretely: `finRecordProc` (the `matched_rows[]`
  element type, one of the two slices AC1 names explicitly) has **all three**
  of its keys shared with `pinStateOutcome`, so a name-based census covered
  `matched_rows` **not at all** — dropping the whole slice would have passed.
  Fixed by switching both walks to collect dotted, `[]`-normalised paths
  (`liveness[].ppid`, `attribution.selected.value`) instead of names. The
  type walk's memo also had to become a **recursion stack rather than a
  visited set**: `trailAdmitResult` is reachable at both `entries[].admit`
  and `selected`, and a plain visited set drops whichever occurrence is
  reached second, silently under-declaring the census's own floor. The floor
  moved 30 → 35 against a real measured count of 41. **Applies beyond this
  ticket:** any future "walk the type, walk the value, compare the key sets"
  census in this family should default to path-based comparison and ask
  explicitly whether any name in the declared set is reachable from more
  than one type before shipping a bare-name version.
- **A plant fixture that is "always on" only works safely once fields are
  sorted into carried-whole vs. reduced-or-dropped, and the sort has to be
  checked against the *builder*, not assumed from the field's type.** This
  ticket's `finWriteInputs()` follows #1291's lesson (`po-1286-plant-only-
  where-the-pipeline-reduces`) directly: `Liveness`, `Attribution`, `Trailer`,
  `RunnerFromEnv` and `ClaudeVersion` are unplanted because they are carried
  whole; `Rows`, `ClaudeCommand`, the trailer scan and the reap log are
  planted because they are reduced or dropped. Getting this sort wrong in
  either direction produces a red test against a correct build (plant a
  carried-whole field) or a green test that proves nothing (skip a
  reduced field's needle).
- **The mandated-mutation pair (M1 inside the format, M2 widening the
  writer's signature) is the concrete two-sided proof this family now
  expects for any redaction claim: one mutation shows the sweep catches a
  leak *through the formatting path*, the other shows it catches a leak
  *through an undeclared file*.** Both were required to go RED and both were
  reverted before merge; neither is dead code in the shipped file — they are
  described in the test's doc comment as evidence, not left as commented-out
  code.

## Lessons learned

- **A structural census that flattens to bare key names is silently blind to
  any field whose name is shared across more than one type in the family.**
  This is the MUST FIX above, generalised: before trusting a name-based
  "declared keys == observed keys" test, check whether the family has grown
  enough sibling types (`finRecordProc`, `pinStateOutcome`,
  `finAttributeRecord`, `finAttributeEntry`, `trailAdmitResult`,
  `finTrailerRecord`) that name collisions are now the common case rather
  than the exception. It was on this ticket, not an earlier one, because
  AC1 was the first test in the family to walk *all seven* types in one
  census.
- **A shipped comment describing where a fixture plant "lands" can be wrong,
  and the only way to know is to measure against the actual fixture the
  test uses, not to trust the comment's prose.** `trailNeedle`'s comment
  says "past the cap"; against the fixture this family actually reuses
  (`trailPaddedTrailer(0)`) it lands well inside the cap. This ticket
  measured and used the correct position rather than propagating the
  comment's claim, and recorded the discrepancy rather than silently
  correcting a sibling's file. A later ticket touching
  `result_trailer_observation_test.go` should fix the comment while it's
  there.
