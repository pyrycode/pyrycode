# Ticket #1137 — Stream e2e: `new_session` id rotation + fresh restart (no `/clear`) under `interactive_runner:"stream-json"`

Adds `TestRelayV2_StreamNewSessionRotatesAndRestartsFresh` — the stream twin of
the PTY `TestRelayV2_NewSessionRotatesOnDisk`. Proves, live and end-to-end, that
`new_session` rotates the session id and restarts the bound runner **fresh**
(a process re-spawn, never a typed `/clear`) under
`interactive_runner:"stream-json"`. The production it exercises —
`Pool.RotateForNewSession` (#1125), `(*streamsup.Runner).RestartFresh` (#1124),
`startFreshRunner`'s type-switch dispatch (#1125) — was already built,
unit-tested, and security-reviewed; this ticket adds no production surface.
Rides the harness (`StartStreamInteractiveWithRelay`, #1141) and the fakeclaude
stream-json mode (#1140).

## Implementation

- `internal/e2e/relay_v2_stream_new_session_test.go` (new, `//go:build e2e`).
  Five ordered milestones, each an acceptance criterion:
  - **M1** — pre-rotation baseline: `send_message` #1 drains to a phone-side
    `assistant_delta` (the #1141 send test verbatim), then asserts the
    bootstrap registry id via `waitForBootstrapID` (non-vacuity for M2).
  - **M2** — on-disk rotation: bounded re-send of `sendNewSessionFrame`
    (mirrors `relay_v2_new_session_test.go`'s actuation loop) until
    `waitForBootstrapIDChange` observes a new `uuidStemPattern`-shaped id with
    a later `LastActiveAt`. `startFreshRunner`'s stream arm is a single path
    (`rotate` then `RestartFresh` with the same id), so a persisted rotation
    is proof the runner restarted fresh, not just that the pool was rekeyed.
  - **M3** — client observes the rotation: drains phone envelopes to a
    `protocol.TypeSessionTransition` with `Reason == "clear"`,
    `NewSessionID == post.ID`, `PreviousSessionID == initialUUID` — the
    phone-side broadcast from `notifyTransition(ReasonClear)`.
  - **M4** — the fresh child serves a subsequent turn: `send_message` #2 acks
    (proving `Route` resolved the rebound `CurrentSessionID` to a pool hit),
    then polls the fakeclaude stdin log for the turn's bytes. Deliberately
    does **not** drain a phone-side `assistant_delta` for turn #2 — see below.
  - **M5** — no `/clear`: the stdin log (a) contains a user-turn marker
    (non-vacuity) and (b) never contains `/clear`.
- `internal/e2e/internal/fakeclaude/main.go` (small additive change): the
  stream-json branch now tees `os.Stdin` through `io.TeeReader` to
  `PYRY_FAKE_CLAUDE_STDIN_LOG` when that env is set — same open flags
  (`O_WRONLY|O_APPEND|O_CREATE, 0o600`) and per-write `Sync` as the existing
  PTY `startStdinReader`, via a new `syncWriter`. The tee lives at the
  `main()` call site so `runStreamJSON`'s signature is untouched — the #1140
  unit test and the #1136 interrupt rider stay byte-identical when the env is
  unset (which they always are). This is the runtime oracle for M5. Full
  detail: [features/fakeclaude-binary.md § Stream-path stdin tee](../features/fakeclaude-binary.md#stream-path-stdin-tee-pyry_fake_claude_stdin_log-1137).

## The post-rotation drain divergence (why M4 doesn't drain a delta)

The stream turn-drain gate (`stream_turn_drain.go`) forwards an event only
when the producing runner's sink tag equals the active conversation's bound
session id. The sink tag is fixed at runner **construction**
(`sinkFor(cfg.SessionID)`); `RestartFresh` re-spawns the child in place and
never rebuilds the runner/Parser/sink, so it stays tagged `initialUUID`
forever. `RotateForNewSession` rebinds `conv.CurrentSessionID` to the new id.
So for any turn issued after a stream rotation, `env.sessionID != active` and
its `assistant_delta`/`turn_end` are dropped at the gate — never reaching the
phone. Asserting a phone-side delta at M4 would hang, not fail cleanly. This
is a **known, already-tracked production gap** — see
[streamsup-package.md § Known gap: frozen sink tag vs. new_session rotation](../features/streamsup-package.md)
and follow-up **#1133** (open, filed ahead of this ticket's merge: re-tag the
drain sink on `RestartFresh`). #1137 is the live confirmation of that gap's
fail-closed shape (dropped, not misdelivered) and proves the boundary (M4's
stdin-log check) is the correct workaround until #1133 lands — not a
production fix in itself.

## Patterns established

- **Rotation observable is on-disk + phone-broadcast, not fake-minted.** The
  PTY `new_session` e2e watches the fake self-rotate its `<uuid>.jsonl` and the
  fsnotify watcher follow it. On the stream path the daemon mints the id
  itself (`RotateForNewSession` → `NewID()` → `saveLocked`); the fake plays no
  part and keeps its cosmetic `"fake-stream"` literal. Any future stream
  rotation e2e should look at the registry + `session_transition`, not at
  fake-side session-id plumbing.
- **A single dispatch path turns an on-disk assertion into a whole-mechanism
  proof.** Because `startFreshRunner`'s stream arm calls `rotate` then
  `RestartFresh(newID)` unconditionally in one place, M2's on-disk check
  (cheap, deterministic) stands in for asserting `RestartFresh` ran directly
  — reusable reasoning for any stream ticket that wants a strong proof from a
  weak-looking observable.

## Lessons learned

From the PR body (developer-flagged):

> M4's "serving a subsequent turn" is proven at the fake-stdin boundary, not a
> phone-side delta: on the opt-in stream path a post-rotation turn's delta is
> dropped at the turn-drain gate because the runner's sink keeps its
> construction-time tag while the conversation rebinds to the new id
> (`RestartFresh` re-spawns in place, never rebuilding the sink). Asserting a
> delta would hang. This is a latent production gap in the still-under-
> construction stream path — a candidate follow-up ticket (re-tag the drain
> sink on `RestartFresh`), separate from `new_session` routing.
>
> Capturing `post` as the *first* registry id change keeps M3 robust: its
> owning `session_transition` is the rotation from `initialUUID` even in the
> rare double-actuation case (matching on `NewSessionID == post.ID`).

The recommended follow-up ticket was already filed as **#1133** before this
PR merged, so no new production ticket is needed from this pass.
