# Ticket #833 — persist per-session model / effort / YOLO and launch claude with them

Sessions now hold their own model, reasoning-effort, and YOLO (bypass-permissions)
settings, persist them in `~/.pyry/<name>/sessions.json`, and honour them at the
`claude` spawn. This is the storage + spawn **primitive** the wire setter (#826b)
and reader (#826c) build on — no wire message ships here. Split from #826.
`security-sensitive` (YOLO can enable `--dangerously-skip-permissions`).

## Implementation

All in `internal/sessions`, four production files, ~70 LOC:

- **`registry.go`** — `registryEntry` gains `Model string`, `Effort string`,
  `YOLO bool`, all `json:"...,omitempty"`, following the exact pattern
  `Bootstrap`/`LifecycleState` already established. Empty Model/Effort mean
  "inherit the daemon template"; `YOLO`'s zero value (`false`) means permissions
  enforced. No new decoder — the existing lenient `loadRegistry` `json.Unmarshal`
  already gives missing keys their zero value and a malformed value (e.g.
  `"yolo": "maybe"`) already fails the whole parse.
- **`session.go`** — new exported `SessionSettings{Model, Effort string; YOLO bool}`
  (the seam #826b/#826c consume) and the pure helper
  `claudeSettingsArgs(s SessionSettings) []string`: model → `--model <x>`,
  effort → `--effort <x>`, `YOLO==true` → `--dangerously-skip-permissions`
  (deterministic order; zero value → `nil`). `Session` gains an unexported
  `settings SessionSettings` field, immutable post-construction, read under
  `Pool.mu` (same discipline as `label`).
- **`pool.go`** — both spawn-config assembly sites apply
  `claudeSettingsArgs`:
  - `New` (bootstrap): reads `entry.Model/Effort/YOLO` in the warm-start branch
    (cold start leaves the zero value), then
    `ClaudeArgs: append(slices.Clone(cfg.Bootstrap.ClaudeArgs), claudeSettingsArgs(settings)...)`.
    The `slices.Clone` is new — today's code aliased `cfg.Bootstrap.ClaudeArgs`
    directly, which can't be true once the field is appended to.
  - `buildSession` (minted): gains a `settings SessionSettings` parameter,
    appends `claudeSettingsArgs(settings)` after `--session-id`, stores
    `settings` on the returned `Session`. `CreateIn` and `GetOrCreateIn` (the
    two call sites) both pass `SessionSettings{}` — #826b is what plumbs real
    values through the mint path.
  - `saveLocked` copies `s.settings.{Model,Effort,YOLO}` into the outgoing
    `registryEntry`, read under the already-held `Pool.mu` (not `lcMu` —
    settings is immutable, unlike `lcState`).
- **`get_or_create.go`** — one-line call-site update: `buildSession(id, label,
  spawnDir, SessionSettings{})`.

**Byte-identical argv for existing sessions (AC #5).** Both `claudeSettingsArgs`
call sites append to a *cloned* slice; the zero-value `SessionSettings` produces
a `nil` append, so a session that never sets anything spawns with the exact
argv it did before this ticket.

**Only the bootstrap round-trips end-to-end across a restart.** `Pool.New` only
ever re-materialises the bootstrap entry from disk (a pre-existing limitation —
see [ADR 016](../decisions/016-bootstrap-ignores-persisted-lifecycle-state.md)).
For minted sessions the round-trip this ticket proves is at the registry
serialization layer only (`saveLocked` → `loadRegistry` → identical struct),
not a live re-spawn — there is nothing in the daemon that re-spawns a minted
session on restart yet.

**Bootstrap ignores `lifecycle_state` but honours `settings` — these are
orthogonal, not a contradiction.** `lifecycle_state` is per-process ([ADR
016](../decisions/016-bootstrap-ignores-persisted-lifecycle-state.md)); spawn
settings are the operator's persisted intent and must survive restart. `New`'s
warm-start branch now does both: force `lcState = stateActive` while reading
`entry.{Model,Effort,YOLO}` verbatim.

## Fail-safe design (security)

See [ADR 030](../decisions/030-plain-bool-failsafe-persisted-flag.md) for the
full rationale. Summary: `YOLO` is a plain `bool`, not `*bool` and not backed by
a custom decoder. Absence of the key, and absence of the flag in
`claudeSettingsArgs`'s output, are the same zero value doing double duty as the
fail-safe default — there is no "disable bypass" flag to forget to emit.
Corruption (wrong JSON type) fails the whole registry load rather than
partially decoding, so `New` refuses to start rather than silently guessing.
Model/effort values on this path are operator-trusted (local 0600 registry,
`exec.CommandContext` argv — no shell, no injection surface); validating
*wire-supplied* (untrusted) model/effort is explicitly deferred to #826b, which
crosses that trust boundary.

## Lessons learned

*(Lifted from the PR's own Lessons learned section.)*

- The bootstrap warm-start path already had a deliberate split — it *ignores*
  persisted `lifecycle_state` (per-process, [ADR
  016](../decisions/016-bootstrap-ignores-persisted-lifecycle-state.md)) but
  must *honour* persisted spawn settings (operator intent). Keeping these two
  reads orthogonal in `New`'s warm-start branch (one forced, one copied
  verbatim) avoided conflating "process restarted" with "operator changed
  their mind."
- The end-to-end spawn-argv assertion extends the `pool_spawndir_test.go`
  recorder idiom to dump `"$@"` plus a `done` sentinel written with shell
  builtins only (no external `mv`), so a reader can tell "not written yet"
  apart from "wrote an empty argv" — the latter is exactly the AC #5
  byte-identical baseline this ticket had to prove a negative about.

**Incidental diff noise:** the code-review auto-commit swept in a regenerated
`internal/e2e/realclaude/testdata/permission_protocol_v2.1.199.json` (random
`session_id`/`uuid`/timestamps/tmp paths from an unrelated realclaude e2e run).
Reverted to `main`'s blob in this documentation commit — the same recurring,
harmless churn noted on #813/#830/#831.

## Out of scope

- Any wire message / verb — setter is #826b, reader is #826c.
- Reloading non-bootstrap sessions on daemon restart (pre-existing limitation,
  not introduced or fixed here).
- Rebuilding a running session's supervisor when settings change (#826b).
- Validating untrusted (wire-supplied) model/effort values (#826b — the ticket
  that actually crosses that trust boundary).
- On-disk field name `yolo` vs `bypass_permissions` — kept `yolo` to match
  ticket/PO vocabulary; a wire-layer alias is #826c's call if needed, not an
  on-disk rename.
