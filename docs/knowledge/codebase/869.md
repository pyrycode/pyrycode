# Ticket #869 — bound the per-conversation inbound backlog; reject-with-retryable on overflow

Implements the inbound-bound mitigation [#704](704.md)'s spec-stage security review flagged as a genuine SHOULD-FIX and deliberately deferred until the live `send_message` wiring ([#721](721.md)/[#722](722.md)/[#723](723.md)) landed. That wiring shipped, so this ticket closes the asymmetry between the carefully-bounded outbound side (`eventring`, `pushQueue`) and the previously-unbounded inbound `msgqueue` backlog: a paired phone with a retry loop or an app bug could grow `convs[convID].items` without limit — worst case exactly when the daemon is least healthy (claude wedged, the drain retrying the head at `RetryInterval` forever). `security-sensitive` — a new reject/drop-policy gate on the inbound, untrusted, phone-originated content surface.

## Implementation

Two production files, both edits additive (no signature change):

| File | Change |
|---|---|
| `internal/msgqueue/queue.go` | `defaultMaxQueuedPerConversation = 100` const (same posture as `defaultRetryInterval`); `Config.MaxQueuedPerConversation int` (`<= 0` ⇒ default, resolved in `New`, so `cmd/pyry/main.go` needs no change); `Queue.max int`; `Enqueue` gains a cap check (`q.max > 0 && len(c.items) >= q.max`) inserted *before* id-assign/append — pure early return, `0` returned, no `nextID` bump, no append, no `notify`, no drain spawn. |
| `internal/relay/handlers/send_message.go` | `msgSendMessageBacklogFull` static message const (mirrors `register_push_token.go`'s `msgBinaryBusy`); the enqueue-then-ack tail gains an `id == 0` branch that logs `conn_id`/`conversation_id`/`message_id` (never `payload.Text`, never a `queued_msg_id` — none assigned) and replies `replyError(ctx, c, env, protocol.CodeServerBinaryBusy, msgSendMessageBacklogFull, true)` without acking. |

- **Reject signal reuses the `uint64` return, `0` sentinel.** Ids are `≥ 1` today and there is exactly one production caller (`send_message.go`), so the reject rides an already-impossible id value instead of a `(uint64, error)` signature change — zero cascade across the ~45 existing `Enqueue` call sites. Documented on both `msgqueue.Enqueue`'s doc and the consumer-side `Enqueuer` interface doc, preserving the "handlers/ imports no `internal/msgqueue`" discipline.
- **Count basis is `len(c.items)`** — the whole in-memory backlog *including the in-flight (draining) head* (peek-not-pop keeps the head in `items` until `advanceLocked`). This is the same basis `Snapshot`/`queue_state` report, so the cap, `Snapshot`, and `queue_state` all agree on "backlog size."
- **Error code reuses `protocol.CodeServerBinaryBusy`** ("server.binary_busy"), not a new `queue.full` code — the AC calls for "the existing server-busy retryable shape," and from the phone's side the action is identical (retry later). A distinct code was considered and deferred (spec § Open questions): a one-line follow-up if backlog-full telemetry is ever wanted.
- **Cap check executes under the existing `q.mu` hold** — no new lock, no new goroutine. Read-then-append is one lock hold, so there is no TOCTOU on `len(c.items)`; concurrent `Enqueue`s serialize on `q.mu` and cannot both append past the cap.

## Patterns established

- **Reject-never-drop is the inbound mirror of ADR 025's "control never drops."** Outbound bounds (`eventring`, `pushQueue`) use class-aware *drop* policies because outbound is daemon-generated and reconstructable; inbound is user content, so overflow must *reject* the new item and tell the sender to retry, never silently drop the new message and never evict the oldest. This is the "different fabric" deterministic safety net (a cheap `len` comparison) mirroring the already-deterministic outbound bounds — not a speculative defense.
- **`defaultRetryInterval`-posture knob**: a package const default overridable via an additive `Config` field resolved in `New`, with the fallback living in `New` so existing `cmd/pyry` construction is untouched. Same shape #704 already used for `RetryInterval`; this ticket reuses the idiom verbatim for `MaxQueuedPerConversation`.
- **A rejected enqueue consumes no id** — accepted ids stay dense. This matters because `Remove` freeing a slot lets the next `Enqueue` succeed and continue the sequence without a gap; verified by a dedicated test (`TestQueue_RejectConsumesNoID_RemoveFreesSlot`).

## Testing

`internal/msgqueue/queue_test.go` (+149 LOC): cap enforced at `Enqueue` (ids `1, 2, 0`), reject-never-drops (`Snapshot` untouched, accepted messages still drain in order, rejected one never delivered), cap is per-conversation (filling A never blocks B), reject consumes no id (`Remove`-frees-slot then next `Enqueue` continues the dense sequence), and a regression guard that the default cap (100) resolves correctly and the existing ~45 call sites' small backlogs never reject.

`internal/relay/handlers/send_message_test.go` (+80 LOC): `fakeEnqueuer` extended with a `reject` mode; new test asserts the retryable `server.binary_busy` envelope, no ack, `Enqueue` called exactly once (the reject is *at* the enqueue point, not before it — unlike the pre-existing unknown-conversation/no-bound-session reject arms), and via a capturing logger that the reject log carries `conversation_id`/`message_id` but never `payload.Text`.

`go test -race ./...` and `go vet ./...` pass; `go build ./cmd/pyry` builds. Code review: **PASS**, one NIT (the `q.max > 0 &&` guard is currently unreachable dead code since `New` always resolves `max` to `≥ 1` — intentional future-proofing per spec, no change requested).

## Lessons learned

- Preserving the `uint64` return arity (reject = `0`) instead of widening to `(uint64, error)` avoided touching any of the ~45 existing `Enqueue` call sites — confirmed by the PR body's own lessons-learned note. When a signature change would ripple across dozens of test call sites but the domain already has an unambiguous "never valid" sentinel value, prefer the sentinel over the idiomatic Go error-return.
