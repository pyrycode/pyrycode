# Ticket #1284 — The staging-gate outcome tier and the rule that an unstaged run is never classified

Adds `internal/e2e/realclaude/finding_staging_gate_test.go` (790 lines, purely
additive). `trailClassifyRun` (#1271) owns one probe run's outcome over a
closed set of eleven values, but it *assumes the run staged* — that a Bash
call was issued, that it was the rig's hold command, that the rendezvous
completed. This ticket builds the tier below it: seven `finOutcome*` staging
outcomes and the gate that decides among them from synthetic conditions
alone, so a run that never staged can never reach the classifier and be
published as `trailOutcomeNoRowMatched` — a real answer, but a false negative
wearing an answer's label when nothing was ever measured. Split from #1278;
offline, `e2e_realclaude` build tag, no live claude or credentials.

## Implementation

- **Seven outcomes, six failures and one pass-through, in their own `stage-`
  sub-namespace** distinct from the eleven's `run-` prefix, for the reason
  `trail_run_outcome_test.go:108-113` gives for its own third namespace: a
  copy-paste between near-identical value spaces must read as a visible
  mistake. **The pass-through (`finOutcomeReadyToClassify`) is deliberately
  not the zero value** — if it were `""`, an unfilled `finOutcomeResult` would
  read as "staged fine, go classify it," the one direction this tier must
  never fail in. `TestFinOutcomeConstantsAreClosed` pins pairwise distinctness,
  non-emptiness, the pass-through's non-zero-ness explicitly, and that the
  zero `finOutcomeResult` reads as none of the seven.

- **`finOutcomeStagingGate(finOutcomeStaging) finOutcomeResult` is pure** —
  same no-exec/no-clock/no-filesystem/no-`*testing.T` contract as `trailGate`,
  `trailClassifyRun`, `trailAdmitAttribution` and `tdnClassifyReapLog`. Arm
  order is most-upstream-first and load-bearing at two points: identity before
  behaviour (a wrong issued command is reported as "not the staged command,"
  not as "the trigger didn't fire," even though both are literally true) and
  instrument failure before its result (`pinScanArgv` returns the zero
  `pinScan` on error, so an errored scan must be reported as an errored scan,
  not as a count of zero).

- **Two guard conditions close two reachable pass-through holes.**
  `IssuedCommand != StagedCommand || StagedCommand == ""` — without the
  second clause, a caller who fills every bool but leaves both command
  fields empty gets `"" == ""` → equal → pass-through. `PinMatchCount !=
  PinWantCount || PinWantCount < 1` — without the second clause, an unfilled
  want agrees with an unfilled match count at zero and again reaches the
  pass-through. Both are mutation-tested in the PR (dropping either clause
  reddens its dedicated fixture row).

- **The structural closure AC4 asked for is the signature itself.**
  `finOutcomeStagingGate` neither takes nor returns a `trailRunReadings`, and
  `finOutcomeResult` has no field either is reachable from — a failure arm
  holds nothing a `trailClassifyRun` call could be made from; the forbidden
  call is unwritable, not merely discouraged. Because a test can't express an
  unwritable violation, `TestFinOutcomeFailuresAreNotRunOutcomes` pins the
  observable consequence instead: `trailIsRunOutcome` rejects all six failure
  values and the pass-through itself.

- **`finOutcomeStaging` is INPUT ONLY — NEVER PUBLISHED**, and is the one
  record in the file with no `json` tags, stated as load-bearing rather than
  incidental (every sibling record in this family states its content rule at
  the type; this one states the converse). Both `IssuedCommand` (verbatim
  model output) and `StagedCommand` (rig-authored but embeds a `t.TempDir()`
  path and an `exec.LookPath` result, `trail_run_rig_test.go:506-556`) are
  captured strings on the same footing, and the two are compared as opaque
  bytes only — never parsed, split, shell-lexed, path-resolved or executed.

- **No Detail interpolates either command, in any form.** Arm 2's Detail
  (command-not-staged) is a fixed sentence with no interpolation site for
  either operand — naming "which operand differed" is one edit from naming
  its bytes. `trailDetail` is reused for the 512-byte cap (no `finDetail`
  twin, per #1280's already-settled argument).

- **`TestFinOutcomeResultCarriesNoCapturedBytes` plants `trailNeedle` in
  *both* commands**, across every fixture row, and — the ticket's own named
  hazard — asserts a per-row headroom bound
  (`reachMaxCommandBytes - len(Detail) >= len(planted)`) before checking
  containment. This is required because a short plant is necessary but not
  sufficient: house-style Detail prose alone ran 446-500 bytes in the first
  draft, leaving only 12-66 bytes of headroom against an ~85-byte plant, and a
  mutation that actually interpolated a command into a Detail **passed** —
  the cap truncated the needle away before `bytes.Contains` ever ran. See
  Lessons learned below.

- **Test coverage — six top-level functions, 0 SKIP**
  (`go test -race -tags e2e_realclaude -run '^TestFinOutcome' -v`, confirmed
  in code review: 79 offline specs pass, 46 live specs skip for lack of
  credentials, unrelated to this ticket). `TestFinOutcomeStagingGate` is
  table-driven over eleven shared fixture rows (`finOutcomeGateCases()`),
  reused by three tests so all three sweep the gate's real value space rather
  than three hand-kept lists that could drift; a coverage map asserts all
  seven values were reached. `TestFinOutcomeSpacesAreDisjoint` checks both
  directions — the seven against `trailIsRunOutcome`, and the shipped eleven
  (`trailRunOutcomeValues()`, not hand-copied) against `finOutcomeIsValue`.
  Prefix census clean: `finOutcome[A-Z]` was 0 before this file, 18 after, all
  in-file; control `trail[A-Z]` 880, non-zero.

## Patterns established

- **A redaction test's non-vacuity has two independent failure sources, and
  both must be closed.** The spec's security review anticipated the fixture
  side (a long *planted* command pushing the needle past the cap). The
  developer found the symmetric hazard on the *prose* side (a capped Detail
  with too little headroom truncates the needle before a leak reaches it,
  even with a short plant). The durable fix asserts headroom per row on the
  output, not just plant length on the input — `reachMaxCommandBytes -
  len(got.Detail) >= len(planted)` — with a failure message that redirects
  long-form argument into the arm's own comment, where no cap applies.
- **Mutation-test the redaction check itself, separately from the logic
  guards.** In this PR the two guard-clause mutations (dropping either `||`
  clause) both went red on the first run; the leak mutation — the one
  guarding the actual security property — was the one that silently passed
  until the headroom assertion was added. A no-captured-bytes test is exactly
  the kind that looks correct while proving nothing.
- **A flat, two-scalar-field record is exactly where a top-level
  `map[string]json.RawMessage` key scan is valid**, per #1280's own
  structural-check finding (a nested `Entries []finAttributeEntry` record
  needed per-entry scanning; this ticket's `finOutcomeResult{Value, Detail}`
  does not). Stated explicitly in the test's own comment as the reason the
  transplant is safe here.

## Lessons learned

From the PR body (#1289):

- **A capped `Detail` helper can make a redaction test vacuous from the
  *prose* side, not just the fixture side.** House-style Details (446-500
  bytes) left only 12-66 bytes of headroom against an ~85-byte planted
  command in the first draft; a mutation that deliberately interpolated
  `IssuedCommand` into a Detail passed, because the cap truncated the needle
  away before `bytes.Contains` ran.
- **The durable fix asserts headroom per row, not prose length once.**
  `reachMaxCommandBytes - len(got.Detail) >= len(planted)` fails naming the
  arm and points at the arm's comment as where long-form argument belongs.
  Shortening prose once would have re-vacuated on the next edit that
  lengthened a Detail.
- **Mutation-test the redaction check itself.** The two guard-clause
  mutations went red immediately; the leak mutation — guarding the actual
  security property — was the one that silently passed on the first attempt.

## Code review

**PASS**, three NITs, none blocking:

- The arm-5-over-arm-6 order row (`erroredAndMiscounted`) is byte-identical
  to the plain `scanErrored` row — both set `PinScanErrored = true` and
  `PinMatchCount = 0` against the base's `PinWantCount = 2` — so the table's
  eleven rows carry ten distinct inputs. The ordering is still pinned (twice
  over), and the collision is a defensible side effect of the fixture
  correctly zeroing the match count for producer fidelity
  (`pinScanArgv` returns the zero `pinScan` on error). Worth collapsing the
  two rows or noting the coincidence in the order row's own comment.
- `finOutcomeStagingGate(tc.in)` is called twice per table row (once inside
  the subtest, once outside to fill the coverage map). Harmless — the gate is
  pure — but reading `got.Value` from inside the closure would keep the
  coverage map fed from the same call the assertions ran against.
- The planted-length premise check ranges a `map[string]string`, so if both
  fixtures were ever over the cap only one failure would be named, chosen by
  map order. A slice would make the failure deterministic; only reachable in
  the already-failing case.

Verification performed and confirmed independently in review: the structural
closure (grep confirms no non-comment reference to `trailRunReadings` or
`trailClassifyRun` anywhere in the file); the AC5 headroom claim, measured
per arm (239-399 bytes of Detail against the 512-byte cap, 113-273 bytes of
headroom, all comfortably above the 87-byte planted command); reuse over
rebuild (`trailDetail`, `trailRunOutcomeValues()`, `trailNeedle`,
`trailIsRunOutcome` all called, none re-derived); and a cross-branch
namespace sweep confirming no collision with any in-flight sibling ticket.
