# Ticket #1175 — realclaude/stream: permission DENY round-trip against live claude

Adds the real-claude counterpart of the fake-tier deny proof (#1139): the
**security-relevant half** of the remote permission round-trip on the
production stream-json runner. Every prior stream permission spec (#1154) only
proved **allow**; a permission denial that silently *executed* the gated tool
anyway (fail-open), or a turn that *hung* on the denied modal, is exactly the
real-claude-specific failure the fake tier cannot surface (the fake-green/
real-red class, #949). Security-sensitive ticket — architect security review
verdict **PASS**. Split from #1083 (T9); sibling leaves are #1173 (multi-turn
continuity) and #1174 (new-session rotation).

## Implementation

- `internal/e2e/realclaude/interactive_stream_permission_deny_test.go` (new
  file, `//go:build e2e_realclaude`, PR #1183). Test-only, zero production
  files, no edits to any existing file.
- `TestInteractiveStreamPermissionDeny` reuses #1154's
  `startStreamModalResolutionHarness` verbatim (no new harness, no new seeded
  UUIDs — the two tests never share on-disk state and the suite runs
  sequentially). Flow: `raiseRealPermissionModal` (#1030) raises a genuine
  `Write` permission modal via `writeFileTrigger` and asserts
  `modal_shown{class=permission}` with a non-empty `modal_id` before any
  answer is sent (AC4 non-vacuity) → seal a `reject_once` answer (the only
  wire-shape delta from #1154's `allow_once`) → drain to `modal_dismissed` and
  assert `Source == "remote"` + `Outcome == "reject_once"` (the attribution
  check, see below) → drain to terminal `turn_state{idle}` → walk the daemon
  workdir for `pyrycode-<nonce>.txt` and assert absence (AC2, fail-closed
  observable).
- **Attribution is the load-bearing addition over a naive allow→deny clone.**
  "File absent + turn idle" is *also* the outcome of a timeout-deny
  (`ModalDismissedPayload.Source == "timeout"`, the #725 approval timer) or a
  dropped/gate-rejected answer — neither proves *our* explicit reject did
  anything. Asserting `Source == "remote"` + `Outcome == "reject_once"` on the
  `modal_dismissed` pins the fail-closed proof to this ticket's specific
  answer, not to some other denial path. Called out as a core AC in the
  architect's security review, not a nicety.
- Rework (`625222d`, after an operator live-gate FAIL): the original design
  called for a single-answer `drainForTurnIdle` (idle-only, no required
  continuation delta — real claude's post-denial continuation is
  non-deterministic, unlike allow's guaranteed reply). The live run showed
  real haiku **retries a denied tool at least once** — a second, distinct
  `tool_use` reissuing the `Write` — so the single-answer flow left that
  retry modal unanswered and the turn hung until the daemon's own approval
  timeout fired. The fail-closed security property held throughout (the
  retry was denied too, once answered); this was purely the test's
  terminating condition. Fix: replaced `drainForTurnIdle` with
  `denyModalsUntilIdle`, which rejects **every** `modal_shown{permission}`
  the turn raises — fresh `reject_once` + fresh `AnswerToken` + fresh reqID
  each time — until terminal `turn_state{idle}`, bounded on two independent
  axes with distinct diagnostics: `maxRetryDenies` (4, a product-question cap
  — "does a fully-denied turn ever terminate" — not a flake to widen) and
  `perTurnReplyBudget` (wall-clock, a daemon-stall diagnostic). Asserts
  `Source == "remote"` on **every** dismissal in the loop, not just the
  first, so a timeout-deny can't masquerade as the explicit reject at any
  retry.
- `requireTriggerFileAbsent(t, workdir, nonce)` walks (not a single
  top-level `os.Stat`) the daemon workdir for `pyrycode-<nonce>.txt` —
  belt-and-suspenders in different fabric from the stochastic
  `modal_shown` gate: the walk is cheap deterministic code guarding against
  claude choosing a sub-path under the workdir, and the nonce is unique per
  run so it cannot false-match another file.

## Patterns established

- **A deny test cannot reuse an allow test's "delta-then-idle" drain.**
  Real claude's post-denial continuation is non-deterministic — it may or may
  not emit a substantive delta — so a deny drain must key on terminal
  `turn_state{idle}` alone and tolerate zero-or-more deltas. Requiring a
  delta (as the allow-side `drainForCompletedTurn` does) would flake a deny
  spec. Applies to any future spec proving a rejection/failure path rather
  than a success path.
- **"Absence + idle" alone is a vacuous proof for any deny test; pin it with
  a `Source`/`Outcome` attribution assertion on the dismissal event.** The
  passing outcome of a genuine explicit-reject and of a timeout-deny (or a
  silently-dropped answer) look identical from the outside (file absent,
  turn eventually idle). Any spec proving "our explicit action caused this
  fail-closed behaviour" needs to assert the resolution's `Source`/`Outcome`
  fields, not just the downstream absence/idle observables.
- **When real claude retries a denied tool, the retry-answering loop must be
  bounded on two independent axes with distinguishable diagnostics** — a
  retry-count cap (a product question: does this ever terminate?) separate
  from the wall-clock budget (a hang/stall diagnostic). Conflating them into
  one timeout loses the ability to tell "claude never stops retrying" from
  "the daemon stalled."

## Lessons learned

- (from the PR body, first pass) A DENY e2e cannot reuse an ALLOW test's
  "delta then idle" drain — see "Patterns established" above.
- (from the PR body, first pass) "File absent + turn idle" is a shared
  outcome with timeout-deny and dropped-answer paths — a deny test needs the
  explicit `modal_dismissed{source=remote, outcome=reject_once}` attribution
  assertion, or it greens vacuously.
- (from the rework) Real claude retries a denied tool at least once (haiku
  reissued the `Write` as a second distinct `tool_use` after the first
  reject) — any deny-then-idle drain must answer every retry modal, not just
  the first, bounded on retry-count and wall-clock as two distinct
  diagnostics.
