# Ticket #1118 — robust shared argv-record wait for the ACP interactive-spawn tests

Three `cmd/pyry` ACP tests (`TestACP_SessionNew_SpawnsOneInteractiveClaude`,
`TestACP_SessionLoad_ResumesExistingClaude`, `TestACPConformance_FullSessionDrive`) polled the fake
claude's argv file with a hardcoded `3 * time.Second` deadline, duplicated at two sites in
`acp_test.go`. The fake claude (`/bin/sh`) writes its argv to `argvFile` only *after* the pool spawns
it through the PTY/service-mode path, so the test side bridges that gap with a poll. Under
full-`make check` fork/exec contention the QA failing runs clocked ~3.03–3.07s — a hair past the
3s boundary — producing a load-sensitive flake (`fake claude never recorded its argv`), not a
product defect. Same failure shape and unmasking circumstance as [#1116](1116.md): QA hit this set
while validating PR #1117, confirmed pre-existing on both `main` and `feature/1116` before this
ticket was filed to fix it. Test-only; zero production change.

## Implementation

- **`argvRecordTimeout = 15 * time.Second`** (`cmd/pyry/acp_test.go`) — single named constant
  replacing both hardcoded `3 * time.Second` literals. ~5× the observed ~3.07s worst-case near-miss;
  1.5× the largest sibling budget in the file (`pool.Ready()` at 5s, serve shutdown at 10s). Carries
  an inline WHY comment: the cost is asymmetric (too-tight → recurring flake masking regressions;
  too-generous → a slightly slower true-failure signal on the rare genuine never-spawn), so the
  budget errs generous. Not tied to `t.Deadline()` — that would let a truly-broken child hang to the
  whole-binary `-timeout` instead of failing cleanly.
- **Inline poll copy collapsed onto `waitOneClaudeArgv`.** `TestACP_SessionNew_SpawnsOneInteractiveClaude`
  had its own byte-for-byte duplicate of the poll loop; deleted in favor of
  `fields := waitOneClaudeArgv(t, argvFile)`. All three spawn tests (`acp_test.go:242`,
  `acp_test.go:664`, `acp_conformance_test.go:481`) now reach the wait through one path — the two
  sites can no longer drift apart.
- Correctness assertions untouched: the divergence-6 `>1`-line `t.Fatalf` and the
  `--session-id <uuid>` equality (after the `--settings` pair strip) fire exactly as before; only
  the deadline widened and the duplicate call site collapsed.
- **Option (b) rejected** — synchronizing on child readiness instead of polling. `WaitForPTY`
  (`internal/supervisor/supervisor.go:612`) signals *child-spawned*, which happens-before the
  shell's first `printf ... >> argvFile`; it cannot serve as the memory barrier for the argv write,
  so a bounded poll of the observable would still be needed downstream of it. Threading `pool`+`id`
  into the helper just to still poll the residual exec→first-write gap was judged disproportionate
  plumbing for a test flake.

## Patterns established

- **This is the same "readiness set upstream of the observable → bounded generous poll" answer as
  the #260 lesson** (`docs/lessons.md:356-359`, control-socket-dialability-lags-Phase-running).
  Confirms the lesson generalizes beyond its original e2e-status context to any
  spawn-then-observe-async-side-effect test. Contrast with [#1116](1116.md), where the observable
  *was* the child-spawn itself — there, `WaitForPTY` was the correct fix. The distinguishing
  question: is the thing you're waiting for the spawn, or something downstream of it? Spawn →
  `WaitForPTY`. Downstream of spawn (a file the child writes after starting) → poll.
- Confirms the "duplicated fixed-wait budget across ≥2 sites is a flake-drift smell, collapse to one
  named constant" habit already used for backoff/readiness values elsewhere in the test suite.

## Lessons learned

- Code review (PR #1119, PASS, no findings) validated the 15s value reasoning directly rather than
  treating it as an arbitrary magic number: worst-case-observed multiplier and sibling-budget
  comparison both check out, and the inline WHY comment was called out as the correct use of the
  project's "no comments unless non-obvious" carve-out — it pre-empts a future contributor
  "tightening" the budget and reintroducing the flake.
- QA's `make check` run confirmed all three named tests passed under full-suite contention on this
  PR — the pragmatic load-repro evidence the ticket's technical notes anticipated (a deterministic
  fails-on-main/passes-after proof isn't possible for a probabilistic-under-load flake).
