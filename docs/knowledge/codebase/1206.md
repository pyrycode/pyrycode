# Ticket #1206 — a per-child-exit seam on the streamsup runner

First of two split children of #1203 (mid-turn crash-clear). `internal/streamsup.Runner` had no way to
tell anything outside the package that a claude child died — the only escaping lifecycle state,
`PhaseStopped`, fires once, on permanent shutdown, and a crash-and-respawn is invisible everywhere else
(no pool transition, no `TurnEnd`, a dropped `system`/`init` line). This slice ships **only the seam**:
one new `Config.OnChildExit func()` field and one unconditional call in `Run`, with no production
consumer — the same order `Interrupt` (#1120→#1121) and `RestartFresh` (#1124→#1125) shipped in. #1207
(open, natively blocked-by this ticket) wires the first consumer: clearing the #1201/#1202 turn-busy
tracker on the one remaining path those two couldn't cover. See
[streamsup-package.md § Per-child-exit seam (#1206)](../features/streamsup-package-per-conversation-turn-busy-track-per-child-exit-seam.md#per-child-exit-seam-1206)
for the full mechanism writeup.

## Implementation

- **`internal/streamsup/runner.go`**: `Config.OnChildExit func()`, declared in the optional-field block
  next to `onSpawn` but **exported** (unlike `onSpawn`, which is unexported and settable only from
  in-package `_test.go` files — insufficient here since #1207's consumer lives in `cmd/pyry`). One
  unconditional `if r.cfg.OnChildExit != nil { r.cfg.OnChildExit() }` call sits between `uptime :=
  time.Since(start)` and `Run`'s post-spawn `if ctx.Err() != nil { return ctx.Err() }` — i.e. *above* the
  shutdown return and the `claude exited` log both. `spawnAndWait` returns at one point and the loop only
  then branches on why the child is gone (shutdown / deliberate restart / crash), so this single call
  covers all three exit paths without enumerating them. Fires unconditionally — including when
  `spawnAndWait` reports `started == false` (a pre-launch setup failure; no claude process ever existed) —
  which is why the doc comment's cardinality is "once per completed supervision iteration," never "once
  per child" or "once per child exit."
- **`internal/streamsup/runner_test.go`**: four new tests, no existing test modified. Crash-respawn
  (mirrors `TestRunner_RestartsOnCrash`, asserts ≥2 fires via a buffered channel), shutdown (`echo_lines`
  mode, exactly 1 fire — the load-bearing AC, since a fire anchored on the `claude exited` log reads 0
  here), deliberate restart (`record_block` mode, exactly 2 fires — one Restart-killed child, one
  shutdown-killed child), and spawn-setup failure (direct `&Runner{}` construction bypassing `New`'s
  `exec.LookPath`, asserts fire count *equals* attempt count exactly, pinning the unconditional-fire
  contract). `sync/atomic` is the only new import.

## Patterns established

- **The two "obvious" fire-site anchors for a "cover every exit path" AC are both wrong, and the reason
  is provable from the callee's own return sites, not from reading the loop top-down.** `spawnAndWait`
  returns from three places, all of which strictly post-date process death (a pre-launch error or a
  post-`cmd.Wait` return) — so any single call placed after that return, but before the loop's first
  branch, is provably safe and provably complete. Anchoring on the `claude exited` log (which sits below
  the shutdown return) or on a `ctx.Err()` return site (there are three; only one is in the actual fire
  window) each pass two of the three exit-path tests and silently fail the third. The general form: when
  a spec says "cover every path out of a loop," find the single choke point every path already funnels
  through before it branches, rather than instrumenting each branch separately.
- **A cardinality contract belongs on the doc comment, in words that stay true for the degenerate case.**
  The field is named `OnChildExit` (correct at the call site's reading level — a consumer wires
  `scfg.OnChildExit = func() { … }` and it reads right), but the comment states "once per completed
  supervision iteration," because "once per child" is false on the setup-failure path where no child ever
  launched. Name for the call site, comment for the precise contract — deliberate tension, not an
  oversight.
- **Exact-count assertions on a supervised-loop test are only non-fragile because of the fake-child mode
  table, not because the test looks deterministic.** `=1`/`=2` assertions hold only because `echo_lines`
  blocks on held-open stdin and `record_block` blocks on SIGTERM — neither self-exits. A fake-child mode
  with its own exit timer would make the identical test flaky; verify the chosen mode's self-exit
  behaviour before trusting an exact-count assertion built on it.

## Lessons learned (from code review, PR#1208 — PASS, 0 MUST/0 SHOULD, 1 NIT)

- **A "you may call any method from this callback" doc claim has two independent axes — deadlock-safety
  and semantic freshness — and only one is obvious.** The comment says the callback may call `Restart`,
  `RestartFresh`, `Interrupt`, `Stdin`, or `State` because no Runner lock is held at the fire site (true —
  `setIterCancel(nil)` released `restartMu` a line above). But `State()` at that point still reports
  `PhaseRunning` plus the *dead* child's PID (cleared to `PhaseBackoff` below the fire, and never cleared
  at all on the shutdown path), and `Restart()` called from inside the callback skips the backoff ladder
  entirely — the fire precedes `drainRestart()`, so the token it pushes drains on the same iteration. A
  "safe to call X" claim needs both axes checked — what X reads/writes, and whether that state has been
  updated *yet at this exact line* — not just whether X takes a lock the caller already holds. This was a
  NIT here (a documentation gap, no consumer yet to be misled), but the same check is a MUST FIX shape the
  moment #1207 or a later caller actually reads `State()` from inside the callback.
- **A call inserted into a loop can corrupt a local computed on an adjacent line, beyond what the AC
  states.** The fire sits one line after `uptime := time.Since(start)`; had it been placed one line
  earlier, a slow callback would inflate `uptime` and, through it, `bo.next(uptime)` — spuriously
  resetting the backoff ladder for a crash-looping child. The spec's chosen window happened to avoid this,
  but the AC never named the hazard. Placement correctness for the stated criteria doesn't guarantee
  placement correctness for an unstated one; check what a slow callback would read or corrupt near the
  call site, not just whether the call itself satisfies the AC.
