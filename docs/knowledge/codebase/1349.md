# Ticket #1349 — Probe rig: stage a live `agent-run` turn on the headless `PYRY_USE_STREAMJSON=1` path (offline)

`finLiveRunStage` (#1340) staged one live `pyry agent-run` turn hardcoded to
#1342's env delta (`PYRY_USE_STREAMJSON=0`, the ptyrunner default). #1353
wants the same rig pointed at the headless stream path. This ticket makes
the delta a parameter, ships the stream-path sibling delta plus its offline
trap, and re-derives the driver's doc comment — which argued its own
correctness from ptyrunner-specific facts in five places, one of them wrong
even on its own path. **No live claude is involved and no turn is staged.**

Three files touched, all `*_test.go`, zero production code:
`finding_live_staging_test.go` (the new delta and its trap),
`finding_live_run_test.go` (the parameter and the doc rewrite),
`finding_exit_path_probe_test.go` (the one call site, one-line change).

## Implementation

- **`finLiveStageStreamEnvDelta() []string`** returns
  `{"BASH_DEFAULT_TIMEOUT_MS=5000", "PYRY_USE_STREAMJSON=1"}` — this file's
  own two literals, never derived from `finLiveStageEnvDelta()` by clone,
  append or `slices.Clone`. The independence is the point: an edit to
  either delta must not silently change the other, and any derivation
  destroys exactly that. `finLiveStageEnvDelta` itself is untouched — the
  Technical Notes forbid renaming or re-homing it, and its own trap reads
  it at two sites.
- **`TestFinLiveStageStreamEnvDeltaNamesTheRunner`** is a sibling of
  `TestFinLiveStageEnvDeltaNamesTheRunner`, never a copy, and the spec is
  explicit that copying its comment would ship a false claim. The shipped
  trap's hostile ambient (`PYRY_USE_STREAMJSON=1`) discriminates **by
  construction** — the non-default value makes a nil-delta control read
  `streamrunner`, proving the assertion isn't vacuously true. The new
  trap's hostile ambient is `0`, and because `reachRunnerPathFromEnv`
  treats only the exact string `"1"` as truthy, an ambient of `0` is
  indistinguishable from unset. Its control therefore **excludes** an
  effective ambient of `1` (under which the nil-delta control would read
  `streamrunner` and go red before the claim is reached) but **cannot
  establish** non-vacuity by construction — the control passes identically
  if `t.Setenv` never ran. The test's own doc states both halves rather
  than inheriting the shipped trap's stronger claim. Both traps are red
  against each other by construction: the shipped one wants
  control=`streamrunner`/claim=`ptyrunner`, the new one wants the reverse,
  so any half-copy contradicts itself on the first assertion.
- **`finLiveRunStage(t *testing.T, envDelta []string) *finLiveRunHandle`**
  — the delta is now a parameter, reaching `spawnProbePyry` verbatim: no
  default, no nil-check, no package-level fallback. A silent default would
  hide the exact failure `reachRunnerPathFromEnv`'s own doc exists to
  surface (an empty delta reads the operator's ambient shell). The one call
  site (`finding_exit_path_probe_test.go:216`) becomes
  `finLiveRunStage(t, finLiveStageEnvDelta())` — unchanged behaviour, and
  its surrounding prose (the skip-guard argument at `:81-89`, the delta
  naming at `:188`) stays true precisely because this caller keeps passing
  the `=0` delta.
- **AC3's byte-identical claim is review-held, not offline-tested** — the
  driver cannot run without a Claude login, so nothing offline executes
  the call site. Code review re-did the comparison field-for-field against
  the shipped trap (`finding_live_staging_test.go:511-533`: `reachEnvDelta`
  containment, `finRecordEnvDelta()` containment, exact count) on both
  review passes rather than accepting the diff's own claim.

### The doc-comment re-derivation

AC4's test is whether a site's **recorded justification cites the runner
path**, not whether code branches on it — nothing in the driver branches,
so a branch-shaped reading would have answered "none" for a driver with
seven such sites, classified individually and fixed in place (never left
standing with a "but see below"):

- **Site A (skip guard)** — restated as a requirement on the *caller's*
  delta ("must name `PYRY_USE_STREAMJSON` explicitly") rather than a fact
  about one value, and the comment now separates the two mechanisms that
  make it true: the rig's own env-side precedence
  (`reachRunnerPathFromEnv`, trap-pinned offline) from `os/exec`'s
  last-wins `Env` dedup (stdlib behaviour nothing in this package
  exercises — cited from the shipped call-site prose rather than
  re-derived).
- **Site B (`cmd.Wait` goroutine) — the load-bearing correction.** The
  shipped reason ("claude runs on a PTY, so the held `cat` does not
  inherit pyry's stdout/stderr pipe write ends") was **wrong even on its
  own path**: `creack/pty`'s `StartWithAttrs` fills stdin/stdout/stderr
  with the tty only when nil, and `ptyrunner/runner.go:296` sets
  `cmd.Stderr = cfg.Stderr` *before* the PTY spawn — so claude's fd 2 is
  pyry's fd 2 on **both** runner paths, and the PTY covers the one fd
  claude never shares in the first place. What actually holds is a
  path-independent claude behaviour (its Bash-tool child gets
  claude-created pipes, not inherited fds), evidenced by the 2026-08-06
  live run. Split into two legs: leg 1 (the rig's own `Wait`) transfers
  unchanged; leg 2 is a **new stream-path-only hazard** — pyry's `Wait` on
  claude's stdout pipe (a pyry-created pipe on the stream path vs. the PTY
  slave on ptyrunner) — bounded by `cmd.WaitDelay = killGrace` (5s,
  `streamrunner/runner.go:44,:204`), well inside `probePyryExitGrace`
  (20s) and `finExitPyryExitDeadline` (120s). If it fires, the symptom is
  not a hang — `pyryExited` still closes — but a **distorted `ExitStatus`**
  on an otherwise-complete run, the same false-attribution class as the
  cleanup-ordering hazard the driver already guards, landing in a
  different field. Whether leg 2 actually fires is not decidable offline
  and is asserted neither way; #1353's first live run is where it gets
  measured.
- **Site C (turn headroom)** — `--max-turns=6` reaches claude by different
  routes (claude's own argv on the stream path, the pyry-side budget
  `Counter` on ptyrunner, which omits it from argv) but bounds the run
  identically on both; the comment now names both mechanisms.
- **Site D (no budget-fired run)** — the conclusion is unchanged and holds
  on both paths; the argument was ptyrunner-only (the budget hook's
  `Terminate`/reap-before-trailer shape) and is re-derived per path rather
  than left standing, since the stream path has no budget hook at all —
  its bound is claude's own `--max-turns`.
- **Site E (signature)** — "NO PARAMETERS BEYOND `t`" is now false by
  construction and is rewritten: exactly one varying input, everything
  else fixed.
- **Site F (permission posture, new prose)** — the stream path's sole
  caller passes `yolo=true` (`--dangerously-skip-permissions`); ptyrunner
  trust-marks the workdir and writes a deny-default settings file. The
  comment relays the repo's own recorded position (`--allowed-tools` is
  the authoritative gate under YOLO) rather than asserting equivalence —
  the flip changes the gate's mechanism, not, on the repo's position, its
  width. The same paragraph is duplicated onto the new delta's own doc,
  since that is where the choice is made.
- **Site G (session id producer) — surfaced by the security pass, not the
  ticket text.** The session id becomes a filename component
  (`jsonlPathFor` → `SessionJSONLPath`). On ptyrunner pyry mints it and
  passes `--session-id`; on the stream path claude mints its own (no
  `--session-id` in its argv) and the rig reads it unvalidated off stdout.
  Recorded as a delta-dependent site with no code change: the producer is
  the real claude CLI, the read target is inside the rig's own temp
  `HOME`, no failure has been observed, and a guard for an unobserved
  failure mode was rejected as the wrong trade at this tier.
- **`scan.MatchCount == 3`**, not named by the ticket, re-derived rather
  than inherited: it holds on both paths because `tdnClaudeNeedle`
  (`--append-system-prompt-file`) is emitted by both argv builders — not
  because of `reachRunnerPathFromArgv`'s framing of that flag as "the
  ptyrunner-shape marker", which names no runner and the comment now says
  so explicitly rather than resting on that framing.

Everything **not** delta-dependent (the FIFO rendezvous, the direct-child
wait, the pin's needles/exclusions, the cleanup order, the
`ExitStatus`-before-`close(pyryExited)` edge) is stated as such
individually rather than covered by "the rest is fine" — the spec calls
that aggregate reading the failure mode this section exists to refuse.

## Patterns established

- **A mechanism cited as "why a wait terminates" needs the resource it
  actually covers checked against the resource the property needs, not
  assumed from the mechanism's name.** "Claude runs on a PTY" sounds like
  it explains why claude's fds don't hold pyry's `Wait` open; in fact
  `pty.Start` only fills stdio slots left `nil`, so a `cmd.Stderr` the
  caller already set (as ptyrunner does) survives the PTY spawn untouched.
  The PTY covered the one fd claude never shared. Before crediting a
  mechanism with a property, name the specific fd/resource it touches and
  check that against the one the property is actually about.
- **Re-deriving a count that turns out unchanged is still worth doing —
  the citation can be wrong even when the number is right.**
  `scan.MatchCount == 3` holds on both runner paths, but the *reason* the
  shipped comment gave (a flag framed elsewhere as "the ptyrunner-shape
  marker") does not transfer; the flag is emitted by both argv builders
  and names no runner. Same number, different — and this time correct —
  citation.
- **A hostile-ambient control's honesty depends on which side of a
  one-sided truthiness rule it sits on.** `reachRunnerPathFromEnv` treats
  only the literal string `"1"` as truthy, so a control built around
  ambient `=1` discriminates by construction (the non-default value
  proves the delta, not the ambient, drove the result) while the same
  shape built around ambient `=0` cannot — `0` reads identically to unset.
  A sibling trap covering the opposite value has to state a *weaker*,
  honest claim rather than mirror the stronger one; copying the argument
  across the asymmetry ships a false statement of what the test proves.
- **When a diff shifts lines in files it edits, sweep inbound pointers by
  re-deriving from the current tree, not by applying a review's line-delta
  table.** The rework here hit exactly this: one citation the reviewer's
  table gave as `:447-479` actually needed `:455-487`, because a second,
  unrelated fix (the `t.Fatalf` inventory correction) added eight lines
  between the review comment and the fix commit. A table computed at
  review time is a snapshot; the fix has to re-read the target, not just
  apply the delta.

## Lessons learned

(From PR #1356's body and its two code-review comments.)

- **`pty.Start`/`StartWithAttrs` only fills stdio fds left `nil` — a
  `cmd.Stderr` already set by the caller is not displaced by the PTY
  spawn.** This is a `creack/pty` behaviour worth remembering anywhere a
  comment in this codebase cites "runs on a PTY" as the reason a
  particular fd is or isn't shared with a child: check what the call site
  set *before* the PTY spawn, not just whether a PTY is involved at all.
- **A filename-anchored `grep` for inbound citations misses bare
  self-references** (`:415-427` with no leading filename, inside the same
  file the shift happened in). The rework's sweep had to separately
  enumerate every bare `:NNN` reference in each touched file, not just
  `grep` for `otherfile\.go:\d+` — the worst-missed citation in this
  ticket was exactly that shape.
- **An "exact and stays exact" claim about a count is a fresh assertion,
  even when the count itself is old, pre-existing debt.** The `t.Fatalf`
  inventory the new prose introduced restated a known-stale undercount
  (already logged in `codebase/1337.md`) but wrapped it in new, emphatic
  language — and code review held the PR to that emphasis rather than
  excusing it as inherited. If a paragraph you're writing makes a claim
  more certain than the code underneath it, that certainty needs to be
  earned, not borrowed from context.
