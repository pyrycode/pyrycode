# Ticket #1463 — Probe instrument: sweep the gather's certified-ordering route for captured bytes (offline)

`finGatherReadings` carries the caller's certified ordering onto
`trailRunReadings.Ordering` **whole** since #1462 (`bd09812`) — the bare
`readings.Ordering = in.Ordering` — and, per this family's standing rule (set
by #1452, restated by #1458/#1459), a new whole-carried route gets a sibling
sweep rather than a third plant on `TestFinGatherReturnsNoCapturedBytes`,
which already marshals `readings` and would go red against correct code. This
ticket ships that sibling: `TestFinGatherOrderingCarriesNoCapturedBytes`, one
input later than #1459's pid sweep and modelled on it section-for-section.
**Its own main job was honesty about being weaker than its two siblings**:
`trailCertifyOrdering` takes three `bool`s and no shipped arm anywhere
renders `Ordering.Detail` into a published string, so there is no live leak
route to fence — the sweep is a discipline against a *future* field and a
future arm that interpolates the ordering's `Detail` for a better failure
message, not coverage of an observed exposure. Offline throughout: no live
claude, no credentials.

PR [#1465](https://github.com/pyrycode/pyrycode/pull/1465). Spec:
[`docs/specs/architecture/1463-gather-ordering-no-captured-bytes.md`](../../specs/architecture/1463-gather-ordering-no-captured-bytes.md)
(architect self-review PASS). One code-review round, PASS with one
non-blocking NIT.

## Implementation

- **`TestFinGatherOrderingCarriesNoCapturedBytes`**, placed immediately after
  `TestFinGatherStagedOrderingReachesTheSightingOutcomes` and before
  `TestFinGatherSightingComesFromTheClassifiedPoll` — the placement that
  makes the re-point's "immediately below" literally true. The plant is a
  `trailOrderResult` struct literal built by a **function**
  (`plantedOrdering`), never a package-level value, for the same
  shared-mutation reason `TestFinGatherPinnedPidCarriesNoCapturedBytes` gives
  its own plant: `Value: trailOrderCertified` (the honest value for this
  fixture, and clear of the classifier's `Ordering.Value == ""` guard) and
  `Detail: "ordering: " + trailNeedle` (52 bytes). `trailOrderResult` has
  exactly two members, so the plant fills both — no third-field
  surface-maximisation argument to make, and the doc says so explicitly
  rather than leaving the absence to look like an oversight next to the pid
  sibling's deliberate three-field maximisation.
- **The arm is decided by the gate, not by the ordering** — measured, not
  assumed, and the spec corrects an earlier draft that got this backwards.
  `finGatherNegativeInputs(t, &stdout)` with only `in.Ordering` replaced
  stays on `trailOutcomeNoRowMatched` (step 8): the whole sighting route
  sits behind step 1's gate-absent branch, so on this fixture's usable gate
  `Ordering` is never consulted at all. The expensive arms
  (`TestFinGatherStagedOrderingReachesTheSightingOutcomes`'
  `trailKeyNamesNoTerminalReason()` + streamrunner-reducing `RunnerPath`
  recipe) were deliberately not borrowed — their budgets are far tighter
  (453–492 of 512 by the classifier's own documented figures) and staging
  the ordering doesn't require reaching them.
- **Five premises, each a named `Fatalf`** turning a vacuous sweep into a
  stop: the plant carries the needle; `readings.Ordering != in.Ordering`
  fails loudly (whole-value `==`, since `trailOrderResult` is two strings —
  this is `TestFinGatherStagedOrderingReachesTheSightingOutcomes`' subject
  arriving as this test's premise); `readings.Gate.Detail` /
  `readings.Admit.Detail` are both non-empty (measured 229 / 264); the arm
  really is `trailOutcomeNoRowMatched` (message: "the control's byte budget
  is THAT arm's"); and `outcome.Detail` doesn't already carry
  `reachTruncationMarker`.
- **Six channels, three marshalled subjects (run outcome, attribution
  record, sighting) plus three named `Detail`s** (outcome's, gate's,
  attribution's) — swept individually rather than folded into the marshal
  loop, so a failure names which leaked. The marshalled `trailRunReadings`
  is **deliberately not a row**, stated in the test's own doc so a later
  reader doesn't "fix" the omission: the needle rides that value by design,
  same as the pid sibling's own carve-out.
- **The control**, built through the shipped renderer off the shipped
  rendering — `trailDetail("%s ordering: %s", outcome.Detail,
  readings.Ordering.Detail)`, never a re-typed format string — with three
  checks: needle present, `len(control) < reachMaxCommandBytes`, no
  `reachTruncationMarker`. Measured 443 clean / 506 under the RED-proof
  mutant (69 / 6 bytes of headroom on the 512 cap) — both silent, so the
  control never fires a budget `Fatalf` alongside the needle diagnosis.
- **The comment re-point (AC6).** Exactly one shipped comment named this
  ticket (`finding_run_gather_test.go`, inside
  `TestFinGatherStagedOrderingReachesTheSightingOutcomes`' "What this test
  does not do" block) — measured, not the six an earlier draft predicted by
  analogy with #1459. Re-pointed to the new test's **name**, following the
  resolved form `TestFinGatherPinnedPidDoesNotReachTheLiveness` set: "a
  reader of this doc is one declaration from the test they want."
- **The two count claims in `TestFinGatherReturnsNoCapturedBytes`' doc**
  ("two of the three inputs that could carry captured bytes…", "THE THIRD
  INPUT IS #1458's `PinnedPid`") were re-verified at `ad12951` and left
  **unincremented** — they count inputs that *can* carry captured bytes, and
  the ordering isn't one, by construction of `trailCertifyOrdering`. The
  paragraph below them (the "PLANT ADDED HERE WOULD BE RED AGAINST A
  CORRECT BUILD" argument) gained a two-sentence extension naming the
  ordering as a second whole-carried value under the same argument — the
  site a later reader stands at when reaching for the third plant. The file
  header's own "Three caller-supplied strings cross… VERBATIM" list was
  left untouched: the ordering has no legitimate-publication entry to
  defend there.
- **Mutation evidence, reproduced independently in code review** via `go
  test -overlay` (no worktree writes): a mutant appending
  `readings.Ordering.Detail` to `trailClassifyRun`'s step-8
  `decide(trailOutcomeNoRowMatched, …)` fall-through reddens exactly the
  marshalled run outcome and the outcome's `Detail` row, on the needle, with
  the other four channels green and the control silent (506/512, no
  marker). Code review additionally proved the mutation-only budget claim
  ("a `Detail` past ~54 bytes") exact on both sides: 54 bytes dies on the
  needle alone, 55 trips the control's own budget `Fatalf` at 512.

## Patterns established

- **A weaker sibling sweep must say it's weaker, not be written by swapping
  the nouns in the stronger one.** The pid sweep (#1459) states "four of six
  channels pass structurally" as a real absence claim with two live
  channels remaining unswept elsewhere; this ticket's honest statement is
  "all six pass structurally, and none is a live leak" — a *stronger*
  absence, and the doc says so explicitly rather than presenting it in the
  weaker test's four-of-six shape. Confirms the general shape
  [`codebase/1459.md`](1459.md) set, now read from the side where the
  claim is actually stronger.
- **A control composing on top of a shipped rendering pays for the plant
  twice under the RED-proof mutant, and the plant's `Detail` length must be
  sized against that doubled cost, not the single-pay clean-tree cost.**
  Clean tree: 380 (arm) + 11 (separator) + 52 (plant) = 443. Under the
  mutant, the same 52-byte plant is already inside `outcome.Detail` once and
  gets appended again: 506. The ceiling on the plant's `Detail` is ~54 bytes,
  not the ~120 the single-pay arithmetic would suggest — the same trap
  [`codebase/1459.md`](1459.md)'s own lessons record for this exact
  compose-on-top control shape, now independently re-measured and pinned
  exact (54 green, 55 red) rather than left as a comment's estimate.
- **A test whose subject is a value the classifier structurally never reads
  on the pinned arm still earns a sibling sweep, because the discipline it
  buys is against a future field, not the present arm.** The producer-side
  argument (`trailCertifyOrdering`'s three-`bool` signature) and the
  consumer-side argument (no shipped arm renders `Ordering.Detail`) are both
  true simultaneously, and the spec required stating both rather than
  treating either as sufficient on its own to skip the test.

## Lessons learned

**From the PR body's own "Lessons learned" section** (developer):

- **A control's byte headroom is a product of the plant's `Detail` length
  when the control composes on top of a rendering the plant is already
  inside of** — a republishing mutant pays for the plant twice, once in the
  base rendering and once in what's appended. At 52 bytes that's 443 clean
  and 506 of 512 under the mutant; a longer plant would have made the RED
  run die on the truncation marker instead of the needle, the exact
  confusion `TestTrailRunOutcomeCarriesNoCapturedBytes`' own doc records
  this family being fooled by on this same field.
- **Staging a value does not move the arm the value is decided under.**
  `finGatherNegativeInputs` stays on step 8 with `Ordering` set, because the
  arm is decided by the gate and the whole sighting route sits behind
  step 1's gate-absent branch. That's what let the sweep keep the cheap
  arm's byte budget while still staging the value the plant needs — the
  opposite of an earlier draft's assumption that staging an ordering would
  move the outcome onto the expensive arms.
