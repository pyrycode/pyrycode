# Ticket #1103 — `internal/permbridge`: pending-approval registry with fail-closed default-deny completer

New package `internal/permbridge` (one production file `permbridge.go` + `permbridge_test.go`). It parks a claude tool-approval request under an opaque id, hands the blocked caller a `Pending` handle to `Await`, and lets a resolver satisfy it with an allow/deny `Verdict` — or, if nothing resolves it, a registry-owned per-entry `time.AfterFunc` timer defaults it to deny. Ships **unwired**: the control-socket verb (#1104), the `pyry mcp-approve` subcommand + spawn-arg injection (#1105/#1106), and the `modal_shown ↔ modal_answer` resolver wiring (#1080) are all siblings that consume this primitive. Split from #1079; part of the Streamrunner Interactive permission bridge.

Full design writeup: [`features/permbridge-package.md`](../features/permbridge-package.md). Spec: [`specs/architecture/1103-permbridge-registry.md`](../../specs/architecture/1103-permbridge-registry.md).

## Implementation

- Mirrors `internal/modalbridge/modal.go`'s registry shape (leaf `sync.Mutex`, opaque-id-keyed map, clone-free since entries aren't shared) plus a per-entry completer (`chan Verdict`, buffered(1)) and a `time.AfterFunc` deadline.
- The security core is `resolve(id, v)` (unexported): `delete(pending, id)` under `mu` is the **sole one-shot arbiter**. Both `Resolve` and the timer callback funnel through it — exactly one wins the delete and becomes the single writer of `p.ch`; the loser is a no-op. Because the send is provably single-writer on a buffered(1) channel, it never blocks and is safe to do outside the lock.
- `Register` holds `mu` across the timer arm *and* the map write, so even a 0-duration timer blocks in `resolve` on `mu.Lock()` until the entry is fully installed — no fire-before-install race.
- Self-contained: imports only stdlib (`encoding/json`, `errors`, `sync`, `time`). No `internal/` imports at all, so — unlike modalbridge — there's no relay-import cycle to document; the package doc states the invariant directly.
- Log-free: a pure data structure, no logger field. Content-free decision logging is left to the consumer (mirrors `acp_permission.go`'s pattern).
- `Request`/`Verdict` are the T1 spike's wire contract (`tool_name`/`input`/`tool_use_id`, `behavior`/`updatedInput`/`message`), kept marshal-friendly but with no control-socket envelope — that's #1104's boundary. `Allow`/`Deny` constructors avoid stringly-typed `"allow"`/`"deny"` at call sites.

## Patterns established

- **Delete-under-mutex as the one-shot arbiter**, reused instead of `acp_permission.go`'s `atomic.Bool` CompareAndSwap arbiter — because the map already needs a lock for the O(1) ops, the delete itself is the free arbitration point. Worth reaching for whenever a map-backed registry needs "exactly one of N racing resolvers wins."
- **Fail-closed via enumeration, not a single guard.** Every non-allow terminal path (deadline, lost caller, unknown id, duplicate/empty id, non-positive timeout) independently yields deny/no-op; allow has exactly one entry point (`Resolve(id, Allow(...))`). The deterministic proof is a 300-iteration allow-vs-timeout race test under `-race` — belt-and-suspenders where the safety net is the mutex-guarded delete, not another stochastic check.

## Lessons learned

- The allow-vs-timeout race test itself caught a **test-code** race: a plain `bool` written by the resolver goroutine and read by the main goroutine after `Await` returns has no happens-before relationship — `Await` returning only synchronizes with the channel send, not with whatever the resolver goroutine does *after* that send. Fixed by handing the resolve result back over a channel instead of a shared variable. General lesson: a concurrent test asserting "what did the other goroutine's `Resolve` return" must carry that value over a channel/sync primitive, not a bare variable, even if the *code under test* passed.
- Code review (PR #1111) flagged a NIT, not a fix: the `AfterFunc` closure captures `id` (not the specific `*pending`), so a stale timer that fires just as its entry is being re-`Register`ed under a **reused** id could in a tight window resolve the *new* entry instead. Judged fail-closed-only (can only ever deliver `Deny(reasonTimeout)`, never allow) and unreachable given claude's unique `tool_use_id`s, so no fix was made — but the primitive's contract is now explicit: **an id must not be re-`Register`ed until its predecessor's timer has drained.** If a future consumer (#1104) ever recycles ids, capture the `*pending` in the closure and identity-check it under `mu` before deleting.
