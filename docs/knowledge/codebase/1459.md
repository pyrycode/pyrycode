# Ticket #1459 — Probe instrument: sweep the gather's pinned-pid route for captured bytes (offline)

#1458 opened a route: `finGatherReadings` carries a caller's pinned-pid read
(`pinStateOutcome`, whose instrument-failed branch puts raw `ps` stderr into
`ToolStderr` and folds it into `Detail`) whole onto `trailRunReadings.PinnedPid`.
No live leak existed — `trailClassifyRun` renders `PinnedPid` through nothing —
but the route was a future-edit exposure with no fence against it. This ticket
ships that fence: a new gather-tier sibling test proving a needle planted in the
reading is absent from every published channel, plus an in-test control proving
the check is non-vacuous. Offline throughout: no live claude, no credentials.

PR [#1461](https://github.com/pyrycode/pyrycode/pull/1461). Spec:
[`docs/specs/architecture/1459-gather-pinned-pid-captured-bytes-sweep.md`](../../specs/architecture/1459-gather-pinned-pid-captured-bytes-sweep.md)
(architect self-review PASS). One code-review round — PASS with one
non-blocking SHOULD FIX and two NITs, all comment-wording, none in the test's
behaviour.

## Implementation

- **`TestFinGatherPinnedPidCarriesNoCapturedBytes`**, in
  `finding_run_gather_test.go`, placed immediately after
  `TestFinGatherPinnedPidDoesNotReachTheLiveness` — a **sibling test**, not a
  third plant on `TestFinGatherReturnsNoCapturedBytes`. That test marshals
  `readings` in full, and `readings.PinnedPid = in.PinnedPid` carries the pin
  whole and unnormalised by design (the equality
  `TestFinGatherPinnedPidDoesNotReachTheLiveness` asserts on purpose), so a
  `PinnedPid` plant added there would be red against a correct build.
- **The plant (`plantedPin`, a closure and not a value)** fills all three
  string-bearing members of `pinStateOutcome` — `Detail`, `StateColumn`,
  `ToolStderr` — each with `trailNeedle`. This is a shape **no single
  `pinClassifyState` arm emits** (the instrument-failed branch that produces
  `Detail`/`ToolStderr` leaves `StateColumn` empty); filling all three is
  deliberate surface maximisation, because the rule enforced is "no `Detail`
  here quotes any input's captured string," not "don't copy the one field
  named in the ticket."
- **Premises (`Fatalf`, so a broken one is a named failure, not a silent
  vacuity):** the plant carries the needle in all three members;
  `readings.PinnedPid == in.PinnedPid` (whole-value equality — the sibling's
  subject, this test's premise, since a narrowed pass-through would leave the
  needle no route to travel); `readings.Gate.Detail`/`Admit.Detail` are
  non-empty; `trailClassifyRun(readings).Value == trailOutcomeNoRowMatched`
  (step 8 — the arm the control's byte budget belongs to); `outcome.Detail`
  carries no `reachTruncationMarker` (so the control below reproduces a
  one-shot rendering, not a cap artifact).
- **Six named channels swept for absence**, each reported individually so a
  failure names which one leaked: the marshalled `trailRunOutcome`,
  `outcome.Detail`, `readings.Gate.Detail`, `readings.Admit.Detail`, the
  marshalled `finAttributeRecord`, the marshalled `finSighting`. Four of the
  six (record, sighting, gate/admit Details) pass structurally — neither
  `trailGate` nor `trailAdmitAttribution` nor the gather ever touches these
  with `in.PinnedPid` — and are kept as live guards against a future edit,
  the same standing `TestFinGatherReturnsNoCapturedBytes` gives its own
  sighting row.
- **Deliberately not a row: the marshalled `trailRunReadings`.** Those bytes
  ride that value by design (AC2); the test's doc states this in its own
  right so a later reader doesn't "fix" the omission by adding the row that
  breaks it against correct code.
- **The control (AC3)** renders what a republishing arm would have rendered —
  through the shipped `trailDetail`, off the shipped `outcome.Detail`, never
  a re-typed copy of the arm's format string — and asserts three things: the
  needle survives, the render stays under `reachMaxCommandBytes`, and it
  carries no `reachTruncationMarker`. This is the discrimination the ticket
  asked to be demonstrated rather than argued: an overrun here is a **budget
  kill wearing a leak kill's clothes**, the exact failure mode this test
  family was fooled by once before (recorded in
  `TestTrailRunOutcomeCarriesNoCapturedBytes`' doc).
- **Six shipped comments re-pointed** (AC4) — the two that had gone outright
  false (`TestFinGatherReturnsNoCapturedBytes`' and
  `TestTrailRunOutcomeCarriesNoCapturedBytes`' docs, both previously naming
  #1459 as owing a sweep that now exists) plus four future-tense mentions
  (`finGatherInputs.PinnedPid`'s doc, `finGatherPinnedReadings`' doc,
  `TestFinGatherPinnedPidDoesNotReachTheLiveness`' doc,
  `finExitRunProbe`'s `PinnedPid:` comment). `grep -rn "1459" internal/`
  returns nothing post-change; each site now names
  `TestFinGatherPinnedPidCarriesNoCapturedBytes` directly.
- **Verified rather than trusted, in code review:** a `go test -overlay`
  mutation (step-8 `decide` interpolating `readings.PinnedPid.Detail`, no
  worktree writes) reddens exactly the marshalled-outcome row and the
  `outcome.Detail` row, on the needle; the control's three assertions stay
  green and no premise fires. Byte budget re-measured independently: shipped
  `outcome.Detail` 380 bytes, control 440/512, 72 bytes of headroom, no
  truncation marker.
- **Citation tail: Δ=0 on both edited files**, verified per-hunk
  (`git diff -U0`) rather than per-file-total — the family's standing method
  since [`codebase/1458.md`](1458.md)'s five-round citation saga. No new
  `file.go:NNN`; symbols named throughout.

## Patterns established

- **A needle plant should fill every string-bearing member of the type it
  targets, not only the one the ticket names.** `pinStateOutcome` has three
  (`Detail`, `StateColumn`, `ToolStderr`); the shipped test fills all three
  even though no single producer arm ever does, because the property being
  swept is "no captured string reaches a Detail," not "this one named field
  doesn't." A future arm quoting `StateColumn` instead of `Detail` still
  reddens.
- **A route-fence's control must compose on the shipped renderer over the
  shipped rendering, never a re-typed copy of the arm's format string** —
  otherwise the control measures the plant's own arithmetic rather than the
  real rendering path, and a shipped format-string change silently
  desynchronises the control from what it claims to test.
- **Distinguish a budget kill from a leak kill explicitly, with dedicated
  assertions on the control** (needle present, under-cap, no truncation
  marker) — not just "the test failed." This family was fooled once by a
  plant that overran a cap and read as a leak kill; the fix generalised into
  a house pattern: any needle-plant control now carries this three-assertion
  shape.
- **A field the classifier renders nowhere still needs coverage if its
  producer can carry live secrets, and the coverage is a sibling test, not a
  plant added to the nearest existing sweep** that already marshals the
  field's whole-value carrier by design. Confirms the same rule
  [`codebase/1452.md`](1452.md) and [`codebase/1458.md`](1458.md) established
  for `RunnerPath`/`PinnedPid`'s pass-through tests, now applied one layer
  further out at the captured-bytes sweep itself.

## Lessons learned

**From the PR body's own "Lessons learned" section** (developer):

- **A per-file citation-tail measurement is only valid below its own anchor —
  each edit point owes its own scan.** The spec measured
  `finding_run_gather_test.go`'s tail "at or below the site-1 doc" and found
  it empty, correctly — but site 3 sits ~1000 lines higher in the same file,
  where a bare `(:415-419)` inherits `finGatherInputs.PyryExited`. That cite
  was already stale on `main` (415-419 lands inside `finSighting`'s own doc,
  a member of the pre-existing-stale family [`codebase/1458.md`](1458.md)
  surfaced) and was left alone, kept unshifted by writing site 3
  line-count-neutral as well.
- **A control that composes on top of a shipped rendering pays for the plant
  twice once the mutation that proves the sweep non-vacuous is applied, so
  the mutant's own growth — not just the plant's — can push it over the
  cap.** The spec's worked example was buildable at 61 bytes (455/512
  shipped); under the mutation proof the base `Detail` grows by the same
  amount the plant adds, and the binding constraint is
  `408 + 2×len(Detail) < 512` — roughly 50 bytes of plant, not the ~132 the
  shipped-tree headroom alone would suggest. Shortened the plant's `Detail`
  to 46 bytes so both the shipped run and the mutation proof pass. **Size a
  compose-on-top control against the mutated tree, not only the shipped
  one.**

**From code review** (PASS, one outstanding SHOULD FIX not addressed in a
follow-up commit as of this writing):

- **`plantedPin`'s budget comment is false against the shipped tree and cites
  an artifact that isn't in it.** It claims the control "pays for this one
  twice … once in the rendering it composes on and once in what it appends,"
  but on the shipped tree `outcome.Detail` carries no plant `Detail` at all —
  the control pays once, at 440/512 with 72 bytes of headroom. It pays twice
  only under a build that has already republished (i.e. under the mutation
  proof), and the comment's "makes the mutation run below die on the cap"
  points at a mutation run that exists only in the PR body, not in the
  shipped file. The ~50-byte constraint the comment is trying to state is
  real and load-bearing (see the developer's own second lesson above), but as
  written it's unverifiable from the tree it ships in — a reader checking it
  finds 72 bytes of slack where it claims none. Reviewer's suggested fix:
  carry the `408 + 2×len(Detail) < 512` arithmetic into the comment itself
  and say plainly that the doubling is conditional on a republishing build.
  **This is a comment defect, not a behavioural one** — it didn't block PASS
  and is worth a small follow-up commit.
- Two NITs, both wording-only, also unaddressed: the control's cap check
  reads `>= reachMaxCommandBytes` but `reachCapCommand` only truncates when
  `len(command) > 512`, so the failure message's "would be TRUNCATED" is off
  by one byte at exactly 512 (the guidance is still correct); and the test
  doc's "the classifier or the gather BUILDS from those readings, never the
  readings" imprecisely describes `readings.Gate.Detail`/`Admit.Detail`,
  which *are* fields of `readings` — the intended distinction is whole-value
  vs. field-scoped, and the code itself is unambiguous.
