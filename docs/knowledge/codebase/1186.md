# Ticket #1186 — idle-evicted bootstrap session not respawned on send (stream runner)

Fixes a silent no-reply: on the stream-json interactive runner, a `send_message` that arrived while a bootstrap session was idle-evicting was acked (enqueued) but never delivered — no respawn, no error, no reply. The PTY path (#396) appeared to honour the respawn contract; the stream path's real-claude gate (#1177) exposed that it didn't, because it sends its resume turn immediately on observing the `session.idle_eviction` WARN.

## Root cause

Not a stream-runner bug. The race is in the shared `internal/sessions/session.go` lifecycle primitive: `Session.Run`'s outer loop only flipped `lcState` to `stateEvicted` (via `transitionTo`) *after* `runActive` returned — i.e. after the child had already been torn down (`cancelSup`/`drainSup`). During that teardown window, the session was still reported `stateActive`. An `Activate` call landing in that window (any caller — stream drain, PTY control-plane attach, per-conversation bound session) took the already-active fast path and no-op'd against a supervisor that was already dying. #1177's timing (send-on-WARN) happens to land in that exact window; the settled-state fake tests #396/#680 wait for `"evicted"` on disk first and so structurally never hit it.

## Implementation

- Split the evicted-direction transition into `beginEvict(reason)` / `endEvict()`, replacing `transitionTo(stateEvicted)` (`internal/sessions/session.go`). `beginEvict` runs *before* `cancelSup`/`drainSup`: fires `notifyTransition`, then flips `lcState = stateEvicted`, stamps `lastActiveAt`, swaps in a fresh `activeCh` — all under `lcMu`. `endEvict` runs *after* the child stops: persists the registry, then closes `evictedCh`. All three `runActive` eviction exits (idle timer, cap-policy `s.evictCh`, defensive spontaneous-exit) call both, back-to-back on the spontaneous-exit path since there's no teardown to hold open there.
- `Session.Run`'s outer loop no longer calls `transitionTo(stateEvicted)` — `runActive` fully commits the eviction itself before returning an error-only result.
- The `stateActive` (reactivation) direction is untouched; `transitionTo` and [ADR 013](../decisions/013-evict-activate-persist-ordering.md) still apply there in full.
- New ADR: [034-two-phase-eviction-commit-signal-before-teardown.md](../decisions/034-two-phase-eviction-commit-signal-before-teardown.md). Evergreen mechanism description added to [idle-eviction.md § Two-phase eviction commit (#1186)](../features/idle-eviction.md#two-phase-eviction-commit-1186).
- Hermetic regression test: `internal/sessions/session_evict_race_test.go`, `TestSession_IdleEviction_ActivateRacingTeardownRespawns`. A `raceRunner` Runner double holds the first teardown open, a racing `Activate` is injected into that held-open window, then the test releases teardown and asserts a second spawn — the sibling to `internal/e2e`'s #396 test, but hermetic (no live claude). Fails on pre-fix `main`, passes after, clean under `-race`.
- No spec file: the architect timed out twice on this ticket; the operator posted a verified reference comment diagnosing the root cause (the teardown-window race, not a `streamsup` `firstRun`/`--session-id` arg issue as the ticket's technical notes speculated), and the fix was built from that comment directly.
- No production changes outside `internal/sessions/session.go`. `internal/streamsup/runner.go`'s `firstRun`/`buildArgs` behavior (flagged as a candidate mechanism in the ticket) was ruled out: the live evidence showed *zero* second `spawning claude` attempts, not a `--session-id`-on-existing-transcript refusal, which pointed at "the drain never reached the spawn" rather than an arg-selection bug.

## Rework

QA caught a regression in the first cut of the split (commit `d6c70c7`): `notifyTransition` stayed at its old call site (Run's outer loop, after `runActive` returned) while only the state flip moved into `beginEvict`. That decoupled the signal from the (now-earlier) flip — `TestPool_TransitionObserver_IdleEvictionFires` failed ~2/46 `-race` runs because a consumer could observe `stateEvicted` before the eviction signal had fired. Fixed in `c497a5b` by threading `reason` into `beginEvict` and firing `notifyTransition` there, immediately before the `lcMu` flip — restoring the pre-#1186 "adjacent, no scheduling point between them" ordering via a `lcMu`-mediated happens-before edge. `TestPool_` family verified clean 30× under `-race` after.

## Lessons learned

- **A two-phase split of a signal+flip+persist+close sequence must preserve the *relative* ordering of the signal to the flip, not just split where persist happens.** It's tempting to reason "the flip moved earlier, the signal can stay where it was" — but if the signal and flip were adjacent (no scheduling point between them) in the original, moving only one of them decouples an implicit "signal-happens-before-flip-becomes-observable" contract that nothing enforced explicitly except position. When splitting a commit into an early half and a late half, audit every side effect in the original for which half it *actually* belongs to, not just move the minimum diff.
- **"No second spawn at all" is a different failure signature than an arg-selection bug, and worth trusting over a plausible-sounding technical-notes candidate.** The ticket's technical notes flagged `streamsup/runner.go`'s `firstRun`/`--session-id` vs `--resume` selection as a candidate mechanism. The live evidence (zero second `spawning claude`) ruled it out immediately — that bug's signature would be a second spawn attempt followed by a claude refusal, not silence. Worth checking the evidence against each candidate's *expected symptom* before diagnosing, rather than defaulting to the most detailed candidate in the ticket.
