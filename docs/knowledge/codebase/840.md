# Ticket #840 — Pool.UpdateSettings persists a partial model/effort/YOLO change

`#833` shipped per-session `Model`/`Effort`/`YOLO` (`SessionSettings`) but left
them immutable post-construction — its own doc comment anticipated this
ticket. #840 adds the one seam the client-facing v2 settings verb (#841, split
from the same #834/#826 parent) needs: a `Pool` method that merges a partial
change into an identified session's stored settings and re-persists. It is
not client-facing — validating untrusted model/effort values is #841's job.
`security-sensitive` (the update can carry YOLO / `--dangerously-skip-permissions`).

## Implementation

Both edits live in `internal/sessions`, no new file for production code (~80
LOC across two files):

- **`session.go`** — new exported `SettingsUpdate{Model, Effort *string; YOLO *bool}`
  next to `SessionSettings`. A `nil` field means "leave the stored value
  untouched"; non-nil overwrites, including `""` for `Model`/`Effort` and
  `false` for `YOLO` — both distinguishable from omitted. `YOLO`'s `*bool` is
  the fail-safe: an absent `YOLO` can never flip bypass on.
- **`pool.go`** — `Pool.UpdateSettings(id SessionID, update SettingsUpdate) error`
  beside `Rename` (~40 lines incl. doc comment), same control-flow shape:
  `p.mu.Lock()` → lookup (miss → `ErrSessionNotFound`, no entry created) →
  build `merged` by overlaying present fields onto a copy of `sess.settings` →
  no-op short-circuit if `merged == sess.settings` (writes nothing to disk,
  keeps registry mtime stable) → swap in `merged` → `saveLocked()`, rolling
  `sess.settings` back to its previous value on save error. No new registry
  schema change needed — #833 already added the fields and the lenient
  decode; mutating the in-memory field is enough for the next `saveLocked` to
  persist it.
- **Doc-comment corrections** (accuracy, not behaviour): the `SessionSettings`
  type comment, the `Session.settings` field comment, and the `saveLocked`
  inline comment at the settings-copy site all said "immutable post-New" —
  corrected to describe mutation via `Pool.UpdateSettings` under `Pool.mu`.

**Locking.** `settings` is a `Pool.mu`-guarded field (like `label`), not
`lcMu`-guarded. `UpdateSettings` holds `Pool.mu` across the merge + `saveLocked`
and never touches any `Session.lcMu` — the documented `Pool.mu → Session.lcMu`
order (`docs/lessons.md` § "Lock order with callback into the host") stays
intact because `saveLocked`'s internal `lcMu` re-acquire is sequential, not
nested inside a lock `UpdateSettings` holds. All registry saves serialize on
`Pool.mu`; the Pool is the sole registry writer, so no reload-before-save is
needed here — a distinction from `internal/devices`' push-token path, which
has a second writer and therefore does need read-modify-write.

**Reach.** The new values arrive at claude through #833's already-shipped
spawn path (`claudeSettingsArgs`) on the session's *next* spawn: for the
bootstrap session, the next daemon restart (the reload path #833 proved); for
a minted session, its next (re)spawn. Making a *running* session pick up the
change without a respawn is a separate sibling (#842) — deliberately not
touched here so #842 stays free to choose evict→rebuild vs in-place.

**Why no race with a running supervisor (code review's blast-radius check):**
`claudeSettingsArgs` is read only at construction time, at both spawn sites,
each from a **value copy** of `settings` taken before the child is spawned —
never from the live `sess.settings` field. A running supervisor bakes its argv
once and never re-reads the field, so `UpdateSettings` mutating
`sess.settings` concurrently with an already-running session is not a data
race — the only two readers of the field itself (`saveLocked` and
`UpdateSettings`) are both under `Pool.mu`.

## Fail-safe design (security)

Three deterministic layers, no stochastic component, for the one
security-critical property — `--dangerously-skip-permissions` never enabled by
absence, omission, or confusion:

1. **Setter (this ticket):** `YOLO *bool`; `nil` → untouched; only a non-nil
   `*bool` changes it.
2. **Persisted layer (#833, unchanged):** plain `bool`, zero value OFF;
   missing key decodes to `false`; malformed value fails the whole
   `loadRegistry` parse. See [ADR 030](../decisions/030-plain-bool-failsafe-persisted-flag.md).
3. **Argv layer (#833, unchanged):** `claudeSettingsArgs` emits the bypass
   flag only for `YOLO == true`, never a "disable" flag.

An operator turning YOLO on through this setter is intended behaviour;
*authorizing* that action is enforced upstream at #841's wire boundary, named
explicitly as out of scope here (not silently assumed).

## Testing

Same-package, table-driven, `-race`. New `pool_update_settings_test.go`
covers: per-field partial merge (AC1), empty-string-as-real-value vs omitted,
YOLO-absent leaves stored value in both directions (AC3), YOLO-present flips
both ways, unknown id returns `ErrSessionNotFound` with the registry file
byte-unchanged (AC4), no-op update writes nothing, concurrent updates
serialize under `-race` (AC2), and a round-trip through a simulated daemon
restart (cold `New` → `UpdateSettings` → `loadRegistry` assert → second `Pool`
from the same registry path → recorder harness shows the new `--model
--effort --dangerously-skip-permissions` in argv) proving AC5.

Code review: **PASS**. `go test -race ./...`, `go vet ./...`, `go build
./cmd/pyry` all pass.

## Lessons learned

None surfaced beyond what the architecture spec already anticipated — the
`Rename` precedent carried over exactly as designed, with no synchronization
surprises. Code review hit a real-claude e2e red
(`TestPtyRunnerVsStreamRunner_StructuralEquivalence`) and proved it an
environmental flake unrelated to this diff (behavior-inert change, count
varies run-to-run, reproduces on `main`) rather than routing back for
false-rework — a previously-seen `thinking_tokens`-count divergence pattern.
Review flagged that test should filter `system/thinking_tokens` events from
its comparison as a worthwhile separate follow-up ticket.
