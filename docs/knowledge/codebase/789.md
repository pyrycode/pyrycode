# Ticket #789 — sweep the `WaitBinary` barrier across fakerelay's dependent-dial tests

Six `internal/e2e/internal/fakerelay` tests established a binary and then immediately issued a *dependent* dial without gating on registration. Under full-suite `go test -race ./...` load they intermittently went red — a phone got `503` "no binary online" instead of the `101` handshake, or a first-claim-wins conflict was missed. Always green in isolation; the failing test *set* varied run-to-run. That is the signature of the accept→register window, not a product defect. This ticket applies the existing `Server.WaitBinary` barrier at every such site. Test-harness-only — no production code changed.

The race is the same one [#371](371.md) fixed for `TestForceCloseBinary`: `websocket.Accept` writes the `101` (unblocking the client's `Dial`) **before** `handleBinary` finishes inserting into `s.binaries` under `s.mu` (`fakerelay.go` accept ~L225, insert ~L254). #371 introduced `WaitBinary` and gated the two tests that *directly probe* server-side maps; it did not sweep the tests whose dependent operation is a plain **dial** that reads the same state inside a handler. #789 closes that gap. See [`features/fakerelay-harness.md`](../features/fakerelay-harness.md) for the harness contract.

## Implementation

- **`internal/e2e/internal/fakerelay/fakerelay_test.go`** — inserts the established idiom between establishing a binary and the first dependent dial, at six sites:
  ```go
  if !s.WaitBinary(ctx, "alpha") {
      t.Fatal("binary registration did not complete")
  }
  ```
  Every gated test already had a 3s `ctx` from `dialCtx(t)` in scope; the barrier reuses it (the 3s is a safety ceiling — `WaitBinary` hits on the first or second 2ms tick in practice).
- **The six sites**, by the raced read they close:
  - Second-binary claim (`/v1/server`): `TestBinaryUpgrade_FirstClaimWins` — the second dial's pre-upgrade claim check (`fakerelay.go` ~L218) must see the entry to return `409` rather than spuriously accept.
  - Phone-after-binary (`/v1/client`): `TestPhoneToBinary_FrameWrappedWithConnID`, `TestBinaryToPhone_FrameUnwrapped`, `TestConnIDIncrementsPerPhone`, `TestPhoneClosedWhenBinaryGoes`, `TestServerClose_NoGoroutineLeaks` — the phone's binary-existence check (`~L300`) must pass to return `101` rather than `503`.
- **`TestConnIDIncrementsPerPhone` gates once before the phone loop, not inside it** — the loop dials multiple phones against one server-id, and registration is stable after the first success. A gate per iteration would be redundant.
- **`t.Fatal` on `false`, never a silent proceed** — a genuinely stuck registration surfaces as a clear barrier failure rather than a confusing downstream `503`, mirroring the `TestForceCloseBinary`/`TestWaitBinary` precedent.
- No new goroutines/channels/state, no new test functions, no phone-readiness barrier. `WaitBinary` reads `s.binaries` under the existing `s.mu`; the gate serializes the test goroutine against the handler's insert via that lock + poll.

## Patterns established

- **Sweep the raced *shape*, don't spot-fix the observed failures.** The report named the tests that happened to fail on two runs; the actual fix target is every test matching "establish a binary, then issue a dependent dial on it." Grepping the shape surfaced `TestServerClose_NoGoroutineLeaks` — a latent flake with the identical cause that was **not** named in the report. Fixing only the reported names would have left it to flake later.
- **Exclude tests that reject *before* the raced check — evidence-based, don't defend an unreachable failure mode.** `TestPhoneUpgrade_RequiresAllHeaders` binds a binary but every dependent phone dial deliberately omits a header, so `handlePhone` returns `400` at its header check (~L289/L290) **before** ever reaching the binary-existence check (~L300) that returns the raced `503`. A `WaitBinary` gate there would guard a `503` that can't occur. The exclusion filter is: does the dependent dial's rejection precede the raced read? `TestRejectNextBinaryWith4409` and `TestBinaryUpgrade_RequiresServerHeader` are excluded for the same class of reason (no dependent dial on the registered binary, or a pure failure-path dial).
- **Reuse the existing in-file barrier over a `bindBinaryReady` helper.** A helper bundling dial + `WaitBinary` would DRY the six sites and structurally prevent future authors from forgetting the gate, but the raw `dialBinary` is still required by the failure-path tests (empty-header `400`, `4409` close, second-claim `409`). A helper would cover only the happy path — leaving two ways to bind a binary and pressuring a refactor of the `#371` precedent tests (scope creep). The explicit gate keeps the file uniform and matches precedent.

## Lessons learned

- **The accept→register window is a recurring harness shape, and applying the barrier to one class of caller doesn't cover the others.** `websocket.Accept` returning ≠ "server-side bookkeeping is complete." #371 established `WaitBinary` and gated the *direct-probe* tests (those that read `s.binaries` via `ForceCloseBinary`); the *dependent-dial* tests read the same state one layer removed — inside a `/v1/client` or second `/v1/server` handler — and were left ungated for four months until concurrent `-race` load surfaced them. When a barrier is introduced for one caller class, sweep every class that crosses the same boundary, not just the one that flaked first.
- **A single-run baseline name-comparison misclassifies a non-deterministic flake set as a regression.** This ticket was filed from QA of PR #788 / [#411](411.md): the merge-base baseline and the PR HEAD both failed in this package with the identical `503` mode but on **different test names**, because the failing set is load-dependent and varies run-to-run. A name-partition ("names that fail on HEAD but not baseline = PR regression") would have routed a clean PR to `needs-rework:developer`. The correct QA move is to re-run the flagged set isolated and full before attributing a red column to the PR — and to file the harness flake (this ticket) rather than the PR.

## Verification

- `go test -race -count=50 ./internal/e2e/internal/fakerelay/` — green, 50/50.
- `make check` (vet + full `-race` suite + staticcheck + substrate-guard) — exit 0, fakerelay `ok`; `go vet ./...` clean.
- Each gated test still asserts its original behavior (conn_id wrapping/unwrapping, `409` conflict, orphan-phone close, no goroutine leak) — the gate only adds a barrier ahead of the dependent dial; it changes nothing the test observes afterward.

## Not in scope

- **No phone-readiness barrier.** There is no phone-side analogue of `WaitBinary`, and no phone-ordering flake has been observed. The only readiness gap these tests hit is binary registration, which `WaitBinary` covers. Adding a phone barrier would defend an unobserved failure mode (evidence-based; out of scope per the ticket).
- **No change to `handleBinary`'s Accept-then-register order.** Pre-Accept registration would impose new ordering constraints on phone routing — out of proportion to a fixture-only flake (same rationale [#371](371.md) recorded).
