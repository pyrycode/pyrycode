# Ticket #1580 — streamsup: install a new spawn argv without killing the running child

`(*streamsup.Runner).Restart` fused two operations: install the next spawn's argv, and cancel the live
child so `Run` relaunches under it. A caller that wants the argv swap without the kill had no way to ask
for it — declining to call `Restart` doesn't give a swap-only path, it gives *no* swap, and the session's
next spawn (crash-respawn, or evict → `Activate`) silently re-execs the stale argv. This ticket adds
`SetSpawnArgs`, the swap half alone, and widens `sessions.Runner` to carry it. No consumer lands in this
ticket and no behaviour changes — `Restart` still does exactly what it did before, just routed through the
same installer `SetSpawnArgs` uses.

## Implementation

- **`internal/streamsup/runner.go`** — three symbols:
  - `setArgsLocked(args []string)` (unexported, `restartMu` MUST be held) does the `slices.Clone` and the
    assignment. It is now **the sole writer** of `r.args` after construction — both `Restart` and
    `SetSpawnArgs` install through it. The clone is load-bearing, not hygiene: without it a caller keeps a
    live handle on the runner's spawn argv and can mutate it *after* installation, racing `beginSpawn`'s
    read.
  - `SetSpawnArgs(args []string)` (exported) is lock → `setArgsLocked` → unlock. No `restartCh` send, no
    `iterCancel` read or call, no `sessionID`/`rotatePending` write — sending any of the first two would
    make it `Restart` under a new name.
  - `Restart(args []string)` is unchanged in signature and behaviour; its inline `r.args = slices.Clone(args)`
    is replaced by a call to `setArgsLocked` **inside its existing single `restartMu` section** — not a
    by-name call to the exported `SetSpawnArgs`, which would split `Restart` into two acquisitions and
    reopen the #1481 window (`beginSpawn`'s doc: a racing `Restart`/`RestartFresh` takes `restartMu`
    exactly once, so it's serialised wholly before or wholly after `beginSpawn`'s section; two acquisitions
    reintroduce a third position where a live child can end up under a pre-rotation id with no live
    iteration cancel).
- **`internal/sessions/runner.go`** — `Runner` gains the `SetSpawnArgs(args []string)` method line. AC 5:
  the interface doc's three stale #1348 claims (phantom `var _ Runner = (*supervisor.Supervisor)(nil)`
  assertion; nil-`RunnerFactory` defaulting to `supervisor.New`; a `Session.Supervisor()` accessor) are
  corrected to describe what exists — one production implementation (`streamRunner`, adapting
  `*streamsup.Runner`), five test doubles, a mandatory factory, and `Session.Runner()` + capability
  type-assertion as the actual concrete-method dispatch mechanism.
- **`cmd/pyry/streamsup_runner.go`** — `streamRunner` gains a one-line `SetSpawnArgs` delegate, and the
  comment above `var _ sessions.Runner = streamRunner{}` drops its back-reference to the phantom
  `internal/sessions/runner.go` assertion (this is now the *only* conformance assertion, not a mirror of
  one).
- **Five test doubles** (`fakeRunner`, `lifecycleRunner` in `internal/sessions/runner_test.go`,
  `raceRunner` in `internal/sessions/session_evict_race_test.go`, `stubRunner` in
  `cmd/pyry/session_router_test.go`, `baseRunner` in `cmd/pyry/inbound_deliver_rotation_test.go`) each gain
  a `SetSpawnArgs`. `lifecycleRunner` records into a new `setArgs [][]string` field, kept separate from its
  existing `restarts` field because the two are different events (an install vs. an install-that-also-ends-
  the-child) — `staticcheck`'s `unused` check doesn't flag the write-only field, matching the precedent its
  sibling `restarts` already set.
- **`internal/streamsup/runner_test.go`** — one new test,
  `TestRunner_SetSpawnArgs_InstallsWithoutKillingLiveChild`, proving both AC 1 halves against one live
  `record_block` child (see Testing).

Nothing outside tests calls `SetSpawnArgs` in this ticket. All fourteen `TestPool_UpdateSettings_*` (seven
in `pool_update_settings_restart_test.go`, seven in `pool_update_settings_test.go`) pass unmodified —
neither file declares a `sessions.Runner` double, so the interface widening needed no edit there.

## Patterns established

- **Lock-held core + exported wrapper, to keep a caller's single-acquisition invariant while adding a
  second entry point.** When two public methods must both install the same guarded state, but one of them
  (`Restart`) has an existing "exactly one `restartMu` acquisition" invariant that a by-name call to the
  other would break, factor the guarded write into an unexported `xxxLocked` helper (repo convention:
  `rekeyLocked`, `saveLocked`, `advanceLocked`) that both public methods call from *inside their own*
  lock section. The naming and the "Caller MUST hold …" doc line are what stop a future refactor from
  re-fusing the two and reintroducing the split.
- **A negative timing assertion must be calibrated against the mutant's latency, not the healthy path's —
  and a seam beats a wider window when one exists on the forbidden path.** The first review round's MUST
  FIX: half (a)'s 250ms settle passed a mutant that performed the kill, because under `-race` the killed
  child took ~1.03s to relaunch (`cmd.Cancel` shells out to `reapDescendantGroupsFn`'s `ps` before the
  SIGTERM). The fix hung the assertion on `reapDescendantGroupsFn` itself via the existing `swapReapSeam`
  test helper — a kill can only reach the child by cancelling the iteration ctx, and `os/exec` invokes
  `cmd.Cancel` (which calls the reap fn first, synchronously) on exactly that, so the stub sees an attempted
  kill within a goroutine wakeup regardless of what the child does about the signal. Stubbing the seam also
  took the real `ps` off the path, so the killed-child respawn dropped from ~1.03s to the 1ms backoff —
  recovering the margin on the count/pid assertions as a side effect, not by widening them.
- **Each forbidden effect named in a spec needs its own discriminator; a kill assertion is blind to a
  leaked hint.** The spec's "what `SetSpawnArgs` must NOT do" names three effects (`restartCh` send,
  `iterCancel` call, `sessionID`/`rotatePending` write). The first review round shipped with only the kill
  pinned; a mutant that sent *only* the `restartCh` hint survived, because it kills nothing (half (a) stays
  green) and still installs the marker (half (b) stays green) — the only visible symptom is
  `RestartCount` staying `0` instead of incrementing on the externally-ended child's respawn. Second round
  added that assertion. Third round (code review) added a fourth mutant for the third effect
  (`rotatePending`) proactively rather than assuming the existing id-form assertions would catch it — they
  did, but "the enumeration says three, the test proves two" is a gap worth mutating even when the fix
  looks like a side effect of other assertions.
- **A capability type-assertion on an anonymous method-set interface, not a concrete-type assertion, is
  the load-bearing dispatch pattern for interface methods deliberately kept off `sessions.Runner`.** The
  PASS-round review caught the AC 5 rework's own replacement doc describing "`Session.Runner()` + a
  `*streamsup.Runner` type assertion" — which would be `ok == false` always, since `Session.Runner()` holds
  the value-typed `streamRunner` adapter in production. The actual mechanism (`interruptRunner`,
  `startFreshRunner`, `beginRotationOrNoop` in `cmd/pyry/main.go`) asserts to anonymous interfaces like
  `interface{ Interrupt() error }`. Worth checking with a fixed-string `git grep` for the literal assertion
  syntax (`.(*ConcreteType)`) before describing "how a consumer reaches the concrete type" in a doc comment
  — it's the same failure shape AC 5 exists to retire, one layer down.

## Lessons learned

From the PR body:

- `runInBackground`'s `join` is single-shot: a deferred teardown covering `t.Fatalf` paths *and* an
  explicit one that inspects `Run`'s error will both call it, and the second call blocks until the helper's
  own 10s deadline and then fails the test. An idempotent `stop()` closure (`stopped bool` guard) gives both
  call sites a safe join without a leaked `Run` goroutine on the fatal paths.
- `internal/sessions`'s `lifecycleRunner` already carried a write-only recording field (`restarts`) before
  this ticket, so `staticcheck` doesn't flag a second one (`setArgs`) — a recording double can record a
  not-yet-dispatched call without tripping the `unused` gate, which is why "record rather than drop" was
  the right default for a double whose method has no production caller yet.

From code review (two rounds, FAIL → PASS):

- A negative timing assertion needs calibrating against the *slowest plausible mutant path under the
  actual gate's flags*, not the healthy path — see the reap-seam pattern above. `-race` was specifically
  what made the kill path 4x slower; the same 250ms window discriminated fine without it, so a test that
  only ever runs without `-race` locally can hide a gate-only failure.
- The PASS round's residual SHOULD FIX (capability-assertion pattern above) and NIT (three of the five test
  doubles live in `internal/sessions`, two in `cmd/pyry` — "the package's test doubles" undercounted) were
  both left uncorrected in code as below the two-round threshold; flagging here in case a future touch of
  `internal/sessions/runner.go` wants to fold them in.
- The carried-over finding that this ticket's own knowledge docs (`sessions-package.md`,
  `streamsup-package.md`) still reproduced the pre-#1348 claims AC 5 retired in code is addressed by this
  documentation pass — see Related.

## Testing

`go test -race ./internal/streamsup/... ./internal/sessions/... ./cmd/pyry/...`, `go vet ./...`,
`make staticcheck`, `make cite-guard` all pass. `TestRunner_SetSpawnArgs_InstallsWithoutKillingLiveChild`
proves both AC 1 halves against one live `record_block` child (never self-exits):

- **Half (a)** — after `SetSpawnArgs`, a 250ms window (bounded by the stubbed `reapDescendantGroupsFn` seam,
  not the settle time) shows zero reap-seam calls, `rec.count() == 1` (no further spawn attempted — the
  recorder fires at the "spawning claude" log site, before `cmd.Start`), and `State().ChildPID` unchanged.
- **Half (b)** — the child is ended by signalling its captured pid directly (`syscall.Kill`, sound only
  because `record_block` never self-exits and so can't have been reaped/recycled), never by calling
  anything on the `Runner` — making the installed marker attributable to `SetSpawnArgs` alone. Spawn 2's
  argv carries the marker, spawn 1's doesn't, spawn 2 `--resume`s the same test session id with no
  `--session-id` (an ordinary continuation, not a rotation), and `RestartCount >= 1` (an externally-ended
  child sends no `restartCh` hint, so `Run` takes the backoff-increment path — the test deliberately does
  **not** copy `TestRunner_LiveRestart`'s `RestartCount == 0` assertion, which holds only because `Restart`
  itself sends that hint).

RED→GREEN verified via `-overlay` mutants under `-race` (the gate's flags), no worktree writes: a control
(`setArgsLocked` installs nothing), a kill mutant (`SetSpawnArgs` also calls `iterCancel`), a hint mutant
(`SetSpawnArgs` sends only the `restartCh` token), and a rotate mutant (`SetSpawnArgs` also sets
`rotatePending`) are all RED 3/3; baseline is green 3/3. Both `TestPool_UpdateSettings_*` files (14 tests)
pass unmodified, and neither appears in `git diff --name-only origin/main...HEAD`.

Code review: two rounds. Round 1 FAIL (one MUST FIX — half (a)'s settle didn't discriminate a kill under
`-race`; three SHOULD FIX — the `restartCh` hint effect unpinned, a false "no-child case" doc sentence on
`SetSpawnArgs`, a fourth stale `#1348` claim on `RunnerFactory`'s doc). Round 2 PASS after rework addressed
all four, with one residual SHOULD FIX (the capability-assertion pattern above) and one NIT, both left as
carried-over notes rather than a third pipeline lap.
