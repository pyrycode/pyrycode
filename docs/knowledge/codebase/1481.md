# Ticket #1481 — streamsup: fuse the spawn-id read and the iterCancel publish into one `restartMu` section

`Run`'s spawn setup read the rotation state (`nextSpawnID`) and published the iteration cancel
(`setIterCancel`) in two separate `restartMu` critical sections, with a `buildArgs` allocation and a
synchronous log write between them. `iterCancel` was still `nil` from the previous iteration across
that gap, so a `RestartFresh`/`Restart` landing there wrote its rotation, read `cancel == nil`,
cancelled nothing, and returned — while the spawn proceeded with the pre-rotation id/argv it had
already read. The child then ran under the stale id for its whole lifetime, and the next
crash-respawn silently discarded every turn since the rotation by consuming the still-set
`rotatePending` in first-run form. Neither branch of `RestartFresh`'s documented contract held. This
closes the window; #1482 (the `setStdin`/`rotating` disarm) was explicitly out of scope and stays
blocked on this landing.

## Implementation

- `internal/streamsup/runner.go`: new unexported `beginSpawn(ctx, firstRun) (iterCtx, cancel, args, forceFirst)` replaces `nextSpawnID` + `liveArgs` + the `Run`-local `buildArgs`/`WithCancel`/`setIterCancel` sequence with **one** `restartMu` acquisition that reads `args`/`sessionID`, consumes `rotatePending`, builds the argv, and publishes `iterCancel` — all under the same lock. `context.WithCancel` is constructed *before* the lock (it takes no runner lock, and `restartMu` must never be held across another package's internal locking).
- `nextSpawnID` and `liveArgs` are deleted outright (zero callers after the fuse; staticcheck's `unused` would have failed on either surviving as dead code).
- `setIterCancel(c context.CancelFunc)` is narrowed to `clearIterCancel()` — no argument, so publishing a non-nil cancel from anywhere but `beginSpawn`'s section is no longer expressible by the type signature, not just discouraged by convention.
- `Run`'s loop body calls `beginSpawn`, re-arms its local `firstRun` from the returned `forceFirst` (a plain assignment, not a `:=`, since a redeclare would shadow the outer `firstRun` and silently break the started-gated flip), logs `"spawning claude"` *after* the section (sync I/O must not run under a leaf mutex — this is also what puts a racer arriving at the log line on the already-published-cancel side of the invariant), then calls `spawnAndWait`/`cancel()`/`clearIterCancel()` as before.
- `internal/e2e/realclaude/interactive_background_idle_probe_test.go`: one comment-only retarget of a symbol-anchored citation from the deleted `setIterCancel` to `spawnAndWait` (verified accurate, not just compiling — `spawnAndWait` is where the `cmd.Env` hop actually lives).
- `docs/knowledge/features/streamsup-package.md`: all four sites naming the old two-section shape rewritten (the `Run` pseudo-code sketch, the #1124 paragraph, the Live-restart-seam paragraph, the `codebase/1124.md` see-also annotation) plus two wording fixes from code review (the "all three are read... published" clause at the Live-restart-seam paragraph; the `Restart` dichotomy sentence now states the third case the fix relies on — an iteration with a live `iterCancel` but no launched child yet, which a racing `Restart` can also catch).
- `docs/knowledge/INDEX.md`: the streamsup row's `#1124` paragraph named the deleted `nextSpawnID()` accessor directly; repointed to `beginSpawn()` with a note that `nextSpawnID` was folded into it.

## Patterns established

- **Fuse racing reads and publishes into one lock acquisition rather than narrowing the gap between two.** The two-section shape wasn't a bug in either section — each was individually correct under its own lock — the bug was the *unlocked interval between them*, during which the invariant the caller relies on ("a live cancel exists once a spawn's id is committed") didn't hold. The fix collapses the interval to zero rather than shrinking it, which is what makes the forbidden state unreachable-by-construction instead of merely low-probability. See [[developer-1481-inject-the-window-s-own-call-out]].
- **API narrowing as the safety net, not a comment.** `setIterCancel(c)` could express the defect (publish a cancel from anywhere); `clearIterCancel()` cannot. A future re-split has to add the parameter back before it can reintroduce the window — a deterministic guard belt-and-suspenders'd against the stochastic discipline of "don't do that," matching the pipeline's own belt-and-suspenders rule that a safety net must be different fabric from the thing it backs up.
- **A synchronous log write inside a race window is a deterministic test hook, not just a smell.** `slog.Handler.Handle` runs on the `Run` goroutine, so a test-only handler that fires the racer on the `"spawning claude"` record pins the interleaving at a fixed point in the statement order — no `time.Sleep`, no repetition count, no calibration. Reusable wherever a race window contains an injectable call-out (`Config.Logger`, `Config.Stdout`, any hook already threaded through for other reasons).

## Lessons learned

From the PR body (developer-flagged, non-obvious):

- The window had exactly one synchronously interceptable statement inside it — the `"spawning claude"` log write. `slog.Handler.Handle` running on the `Run` goroutine turns an injected `Config.Logger` into a fixed point in the statement order: no sleep, no repetition, no window calibration. When a race window contains a call-out the test can inject, that call-out is the deterministic hook — see the pattern above.
- "Which spawn attempts actually launched a child" is directly observable without polling: `onSpawn` fires after `cmd.Start`, on the same single goroutine that logged the attempt, so inside `onSpawn` the *last* recorded argv is that child's. Attempts torn down before `cmd.Start` leave no entry, which is exactly the distinction the invariant needs ("no child ever ran under the pre-rotation id"), not the weaker "some spawn used the right id."
- Narrowing the API beat adding a comment — see the API-narrowing pattern above; recorded here as the reasoning trail, not just the resulting convention.

## Testing

`go test -race -count=1 ./internal/streamsup/` green (full package: `ok … 4.614s`); `go vet ./...`,
`staticcheck ./internal/streamsup/...`, `make cite-guard` pass; `go vet -tags e2e_realclaude
./internal/e2e/realclaude/` compiles (comment-only edit there).

**AC4 mutation evidence (both trees run, both recorded):** the mutant is the merge-base `runner.go`
plus a `beginSpawn` shim reproducing the pre-fix split shape (`nextSpawnID`, released, then
`setIterCancel`), applied via `go test -overlay` with no worktree writes; `go vet -overlay=…` confirmed
clean first so the RED is a test failure, not a compile error.

- **Mutant, RED:** `TestRunner_RestartFreshRacesSpawnSetup` and `TestRunner_RestartRacesSpawnSetup`
  both FAIL — a child launches under the pre-rotation id / pre-swap argv, and the spawn-attempt/launch
  count comes back `1`/`1` instead of the expected `2`/`1` (the racing request must cancel the
  iteration it raced, leaving that attempt `started == false`).
- **Shipped tree, GREEN:** both new tests pass; code review independently re-ran the mutant and the
  shipped tree rather than trusting the PR's numbers, plus `-race -count=10` on the shipped tests to
  probe the `rec.count() == 2 && len(launched) == 1` assertions for order-flakiness (stable — the
  interleaving is pinned by the log hook, not timing).

Code review (PASS, PR #1569) independently verified `os/exec.Cmd.Start` on the toolchain in use
(go1.26.2) returns `ctx.Err()` from a `select` above the fork and above any `cmd.Process` deref, so the
`started == false` relay is real and not merely asserted; confirmed `buildArgs` copies `base` rather
than retaining it (justifying the dropped `slices.Clone`); swept the package for surviving references
to the three deleted/narrowed accessors (none outside frozen per-ticket spec/codebase artifacts); and
confirmed the argv `beginSpawn` builds is byte-identical to what the old two-section code built,
which is why `needs-real-claude` stays correctly omitted. Three NITs, all documentation wording,
none blocking — two addressed in this pass (the `streamsup-package.md` wording above), the third
(the stale `nextSpawnID` mention in `INDEX.md`) addressed in this pass too since it names the
documentation phase as sole writer.
