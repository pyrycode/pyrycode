# Ticket #1364 — Probe instrument: prove the published trailer key-name bounds bite, over fixtures that fail on their own preconditions (offline)

#1363 shipped `finBoundKeyNames` and stated five clauses in its doc comment —
none pinned. The artifact's standing safety sentence
(`finWriteSafetyClaim`, `finding_artifact_write_test.go:124`) describes the
trailer key-name field as bounded, so until this ticket "bounded" was a claim
an operator relied on rather than a checked property. This ticket pins all
five clauses, offline, with fixtures built to fail on their own preconditions
rather than pass through them — the hazard named up front in the ticket body:
`trailScan`'s `bufio.Scanner` buffer aborts past 64 KiB rather than
truncating, so a naive hostile fixture that grows past it renders the names
field `null` and every bound assertion over it passes having proved nothing.

## Implementation

- **One new file, nothing else touched.**
  `internal/e2e/realclaude/finding_key_name_bounds_test.go` (382 lines,
  `//go:build e2e_realclaude`). Placement was the ticket's own zero-risk
  recommendation: a new file adds no line to any existing file, so the
  inbound-cite-preservation AC (four named thresholds across four files) holds
  by construction rather than by argument. The file's header states the
  reference to `finBoundKeyNames` is **one-directional** — the new file cites
  the helper, the helper says nothing about the new file — specifically so a
  later editor does not "fix" the family's usual name-the-test-at-the-contract
  convention into a cite-sweep-triggering edit.
- **Two hostile fixtures, both functions (never package-level vars, since this
  package runs `-race` in parallel):**
  - `finOverlongKeyName()` — one key name sized `finTrailerMaxKeyNameBytes + 1`
    bytes off the constant, with a descriptive stem so a failure message shows
    *what* was truncated.
  - `finOverlongKeyNameTrailer()` — `trailPaddedTrailer(0)` with that name
    spliced in as one extra top-level key. Splicing onto the shipped renderer
    (rather than a fresh literal) is what makes the fixture's other eleven
    names the *real* envelope names, so `trailExpectedKeyNames()` is a valid
    expectation for "the line's short names are still published unchanged."
  - `finManyShortNames(n)` / `finManyKeyNamesTrailer(extra)` — `extra`
    synthetic short keys beside the mandatory `"type":"result"` (without which
    `trailScan` never matches and the row would compare two empty reads).
    Called with `finTrailerMaxKeyNames`, so the fixture sizes itself off the
    constant rather than a hard-coded count.
  - Measured on this tree: 457 bytes / 273 bytes, both two orders of magnitude
    under the 65535-byte scanner ceiling.
- **The drive helper, `finPublishedKeyNames`,** chains
  `trailScan` → `finTrailerSighting` → `finTrailerBuild` and returns both the
  unbounded reader output and the published (bounded) names, so a row can
  assert both halves entirely from shipped code. It stops at `finTrailerBuild`
  deliberately — the remaining hand (`finRecordBuild` embedding the sub-record
  whole) is already pinned by `TestFinRecordEmbedsTrailerRecordWhole` and
  `TestFinRecordPublishesTheTrailerKeyNamesTheReaderRead`
  (`finding_run_record_test.go`), so driving a fourth hand would add cost and
  no discrimination. **The fatal precondition is the ceiling defence**: it
  asserts `scan.State == trailSeen` and a non-nil decode before anything else,
  reporting `scan.Detail` (this rig's own prose, no line bytes) rather than
  `scan.Line` in the failure message — the security review's one actionable
  finding, honoured.
- **Four tests, one per clause-group:**
  - `TestFinPublishedKeyNamesBoundAnOverLongName` (AC1) — asserts, per
    published name and marker-aware
    (`len(strings.TrimSuffix(name, reachTruncationMarker))`), that no name
    keeps more than the per-name bound *from the line*; `len(name) <=
    finTrailerMaxKeyNameBytes` is explicitly the wrong assertion since the
    marker adds 29 bytes on top, publishing a truncated name at 93 bytes. One
    `reflect.DeepEqual` against `trailExpectedKeyNames()` plus the truncated,
    marked entry (sorted) covers both "bounded" and "still present, not
    dropped."
  - `TestFinPublishedKeyNamesBoundTheNameCount` (AC2) — asserts the published
    count is *exactly* `finTrailerMaxKeyNames` (not "at most" — that's
    trivially true of an empty field) and that the kept set is the reader's
    alphabetic prefix; the fixture's `type` sorts last of the 33 names and is
    the one the cut removes, the exact consequence
    `finTrailerRecord`'s own comment warns a reader about.
  - `TestFinBoundKeyNamesReturnsNilForEmptyInput` (AC3 clause 1) — direct
    call, two rows (`nil`, `[]string{}`), asserts `nil` specifically —
    `len(got) == 0` is exactly the mutant this guards against, since a
    non-nil empty slice marshals to `[]` where a not-seen record must render
    `null`.
  - `TestFinBoundKeyNamesAllocatesItsOwnBackingArray` (AC3 clause 5) — direct
    call, three rows (under both bounds / over the count bound / over the
    per-name bound), each asserting `&got[0] != &in[0]`. Content (`want`) is
    asserted on the fast-path row alone — see Lessons learned below for why
    the other two rows' `want` was removed during development.

## Review cycle

One pass, **PASS**, no MUST FIX. Three NITs, all non-blocking:

1. The spec's mutant matrix claimed the over-count-returns-nil mutant reds on
   exactly one row; measured, it reds on two (see Lessons learned).
2. The header comment's claim that `sort.Strings` on the AC1 expectation is
   valid "because truncation keeps the first `finTrailerMaxKeyNameBytes`
   bytes" holds for this fixture but isn't universal — two names sharing a
   64-byte prefix would collapse to one string. `finBoundKeyNames`' own doc
   comment already names this; correct as written for what this row drives.
3. **`finding_run_gather_test.go:581`**, the *live-fill* call site of
   `finBoundKeyNames` (as opposed to `finTrailerSighting`'s fixture-side
   call), is not driven by any test in this package — a mutation dropping the
   bound at that call site specifically stays green. Outside this ticket's
   ACs (scoped to the helper's five clauses, proven reachable through either
   fill), recorded here for whoever next touches that call site to pick up.

Security review (spec self-review, ticket carries `security-sensitive`):
**PASS**. Confirmed both `finSighting.KeyNames` fill sites route through
`finBoundKeyNames` with no unbounded path to the published field, and that no
failure message in the new file interpolates `scan.Line` or `trailNeedle`.

## Patterns established

- **A fatal non-vacuity guard can widen a mutant's red past a spec's
  predicted sole-redness, and that's correct, not a sign the design is
  loose.** The spec's matrix predicted the over-count-returns-nil mutant
  would be red on `…BoundTheNameCount` alone; it's also red on
  `…AllocatesItsOwnBackingArray`'s over-the-count row, because that row's
  prescribed `len(got) == 0` fatal (guarding the `&got[0]` address
  comparison from indexing nothing) fires on a nil result too. Expect this
  whenever a design's mutant matrix claims sole-redness for a mutant that
  empties a result some *other* row separately guards against with its own
  fatal precondition.
- **Asserting content on every row of a fast-path-only test costs
  sole-redness for no benefit.** A first draft carried a `want` on all three
  `…AllocatesItsOwnBackingArray` rows; that made the count-bound mutant red
  in two tests with the second message adding nothing, since the published
  tier already pins those contents over real fixtures. `want` is now set on
  the fast-path row alone — the one row whose contents the helper must leave
  untouched, and the only row nothing else in the file pins.
- **A hostile fixture for a resource-bounded reader needs its own ceiling
  argument, not just a bound violation.** Both fixtures here are a few
  hundred bytes specifically to stay under `trailScan`'s 64 KiB scanner
  ceiling — past it the scan *aborts* rather than truncating, which would
  make every bound assertion vacuously true over a record that published
  nothing. The drive helper's fatal `trailer-seen` precondition is the
  reusable shape for this: assert the state that would make the row
  vacuous, before asserting the bound itself.

## Lessons learned

(From PR #1370's body and its code-review comments; PR: "Prove the published
trailer key-name bounds bite (#1364)".)

- Same fatal-guard and content-assertion lessons as recorded under Patterns
  established above — both were flagged by the developer as PR-body "Lessons
  learned" and are load-bearing enough to repeat there rather than bury as
  pure implementation detail.
- **A spec's own explored-and-cut design decision is worth stating in the
  shipped file even when it goes nowhere near the diff.** The ticket measured
  and explicitly rejected adding a second row under
  `TestFinTrailerRecordCarriesNoCapturedBytes` for the Detail-interpolation
  prohibition — the over-long-name fixture's names-interpolating mutant
  reaches 444 bytes against the 470-byte headroom budget and would have
  shipped green over the violation it claims to detect. That reasoning is
  recorded in the ticket body rather than re-derived by #1362, which inherits
  the obligation via a names-field-only needle sweep instead (no dependence
  on a byte budget).
