# Ticket #1116 — deterministic bootstrap-readiness wait in `pool_test.go`

Replaced three wall-clock `pool.Default().State().ChildPID > 0` poll loops (fixed 2s deadline,
20ms `time.Sleep` step) in `internal/sessions/pool_test.go` with an event-driven wait on the
existing `Supervisor.WaitForPTY` readiness signal — the same signal `Session.Activate` already
funnels through ([ADR 023](../decisions/023-activate-waits-pty-readiness.md)). Under `-race`'s
scheduling slowdown, `pty.Start` could exceed the 2s budget, tripping `bootstrap child never
started` as a timing artefact rather than a real defect — a recurring flake family previously seen
under #823/#924/#949/#1024, most recently unmasked (not caused) by PR #1115/#1109. Test-only;
zero production change.

## Implementation

- **`waitBootstrapReady(t *testing.T, pool *Pool)`** (`pool_test.go`) — the single replacement for
  all three sites. Derives a `context.WithTimeout(context.Background(), 30*time.Second)` backstop,
  calls `pool.Default().sup.WaitForPTY(ctx)`, `t.Fatalf`s on non-nil error. `sup` is the unexported
  `Runner` field on `*Session`; reachable directly because the test file is `package sessions` — no
  production accessor added.
- Replaced at:
  - `TestPool_Run_StartsWatcher` (RotateID bootstrap wait) — the downstream jsonl-write +
    on-disk-registry poll (a *different* synchronization point, `RotateID`'s `saveLocked`) is
    unchanged and stays a 2s poll; it has not been observed flaking.
  - `TestPool_Supervise_AfterRunReturns_ReturnsErrPoolNotRunning`
  - `TestPool_Supervise_ConcurrentCalls_RaceClean`
- The explicit `if ChildPID == 0 { t.Fatal(...) }` re-check at each site was removed, not kept
  redundantly: `setSession` (which closes `sessReadyCh` and unblocks `WaitForPTY`) runs one line
  after `onSpawn` sets `ChildPID` (`supervisor.go` `runOnce`), so readiness *implies* a live,
  non-zero PID — re-checking it would just reintroduce a smaller timing dependency for no coverage
  gain.
- `Pool.Ready()` was considered and rejected as the signal: it closes as soon as `Pool.Run` has
  *scheduled* the bootstrap's `sess.Run` goroutine, before the child has actually spawned — it
  would not guarantee the live PID site 1's rotation watcher needs to probe.

## Patterns established

- **ADR 023's `WaitForPTY` readiness signal is now the standard test-side replacement for
  `ChildPID > 0` polling**, not just a production-code pattern. Confirms the shape is reusable
  wherever a test needs to observe "bootstrap child has spawned" deterministically.
- The identical `pool.Default().State().ChildPID > 0` poll (via the shared `pollUntil` helper, 2–10s
  budgets) still exists at ~20 sites across `pool_cap_test.go`, `pool_get_or_create_test.go`,
  `pool_create_test.go`, `pool_remove_test.go`. Deliberately **not** migrated here — those sites have
  not been observed flaking, and migrating them would have pushed this ticket past S (4 extra
  files, >5 edit sites). If the same flake shape recurs at one of those sites, migrate it there
  using this ticket's `waitBootstrapReady` as the template; don't preemptively touch them.

## Lessons learned

- Code review (PR #1117, PASS) noted one non-blocking NIT: on backstop expiry (`waitBootstrapReady`
  → `t.Fatalf`), sites 2 & 3 no longer drain `cancel(); <-done` before failing (the old
  `if ChildPID == 0 {...}` branch did). This leaks the `pool.Run` goroutine and its `/bin/sleep
  3600` child until process exit on that path. Immaterial in practice — the 30s backstop only trips
  on an already-wedged bootstrap — and was explicitly sanctioned by the spec's per-site edit
  instructions. Worth a one-line `cancel(); <-done` restore inside `waitBootstrapReady`'s error path
  if this class of test is ever hardened further, but not required.
- QA's run on this PR turned up three pre-existing, unrelated `cmd/pyry` ACP test failures
  (`TestACPConformance_FullSessionDrive`, `TestACP_SessionLoad_ResumesExistingClaude`,
  `TestACP_SessionNew_SpawnsOneInteractiveClaude`), confirmed present on both baseline and PR HEAD
  and filed separately as #1118. `internal/sessions` — the package this ticket actually touches —
  passed cleanly. Noted so a future pass doesn't re-diagnose #1118 as caused by this change.
