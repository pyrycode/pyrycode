# Ticket #842 — live-apply per-session settings by restarting the running session

`#845` persists a `set_session_settings` change (model/effort/YOLO) via `Pool.UpdateSettings`, but the new values previously reached claude only on the session's *next spawn* — a running session kept its stale settings until an unrelated crash or eviction restarted it. #842 adds the missing live-restart seam and drives it from `UpdateSettings`'s successful-persist tail, so one client message both persists and takes effect on the currently-running child. `security-sensitive`: the YOLO fail-safe-OFF invariant must survive the induced restart.

See [ADR 031](../decisions/031-settings-restart-fire-and-forget.md) for the fire-and-forget / induced-child-exit design rationale, and `docs/specs/architecture/842-live-restart-on-settings-change.md` for the full spec (including the § Security review, verdict PASS).

## Implementation

Two packages, six files (~845 LOC incl. tests, no new production file):

- **`internal/supervisor/supervisor.go`** — new `Supervisor.Restart(args []string)`, the seam `sessions` calls. Adds `restartMu` (a new **leaf** mutex — never nested with `mu`/`sessMu`/`convMu`) guarding three fields: `claudeArgs` (the live spawn args, read via `liveArgs()` at the top of each `Run` iteration instead of the immutable `cfg.ClaudeArgs`), `iterCancel` (the current iteration's cancel func, published by `setIterCancel`), and `restartCh` (buffered 1, a coalescing "deliberate restart" hint). `Run` now runs each iteration on `iterCtx, cancel := context.WithCancel(ctx)` and moves shutdown detection from the child-exit error to the *parent* ctx (`if ctx.Err() != nil { return ctx.Err() }`) — this is what lets an `iterCtx`-only cancel (a `Restart` kill) fall through to relaunch instead of being mistaken for shutdown. Post-`runOnce`, `drainRestart()` non-blockingly checks the hint: present → skip backoff and relaunch immediately (a settings restart is not a crash); absent → the normal backoff wait, which now also selects on `restartCh` so a restart arriving *during* backoff (child already crashed) interrupts the wait.
- **`internal/sessions/session.go`** — `Session.spawnBase []string`, the settings-free argv (template/bootstrap args + any construction-time resume suffix, e.g. `--session-id <id>` for a minted session), stored alongside the existing full `ClaudeArgs`. New `Session.spawnArgs(settings SessionSettings) []string` — `append(slices.Clone(s.spawnBase), claudeSettingsArgs(settings)...)` — the **single** argv-recompose path outside construction, reusing #833's `claudeSettingsArgs` so the YOLO fail-safe has exactly one origin.
- **`internal/sessions/pool.go`** — `Pool.New` (bootstrap) and `Pool.buildSession` (minted) now compute and store `spawnBase` alongside the existing full-args construction (byte-identical resulting argv). `UpdateSettings`'s `defer p.mu.Unlock()` became explicit unlocks so the restart trigger runs **outside** `Pool.mu`: after a real change persists successfully, `newArgs := sess.spawnArgs(merged)` and `sup := sess.sup` are captured under `p.mu`, the lock is released, then `sup.Restart(newArgs)` runs unlocked. Not-found, no-op, and persist-failure paths all return before this point — `Restart` is never called for them, so an unknown id, an identical-value update, or a failed save never disturbs a running child.

`Restart` is called unconditionally on any real settings change, for both running and evicted sessions — the argv swap always happens; only the kill is conditional on a live `iterCancel`. This incidentally closes a latent gap #833 left open: a *reused* supervisor (evict → activate within one process) previously re-ran with stale baked args; now `Activate` after an `UpdateSettings` call picks up the swapped args for free.

## Concurrency

No new goroutine — the restart runs on the supervisor's existing `Run` goroutine (already owned by `runActive`) plus the caller's dispatch goroutine (which only swaps a slice and sends a non-blocking signal). `restartMu` is leaf-only: `Restart` releases it before calling the captured `cancel()`. Lock order `Pool.mu → Session.lcMu` (`docs/lessons.md`) is untouched — `Restart` never acquires `Pool.mu` or any `Session.lcMu`, and `UpdateSettings` releases `Pool.mu` before calling it. Because the restart keeps `Supervisor.Run` running (it loops internally rather than returning), `runActive`'s `<-runErr` never fires and the session's active/evicted state machine doesn't see the restart happen at all.

## Security

The bypass flag (`--dangerously-skip-permissions`) has exactly one origin, `claudeSettingsArgs`, reused verbatim by the new `spawnArgs` recompose path; `spawnBase` is operator-controlled (template/bootstrap args + `--session-id`) and never YOLO-derived. So no persisted-`false` state can recompose into a bypass child across a restart. The restart is additionally a **net security improvement** on the pre-#842 behavior: without it, flipping YOLO `true→false` would persist `false` while an already-running `--dangerously-skip-permissions` child kept executing indefinitely; the unconditional kill on a real settings change now terminates that bypass child promptly. Code review confirmed this with dedicated tests (`TestPool_UpdateSettings_YOLORevoke_DropsBypassOnRestart`, `..._YOLOAbsent_NoBypassOnRestart`).

## Testing

`go test -race ./...`, `go vet ./...`, `go build ./cmd/pyry` all pass. New coverage: `internal/supervisor/restart_test.go` (byte-identical baseline when `Restart` is never called, swap-and-skip-backoff on a running child, swap-only when no live child, during-backoff interrupt, shutdown still returns a context error, two rapid restarts coalesce to one relaunch with the latest args) and `internal/sessions/pool_update_settings_restart_test.go` (bootstrap `--continue` restart, minted `--session-id` restart, single-call persists-and-relaunches, no-op and persist-failure skip the relaunch, evicted-session swap-only, YOLO revoke/absent bypass assertions).

Code review: **PASS**, two NITs (non-blocking, left as-is):

- A `Restart` on an evicted session leaves a `restartCh` token pending until the *next* `Activate`'s first child exit, which then skips one backoff. Benign — the token is content-free and `claudeArgs` is read independently, so a stale-vs-fresh token is indistinguishable and the relaunch args are always correct.
- The minted-session restart relaunches with a bare `--session-id <id>` (no `--continue`) — the fake-recorder test harness can't prove real `claude --session-id <existing-id>` *resumes* rather than forks/errors on a second spawn. Flagged in the spec's Open Questions as needing confirmation before any consumer drives minted-session live-restart; not a blocker for the primary (bootstrap) path, which is fully covered.

Also hit and cleared the known pre-existing environmental red (`TestPtyRunnerVsStreamRunner_StructuralEquivalence`, `thinking_tokens` model-nondeterminism — same flake noted in [codebase/840.md](840.md) and [codebase/845.md](845.md)) — reproduces identically on `main`, exercises zero changed code paths.

## Lessons learned

- **`restartCh` must be sent unconditionally, not gated on a live child.** During backoff, `iterCancel` is already `nil` (no iteration running). A "send the hint only if `cancel != nil`" version of `Restart` would never break the backoff-wait `select`, so the during-backoff-interrupt AC would silently fail. The correct shape: always send the (buffered, coalescing) hint; only the `cancel()` call is gated on a live child.
- **Testing `--continue` end-to-end needs a script-file fake claude, not `sh -c SCRIPT`.** `ResumeLast` prepends `--continue` to the whole argv; `sh --continue …` rejects the flag as invalid `sh` usage instead of passing it through. A standalone recorder script file records the leading `--continue` as a plain positional argument, which is what the bootstrap-restart test needed to assert on.
