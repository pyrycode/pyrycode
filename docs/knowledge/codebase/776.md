# Ticket #776 — Sign the `pyry update` checksums file (integrity beyond "GitHub served it")

Adds a detached Ed25519 signature over `checksums.txt`, verified against a public key compiled into the pyry binary **before** any digest is parsed from it. Previously the update path's integrity rested entirely on "GitHub served both files honestly": a compromised release pipeline or a stolen publishing token could serve a matching `(tarball, checksums.txt)` pair and the SHA-256 check would pass against attacker-chosen bytes → arbitrary code over the running binary via `AtomicReplace` + restart. The signature breaks the "trust whoever published the release" assumption — without the separately-custodied private key an attacker cannot pass the gate. Severity LOW (operator-invoked over HTTPS); scheme rationale in [ADR 028](../decisions/028-ed25519-checksums-signature.md).

## Implementation

- **New primitive `internal/update/signature.go`** — `VerifySignature(data, sig []byte, pub ed25519.PublicKey) error`, a pure function (no I/O, no context, no goroutines) mirroring `checksum.go`'s pure-function + exported-sentinel shape. Returns `nil` iff `pub` is 32 bytes, `sig` is 64 bytes, and `ed25519.Verify(pub, data, sig)` is true. Two sentinels:
  - `ErrInvalidSignature` — the sig does not verify **or** is not exactly `ed25519.SignatureSize` (64) bytes. One sentinel because a caller only ever branches "signed correctly vs not."
  - `ErrInvalidPublicKey` — the supplied key is not exactly `ed25519.PublicKeySize` (32) bytes. **The length checks run before `ed25519.Verify` so a malformed key/sig yields a sentinel error instead of `ed25519.Verify` panicking.** Error strings are clean sentinel-carriers — never the key or signature bytes.
- **Baked-in trust root** — `const releaseSigningPublicKeyHex` in `cmd/pyry/update.go` (hex-encoded raw 32-byte Ed25519 public key). Kept as a package-level constant, not a new file, to hold the new-file count at 3. Its doc comment records the `openssl genpkey`/`openssl pkey … | tail -c 32 | xxd -p` generation recipe and points at `docs/release-tooling.md`.
- **`runUpdate`** decodes the constant (`hex.DecodeString` + 32-byte length check → wrapped `update: signing key: …` on failure) and sets a new `signingPubKey ed25519.PublicKey` field on `updateOptions`. This field is the test seam: production sets it from the constant; tests inject a throwaway test key, never the production private key.
- **The gate in `doUpdate`** — inserted between the `checksums.txt` `FetchAsset` and `ParseChecksumsFile`: fetch `checksumsURL + ".sig"` → `update.VerifySignature(sumsBytes, sig, o.signingPubKey)`, both wrapped (`update: download signature: …` / `update: verify signature: …`). Verify runs over the **raw fetched bytes** (no trim/normalize) — the signature covers the exact file GoReleaser signed. A progress line `==> Verifying signature... ok` / `FAIL` mirrors the SHA-256 line.
- **Fetch order:** tarball → checksums → **signature → verify-signature** → parse-checksums → verify-SHA256 → extract → replace → restart. Tarball-first is unchanged, so the pre-existing `FetchFailure` e2e (which 500s the tarball) still aborts before any signature logic.
- **Release pipeline** — `.goreleaser.yaml` gains a `signs:` block (`artifacts: checksum`, `signature: "${artifact}.sig"`, `cmd: openssl pkeyutl -sign -inkey {{ .Env.PYRY_SIGNING_KEY_FILE }} -rawin …`). `.github/workflows/release.yml` materializes the private key from the `PYRY_RELEASE_SIGNING_KEY` secret into a `0600` temp file under `${RUNNER_TEMP}` (destroyed with the job) and passes its path via `PYRY_SIGNING_KEY_FILE` to the goreleaser step — mirroring the existing `HOMEBREW_TAP_TOKEN` threading.
- **New `docs/release-tooling.md`** — the operational deliverable (AC-5), referenced by `release.yml` but previously missing. Documents keypair generation, private-key custody (a repo Actions secret distinct from and tighter than the publishing token), keeping public/private matched, and the first-signed-release smoke test.

## Patterns established / reinforced

- **Fail-closed is structural, not a flag.** The sig-fetch + verify are *unconditional* steps between fetch and parse. There is no code path from "signature missing/bad" to "proceed unsigned." A 404 on the `.sig` surfaces as a `FetchAsset` error and aborts exactly like a missing tarball — the same fail-closed shape the missing-tarball path already had. This is the AC-2 downgrade defense: an attacker who *deletes* the signature cannot downgrade the check.
- **Length-check before `ed25519.Verify`.** `ed25519.Verify` panics on a wrong-length public key; guarding length first turns a malformed baked-in constant (or a garbage `.sig`) into a returned error, not a panic. `TestReleaseSigningKey_Decodes` asserts the constant decodes to 32 bytes so a typo is caught at test time, not release time.
- **OpenSSL-and-`ed25519.Sign` share one wire.** `openssl pkeyutl -sign -rawin` over an Ed25519 key emits the raw 64-byte RFC 8032 signature `ed25519.Verify` accepts directly — no envelope, no algorithm tag, no BLAKE2b prehash. Because Ed25519 is deterministic/canonical, the OpenSSL output is byte-identical to `ed25519.Sign` for the same key+message, so tests that sign fixtures in-process with `ed25519.Sign` fully exercise the production CI verify path with zero new dependencies.
- **Intentional both-ends coupling** (same as `AssetName` ↔ `.goreleaser.yaml`): the `.sig` suffix in `doUpdate`'s `sigURL` and `.goreleaser.yaml`'s `signature: "${artifact}.sig"` must agree; both live in this repo and move together.

## Tests

- `internal/update/signature_test.go` — table-driven: valid → nil; tampered data → `ErrInvalidSignature`; wrong key → `ErrInvalidSignature`; truncated/over-length sig → `ErrInvalidSignature` (not a panic); wrong-length public key → `ErrInvalidPublicKey` (not a panic); empty data with a valid empty-data sig → nil.
- `cmd/pyry/update_test.go` — a deterministic throwaway keypair (`testSigningPriv/testSigningPub` from `ed25519.NewKeyFromSeed`); `newFakeReleaseServer` now auto-signs the checksums it serves and exposes them at `checksums.txt.sig` with its call signature unchanged (so all existing callers keep working); `updateOptions` literals that reach the gate set `signingPubKey: testSigningPub`. New `TestUpdate_MissingSignature` (404 on `.sig` → `download signature` error, `replace` sentinel not called), `TestUpdate_BadSignature` (`.sig` signed by a different key → `verify signature` error), and `TestReleaseSigningKey_Decodes`.
- `cmd/pyry/update_e2e_test.go` — new `TestUpdate_MissingSignature_E2E` (mirrors `FetchFailure_E2E`: server serves tarball + checksums, 404s the `.sig`) asserts abort before `AtomicReplace`, inode unchanged, daemon still answering, success line absent — the integration-level AC-2 downgrade proof.
- AC-4 (pipeline emits the signature) is validated by `goreleaser check`; a real signed release is the operator's first-release smoke test.

## Lessons learned

- **The `//go:build e2e_update` suite was un-runnable before this change.** `spawnDaemonE2E` never set `cmd.Dir`, so the spawned daemon inherited the test process's cwd (the package dir) and the workdir-confinement guard aborted startup for the whole suite. This was pre-existing and went unnoticed because **CI does not run the `e2e_update` tag**. Fixed with a one-line `cmd.Dir = home` in the shared helper (required for the new e2e test's daemon to start at all). Takeaway: a build-tagged suite CI never runs can silently rot; the tag's tests only get exercised when someone runs them locally.
- **`openssl pkeyutl -sign -rawin` over Ed25519 = raw RFC 8032 signature, no prehash.** This is what lets the CI signer and the Go verify path share one format with zero new deps. minisign's default `ED` mode would have prehashed with BLAKE2b-512, forcing a new hash dependency — the reason a bare raw signature was chosen over the minisign envelope (see [ADR 028](../decisions/028-ed25519-checksums-signature.md)).
