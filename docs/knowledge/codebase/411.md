# Ticket #411 — `agent-run --disallowed-tools` → settings `permissions.deny`

`pyry agent-run` gains an optional `--disallowed-tools` flag whose tokens land in the per-spawn settings file's `permissions.deny`, mirroring the existing `--allowed-tools` → `permissions.allow` wiring. Listing claude's human-interaction tools (`AskUserQuestion`, `EnterPlanMode`, `ExitPlanMode`) there removes them from the model's tool surface **entirely** — not offered, not called, no runtime-denial event. This is the enforcement lever the 2026-07-04 spike settled on, replacing the ticket title's stale "forward `--disallowed-tools` to claude as a CLI flag" shape (which targeted the legacy `PYRY_USE_STREAMJSON=1` path that doesn't even offer these tools). Origin: [#398](398.md) — a developer agent called `AskUserQuestion`, work stranded, PR #410 recovery.

Companion **agent-dispatcher#7** (done manually alongside) makes the dispatcher pass `--disallowed-tools "AskUserQuestion,EnterPlanMode,ExitPlanMode"`. Ordering constraint: this pyry side must ship **and `pyry` be rebuilt/reinstalled** before the dispatcher flips, or every dispatch errors on the unknown flag.

## Implementation

- **`internal/agentrun/settings/settings.go`** — additive entry point, not an atomic signature change:
  - `permissions` struct gains `Deny []string \`json:"deny,omitempty"\`` positioned **between** `Allow` and `DefaultMode` (present-case key order reads `allow, deny, defaultMode`). `omitempty` is load-bearing: nil / `len==0` → the `deny` key is dropped → bytes byte-identical to today for every deny-less caller.
  - Three functions replace the one: unexported `writeSettings(allowed, disallowed []string)` core (the old `WriteSettings` body verbatim + `Deny: disallowed` in the literal, keeping the `len(allowed)==0` guard and its exact error string `agentrun/settings: allowedTools required`); `WriteSettings(allowed []string)` → `writeSettings(allowed, nil)`; new `WriteSettingsWithDeny(allowed, disallowed []string)` → `writeSettings(allowed, disallowed)`. Deny is **never** validated for emptiness — empty is the legal "no deny key" case.
- **`cmd/pyry/agent_run.go`** — pure pattern-echo of the allow path:
  - Seam `settingsWrite = settings.WriteSettings` → `settings.WriteSettingsWithDeny` (its inferred type becomes `func([]string, []string) (string, error)` — the sole driver of the test-mock edits).
  - New optional `fs.String("disallowed-tools", "", "…denylist (optional)")` flag; `disallowedTools []string` field on `agentRunArgs`; parse via `parsed.disallowedTools = splitAllowedTools(*disallowedTools)` (reused verbatim — pure tokeniser, name stays historical). No required/non-empty check.
  - Call site: `settingsWrite(parsed.allowedTools, parsed.disallowedTools)`.
- **Untouched by construction** (the whole point of the additive design): `internal/agentrun/selfcheck` keeps its own 1-arg `settingsWrite = settings.WriteSettings` seam; the realclaude byte-equivalence pin (`internal/e2e/realclaude/ptyrunner_byte_equivalence_test.go:436`) stays on `settings.WriteSettings(allowedTools)`; the existing settings golden-byte tests are unmodified. This is the cleanest possible evidence for AC3 (back-compat, byte-unchanged) — the tests that prove nothing regressed are themselves unchanged.
- **Legacy `PYRY_USE_STREAMJSON=1` path out of scope** — `buildStreamRunnerClaudeArgs` doesn't offer these tools, so no deny is load-bearing there. Left untouched.

Data flow: `--disallowed-tools "A,B,C"` → `splitAllowedTools` → `[A,B,C]` → `WriteSettingsWithDeny(allow, [A,B,C])` → `{"permissions":{"allow":[…],"deny":["A","B","C"],"defaultMode":"dontAsk"},"enableAllProjectMcpServers":true}` → `--settings <path>` → claude omits A,B,C from the model's surface. Absent / empty flag → nil deny slice → `deny` key omitted → bytes identical to today.

## Patterns established

- **Additive sibling + shared unexported core to extend a byte-golden-pinned writer.** When a function's exact output bytes are the contract (golden tests) and back-compat requires "absent input → byte-unchanged", don't change the signature (that ripples to ~20 call sites and dirties the very byte-equivalence tests that prove no regression). Add a wider sibling (`WriteSettingsWithDeny`), keep the narrow entry point (`WriteSettings`) as a `(…, nil)` wrapper, and route both through one private core. Forced compile edits dropped from ~20 to 7. This is the concrete instance of the architect's additive-entry-point call (spec § "Decision: additive entry point").
- **`omitempty` makes "optional field absent → byte-unchanged" structural, not a special case.** No branch, no "if empty skip" logic — the JSON encoder drops the key, and the golden test for the empty case simply asserts byte-equality against the pre-existing allow-only golden. AC3/AC4 fall out of the struct tag.
- **Reuse the tokeniser across allow and deny despite the allow-specific name.** `splitAllowedTools` is a pure `strings.FieldsFunc` tokeniser; renaming to `splitToolList` would ripple the call site + `TestSplitAllowedTools` for marginal gain. Simplicity-first: reuse as-is, note the historical name.

## Lessons learned

- **The enforcement lever was mis-named in the ticket title for months.** The title said "forward `--disallowed-tools` to claude" — a CLI flag on claude's argv. The 2026-07-04 spike (two real interactive PTY sessions) proved that shape is stale: it predates the 2026-05-19 pivot to settings-file tool-gating and targeted the legacy stream-json path that doesn't offer these tools. The correct lever is the same `permissions.deny` in the `--settings` file that `permissions.allow` already flows through. Lesson: when a ticket title names a mechanism, re-confirm the mechanism against the current architecture before building — the settled design (`deny` list) removes the tool from the surface entirely, whereas the stale design (argv flag) at best produces a runtime denial that wastes a turn and arms the agent-dispatcher#8 watchdog.
- **`deny`-list removal is strictly better than runtime denial under `dontAsk`.** With no deny entry, a human-only tool is offered, called, and runtime-denied ("Permission to use … denied … don't ask mode") — the same runtime-denial-then-watchdog shape as tui-driver#185. With the name in `deny`, the tool never reaches the model. Clean surface removal, not a late reject.

## Out of scope (deferred)

- **Legacy `PYRY_USE_STREAMJSON=1` symmetry.** `buildStreamRunnerClaudeArgs` could grow a `--disallowed-tools` forward for parity, but no deny is load-bearing there (the path doesn't offer these tools). Optional, not required by any AC. Pick up only if the streamrunner path ever starts offering interaction tools.
- **`splitAllowedTools` rename.** Reused as-is for the deny flag; a generic `splitToolList` is a clean-up-ticket rename, not a behaviour-adding slice's job.
