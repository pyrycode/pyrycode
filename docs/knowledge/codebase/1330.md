# Ticket #1330 — Order inbound delivery against a `new_session` rotation's respawn

`startFreshRunner` ran `rotate()` — including `Pool.RotateForNewSession`'s `ReasonClear`
transition fan-out — to completion before calling `RestartFresh`, so the clear reached
clients while the outgoing child was still alive and the fresh one did not yet exist. A
turn accepted in that ~4 ms window was written into the doomed child; msgqueue read the
successful write as a commit and dropped the head, so the turn vanished. This closes the
window: a rotation gate on `*streamsup.Runner`, armed strictly before `rotate()` and
cleared only when the successor child's stdin binds, makes every `WriteUserTurn` in
between return the retryable `ErrNoLiveChild` instead of writing into the outgoing child.
It also closes Open question 4 from [#1295](1295.md)'s outcome
(`docs/specs/architecture/1295-forced-rotation-delivery-ordering.md:518`, "the
clear-before-`RestartFresh` window … not structurally excluded").

## Implementation

- **`internal/streamsup/runner.go`** — two new fields under the existing `mu` (guarding
  `stdin`): `rotating bool` and `rotateGen uint64`. `mu`'s doc comment is widened from "guards
  stdin" to "guards which child, if any, may receive a turn" — deliberate, since the whole
  property depends on `turnTarget` answering "is a rotation armed?" and "which child's
  stdin?" as **one question** under **one acquisition**; two acquisitions reopen the race at
  nanosecond width.
  - `BeginRotation() (abort func())` sets `rotating = true`, bumps `rotateGen`, and returns a
    disarm that is live only if no later arm has landed (checked against the captured
    generation) — mirrors `openForDelivery`'s undo in `cmd/pyry/stream_turn_busy.go`. The stamp
    matters because two overlapping `new_session` frames are an ordinary shape (the e2e's own
    M2 loop re-sends every ~250 ms): the loser's `rotate()` fails `ErrSessionNotFound`
    (`sessions/transition.go:120-123`) and runs `abort()`; unstamped, that would clear the
    *winner's* arm while the winner's outgoing child is still alive — reproducing this exact
    defect on demand from two frames.
  - `turnTarget() (w io.Writer, gated bool)` — the single-acquisition read `WriteUserTurn` now
    calls instead of `Stdin()` directly.
  - `WriteUserTurn` calls `turnTarget`; on `gated`, logs one **Info** record (not the spec's
    `Debug` — see below) naming only the event discriminant and the runner's own session id,
    then falls through to the existing `WriteTurn(ctx, w, payload)`, whose nil-writer branch
    (unchanged) returns `ErrNoLiveChild` without writing or consuming the turncommit claim.
  - `setStdin` clears `rotating` in the same acquisition it publishes the new stdin handle.
    `takeStdin` deliberately does **not** — the gate must survive the teardown, since that
    teardown is the middle of the window it covers, not its end.
- **`cmd/pyry/main.go`** — `startFreshRunner` gains `abort := beginRotationOrNoop(r)` ahead of
  `rotate()`, running `abort()` only on `rotate`'s error path. The existing
  rotate-before-`RestartFresh` order (load-bearing for the double-rotation watcher skip-set,
  per the function's pre-existing doc comment) is unchanged — the arm is inserted ahead of
  both statements, not between them. `beginRotationOrNoop` is an **optional** type assertion
  (`interface{ BeginRotation() func() }`) rather than a widened `case`, so
  `restartFreshStub`/`bothMethodsStub` in `new_session_routing_test.go` keep exercising the
  same dispatch shape without silently degenerating into the inert `default` arm.
- **`cmd/pyry/streamsup_runner.go`** — `streamRunner.BeginRotation() func()` forwards to the
  runner, the third concrete method reached by type assertion off the un-widened
  `sessions.Runner` (after `Interrupt` #1120, `RestartFresh` #1124).
- **Tests**: a third test in `cmd/pyry/inbound_deliver_rotation_test.go`,
  `TestInboundDeliver_RotationInProductionOrder_DeliversToFreshChild`, drives the **real**
  `startFreshRunner` (not a hand-ordered fixture sequence like #1295's test) so it is RED on
  the unmodified tree. `internal/streamsup/runner_test.go` gained three scenarios at the
  `*Runner` layer: gate refuses mid-rotation, a fresh spawn clears it, and the
  generation-stamped abort. `TestInboundDeliver_RotationWithoutHold_WritesIntoThePreRotationChild`
  (the fixture-reachability control, no rotation ever begins) was run — not assumed — and
  stayed green on both trees.

## Deviation from spec: the refusal record is Info, not Debug

The spec left the level as an open question. Debug would have satisfied the e2e's AC-1 guard
(which greps the daemon's whole captured stderr for the literal `level=DEBUG`) from the fix's
own diagnostic, since the refusal fires on essentially every rotation — converting AC-4's
20-run stability measurement into a near-tautology. Info keeps the operator-facing
discriminator ("refused by the gate" vs. "no child yet") without touching the AC-1 guard's
`level=DEBUG` grep. Verified independently in code review by reading
`relay_v2_stream_new_session_test.go:528-546`/`:620`, not taken on the PR's word.

## Patterns established

- **Single-acquisition check-and-capture as the exclusion mechanism, not a convenience.**
  Whenever "is condition X armed?" and "read resource Y" must be answered as one fact (here:
  is a rotation in flight, and which child's stdin), they belong under one lock acquisition.
  Splitting them narrows a race to a smaller window instead of excluding it — and looks like a
  harmless simplification to a later reader.
- **Generation-stamped abort for a two-frame overlap**, the same shape as
  `openForDelivery`'s undo (#1199): a disarm/undo obtained from an earlier call must not fire
  if a later call of the same kind has since landed. Applies whenever a "begin/end" pair can be
  entered again before the first end runs.
- **Optional-capability type assertion over widening a type-switch case**, to add a new
  concrete method to one dispatch arm without silently re-routing existing stub-based tests
  that don't implement it into a different (and now-vacuous) arm.
- **Refuse and let the existing retry ladder recover, rather than block the caller.** Reuses
  msgqueue's pre-existing `ErrNoLiveChild` retry/give-up path instead of adding a new
  wait/wakeup mechanism inside the runner.
- **Choose a log level against what an acceptance criterion's own instrument actually
  measures**, not by taste or convention. A new record on a path a stability AC greps can
  satisfy that AC's guard by construction; check the grep before picking the level.

## Lessons learned

From [PR #1332](https://github.com/pyrycode/pyrycode/pull/1332)'s own **Lessons learned**
section:

> A new log record can satisfy the very guard a ticket measures against. The AC-1 guard is
> "some `level=DEBUG` anywhere in the capture," so any new Debug producer on the exercised path
> makes it green by construction. Before adding a record on a path a stability AC measures,
> check what the AC's assertion actually greps for.
>
> A wall-clock delta is not wiring evidence until the baseline is measured. The M3→M4 gap
> looked exactly like the spec's predicted "one 1 s retry" signature — and the unmodified tree
> produced the identical gap. The overlay probe of the daemon's own capture was the check that
> actually discriminated.
>
> `go test -overlay` covers the read-only cases too, not just mutation. The same technique
> served three jobs here without ever dirtying the worktree: reverting production files for the
> AC-3 RED, grading mutants, and adding a diagnostic `t.Logf` to a file an AC forbids modifying.
>
> The fixture's teardown must be asynchronous to model `RestartFresh`. `RestartFresh` returns
> after `cancel()`; the kill and `takeStdin` run later on the Run goroutine. A fixture that
> tears down synchronously inside `RestartFresh` makes "the woken delivery found the child
> already gone" a race, and the unmodified-tree red becomes flaky instead of a deterministic
> misroute.

**Code review ([PR #1332 review](https://github.com/pyrycode/pyrycode/pull/1332#issuecomment-5187662439),
decision PASS, 1 SHOULD FIX + 1 NIT) surfaced two things worth recording as named, accepted
gaps — same shape #1295 recorded for its own file family:**

1. **[SHOULD FIX, accepted, not fixed] The gate's release is not generation-aware — only half
   of the two-frame protection the `rotateGen` stamp closes is actually closed.** `setStdin`
   clears `rotating` unconditionally for *any* child that binds, not specifically for the
   successor of the arm currently standing. Concretely: frame 1 arms (gen 1) → `rotate1` →
   `RestartFresh` → `cancel()` returns with the respawn still pending on the Run goroutine →
   frame 2 arms (gen 2) and enters `rotate2` → frame 1's respawn completes → `setStdin` clears
   `rotating` **while frame 2's arm is standing and frame 2's outgoing child is still alive** →
   a turn delivered before frame 2 reaches `RestartFresh` lands in the child frame 2 is about
   to kill. That is this ticket's original defect, reopened from the same two overlapping
   frames the `abort` stamp defends against on the *arm* side — the spec analysed overlapping
   frames only for `abort`, not for the release, so this is a genuine gap rather than a ruled
   decision. Accepted as-is per the project's evidence-based-fix-selection rule: this window is
   strictly narrower than the pre-fix ~4 ms-on-every-rotation window, no failure of this shape
   has been observed, and the spec explicitly specified `setStdin` as the clear point. If
   evidence of this narrower race ever surfaces, the fix is a generation-aware clear: capture
   the arm generation at `RestartFresh` and compare it in `setStdin` before clearing, the same
   shape `abort` already uses.
2. **[NIT, not fixed] `runner.go:415`'s new slog key is `"session"`; the repo's dominant
   convention is `"session_id"`** (71 occurrences vs. 2, the other being
   `control/server.go:1182`). No behavioural effect; a future edit to this file should prefer
   `"session_id"`.

**AC-4's 20-green sample does not discriminate on every host — measured, not assumed.**
Independent re-run in code review: the fixed tree went 20/20 green (matching the PR), but the
*pristine* `ac25ad8` tree (via `go test -overlay`, no revert) went **14/14 green sequentially
and 24/24 green under 4-way concurrency — 38/38 green total** on that host, where the ticket's
own cited baseline was 4-in-34 red. The 4-in-34 rate is load- or host-specific and did not
reproduce during review. Two consequences: (1) AC-4's 20-green run is not, by itself, evidence
this fix changed anything on a host where the baseline is already stable — the AC-2 unit test
(deterministic RED pristine → green fixed, re-verified 5/5 in review) is the ticket's real
proof; (2) the "0 M4 stalls, nothing to report on #1298" reading in the PR is still correct as
written, since the pristine tree produced 0 M4 stalls in the same review sample.

**`make e2e-realclaude` SKIPPED rather than passed in both the PR's and the review's
environment** — no Claude login available, so all 46 `e2e_realclaude` specs skip, including the
live-claude twin of this exact seam (`TestInteractiveStreamNewSessionRotatesAndSpawnsFresh`).
Code review added the `needs-real-claude` label so the dispatcher parks a manual live-gate run;
nothing in this ticket's evidence asserts that gate is green.
