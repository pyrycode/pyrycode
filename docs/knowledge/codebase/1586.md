# Ticket #1586 — `request_session_settings` names the conversation it asks about

`request_session_settings` was a bare frame: a client could ask for the current run
configuration (session id, model, effort, YOLO, context-window usage) but had no way to say
which conversation it meant. Its sibling read verb, `request_snapshot`, already carried a
`conversation_id` and validated it through the `KnownConversation` seam before doing any
work. This ticket adds the same field and gate to `request_session_settings` — field and
validation only, **no reported value moves**. Making the reported values follow the named
conversation is #1587.

## Implementation

- `internal/protocol/settings.go`: new `RequestSessionSettingsPayload{ ConversationID string
  \`json:"conversation_id"\` }`, no `omitempty` — mirrors `RequestSnapshotPayload`, and
  deliberately unlike the sibling `SetSessionSettingsPayload`'s pointer-plus-omitempty
  presence contract. Absent and empty are the *same* case here ("no conversation named"), so
  nothing needs to tell them apart; keeping the key always on the wire lets a fixture pin the
  full shape.
- `internal/relay/v2session_settings.go`'s `handleRequestSessionSettings` gains a tolerated
  decode (`_ = json.Unmarshal(env.Payload, &p)`) and one boolean gate:
  ```go
  addressable := p.ConversationID == "" ||
      (m.cfg.KnownConversation != nil && m.cfg.KnownConversation(p.ConversationID))
  ```
  Short-circuit order is load-bearing twice: the empty-id check first means an unnamed
  request never reaches the registry (the fresh-daemon case — `conversations.Load` seeds
  nothing, so there is no id in existence to send, and failing this closed would have
  regressed the shipped desktop#491 fix); the nil-seam check second fails a *named* id closed
  when the registry is unwired, matching `handleRequestSnapshot`'s own posture. The three
  existing seam reads (`BootstrapSessionID`, `SnapshotSettings`, `SnapshotUsage`) moved inside
  `if addressable { … }`; an unaddressable request consults none of them and falls through
  with every value at its zero — the same `session_settings` reply shape the wire contract
  already defines as a real answer, never a `TypeError`.
- `internal/relay/v2session_seams.go`: `V2SessionConfig.KnownConversation`'s doc comment now
  names both consumers and both postures — `request_snapshot` rejects an unknown id with
  `conversation.not_found`; `request_session_settings` degrades to the zero-valued reply
  instead. No new field; the seam was already wired in production
  (`cmd/pyry/relay.go:startRelayV2`).
- `internal/relay/v2session_settings_read_test.go`: a `countingReadSeams` helper wires the
  three run-configuration seams to **non-zero** fixture values and counts every consultation
  with `atomic.Int64`s. This is what makes "an unknown conversation gets zeros" a
  discriminating test — with the seams left unwired (the pre-#1586 `allReadSeams` fixture) the
  zero reply is the same reply whether or not the gate exists. Two new tests:
  `_ConversationGate` (table-driven over known / unknown / nil-seam / empty / no-payload rows,
  asserting both the reply and the seam-consultation counters) and
  `_NonInteractiveMakesNoLookup` (the capability gate must precede the registry lookup, not
  just suppress the reply).
- The five tests the ticket required to stay green with **unmodified assertions** all do:
  `_ReportsRunConfig`, `_AnswersWithoutASnapshotter`, `_NilSeamsDegradeToZero`,
  `_IgnoresAnyPayload`, and `internal/e2e.TestRelayV2_StreamRequestSessionSettings` — all five
  send no `conversation_id`, so all five take the `""` short-circuit. Their doc comments,
  which had called the frame bare as a stated reason, were rewritten (not their assertions) —
  `internal/protocol/codes.go`'s `TypeRequestSessionSettings` block comment, plus the three
  comments in the technical notes below.

See `docs/specs/architecture/1586-request-session-settings-conversation-id.md` for the full
design rationale, including the architect's self-review security pass (PASS, 9/9 categories —
the existence oracle this creates is accepted rather than mitigated, since `list_conversations`
already gives any paired conn a strictly stronger version of it, ungated).

## Patterns established

- **A zero-valued "unknown" reply needs non-zero seams to be a falsifiable test.** Any AC of
  the shape "an unresolvable X gets an all-zero reply" is vacuous against fixtures that leave
  the underlying value seams unwired, because an unwired daemon answers with the same zeros
  regardless of the gate. Wire the value seams to non-zero fixture constants and count
  consultations — `countingReadSeams` here, mirroring the shape a future read-gate ticket
  should reuse rather than reinvent.
- **A capability gate's ordering-vs-a-second-check claim needs its own counter, not just a
  no-reply assertion.** Reordering the interactive gate below the decode+lookup still produces
  no reply either way, so `_ReportsRunConfig`'s existing no-reply test is blind to that
  regression. `_NonInteractiveMakesNoLookup`'s registry-lookup counter is the only thing that
  catches it — confirmed by mutation (reordering the gate reddens that test alone).
- **A read verb and a write-adjacent read verb can share a validation seam but diverge on
  failure posture.** `request_snapshot` and `request_session_settings` both gate on
  `KnownConversation`, but the first rejects with an error frame and the second degrades to a
  zero-valued reply — because the second's wire contract already defines its zero payload as a
  real answer (`session_id: ""` = "nothing to address"), so adding an error branch would be a
  new failure shape for a verb documented as always answering. The seam is shared; the
  reply-shape decision is not, and both are recorded together on the seam's own doc comment so
  the divergence survives the next reader.

## Lessons learned

(from the PR body's own "Lessons learned" section, and the two code-review rounds on
pyrycode/pyrycode#1594)

- **A comment this ticket edits is still in scope even when the spec under-enumerated it.**
  The architecture spec's AC #5 sweep named three comments to correct; code review found a
  fourth (`internal/protocol/codes.go`'s block-level paragraph above the `TypeRequestSessionSettings`
  const, which still asserted "no attacker-controlled field" four lines above a trailing
  comment that had already been corrected — the file contradicted itself). The fix routed to
  developer rather than back to a spec re-issue, because the ticket's AC is the contract and
  the fix was a comment edit inside a file already in the diff. The developer then found a
  *fifth* of the same class by re-sweeping the claim vocabulary rather than trusting either the
  spec's or the reviewer's enumeration — `TestRelayV2_StreamRequestSessionSettings`'s doc
  comment still stated "the frame is bare" as the verb's contract while its own inline comment
  forty lines below already said otherwise. Enumerated "N, and no more" comment sweeps are a
  lower bound, not a proof of completeness; re-grep the claim's vocabulary after a fix lands,
  not just before.
- **A round-trip test can look like it pins a decision while a narrower test actually owns
  it.** `TestRequestSessionSettingsPayload_RoundTrip`'s comment credited it with pinning the
  no-`omitempty` decision on `ConversationID`. Measured under `go test -overlay` with
  `omitempty` spliced onto the tag, that test stayed green — its fixture id is non-empty, so
  the key survives omission — and only `TestRequestSessionSettingsPayload_EmptyConversationID`
  went red. The credit was moved to the test that actually earns it, and the round-trip test's
  comment now says explicitly why it *cannot* pin the decision. General shape: a byte-equal
  round trip only pins an encoding decision if the fixture value exercises the boundary the
  decision is about (here, emptiness) — a non-empty fixture is blind to `omitempty` by
  construction, whatever the comment claims.
