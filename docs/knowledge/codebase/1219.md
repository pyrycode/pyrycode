# Ticket #1219 — Test-owned open window for `TestRealClaude_SigtermMidToolUse`

`TestRealClaude_SigtermMidToolUse` (#422) is the only live coverage of pyry's
shutdown-while-a-tool-is-running contract. This ticket rescued it from two
consecutive fixture defeats — claude's Bash-tool policy kept ending the
in-flight command before the test could signal it — by moving ownership of the
blocking window from claude to the test, and then re-derived invariant 4's
on-disk discriminator twice as live operator runs falsified each shape in
turn. Size S, test-only: `internal/e2e/realclaude/sigterm_mid_tool_use_test.go`
only, zero production source files, across all three rounds.

See [features/e2e-realclaude.md](../features/e2e-realclaude.md) for the suite
contract and [codebase/422.md](422.md) for the original #422 design this
supersedes (two of its bullets now point back here).

## The problem

Invariant 4 — "the signal genuinely landed mid-tool_use" — is the precondition
that makes the other three invariants (full-subtree cleanup, JSONL
consistency, bounded exit) mean anything. #422's original fixture blocked on
`sleep 30`, then `tail -f /dev/null` after claude 2.1.158 refused standalone
sleeps (#563). By 2026-07-27, claude 2.1.220 was attaching its own timeout to
every Bash call and, on expiry, **backgrounding the command and returning a
tool_result immediately** — so the fixture command reported itself finished
before the test could send SIGTERM. Chasing a third command was explicitly
ruled out as a treadmill; the fix had to change who owns the open window.

## Round 1 — the FIFO ownership inversion (`6ca5b37`)

```
test:   mkfifo <workdir>/sigterm-hold
test:   goroutine → open(fifo, O_WRONLY)   [blocks: no reader yet]
claude: Bash → cat <workdir>/sigterm-hold  [blocks: no writer yet]
        ↓ both opens complete at the same instant — a rendezvous
test:   holds the write end, never writes  → cat blocks in read() forever
test:   Close() (t.Cleanup only)           → cat sees EOF and exits
```

`holdFIFO(t, path) <-chan struct{}` never exposes the `*os.File` to the
caller — release is only reachable via `t.Cleanup`, which by construction runs
after the test body, so invariant 1 cannot pass vacuously. The blocking
`open(O_WRONLY)` also removes a 100ms poll-lag that had been losing the race
against claude's 5s timeout. Confirmed live: claude's `tool_use` input was
`{"command":"cat …/sigterm-hold"}` with **no `timeout` field** — the
escape-hatch trigger ("claude backgrounds a FIFO wait too") was falsified, not
met.

## Round 2 — claude corroborates on a surface the old assertion forbade (`08a73eb`)

The inversion held (invariants 1–3 and 4a all green), but claude writes a
synthetic `tool_result` into the session JSONL during its own teardown:

```json
{"type":"tool_result","content":"The user doesn't want to proceed...",
 "is_error":true,"tool_use_id":"toolu_..."}
… "toolDenialKind":"user-rejected","interruptedByShutdown":true,"version":"2.1.220"
```

`interruptedByShutdown: true` is claude *recording* the very fact invariant 4
exists to prove — but the old assertion ("no matching tool_result") forbade
any tool_result at all. **Dropping the on-disk check was considered and
rejected**: it would be vacuous under the exact defeat this ticket exists to
fix — if claude backgrounds the command instead, `cat` keeps running, the FIFO
stays held, and invariants 1–3 all pass with the scenario unstaged. The fix
was to flip the sign: accept an interruption artifact, reject a completion.
This shipped as `interruptedByShutdown` being the sole accepting signal,
rejecting every unknown.

## Round 3 — the operator gate falsifies round 2's founding principle (`391a5e9`/`d52729e`)

Eight consecutive live operator runs against claude 2.1.220: **7 PASS, 1
FAIL**. `interruptedByShutdown` — the shape round 2 was built entirely
around — occurred in **zero** of the eight. The one failure staged the
scenario perfectly (rendezvous fired, write end held, pre-SIGTERM snapshot
clean, invariants 1–3 green) and was failed for recording an ordinary
`"Exit code 1"` — no timeout, no background handle, no interruption marker.
The likely mechanism: pyry's reaper SIGKILLs the Bash descendant group
(invariant 1 doing exactly its job), claude observes the child die, and writes
a plain failed-command result before it processes its own SIGTERM — a race
between two teardown steps. **The check was accusing pyry of the one thing it
did right.**

Round 2's founding principle — *"every unknown resolves to REJECT"* — was the
defect. The fix flips polarity again, this time to **reject only on positive
evidence that claude's own bound ended the call**, and accept everything else.
`classifyBashToolResult` (`sigterm_mid_tool_use_test.go:699`) is now a
four-way classifier:

| `toolResultKind` | Meaning | Verdict |
|---|---|---|
| `toolResultAbsent` | no matching tool_result — claude torn down before writing one | ACCEPT |
| `toolResultInterrupted` | `interruptedByShutdown: true` | ACCEPT |
| `toolResultUnbounded` | ordinary result, no bound, no interruption marker (the 2026-07-29 shape) | ACCEPT |
| `toolResultBounded` | positive evidence of claude's own bound | REJECT |

Evidence precedence (asymmetric on purpose, `classifyBashToolResult`
doc comment): a background handle or timeout-expiry record on the
**result** (`toolUseResult.backgroundTaskId` / `timedOutAfterMs`) outranks
everything; an interruption marker outranks a bound recorded only in the
**tool_use params** (`input.timeout` / `input.run_in_background`), because the
params only record intent at request time, not whether the bound ever fired.

**Two surfaces, not one, because #1223's probe showed neither alone
discriminates both of claude's bounding branches**: the 2026-07-27 defeat was
a bound the *model* chose, visible only as `input.timeout` in the call params;
#1223 then established a second, client-side default (`BASH_DEFAULT_TIMEOUT_MS`)
that backgrounds identically with **no** `timeout` field on the tool_use at
all, in 10 live reps out of 10. A single-surface check would pass one branch
vacuously.

`is_error` was considered and rejected as the discriminator, on two
independent grounds that converged: (1) `resilience_test.go:126` asserts
`is_error == true` on a Bash tool_result for a command that ran to
**completion** and exited non-zero — reading it would accept a completed
command as proof the signal landed mid-call, the exact thing invariant 4
exists to reject; (2) #1223's probe capture later showed the backgrounding
envelope carries `is_error: false` while **both** accepting shapes carry
`is_error: true` — reading it would have inverted the guard, not just
weakened it.

### What the flip gives up, and where it moved

Accepting on unknowns means an unknown claude never gets a chance to reject.
That rejecting power didn't vanish — it moved to a **pre-SIGTERM JSONL
snapshot** (`sigterm_mid_tool_use_test.go:459-471`), different fabric on
purpose: a pure timing fact with no claude field in the loop. A bounding
defeat's `tool_result` is always written *before* the signal (the call ended
on claude's clock, which had nothing to do with SIGTERM), so any matching
tool_result present at the instant SIGTERM is about to be sent means the
scenario was never staged — checked and rejected before pyry is even
signalled, so it cannot be misread as a production regression. Neither check
is sufficient alone: the snapshot misses a result flushed just after it reads;
the post-exit classifier is what catches that case.

**Known accepted-risk hole** (recorded in the file header, not closed): if
claude backgrounds the command *and* the tool_result never reaches disk
before SIGTERM, both checks see nothing → `toolResultAbsent` → accepts,
vacuously. Never observed; the window is the ~100ms poll interval on the
pre-SIGTERM disk read. Not closed per evidence-based fix selection — no
observed instance, and the closer (bound the on-disk `input.timeout` against
this test's own worst-case time-to-SIGTERM rather than asserting its absence)
is recorded as an open question rather than implemented.

  params bound reddens only the two 2026-07-27 rows; restoring the old

- `TestHoldFIFO_RendezvousAndRelease` — unchanged across all three rounds,

- Live gate: `make e2e-realclaude` with real credentials,
  `TestRealClaude_SigtermMidToolUse` passing and not skipped (`needs-real-claude`

## Patterns established

- **A stochastic accepting condition needs a live-run sample, not one green
  run, before it's trusted.** Round 2's `interruptedByShutdown`-only
  discriminator passed two live runs and looked solid; an 8-run operator gate
  is what surfaced that the accepting shape it was built around occurs in 0
  of 8 real runs, and that the shape it *rejected* (`toolResultUnbounded`) is
  actually the dominant one (7 of 8). When a check's positive case depends on
  a race between two async teardown paths, size the live sample to the race,
  not to "does it pass once".
- **A polarity flip doesn't remove rejecting power, it relocates it — find
  where, and it needs different fabric.** Round 3's accept-on-unknown flip
  only holds because the pre-SIGTERM snapshot (a timing fact) independently
  catches what the post-exit classifier (a claude-field read) now lets
  through. Pairing a stochastic signal's weakening with a deterministic,
  differently-sourced check is the same belt-and-suspenders shape as
  CLAUDE.md's "different fabric" rule, applied inside a single test file
  rather than across a code/prompt boundary.
- **Log the classification on every run, pass or fail.** `t.Logf("invariant
  4b: … classified as %q", kind)` (`:573`) is what made the round-3 defect
  diagnosable at all — the `-v` log across 8 runs showed `interrupted`
  occurring zero times, which a bare pass/fail signal would have hidden
  entirely (7 passes would have just looked like 7 passes).
- **A single probe capture from a sibling ticket can retire a "worst-case
  assumption" rather than merely narrow it.** Round 2's AC2 needed a
  worst-case value for `is_error` on the backgrounding envelope because the
  original 2026-07-27 transcript didn't retain it. #1223's later verbatim
  probe of the same claude version settled the actual value (`false`) *and*
  revealed that the assumed worst case (`true`) would have made `is_error`
  vacuous as a discriminator on the branch #1223 uncovered. Worth checking
  sibling probe tickets for a real capture before leaning on a hypothesized
  worst case.

## Lessons learned (from code review, PR #1222)

- **Zero-executable-line-changed is a provable, and the strongest,
  verification claim for a prose-only rework.** Round 3's final rework
  (`d52729e`, fixing three review findings that were all comment/doc text) was
  verified by `git diff -U0 <prev>..HEAD -- <file> | grep -vE '^[+-]\s*(//|$)'`
  returning empty — proof the runtime behaviour reviewed at 0 MUST-FIX carried
  forward bit-for-bit. Reach for this whenever a rework is genuinely
  comment-only; it's cheaper and stronger than re-deriving correctness.
- **A margin quoted without its reference frame is unverifiable, and the two
  frames can point opposite directions.** `heldBeforeSignal` measures
  rendezvous→SIGTERM (50s: `waitForBashSubprocess` 25s + `waitForSessionID`
  10s + `waitForBashToolUseOnDisk` 15s), not pyry-start→SIGTERM (100s, adding
  `waitForDirectChild` 25s and the rendezvous wait itself 25s). Against
  claude's 120s client-default bound, 50s is a 70s margin; 100s is a 20s
  margin — and only the first frame is the one that matters, because a bound
  that hasn't started running (claude's clock starts at the *command*, i.e.
  the rendezvous) cannot expire. Reviewed twice (`391a5e9`'s SHOULD-FIX-1,
  discharged in `d52729e`); the fix was naming the frame everywhere the number
  is quoted, not just fixing the arithmetic.
- **A review's own lesson, applied to its own NITs, finds more than the review
  did.** `d52729e`'s rework grepped the *claim* ("no tool_result" / "never
  written" / "cannot return") rather than the cited line for SHOULD-FIX-2, and
  the sweep surfaced a second site the review hadn't flagged. The same sweep
  discipline, applied to NIT-3's "every bounding defeat writes before the
  signal" overstatement, found a sibling instance in the file header the NIT
  itself hadn't named.
- **A superseded-content marker needs to carry forward everything it demotes,
  not just the headline change.** The final review's one surviving finding
  (below the 3-finding fail threshold, left as a follow-up, not fixed in this
  PR): the `SUPERSEDED 2026-07-29` marker on the architecture spec's Part II
  correctly documents the polarity flip, but demoting that Part to "history"
  also orphaned its recorded **accepted risk** (the vacuous-accept hole above)
  without carrying it into the header as the new authoritative location. The
  header's own complementarity claim ("classifyBashToolResult for how the two
  holes fail to overlap") reads as complete but the two holes *do* overlap in
  exactly that one case. **Follow-up, not fixed here**: qualify the header's
  complementarity claim and the spec's superseded marker to name the residual
  hole explicitly, rather than letting the marker imply nothing was lost.
  `docs/specs/architecture/1219-sigterm-mid-tool-use-test-owned-window.md:494`
  and `:503` also still carry the pre-round-3 `~75s`/`25+25+10+15` numbers and
  "defeat #4" naming (round 3 renumbered to #5) under that same marker — same
  follow-up, not addressed by this rework.
