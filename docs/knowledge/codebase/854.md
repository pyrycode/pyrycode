# Ticket #854 — Fix interactive bootstrap deadlock: route bootstrap-bound reply via PID probe

On a fresh daemon, the interactive bootstrap session (the one Desktop/Mobile drive over the
relay) never answered a live send: `resolveTarget` selected the by-id reply resolver keyed on
the bootstrap **pool** id, but the bootstrap claude spawns without `--session-id` and mints its
own on-disk transcript uuid, so `<poolID>.jsonl` never appears and the turn stream loops
`bootstrap child … has no jsonl open yet` forever. Fixed by routing a conversation bound to the
bootstrap session through the same PID-probe resolver the `convID == ""` (no-route-yet) branch
already uses, converging the "no jsonl yet" wait once the first turn creates the transcript
instead of rejecting/looping forever. PR #873.

## Implementation

- `resolveTarget` (`cmd/pyry/interactive_turn_stream_v2.go:439-482`) now has **three** branches,
  not two: `convID == ""` (bootstrap, probe resolver — unchanged) → `convID != ""` resolving to
  the **bootstrap** session (**new**: probe resolver, `resolveOwnBootstrapJSONL`) → `convID != ""`
  resolving to a non-bootstrap session (by-id resolver, `resolveBoundSessionJSONL` — unchanged).
  The new branch is detected via `host == bootstrap` — both are `turnbridge.SessionHost` over a
  `*supervisor.Supervisor` pointer, so the comparison is a stable identity check, not a
  session-id string comparison (cleaner and avoids a race on which id "wins").
- No new resolver, no new state machine, no new PTY-write path. The fix is *only* which resolver
  closure `resolveTarget` selects for the bootstrap-bound case — it reuses
  `resolveOwnBootstrapJSONL` verbatim, inheriting its confidentiality guard (canonical dir +
  UUID-stem check) unchanged.
- `resolveTarget` is shared with the modal stream (`cmd/pyry/interactive_modal_stream_v2.go:63`),
  which had the *same* bootstrap-bound JSONL deadlock — it benefits from this fix automatically
  (code review verified no divergence: the modal stream's paired `boundScreenText` was already
  screen-based, not JSONL-based, so nothing else needed to change there).
- New unit test: `TestResolveTarget_BootstrapBoundUsesProbeResolver`
  (`cmd/pyry/interactive_turn_stream_v2_test.go`) — RED on pre-fix `main` (the by-id resolver
  stats the missing `<poolID>.jsonl` and errors), GREEN after (the probe binds to the daemon's
  own open file). This is the fast unit-test gate for the fix; see below for the real-claude e2e.
- New real-claude two-turn liveness e2e: `internal/e2e/realclaude/interactive_bootstrap_liveness_test.go`
  (`TestInteractiveBootstrapLiveness`, tag `e2e_realclaude`, in the `make e2e-realclaude` gate).
  Spawns a fresh real `pyry` daemon (real `claude --model haiku`) in an isolated authenticated
  HOME, seeds the bootstrap pool id + a bound conversation deterministically
  (`seedBootstrapRegistry`/`seedBoundConversation`, transcribed from `internal/e2e/harness.go`
  per #861), pairs a phone over the encrypted v2 wire, and drives two turns, asserting a
  non-empty `assistant_delta` per turn within a generous timeout. Content-agnostic (liveness
  only). The daemon spawn routes its control socket through a transcribed `shortSocketPath` (the
  #860 fix) — this is load-bearing: a `<home>/pyry.sock` under the long authenticated
  `t.TempDir()` HOME overflows macOS's 104-byte `sun_path` limit and the daemon never reaches
  readiness, so RED could never reach the deadlock it exists to observe.
- The harness is a **transcription**, not an import, of `internal/e2e`'s daemon-spawn helpers —
  `internal/e2e` is build-tag-fenced `e2e || e2e_install`, disjoint from `e2e_realclaude`, so
  sharing code across the two isn't possible without a new shared package (out of scope for an
  S ticket; same duplication `ensurePyryBuilt` already required).

## Decision: approach A (inject via existing send path), not B (`--session-id`)

The ticket offered two approaches. Approach A — bind the bootstrap-bound reply by PID probe,
reusing the existing guarded `WriteUserTurn` → `DeliverPrompt` send path to create the transcript
— was chosen over B, spawning the bootstrap with an explicit `--session-id` + private per-cwd
workdir. B is the redesign owned by a separate open ticket, #839 (deterministic bootstrap
`--session-id`, retiring the `--continue` restart heuristic and startup adopt-by-mtime); choosing
B here would have duplicated #839's charter and pinned a uuid pre-emptively. A converges the
fresh-daemon deadlock without touching the bootstrap's resume/rotation lifecycle, leaving #839's
redesign untouched. Full rationale + adversarial security review (trust boundary, no new PTY
inject path, `#678` isolation guard preserved) in the architecture spec:
[`docs/specs/architecture/854-interactive-bootstrap-liveness.md`](../../specs/architecture/854-interactive-bootstrap-liveness.md).

## Patterns established

- **A bootstrap-bound conversation is a third `resolveTarget` case, not a variant of either
  existing one.** `host == bootstrap` pointer identity is the correct and cheapest way to detect
  it — cleaner than comparing session-id strings, and it composes safely with any future resolver
  the non-bootstrap branch might grow, since it's checked before `sessionID`/`convDir` are used
  for anything.

## Known limitation (code review SHOULD FIX, not addressed — low severity, flagged for a future ticket)

Code review (PASS, one non-blocking SHOULD FIX) found that `drainForAssistantReply` in the new
e2e correlates a turn only by `ConversationID` + non-empty text, not by `AssistantDeltaPayload.TurnID`.
Turn 1's drain returns on the *first* non-empty delta without draining to `turn_end`; a
multi-flush Turn-1 reply (several coalesced deltas) could leave extra Turn-1 deltas buffered, and
Turn 2's drain could then read a **leftover Turn-1** delta and "pass" without the daemon ever
answering the second send. Single-delta short replies (the common case, and what haiku on this
prompt shape typically produces) are unaffected — this is a rigor gap in a multi-delta edge, not
a break of the primary liveness oracle. Not fixed in this PR (non-blocking). If this gate is ever
relied on to catch a turn-2-specific regression, tighten it: capture Turn 1's `TurnID` and require
Turn 2's delta to carry a different one, or drain Turn 1 to its `turn_end` before sending Turn 2.

## Lessons learned

- The bootstrap session's pool id ≠ its on-disk transcript uuid (spawned without `--session-id`),
  so a bootstrap-bound conversation must resolve its reply by PID probe, not by the bound uuid.
  Detect the bootstrap-bound case via `host == bootstrap` (pointer identity on
  `turnbridge.SessionHost`) — both sides resolve to `pool.sessions[pool.bootstrap].Supervisor()`,
  a stable pointer — which is cleaner than comparing session-id strings.
- Restoring a fixed file after a RED-on-`main` check via `git checkout`/`git stash drop` is
  dispatcher-denied (it caused this ticket's earlier salvage — see the `bdd78a4` WIP commit on
  this branch). Use a plain `cp` to a scratch backup and back — no git index operations — to
  observe RED without touching tracked history.
- **`internal/e2e/realclaude` could not be observed GREEN on the code-review host**: real claude
  there was 2.1.199, but the realclaude suite's PTY driver (tui-driver) is pinned to v1.9.0, which
  doesn't recognize claude 2.x's startup dialog (`UnexpectedModalError{ModalClassUnknown}`) — an
  environmental, suite-wide block confirmed by an unrelated pre-existing PTY test failing
  identically in the same run (this is a known, previously-observed environmental block —
  claude-2.x vs. pinned tui-driver-1.9.0 — not new to this ticket). The fix was verified instead via the deterministic unit gate
  (`TestResolveTarget_BootstrapBoundUsesProbeResolver`) plus static review. Operator must confirm
  `make e2e-realclaude` GREEN on a tui-driver-compatible claude version before relying on this
  gate pre-ship.
- **Documentation debt found and fixed in passing**: `docs/knowledge/features/turnbridge-package.md`'s
  "Which JSONL, and surviving `/clear` rotation" section still described the `convID == ""`
  bootstrap branch as picking a plain mtime "recency" resolver — stale since #827 (which
  probe-preferred that branch to `resolveOwnBootstrapJSONL`) and never corrected because #827's
  own documentation phase did not run (noted explicitly in `codebase/838.md`). Corrected as part
  of this ticket's docs pass alongside the new #854 bootstrap-bound branch, since both live in the
  same paragraph.
