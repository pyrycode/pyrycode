# Ticket #1181 — Deflake `TestSession_Activate_GuaranteesPTYBound`

`TestSession_Activate_GuaranteesPTYBound` (`internal/sessions/session_test.go`) failed intermittently under full-suite `make check -race` (once in 20+ runs, never isolated or package-scoped). Surfaced while QA-gating PR #1180 (#1174) but confirmed pre-existing and unrelated — that PR touched no `internal/sessions` code.

## Root cause — test-timing fragility, not a production race

The old fixture armed an 80ms idle timeout with no client attached and reached `stateEvicted` by waiting for that timer to fire. On re-activation, `runActive` re-arms a fresh 80ms idle timer at the top of the function; with no client to defer it, the timer could fire *again* in the gap between `Activate` returning and the test's 10ms re-check. That eviction calls `setSession(nil)`, which freshens `sessReadyCh` to a new unclosed channel, so the re-check waited on an open channel and hit its deadline — the observed `context deadline exceeded` signature. `Activate`'s own contract (its final statement is `WaitForPTY`) never failed; the test was racing a legitimate *later* eviction, not observing a bind failure.

## Fix

Structural, not a widened deadline: `helperPoolIdle(t, 0)` disables idle eviction entirely (`timerCh` stays `nil`, so nothing can ever call `setSession(nil)` after `Activate`). The evicted→active cycle is now driven deterministically via `Evict`/`Activate` — the same idiom `TestSession_ActivateBlocksUntilPersisted` (`session_persist_test.go`) already used. Once re-activation runs `setSession`, `sessReadyCh` stays closed permanently, so the re-check reads an already-closed channel with no timing dependence.

The 10ms check window itself was deliberately left unchanged — it exists to preserve "bound at return, not eventually"; widening it would mask a returns-before-bound regression. Determinism comes from `idleTimeout=0`, not from the window size.

No production code changed.

## Pattern established

When a lifecycle test needs a deterministic evicted↔active cycle in `internal/sessions`, prefer `helperPoolIdle(t, 0)` + explicit `sess.Evict(ctx)` + `sess.Activate(ctx)` over relying on the idle timer to reach `stateEvicted`. `Evict` force-evicts via the buffered `evictCh`, independent of `idleTimeout`, and blocks until the persist completes — no polling needed. Racing a live idle timer against a test's own assertions reintroduces exactly this class of full-suite-only flake.

## Lessons learned

A flake signature of `context.DeadlineExceeded` (not `context.Canceled`) on a channel-wait immediately following a state-changing call is worth checking against "was a fresh instance of this channel just allocated by an unrelated concurrent trigger" before assuming the call under test is broken — here, `WaitForPTY`'s channel-freshening-on-clear behavior (`TestSupervisor_WaitForPTY_FreshensAfterClear`) was the exact mechanism, and the eviction that triggered it was the *test fixture's own* timer, not a bug in `Activate`.
