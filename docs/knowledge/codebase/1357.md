# Ticket #1357 — Probe instrument: read a result trailer's top-level key names off the full matched line, before the cap (offline)

`resultTrailer` (#1266) is a fixed eight-field decode with no `result`
member — deliberate, because it is what makes the 512-byte cap
(`reachCapCommand`) safe to apply to the verbatim trailer line alone. That
fixed shape cannot answer one question: `TerminalReason` is a plain
`string` with `omitempty`, so an **absent** `terminal_reason` and one
emitted as `"terminal_reason":""` both decode to `""`. That distinction
matters because `terminal_reason` is a pyry invention — on the headless
`PYRY_USE_STREAMJSON=1` path a healthy run's trailer is claude's own
`result` line, carrying no `terminal_reason` at all, while pyry's
synthesised idle-stall trailer carries it unconditionally. This ticket
ships a reader that answers *which keys the line carried*, not any
field's value, so the two cases become distinguishable without widening
`resultTrailer`. **No live claude, no verdict reached, no production
code touched** — one new test-only file plus a two-line extension of
#1266's own file.

## Implementation

- **`trailKeyNames(line []byte) []string`** (new file
  `trailer_key_names_test.go`) decodes `line` into
  `map[string]json.RawMessage`, collects the keys, sorts them, and
  discards the map. Signature is `[]byte` in, `[]string` out, **no
  `error`** — the failure arm (decode error) returns `nil` and renders no
  part of the error, because `json.SyntaxError` carries a byte offset
  into its own input and `json.UnmarshalTypeError` names the offending
  value, both attacker-chosen and uncatchable by any fixture needle. That
  containment is structural (the map never escapes the function) rather
  than a discipline to remember.
- **The field** — `trailScanResult.KeyNames []string` with JSON tag
  `trailer_keys` (`result_trailer_observation_test.go:98-140`),
  `omitempty` matching the tier's convention for fields empty unless
  `State == trailSeen`. The tag is deliberately clear of all six
  `finGatherForbiddenKeys` substrings (`command`, `args`, `comm`, `argv`,
  `line`, `stderr`) because #1358 carries this field's name onto
  `finSighting`, which *is* swept — there is no rule to satisfy at this
  tier itself.
- **The wiring** — one line inside `trailScan`'s existing match return
  (`result_trailer_observation_test.go:176-210`):
  `KeyNames: trailKeyNames(scanner.Bytes())`. `scanner.Bytes()`, **not**
  `Line` — `Line` is the capped copy, and on a realistic trailer (`result`
  pushes the line past 512 bytes) the cap lands inside the `result`
  string, leaving truncated JSON that decodes to zero keys. The full line
  is what the existing `resultTrailer` decode already runs against, for
  the same reason.

## The five acceptance criteria, and how each is proved

- **AC1 (ordering)** — `TestTrailKeyNamesReadsTheFullLine` runs the same
  expected eleven-name slice against `trailFixtureTrailer` (green under
  either implementation — the cap never fires) and
  `trailPaddedTrailer(2000)` (**the red**: a reader fed `Line` returns
  zero names here). A third sub-test calls `trailKeyNames` directly on
  that scan's own `.Line` and asserts it yields none, pinning the
  ordering by a red rather than a comment.
- **AC2 (absence vs. zero value)** —
  `TestTrailKeyNamesSeparatesAbsenceFromZeroValue` compares two fixtures
  differing in exactly one thing (whether `terminal_reason` is on the
  line at all), both carrying `"type":"result"` so `trailScan` matches
  both. Asserts the key-name reads differ *and* that both decode through
  `resultTrailer` to the same `""` — the second half is what proves the
  existing decode could not have answered this on its own.
- **AC3 (containment)** — `TestTrailKeyNamesCarryNoValues` plants a
  distinct needle in each of `result`, `session_id`, `subtype`,
  `stop_reason`, `terminal_reason` (a fixture the test renders itself —
  `trailNeedle` is a single shared constant spliced only into `result`
  and does not serve five positions). `result`'s needle sits past the
  512-byte cap, verified by offset assertion rather than trust. **The
  assertion is scoped to `KeyNames` alone**, not a whole-record marshal:
  the neighbouring idiom forty lines up (`TestTrailScan`'s padded
  sub-test) is correct there because `trailPaddedTrailer` plants only in
  `result`, a field `resultTrailer` doesn't decode — copied here it goes
  red against a *correct* build, because `Subtype`, `StopReason` and
  `TerminalReason` are carried through `Trailer` by design and published
  verbatim downstream (that leak surface is #1358's, with its own
  narrower plant list). A non-vacuity precondition (`KeyNames` equals the
  expected eleven) is asserted before the sweep, so a reader that returns
  nothing can't pass this vacuously.
- **AC4 (order independence)** — folded into AC1: both rows assert
  `reflect.DeepEqual` against one `trailExpectedKeyNames()` function
  (never a package-level var — `go test -race` runs this package's tests
  in parallel over a shared backing array), an exact sorted slice rather
  than a weaker two-reads-agree comparison.
- **AC5 (no widening, no map reachable)** —
  `TestTrailResultTrailerFieldSetIsPinned` walks `resultTrailer`'s eight
  `(name, json tag, type)` triples via `reflect`, comparing types against
  `reflect.TypeOf` values rather than string literals.
  `TestTrailScanResultReachesNoRawMessageMap` reuses `finRecordInputReaches`
  in `TestFinSightingReachesNoScanType`'s shape, banning
  `map[string]json.RawMessage` — **the map type, never its element**:
  `trailScanResult` already reaches `json.RawMessage` itself, through
  `Trailer *resultTrailer` → `PermissionDenials *[]json.RawMessage`, so a
  ban naming the element would be red against correct shipped code on the
  day it was written. The test asserts that reachability as a control, so
  the map-ban's green is a property of the record and not of a walk that
  reports clean on everything.

## Patterns established

- **A reader whose only safe output is "did this value appear" should be
  typed so the unsafe output can't type-check, not just be reviewed for
  it.** `trailKeyNames` returning `[]string` with no `error` makes "no
  value from the line crosses this boundary" true by construction: there
  is no return path a decode error, a raw map, or a `json.RawMessage`
  could travel out on. The alternative — `([]string, error)` with the
  caller expected to never render the error — depends on every future
  caller remembering that discipline.
- **A containment sweep copied from a neighbouring test can go red
  against a correct build** when the two tests' fields don't decode the
  same things. `TestTrailScan`'s whole-record marshal sweep is correct
  for `trailPaddedTrailer` because that fixture plants only in `result`,
  a field `resultTrailer` doesn't carry. The same marshal-and-search
  idiom applied to a fixture with needles in `subtype`/`stop_reason`/
  `terminal_reason` — fields `resultTrailer` *does* carry and publishes
  by design — fails on a correct implementation. Scope containment
  assertions to the specific output field being proved safe, not the
  enclosing record, when the record has other fields with a different
  publication contract.
- **A type-reachability ban must name the type that would change, not
  the type already known to be reachable.** `trailScanResult` already
  reaches `json.RawMessage` via `PermissionDenials`; banning that element
  type would be red on day one. Banning `map[string]json.RawMessage`
  instead is green today and catches the actual regression class (a
  future field that carries the *decode*, not a slice of pre-parsed
  denial payloads). Pair the ban with a control assertion that the
  walk still finds the known-reachable type, so the ban's green is
  proven rather than a property of a walk that never finds anything.

## Lessons learned

(From PR #1359's body and its code-review comments; see also
[`codebase/1349.md`](1349.md)'s Lessons learned for the same failure
mode's first occurrence.)

- **A filename-anchored pointer sweep misses the bare continuation cite
  in the same sentence.** `finding_trailer_evidence_test.go:382` names
  the aborted arm as `result_trailer_observation_test.go:289-290` and the
  deadline arm as a bare `:270` — both point into the shifted file, only
  one carrying the filename `grep` can anchor on. Grepping the filename
  found 24 of 25 targets and left the one that mattered.
- **Checking each pointer against the pre-change file first is what
  separates PR-created staleness from pre-existing debt.** All 25
  `internal/`-side targets resolved correctly on `main`, so the whole gap
  was this diff's own line-shift — worth establishing before rewriting,
  since a pointer that was already wrong belongs to a different ticket.
- **A mechanical old→new line map (built by diffing the two file
  versions) preserves what a pointer resolves to; re-deriving a target by
  hand does not.** Applying the map was content-preserving for all cites
  at once, including one whose target is a deliberately approximate
  anchor (a blank line) that needed to stay exactly as approximate as it
  was pre-PR — a hand rewrite would have "corrected" it to something more
  precise and, in doing so, changed its meaning.
- **Rewording a comment inside the file the cites point at re-shifts
  every downstream target.** A NIT fix that made the `KeyNames` doc two
  lines longer turned all 24 correctly-swept cites into off-by-two; the
  fix was reverted to a same-length wording rather than cascading into 26
  more rewrites. Any edit to a heavily-cited file's line count is a
  second sweep, whether or not it looks like one.
