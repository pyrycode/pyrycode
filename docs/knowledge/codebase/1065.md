# Ticket #1065 — scope `modal_shown` per conversation

Split from [#1063](https://github.com/pyrycode/pyrycode/issues/1063) (itself split from
#1050). #1063 bundled two separable concerns; this is the **confidentiality-scoping**
half — adding a `conversation_id` outbound stamp to `ModalShownPayload` so a permission
modal's tool title/input summary can no longer fan from conversation A to a conn viewing
conversation B on the internet-exposed relay. The detection/emission half (making a
minted per-conversation session raise the modal at all) is sibling
[#1066](https://github.com/pyrycode/pyrycode/issues/1066), which this **blocks**: once
#1066 turns on multi-conversation modal broadcast, every `modal_shown` is already
confidentiality-scoped. This is the `#1062`-shaped change (`turn_state` scoping,
[codebase/1062.md](1062.md)) applied to the modal payload — a **stamp-and-filter**, not
new daemon-side per-conn gating (`ActiveConn` stays `{ConnID, Interactive}`).

## Implementation

~20 LOC of new logic across the 4 spec-predicted production files, dominated by a
mechanical signature cascade (`Record` gains a `convID` param at 14 call sites across 3
test files; `Handle` gains a `convID` param at 15 call sites in 1 test file):

- `internal/protocol/messaging.go` — `ModalShownPayload` gains `ConversationID string
  json:"conversation_id"`, declared **first** (leading, no `omitempty`), matching
  `TurnStatePayload`/`QueueStatePayload`/`SessionErrorPayload`. The struct doc's stale
  "there is no conversation_id" clause is revised: the new field is an **outbound**
  routing/scoping key, daemon-asserted from `active.CurrentConversation()`; the
  **inbound** anti-forgery model is explicitly called out as unchanged —
  `ModalAnswerPayload`/`ModalCancelPayload` still carry no `conversation_id`, and an
  answer is authorized by resolving `ModalID` server-side against the registry.
- `internal/modalbridge/modal.go` — `Outstanding` gains `ConversationID string`.
  `Record(req, wireClass, convID string)` stamps `p.ConversationID = convID` and stores
  `Outstanding.ConversationID` in the **same** critical section as the rest of the entry
  (atomic — no window where a stored modal lacks its scope). `Snapshot` restamps
  `ConversationID` from each `Outstanding`, which is what scopes `reconcileModals`'
  reconnect replay identically to the initial broadcast **for free** — `reconcileModals`
  (`internal/relay/v2session_modal.go`) marshals the `Snapshot()` payload verbatim and
  needed zero changes. `buildPayload` is untouched: `Record` owns the routing stamps
  (`ModalID`, `ConversationID`), `buildPayload` owns content only.
- `cmd/pyry/interactive_modal_v2.go` — `Handle`/`handleModalShown` gain a `convID`
  parameter, passed to `reg.Record`. `handleModalHidden` ignores it (`modal_dismissed`
  carries no `conversation_id`).
- `cmd/pyry/interactive_modal_stream_v2.go` — `boundScreenText` changes from `func()
  string` to `func() (convID, screen string)`, returning **both from the same single**
  `active.CurrentConversation()` read that previously selected only the screen host.
  `runModalStream` threads the pair into both `Handle` arms (`Hidden` gets `("", "")`).
  This single-read pairing is the security core: the screen the modal carries and the
  conversation it is stamped for cannot diverge, because they come from one cursor read
  — a second, independent read inside the emitter could observe a cursor flip between
  the two reads and stamp conversation A's screen with conversation B's id (the exact
  leak the ticket exists to close).

Golden fixture (`internal/protocol/testdata/modal_shown.json`) and roundtrip test
(`TestModalShownPayload_RoundTrip`) updated — `"conversation_id"` is the first JSON key
(`canonical` = `json.Compact`, not key-sort, so wire order must match struct declaration
order).

## Patterns established

- **Single-read pairing closes a TOCTOU, not just a code-style nit.** Content and its
  security-relevant scope label must be sourced from one read of shared mutable state
  when they're consumed together — deriving them from two independent reads of the same
  cursor (even microseconds apart) reopens the confidentiality gap the stamp exists to
  close. See [[architect-outbound-scoping-stamp-single-read-atomic-store]].
- **Trace the replay path before assuming a stamp needs a second production site.**
  `reconcileModals` replays `Snapshot()`'s payload verbatim — stamping the *stored*
  payload (in `Record`/`Snapshot`) scopes both initial delivery and reconnect replay with
  one write site, keeping this ticket at 4 production files instead of 5.
- **Execute a mechanical signature cascade before writing new tests.** The spec called
  out threading `convID`/`""` through ~29 existing call sites as pure mechanical work to
  do *first*, so it wouldn't become turn-1 discovery cost ahead of writing the two
  substantive new tests (AC2/AC4 concurrent-conversation, AC3 stored-payload scoping).

## Lessons learned

From the PR body: the spec's edit inventory — despite being exhaustive enough to list
individual call-site counts per file — omitted
`cmd/pyry/interactive_modal_stream_v2_test.go` (5 `runModalStream` callers + the
`boundScreenText` table-driven tests), one of the two signatures actually being changed.
Running `codegraph_callers` on `boundScreenText` and `runModalStream` before starting the
cascade surfaced the gap before the build broke, rather than after. Worth doing on every
signature-changing ticket even when the spec already ships a detailed inventory — plain
functions are what `codegraph_callers` catches reliably; method call sites (`x.M(...)`)
still need a grep cross-check (it missed `reg.Record`/`e.handleModalShown` on the sibling
#994 ticket). See [[dev-spec-edit-inventory-omits-test-callers-codegraph-catches]].

## Not weakening inbound anti-forgery (explicit non-regression)

Verified in the spec's security review: `ModalAnswerPayload`/`ModalCancelPayload`
(`internal/protocol/messaging.go`) carry no `conversation_id`; `handleModalAnswer`/
`handleModalCancel` (`internal/relay/v2session_modal.go`) resolve the inbound `ModalID`
server-side against the registry. A phone still cannot assert which conversation an
answer targets — the new field is outbound-only. `security-sensitive` per the modal
body (tool title/input summary) being application content that must not cross a
conversation boundary; see
[[security-sensitive-label-tracks-design-not-lineage]].
