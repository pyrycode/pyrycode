# Ticket #1030 — modal answer + cancel real-claude liveness gate

Adds `TestInteractiveModalResolution` to `internal/e2e/realclaude/` (new file
`interactive_modal_resolution_test.go`, `//go:build e2e_realclaude`) — the
first real-`claude` coverage of the **modal-resolution verbs**. Split from
#963 per the [PO split-per-family
convention](po-realclaude-liveness-capstone-splits-per-family.md); sibling of
#1028/#1029/#1031 for the other verb families, and the hardest of the four
because the trigger is not a test env-var but real claude choosing to call a
gated tool under default permission mode.

## Implementation

One daemon, one bound conversation, two sequential real-permission-modal
cycles over the same Noise v2 channel:

- **Phase A (answer, AC #1)** — send a Bash-triggering prompt, drain to
  `modal_shown{Class:"permission"}` (asserted **before** resolving — the
  non-vacuity gate), send `modal_answer{allow_once}`, then prove the session
  proceeded via a subsequent non-empty `assistant_delta`
  (`drainForAssistantReply`, reused verbatim from #854). Claude's words are
  never asserted.
- **Phase B (cancel, AC #2)** — raise a second modal (distinct nonce), send
  `modal_cancel`, and observe the `modal_dismissed{Outcome:"cancelled",
  Source:"remote"}` **broadcast**. `modal_cancel` is fire-and-broadcast — there
  is no reply correlated to the cancel request — so the proof is
  state/broadcast-shaped, never a correlated cancel-reply.

Test-only, zero production files touched. New symbols, all in the one new
file:

- `spawnPermissionDaemon` — byte-identical to `spawnBootstrapDaemon` (#854)
  **except** it drops the trailing `--dangerously-skip-permissions` flag.
  That one omission is the entire trigger mechanism: real claude then runs in
  default permission mode, and the first gated Bash call blocks on a real TUI
  permission modal instead of sailing through.
- `startModalResolutionHarness` — mirrors `startPerConversationHarness` (#997)
  with two deltas: pairs the phone WITH `--allow-remote-permissions` (the
  answer-side device gate on `ResolveAnswer`), and spawns via
  `spawnPermissionDaemon` instead of `spawnBootstrapDaemon`.
- `raiseRealPermissionModal` — the shared trigger scaffold both phases call:
  sends the Bash-trigger prompt, drains to `modal_shown`, asserts
  `Class == "permission"` and non-empty `ModalID`, returns the id.
- `drainForControlEvent` — a Type-only broadcast drain (no `InReplyTo`
  correlation), the new variant of #1028's `drainForReply`. `modal_shown` and
  `modal_dismissed` are `EventID==nil` broadcasts; this decrypts every
  `noise_msg` in arrival order (nonce lockstep) and returns the first envelope
  matching the wanted `Type`, `t.Fatal`ing on `TypeError` or on deadline.

The trigger prompt: *"Use the Bash tool to run the command: echo
pyrycode-\<nonce\>. After it completes, reply with a single short word."* The
per-phase nonce keeps Phase A/B commands distinct; the "reply with a single
short word" tail guarantees Phase A's post-answer `assistant_delta` has
something to land on without asserting claude's actual words.

## Reliability determination

The architect's explicit call (ticket delegated this): **ship both branches**,
not narrow to one. Rationale recorded in the spec:

- Version skew between `tui-driver` and installed `claude` — the thing that
  would make a real-modal trigger unreliable — was already resolved by the
  `tui-driver v1.10.0` bump (locked to claude `2.1.199`), superseding the
  stale [`env-realclaude-pty-blocked-claude2-vs-tuidriver19`](env-realclaude-pty-blocked-claude2-vs-tuidriver19.md) memory.
- The daemon's #798 modal surfacer already broadcasts `modal_shown` for a
  detected permission modal with **zero production change** — `runSupervisor`
  trust-marks `-pyry-workdir` at startup (`cmd/pyry/main.go:692`), so dropping
  `--dangerously-skip-permissions` yields only the per-tool permission modal,
  never a startup trust modal.
- Both branches have a deterministic *positive* observable (a continuation
  `assistant_delta`; a `modal_dismissed` broadcast) — neither depends on a
  flaky negative. The one shared risk surface is the trigger itself (real
  claude raising + tui-driver classifying), not either resolution verb, so
  narrowing to one branch would not de-risk anything; if preship shows trigger
  flake, the fix is trigger-robustness or deferral, not dropping a branch.

## Patterns established

- **A real-permission-prompt trigger is one flag removed from an existing
  spawn helper, not a new spawn path.** `spawnPermissionDaemon` is
  `spawnBootstrapDaemon` minus `--dangerously-skip-permissions` — the entire
  "new surface" for real-modal liveness testing is that single omission plus
  pairing with `--allow-remote-permissions`. Future real-tier tests that need
  a real permission gate should reuse this shape rather than inventing a new
  spawn helper.
- **Broadcast (non-reply) drains get their own helper, not an `InReplyTo`
  relaxation on the reply drain.** `drainForControlEvent` is a Type-only
  sibling of #1028's `drainForReply`, not a parameter added to it — keeps the
  correlated-reply invariant (`drainForReply` always checks `InReplyTo`) from
  being weakened for the one caller that doesn't have a request to correlate
  against.
- **The permission-answer device gate (`--allow-remote-permissions`) has to be
  paired up front.** Without it, `ResolveAnswer` denies at the gate silently
  from the test's perspective — no continuation streams, and
  `drainForAssistantReply` just deadlines. Any future real-tier test that
  drives `modal_answer` needs this pairing flag or will misdiagnose a gate
  denial as a liveness failure.

## Lessons learned

- The #383 `permission_protocol_spike_test.go` null finding ("no permission
  event on stdout") is about the `agent-run` **stream-json** path — a
  different surface from this ticket's **interactive-PTY** TUI-grid modal
  path. Don't read #383 as evidence that real permission prompts can't be
  observed in the interactive daemon path; they surface via tui-driver grid
  detection there, not via a stdout event.
- `modal_cancel` truly has no correlated reply (confirmed against
  `relay_v2_modal_cancel_test.go:25`) — any future real-tier modal test must
  drain for the broadcast dismissal, not wait on a reply that will never
  arrive.
