# Ticket #1494 — `eventring.After`: an id beyond the ring's id space is a gap, not caught-up

`security-sensitive` · closes the resync-not-silence promise [`docs/protocol-mobile.md`](../../protocol-mobile.md) makes for [reconnect replay (#647)](v2-session-manager.md), narrowing what the [#663 caught-up-watermark clamp](663.md) actually defends.

`Ring.After` classified `afterID >= latestID` as caught-up in one branch, lumping together two different inputs: `afterID == latestID` ("the phone has everything") and `afterID > latestID` ("the phone names an id this daemon never issued"). The second is the shape a daemon restart leaves behind — the ring is purely in-memory, so per-conversation ids restart at 1 while a reconnecting phone still holds a high cursor. Classified caught-up, the phone got no `resync`, kept its stale cursor, and — dedup'ing durably on `event_id` per the wire contract — silently dropped every live event until the daemon's ids climbed back past it. The empty-ring branch of `After` already got this right (`afterID > 0` against an unknown conversation was already a gap, on exactly this reasoning); the non-empty branch didn't apply the same logic.

## Implementation

- **The whole production change is one split comparison** in `internal/eventring/ring.go`'s `After`: `afterID > latestID` now returns `(nil, true)` (gap); `afterID == latestID` stays `(nil, false)` (caught-up). Everything else in `After` — the oldest-fell-off-the-back gap check, the ascending scan, the unreachable tail — is untouched.
- **`replayMissed` (`internal/relay/v2session_replay.go`) needed no logic change**, only comment corrections. For `afterID > newest` it now takes the gap branch: `emitResync` forwards one `TypeResync` marker and returns *before* the `s.replayThrough = min(afterID, newest)` clamp line. On this input class the watermark is never written at all and stays `0`, so `forwardEnvelope`'s guard is inert for the conn — live delivery survives the reclassification through a different mechanism (untouched watermark) than before (clamped watermark).
- **The resync is structurally first, not just first-in-practice.** `replayMissed` runs at the tail of `handleNoiseInit`'s success path on the manager's single `Run` goroutine, and `emitResync` forwards inline via `forwardEnvelope`, not through the buffered push stream — `Run` hasn't returned to its select, so no drain pass can have run ahead of it.
- **Doc/comment sites corrected atomically with the code**, per the spec's seven-site sweep: `ring.go`'s `After` and `NewestID` doc comments, `v2session_replay.go`'s `replayMissed` doc comment and clamp comment, `docs/protocol-mobile.md`'s reconnect-replay bullet table (gains a fourth "beyond the id space → resync" bullet), and `docs/knowledge/features/{eventring-package,v2-session-manager}.md`. All now describe caught-up as exactly `afterID == latestID` and route the beyond case to gap.
- **Test retargeting** (`internal/eventring/ring_test.go`, `internal/relay/v2session_replay_test.go`): `TestAfter_CaughtUp`'s `afterID=99` row moved into a new `TestAfter_GapBeyondIDSpace` (rows `6`, `99`, `math.MaxUint64`); `TestV2Session_Reconnect_CaughtUp_NoReplay` narrowed to only its `at-newest` subcase, with `beyond-newest` and `hostile-max-uint64` moved into a new `TestV2Session_Reconnect_BeyondNewest_EmitsResync` (mirrors `…_Gap_EmitsResync`'s shape, asserts one `TypeResync` frame where it previously produced zero). `…_OutOfRangeLastEventID_LiveStreamDelivered` and `…_ClearRotation_LiveStreamDelivered` keep their assertions but shift envelope indices (one extra `resync` frame ahead of the live one) and get rewritten doc comments explaining they now exercise the gap branch, not the clamp.

## Patterns established

- **A classification-boundary fix that widens a resync class is a subtraction from an existing clamp's reachable input set, not an addition to it — verify the subtraction, don't just assert the new branch works.** The architecture spec predicted `min(afterID, newest)` would become unreachable single-goroutine once the beyond-id-space class moved to the gap branch, leaving only the pre-existing `NewestID`/`After` concurrent-read window. The developer confirmed this by mutation rather than by re-reading the reachability argument: `s.replayThrough = min(afterID, newest)` → `= afterID` reddened nothing post-change, and the identical mutation against the pre-change tree reddened exactly the three rows the spec named. Both runs are what make "the clamp is now defence-only" a measured delta instead of an assertion.
- **When an AC names a mutation in prose ("revert `>` to `>=`"), run the structural revert, not the literal operator swap.** Swapping only the operator inside the shipped two-branch shape (`>` → `>=`) leaves the `==` arm dead code and reddens the wrong side (the caught-up tests, not the new gap test). The revert that actually pins the new gap test is collapsing back to the single pre-change `if afterID >= latestID { return nil, false }`. Both variants were run; they pin opposite boundaries, and per the spec's mutation record, neither arm of the two-branch split is free.

## Lessons learned

- **A "revert the operator" mutation is not always the revert the AC means.** AC #1 asked for "reverting `>` to `>=`". Applied literally to the shipped two-branch shape, that leaves the `==` arm unreachable and reddens the *caught-up* tests while the new gap test stays green — the opposite of the AC's intent. The mutation that actually pins the new test is the structural revert to the single pre-change `if afterID >= latestID { return nil, false }`.
- **A mutation that removes a use can fail to compile rather than fail a test.** Dropping the `min(afterID, newest)` clamp leaves `newest` declared-and-not-used, so the first AC #4 run reported `[build failed]` — not a red test and not evidence of anything. The mutant needs `_ = newest` after the `NewestID` read to keep the read alive and isolate the clamp as the only variable.
- **"Reddens nothing" needs a baseline to mean anything.** Post-change, the clamp mutation is silent, which is indistinguishable from a mutant that never applied. Running the identical mutation against an overlay of the four touched files at their pre-#1494 `HEAD` content reproduced the three reddened rows the spec predicted — that's what turns the post-change silence into a measured delta rather than an unverified claim.
- **INDEX.md can go stale from a change it never touches.** The developer correctly left `docs/knowledge/INDEX.md` alone (documentation-phase-owned), but its `v2-session-manager.md` and `eventring-package.md` one-line summaries had inlined the pre-#1494 contract verbatim — `caught-up `afterID>=latestID → (nil,false)`` and "an aged-out position gets a `resync`" (silently missing the beyond-id-space class). Corrected in this pass: `afterID==latestID` for caught-up, an explicit `afterID>latestID` gap clause, and the beyond-id-space case added alongside aged-out as a resync trigger.

## Security review

Architect self-review (full text in `docs/specs/architecture/1494-eventring-beyond-id-space-is-gap.md` § Security review) verdict: **PASS**. The change narrows the untrusted `last_event_id`'s reach rather than widening it: before, `afterID > latestID` flowed into `s.replayThrough` via the clamp; after, that class returns at the gap branch and is never written to per-conn state at all. One accepted finding: an authenticated phone can now binary-search the caught-up/resync boundary to learn a conversation's exact event count — no privilege gain or cross-conversation leak, since `cursor()` resolves the conversation daemon-side and never consults phone input. Log volume on `v2.replay.resync` rises (it's now the post-restart and stale-cursor path, not only aged-out) but no new field or content. Amplification is 1:1 with an authenticated Noise handshake, so no cap was added.
