# Ticket #1500 — streamsup: consume the interrupt `control_response` ack instead of surfacing it as `unrecognized_message`

Interrupt on the stream-json path is a stdin `control_request`; claude acks it ~40ms later on the
same stdout `Parser` reads, then ends the turn. `consumeLine` had no arm for the ack, so it fell to
`emitUnrecognized` and every interrupt put a diagnostic `unrecognized_message` row on the phone —
degrading the one frame whose whole value is meaning "claude started emitting something new." Fix
is one `case "control_response"` arm that consumes the ack content-free. PR
[#1607](https://github.com/pyrycode/pyrycode/pull/1607), code review **PASS**, two NITs, neither
blocking. A rework commit (`9d467f8`) followed the first real-claude gate run — see § The gate
found a second, pre-existing bug.

## Implementation

- **Own `case` arm, not an `ignoredLineTypes` member** — the same choice #1404 made for
  `rate_limit_event`, for the identical structural reason: a `control_response` carries no
  top-level `subtype` (nothing for `emitSystemSubtype` to dispatch on), the map's provenance is a
  measured 2026-07-27 census that never interrupted so never saw this type, and unreachability by
  matching beats unreachability by list membership. `TestParser_IgnoredLineTypesIsTheMeasuredSet`
  is consequently **untouched**, `want` still `{"system": true}`.
- **The ticket's proposed fixture shape was wrong, and the architect caught it before code.** AC1
  guessed `{"type":"control_response","request_id":…,"response":{"subtype":…}}` (top-level
  `request_id`, mirroring the request side). The real shape — pinned by a verbatim capture already
  committed at `internal/e2e/realclaude/testdata/set_permission_mode_v2.1.220_revoke.json` and
  transcribed in
  [`set-permission-mode-inband-probe.md`](../features/set-permission-mode-inband-probe.md#the-control_response-received-verbatim) —
  nests **both** `subtype` and `request_id` under `response`. The response side inverts the
  request side (`marshalInterruptEnvelope` does put `request_id` top-level on the request). This
  also flips the ticket's own shape argument: it offered "`control_response` carries a `subtype`,
  unlike `rate_limit_event`" as the fact distinguishing the two designs; against the capture there
  is no top-level `subtype`, so `streamLine.Subtype` decodes empty — exactly #1404's fact. The
  analogy the ticket doubted turned out exact, not weaker.
- **The arm matches on top-level `type` alone** and reads nothing below it. A success ack, a NAK
  (`subtype:"error"`), an ack with no `response` object, and an ack carrying an unmeasured inner
  `response` payload are all consumed identically — deliberate (Evidence-Based Fix Selection: only
  `success` has ever been observed for an interrupt, no branch built for a failure shape that
  doesn't exist). One `Debug` record names the type only, never the line, never `request_id` —
  the same content-free discipline `emitRateLimit` and the ignored-list drop already hold.
  `thinkingSinceEmit` is deliberately untouched: an ack is not a turn boundary, and that
  accumulator keeps its single reset point at the `result` arm.
- **fakeclaude's interrupt rider** (`writeInterruptAck`) now writes the ack **before** the
  interrupted `result`, on the same writer, matching claude's real order and — more importantly —
  giving the e2e's zero-assertion its causality: the `turn_end` a test already blocks on cannot
  arrive unless the ack already went through the parser. `inControlRequest` gained a top-level
  `RequestID` field so the fake can echo the daemon's real correlation id;
  `interruptControlRequest` widened `bool` → `(string, bool)` with its one caller updated.
- **Two exact-count fakeclaude tests were the free discriminator, left untouched.**
  `TestRunStreamJSON_InterruptMode_InterruptEndsTurnCancelled` (`want 1`) and
  `…_InFlightThenInterrupt` (`want 2`) go red the instant the rider is added and green again the
  instant the parser arm lands — with no test-code edit. Both counts were verified unmodified in
  the diff; bumping them would have deleted the discriminator.
- **Live tier:** `drainForCancelledTurnEnd` gained the standing `unrecognized_message` sentinel
  the interrupt window lacked (mirroring `drainForCompletedTurn`'s), naming both readings —
  daemon-bug (`control_response` at `line_type`) vs. a genuinely new type mid-interrupt. This is
  the only tier that observes a real claude's ack.
- **AC5 doc/comment sweep:** every count/membership claim about `ignoredLineTypes` stayed literally
  true, untouched, as the own-arm shape predicted. `turnevent/event.go`'s `Unrecognized` doc now
  describes two consumed-by-their-own-arm types; `interactive_stream_unrecognized_test.go` gained a
  `CORRECTED 2026-08-19` note recording the second exception. One new doc row was owed and added:
  [`streamsup-package.md`](../features/streamsup-package.md)'s event-catalog table gains a
  `control_response` row beside `rate_limit_event`.

## The gate found a second, pre-existing bug

The first real-claude gate run on the new AC4 sentinel went red — correctly, but not for the ack.
Interrupting a turn makes claude inject a synthetic `user`/`text` block announcing its own
cancellation (`"[Request interrupted by user…]"`), which `emitUser` surfaces as
`Unrecognized{Site: user_block, Kind: "text"}` — **correctly**, by the same 2026-07-27 census rule
that's right everywhere else (`user` messages carry `tool_result` blocks and nothing else). It's
the exact sibling of `harnessNoOutputNudge` (#1247), and it is **pre-existing on `main`**: `emitUser`
is untouched by this ticket's diff, so this frame ships on every interrupt today, independent of
`control_response`. The sentinel was simply the first thing that ever looked.

Fixing `emitUser` is a production change outside this ticket's diff and unreviewed by its spec —
Scope Discipline. Filed as **#1611** (open); rework commit `9d467f8` carves out that one measured
specimen (`interruptNoticePrefix`, matched site + type + a **prefix**, not an exact literal — see
below) with a pointer to #1611 and a named deletion step. The carve-out `t.Logf`s rather than
skipping silently, and it cannot mask this ticket's own regression: a `control_response` reaching
the drain arrives at `site="line_type"`, a different site than the carve-out's `user_block`.

That gate run is also the **first live evidence** that a real claude's `control_response` ack does
not reach the phone — no earlier tier had observed a real ack at all.

## Patterns established

- **A ticket's own proposed fixture shape can be wrong even when it asks for confirmation, and the
  repo may already hold the disproof.** The AC pointed at a spec whose prose was shorthand
  (commits to no nesting) and could neither confirm nor refute the guess. The actual authority was
  a verbatim capture already committed under `internal/e2e/realclaude/testdata/`. When an AC says
  "confirm the exact shape," look for a committed capture before trusting prose.
- **A wrong fixture guess can invert the design argument built on it.** Recheck the *distinguishing
  fact* an analogy rests on against real bytes, not just the shape itself — here the "flip" (no
  top-level `subtype`) made the `#1404` analogy stronger, not weaker.
- **An exact-literal carve-out can be wrong even when the repo's own precedent uses one.** `#1247`
  pinned its harness literal exactly; copying that here would have reddened roughly half the time —
  two live runs of the same claude version, same prompt, same interrupt timing, produced two
  different trailing clauses (`"...for tool use]"` vs `"...]"`). Two observations were what
  surfaced this; one would have looked like a stable literal. Match on the stable prefix plus
  structural fields (`site`, `type`) instead.
- **A brand-new zero-assertion over a live surface is a measurement, not just a test** — its first
  red is as likely to be a discovery as a regression. Build the discriminator (failure message
  naming `Site`/`MessageType`/`Raw`) in before the first run, so a red gate becomes a filed ticket
  in one cycle rather than a debugging session.
- **`-overlay` mutation testing stops at a subprocess `go build` boundary.** Any e2e that shells
  out to build its own binaries (`ensurePyryBuilt`, fakeclaude's build) sees the unmutated tree
  under a bare `-overlay` on the outer `go test`; `GOFLAGS=-overlay=<path>` is what reaches the
  child `go build` processes. Code review independently re-ran the mutation this way and got the
  real regression string back (`type="control_response"`), confirming the propagation.
- **An asymmetric mutant pair is what proves a zero-assertion is not vacuous.** Reverting the
  parser arm reddens the e2e's zero while the fake's emitted-line arrival control stays green;
  deleting the fake's ack write reddens the arrival control while the e2e zero stays green. Neither
  row alone distinguishes "the ack was consumed" from "the ack was never written."

## Lessons learned

From the PR body's own "Lessons learned" (developer) and the rework's, both verbatim/paraphrased
above under Patterns established where they generalize. Two additional points worth keeping
separate because they're about process rather than a reusable code pattern:

- A live suite's SKIP and PASS are both exit 0, for a single-test `-run` just as much as a full
  sweep — the executed-test count is the only thing that separates them. This bit the very sentinel
  this ticket added: the first invocation attempt skipped with no credential (exit 0), which would
  have read as "passing" without counting `=== RUN` lines.
- Code review flagged (NIT, not fixed) that `streamsup-package.md:1185`'s `codebase/1404.md` index
  line still calls `rate_limit_event` "the fifth arm" though there are now six switch arms —
  judged correct as historical attribution of what #1404 contributed, not a live count, and left
  alone. `:268`'s "fifth **mapping**" is genuinely unaffected: `control_response` maps to no event.
