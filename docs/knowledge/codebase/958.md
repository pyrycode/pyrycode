# Ticket #958 — Close the fakeclaude JSONL-trigger empty-read race

`TestTwoPhoneStructured_InteractiveReceivesStream`
(`internal/e2e/relay_two_phone_structured_test.go`) and
`TestRelayV2_InterruptStopsRunningTurn` (`internal/e2e/relay_v2_interrupt_test.go`)
intermittently failed under the full-suite `-tags e2e -race` leg with
`interactive phone A did not receive the full structured stream … missing
required types [tool_use turn_end]`. Both tests drive `fakeclaude` through
the same `PYRY_FAKE_CLAUDE_JSONL_TRIGGER` consumer
(`emitStructuredJSONLIfTriggered`, `internal/e2e/internal/fakeclaude/main.go`)
— two witnesses of one root cause.

## Diagnosis

Every producer drop is `os.WriteFile(jsonlTrigger, payload, 0o600)` =
`open(O_CREATE|O_TRUNC|O_WRONLY)` **then** a single `write(2)`. Between the
open (which truncates to 0 bytes) and the write, the trigger file exists but
is empty. The consumer's ~50 ms poll loop can land its `os.ReadFile` in that
window: `err == nil`, `data == []byte{}`, which the pre-fix code treated as a
normal (if trivial) payload — it ran `f.Write(nil)` (a no-op append), then
**`os.Remove(path)`**, unlinking the trigger before the producer's write ever
landed. In the structured test, the kicker goroutine self-heals by re-dropping
every 250 ms, but the load-bearing full-fixture drop (`dropFull`) is
`sync.Once` — losing it left phone A with only `turn_state`/`assistant_delta`,
tripping the vacuous-pass guard. Under full-suite `-race` contention the
open→write window stretches, which is why isolated re-runs never reproduced it
(confirmed 3/3 pass) while full-package runs did.

This is the same create-before-content race family
[#956](956.md) closed one file over in `waitForRotatedJSONL`, and the exact
NIT [#642](642.md)'s code review deferred ("an `os.Rename`-from-temp would
make the write atomic **if CI ever shows it**") — full-suite `-race` finally
showed it.

The two alternate mechanisms named in the ticket were considered and ruled
out by static reading, not fixed: the cold-start producer-subscribe re-race
(already closed by the pre-created initial JSONL + re-drop kicker — it would
zero out A's set entirely, not leave a `turn_state`-only partial) and deadline
starvation (the observed message reports a *partial* set, i.e. a
consumed-then-lost fixture, not "nothing arrived in time" — a wider deadline
was explicitly banned by the ticket's AC and wouldn't close a lost fixture
anyway).

## Implementation

One four-line gate at the shared consumer
(`internal/e2e/internal/fakeclaude/main.go:435`, inside
`emitStructuredJSONLIfTriggered`): after a successful `os.ReadFile`, a
zero-byte read now `return`s **without** calling `os.Remove` — the trigger is
left in place so the producer's write lands and the next ~50 ms poll consumes
the full content. Non-empty reads are unchanged (cap, write, sync, remove).
An empty append is never a legitimate payload, so skip-and-retry can't drop
real data or hang.

A producer-side fix (write-to-temp + `os.Rename`, the direct mirror of
[#956](956.md)'s fix) was rejected: the structured test has three drop sites
(250 ms kicker, `dropFull`, plus the interrupt test's own kicker) versus one
shared consumer edit, so the consumer gate is the single seam that covers all
present and future producers.

New untagged unit test `internal/e2e/internal/fakeclaude/jsonl_trigger_test.go`
(`package main`, no `//go:build` tag, mirrors `esc_detect_test.go`) pins the
contract in-process, closing the CI-coverage gap #642 flagged (the e2e files
never compile upstream of code-review): empty trigger is skipped and survives
(RED pre-fix — the trigger used to be removed), non-empty trigger is consumed
and removed, missing trigger is a no-op.

Neither e2e test file was touched — `failVacuous`, the four-required-types
gate, and the "A observed before B's negative" ordering are byte-identical by
construction.

## Patterns established

- **A poll consumer that both reads-and-removes must gate the removal on a
  non-empty/complete read, not just a nil error** — `os.ReadFile` succeeding
  with zero bytes is the open→write window, not a payload. Same shape as
  [#956](956.md)'s `Size() > 0` gate, one layer down: #956 gated the *reader's
  poll* on the file being non-empty before returning it; #958 gates the
  *consumer's destructive step* (`os.Remove`) on the read being non-empty
  before acting on it. Any future poller against a file this double
  truncate-then-writes should gate on non-empty content before doing anything
  irreversible with what it read.
- **One shared-consumer edit can close a race for every current and future
  producer**, avoiding an N-site producer-side fix that has to be re-derived
  at each drop site.

## Lessons learned

- **A stubbed PR-body placeholder plus a 0-byte verification-loop log file is
  itself signal, not just missing documentation.** The spec deliberately
  relocated the AC's diagnosis + ≥20-run contention evidence to the PR body
  (to keep the developer turn's fixed-cost housekeeping out of the
  implementation budget). The dispatcher's auto-commit swept in an unfilled
  branch (`f1736c4`) whose PR body still read "to be recorded by developer …
  filling in from repo state" and whose `scratchpad_958_e2e_loop.log` — the
  redirect target of the mandated verification loop — was 0 bytes. First-pass
  code review correctly read that combination as "the required verification
  did not complete" and failed the PR on process grounds even though the
  1-file, 4-LOC diff was already correct. Second-pass review ran the ≥20-run
  contention proof itself (20/20 targeted + one full `internal/e2e` package
  run under `-race`, `184.303s`) and passed on the strength of that
  independent evidence plus the spec's already-committed diagnosis section —
  see [`architect-958-jsonl-trigger-empty-read-gate`](../../specs/architecture/958-jsonl-trigger-empty-read-gate.md)
  for the deviation rationale. **When a developer PR body's evidence section
  is a stub, treat the architect spec's Diagnosis section as the load-bearing
  record instead of waiting on the PR body to be filled in retroactively.**
- The same auto-commit sweep landed the stray log as a tracked file; a
  follow-up commit (`7412828`) removed it and added `scratchpad_*`/`*.log` to
  `.gitignore` so future auto-commit sweeps in this worktree can't re-land
  scratchpad output. This is the same class of leak `.codegraph` was already
  guarded against.

## Security review

**Not security-sensitive.** Harness-timing fix in a test-only stand-in
(`internal/e2e/internal/fakeclaude`); no `pyry` runtime code touched, no new
trust boundary, and the #607/#632 capability-gate assertions the two e2e
tests exercise are provably unchanged (neither test file was edited).
