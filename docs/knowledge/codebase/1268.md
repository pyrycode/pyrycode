# Ticket #1268 — Prove the trailer classifier flips inside its own rig against real processes

Adds `internal/e2e/realclaude/trail_run_rig_test.go` (594 lines, purely
additive — no existing file edited, no existing call site changed). Closes the
gap the three prior tickets in this family left open: [#1266](https://github.com/pyrycode/pyrycode/issues/1266),
[#1270](https://github.com/pyrycode/pyrycode/issues/1270) and
[#1271](https://github.com/pyrycode/pyrycode/issues/1271) all prove their piece
against fixtures and synthetic buffers, but `trailClassifyRun` is pure — it
will happily classify inputs gathered from somewhere other than where a probe
claims to gather them, so a rig wired to the wrong path emits the same
positive as one wired to the right one. This rig closes that by gathering the
classifier's own inputs through the live producer chain
(`trailWaitForTrailer` → `trailGate`, `pinScanArgv`, `pinReadState`,
`tdnClassifyReapLog` → `trailAdmitAttribution`) against a real FIFO and a real
`cat`, before the subject exists and then across its life and death. Split
from [#1254](https://github.com/pyrycode/pyrycode/issues/1254); offline,
`e2e_realclaude` build tag, no live claude, no credentials, no network.

## Implementation

- **One seam, `trailRigGather(stdout *probeSyncBuffer, needles []string) (trailRunReadings, trailObservation)`,
  is the entire rig.** All four gathers in the file call it, so "no field of
  `trailRunReadings` is hand-assigned" is checkable in one place rather than
  argued across call sites. `tdnClassifyReapLog` is called over a **literal
  `nil` inside the function**, never a parameter — that is what turns "no
  reap line was synthesised" into a property of the file instead of a promise
  about its callers. The returned `trailObservation` is a rig-local
  intermediate: it is never assigned into `trailRunReadings` (which has no
  field that could hold it — taking the embedding would promote the trailer
  pointer back into reach) and never published.

- **The mandatory-guard shape for `Admit`, forced by the classifier's own
  contract.** `trailAdmitAttribution` is only called when
  `readings.Gate.Reason != ""`, because C4 rejects a non-empty `Admit` under a
  gate that certifies nothing and C3 rejects a zero `Admit` under one that
  does — calling the predicate unconditionally fails C4 on every non-usable
  gate, skipping it unconditionally fails C3 on every usable one. "No reap
  log" does not mean "no attribution value."

- **`trailOutcomeRunningAtTrailer` stays unreachable, deliberately, and the
  file says so twice** (header and the during-subject failure message). It
  comes from step 2 alone, gated on `trailAdmitProof`, which requires a reap
  line this rig must not grow. A live `cat` lands on
  `trailOutcomeMatchedUnattributed` instead — the honest answer for a match
  with a silent attribution.

- **The flip is `MatchCount`-driven (step 8 → step 7), never liveness-driven.**
  `TestTrailRigFlipsAcrossOneSubjectLifetime` takes a pre-subject reading
  (`trailOutcomeNoRowMatched`, with `RowsScanned > 0` asserted first to
  separate it from `trailOutcomeVoidNoRowsParsed`, and `ArgvScanErrored`
  checked before that so a broken instrument can't pass as the negative) and
  a during-subject reading (`trailOutcomeMatchedUnattributed`), then asserts
  the two outcome values differ as its own assertion rather than an inference.

- **Both dead readings are taken and land on distinct per-pid states.** After
  `cmd.Process.Kill()` but before `Wait()`, the test polls
  `pinReadState(subjectPID)` under `trailRigDeathWait` until it settles on
  `pinStateExitedNotReaped` — `pinStateRunning` is retried (kill is async),
  but `pinStateInstrumentFailed` and `pinStateNoSuchProcess` both fail the
  test immediately (the latter is unproducible here: the test is the parent
  and has not yet waited, so reaching it means the rig lost the parent
  relationship the whole claim rests on). After `cmd.Wait()`, a single
  (unpolled) read asserts `pinStateNoSuchProcess`. The argv match set is
  deliberately not asserted at either dead reading — `ps` renders a zombie's
  `command=` without the original argv, and which form a platform prints
  isn't this ticket's claim.

- **`TestTrailRigBoundIsMeasuredFromTheLastMiss` (AC4) pins the margin, not
  just the sign.** A start-derived staleness sits within roughly one poll
  interval of the induced lateness on either side, so a bare `< induced`
  would pass under the start-derived bug whenever goroutine scheduling
  exceeded the post-append poll granularity. The threshold is
  `induced - 2*probePollInterval` (`trailRigStalenessMargin`), against an
  induced gap of `8*probePollInterval` (`trailRigInducedLateness`) — leaving
  a correct reading ~5 intervals of headroom and a buggy one ~2 intervals the
  wrong side of the line.

- **`TestTrailRigCarriesMoreThanOneMatchedRow` (AC5) stages through a shell,
  not a second direct child**, because staging A's `cmd.Wait()`-reaps-the-
  subject property only holds for a direct child; a shell-wrapped `cat` is a
  grandchild the shell's own `Wait()` doesn't reap. The shell command is a
  compile-time constant (`"$1" "$2"; exit 0`) with both operands passed
  positionally — no interpolation site — and the trailing `exit 0` defeats
  `sh`'s exec-optimisation so the wrapper genuinely forks (measured, not
  assumed: mutating to `exec "$1" "$2"` drops the match count from 2 to 1 on
  darwin 25.5, confirming the fallback two-FIFO staging wasn't needed).
  `SysProcAttr{Setpgid: true}` plus a `defer`'d `syscall.Kill(-pgid, SIGKILL)`
  then `cmd.Wait()` closes the subject deterministically — `cmd.Process.Kill()`
  on the shell alone would not reach the `cat`.

- **Both subjects run with an empty `Env`.** Defence in depth from the
  architect's SHOULD FIX: `ps` reads only `pid=,ppid=,pgid=,command=` today
  (`pinStateColumns` has an enforcing test against ever adding a command/env
  column), so this isn't a live exposure, but it makes "this rig's subjects
  cannot leak the operator's `CLAUDE_CODE_OAUTH_TOKEN`/`ANTHROPIC_API_KEY`
  through any future column addition" true by construction. **Lesson the
  developer surfaced fixing it:** an empty `Env` and a bare command name
  inside the `sh -c` string are in tension — the shell gets no `PATH`, so a
  bare `cat` would resolve only via the shell's compiled-in default.
  Resolved with `exec.LookPath("cat")` in the parent, passed as a second
  positional parameter, which keeps the command string a compile-time
  constant *and* removes the `PATH` dependency, rather than trading one
  review property for the other.

- **Cleanup-ordering trap named but not re-derived here**, per the spec: `t.Cleanup` runs
  LIFO after the test body, and `holdProbeFIFO` registers its release
  cleanup at call time, so a `t.Cleanup`-registered `cmd.Wait()` would
  deadlock — the FIFO's write end (and the `cat`'s only path to EOF) wouldn't
  release until after the wait it's blocking. Both stagings kill/wait the
  subject from the test body or a `defer` inside it, never from `t.Cleanup`.

- **Test coverage: three `TestTrailRig*` functions, verified genuinely
  running rather than skipped** (this package's whole point, restated in the
  ticket's own AC5) — `go test -tags e2e_realclaude -race -v
  ./internal/e2e/realclaude/...` was 331 PASS / 46 SKIP / 0 FAIL at review
  time, with all three new specs `--- PASS` and zero `--- SKIP` against
  `TestTrailRig`. Each load-bearing assertion was mutation-tested (buffer
  pre-seeded → bound reads `since-poll-start`; `exec "$1" "$2"` → match count
  drops from 2 to 847-row-1; `cmd.Wait()` moved before the zombie poll →
  `no-such-process` before the test waited; during-subject gather wired to a
  wrong path → 0-of-847 matched).

## Patterns established

- **A pre-subject negative plus in-rig transitions, not just a positive
  fixture, is what proves a rig — as opposed to an instrument — is wired to
  the thing it claims to measure.** A pure classifier proven correct in
  isolation says nothing about which path fed it; the discriminating claim is
  the *flip* observed through the same code path the live probe will use,
  taken both before the subject exists (a genuine negative, not a
  nothing-was-measured void) and while it lives and dies. Reusable shape for
  any future ticket in this family that stages a "does the rig reach the
  thing it claims to reach" proof.
- **Funnel every gather in a proof-of-wiring rig through one seam that
  literal-`nil`s (rather than parameterizes) any input the rig must not be
  able to synthesise.** Making an input un-passable at the function signature
  is what turns a promise ("no call site passes a reap line") into a property
  of the file.
- **A negative reading must differ from the positive one in exactly the
  dimension under test.** Here: same held pgid, same needle-scan machinery,
  same trailer buffer state — only `MatchCount` moves. Any other axis that
  also differed would leave the flip's cause ambiguous.
- **When a margin assertion could pass under the bug it exists to catch,
  compute the threshold from the bug's own error bound, not from the correct
  value's sign.** `< induced` passes under the start-derived bug whenever
  scheduling noise exceeds one poll tick; `< induced - 2*pollInterval` does
  not, because that's derived from how far off the buggy reading can land.

## Lessons learned

- **`sh`'s exec-optimisation on a single-command `-c` string is real and
  measured, not assumed** — the spec flagged it as an open question with a
  fallback (two direct subjects on two FIFOs) prepared. The trailing `exit 0`
  defeated it on darwin 25.5, confirmed by mutation (dropping to `exec "$1"
  "$2"` measurably cut the match count from 2 to 1), so the fallback wasn't
  needed. Future platforms this runs on should re-check this if `MatchCount >
  1` ever fails.
- **An empty subprocess `Env` and a bare command name inside a `sh -c` string
  are in tension** — the empty `Env` (security review's defence-in-depth
  SHOULD FIX) strips `PATH` from the shell's children, so a bare `cat` inside
  the wrapped script fails to resolve even though `exec.Command`'s own
  binary resolution (which happens against the *parent's* `PATH` before
  `Env` applies) makes it look like it should work. Fix: resolve the binary
  in the parent (`exec.LookPath`) and pass it as a positional parameter, not
  as a bare name inside the script string. General shape: any future
  `sh -c` subject staged with an empty `Env` needs every binary it invokes
  pre-resolved and passed positionally, not typed into the script.
- **A permit-list stated as a header rule needs a periodic self-check against
  the file it governs.** Code review's NIT: the header states the rig's
  `t.Fatalf` content rule as a positive permit list ("may name counts, pids,
  verdicts, outcome values and BoundFrom") but the file's own `Detail`
  strings exceed it in six places — benign in substance (both `Detail`
  sources are independently content-governed: `trailRunOutcome.Detail` by an
  existing enforced test, `pinStateOutcome.Detail` by `ps`'s own stderr,
  which structurally can't carry a credential), but left as an open NIT
  rather than fixed in this PR (decision was PASS, not SHOULD FIX). Worth
  closing with one clause the next time this file is touched.
- **Two other NITs left open, non-blocking (PASS verdict, no rework
  triggered):** staging A doesn't `defer` the kill/wait the way staging B
  does, so six `t.Fatalf` paths between `cmd.Start()` and the explicit kill
  leave a zombie for the rest of the test binary (bounded — no hang, no
  cross-test contamination, `holdProbeFIFO`'s cleanup still delivers EOF);
  and nothing joins `subjectPID` against `scan.Matches` to prove the matched
  row *is* the subject rather than merely that some row matched and the
  subject's pid independently transitioned — noted as relevant for the live
  probes downstream, where the ambient process table is less trivially
  unique than a fresh `t.TempDir()` path.
