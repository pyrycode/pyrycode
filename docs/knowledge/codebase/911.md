# Ticket #911 — Bound `request_debug_bundle` to one in-flight bundle per conn

Reliability-review finding (2026-07-10, question 4: where can this break):
`pushQueue.enqueue` (`internal/relay/v2session.go`) admits control-class envelopes
past `pushQueueCap` (256) as a documented "soft overflow," justified by a comment
claiming the all-control saturated state is "unreachable in practice … the phone
cannot drive control volume (push is server→phone only)." [`StreamBundle`](../features/v2-session-manager.md#debug-bundle-streaming-812--streambundle--bundleenvelopes--reassemblebundle)
(#812, wired by #813) falsified that premise: it enqueues `ceil(bundle/48000)`
`debug_bundle_chunk` envelopes plus one `debug_bundle_done`, all control-class, all
never-droppable. Against a relay leg that's up but slow, a client retry loop
against `request_debug_bundle` stacks another full bundle's chunks onto the queue
per retry — unbounded daemon memory growth from one small untrusted inbound frame,
no hostile actor required. `security-sensitive`: an amplification/resource-exhaustion
path on the internet-exposed v2 relay surface. See
[`features/v2-session-manager.md`](../features/v2-session-manager.md) §
"The all-control saturated state IS reachable" and § Inbound debug-bundle request
for the updated narrative.

Spec: [`911-debug-bundle-inflight-gate.md`](../../specs/architecture/911-debug-bundle-inflight-gate.md).
Siblings: [`812.md`](812.md) (`StreamBundle` primitive), [`813.md`](813.md) (`request_debug_bundle` verb + `handleDebugBundleRequest`).

## Implementation

- **One production file, `internal/relay/v2session.go`** (+81/-7 net). No new wire
  code, no new exported types, no signature changes.
- **New unexported method `bundleInFlight(connID string) bool`.** Locks `pushMu`
  alone, looks up `m.queues[connID]`, scans `q.items` for any entry whose
  `env.Type` is `protocol.TypeDebugBundleChunk` or `protocol.TypeDebugBundleDone`,
  unlocks, returns whether one was found. `!ok` (unknown conn) → `false` — the
  safe direction, since a non-open conn's later `StreamBundle`/`Push` fails closed
  with `ErrConnNotFound` regardless. A pure `O(len(items))` read, released before
  any reply — same lock discipline as `enqueue`'s own drop scan.
- **One new call site in `handleDebugBundleRequest`**, inserted after the existing
  `DebugBundler == nil` check and **before** `archive, err := m.cfg.DebugBundler()`:
  a busy conn short-circuits to `debugBundleReplyError` (the existing deterministic
  `server.binary_offline` / `msgDebugBundleUnavailable` / `Retryable: true` reply,
  reused byte-for-byte) and returns — skipping the on-disk assembly, not merely
  the enqueue (AC #1).
- **Comment correction (AC #5)** on both `pushQueue.enqueue`'s soft-overflow
  paragraph and the `pushQueueCap` doc comment: the "unreachable in practice"
  claim is replaced with an explanation that `StreamBundle`'s control-class
  chunks make the all-control saturated state reachable, and that #911's
  per-conn gate is what bounds it (≈ 4/3 × archive per conn, via the base64
  `json.Marshal` per chunk — not an alias into the archive's backing array).
- **New tests in `internal/relay/v2session_debugbundle_test.go`** (+278 LOC),
  built with a `gatedRecorder` (atomic up/down flag) and `Connected:
  gated.connected` wired into the manager config — `bundleManagerFor` doesn't
  wire `Connected` by default, so the new setup extends it locally to hold the
  transport down and keep bundle frames queued:
  - `TestV2Session_DebugBundle_RejectsSecondWhileQueued` (AC #1/#2) — with the
    transport held down, a second and third `request_debug_bundle` on the same
    conn are rejected (`TypeError`, `CodeServerBinaryOffline`,
    `msgDebugBundleUnavailable`, `Retryable: true`, `InReplyTo` matching the
    rejected request), `fakeBundler.callCount()` stays at 1 (no re-assembly), and
    `queueLen` does not grow across retries.
  - `TestV2Session_DebugBundle_ServedAfterDrain` (AC #4) — once the transport
    recovers and the queue drains to 0 (all chunks plus `debug_bundle_done`), a
    subsequent request is served normally; `callCount` increments and the fresh
    bundle reassembles byte-for-byte against the source archive.
  - `TestV2Session_DebugBundle_PerConnIsolation` (AC #3) — conn A busy (held
    queue) does not cause conn B's `request_debug_bundle` to be rejected; B is
    served while a repeat on A is still rejected.
  - Existing debug-bundle tests (`CaptureOn/Off`, `UnpairedRefused`,
    `NeverLogsContentEncryptedOnly`, `ErrorReplies`) stay green — the gate only
    fires when a bundle is already queued, so the single-request happy paths
    (empty queue at request time) are unaffected.

## Patterns established

- **Request-time in-flight gate over atomic-drop-at-enqueue.** The ticket's
  Technical Notes offered two shapes; the architect chose the request-time gate
  (reuse the existing Run-goroutine handler + `debugBundleReplyError`, zero new
  queue machinery) over atomic-drop-at-enqueue (would have had to fight
  `pushQueue.enqueue`'s carefully-specified ADR-025 drop semantics and add a
  byte/reservation concept the queue doesn't have). When a request-time handler
  already owns a deterministic reply path and runs on the resource's
  single-owner goroutine, gating at the request is cheaper and more surgical
  than teaching the shared primitive a new rejection mode.
- **A `pushMu`-guarded scan is exempt from "never held across an external call"
  as long as it's a pure read released before any reply.** `bundleInFlight`
  establishes this as a reusable idiom alongside `enqueue`'s own drop scan and
  the test-only `queueLen` helper — any future per-conn queue-state check can
  follow the same shape (lock alone, scan `q.items`, unlock, then act).
- **An append-only concurrent mutator can only make a boolean gate *more*
  conservative, never race it open.** Because `Push` (the only off-`Run` queue
  mutator) can only append frames, `bundleInFlight`'s check-then-reply has no
  TOCTOU: between the scan and the reply, `Push` can turn `false` into `true`
  (admits fewer requests, never more) but can never clear a `true`. This
  argument — "the only concurrent writer moves the gate the safe direction" — is
  reusable wherever a boolean queue-state gate is checked outside the lock that
  protects the eventual action.

## Lessons learned

- **A "documented as unreachable in practice" comment is a standing invariant
  that a *later* ticket can silently falsify — grep for the premise, not just
  the code, when a new producer lands on a shared primitive.** #812/#813 made
  the phone able to drive control volume for the first time (bundle chunks),
  which is exactly the scenario `pushQueue.enqueue`'s soft-overflow comment
  asserted couldn't happen. Neither #812 nor #813's review caught this because
  the comment lived in a file neither ticket's diff touched. When a ticket adds
  a new control-class producer onto an existing shared queue, checking every
  extant comment that asserts a bound on that queue's *inputs* — not just
  reviewing the new code in isolation — is what surfaces this class of drift.
