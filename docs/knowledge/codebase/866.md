# Ticket #866 — guard `Session.id` under `lcMu` vs live `/clear` rotation (`RotateID`)

`Pool.RotateID` wrote `sess.id = newID` under `Pool.mu` only, on the strength of an invariant comment claiming no lifecycle goroutine ever observes the id concurrently. That invariant went stale the moment #839 wired `RotateID` into the live fsnotify `/clear` rotation watcher (`Pool.Run` → `OnRotate` → `onRotate` → `RotateID`): the watcher goroutine runs concurrently with every session's own lifecycle goroutine and fires on each `/clear`. Two lifecycle-goroutine sites read `sess.id` with no lock at all — `session.go:407` (`PreviousID: s.id` in the eviction-transition notify) and `session.go:521` (`"session_id", string(s.id)` in the idle-eviction warn log) — so a `/clear` rotation racing the same session's eviction path was a data race on a two-word string header. Latent in production (no `-race` there), but a genuine `go test -race` finding once exercised.

## Implementation

- **`sess.id` is now a two-lock field.** `RotateID`'s write moved inside the `lcMu` section it already opened for `lastActiveAt` (`pool.go`) — no new mutex, same lock order (`Pool.capMu → Pool.mu → Session.lcMu`). The write holds *both* `Pool.mu` (W, via the function-level `defer`) and `lcMu`; a read is race-clean holding *either one*.
- **New unexported accessor** `(*Session) currentID() SessionID` (`session.go`) — `s.lcMu.Lock(); defer s.lcMu.Unlock(); return s.id`. All lifecycle-goroutine reads route through it: `session.go:407`'s `PreviousID`, `session.go:521`'s warn-log field, and `Session.ID()` itself (`func (s *Session) ID() SessionID { return s.currentID() }`). `ID()` had zero production callers at fix time, but routing it too keeps the invariant exception-free for the first future caller.
- **`Pool.mu`-holding readers are untouched** — `List`, `ResolveID`, `Snapshot`, `saveLocked`, `Activate`'s cap-path map lookups all keep reading `sess.id` directly; converting them to `lcMu` would be a no-op correctness-wise and was explicitly called out (by the architect and reused from memory of prior tickets) as the wrong move.
- **Three comments corrected**, all previously citing the stale "no concurrent reader" claim: the `RotateID` invariant comment, the `BootstrapID` comment (which justified reading `p.bootstrap` instead of `sess.id` by appeal to the same stale invariant — the conclusion was still right, the reasoning needed updating), and a new lock-discipline comment added to the `id` field itself (`session.go`), matching the style already used for `label`/`settings`/`lastActiveAt`.
- New test file `internal/sessions/pool_id_race_test.go` — `TestPool_RotateID_IDRace` runs a writer goroutine ping-ponging `RotateID(a, b)`/`RotateID(b, a)` against a reader goroutine hammering `sess.ID()` on the same live `*Session` (300 iterations each). It asserts only "no `-race` report" — the id value legitimately flip-flops, so there's nothing to compare. Non-vacuity was confirmed manually per the architect's spec: reverting either guard (write outside `lcMu`, or `currentID()` back to a bare field read) reliably fires a `DATA RACE` report; both were restored before landing.

Full diff: `internal/sessions/pool.go` (+comments, write relocation), `internal/sessions/session.go` (+`currentID()`, +field comment, 2 call-site swaps), `internal/sessions/pool_id_race_test.go` (new).

## Patterns established

- **Stale "no concurrent reader" invariants are a standing risk whenever a primitive gets wired into a live watcher later.** The fix pattern here — a two-lock field, written under both locks, read under either — reconciles two independently-correct reader classes (`Pool.mu`-holders vs. lifecycle-goroutine readers) without converting either one. Reach for this shape (rather than picking one lock and converting all readers to it) whenever a field has two structurally different reader populations that already hold different locks for unrelated reasons.
- **Grep sibling comments citing the same invariant before landing a fix.** `BootstrapID`'s comment referenced the identical stale "no concurrent reader of `sess.id`" claim as its rationale for reading `p.bootstrap` instead. The conclusion (`BootstrapID` should keep reading `p.bootstrap`, not `sess.id`) didn't change, but the comment would have kept asserting a falsehood if not updated alongside the primary fix.

## Known gap (non-blocking, flagged in code review, not yet a filed ticket)

`Pool.Activate`'s LRU-eviction path (`pool.go:1439,1441`) reads `sess.id`/`victim.id` as arguments to `pickLRUVictim` while holding only `capMu` — `Pool.mu` is acquired *inside* `pickLRUVictim`, i.e. **after** Go evaluates those call arguments. This read is therefore unguarded by either lock and races with `RotateID`'s write when a `/clear` hits the same session mid-`Activate`. It predates #866 (unchanged by this fix), and is nil-impact today: the torn value (`target`) is only used to exclude an already-known-inactive session from victim candidates, and that exclusion check is provably unreachable for an active target. Still latent, still real per the race detector. The two lock-discipline comments this ticket added (on the `id` field and on `RotateID`) both list `Activate` among the clean `Pool.mu`-holders, which is inaccurate for these two specific reads — a future maintainer trusting that comment could get burned. Worth a follow-up ticket to read `sess.id`/`victim.id` once under `Pool.mu` (or thread the already-known `id` argument through instead of re-reading the field) — not filed yet.
