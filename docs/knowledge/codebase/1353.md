# Ticket #1353 — Probe: does `pyry agent-run` reach its normal exit path on `PYRY_USE_STREAMJSON=1` while a backgrounded command is still running? (live)

The headless-stream structural sibling of #1337. #1337 measured the ptyrunner
default (finding: pyry declared the turn finished while the command it launched
was still running, filed as #1354). Nobody had measured the headless
`PYRY_USE_STREAMJSON=1` path, and it isn't a row flip on #1337's probe: this path
writes no reap log on a clean exit, its trailer is claude's own `result` line, and
the strongest claim it can support is weaker than #1337's by construction (see
below). This ticket ships the live entry point; ten prior offline blockers
(#1349, #1352→#1436→#1437→#1444→#1446/#1447/#1448, #1452, #1453→#1456/#1457→
#1458/#1459, #1462/#1463) shipped every instrument it composes. **It adds no
instrument of its own** except one pure certification helper and its trap.

New file: `internal/e2e/realclaude/finding_stream_exit_path_probe_test.go`
(`//go:build e2e_realclaude`, 694 lines), plus a comment-only, per-hunk
line-neutral edit to `internal/e2e/realclaude/finding_live_run_test.go` (2
sentences, correcting the "only caller" claim `finLiveRunStage` gaining a second
caller falsifies). No production `.go` file touched. Spec:
[`docs/specs/architecture/1353-stream-exit-path-probe.md`](../../specs/architecture/1353-stream-exit-path-probe.md)
(architect self-review PASS). PR
[#1466](https://github.com/pyrycode/pyrycode/pull/1466). One code-review round,
PASS with one non-blocking SHOULD FIX and three NITs.

## Implementation

- **The one design decision: certify the ordering AFTER the gather, and fill
  `trailRunReadings.Ordering`, never `finGatherInputs.Ordering`.** #1462 shipped
  the input field and left it deliberately unfillable by any live caller —
  `trailCertifyOrdering` needs `trailerSighted`, and the only thing that sights a
  trailer is `trailWaitForTrailer`, called *inside* `finGatherReadings` itself, so
  no caller can know the premise before the call it would have to pass it to.
  Recovering it with an earlier `trailWaitForTrailer` would degrade the gather's
  own observation to `trailBoundFromStart` — a discriminator whose own doc says it
  bounds nothing — and that degraded value is what fills the published
  `BoundFrom`, `Staleness` and the gate: a mis-report, not merely a cost. This
  ticket routes *around* the circularity instead of resolving it:
  `readings.Ordering = finStreamCertifyOrdering(sighting.State, pyryExited)` runs
  immediately after the one `finGatherReadings` call and strictly before
  `finExitClassify`. `finGatherInputs.Ordering`'s zero and its "no live caller"
  doc both stay true and unedited — a reader must not conclude the input field
  became fillable.
- **`finStreamCertifyOrdering(sightingState string, pyryExited bool)
  trailOrderResult`** is the one new symbol. Its third argument to
  `trailCertifyOrdering` — `holdHeld` — is a **structural `true`, not a guess**:
  `holdProbeFIFO` releases the FIFO write end only inside the `t.Cleanup` it
  registers itself, which by construction runs after the subtest body returns;
  this rig registers no cleanup of its own and takes its wait on pyry's exit
  **in the body**, so the hold outlives that wait by construction. Getting this
  wrong is the one threat #1462's security review left open: a probe that
  *guessed* `holdHeld` could publish `run-alive-at-sighting-by-ordering` on a run
  where the hold had already been released, and a released hold means the pinned
  pid could have been retired and reissued between the sighting and the later
  read — the artifact would then name a process it can't show is the same one.
  The parameter is the scan's own `string` state, never a `finSighting` (which
  carries `TerminalReason`/`StopReason`/`Subtype`/`KeyNames` this decision
  doesn't need, and a denylist over those wouldn't catch), so no captured byte
  can reach the function at all.
- **The offline trap, `TestFinStreamCertifyOrderingMapsThePremises`**, six rows
  (three scan states × two exit outcomes — `trailAbsent` and `trailAborted` are
  distinct states that must map identically, so a table with only one would let
  a `sightingState != ""` implementation pass unnoticed) plus one assertion that
  spans every row: **no row may answer `trailOrderVoidUnheld`**. That single
  clause is what makes the trap discriminating and not decorative — a
  `holdHeld=false` mutant reddens all six rows because that void outranks both
  other premises (the hold's failure removes the claim's *subject*, not merely an
  endpoint). RED→GREEN proven via three `go test -overlay` mutants (`holdHeld`→
  `false`; `== trailSeen`→`!= ""`; the first two premises transposed), each FAIL
  against an otherwise-green 6/6 tree.
- **The body, `finStreamExitRunProbe`, is load-bearing at four points, in
  order.** (1) Stage under `finLiveStageStreamEnvDelta()` — the FIFO write end
  stays held because this rig registers no cleanup of its own, an **inversion**
  of the neighbouring `background_reach_probe_test.go` precedent (which releases
  the FIFO first so pyry gets a real chance to finish) and not a copy of it. (2)
  Wait for pyry's own exit **in the body**: a channel receive on `h.PyryExited`,
  with `h.ExitStatus` read **inside the receive arm only** — that channel's close
  is the sole happens-before edge with the driver's `cmd.Wait` goroutine, so any
  shape hoisting the field out of the arm is a data race `go test -race` would
  catch; there is deliberately no helper that would make that easy to write. (3)
  The claude-still-alive read, `pinReadState(h.ClaudePID).Verdict`, taken after
  the wait — its **meaning is re-derived for this path**: on ptyrunner the
  expected `no-such-process` comes from `sess.Close()`'s SIGTERM; here claude
  exits on its own before pyry returns, so the same value arrives for a different
  reason and decides only whether any parentage-based view of the command could
  have been informative at all — corroboration, never the finding. (4) A
  **second**, distinct `pinReadState` call over the during-turn pinned set's
  first pid (`h.Pin.PGIDs[0]`, guarded so an empty set takes no read rather than
  calling `pinReadState(0)`, which would falsely claim an instrument ran) —
  never a reuse of the claude read, which names a different process. This
  discharges the three sub-clauses the AC puts on the aliveness reading
  structurally rather than by argument: pinned during the turn while reachable,
  matched on the FIFO path in full argv; the re-check is a lookup for that pid
  alone with no descendant requirement; and `pinReadState`'s closed set
  separates `pinStateRunning` from `pinStateExitedNotReaped` because `ps` lists a
  zombie as a row.
- **One `finGatherReadings` call**, `Needles` the FIFO path alone (never the
  driver's two-needle list — this gather has no `finLivePinReduce`-style
  separation, so a claude needle would pollute the classifier's match-count
  arms), `RunnerPath` reduced at the call site via `tdnRunnerFromArgv` (never
  inside the gather, and never `reachRunnerPathFromArgv`, which keys on
  `--append-system-prompt-file` and both builders emit it) — this is the reading
  that makes `trailGateAbsentOwesNone` reachable at all from a live run, and the
  same reading `finRecordBuild`'s `runner_from_argv` is built from, so the record
  and the gate cannot disagree. `finExitClassify` is **reused from #1337's
  probe, not copied**: staging is decided before the classifier is consulted, so
  an unstaged run's post-trailer scan (which still parses a healthy process
  table and matches nothing) never reaches an answer about a run in which no
  command ever existed.
- **The log channel, seven sites, `t.Logf` only** (the artifact writer's two
  files are untouched). Every rendering is `json.Marshal` or field-by-field —
  never `%v` on a struct or slice, the concrete mechanism that would otherwise
  print `h.Pin.Rows`' verbatim argv from an ordinary-looking debug line. The
  pinned-pid read is logged as `.PID` + `.Verdict` only, never whole (its
  `Detail`/`StateColumn`/`ToolStderr` are string-bearing and the
  instrument-failed branch folds raw `ps` stderr into `Detail`). The finding
  sentence (site 7) is keyed on the classifier's value and states, in the same
  breath: the exit code alone can't separate a completed run from a terminated
  one (both exit 0, and since #1388 a complete result trailer additionally makes
  `streamrunner` discard claude's non-zero status); what carried the answer was
  the certified ordering and the pinned-pid re-read, never a trailer field; and
  no declared-finished instant exists on this path, so #1337's stronger
  aliveness-at-declared-finish claim is recorded as **unavailable here**, never
  restated in weaker words.
- **No `ps -E`/`-Eww` anywhere** — the only `ps` this file reaches is
  `pinReadState`'s `pid=,ppid=,stat=` pinned lookup. The raw trailer line is
  unreachable by the shape of the gather's third return (`finSighting` carries
  neither `trailScanResult.Line` nor the `*resultTrailer`), not by discipline
  alone.
- **The shipped-file edit is comment-only and per-hunk line-neutral** (`git diff
  -U0`: 1↔1 and 5↔5), correcting `finding_live_run_test.go`'s "exercised
  end-to-end only by the live entry point in #1337" / "`finLiveRunStage`'s ONLY
  caller" sentences to name both `finExitRunProbe` (#1337) and
  `finStreamExitRunProbe` (#1353). Chosen specifically to avoid displacing any of
  that file's 3 in-package + 15 `docs/`-side inbound numeric citations — the tax
  #1452 and #1458 both paid on this same file family.
- **Prefix freeness verified and recorded**, `git grep -o -h -E
  '<prefix>[A-Za-z0-9_]*' -- '*.go'`: `finStream` → 0, controls `finExit` → 35,
  `trailOrder` → 171, an absent prefix → 0.
- **Deviation from the spec's size table, disclosed in the PR body**: 700 new +
  6 rewritten lines against a ~530-line estimate and a ≤~600 red line. The
  overage is comment prose, not code (one `if`, one `select`, one `switch` of
  the file's own) — every claim the spec's §§ 2, 4, 4a, 5, 7 require a comment
  to carry is present; the developer trimmed the one place a shipped symbol's
  own doc had been re-argued (`finGatherInputs.PinnedPid`'s selection/timing
  rules, now cited instead) and left the rest.

  `run-void-pyry-did-not-exit`, but that value is **unreachable on this path** —

  run *actually* reached rather than transcribing AC5's mapping verbatim.
  `run-void-sighting-route-not-staged` is likewise unreachable from this rig now

- **NIT**: size overage (700 vs ~530/≤600), disclosed and proportionate — 18%
  larger than the sibling for a file that additionally ships
  `finStreamCertifyOrdering` and its trap, measured against the sibling's

## The live measurement — not yet taken, and the gate that removed the label did not run it

**As of this writing, no live finding exists for this ticket, despite
`needs-real-claude` having been removed and the ticket advanced to
Documentation.** This matters enough to record precisely, because it is easy to
misread as done:

The dispatcher's automated "Real-claude gate" ran
`go test -tags e2e_realclaude -timeout 20m -json ./internal/e2e/realclaude/...`
against the merged branch and posted **652 executed, 652 passed, 0 failed** —
and on that evidence removed `needs-real-claude` and moved the ticket here.
But that invocation sets none of this family's opt-in env vars, and
`TestRealClaude_StreamExitPathWhileCommandRuns` — **the one test this ticket
exists to run** — is explicitly named among the run's own 15 *skipped, not
counted* tests, alongside #1337's equally-gated
`TestRealClaude_ExitPathWhileCommandRuns`. A skip is not a pass, and the gate's
own evidence comment says so about the suite in aggregate — but the label
removal did not check whether *this ticket's specific* opt-in test was among
the skips before treating "0 failed" as sufficient.

Compare #1337: its own gate parked on `needs-real-claude` with an *operator*
required to run the exact invocation by hand (2026-08-06, claude 2.1.220), and
its codebase note (this file's model) was written *before* that live run
happened, explicitly saying so, followed nine minutes later by the operator's
finding comment and, the same day, a follow-up ticket (#1354) for the gap it
found. That is the precedent this ticket's own AC6 assumes. #1353's automated
gate is a newer dispatcher capability that evidently does not (yet) know to run
per-ticket opt-in-gated probes as part of clearing `needs-real-claude` for a
ticket that carries one — it can only prove the *rest* of the tagged suite
still compiles and passes.

**Consequences for this ticket's acceptance criteria**, stated precisely rather
than assumed:

- **AC6 — the issue comment with the claude version, the observed runner path,

- The exact invocation remains, unchanged, in the skip message and the PR body:

This is not a defect in the shipped code — every AC the developer and code

must run each ticket's *named* opt-in invocation before clearing
`needs-real-claude` on a ticket that has one, or ticket-specific opt-in probes
need a distinct label the generic gate does not clear. Filing or fixing that is
outside this ticket's and this documentation pass's scope; recorded here so the
next reader — or whoever eventually runs the invocation above — knows the
finding is still open, not merely unwritten.

## Patterns established

- **A shipped field's "no live caller can fill this" prohibition can be routed
  around without being violated**, by certifying the same information onto a
  *sibling* field the composition fills after the call the prohibited field
  would need to be passed before. The prohibited field's zero, its doc, and the
  circularity argument all stay true and unedited; nothing downstream needs to
  know the routing happened. Reusable wherever a later ticket finds a shipped
  "structurally unfillable" field and a live use for the value it would have
  carried.
- **A structural `true` beats a guessed one, and the belt is deterministic code,
  not a second stochastic reading of the prose.** `finStreamCertifyOrdering`'s
  third argument is provably true from `holdProbeFIFO`'s own release mechanics
  plus this rig's own choice to register no cleanup; the offline trap's
  no-`trailOrderVoidUnheld`-row assertion is the deterministic check that would
  catch a future edit accidentally making the premise guessable again. Confirms
  the project's standing "belt-and-suspenders means different fabric" principle
  at the level of a single boolean.
- **Two probes calling the identically-typed, identically-shaped read
  (`pinReadState(h.ClaudePID).Verdict`) can mean opposite things**, and copying
  the sibling's explanatory comment across would ship a false claim. On
  ptyrunner the expected `no-such-process` comes from an active SIGTERM; here it
  comes from claude's own unforced exit before pyry returns. Same code, same
  expected value, different mechanism — the doc has to be re-derived per path,
  not inherited.

## Lessons learned

(From the PR body's own "Lessons learned" section, the code review, and this
documentation pass.)

- **A "reuse, do not rebuild" spec can still leave one field structurally
  unfillable, and routing around it beats widening it or waiting for a
  resolving ticket.** See "Patterns established" above; `finGatherInputs.Ordering`
  stays exactly as #1462 shipped it.
- **The reap-log absence on this path is structural, not a shortfall** — worth
  restating because it inverts #1337's central evidentiary argument rather than
  merely weakening it: `streamrunner.Run` reaps only inside `cmd.Cancel`, whose
  own comment says it never fires on a clean exit, so a healthy stream-path run
  writes *no* reap line at all. A post-trailer argv match here is therefore the
  **predicted** reading, not the anomaly it would be on #1337 (which found 0
  matches across 893 rows precisely because its reap had already killed the
  group).
- **A spec's "these files look like they need an edit and do not" list clears
  sites, not files** — see the code-review SHOULD FIX above, saved to agent
  memory as `code-review-spec-no-edit-list-is-incomplete`. When a branch adds a
  second caller/producer where the tree previously had exactly one, grep the
  whole package for the claim class before trusting a spec's per-file clearance
  argument.
- **An automated "real-claude gate" that runs the generic tagged suite is not
  evidence about a ticket-specific, opt-in-gated live probe**, even when it
  reports 100% pass on hundreds of executed tests — if the specific test is
  among the (correctly, honestly reported) skips, "0 failed" says nothing about
  it. See "The live measurement — not yet taken" above. This is the same class
  of false-green risk the project has been burned by before at the exit-code
  layer (#1168/#1169) and at the skip-vs-pass layer (this ticket's own gate
  comment quotes 2026-07-22 as the precedent) — here it recurs one layer up, at
  *which tests a generic gate invocation actually exercises* for a ticket
  carrying a named, opt-in invocation of its own.
