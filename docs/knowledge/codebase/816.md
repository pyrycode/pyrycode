# Ticket #816 — demote mid-run trust/network detection from fatal to logged

`ptyrunner.Run`'s event loop treated a **mid-run** trust-folder modal or
network-failure detection as fatal — it returned `ErrTrustModalDetected` /
`ErrNetworkFailure` the instant the `EventKindPty{ModalShown(trust),NetworkFailureShown}`
event fired, killing an otherwise-progressing run on the first match. This ticket
reverses only that **policy**: the two mid-run cases now `Warn` +
`SetTerminalDetail` + continue, converging on the shape the mid-run
`EventKindPtyMcpFailureShown` case already used. The mid-run monitoring
**mechanism** from [#513](513.md) (the `tuidriver.Session.Events` unified stream)
is untouched. The startup/idle `WaitReady` aborts stay fatal — a trust/network
failure *before* the run begins means it genuinely cannot start.

The justification for the old fatal short-circuit was forgery: during the
2026-07-07 tui-driver detection review, every mid-run fire of these two detectors
in the 1136-cast corpus was a **content forgery** (an agent rendering a ticket
body or the detector's own source that quotes the anchor string onto the grid).
tui-driver v1.8.0's structural detectors (#219–#227) removed that — trust now
requires the dialog option-row shape, network is re-anchored on the live
`Unable to connect to API` line and bottom-region scoped — and they are live via
pyry **v1.8.1**. With forgeries no longer classifying, a mid-run match is far more
likely genuine, and a false kill on a single mid-stream match is strictly worse
than a slightly later watchdog stop. This ticket removes the remaining blast
radius so even a *genuine* mid-run blip does not kill a live run.

Spec: [`816-demote-midrun-trust-network-detection.md`](../../specs/architecture/816-demote-midrun-trust-network-detection.md).
Parent (introduced the mid-run stream this reverses the policy of): [`513.md`](513.md).

## Implementation

Single production file, no new types/functions/signatures. Blast radius is zero
outside the package: no non-test production code branches on these sentinels
(`cmd/pyry/agent_run.go`'s `runAgentRunPty` propagates `Run`'s error unchanged),
so a mid-run detection now collapsing instead of returning a sentinel changes no
consumer contract.

- **The two mid-run cases demoted (`runner.go:540-549`).** In the `for ev := range ch`
  switch:
  - `EventKindPtyModalShown` + `ModalClassTrustFolder`: `Warn` +
    `SetTerminalDetail("trust_modal_detected")`, then fall through. `return
    ErrTrustModalDetected` removed.
  - `EventKindPtyNetworkFailureShown`: `Warn` +
    `SetTerminalDetail("network_failure_detected")`, then fall through. `return
    ErrNetworkFailure` removed.
  - `EventKindPtyMcpFailureShown` was already `Warn` + continue (mcp banners have
    never been fatal). All three now share one adjacent rationale comment
    (`runner.go:527-539`).
- **`SetTerminalDetail` deliberately retained on the demoted path.** It is
  idempotent-first-wins and surfaced **only** when the run resolves to
  `ExitReasonError` (`streamjson/emitter.go`). So:
  - Run recovers to end-of-turn (`ExitReasonCompletion`) → detail ignored, clean
    `success` trailer, no pollution.
  - Run later genuinely wedges (no end-of-turn → the PTY-quiet watchdog fires →
    `ExitReasonError`) → the wedge trailer's `terminal_reason` reads
    `trust_modal_detected` / `network_failure_detected`. First-wins lets the
    earlier mid-run detection beat the watchdog's own, less-specific
    `watchdog: …` detail, so the trailer *names* the condition that preceded the
    wedge.
- **Startup/idle aborts untouched (`runner.go:402-411`).** `ready.TrustModal` →
  `ErrTrustModalDetected`, `ready.NetworkFailure` → `ErrNetworkFailure` still
  return. `ready.McpFailure` stays non-fatal (as since #513). The demotion applies
  only to detections that fire mid-run.
- **Stale contract doc corrected (`runner.go:203-213`).** The `Run` doc bullet
  claimed the sentinels also surface "on a mid-run `EventKindPty{…}` transition."
  Rewritten so `ErrTrustModalDetected` / `ErrNetworkFailure` are documented as
  returned **only** from the startup/idle `WaitReady` classification; mid-run
  trust/network/mcp detections are logged and consumed (the run continues), with
  the terminal detail still landing on the wedge trailer if the run later fails to
  reach end-of-turn. `ErrMcpFailureBanner` was dropped from the returned list — it
  was never returned (non-fatal at idle and mid-run alike). The sentinel `var`
  docs (`runner.go:64-77`) are already idle-scoped and stay accurate; both
  sentinels remain live (still returned from the startup path), so no dead-code
  issue.

### Test flip — `TestRun_MidRun_ModalAndBannerDetection` (`runner_test.go`)

The `mid_trust` / `mid_network_failure` helper fixtures need **no change** — they
already emit the detector event after the prompt lands and then wedge with no
end-of-turn, which is exactly the demoted path. The table test was reworked:

- Dropped the `want error` / `substring` fields; assert `Run` returns `nil` and
  that neither sentinel is returned (`!errors.Is` for both). This is the core
  "does NOT end the run" contract.
- Kept the `wantReason` assertion (`terminal_reason` ==
  `trust_modal_detected` / `network_failure_detected`) — proves the demoted branch
  still recorded the detail and that it survived onto the wedge trailer.
- Added `trailer.is_error == true` — documents that the run still *fails*, just via
  the watchdog rather than the fatal sentinel.

The startup-abort tests (`TestRun_TrustModalDetected`,
`TestRun_NetworkFailureDetected`, `TestRun_McpFailureNonFatal`,
`TestRun_RecordOn_ErrTagged`) are unchanged and stay green.

## Patterns established

- **Reverse a policy without disturbing its mechanism.** #513 built the
  unified-stream mid-run monitoring and made trust/network fatal on a mid-run
  fire; #816 flips *only* the fatal response to `Warn` + continue, leaving the
  event loop, the merge goroutine, and the watchdog byte-for-byte. When a change
  is "we no longer want to *react* this way to X," locate the single reaction site,
  not the detection machinery — here, two `return` statements, converging on a
  sibling case that already had the desired behaviour.
- **Belt-and-suspenders means different fabric.** The remaining fatal net for a
  genuinely wedged run is deterministic code — the PTY-quiet watchdog plus the
  dispatcher's wall-clock cap — not a stochastic detector short-circuit. A
  transient network blip is separately covered by claude's own ~10× backoff
  retry. Removing the stochastic kill is safe precisely because the deterministic
  net already exists.
- **A non-fatal path can still record a terminal detail, and it's diagnostic-positive
  to do so.** Because `SetTerminalDetail` is first-wins and surfaces only on
  `ExitReasonError`, keeping the call on the demoted branch costs nothing on a
  clean completion and *improves* the wedge trailer when the run does fail: the
  trailer names the mid-run condition that preceded the wedge instead of the
  generic watchdog reason. The demotion gives the run a chance to progress and,
  if it can't, still explains why.

## Lessons learned

Lifted from the PR body's "Lessons learned" section (developer-flagged; confirmed
by the code-review NIT as correct engineering judgment):

- **The mid-run wedge test races the watchdog for the first-wins
  `SetTerminalDetail`, and the race is won or lost by `PromptCommitTimeout`, not
  just the watchdog limit.** Both the watchdog and the event loop only start
  *after* `DeliverPrompt` returns — which blocks for `PromptCommitTimeout`
  (tui-driver default **3 s**) when the fixture never commits. The watchdog
  measures `buf.QuietFor()` (wall-clock since the last PTY byte), so a short
  `PTYQuietLimit` **alone** makes the watchdog win instantly: quiet has already
  accrued past the limit before the event loop even opens. The fix is to *also*
  set a short `PromptCommitTimeout` (200 ms) so the event loop starts before quiet
  accrues — the same pairing `TestRun_WatchdogFires` uses. The flipped test
  therefore sets `PromptCommitTimeout = 200ms` **and** `WatchdogTick = 50ms` +
  `PTYQuietLimit/SpinnerFreezeLimit = 2s`, giving the detection ~1.75 s of margin
  to set `terminal_reason` before the watchdog fires and ending each subtest in
  ~2 s. This deviates from the spec's suggested opts (`PTYQuietLimit: 1s`, no
  commit-timeout change); the deviation is correct because the spec under-counted
  the 3 s commit window that gates when the loop starts.

## Notes

- **Not security-sensitive.** This *removes* a forgery-triggerable fatal on a local
  PTY boundary (security-net-positive), adds no new surface or parsing, and leans
  on hardening (tui-driver v1.8.0 structural detectors) that already shipped in a
  separate repo. No new design surface.
- **No ADR.** The demote-vs-keep-fatal trade-off is fully argued in the ticket body
  and spec (the counter-argument — a genuine mid-run trust modal means the run is
  wedged on an un-answerable prompt — is answered by claude's own retry, the
  watchdog, and the vanished forgery justification). It reverses one policy bit of
  an existing mechanism, not a net-new cross-cutting convention; follows #513's and
  #813's no-ADR precedent.
- **Feature doc left untouched, by design.** `ptyrunner-package.md` still describes
  the pre-#513 post-idle one-shot snapshot detection and never documented the
  mid-run event loop at all — so #816 falsifies no existing sentence in it. That
  doc's broader staleness (across #478/#479/#509–#513) was already recorded in
  [`513.md`](513.md) (Related §), which deferred a from-scratch rewrite to a
  dedicated feature-doc-refresh ticket. Patching an isolated #816 note into a body
  that lacks the #513 context would be a dangling reference and exactly the
  piecemeal drift that deferral avoids; the refresh ticket should fold in the
  demotion when it rewrites against post-#816 state.
- **Code review: PASS (PR [#818](https://github.com/pyrycode/pyrycode/pull/818)),
  no blocking findings.** One NIT confirmed the `PromptCommitTimeout` deviation
  above as sound. `make check` green (vet + race + staticcheck + substrate-guard).
  One unrelated known flake (`TestFatalCloseCodes_HaltsReconnect_RacingSendError`
  in `internal/transport`) went red once in a full run, passed 3× isolated — no
  relationship to this change.
