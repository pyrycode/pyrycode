# #1124 — streamsup: restart the runner into a fresh session under a new id

**Size:** S. Purely additive, one package (`internal/streamsup`), no interface change, no new file — 2 new
`restartMu`-guarded fields, 1 new exported method (`RestartFresh`), 1 new unexported accessor
(`nextSpawnID`), 1 call-site edit in `Run`. Not security-sensitive — the routing sibling (#1125,
blocked-by this ticket) carries the security review; this ticket delivers only the runner-internal
mechanism #1125 consumes.

## What shipped

`RestartFresh(newID string)` on `*streamsup.Runner`: rotates the runner's persistent session id to
`newID` and re-arms first-run form, so the *next* spawn uses `--session-id <newID>` (a fresh transcript,
no fork) instead of `--resume`. A later crash-respawn then `--resume`s the **rotated** id — never the
pre-rotation one, which is the load-bearing subtlety the ticket called out (a naive `Restart` would
silently regress to the old id).

The id source moved from the private, construction-time `cfg.SessionID` to a `restartMu`-guarded mutable
`r.sessionID` (seeded from `cfg.SessionID` in `New`). `Run`'s spawn loop now reads `nextSpawnID()` instead
of `r.cfg.SessionID` directly: it snapshots `(sessionID, rotatePending)` and clears `rotatePending` in one
critical section (no TOCTOU between the id read and the flag consume). When `rotatePending` is true, `Run`
re-arms its Run-goroutine-private `firstRun` local to `true` before calling `buildArgs` — `buildArgs`
itself is untouched, byte-identical to before.

`RestartFresh` mirrors `Restart`'s concurrency discipline exactly: publish under `restartMu` (here,
`sessionID` + `rotatePending` instead of `args`), send the non-blocking `restartCh` hint, then cancel
`iterCancel` if a child is live — hint-before-cancel, same as `Restart`, so the post-spawn drain observes
the token even if the cancelled child exits before the hint is read. Two rapid `RestartFresh` calls
coalesce to one relaunch with the newest id, same as `Restart`'s args-swap coalescing. Unlike `Restart`,
it leaves `r.args` untouched — `new_session` rotates the id, not the model/flags; args stay owned by
`Restart`/`UpdateSettings`. An empty `newID` is a no-op (`Warn`-logged) — the runner never spawns
`--session-id ""`; this is a deterministic last-resort guard, the real validating boundary is the
pool/routing layer (#1125), per the project's "caller-supplied id validation at the primitive boundary"
convention.

The existing `started`-gated `firstRun` flip (fixed 66cc50e, see
[streamsup-package.md](../features/streamsup-package.md)) does the rest of the work for free:

- **Fresh spawn succeeds:** `firstRun` flips back to `false`, so the next crash-respawn `--resume`s the
  rotated id.
- **Fresh spawn's setup fails** (`cmd.StdinPipe`/`cmd.Start` error, `started == false`): `firstRun` stays
  `true`, so the retry keeps trying `--session-id <newID>` — the fresh id was never established on disk,
  so a `--resume` retry would error "no conversation found," exactly the failure mode the pre-existing
  `firstRun` gate was built to avoid, now extended to the rotated id for free.

## Patterns established

- **Rotate the mutable id, not the args.** When a caller-driven restart needs to change *what session*
  the runner spawns into (not what flags it spawns with), add a dedicated field + accessor pair
  (`sessionID`/`rotatePending` via `nextSpawnID`) rather than routing it through the existing
  args-swap (`Restart`). The two concerns — argv content vs. session identity — stay independently
  mutable under the same lock, composing cleanly if both fire close together.
- **Consume-on-read for one-shot cross-goroutine flags.** `nextSpawnID` snapshots and clears
  `rotatePending` in a single `restartMu` critical section, so a rotation fires exactly once regardless
  of how many `Run` iterations pass before the next spawn (including setup-failure retries, which must
  *not* re-consume — and don't, since `rotatePending` is already cleared and `firstRun`'s own state
  carries the "not yet established" signal across retries).
- **New exported method, not a widened interface.** `RestartFresh` is a concrete `*Runner` method, kept
  off `sessions.Runner` (#1077) — same discipline as `Interrupt` (#1120) and `SendEsc`. The consuming
  sibling reaches it via a narrow interface or type assertion, a decision left to that ticket.

## Lessons learned

None beyond what the spec already anticipated — the implementation matched the architect's seam
(`RestartFresh`/`nextSpawnID`) and test plan (three scenarios: rotate-then-resume, no-live-child safety,
empty-id no-op) without deviation.
