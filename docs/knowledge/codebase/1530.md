# Ticket #1530 — `internal/devices`: cross-process locked read-modify-write

Adds `WithLock`, a `flock(2)`-backed critical section that lets `pyry pair`, `pyry pair revoke`, and the daemon's `register_push_token` serialize their `devices.json` read-modify-writes across OS processes. This slice ships the primitive only — no caller is rewired, so the cross-process race stays open until the two consumer slices (`cmd/pyry` writers, then the daemon writer) land.

Split from #1510. See [ADR 029 correction](../decisions/029-devices-registry-reload-at-handshake.md#correction-2026-08-19-1530) and [`features/devices-registry.md` § Two-writer clobber guard](../features/devices-registry.md) for the prior design this ticket overturns.

## Implementation

- New file `internal/devices/lock.go`: `WithLock(devicesPath string, wait time.Duration, fn func() error) error`, `DefaultLockWait = 5 * time.Second`, `ErrLockBusy`. No new package, no new types, stdlib only (`syscall.Flock`, no build tag — `golang.org/x/sys` stays indirect; Windows is out of scope per `CLAUDE.md`).
- **Sole acquirer.** `WithLock` is the only place that takes the file lock. `Load`, `Save`, and `Reload` are unchanged and do not acquire — nesting would open a second file description and self-contend, since `flock(2)` locks the open file description, not the process.
- **Lock lives on a sibling file, `devicesPath + ".lock"`, never on `devices.json` itself.** `Save` commits via temp-file + `os.Rename`, which installs a new inode at the target path; a lock held on the pre-rename inode stops excluding a second acquirer that opens the path afterwards. The sidecar's inode is never replaced, so it keeps excluding across a `Save` inside the critical section. The lock file is created on demand at `0600`, never deleted (deletion races acquisition), and never written to — it exists only to own a stable inode.
- **Bounded, non-blocking acquisition.** `LOCK_EX|LOCK_NB` polled every 10ms against a `wait`-derived deadline, not a blocking `LOCK_EX`. This is the one deliberate divergence from `docs/specs/architecture/341-agentrun-trust-helper.md`'s otherwise-identical lock design (sibling file, `O_CREATE|O_RDWR` `0600`, never-delete, defer-unlock-then-close): #341 chose blocking because it "has no nonblocking-acquire requirement," but this primitive does — a daemon handler must not wedge forever behind a stuck CLI process. Exhausting the wait returns `ErrLockBusy` naming the lock path; `fn` is never invoked and the on-disk file is left byte-unchanged. `EWOULDBLOCK == EAGAIN` on both darwin and linux, so one `errors.Is` check covers both.
- **Callback shape is `func() error`, not `func(*Registry) error`.** A callback taking a freshly-`Load`ed registry would be wrong for the daemon: `RegisterPushToken` mutates a long-lived `*Registry` carrying un-persisted `LastSeenAt` bumps and in-flight push state, and handing it a fresh registry would discard that. The bare thunk lets each of the three writers compose its own `Load`/`Add`/`Save`, `Load`/`Remove`/`Save`, or `Reload`/`Save` sequence.
- Cold-start mkdir: `os.MkdirAll(filepath.Dir(lockPath), 0o700)` runs before the lock file is opened, ahead of `devices.Load` in the future `pyry pair` wiring — on a first-ever pair the instance directory doesn't exist yet (it's created later by `identity.LoadOrCreate` and by `Save`'s own mkdir). Same mode `Save` already uses against the same directory.
- `fn`'s error returns verbatim (not wrapped), so callers' `errors.Is` against their own sentinels keeps working.

## Patterns established

- **Sidecar-lock-over-atomic-rename is now the in-repo precedent for this specific hazard** (flock + rename-replaces-inode). #341's spec derived the same design independently but shipped without implementing it; this is the first `flock` in the repo. Any future file needing cross-process exclusion around an atomic-rename write path should reuse this shape rather than re-derive it.
- **Bounded non-blocking acquisition (`LOCK_EX|LOCK_NB` + poll-to-deadline) over blocking `LOCK_EX`** whenever a caller runs on a request path that must not wedge behind a peer process. Contrast with #341, which chose blocking because it had no such caller.
- **Same-process two-goroutine tests are a valid mutual-exclusion proof for `flock`**, because it locks per open file description rather than per process — no subprocess harness needed. This does not generalize to `fcntl` byte-range locks, which are per-process and would not contend the same way.

## Lessons learned

- The primitive alone proves nothing about the bug it exists to fix — this slice deliberately ships no caller rewiring, so `internal/devices` today is unchanged in behavior; the cross-process race (both the lost-add and, per the architecture doc's revoke-direction analysis, the lost-revoke case) stays open until the `cmd/pyry` and daemon consumer slices land and start calling `WithLock`.
- ADR 029's "the next reload reconciles it" consequence and its flock rejection rationale were wrong: `Reload` reconciles memory *into* disk with disk authoritative for membership, so once a `Save` writes a snapshot omitting a device, that device is gone from disk permanently — no later reload resurrects it. See the correction appended to ADR 029 and the caveat added to `features/devices-registry.md` § Two-writer clobber guard.
