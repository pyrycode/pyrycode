# Ticket #1382 — Map claude's `task_updated` background-task subtype to a bounded daemon event

Second scalar subtype on the `system` dispatch #1380 built. `system/task_updated` carries `task_id` and `patch` — `patch` being an **object** observed with one key (`is_backgrounded`) and whose future keys are claude's to choose. That typing question is what separates this ticket from #1380's six plain strings, and is the ticket's real substance: one arm in `emitSystemSubtype`, one variant on the `turnevent` sum type, one cap constant.

## Implementation

- **`turnevent.BackgroundTaskUpdated`** (`internal/turnevent/event.go`) — new variant, placed right after `BackgroundTaskStarted`. Fields: `TaskID` (claude's `task_id`, join key back to the `BackgroundTaskStarted` that opened the task, no translation), `Patch` (claude's `patch`, carried **whole and unparsed** as serialized text), `TruncatedFields []string` (declaration-order cut report, `nil` when nothing cut). Same two deliberate drops as its sibling — `session_id` and `uuid` — enforced by decode-target absence *and* a reflection sweep in the test.
- **`Patch` is a `string`, not `json.RawMessage`** — a two-stage decision, not one:
  - At the decode boundary (`systemTaskUpdatedLine.Patch`) it *is* `json.RawMessage`: verbatim bytes, no key reordering, no `float64` rounding of a large integer id. Declaring a struct shape would discard every key claude hasn't shipped yet (`streamMessage.Content`'s reasoning, reused).
  - At the event boundary it becomes a bounded `string`, following `Unrecognized.Raw`'s precedent verbatim: the producer truncates at construction, and a truncated object is no longer valid JSON, so typing it as raw JSON would be a lie.
  - Pipeline: `line []byte` → `json.RawMessage` (verbatim) → `truncateField` → `string` on the event — the same shape `emitUnrecognized` already has, one field down.
- **`maxTaskPatch = 4 << 10`** (`internal/streamsup/parser.go`) — a new, independent constant, argued from the envelope rather than the observation: the captured patch is 24 bytes with one key, and a single-key patch says nothing about a two-key one, so the observation is too weak to multiply (unlike `maxTaskDescription`, which could anchor on a command line's reasoned size distribution). Worst case one `BackgroundTaskUpdated` carries `maxTaskFieldID + maxTaskPatch` = 4352 bytes = 6.6% of the 65519-byte v2 envelope cap, deliberately in line with `BackgroundTaskStarted`'s 7.4% so the event family has one worst case to hold in mind. Kept a separate constant from `maxTaskDescription` even though both currently equal 4096 — they bound different fields for different reasons, and folding them would let a future change to one silently move the other's budget. Test fixture pins it as an independent literal (`taskPatchCapFixture`), same discipline as #1380's cap fixtures.
- **Dispatch** — one new arm: `case "task_updated": return p.emitBackgroundTaskUpdated(line)`. Nothing else in `consumeLine` changes; `system` stays on `ignoredLineTypes`, so `TestParser_IgnoredLineTypesIsTheMeasuredSet`'s pin on `{system, rate_limit_event}` stays green untouched.
- **`systemTaskUpdatedLine`** — new decode target, two fields only (`task_id string`, `patch json.RawMessage`). The two field types are deliberately asymmetric: `TaskID` stays a `string` so a non-string `task_id` fails the whole decode (undecodable path); `Patch` as `json.RawMessage` accepts *any* valid JSON value, which is the deliberate permissiveness — "whatever claude puts there" is the point, and inventing a validation rule for a shape observed once is exactly what #1380 declined to do for missing fields.
- **`emitBackgroundTaskUpdated`** mirrors `emitBackgroundTaskStarted` structurally: decodes the **top-level** `line` bytes (never a nested field — what keeps the event unforgeable out of claude's own tool output), undecodable payload → content-free `Debug` naming the subtype keyword only, no event, `return true`; both fields bounded via the same local `bound` closure as sequential statements (not a composite literal) so `TruncatedFields`' declaration order is visible to a reader.
- **One genuinely new property, found and documented but not test-pinned**: `truncateField`'s scrub is load-bearing on the *untruncated* path for `Patch` specifically. `encoding/json` U+FFFD-replaces invalid bytes when decoding into a `string`, but copies them verbatim into a `json.RawMessage` — so an invalid UTF-8 byte inside `patch` survives decode and is silently deleted by the scrub even when nothing is cut. `truncateField`'s doc comment was corrected (`CORRECTED 2026-08-07 (#1382)`) to scope its old "no-op in practice" claim to string-decoded fields; `Patch`'s doc states the consequence: `TruncatedFields` reports the cap cut only, never a scrub removal, so `Patch` can differ from claude's bytes without being listed as truncated. Code review verified the property is real via `-overlay` mutation (see Code review notes) but no persisted test pins it — flagged as a coverage gap, not a correctness one.
- Field mapping and cap arithmetic built from the same committed capture #1380 used, `internal/e2e/realclaude/testdata/dropped_lines_v2.1.220.json`, read through the existing `capturedSystemLine` reader (no second reader written). The bound itself is proven by synthesized lines — the capture (170 bytes, `patch` at 24) is far under every cap and cannot prove a bound.

## Patterns established

- **A field mapping and its bound can require two different provenance inputs even under one "build from the capture" rule.** The capture proves *which fields exist and where they land*; it cannot prove a cap nothing in it approaches. Reading the rule as "no synthesized line anywhere in the file" would make the bound criterion unprovable — the ticket's own AC drew that boundary explicitly (field-mapping structure vs. line-level synthesis), and it's a reusable distinction for #1381.
- **An inherited test-guard expression can silently weaken when the shape it was fitted to changes.** #1380's sweep-floor `swept < len(routes)*2` was exact-fit only because `BackgroundTaskStarted` has as many routes as string fields (4 and 4). `BackgroundTaskUpdated` has 1 route (`TaskID`) and 2 string fields (`TaskID`, `Patch`), so the same expression would floor at 2 against an actual 4 — passing with half the sweep silently unrun. Replaced with a literal `4` (2 string fields × 2 dropped keys) with the arithmetic written down, rather than copying the expression forward.
- **A "carried whole, not key-enumerated" claim needs a synthesized multi-key fixture; the capture alone cannot falsify a key-enumerating implementation** that happens to match its one observed key. The line-level keys stay exactly the capture's; only `patch`'s *internal* structure is invented, and only to prove the mapping declares nothing about it.
- **`json.RawMessage` copies its input on decode** — verified, not assumed — so a value decoded from a subslice of the parser's read buffer does not alias it and creates no retention hazard. Worth restating for any future field that decodes into `RawMessage`.
- **A `CORRECTED (#N)` doc comment records a property discovered mid-build and inherits no test row for free.** `truncateField`'s scoped no-op claim is the second instance of this shape in the package (the first being #1380's own history); code review's mutation run confirmed the underlying property is real even though nothing pins it.

## Lessons learned

(From the PR body — developer's notes, lightly trimmed.)

- The architect's AC5 comment sweep missed one site, and the miss was in a sentence's tail: `capture_test.go`'s doc read "#1381 … and #1382 … map the sibling subtypes out of the same file, **and this package already drives both through the drop table**." The sweep quoted the first clause (names no set, correctly ruled no-edit) and stopped; the trailing clause asserts `task_updated` *is* in the still-dropped set, which moving its row falsifies. Corrected in this PR. When an AC says "verify rather than assume," the unit to verify is the whole sentence, not the part a prior sweep already quoted.
- The design's §5 claim (scrub is load-bearing on the untruncated `Patch` path) was worth confirming empirically before writing the doc correction, and it held: a line with a raw `0xff` inside a JSON string value decodes to U+FFFD in a `string` field but is copied verbatim into a `json.RawMessage`.
- An inherited sweep guard is not inherited as an *expression* — see Patterns above; replaced `len(routes)*2` with a literal `4` and wrote down why.
- The over-cap `patch` fixture had to be built so the cut lands *inside* a string literal, or the `json.Valid(Patch) == false` typing proof would be incidental rather than deterministic. Splitting the fixture into `{"note":"` / value / `"}` makes the byte arithmetic visible; asserting validity in both directions (intact patch valid, cut patch invalid) is what keeps the row from passing vacuously.
- `gofmt -l ./internal/streamsup` reports `helper_test.go` dirty on `main` too — pre-existing, not in this diff, left alone. Filter `gofmt -l` output to the PR's own changed files before trusting it as a finding.
