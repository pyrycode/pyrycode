# Ticket #1496 — class-aware fan-in overflow: reserve slots so a turn-closing envelope is never crowded out

`sinkFor`'s non-blocking send onto the 256-slot stream-json fan-in dropped the newest envelope of **any**
class on a full channel, `turnevent.TurnEnd` included. `pushQueue.enqueue` — the precedent `sinkFor`'s own
comment cited — is deliberately class-aware and never drops a control event, per ADR 025 § Backpressure's
*"control events (`modal_shown`, `turn_end`, `tool_*`) never drop."* The fan-in was the one place in the
stream-json path that promise didn't hold. Because `turnBusyTracker.observe` has no `TurnStart` — only
openers (`ThoughtChunk`/`TextChunk`/`ToolStart`/`ToolUpdate`) and a `TurnEnd` closer — a dropped `TurnEnd`
wasn't merely late, it was unrecoverable: the mark stayed open with nothing left to ever clear it,
`waitIdleForDelivery` parked every later `send_message` until `streamTurnHoldTimeout`, and `msgqueue`
eventually gave up with `session_error`. This also falsified the "no reachable sequence leaves a
conversation reported busy forever" claim that `turnBusyTracker`'s own doc comment, [`codebase/1210.md`](1210.md)
and [`codebase/1199.md`](1199.md) record as SATISFIED — not because #1201–#1210's clear-side feeds were
wrong, but because the fan-in could discard the `TurnEnd` before any of them ever saw it.

## Implementation

- **`cmd/pyry/stream_turn_busy.go`**: `observe`'s existing `switch ev.(type)` is extracted into a pure
  classifier, `turnMarkFor(ev turnevent.Event) turnMark` (`turnMarkNone | turnMarkOpen | turnMarkClose`),
  the sole definition of the open/close split now read by two callers — `observe` (applies the mark) and
  `sinkFor` (refuses to drop a closer). Closing class is exactly `turnevent.TurnEnd` and the fan-in's `exit`
  envelope; everything else, including a future unrecognized variant, falls to `turnMarkNone`/droppable —
  the safe default, since a variant wrongly left droppable only costs transcript fidelity while the only
  misclassification that wedges is a closer marked droppable, and closers are the enumerated arm rather than
  the fall-through. `observe` itself is behaviourally unchanged — it now switches on `turnMarkFor(ev)`
  instead of the inline type switch — and its existing test tables pass unmodified, pinning the extraction
  as a pure refactor.
- **`cmd/pyry/stream_turn_drain.go`**: new unexported const `streamTurnSinkCloseReserve = 32`.
  `streamTurnSink` gains one field, `droppableCap int`, computed once in `newStreamTurnSink` as
  `buf - min(streamTurnSinkCloseReserve, buf/2)` — the `buf/2` clamp keeps `droppableCap >= 1` for every
  `buf >= 1` and is what keeps `TestStreamTurnSink_ExitDropWhenFull`'s buffer-of-1 fixture meaningful (the
  reserve degenerates to 0 there). `newStreamTurnSink`'s signature is unchanged, so none of its ten
  production-plus-test construction sites needed an edit. `sinkFor` now branches on `turnMarkFor(ev)`
  first: a closing-class event skips the watermark and sends against the channel's **full** capacity,
  falling back to a `Warn` log (`stream_turn.close_sink_full`, fields `event`+`kind`+`session_id`) only if
  that send still loses the race; a droppable event is refused once `len(s.ch) >= s.droppableCap`, with the
  existing `Debug` log unchanged. `exitFor` needed no code change — the exit envelope is closing-class and
  already sent unwatermarked with a `Warn` drop; only its doc comment needed correcting ("same NON-BLOCKING
  send as `sinkFor`" stopped being true for the droppable class).
- **Why a reserve, not a real queue.** A channel producer can't inspect or remove a queued element without
  receiving it, so mirroring `pushQueue.enqueue`'s `[]queuedEnv`-under-mutex shape literally would break the
  fan-in's documented sole-reader invariant. A separate control lane or a producer-issued
  `clearForSession` were both rejected on ordering grounds: every one of the ~256 already-buffered events is
  an opener under `observe`'s whitelist, so a clear landing ahead of them is immediately re-opened behind it.
  Reserving tail slots on the existing channel needed neither.
- **Trilemma leg.** ADR 025's bounded ∧ never-drop-control ∧ never-block-producer is unsatisfiable here as
  it is for `pushQueue`. The two queues resolve it in opposite directions: `pushQueue` yields
  strictly-bounded (soft-overflows control past nominal cap), affordable because #911's per-conn in-flight
  gate bounds the excursion to one bundle's chunks. The fan-in yields never-drop-control instead, because its
  producer is claude's stdout — unrate-limited, no analogous gate — so a soft overflow there would be an
  unbounded-growth vector rather than a bounded one. The reserve partitions existing channel capacity; it
  adds none, so the fan-in stays strictly bounded at `cap(s.ch)`.
- **Tests** (`cmd/pyry/stream_turn_drain_test.go`, `stream_turn_busy_test.go`): AC1 pushes `buf` openers past
  the watermark then a `TurnEnd`, and asserts the conversation reaches not-busy once the drain empties —
  verified red on the unmodified tree first (today's bug drops the `TurnEnd` and `Busy` never clears). AC2
  wraps the tracker's `resolve` to record `Busy` at each call and asserts exactly one `false` reading, and it
  is the first — ordering as a deterministic sequence rather than a timing window. AC3 drives `sinkFor`/
  `exitFor` well past capacity with the drain never started, under a bounded-timeout `select`, asserting
  every call returns. AC4 pins the unchanged `Debug` droppable-drop shape. AC5 mirrors
  `TestStreamTurnSink_ExitDropWhenFull` at `buf == 1` for the new `Warn` closing-class drop, asserting
  exactly three content-free attributes. A new classifier-totality table covers every `turnevent.Event`
  variant, including `RateLimited`/`BackgroundTaskStarted` pinned to `turnMarkNone`. A reserve-arithmetic
  table pins `buf → droppableCap` at 256, 1, and one small even value.

## Patterns established

- **A channel-based fan-in can get class-aware never-drop semantics without becoming a mutex-guarded queue,
  as long as the never-drop class is provably small and the asymmetry that makes losing the *other* class
  safe is structural.** The reserve mechanism works here specifically because `turnBusyTracker`'s mark is
  idempotent-to-open — losing some or all openers is harmless, only open-without-close wedges — so reserving
  capacity for closers alone is exactly sufficient. This does not generalize to a fan-in where losing an
  arbitrary droppable-class event has an unbounded consequence.
- **The never-drop class at a given queue is defined by loss consequence at that layer, not by inheriting
  the wire-level class from a queue one layer downstream.** ADR 025 classifies `tool_*` as control on
  `pushQueue`; applying that literally at the fan-in (`turnevent.Event`, one layer upstream of the wire
  protocol) would have put `ToolStart`/`ToolUpdate` in the never-drop class and left the droppable class
  empty in exactly the filed repro — a tool-heavy burst. `tool_*` keeps its ADR 025 status downstream,
  unchanged; this reserve is additive protection at a second, narrower boundary.
- **One classifier shared by both the write-side gate and the read-side consumer is what makes a "these two
  sets must agree" invariant structural rather than a comment two files have to keep in sync.** `turnMarkFor`
  is read by both `observe` and `sinkFor`; a future `turnevent.Event` variant added to one and not the other
  is a compile-time single edit, not a silent two-file drift.

## Lessons learned (from PR review — see PR body for verdict detail)

- **A ticket's own "docs to reconcile" list is a claim inventory, not a suggestion.** The issue named six
  doc locations carrying the "no reachable sequence leaves a conversation reported busy forever" claim as
  SATISFIED. That claim was true about the *clear-side* feeds (#1201/#1202/#1210) and false about a
  precondition none of those tickets touched — whether the fan-in ever let the `TurnEnd` reach `observe` at
  all. Reconciling it required distinguishing "this ticket's clear-side work is unchanged and correct" from
  "the claim built on top of it needs a qualifier," rather than either leaving the claim unedited or
  rewriting the tickets that made it.
- **The size guard in the issue (route to `needs-rework:po` if the fix needs a queue-primitive replacement)
  was the right gate to check first**, not an afterthought: the reserve mechanism keeping
  `newStreamTurnSink`'s signature unchanged is what kept this at the filed S estimate — a mutex+slice+signal
  replacement would have cascaded into `streamTurnSink`, `sinkFor`, `exitFor`, the drain's `select`, and
  every one of their tests, which the issue explicitly called an M/L-sized different ticket.
