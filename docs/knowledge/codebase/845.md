# Ticket #845 — handle the `set_session_settings` v2 verb: validate, persist, reply

Split from #841 (itself split from #834/#826), sibling of #844 (wire vocabulary,
merged first). This is the **daemon-side handler**: it intercepts
`set_session_settings` in `dispatchAppFrame` before `dispatch.Route`, gates on
the negotiated `interactive` capability, validates the untrusted `model` /
`effort` fields at the wire boundary, persists via the injected
`SettingsUpdater` seam (`sessions.Pool.UpdateSettings`, #840), and always
replies — a deterministic `session_settings_updated` success or a fixed-string
`error` failure. `security-sensitive`: the untrusted remote write path for
per-session model/effort/YOLO that #833 explicitly deferred to this ticket.
Change takes effect on the session's *next* spawn (#833's argv path);
live-restart of a *running* session is sibling #842, out of scope here.

## Implementation

Three production files, no new production types beyond one interface, one
struct, one sentinel (~150 LOC):

- **`internal/relay/v2session.go`** — the bulk of the change:
  - `SettingsUpdate{Model, Effort *string; YOLO *bool}` + `SettingsUpdater`
    interface + `ErrSessionUnknown` sentinel, declared consumer-side beside
    `Interrupter` / `SessionStarter` / `QueueRemover` so `internal/relay`
    imports neither `internal/sessions` nor `cmd/pyry`.
  - `V2SessionConfig.SettingsUpdater` — optional, nil-safe field (nil ⇒
    deterministic "unavailable" reply, never a silent drop).
  - `case protocol.TypeSetSessionSettings` added to `dispatchAppFrame`'s
    control-envelope switch, mirroring `TypeRequestSnapshot` /
    `TypeRequestDebugBundle`.
  - `handleSetSessionSettings` — capability gate → decode → validate
    `model`/`effort` → nil-seam guard → persist → reply. Order is
    load-bearing (see spec `docs/specs/architecture/845-set-session-settings-handler.md`
    § Design for the full walk). Unlike the fire-and-forget verbs
    (`interrupt`/`new_session`/`dequeue_message`), the interactive path
    **always** replies.
  - `settingsReplyError` — a third near-identical copy of the
    `snapshotReplyError` / `debugBundleReplyError` shape (marshal
    `protocol.ErrorPayload` → seal via `forwardEnvelope`); the package's
    established per-handler-owns-its-helper posture, not extracted.
  - `validModel` / `validEffort` — defined locally (the ticket forbids
    assuming a sibling provides them). `validModel` is a **shape check, not
    an allowlist** (1–64 bytes, first byte alphanumeric, charset
    `[A-Za-z0-9._-]`, `""` accepted as "clear") — the argv-injection defense
    #833 deferred. `validEffort` is the closed enum `{"", low, medium, high,
    xhigh, max}`, mirroring `cmd/pyry/agent_run.go`'s `validEfforts` but
    defined relay-local.
- **`cmd/pyry/main.go`** — `settingsUpdaterAdapter{p *sessions.Pool}` wraps
  `*sessions.Pool.UpdateSettings`, mapping `sessions.ErrSessionNotFound` →
  `relay.ErrSessionUnknown` (the **only** place this mapping lives — the
  project convention that sentinel-to-wire mapping is the consumer's job, not
  the primitive's). Wired at the single `startRelay(...)` call site as
  `settingsUpdaterAdapter{pool}` (`pool` already in scope alongside
  `sessionMinter{pool}`).
- **`cmd/pyry/relay.go`** — threads a new `settings relay.SettingsUpdater`
  param through `startRelay` → `startRelayV2` (each has exactly one caller),
  wired into `V2SessionConfig.SettingsUpdater`.
- **`internal/relay/v2session_settings_test.go`** (new, 481 LOC) — table-driven
  over capability gate, all three success-field combinations (including the
  `model:""`/`effort:""` "clear" values), all three failure branches, the
  never-echo discipline (asserted on both the wire reply and the log buffer),
  malformed/invalid-value rejection, interception-before-`dispatch.Route`, and
  standalone `validModel`/`validEffort` unit tables.

## Design highlights (from the architecture spec)

- **Atomicity (AC #1).** Validation rejects before the seam is touched, and
  `Pool.UpdateSettings` (#840) merges all present fields under one atomic
  `saveLocked` with in-memory rollback — a rejected or failed request
  persists nothing, and no combination of fields can partially apply.
- **YOLO fail-safe (the primary asset).** Three deterministic layers, no
  stochastic component: the `*bool` presence contract (absent ⇒ `nil` ⇒
  untouched), `json.Unmarshal` strictness (a malformed `yolo` fails the
  type-decode before the seam is ever reached), and only an explicit
  `"yolo":true` sets `*true`. Belt-and-suspenders is different fabric here —
  both layers are code, not a second stochastic check.
- **Argv-injection defense.** Model/effort values reach claude as separate
  argv tokens (`claudeSettingsArgs`, #833) under `exec.CommandContext` with no
  shell, so the residual risk is a leading-dash value confusing claude's own
  flag parser (`--model --foo`). `validModel`'s first-byte-alphanumeric rule
  closes it; `validEffort`'s closed enum admits no free-form value at all.
- **Non-interactive conn is fully inert** — no decode, no seam call, **no
  reply** (AC #6). Because it never replies, an unauthorized peer cannot use
  the verb as a session-existence oracle.
- **Never-echo.** All three failure replies carry fixed message constants
  (`msgSettingsMalformed` / `msgSettingsNotFound` / `msgSettingsUnavailable`);
  no decode-error string, wrapped `err`, raw frame byte, or model/effort value
  ever reaches the wire or a log. The success reply echoes only the client's
  own confirmed-real `session_id` (safe: it matched a real session key on the
  nil-error path, carried in a typed struct field, not an error interpolation).

## Concurrency

No new goroutine, no new lock. Runs on the manager's single `Run` dispatch
goroutine like every other `dispatchAppFrame` handler — `s.interactive` reads
lock-free (single-owner invariant), and the seam call crosses into
`internal/sessions` where `Pool.UpdateSettings` takes `Pool.mu` synchronously
and returns before the handler continues. Consistent with the existing
synchronous-handler posture (`handleDebugBundleRequest` does heavier I/O the
same way); offloading would break the reply-correlation-on-`Run` pattern.

## Testing

`go test -race ./internal/relay/... ./cmd/pyry/...` and `go vet ./...` pass.

Code review: **PASS**. One NIT (non-blocking): on the success path, settings
persist before the reply marshal — if that marshal ever failed the handler
would reply `server.binary_offline`/retryable despite the change already
having committed. Unreachable in practice (`SessionSettingsUpdatedPayload` is
a one-string struct that cannot fail to marshal) and matches the package's
existing defensive-marshal-guard posture in `snapshotReplyError` /
`debugBundleReplyError` — noted, not fixed.

Code review also hit the suite-wide `TestPtyRunnerVsStreamRunner_StructuralEquivalence`
real-claude e2e red and proved it environmental (claude-CLI-version drift —
`system/thinking_tokens` events not yet in the test's drift-allowlist —
reproduces identically on `main`, disjoint from this diff's changed files, and
the failing test never routes a frame through the relay handler). Not
attributed to #845; a suite-wide test-maintenance follow-up was flagged
separately (not filed as a ticket by this pass).

## Lessons learned

- A "truncated-JSON payload" malformed case is **unreachable at the handler**:
  the payload rides `Envelope.Payload` (`json.RawMessage`), so invalid JSON
  there fails the *outer* envelope decode and the frame never routes to the
  handler — it falls through to `dispatch.Route` instead. The reachable
  handler-level decode failure is a *valid-JSON-but-wrong-shape* payload (a
  type mismatch, or a JSON array/string where an object is expected) — that's
  what `TestV2Session_SetSessionSettings_MalformedRejected` actually exercises.
