# Ticket #1028 — conversation-lifecycle real-claude liveness gate

Adds `TestInteractiveConversationLifecycle` to `internal/e2e/realclaude/` (new
file `interactive_conversation_lifecycle_test.go`, `//go:build e2e_realclaude`)
— the first real-`claude` coverage of the conversation-management verbs. Split
from #963 per the [PO split-per-family
convention](po-realclaude-liveness-capstone-splits-per-family.md); sibling of
#1029/#1030/#1031 for the other verb families.

## Implementation

Drives create → rename → archive → unarchive → delete on ONE conversation over
the same Noise v2 encrypted channel against a freshly-spawned daemon on real
`claude --model haiku`, with a `send_message` liveness turn inserted between
unarchive and delete. Each verb's effect is asserted from an
operator-observable signal, not merely that the send didn't error:

- **rename** — reply `ConversationUpdatedPayload.Name` matches the new label.
- **archive** / **unarchive** — reply `IsArchived` flips true then false.
- **delete** — reply carries the deleted id, and the new
  `readConversationIDsOnDisk` helper confirms the on-disk
  `<home>/.pyry/test/conversations.json` registry no longer holds the row.
- **liveness** — `sealSendMessage` + `drainForAssistantReply` (the exact #854
  liveness-drain shape) proves a non-empty `assistant_delta` streams for the
  conversation while it's still bound to the live session; claude's words are
  never asserted (substrate-guard safe).

Test-only — zero production files touched. Reuses the #997 per-conversation
harness (`startPerConversationHarness`, `createConversationViaPhone`,
`sealEnvelope`, `drainForReply`) and the #854 turn drive/drain
(`sealSendMessage`, `drainForAssistantReply`, `mustJSON`) verbatim. The only
new code is `readConversationIDsOnDisk` (~25 lines) and a small
`assertConversationUpdated` local helper that collapses the three metadata
verbs' identical decode+ID-correlate steps to one call site.

## Ordering rationale

The liveness `send_message` sits between unarchive and delete, not at the
start or end:

- The metadata verbs (rename/archive/unarchive) then run on a **quiescent**
  wire — after create, the per-conversation claude session is spawned but
  idle, so their drains are fast and non-flaky.
- Only the delete drain has to skip the tail of the in-flight liveness turn's
  streamed `assistant_delta` frames before reaching `conversation_deleted` —
  isolating "drain past a live stream" complexity to one step.
- Proving liveness *after* the archive round-trip is a strictly stronger
  claim: it shows the live session survived archive/unarchive, which mutate
  only the registry `is_archived` flag and never touch `CurrentSessionID`.

## Patterns established

- Handlers for `create`/`archive`/`delete_conversation` are pure registry ops
  with **no live-session guard** and an eager `Save` before the reply — safe
  to archive/delete a conversation whose claude session is alive, and the
  reply is a reliable proxy for "the registry row already reflects this".
- Metadata-verb drains (rename/archive/unarchive) get their own
  `metaVerbReplyBudget = 30s`, distinct from `perTurnReplyBudget` (120s) used
  for the liveness turn and the delete drain (which must outlast the liveness
  turn's stream tail).

## Lessons learned

(From the PR body's Lessons learned section — see PR #1032.) The ordering
choice above (liveness between unarchive and delete) was deliberate, not
incidental — worth preserving as a design note here in case a future ticket
is tempted to move the liveness step to simplify the spine, since doing so
would spread "drain past a live stream" complexity across the archive/unarchive
steps too.
