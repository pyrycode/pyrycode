# Ticket #1589 — wait for the argv record before every teardown in `TestRunner_LiveRestart`

`TestRunner_LiveRestart` (`internal/streamsup/interface_test.go`) gated both of its teardowns
solely on `onSpawn`, which fires immediately after `cmd.Start` returns — proof fork/exec
succeeded, not that the child ran a line of Go. Both teardowns (`Restart` after spawn 1,
`cancel()` after spawn 2) SIGTERM the live child via `cmd.Cancel`, and a child still in runtime
startup dies on the *default* SIGTERM disposition, before `record_block` writes its argv line.
Under full-suite `-race` contention this cost the test one or both capture lines (~10% on `main`,
confirmed pre-existing and independent of PR #1588/#1580). Test-only fix; zero production change.

## Implementation

- **`waitArgvLines(t, path, n)`** (`internal/streamsup/interface_test.go`, beside `TestRunner_LiveRestart`,
  same colocation precedent as `findEchoedLine`) — bounded poll (10ms tick, 5s deadline) on the
  argv capture file, returning once it holds `n` complete records.
  - **Complete-records rule**: splits on `"\n"` and drops the final element rather than
    `strings.TrimRight`-then-split. The dropped shape would count a torn trailing write (a `-race`
    reader catching an `O_APPEND` write mid-line) as a full record; the kept shape can't.
  - `fs.ErrNotExist` is treated as zero records (the child only creates the file on its first
    write via `O_CREATE`), but any other read error is an immediate `t.Fatalf` rather than budget
    burned on a real I/O fault.
  - The 5s deadline is documented as a FAILURE BOUND, not a calibration — same idiom as
    `launchRecorder.waitLaunch` in `runner_test.go`.
- Two call sites: `waitArgvLines(t, argvFile, 1)` ahead of `r.Restart(...)`, `waitArgvLines(t,
  argvFile, 2)` ahead of `cancel()`. The second call's return value replaces the old
  post-teardown `os.ReadFile` + manual split + length check entirely — superseded, not duplicated.
- All four existing argv/context/restart-count assertions are unchanged in meaning; only their
  input (`lines`) now binds earlier.
- Rejected direction (from the ticket): recording argv parent-side via the existing
  `launchRecorder` instead of waiting on the child-written file. Removes the race but weakens the
  test's distinctive value — the file proves argv as *delivered through exec*, not merely as the
  parent *constructed* it (`TestBuildArgs` already covers construction).

## Patterns established

- Same class as [#1118](1118.md) (`docs/lessons.md:356-359`: when a readiness signal is set by
  code that runs *before* the observable, poll the observable under a bounded deadline — don't
  treat the readiness signal as a memory barrier). The shape differs from #1118 rather than
  repeating it: #1118 had a poll that was merely too tight and needed widening; here there was no
  poll at all, and the unsynchronized teardown didn't just fail to observe the write — it could
  *kill the child before the write happened*. Confirms the underlying lesson generalizes to a
  second, more severe failure shape (missed-observation vs. actively-preempted-write).
- Deterministic red/green discriminator built by **widening the window, not reproducing the
  load**: injecting `time.Sleep(150ms)` ahead of the child's argv write via `go test -overlay`
  (scratch-copied `helper_test.go`, nothing written into the worktree) turned a ~10% flake into a
  reliable 3/3 FAIL, isolating the exact race the fix closes. A pre-fix **control** run (same
  command, no overlay) at 3/3 PASS is what makes the overlay a discriminator rather than a
  universally-red build — run both, not just the delayed one.
- A single `waitArgvLines(t, path, n)` helper serving both call sites, rather than inlining the
  poll twice, follows the existing single-caller-helper-colocated-with-its-test convention
  (`findEchoedLine`) — even though here it does have two call *sites* within the one test.

## Lessons learned

- Code review (PR #1591, PASS, no findings) re-ran the PR's own discriminator independently and
  added two mutants the ACs implied but the PR table didn't cover: deleting the first
  `waitArgvLines` call, and moving the second call to *after* `cancel()`/`join()`. Both went red
  3/3 with distinct failure signatures (`want ≥2 … have 1`), confirming each wait is the sole
  guard for its own teardown rather than one of them being decorative. Worth carrying forward:
  when an AC says "before **each** action," the PR's own discriminator table should show a mutant
  per action, not just a single before/after pair for the feature as a whole.
- Code review also surfaced a property the implementation comment undersells: the *first*
  `waitArgvLines` call doesn't just prevent argv loss — it pins the *ordering* the assertions
  depend on. Without it, spawn 1's and spawn 2's writes could in principle land out of order, and
  `lines[0]`/`lines[1]` would be silently swapped rather than merely short (which the `≥2` length
  check alone wouldn't catch). No code change resulted — flagged as a "worth knowing" property of
  an existing wait, not a defect — but it's a reminder that a synchronization fix aimed at one
  failure mode (missing records) can incidentally close a second, unstated one (misordered
  records); worth checking for on future waits of this shape.
