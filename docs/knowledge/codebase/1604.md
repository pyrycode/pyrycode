# Ticket #1604 — sessions: deliver a bypass revocation in-band; keep the enable on the restart

`Pool.UpdateSettings`' live-apply now splits on the **direction** of a bypass change rather than
its presence. A YOLO revoke (`true → false`) reaches the running child as a `set_permission_mode`
control request — the #1603 writer, measured live by #1595 — with no respawn; the same call still
installs the bypass-free next-spawn argv, so the revocation also survives a crash-relaunch, a
rotation or an eviction. A YOLO enable (`false → true`) keeps the restart, because claude gates the
escalation on the launch argv and refuses the control request in words. PR
[#1615](https://github.com/pyrycode/pyrycode/pull/1615), code review **PASS**, three NITs (all
documentation-phase pickups, folded in below). Split from #1596; unblocks #1574 (which may **not**
delete `Restart` — the enable direction is a live production caller) and #1605 (the live composed-
path proof).

## Implementation

- **`internal/sessions/runner.go`** — `Runner` gains `RevokeBypass() error`. It is **on** the
  interface, unlike `Interrupt`/`RestartFresh`/`BeginRotation`, because its consumer
  (`Pool.UpdateSettings`) is inside `internal/sessions`, with no `cmd/pyry` dispatch site to
  type-assert at. A structural assertion there would fail **open** — its unmatched arm is a silent
  no-op, leaving the posture un-revoked while the update reports success — so the interface method
  makes a runner that cannot revoke a **build** failure instead (AC1's dispatch requirement).
  `*streamsup.Runner` already had the method from #1603, so the six-site cascade is entirely
  mechanical: one adapter forward (`cmd/pyry/streamsup_runner.go`) plus five one-line test doubles
  (`baseRunner`, `stubRunner`, `fakeRunner`, `raceRunner`, and the recorder `lifecycleRunner`,
  which gains a `revokes int` **count** — not a bool — read back via `revokeCount()` under its
  existing mutex, so a test can tell "exactly one" from "two" and catch a double-send).
- **`internal/sessions/pool.go` — `inBandDeliverable`** stays a single `bool` but its arm 1 now
  reads a present `YOLO`'s *value*: `true` (enable) rejects to the restart branch, `false`
  (revoke) falls through toward in-band. The nothing-present reject arm gains a `YOLO == nil`
  conjunct — without it a bare `SettingsUpdate{YOLO: ptr(false)}` fell through to `false` and
  never reached the in-band branch. The predicate still keys on what the frame carried, not on a
  diff against stored state: a revoke equal to the stored value still goes in-band (harmless — the
  child was never in bypass, the delivery is fire-and-forget, and the installed argv carries no
  flag either way), and an empty-value `Model`/`Effort` reject still wins over a revoke in the same
  frame (harmless — the restart recomposes argv from the *merged* settings, so the respawn carries
  the revocation anyway; no frame can lose a revocation by mixing).
- **`deliverSettingsInBand`** gains a third clause after model and effort: `if update.YOLO != nil
  && !*update.YOLO { sup.RevokeBypass() }`, same fire-and-forget contract (log at `Info`, swallow)
  as the two existing sends. The `!*update.YOLO` half is unreachable under the current predicate —
  arm 1 already rejects an enable — and is kept anyway as an independent enable-direction
  fail-safe, directly asserted by `TestPool_DeliverSettingsInBand_EnableWritesNothing` rather than
  left as untested defence. Ordering is model → effort → bypass, extending the order
  `claudeSettingsArgs` already fixes. The record's `setting` field is `"bypass"` with no value
  to leak — `RevokeBypass` takes no mode parameter, so #833's keep-values-out-of-the-log rule is
  satisfied structurally.
- **`Pool.UpdateSettings`** itself is unchanged in control flow. A comment now sits directly on
  the `sup.Restart(newArgs)` call stating it is a live production caller and that #1574 may not
  delete it — deleting it would regress an enable from "applies now" to "applies at the next
  spawn". The doc above the two-branch split names the direction split and cites #1595/#1603.
- **`(*streamsup.Runner).RevokeBypass`'s doc** (`internal/streamsup/runner.go`) is corrected: it
  previously predicted `sessions.Runner` "stays un-widened" and that #1604 would reach it "via a
  type assertion". It now states what shipped, with `Interrupt` recast as the *contrast* (dispatch
  in `cmd/pyry` → assertion) rather than the parallel.
- **Tests** — `TestInBandDeliverable` gains three rows and flips two (`YOLO` revoke-only, revoke
  with effort, revoke with cleared model → restart; `{Model, YOLO: false}` and `{YOLO: true}`
  renamed to name the direction). `TestPool_UpdateSettings_YOLORevoke_DropsBypassOnRestart` is
  renamed to `_DropsBypassInBand` and retargeted off `runnerDouble`'s `revokeCount()` /
  `restartArgs()` / `spawnArgSets()` / `userTurns()` instead of `waitArgv` on a real second spawn —
  the old wait mechanism cannot work once no respawn happens, since `lifecycleRunner.Restart` is
  what feeds `recordArgv`. `TestPool_UpdateSettings_YOLOAbsent_NoBypassInBand` is **not** dragged
  back to a respawn assertion; it gains exactly one line, `revokeCount() == 0`.
  `TestPool_UpdateSettings_LiveRestart_Bootstrap` is extended (not duplicated) with
  `revokeCount() == 0` alongside its existing restart-argv assertion — the enable-direction
  regression pin. `TestPool_DeliverSettingsInBand_EnableWritesNothing` calls the unexported
  delivery directly with `SettingsUpdate{YOLO: ptr(true)}`, a shape `inBandDeliverable` never lets
  through, which is the only red available for a mutant that drops the `!*update.YOLO` conjunct.

## Patterns established

- **A structural type-assertion's failure mode is what decides interface-vs-assertion placement,
  not import-cycle avoidability.** An earlier draft of this ticket's notes ruled out the assertion
  escape on the grounds that `internal/sessions` must not import `internal/streamsup` — wrong,
  since the escape `cmd/pyry` uses for `Interrupt` is a structural assertion against a
  locally-declared anonymous interface (`interface{ Interrupt() error }`), needing no import at
  all, and there is no cycle to appeal to either direction. What actually rules it out: a
  structural assertion's unmatched arm is a silent no-op, and here that would mean a runner
  missing the method leaves a security posture un-revoked while the caller reports success. The
  correct rule is "where does the consumer sit" (`SetSpawnArgs`/`RevokeBypass` inside
  `internal/sessions` → interface; `Interrupt`/`RestartFresh`/`BeginRotation` dispatched from
  `cmd/pyry` → assertion), and the correct justification for the interface side is fail-open risk,
  not import topology.
- **A boolean partition can gain a second axis (presence → presence-and-value) without becoming a
  differ, as long as the new axis is still a property of the wire frame.** `inBandDeliverable`
  reading a present `YOLO`'s value is not the "diff against stored state" refactor its own doc
  warns against — the direction is expressed in what the client sent, not in a comparison against
  what is on disk. Keep this distinction explicit in the doc whenever a predicate like this grows
  a new conditional; it is the natural next reviewer question.
- **An unreachable-under-the-current-predicate guard still earns its own direct test**, so it is a
  proven fail-safe rather than defense that has never been exercised. Calling the unexported
  `deliverSettingsInBand` directly with a shape the public predicate never admits is the only way
  to reach that branch, and it is what turns "the compiler can't prove this is dead" into "here is
  the red it produces when someone deletes it."
