# Ticket #920 — e2e: re-key over the v2 wire harness

`security-sensitive` · wire coverage for the scheduled Noise_IK re-key (ADR 024 § "1-hour re-key cadence", the rotation canary).

Before this ticket, re-key was covered only in-process (`internal/relay/v2session_test.go`, at the `V2SessionManager` boundary). The scheduled hourly re-key is the one v2 mechanism that fires on a timer against a live session, so a rotation regression surfaced late and in the field. This ticket adds end-to-end coverage over the `fakerelay` + `fakephone` harness so the regression is caught before ship.

## Implementation

- **Test-only timing seam — three optional `V2SessionConfig` fields** (`internal/relay/v2session.go`): `RekeyInterval`, `RekeyReplyTimeout`, `RekeyRetryInterval`. Each is zero-by-default; a zero reads the existing package-var default (1h / 30s / 1m). Read at exactly one site each — `armRekeyTimer`, `armRekeyReplyTimer`, `armRekeyRetryTimer` — as `if cfg.X > 0 { use it } else { package var }`. This matches the struct's existing optional-field idiom (`Connected`, `Reconnect`: zero/nil ⇒ default). The e2e tests live in `package e2e` and cannot mutate `internal/relay`'s unexported timing vars the way the in-package tests do, so without an exported knob the timer-driven scheduled path is untriggerable from an e2e test. Production (`cmd/pyry`) sets none of the three → behaviour byte-identical to today.
- **One new test file** `internal/e2e/relay_v2_rekey_test.go` (`//go:build e2e`), `TestRelayV2_Rekey` with three subtests, structured like `TestRelayV2_Handshake`. Non-parallel (they wait on real timers and assert emit ordering).
- **Non-vacuity is pinned by a round-trip UNDER THE ROTATED KEYS** in every subtest: seal a request with the new send CipherState, decrypt the reply with the new recv CipherState. A responder that failed to swap CipherStates would reject the new-key frame at 4421, so a clean round-trip is proof the old keys were retired. This is the wire port of `v2session_test.go`'s `RoundTripUnderNewKeys`.

AC coverage:

- `scheduled_happy_path_and_rearm` — AC1 (timer emits `rekey_request{scheduled}` → phone re-handshakes reusing the same static → round-trip under new keys) + AC2 (a second `rekey_request` fires at the shrunk interval, proving `rekeyComplete` re-armed the timer rather than a one-shot fire).
- `phone_initiated_spontaneous` — AC3 (a cold `noise_init` in the open state, no preceding `rekey_request`, is accepted and rotates keys). Scheduled interval set to 30s so only the phone-initiated rotation happens.
- `transport_down_at_boundary` — AC4, post-#912 shape (see Deviations).

## Deviations from the architect spec

The spec (`docs/specs/architecture/920-e2e-v2-rekey-over-wire.md`) was written before #912 landed; three implementation-time deviations, all reviewer-relevant:

1. **Third config field.** The spec named two fields (`RekeyInterval`, `RekeyReplyTimeout`). #912 introduced `rekeyRetryInterval` (the 1m re-arm used when a scheduled emit is deferred while the leg is down). Testing the post-#912 AC4 self-heal in reasonable wall-clock needs that retry shrunk too, so a third field `RekeyRetryInterval` was added on the same idiom. Same test-only population, same net-neutral security posture.
2. **AC4 rebased to the post-#912 behaviour** (the spec's Open Question #1). #912 merged as PR #932 before this ticket landed, so AC4 no longer asserts the pre-#912 nonce-burn teardown (4426 + `noise.rekey_failed`). It now asserts the survive-and-retry path: while the leg is down the scheduled emit defers (logs `v2.rekey.emit.deferred_transport_down`, seals nothing, arms no reply window), and when the leg recovers the bounded retry emits the deferred `rekey_request`, the phone completes the rotation, and the session survives — no 4426, no `noise.rekey_failed`. The disjoint-region prediction held: #912 edits `handleWake`/`handleManualRekey`, this ticket edits the config struct + the three timer arms, no textual conflict on the main merge.
3. **AC4 deferral evidenced via the capturing log, not a wire "no frame" receive.** `coder/websocket` closes the phone conn on a read-deadline timeout (`fakephone.go` doc comment: "a timed-out Client cannot be reused"), so the spec's "phone receives no `rekey_request` while down" wire-timeout would have killed the conn needed for the recovery half. Instead the down-window deferral is observed by polling the manager's captured log for `v2.rekey.emit.deferred_transport_down` (`waitForLog`), and the strong positive is the wire recovery: the phone receives the self-healed emit and completes the rotation.

## Down primitive

The `transport_down_at_boundary` case flips a test-owned `atomic.Bool` behind `cfg.Connected` (`downShim`): `transportDown()` is `Connected != nil && !Connected()`, so this reproduces "leg down" at exactly the boundary the #912 gate consults — deterministic, no transport reconnect-backoff race. `Outbound` is left as the real `conn.Send`; post-#912 nothing is sent during the down window (the emit defers before any send), so no `Outbound` wrapping is needed.

Files touched: `internal/relay/v2session.go` (+3 struct fields, +3 one-line reads in the timer arms), `internal/e2e/relay_v2_rekey_test.go` (new). No `cmd/pyry`, `fakerelay`, or `fakephone` change.

## Security review

Architect self-review (full text in the spec § Security review) verdict: **PASS**. The one production change is an additive, test-only-populated timing seam with no wire exposure and no effect on the default security posture: the three fields are set only by in-process Go call sites, never from the wire, a file, or operator input, and production leaves them zero. A shrunk interval only raises rotation frequency (strictly more forward secrecy); no value weakens the shipped 1h posture, disables rotation, or touches key material, the peer-static pin, or the AEAD. The third field (`RekeyRetryInterval`) added at implementation time carries the same posture. The test design is non-vacuous on the rotation property it certifies (round-trip under the rotated keys).
