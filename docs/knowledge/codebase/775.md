# Ticket #775 — exit a removed session's lifecycle goroutine on `Pool.Remove`

`Pool.Remove` deleted the session's registry entry and evicted its child, but the
session's lifecycle goroutine — the body of `Session.Run` — then looped into `runEvicted`
and parked on `activateCh` / `ctx.Done()`. The session was no longer reachable via
`Pool.sessions`, so nothing could ever signal `activateCh`, and the `ctx` there is the
pool's **shared** errgroup context (`gctx`), which cancels only at full pool shutdown. The
goroutine and everything it captured (`*Session`, `*supervisor.Supervisor`,
`*supervisor.Bridge`, logger) therefore leaked for the daemon's lifetime — one orphan per
create+remove cycle. `#94` documented this as a bounded cost (fine for a handful of
operator-driven removes); on a long-lived daemon that churns many create+remove cycles it
is an unbounded leak. This ticket makes the removed goroutine exit **promptly**.

## Implementation

Two production files, purely additive — one new per-session channel field, one new
`runEvicted` select case, one `isRemoved()` guard in `Run`, one `close()` in `Remove`, and
the two construction sites initialising the field. No new package, no exported type, no
signature change, no new goroutine topology.

| File | Change |
|---|---|
| `internal/sessions/session.go` | New write-once field `removedCh chan struct{}` on `Session`, deliberately **outside** the `lcMu`-guarded block (it is read without `lcMu`). New `case <-s.removedCh: return nil` arm in `runEvicted`. New `isRemoved()` non-blocking helper. New guard in `Run`'s `stateEvicted` branch: after `runEvicted` returns nil, `if s.isRemoved() { return nil }` **before** re-transitioning to active. |
| `internal/sessions/pool.go` | `close(sess.removedCh)` in `Pool.Remove`, placed past the `saveLocked` rollback branch and off `p.mu`, immediately before the existing `sess.Evict(ctx)`. `removedCh: make(chan struct{})` added to both `Session` literals — bootstrap (`New`) and `buildSession`. The stale lifecycle-after-Remove doc-comment (`pool.go:611-618`) rewritten to describe the prompt exit. |

### Data flow

```
Pool.Remove(id):
  p.mu.Lock() → delete p.sessions[id] → saveLocked (rollback+return on failure)
              → disposeJSONLLocked → p.mu.Unlock()
  close(sess.removedCh)          ← level-triggered broadcast; needs no lock
  sess.Evict(ctx)                ← drives active→evicted (SIGKILL child, join supervisor)

Session.Run loop (the lifecycle goroutine):
  stateActive  → runActive: Evict's evictCh fires → cancel+drain supervisor
               → transitionTo(stateEvicted) closes evictedCh (unblocks Remove's Evict)
  stateEvicted → runEvicted parks on { ctx.Done | removedCh | activateCh }
               → removedCh closed  → return nil
               → Run: isRemoved() == true → return nil   (goroutine exits; captured objects → GC)
```

## Patterns established

- **Close-on-remove channel chosen over a per-session `context.WithCancel(gctx)`.** The
  ticket floated both seams. The channel wins on two counts. (1) **No construction-ordering
  race:** a per-session cancel must be derived from `gctx`, which is only known when
  `Run(gctx)` is called — so the `CancelFunc` can't be stored at construction, and a `Remove`
  landing before `Run`'s first line would read a nil cancel. `removedCh` is allocated at
  construction (always non-nil before `Run` is scheduled); an early `Remove` still works
  because the closed channel is observed the instant `Run` reaches `runEvicted`. (2)
  **Deterministic shutdown-vs-removal discrimination:** `ctx.Done()` → `ctx.Err()` (propagate,
  pool shutdown); `removedCh` → `nil` (removal). No "which context fired?" ambiguity a
  shared-parent cancel would introduce.
- **`nil` != removed — a nil `removedCh` is a valid "never removed" state.** A nil channel is
  a never-ready select case, and `isRemoved()`'s non-blocking read defaults to `false`. So
  bare `Session` literals in tests (and any future non-pool construction) need no change; the
  field is only meaningful when the owning `Pool` closes it. The bootstrap allocates one it
  never closes (`ErrCannotRemoveBootstrap`) — a harmless always-open channel, allocated for
  uniformity.
- **`removedCh` is watched only in `runEvicted`, never `runActive` — the load-bearing
  invariant.** `Remove` always calls `Evict`, which deterministically drives active→evicted:
  `evictCh` → `runActive` returns `(ReasonEviction, nil)` → `Run` runs
  `transitionTo(stateEvicted)`, which **closes `evictedCh`** and thereby unblocks the `Evict`
  call inside `Remove`. Only *then* does `Run` loop into `runEvicted` and observe the
  already-closed `removedCh`. If `runActive` also selected on `removedCh`, a select race could
  return **before** `transitionTo` closed `evictedCh`, leaving `Remove`'s `Evict` blocked
  until the caller's ctx expires — a hang. Catching removal one step later (in the park state)
  keeps the child-termination path untouched.
- **The `isRemoved()` re-check makes removal win over a racing `Activate` — a latent-bug
  improvement.** In `runEvicted`, `removedCh` closed and `activateCh` firing concurrently →
  Go picks one arm. Either way, `Run` re-checks `isRemoved()` before re-transitioning to
  active, so a removed session can **never** resurrect — closing a race that previously could
  re-park→re-activate a removed session.
- **Removal returns `nil`, never `context.Canceled` — the errgroup blast-radius rule.** Every
  `Run` executes as `g.Go(func() error { return sess.Run(gctx) })` on the pool's shared
  errgroup. A `context.Canceled` return would make the errgroup cancel `gctx` and tear down
  **every** sibling session plus the relay leg — the exact blast radius the non-fatal
  persist-failure handling (`session.go:281-295`) exists to avoid. Removal is a clean exit;
  `ctx.Err()` is reserved for the genuine `case <-ctx.Done()` (pool shutdown) paths.
- **Single-close is structural — no `sync.Once`.** `Remove` is single-shot per id: a second
  `Remove` for the same id finds no `p.sessions[id]` under `p.mu` and returns
  `ErrSessionNotFound` before reaching the close. The map-delete-under-`p.mu` guard already
  enforces single-close; adding a guard would be a defence for an unobserved failure mode.

## Lessons learned

- **`removedCh` is watched only in `runEvicted`, never `runActive`:** adding it to `runActive`
  could let a select race return before `transitionTo(stateEvicted)` closes `evictedCh`,
  hanging `Remove`'s `Evict` call. The `isRemoved()` re-check after `runEvicted` is what makes
  removal win even when a racing `Activate` fires — so a removed session can never resurrect (a
  latent-bug improvement). (Lifted from the PR's Lessons-learned section.)

## Out of scope (deferred)

- **Eviction notification on Remove (pre-existing).** Removing an *active* session still drives
  `runActive → ReasonEviction → transitionTo(stateEvicted) → notifyTransition(ReasonEviction)`
  — a `session.evicted` transition fires for a session that is being *deleted*, not idle-evicted.
  This is existing behaviour (Remove always called Evict); the fix preserves it deliberately
  (suppressing it race-free would require `runActive` to learn about `removedCh`, reintroducing
  the `Evict`-hang hazard and mutating the outbound event stream as a side effect of a leak fix).
  Whether a removed session should emit an id-stable eviction event is a separate question — file
  a follow-up if it proves wrong.
- **Redundant post-remove registry write (pre-existing).** The active→evicted `transitionTo` on
  the remove path calls `pool.persist()`, writing the registry once more (already without the
  removed session). Harmless and pre-existing; not addressed here.

## Testing

Three new same-package tests (stdlib only, `-race`-clean), one per AC.

- `TestSession_Run_RemovedCh_ExitsClean` (**AC-1**, `session_test.go`) — bare evicted `Session`
  literals (the evicted→removed path touches neither `sup` nor `pool`). Sub-test `parked_then_removed`:
  close `removedCh` while `Run` is parked in `runEvicted`; assert `Run` returns `nil`. Sub-test
  `removal_wins_over_activate`: pre-load a pending `activateCh` **and** close `removedCh` before
  `Run` is scheduled; assert `Run` still exits `nil` (the `isRemoved()` re-check wins) rather than
  re-activating into a nil-supervisor deref.
- `TestPool_Remove_NoCollateralTeardown` (**AC-2**, `pool_remove_test.go`) — drives `pool.Run`
  manually (`activeCap 0`, two non-bootstrap sessions + bootstrap). `Remove` one; assert (a) the
  survivor's `ChildPID` is unchanged and still `stateActive` and its process is alive, (b) the
  bootstrap is untouched, and (c) `pool.Run` has **not** returned (the background goroutine is
  still blocked — the direct proof the removed `Run` returned `nil`, not an error, so the shared
  errgroup never propagated a teardown).
- `TestPool_Remove_NoGoroutineLeak` (**AC-3**, `pool_remove_test.go`) — **not** `t.Parallel`
  (`runtime.NumGoroutine` is process-global). One warm-up create+remove cycle brings the pool to
  steady state, then `runtime.GC` + `Gosched` settle → record `baseline`. Loop 20 create+remove
  cycles; poll-until-settle (`pollUntil`, 10s) for `NumGoroutine() <= baseline + jitter` (jitter 3
  — child SIGKILL + `Wait` + goroutine teardown is async, so a fixed sleep would flake). If the
  lifecycle goroutines were leaking the count would climb toward `baseline + 20` and never settle.

`go test -race ./...` and `go vet ./...` pass.
