# Ticket #917 — collapse `startRelay`/`startRelayV2` wiring into a `relayWiring` struct

Reliability-review finding (2026-07-10): `startRelay` (`cmd/pyry/relay.go`) and `startRelayV2` had each grown to ~20 positional parameters as every daemon seam (settings, snapshot usage, debug bundler, queue emitter, …) appended one more positional arg. Two adjacent directory-path strings (`claudeSessionsDir`, `defaultCwd`) — plus two adjacent bools and three bare-string identifiers — were a silent transposition hazard: swapping them compiles clean and misbehaves at runtime (e.g. the JSONL resolver scanning the wrong dir). Pure behaviour-preserving refactor, no design surface change.

## Implementation

- New unexported, `cmd/pyry`-local struct `relayWiring` (`cmd/pyry/relay.go`) carries **all 21** call-site-supplied wiring values — not just the fields shared between the two functions. `startRelayV2`-only config values (`relayURL`, `version`, `allowInsecure`, `v2Enabled`, `shutdown`) still travel in the struct even though `startRelayV2` never reads them, because they're still call-site transposition hazards and AC2 requires *every* wiring argument bound by name.
- `startRelay` reads `w.<field>` and forwards the **same struct value unchanged** to `startRelayV2` — one struct threaded whole, not a shared-subset-plus-positional-tail split.
- `ctx`/`logger` stay leading positional args on both functions (idiomatic Go). The three values `startRelay` produces internally and hands to `startRelayV2` — `conn` (`relay.Connect`), `registry` (`devices.Load`), `serverID` (`identity.LoadOrCreate`) — stay trailing positional args; they are locals, not call-site wiring, so they don't belong in the struct.
- `staticKey`/`StaticPriv` stays a local loaded inside `startRelayV2` (`keys.LoadOrCreate`) — explicitly out of scope; its no-log/no-wire contract is untouched.
- Every field carries a doc comment restating the semantics previously implicit in the parameter name / function doc — in particular `claudeSessionsDir` (own-claude-child transcript tail dir; empty disables reconcile/rotation-watch/turn-modal streams) vs. `defaultCwd` (default workspace stamped on cwd-less new conversations) are now textually distinguished at the field, not just positionally adjacent.
- Call site: `cmd/pyry/main.go:872` (`runSupervisor`) changed from one 21-arg positional call to a `relayWiring{...}` named-field literal — one field per line, so a same-typed swap is now a one-line diff instead of a silent reorder.
- ~35 mechanical `w.<field>` renames across `startRelay`/`startRelayV2`; no control-flow, branch, or handler-wiring changes. `go build`, `go vet`, `go test -race` pass unchanged — no test references either function directly (confirmed by grep before the change).

## Patterns established

- **Wiring-struct-for-positional-sprawl**: when a `cmd/pyry`-local function's positional parameter list grows past the point where same-typed adjacent params become a silent-swap hazard, collapse to one unexported, whole-struct-threaded, named-field struct at the single call site — not a partial "shared fields only" struct with a positional remainder. Threading the whole struct (including fields the callee doesn't read) is preferred over splitting, since AC-level "every argument bound by name" can't be satisfied by a partial extraction. Locals a function produces internally for a downstream callee (not supplied by the call site) stay positional — they aren't wiring.
- This mirrors the existing `Config`-struct-as-named-fields idiom already used by `internal/relay.Config`, `internal/dispatch.Config`, `internal/msgqueue.Config` — same shape, applied at the `cmd/pyry` orchestration layer rather than a package boundary.
- Confirmed (again) that positional→named-field struct refactors are **not** security-sensitive by themselves, even when the args being repackaged include crypto-adjacent seams (`StaticPriv`/`settings`) — no new input acceptance, validation, or routing change. Security-sensitivity tracks new design surface, not the presence of security-flavored fields being moved.
