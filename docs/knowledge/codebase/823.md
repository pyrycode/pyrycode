# Ticket #823 — `change_workspace` v2 wire verb

Adds the fourth conversation write-verb: `change_workspace` moves an existing
conversation to a client-chosen workspace folder (desktop's Workspace Picker
sheet; mobile stubs the action today). "Workspace" **is** the conversation's
`Cwd` field — this codebase has no separate workspace-id concept — so the
target is a filesystem path (mirroring `create`/`promote` `cwd`), not an id.
This is the first verb in the `rename_conversation` (#820) / `delete_conversation`
(#822) / `archive`+`unarchive` (#880/#881) family where untrusted client input
reaches a filesystem path — the material difference that earns it
`security-sensitive` where its siblings (a display string, and nothing,
respectively) were not.

## Implementation

Six production files touched, one new (`change_workspace.go`), ~300 total LOC
— same vocab-spread shape as the family's documented false-positive
(`docs/specs/architecture/823-change-workspace-wire-verb.md` § "Scope / size
note"):

- `internal/protocol/codes.go` — `TypeChangeWorkspace = "change_workspace"`
  (phone → binary request), in the Conversations block after
  `TypeUnarchiveConversation`. **No new reply type** — the reply reuses
  `conversation_updated` / `ConversationUpdatedPayload` (the record still
  exists; only `cwd` changed).
- `internal/protocol/conversations_write.go` —
  `ChangeWorkspacePayload{ConversationID, Cwd string}`, both required, no
  pointers (mirrors `PromoteConversationPayload`'s value-typed fields).
  Deliberately not a `PromoteConversationPayload` reuse (that also carries a
  required `Name` — false dependency, same rationale the sibling payloads
  document).
- `internal/protocol/envelope.go` — `TypeChangeWorkspace` added to
  `v1TypeSet`. A v1 `dispatch.Route` write verb, not a v2-control frame — "v2
  wire message" in the title names the encrypted v2 *transport*, not the v1/v2
  *type partition*, same classification as #820/#822/#881.
- `internal/protocol/compat_test.go` — the type added to all three v1
  enumerations; hardcoded count bumped 21 → 22.
- `internal/conversations/conversation.go` — `Cwd`'s doc comment corrected: it
  previously claimed "never updated after creation," which this verb makes
  false. Comment-only change, no field/tag change.
- `internal/relay/handlers/change_workspace.go` (new, ~215 LOC) —
  `ChangeWorkspace(reg ConversationWorkspaceUpdater, resolve WorkspaceResolver, registryPath string, logger *slog.Logger) dispatch.Handler`.
  Flow: decode → empty/whitespace-`cwd` guard (**must precede** confine — an
  empty target resolves to the daemon's process cwd, which may sit inside
  `$HOME` and silently pass) → `resolve(p.Cwd)` (confine to `$HOME`, any
  non-nil error is the rejected branch — the handler does not discriminate on
  `errors.Is(err, ErrWorkspaceRejected)`, since the resolver's contract wraps
  every failure and every failure is deterministic) → `reg.Update(id, fn)`
  sets `cv.Cwd = resolved` and snapshots the `ConversationUpdatedPayload`
  inside the locked closure (mirrors rename's TOCTOU-free pattern;
  `LastUsedAt` **not** bumped — a metadata edit is not a "use") → eager
  best-effort `reg.Save` → reply `conversation_updated`.
- `cmd/pyry/relay.go` — the new `resolveWorkspaceDir` adapter (`expandTilde`
  → strict, non-creating `confineWorkdirToHome`, wrapping every failure with
  `handlers.ErrWorkspaceRejected`) plus two wiring lines (v1 `d.Register`
  block and the v2 `Handlers` map), reusing `convReg` and
  `resolveConversationsRegistryPath(instanceName)`.

`ConversationWorkspaceUpdater` is the consumer-declared minimal interface
(`Update` + `Save`) `*conversations.Registry` satisfies structurally — same
pattern as `ConversationRenamer` (#820) / `ConversationDeleter` (#822) /
`ConversationArchiver` (#881).

`list_conversations` reads the live registry, so it reflects the new
workspace for free (AC #2) — no list-handler change.

### Stores the resolved realpath, not the raw path

Unlike `create_conversation` (which stores the raw `p.Cwd`), this handler
persists `resolve`'s returned realpath. Three reasons, all in the handler's
doc comment: (1) validate == store — the persisted value is the one that was
security-confined; (2) idempotent for every downstream consumer — the next
fresh spawn's `resolveSpawnDir` and #686's transcript resolver both
re-canonicalise `conv.Cwd`, and `EvalSymlinks(realpath) == realpath`, whereas
a raw `~/…` would mis-resolve through the tilde-unaware `confineWorkdirToHome`
those consumers call; (3) the desktop workspace chip shows the real location.

### The confine adapter: strict, non-creating, no trust-mark

`resolveWorkspaceDir` (`cmd/pyry/relay.go`) diverges from the create-path
`resolveSpawnDir` in two deliberate ways:

- Uses the **strict** `confineWorkdirToHome`, not `…Creating`. This verb is a
  metadata edit, not a spawn — it must not create a directory as a side
  effect. A non-existent target fails `EvalSymlinks` and is rejected,
  satisfying AC #3's "or is unresolvable" branch for free.
- Does **not** call `trustMark`. Trust-marking auto-accepts claude's
  workspace-trust modal and is a spawn concern; marking here would
  prematurely auto-trust a directory that may never be spawned into. The next
  fresh spawn's `resolveSpawnDir` trust-marks then.

No new parameter is threaded through `startRelay`/`startRelayV2` — unlike
create's `SessionCreator` (which needs `*sessions.Pool` from `main.go`'s
scope), `resolveWorkspaceDir` is a free function co-located with its two call
sites directly in `relay.go` (package `main`), closing over nothing.

### Security-sensitive: two logging divergences from create/rename

Carries `security-sensitive`. Divergence 1 (inherited from delete #822): the
malformed branch logs `conn_id` only — never the decode `err` (can embed
offending input bytes) and never `conversation_id` (may hold raw attacker
bytes from a partial decode). Divergence 2 (**new to this verb, the
load-bearing one**): `create_conversation.go` logs the wrapped confine `err`
on spawn-dir rejection, and that `err` names the offending path.
`change_workspace`'s confine-rejected branch must NOT — it logs `conn_id` +
`conversation_id` only, never the confine `err`, never the path (AC #5). Both
divergences are called out in the handler's doc comment so a future editor
does not "fix" them back by pattern-matching create.

All four reject branches (`malformed`, `empty`, `rejected`, `not_found`)
reply a fixed static string; none echoes the supplied path, id, or a
decode-error fragment.

## Testing

- `internal/relay/handlers/change_workspace_test.go` (new, ~470 LOC) — clones
  `delete_conversation_test.go`'s harness with a hermetic fake
  `WorkspaceResolver` (`acceptResolver` / `rejectResolver` closures — no real
  filesystem touched by the handler test). Covers: success updates + replies +
  persists across a fresh `Load` (AC #1 restart-survival), `list_conversations`
  reflects the new workspace with no list-handler change (AC #2), confine
  rejection leaves `conv.Cwd` unchanged and the `change_workspace.rejected`
  log record carries no `err`/path (AC #3, AC #5 — the security-critical
  test), not-found leaves the registry unmodified (AC #4), malformed payload
  no-leak (`conn_id` only in the log record), empty/whitespace `cwd` rejected
  before confine is ever invoked, and a no-echo assertion that an
  injected-looking id/path never appears in any reject reply message.
- `cmd/pyry/change_workspace_dir_test.go` (new, ~120 LOC) — pins
  `resolveWorkspaceDir` directly: within-`$HOME` existing dir → its realpath;
  bare `~` → `EvalSymlinks($HOME)`; outside-`$HOME` dir → rejected wrapping
  `handlers.ErrWorkspaceRejected`; non-existent within-`$HOME` target →
  rejected *and* not created (proves the strict confiner's non-creating
  contract); a `$HOME`-rooted symlink pointing outside → rejected (the
  realpath-before-containment-test proof). The strict confiner's own
  escape/symlink logic is otherwise covered by `confineWorkdirToHome`'s
  existing tests — this file only pins the tilde-expand + sentinel-wrap
  wrapper.

`go test -race ./...`, `go vet ./...` pass per the architecture spec's
testing strategy.

## Lessons learned

- **This ticket does not add an `internal/protocol` round-trip test or
  `testdata` fixture for `ChangeWorkspacePayload`** — a divergence from every
  direct sibling. #820 (`RenameConversationPayload`), #822
  (`DeleteConversationPayload`/`ConversationDeletedPayload`), and #881
  (`ArchiveConversationPayload`) each added a `TestXPayload_RoundTrip` in
  `conversations_write_test.go` plus a matching `testdata/*.json` fixture.
  `ChangeWorkspacePayload` has neither; its only exercise is indirect, via
  `json.Unmarshal` inside the handler tests. Worth a follow-up if a future
  ticket touches this payload's wire shape — there's no golden fixture
  pinning its exact JSON field order/tags the way the rest of the
  conversations-write slice has.

## Out of scope

- **Re-spawning the conversation's *live* session in the new workspace.**
  `conv.Cwd` is deliberately decoupled from a running session's captured
  spawn `WorkDir` (#685/#686); this verb changes the *recorded* workspace
  only. The new folder takes effect on the conversation's next fresh session
  spawn, which re-runs the full `resolveSpawnDir` confinement + trust-mark.
  Moving a live session (teardown + re-mint + trust-mark the new dir) is a
  separate, larger concern.
- **Live fan-out to other connected clients.** Same posture as the rest of
  the family: the reply goes only to the requester; other clients pick up
  the new workspace on their next `list_conversations`.
- **`cwd` vs `workspace` wire field name.** The spec ships `cwd` (family
  convention). If desktop settled on a different tag at integration, it's a
  one-line change to `ChangeWorkspacePayload`, not a design blocker.
