# Ticket #949 — wire `promote_conversation` handler (save-as-channel)

`promote_conversation` was a fully-defined wire verb — message type, payload,
reused reply, and the `Registry.Promote` primitive all pre-existed — but no
`V2SessionConfig.Handlers` entry ever called it. Since #913 removed the legacy
v1 `d.Register` block and the `PYRY_MOBILE_V2` switch, that map is the **sole**
dispatch table, so the missing entry meant every `promote_conversation` frame
fell through to `protocol.unsupported` and "Save as channel" silently failed
on both remote clients. Pure wiring plus a test — the only design fork was
what to do with the payload's required `Cwd`, which `Registry.Promote` does
not consume.

## Implementation

One new handler file, one wiring line, two new test files:

- `cmd/pyry/relay.go` — one line added to the `Handlers` map literal in
  `startRelayV2`, alongside `TypeRenameConversation`:
  `protocol.TypePromoteConversation: handlers.PromoteConversation(w.convReg, resolveConversationsRegistryPath(w.instanceName), logger)`.
- `internal/relay/handlers/promote_conversation.go` (new, ~194 LOC) —
  `PromoteConversation(reg ConversationPromoter, registryPath string, logger *slog.Logger) dispatch.Handler`.
  Clones `RenameConversation`'s shape (decode → registry op → eager `Save` →
  reply), with one extra step: `Registry.Promote` returns only an `error`, not
  the updated row, so the handler reads it back via `Get` before building the
  `conversation_updated` reply. `ConversationPromoter` is the consumer-declared
  minimal interface (`Promote` + `Get` + `Save`) `*conversations.Registry`
  satisfies structurally — same pattern as `ConversationRenamer` (#820) /
  `ConversationDeleter` (#822) / `ConversationArchiver` (#881) /
  `ConversationWorkspaceUpdater` (#823).
- `internal/relay/handlers/promote_conversation_test.go` (new, ~477 LOC,
  table-driven, ten scenarios) — happy path (inherits seeded `Cwd`), payload
  `Cwd` deliberately ignored, eager-persist survives reload, not-found,
  already-promoted, empty/whitespace name, name-in-use, malformed payload,
  no-leak logging, static reject messages.
- `internal/e2e/relay_v2_promote_test.go` (new, ~168 LOC, build tag `e2e`) —
  `TestRelayV2_Promote` pairs a device, seeds a scratch conversation, drives
  the real Noise_IK handshake against a spawned daemon, sends
  `promote_conversation` over the encrypted channel, asserts
  `conversation_updated` with `IsPromoted:true`, and re-reads
  `conversations.json` off disk to confirm the promotion persisted (AC #4).
  RED on main (no handler → `protocol.unsupported`), GREEN after.

Error-sentinel mapping (`errors.Is` on `Registry.Promote`'s four sentinels —
no error falls through to `unsupported`):

| Sentinel | Wire code |
|---|---|
| `ErrPromotionNameEmpty` | `protocol.malformed` |
| `ErrConversationNotFound` | `conversation.not_found` |
| `ErrConversationAlreadyPromoted` | `conversation.already_promoted` |
| `ErrPromotionNameInUse` | `protocol.malformed` (folds in — no new wire code) |
| `Get` miss after successful `Promote` (racy concurrent delete) | `conversation.not_found` |

Logging discipline adopts `change_workspace`'s malformed-branch divergence,
not `rename`'s: the malformed branch logs `conn_id` only — never the decode
`err` or `conversation_id` (a decode failure may leave the id holding raw
attacker bytes). Every other branch runs post-decode and logs
`conversation_id` as a proven-decoded field. The channel `name` is user
content and is never logged on any branch (rename precedent).

## The Cwd decision (Option B — inherit, don't consume)

`PromoteConversationPayload` carries a required `Cwd` that `Registry.Promote`
does not consume — the reason this ticket carries `security-sensitive`. Two
options existed: (A) promotion also sets the workspace, requiring the
untrusted path be `$HOME`-confined per `change_workspace` precedent (#823);
(B) the channel inherits the scratch conversation's existing `Cwd`, and the
payload `Cwd` is read off the wire and discarded.

**Chose (B).** Promotion is a naming/persistence operation, not a relocation;
every conversation already carries a valid `Cwd` set at `create_conversation`
time, so inheritance is always well-defined; and it avoids introducing a new
untrusted-path-as-workdir surface (no `WorkspaceResolver`, no registry API
change, no two-step promote-then-update-cwd TOCTOU window). The reply's `Cwd`
is the row's pre-existing (already-confined) value, read back via `Get` — so
it's still truthful.

**Consequence:** this verb opens **no new untrusted-path surface** — it's in
the same trust class as `rename` (stores a display string), not
`change_workspace` (stores a path). The payload `Cwd` field stays on the wire
for client symmetry but is neither validated nor stored. A future editor MUST
NOT wire it up without re-opening this decision and the security review — the
`TestPromoteConversation_PayloadCwd_IsIgnored` test is the regression guard
(assert reply/stored `Cwd` is the seeded value, not the payload's differing
one).

If a future ticket wants "Save as channel *into a different folder*", that's
Option A — a separate, larger security-sensitive ticket combining promote
with a `change_workspace`-style confined path set, not a silent extension of
this handler.

## Security review

**Verdict: PASS.** Full self-review in
[`specs/architecture/949-promote-conversation-wire-verb.md`](../../specs/architecture/949-promote-conversation-wire-verb.md)
§ Security review. The central finding: the label anticipated Option A (an
untrusted-path-as-workdir surface); the design chose Option B and so never
builds that surface. `[File operations]` is N/A — no `filepath.Abs`, no
confine, no `MkdirAll` — because the untrusted `cwd` is never consumed. All
three untrusted payload fields are contained: `conversation_id` is an
exact-match registry key only; `name` is an opaque display string
(`Registry.Promote` enforces non-empty + cross-row uniqueness); `cwd` is
discarded. No new goroutines, no crypto, no subprocess surface, all reject
replies are fixed static strings.

## Concurrency

`Promote`→`Get` is two lock acquisitions, not atomic. A concurrent delete of
the same row between them surfaces as a `Get` miss → `conversation.not_found`
(truthful current state); any other concurrent write is reflected verbatim in
the read-back (also truthful). Replay is idempotent-safe — a re-promote of an
already-promoted row is refused `already_promoted`, no nonce needed.

## Out of scope

- **Promoting into a client-chosen new folder** — Option A, deferred per
  § The Cwd decision.
- **Live fan-out to other connected clients** — reply goes only to the
  requester, matching the rest of the conversation-write family; other
  clients pick up the promotion on their next `list_conversations`.
- **Desktop real-daemon actions e2e** (pyrycode-desktop, filed alongside this
  ticket) — was natively blocked-by this issue; now unblocked.
