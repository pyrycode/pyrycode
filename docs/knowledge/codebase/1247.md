# Ticket #1247 — Suppress claude's no-visible-output self-nudge at the user-block drop site

Backgrounding a command produces a turn with no visible model output, and
claude's harness then injects a `user` message holding a `text` block prodding
the model to speak (reproduced 3 of 3 on the #1240 probe, claude 2.1.220).
`emitUser` (`internal/streamsup/parser.go`) previously surfaced every non-
`tool_result` user block as `Unrecognized{Site: user_block}` — correct per the
2026-07-27 measurement, which never drove a backgrounded command — so this one
benign, per-occurrence-of-a-common-action payload reached clients as an
`unrecognized_message` frame carrying nothing actionable, and armed the shared
real-claude drain's zero-unrecognized assertion (`interactive_stream_liveness_test.go:229`)
against a known-benign payload the first time any live spec backgrounds a
command. Spec: `docs/specs/architecture/1247-harness-nudge-suppression.md`.
PR: [#1249](https://github.com/pyrycode/pyrycode/pull/1249). Size S — one
production file (`internal/streamsup/parser.go`, one constant + a 6-line guard
+ a corrected comment) and its test file (5 table rows + 1 log-assertion test),
well under 30 lines of production code.

See [features/streamsup-package.md](../features/streamsup-package.md) for the
parser's full drop-site table (updated by this ticket) and
`docs/specs/architecture/unrecognized-claude-messages.md` for the two-tier
design this amends.

## Implementation

- **One documented 100-byte constant, `harnessNoOutputNudge`**, matched by
  byte-exact `==` — no trim, no fold, no prefix, no substring. Provenance is
  thin and the doc comment says so: transcribed byte-exact from the #1247
  capture (the ticket body), claude 2.1.220, one probe session (#1240), 3
  occurrences; the string exists in no tracked file, and a widened
  `~/.claude/projects` census corroborated nothing. Exact equality is the
  tolerance that provenance earns — a prefix or substring match would swallow
  the next harness payload, or a future prompt echo on this surface, in
  silence; exact match instead fails safe: wording drift brings the
  `Unrecognized` row back and a human looks.
- **The guard sits in `emitUser`, before the `block.Type != "tool_result"`
  arm**, and uses `continue`, not `return` — the suppression is scoped to the
  matching *block*, so a `tool_result` sharing the message still maps to
  `ToolUpdate`. Pinned by a table row with the nudge block first and a
  `tool_result` second, expecting exactly one `ToolUpdate`.
- **`block.Type == "text"` is a required conjunct, not implied by the string
  match**, and it is what keeps the guard structurally unreachable from tool
  output: a `tool_result`'s payload decodes into `streamBlock.Content`, never
  into `Text` (`parser.go:178-194`), so a tool result whose content *is* the
  nudge still maps normally. Pinned by its own table row.
- **This is the parser's first block-level suppression.** `ignoredLineTypes`
  is top-level types only and stays a `map[string]bool` with a pin test
  (`TestParser_IgnoredLineTypesIsTheMeasuredSet`, unchanged); the new tier is a
  single `const`, not an entry on that map or a new one-element set. A
  **second** confirmed harness payload, with a measurement behind it, is what
  earns the promotion to a set — not before. `emitAssistant`'s comment already
  stated the block-level position ("No known-ignored list at block level …
  Any fourth is news"); this is that fourth, and it says so.
- **`ignoredLineTypes`' comment is corrected in place**, not appended to
  elsewhere: the 2026-07-27 measurement's conclusion ("user/text needs no
  ignore entry … a real change worth surfacing") is now wrong for exactly one
  string, and the correction sits right beside it.
- **The drop is Debug-logged with `site` and `type` only**, mirroring the
  existing known-ignored line drop — never the text. Asserted by a capturing
  `slog.Handler` (`logRecorder`, mirroring `spawnArgsRecorder`'s four-method
  shape) whose *third* assertion is the load-bearing one: no captured attr
  value, across every record on the path, contains the nudge text. The first
  two assertions only describe what is present; this is what would catch a
  later edit appending `"text", block.Text` to the log call.
- **Every test fixture is a string literal (`harnessNudgeFixture`), never the
  production constant.** A fixture built from `harnessNoOutputNudge` asserts
  nothing about the bytes — editing the constant would drag the test green
  with it. The literal is what makes an edit to the constant go red; the
  architect's spec called this out as the point of the whole test set (see
  the sibling memory note on pinning literals, not constants).
- **5 new table rows** in `TestParser_LineMapping`: the nudge alone (silent),
  the nudge alongside a `tool_result` (scoping), the nudge embedded in longer
  text (kills substring), one word of the nudge altered near the end via
  `strings.Replace` on the literal (kills prefix, and is the fail-safe
  direction as an executable assertion), and a `tool_result` whose content is
  the nudge (pins the trust boundary). The existing `"unknown user block type
  surfaces"` case (`parser_test.go:159`, pre-#1247) is untouched — it is the
  anti-widening guard, not a case to update, and the PR diff is pure additions
  against `main` on that file.

## Patterns established

- **A matcher's tolerance should be proportional to how well-attested the
  string is.** One version, one session, three occurrences earns exact
  byte-equality, not a prefix or a structural (`[…]`) match — even though the
  bracketed form is a visible, plausible signal. The failure-direction table
  (exact / prefix / structural × drift / new-payload) is the reusable
  argument: pick the matcher whose *failure* is the one you can tolerate,
  not the one that "looks like it'll generalize."
- **A block-level suppression is a new tier, not a new entry on
  `ignoredLineTypes`.** That map is documented and pinned as a *top-level*,
  re-measured, growable list. A one-element set keyed on 100 bytes of prose
  would misrepresent thin provenance as an established list to add to.
  Promote constant → set only on a second independently-measured payload.
- **Capturing every log record and selecting by message in the assertion is
  strictly stronger than filtering inside the `slog.Handler`.** Proves both
  "the drop record has exactly these attrs" and "the text didn't leak into
  some *other* record on the same path" — the second is what the spec's
  `spawnArgsRecorder`-mirroring shape alone would have missed. Same struct, no
  extra test infrastructure.

## Lessons learned

- **`gofmt -l` hits in `internal/streamsup/` can be baseline noise, not a diff
  finding.** `helper_test.go` is unformatted on `main` (confirmed via `git
  show main:… | gofmt -l /dev/stdin`) and untouched by this PR. Filter
  `gofmt -l` output against the PR's changed files (`gh pr diff --name-only`)
  before reporting it.
- **Deriving a "drifted wording" fixture by `strings.Replace` on the captured
  literal, rather than re-typing it with one word changed, makes the fixture
  self-checking.** A hand-retyped drift risks a second transcription error
  that silently collapses the drift case into a duplicate of the silent-drop
  case; a replacement that ever stopped matching would fail loudly (the
  target substring not found) rather than pass vacuously.
- **`logRecorder.WithAttrs` returning the receiver and discarding its argument
  is a known, accepted blind spot**, not a gap to close here: it can't catch a
  future `p.log.With("text", block.Text).Debug(...)`, only a literal third
  arg on the `Debug` call. Flagged as a code-review NIT, explicitly no change
  requested — the realistic way the content-free rule breaks (appending
  `"text", block.Text` to the existing `Debug` call) is exactly what the
  third assertion catches, and the spec's shape (mirroring
  `spawnArgsRecorder`) was followed as prescribed.

## Deliberately not built here

- **A real-claude spec that backgrounds a command.** Would prove the shared
  drain's zero-unrecognized assertion is disarmed for this payload under live
  claude, but no such spec exists and the offline parser tests cover the
  behaviour completely. Out of scope per the architect's spec; the ticket's
  own criteria are all offline-provable.
- **`needs-real-claude`.** Deliberately not added — every AC is offline-
  provable (table-driven parser mappings, a capturing `slog.Handler`, a
  comment correction), and the change carries no live-claude behaviour in its
  acceptance criteria. `make e2e-realclaude`'s live specs (43) all skipped for
  want of a login in the dispatch environment; 168 offline specs really ran.
  Adding the tag would park an offline-provable ticket in Inbox for a gate
  with nothing to verify.
- **A key-set check on sibling fields riding the nudge block** (e.g.
  `{"type":"text","text":"<nudge>","injected_by":"…"}` still matches and is
  dropped whole). Accepted residual in the architect's security review: the
  package already decided unknown sibling fields don't change a block's
  disposition (`"known block with unknown extra fields still maps"`,
  `parser_test.go:187-194`), and an adversary able to add fields to a `user`-
  message block already has a strictly better target — a forged `tool_result`
  block, which does reach the tool tracker.

## Security note

`security-sensitive` label, architect self-review, verdict **PASS**. The one
live question — keying a guard on a string, the influenceable side of the
trust boundary (the shape that made #1229 dangerous) — is answered
structurally rather than by argument: attacker-influenced material never
arrives as `block.Text`, only inside a `tool_result`'s `Content`
(`streamBlock`, `parser.go:178-194`), so tripping the guard requires control
of the block's *type*, not just of a string. Pinned by the fifth test row
("tool_result whose content is the nudge still maps"). Blast radius is
diagnostic-only: `Unrecognized` is outside `stream_turn_busy.go`'s opener
whitelist, so it can never open or close a turn — a successful forgery hides
one row from a human, nothing more. `crypto/subtle.ConstantTimeCompare` was
considered and correctly rejected: the compared value is published verbatim
in the issue, so it is not a secret and timing leaks nothing. Two residuals
accepted (sibling-field carve-out above; a genuine user message could in
principle be swallowed only if it were byte-identical to the 100-byte string
— the direct, narrow payoff of exact-match over any looser matcher).
