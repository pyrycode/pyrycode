# Ticket #1080 — Modal wiring for stream: permbridge ⇄ modalbridge round-trip

Closes the stream-json permission loop. A `permbridge`-parked approval (#1103 —
claude blocked on the MCP permission-prompt-tool) now surfaces to interactive
clients as the **same** permission `modal_shown` payload they already answer
(#716), and a client's `modal_answer` resolves the parked completer to
allow/deny — keyed by `modalID`. Takes desktop#483's permission gate green.

Spec: [`docs/specs/architecture/1080-stream-modal-wiring.md`](../../specs/architecture/1080-stream-modal-wiring.md).

## Implementation

A new `cmd/pyry` type, `streamApprovalBridge` (`modal_resolve_v2.go`), joins the
two composition scopes that previously never met: the control-server-owned
`permbridge.Registry` (claude-facing completers, keyed by `tool_use_id`) and the
relay-owned `modalbridge.Registry` (client-facing modals, keyed by a minted
`modal_id` nonce). It owns the `modal_id ⇄ tool_use_id` correlation neither
registry holds, in a `map[string]string` guarded by a leaf `sync.Mutex`.

- **`Surface(req permbridge.Request) (retire func())`** — called from
  `internal/control/server.go`'s `handleApprove` via a new
  `SetApprovalSurfacer` seam (mirrors `SetRekeyer`/`SetApprovalRegistry`
  exactly). Builds the permission modal via
  `modalbridge.PermissionRequestForClass` + `Record` (byte-compatible 4-option
  / reject-once-default payload by construction), stores the correlation, and
  broadcasts `modal_shown`. Returns a `retire` closure. On `Record` RNG
  failure: drop the modal, no correlation stored, no-op retire — claude times
  out to deny via permbridge's own timer (fail-closed degrade).
- **`ResolveStream(modalID string, allow bool, denyReason string) (handled bool)`**
  — `modalResolverV2.ResolveAnswer`'s new stream (verdict) arm, dispatched
  alongside the existing tui keystroke arm via a new optional
  `streamApprovals streamApprovalResolver` field (nil-default, the #1014
  pattern — the 18 existing `newModalResolverV2` test call sites are
  untouched). `handled=false` when `modalID` isn't in `byModal` → caller
  routes the keystroke arm instead. On allow, echoes the parked `Input`
  byte-verbatim via `permbridge.Allow`; on deny, uses the fixed content-free
  `reasonRemoteDeny` constant (never host-derived).
- **`retire(modalID)`** — the guaranteed cleanup + dismissal backstop,
  `defer`red by `handleApprove` right after `Surface` returns, so it fires on
  *every* terminal `Await` path (answer, timeout, disconnect, shutdown). Two
  steps with two different arbiters: (1) unconditionally delete
  `byModal[modalID]` under `mu` — the sole correlation deleter; (2)
  `modal.Resolve(modalID)` (the modalbridge one-shot) decides whether *this*
  call also owns the dismissal broadcast — a miss means `ResolveAnswer`
  already consumed + broadcast it (answer path, no second broadcast); a hit
  means timeout/disconnect/shutdown, so `retire` audits `denied_timeout` and
  broadcasts `modal_dismissed` itself.
- **Wiring**: `startRelayV2` (`cmd/pyry/relay.go`) constructs the bridge over
  the same `*permbridge.Registry` `runSupervisor` creates (`relayWiring`
  gained an `approvals` field) and the same `*modalbridge.Registry` the
  emitter/resolver already share, sets `modalResolver.streamApprovals = bridge`
  **before** `mgr.Run` starts (no data race on the resolver field), and
  returns `bridge.Surface` outward through `startRelay` to `main.go`, which
  calls `ctrl.SetApprovalSurfacer(surface)` right after
  `ctrl.SetApprovalRegistry(...)`. `startRelay`/`startRelayV2` each gained a
  `surface func(permbridge.Request) func()` return value — both have exactly
  one production caller, both updated. A nil `w.approvals` (foreground/v1/relay
  disabled) leaves everything nil, restoring pre-#1080 keystroke-only/modal-less
  behaviour.
- **No new timer.** The stream modal deliberately does not call
  `ArmModalTimeout` — `permbridge`'s own registry-owned timer is the sole
  timeout authority (two timers would drift, and `ResolveTimeout` routes an
  Esc keystroke that has nothing to target on the stream-json path). `retire`
  is the prompt client-dismissal backstop instead.

Files touched: `cmd/pyry/main.go`, `cmd/pyry/modal_resolve_v2.go` (bulk of the
new code — bridge + resolver arm), `cmd/pyry/relay.go`, `internal/control/server.go`,
plus new tests `cmd/pyry/stream_approval_test.go` and
`internal/control/approve_surfacer_test.go`.

## Patterns established

- **Correlation-owning bridge between two independently-scoped registries.**
  When two primitives each own half of a workflow but are keyed by different
  ids and constructed in different composition scopes, the join lives in a
  small `cmd/pyry` type that holds the id↔id map — neither registry is
  widened to know about the other. Mirrors how `interactiveModalEmitterV2` and
  `modalResolverV2` already flank `modalbridge.Registry` without either owning
  it.
- **Split-arbiter cleanup**: when a "delete a correlation" step and a
  "broadcast a one-time event" step are gated by *different* one-shot
  primitives, gating the correlation delete behind the *other* primitive's
  one-shot leaks state on the path where that primitive's one-shot doesn't
  fire. Keep the delete unconditional and the broadcast gated separately by
  its own arbiter (`modalbridge.Resolve`). See Lessons learned.
- **`retire`-after-`Await` as a uniform terminal-path backstop** —
  `defer retire()` right after a blocking-verb park+surface call covers
  answer/timeout/disconnect/shutdown with one code path, rather than four
  separate cleanup call sites. Same shape as `handleAttach`'s `defer` for its
  own resources.

## Lessons learned

(Verbatim from the PR body's "Lessons learned" section, PR #1129.)

- The single-dismissal arbiter (`modalbridge.Resolve`) and the correlation
  delete have **different** arbiters: gating the `byModal` delete behind the
  modalbridge one-shot leaks the map on the answer path (`ResolveAnswer`
  consumes modalbridge before the completer resolves, so `retire`'s `Resolve`
  misses and never deletes). Keeping the delete unconditional and separate
  from the dismissal broadcast is the fix — covered by the no-correlation-leak
  test on both answer and timeout paths. This was caught as a MUST FIX in the
  architect's own spec-stage security review, before any code landed.
- `modalResolverV2.reg` and `streamApprovalBridge.modal` must be the **same**
  `*modalbridge.Registry` instance for correlation to work; the resolver-field
  wire (`modalResolver.streamApprovals = bridge`) must be set **before**
  `mgr.Run` starts, or a `modal_answer` on the Run goroutine races the field
  write.

Code review (PR #1129, PASS) flagged two NITs, neither requiring rework:

- A tight-window race where a client `modal_answer` can win the modalbridge
  consume just as a timeout/disconnect `retire` runs its unconditional
  `delete(byModal)`; `ResolveStream` then reads an empty map and routes a
  spurious keystroke into the active supervisor. Fail-safe (permbridge was
  already deny-resolved by the timeout that triggered `retire`) and
  unobserved — left as-is per evidence-based fix selection.
- `streamApprovalBridge.broadcast` closely mirrors
  `interactiveModalEmitterV2.broadcastInteractive` but needs its own
  `mu`-guarded envelope counter (concurrent control-handler goroutines, vs. the
  emitter's single producer goroutine) and stricter log discipline (omits
  `err` from the push-drop log). Deliberate duplication, not unified — not
  worth parameterising the lock for a ~400-line-ethos project.
