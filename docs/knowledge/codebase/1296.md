# Ticket #1296 — Attach the daemon's ack #2 → expiry log window to M4's failure record

`TestRelayV2_StreamNewSessionRotatesAndRestartsFresh` (#1137) fails intermittently at M4.
#1273 made the failure self-describing (elapsed stamps, stdin-log size delta, registry
re-read) but its own developer flagged what remained fused: a frozen stdin log is
consistent with both "delivery stalled inside the seam" and "the fresh child never
spawned." This ticket closes that gap for the first pair — "the drain retried and was
refused" vs. "the drain was not in the error-return arm" — by attaching the daemon's own
log output for the dead window to the failure message. Diagnostic-only, no production
code, no deadline or retry change.

## Implementation

All changes are inside `internal/e2e/relay_v2_stream_new_session_test.go`:

- **Window boundary is a byte offset, not a timestamp.** `ackTwoLogLen := len(h.Stderr.Bytes())`
  captured beside the existing `ackTwoBytes` stdin-log read. `h.Stderr` (`safeBuffer`) is
  append-only — `Write`/`String`/`Bytes` only, no `Reset`, no `Read` — so byte *N* means the
  same byte for the test's lifetime and `snapshot[ackTwoLogLen:]` is exactly "what the
  daemon logged after ack #2," with no clock or format coupling. Same instrument at both
  ends, matching the file's existing stdin-log discipline.
- **`daemonLogWindow(snapshot, since, budget) string`** — one pure function (no `*testing.T`,
  no I/O, no clock) owning every honesty obligation. Four arms: `<unmeasurable: …>` when
  `since` is negative or past the snapshot end (unreachable while `safeBuffer` stays
  append-only — the guard exists so that assumption is checkable); `<empty: …>` for a
  zero-length window; verbatim rendering under budget; head+tail with an exact elided-byte
  count over budget. Never returns `""`. The header states the window's **total** byte count
  (not the kept count) and the count of `msgqueueRetryWarn` matches, naming the literal it
  matched so a count of 0 is checkable against a visible needle.
- **`daemonLogBudget = 8 << 10`** and **`msgqueueRetryWarn = "msgqueue: delivery failed, will retry"`**
  (verbatim from `queue.go:607`) as package-level constants. The literal is duplicated
  rather than exported from `msgqueue` — exporting an operator-facing log string would turn
  it into an API.
- **Message ordering**: computed verdicts (ack #2, stdin-log delta, registry re-read, the
  daemon window) print ahead of the static legend, which explains how to read the window —
  ~1 retry Warn/s means the error-return arm; zero Warns means *not that arm*, explicitly
  **not** "the daemon never tried," naming the three states silent at Info level (parked in
  `Activate`, parked in the mid-turn hold, or retrying under the Debug-level pending/hold
  branch). `log=%q` (the stdin log) stays last.
- **Corrected the deadline-pin comment** (lines ~388–420). The prior prose ("the drain BLOCKS
  … with no periodic retry, so a missed wake-up is an unbounded stall") was wrong on both
  clauses: the error arm retries every `defaultRetryInterval` (1 s) and gives up after
  `defaultGiveUpAfter` (2 m); the parked waits are bounded, not unbounded
  (`inboundActivateTimeout` 30 s, `streamTurnHoldTimeout` 15 min) — merely silent at Info
  level for the whole of this 20 s window. The spec's own suggested replacement phrasing
  ("20 s, 60 s and 300 s all sit below both silent bounds") was itself false — 60 s and 300 s
  both exceed the 30 s `Activate` bound — and the developer did not paste it; the shipped
  comment scopes silence correctly to "this 20 s window."
- **Folded in `&& e.ID != ""`** on the failure-time registry re-read, closing the gap #1273
  named as a fold-in for the next ticket touching this file (`docs/knowledge/codebase/1273.md`).
- `TestDaemonLogWindow` (table-driven, package-private) pins the four arms plus Warn-count
  scoping (a copy of the literal placed before `since` must not count) and the never-`""`
  invariant.

## Patterns established

- **A window boundary from an append-only buffer is a byte offset, not a timestamp.** When
  the target is a `safeBuffer`-shaped sink (`Write`/`String`/`Bytes` only, no `Reset`), the
  cheapest stable boundary is `len(buf.Bytes())` captured at the reference moment — no clock,
  no parsing, and it survives concurrent appends by construction.
- **A count is the primary datum; an excerpt is corroboration.** When a diagnostic's job is
  "did X happen and how many times," compute the count directly (`bytes.Count`) rather than
  asking a human to eyeball a possibly-elided excerpt — the count survives truncation the
  excerpt does not, and it should name the literal it matched so a zero reads as checkable
  rather than trusted blind.
- **A bound's header states the total, never the kept size.** Reporting only what survived
  elision is indistinguishable from silent truncation; the honesty obligation is symmetric —
  a short window must not *look* truncated either, so the complete-arm rendering says nothing
  about eliding.
- **Head *and* tail, not head alone**, when the over-budget case is "an unexpectedly chatty
  run" rather than "an unbounded stream" — onset and the last thing said are both load-bearing
  and head-only elision can bury either.
- **An exact-multiple byte count is a stronger boundary proof than an absent needle.** From
  the PR: proving a window contains only post-boundary lines by dividing its size by a known
  uniform line length rules out every pre-boundary byte at once; grepping for one absent
  needle only proves that one line was excluded.

## Lessons learned

From the PR body's own **Lessons learned** section
([PR #1301](https://github.com/pyrycode/pyrycode/pull/1301)):

> An exact-multiple byte count is a stronger boundary proof than an absent needle. AC-5 asks
> that pre-window output not appear; grepping for one startup line proves only that line was
> excluded. The window's size dividing exactly by the uniform Warn-line length (4541 = 19 ×
> 239) proves the window contains the post-ack lines and nothing else — the arithmetic rules
> out every pre-ack byte at once, where the needle rules out one.
>
> Sizing a diagnostic's bound against the arm it exists to detect makes the common failure
> render complete. The modelled ~20 Warns came in at 4541 B against an 8 KiB budget, so the
> expected recurrence never elides; elision stays reserved for a genuinely chatty run, and the
> header's count survives it either way.
>
> Folded in the one-clause `&& e.ID != ""` guard #1273's knowledge doc left standing on the
> failure-time registry re-read — an empty id would otherwise print as a manufactured
> second-rotation proof.

**A code-review NIT survived to merge as a named, accepted gap** (below the threshold to
block; the shipped code still reads this way). The corrected deadline-pin comment states
"past 15 min a wedged hold gives up and surfaces a typed `session_error`" — the actual
give-up is at roughly **30 min**, not 15: `streamTurnHoldTimeout` (15 min) bounds a single
*attempt*, not the client-visible outcome. Attempt 1 times out at 15 min and only *starts*
msgqueue's give-up streak (`elapsed ≈ 0 < defaultGiveUpAfter`); attempt 2 times out at ~30 min
with `elapsed ≈ 15 min ≥ defaultGiveUpAfter` (2 m), which is when `OnGiveUp` actually fires
(`cmd/pyry/main.go:1531-1537` states this: "Worst case ≈ 2× this value"). The conclusion the
comment supports is unaffected — every deadline it adjudicates (20 s/60 s/300 s) sits far
below both 15 min and 30 min — so this was accepted as non-blocking. **The phrasing traces to
the architecture spec (§ D5), which made the same per-attempt-vs-client-visible conflation.**
A future ticket touching this file should fold in the reviewer's suggested fix ("past ~30 min
(two 15-min attempts) a wedged hold gives up…") rather than let this re-surface as a fresh
finding — same "SHOULD FIX/NIT survives as a named gap" shape #1273 and #1295 recorded for
this file family. **Process note for future spec-writing on this file:** two tickets running
(#1273's ticket-authored replacement, and now #1296's spec-authored replacement) have each
introduced a *new* factual error while correcting a prior one — verify a replacement's own
arithmetic against every bound it names, not only against the clause it's fixing.

## What this record will and will not decide

**Will:** separate "the drain retried and was refused" (~20 Warns) from "the drain was not
in the error-return arm" (0 Warns) — the pair #1273 left fused. Under this fixture's default
configuration (no trust modal), 0 Warns narrows further to *parked in `Activate` or the
mid-turn hold*, since the third silent state (Debug-level pending/hold retry) requires
`Readiness{TrustModal:true}`, which this test never configures.

**Will not:** distinguish the two parked states from each other (both silent at Info level
for the whole window — separating them needs `-pyry-verbose`, deliberately not enabled, or a
production-side observable). Nor does it decide "the fresh child never spawned" on its own —
`streamsup` logs spawn/exit/backoff lines at Info, so they appear in the window *if they
happen*, but their absence is weak (a child spawned before ack #2 logs nothing afterward).
Process liveness at failure time remains a next-ticket concern; #1298 (straggler-re-mark
hypothesis) may be the same stall via a different mechanism.
