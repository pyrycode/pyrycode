# Ticket #1401 — ACP `session/update` payload shape for the background-task events

Gives claude's background-task lifecycle (`BackgroundTaskStarted` /
`BackgroundTaskUpdated` / `BackgroundTaskRoster` in `internal/turnevent`) an ACP
payload shape for the first time. The facts already reach a mobile client
(#1393/#1394); without an ACP shape a desktop client can't tell a turn that ended
with work still running from a genuine finish (#1240's symptom). Split from
#1399; PR [#1403](https://github.com/pyrycode/pyrycode/pull/1403), code review
PASS (1 SHOULD FIX, below the 3-finding merge threshold).

## Implementation

- Four new exported types in `internal/acpbridge/outbound.go`: `BackgroundTaskStarted`,
  `BackgroundTaskUpdated`, `BackgroundTaskRoster`, and the roster's entry type
  `BackgroundTask`. Full field mapping, the discriminant choice, the
  `MarshalJSON` nil-normaliser, and the three `SECURITY:` sites are documented in
  [features/acpbridge-package.md § Background-task payload shapes](../features/acpbridge-package.md#background-task-payload-shapes--declared-not-yet-wired-1401).
- ACP has no in-taxonomy `sessionUpdate` variant for a background task, so the
  ticket's open question — extension discriminant vs. reusing one of the four
  generic ones — was resolved by the architect on a dominance argument (reuse is
  weakly dominated: identical failure under a strict host, worse under a lenient
  one that misreads the body as a real tool call) and recorded as **[ADR 027
  divergence 7](../decisions/027-acp-mapping.md)**, not in § "ACP taxonomy
  reference" (that section is a verbatim external-spec port; a pyry-invented
  string there would read as spec truth).
- `TestACPConformance_DialectLock` (`cmd/pyry/acp_conformance_test.go`) gained
  three rows locking the new constants against divergence 7's literal strings,
  and its comment was corrected: seven discriminants now, not four, with two
  different homes (taxonomy reference vs. divergence 7).
- **No `MapUpdate` arm.** The three neutral variants still fall to `default:` /
  `ok == false` — deliberately deferred to #1402, mirroring the #1393-then-#1394
  split on the mobile lane. Nothing produces these events on the ACP lane either
  (#1400). The new test, `TestBackgroundTaskPayloadWireShape`, marshals payload
  values directly since there's no mapper to drive them through.

## Patterns established

- **Declare-then-wire split, ACP side.** When a neutral `turnevent` variant needs
  a new wire shape but its `MapUpdate` arm and producer aren't ready, land the
  types + discriminant + ADR row alone, with `default:` doing the honest
  fallback. Precedent existed one lane over (#1393/#1394 mobile); this ticket
  established the identical pattern for `acpbridge`.
- **An ADR divergence is the home for a protocol extension, not the taxonomy
  port section.** When a mapping has to invent something the external spec
  doesn't have, write the invented string and its justification into a numbered
  divergence, and keep the spec-ported section byte-for-byte what it claims to
  be (source + capture date stated, nothing invented mixed in).
- **Reviewing a `MarshalJSON` nil-normaliser by mutation testing must check that
  each mutant actually compiles as the intended change** (see Lessons learned) —
  code-review ran the mutant matrix via `go test -overlay` (no worktree writes),
  and this ticket is a fresh instance of picking the mutation that actually
  exercises the code path, not just one that happens to fail to build.

## Lessons learned

From the PR body's own "Lessons learned" section (developer, verbatim):

> A `MarshalJSON` mutation has two inequivalent expressions and only one of them
> tests anything. Flipping the receiver to a pointer *in place* fails to compile
> (`alias(u)` no longer converts), so it reads as a detection when nothing was
> actually exercised; the mutation that bites is the pointer receiver **with**
> the deref (`alias(*u)`), which compiles, silently never fires through an
> `any`, and is caught only by the nil-`Tasks` row. Same for dropping a struct
> field the fixture still sets — a build break, not a row. Any mutant whose
> overlay run fails to *build* should be re-expressed until it compiles, or it
> has verified nothing.

Code review independently confirmed the empty-roster row (row 4) is the sole RED
for three distinct mutations (`MarshalJSON` deleted, `tasks` gains `omitempty`,
`droppedTasks` gains `omitempty`) plus the build-break pointer-receiver case,
which is what keeps AC 4's row from being the vacuous one the ticket's own text
warned against.

**Known outstanding nit (not blocking, not fixed in this PR):** `outbound.go`'s
`TruncatedFields` doc comment says it's "omitempty on all four types" — it's
three; `BackgroundTaskRoster` has no `TruncatedFields` field at all, and the
same comment block says so two sentences later. Code review flagged this as a
single SHOULD FIX plus two related NITs (all one-word count corrections), all
below the 3-finding merge threshold. Worth a one-word fix whenever `outbound.go`
is next touched — most likely #1402.
