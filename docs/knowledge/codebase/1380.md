# Ticket #1380 — Map claude's `task_started` background-task subtype to a bounded daemon event

claude's background-task lifecycle (a spawned `local_bash` command that outlives the turn that started it) was reaching `internal/streamsup`'s parser and being discarded whole: every `system` line was dropped through `ignoredLineTypes` regardless of subtype. That's the root cause of #1240's symptom — the daemon reports `turn_end`/`end_turn` and state `idle` while a backgrounded command is provably still alive, with nothing reaching a client that separates the two. This ticket maps the first captured subtype, `system/task_started`, into a new `turnevent.BackgroundTaskStarted` and lays down the two mechanisms its siblings ride: `system` subtype dispatch and a construction-time bound on claude-derived text. `task_updated` (#1382) and `background_tasks_changed` (#1381) extend the same mapped set and the same event family.

## Implementation

- **`turnevent.BackgroundTaskStarted`** (`internal/turnevent/event.go`) — a new variant of the sealed `Event` sum type. Fields: `TaskID` (claude's `task_id`, the join key later lifecycle lines use), `ToolCallID` (claude's `tool_use_id`, deliberately renamed to match the name `ToolStart`/`ToolUpdate` already use for the same identifier), `Description` (the literal Bash command line — safe to render, never to execute), `TaskType` (plain `string`, not a closed enum — one observed value, `local_bash`, doesn't earn a closed set), and `TruncatedFields []string` (the cut report, `nil` when nothing was cut).
- **Two captured keys are deliberately not carried**: `session_id` (claude's session identity, not the daemon's conversation identity) and `uuid` (claude's per-line message id, no daemon reader). Both drops are enforced by a reflection sweep in the test, not just documented — see Patterns below.
- **Dispatch** (`internal/streamsup/parser.go`) — the subtype match lives *inside* `consumeLine`'s existing `ignoredLineTypes` branch, guarded on `sl.Type == "system"`: `if sl.Type == "system" && p.emitSystemSubtype(sl.Subtype, line) { return }`. `system` stays on `ignoredLineTypes`, so `emitUnrecognized` (the top-level alarm) is structurally unreachable from any `system` line whatever its subtype — this is what keeps `TestParser_IgnoredLineTypesIsTheMeasuredSet`'s `reflect.DeepEqual` pin on `{system, rate_limit_event}` green and unedited.
- **`emitSystemSubtype(subtype string, line []byte) bool`** — the single enumeration site of the mapped set (`case "task_started": return p.emitBackgroundTaskStarted(line)`, `default: return false`). Every comment describing the drop rule points here rather than restating the set.
- **`emitBackgroundTaskStarted`** decodes a *second* `json.Unmarshal` of `line` — the top-level bytes, never a nested field — into the new unexported `systemTaskStartedLine` shape (`task_id`, `tool_use_id`, `description`, `task_type` only; `streamLine` itself is left at `Type`/`Subtype`/`Message`, unwidened). Decoding from anywhere but `line` would make the event forgeable out of claude's own tool output (flagged in architect security review, verified in code review). A payload that won't decode is dropped with a content-free Debug and **no** `Unrecognized` — surfacing a malformed known subtype there would break the structural guarantee above.
- **Bound** — `truncateField` mirrors `emitUnrecognized`'s `truncateRaw` precedent: cut at construction, `strings.ToValidUTF8` scrub after (empty replacement, so a mid-rune cut *deletes* the partial rune — a multi-byte cut can land 1–3 bytes under the cap), boundary `<=` (exactly-at-cap is not truncated). Two new constants: `maxTaskFieldID = 256` (identifiers — ~9× the capture's longest, `tool_use_id` at 29 bytes) and `maxTaskDescription = 4 << 10` (the model-authored command line — ~32× the capture's redaction-adjusted real length of ~126 bytes). Worst case per event: `3×256 + 4096 = 4864` bytes, 7.4% of the 65519-byte v2 envelope cap.
- **Field mapping and cap arithmetic are built from the committed capture** `internal/e2e/realclaude/testdata/dropped_lines_v2.1.220.json` (#1260), never a hand-built line — enforced at the reader (`capturedSystemLine` asserts `is_capture == true` and exactly one matching record before returning any payload).
- **Four comment corrections** to the old "`system` is ignored wholesale" claim, all landing in this PR: `ignoredLineTypes`' own comment (`parser.go`, the canonical statement — the 2026-07-27 measurement is a refinement, not a reversal: it was about *what to draw*, used to decide *what to send*; those are separate decisions), the `default:` arm's inline comment, `TestParser_IgnoredLineTypesStaySilent`'s in-body comment, and `Unrecognized`'s doc comment in `turnevent/event.go` (prose pointer only — `turnevent` must not import `streamsup`).

## Patterns established

- **Subtype dispatch nests inside the ignored-type drop branch, not beside it.** Keeping `system` on `ignoredLineTypes` while matching subtypes *inside* that branch is what makes "no `system` line reaches the unrecognized lane" a structural property instead of a tested one. #1381/#1382 should follow the same placement.
- **A provenance rule ("build from the capture") is enforced at the reader, not by review discipline.** `capturedSystemLine` fails fast on `is_capture != true` or a non-exactly-one match, so a hand-built substitute file breaks before any field mapping is read.
- **A "field X is deliberately dropped" claim is proven by reflecting over every string field on the struct, not by checking the N known fields.** `TestParser_TaskStartedMapsFromCapture` sweeps all string fields on `BackgroundTaskStarted` for claude's `session_id`/`uuid` values, with a `swept < len(routes)*2` guard so the sweep can't silently visit nothing. This is what lets the drop survive #1381/#1382 adding fields without anyone remembering to extend a checklist.
- **Cap fixtures must be built from independent literals, never the production constants** (`taskFieldIDCapFixture = 256`, kept separate from `maxTaskFieldID`) — a fixture built from the constant it validates goes green even if the constant is halved. Code review mutation-tested this (`maxTaskFieldID` 256→128 went RED across 5 rows).
- **One reusable capture reader for a whole sibling group.** `capturedSystemLine(t, subtype)` in the new `internal/streamsup/capture_test.go` is written once for #1380 and is what #1381/#1382 read the same file through.

## Lessons learned

(From the PR body — developer's notes, lightly trimmed.)

- A "build it from the capture" provenance rule is best enforced at the reader, not by review: `capturedSystemLine` asserts the file's top-level `is_capture` before returning any payload, and requires *exactly one* matching record — two would make "the captured line" ambiguous, and silently taking the first is the kind of choice that should be deliberate.
- A "field X is deliberately not carried" assertion rots into decoration unless it sweeps by reflection. Checking the known fields against the payload's `session_id` passes forever once someone adds a fifth field; sweeping every string field on the struct covers fields added later by siblings, and a `swept` counter keeps the sweep from silently visiting nothing.
- `truncateRaw`'s scrub uses an *empty* replacement, so a mid-rune cut deletes the partial rune — a multi-byte truncation result is legitimately 1–3 bytes under the cap. Exact-length assertions have to be built from ASCII fixtures; a multi-byte row can only assert validity and the ceiling.
- Ordering a report by struct-literal field order rests on Go's left-to-right operand evaluation rule. It's spec-guaranteed, but sequential statements make the ordering visible to a reader instead of inferred — worth doing when the order itself is what's being pinned (`TruncatedFields`' declaration order here).
