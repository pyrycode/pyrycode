# Ticket #1419 — The trailer gate tells an absent `terminal_reason` from a present-and-empty one (offline)

`trailGate`'s empty-`terminal_reason` arm (`trailer_admissibility_test.go`) collapsed two shapes onto
one answer and published one sentence about both, ending `NO LIVE REPRO EXISTS`. That claim is true of
a `terminal_reason` key that is on the line with a blank value (`streamjson/emitter.go:383-391` is a
chokepoint pyry cannot render past) and **false** of a trailer with no `terminal_reason` key at all —
which is what every healthy `PYRY_USE_STREAMJSON=1` run produces: `streamrunner.Run` tees claude's
stdout unchanged and synthesises a trailer only when the idle-stall watchdog fired with no result seen.
The arm now splits in two, deciding on the scan's key names rather than the decoded value. No answer
changes: both shapes still return `trailGateOutOfContract` with `Reason` empty, so the five-value gate
allowlist, `trailClassifyRun`'s C1/C2, and every downstream consumer are untouched. Purely additive to
one existing test file — one new fixture pair, one new `trailGateCases()` row, zero production files.
PR [#1421](https://github.com/pyrycode/pyrycode/pull/1421). Split from #1416.

## Implementation

- **`trailer_admissibility_test.go`** — the `if reason == ""` guard stays as the outer condition; inside
  it, a new `if !slices.Contains(in.Scan.KeyNames, trailReasonKeyName)` branch returns the absence arm,
  falling through to the (rewritten) present-and-empty arm otherwise. Both still carry
  `RunnerPath: in.RunnerPath` and read no path. `trailGateOutOfContract`'s doc comment moves from "three
  sub-cases" to "four."
- **Presence is membership, never the decoded value or cardinality.** `slices.Contains(in.Scan.KeyNames,
  trailReasonKeyName)` — the same read `trailReasonAgainstPath` opens with. Inside this block the decoded
  value is always `""`, so keying on it would silently route every input to the absence arm; keying on
  `len(KeyNames) > 0` reads a scan-produced absence (six names, merely missing `terminal_reason`) as
  present.
- **`trailGateAbsentReasonScan()` / `trailGateEmptyReasonScan()`** — new fixture functions (not vars, for
  the `go test -race` reason `trailExpectedKeyNames()` already states), each `trailScan` over one of the
  shipped `trailKeyNamesNoTerminalReason()` / `trailKeyNamesEmptyTerminalReason()` fixtures. Going through
  `trailScan` is load-bearing, not stylistic: the absence fixture's `KeyNames` is scan-produced (six real
  names), which is the only reason the cardinality mutation (`len(KeyNames) > 0`) can be caught at
  all — a hand-built `KeyNames: nil` reads as absent under that mutant too and would leave the row
  proving nothing.
- **Two shipped fixtures repaired.** The `trailGateCases()` row at (was) `:703-708` — a hand-built
  `trailScanResult{State: trailSeen, Trailer: &resultTrailer{Type: "result"}}` with `KeyNames` unset,
  which is absence-shaped under the new reading — now uses `trailGateEmptyReasonScan()`. The Detail
  sub-test's matching input is repaired the same way. Without the repair the present-and-empty arm was
  unreachable from the suite and both of its Detail assertions passed against the absence arm instead.
- **A ninth `trailGateCases()` row** (`trailGateAbsentReasonScan()`, `want: trailGateOutOfContract`,
  `RunnerPath: trailRunnerUnread()`) covers the absence arm — after the repair, no other row in the slice
  is absence-shaped, so without this row `TestTrailGateIgnoresTheRunnerPath`'s clause-B carriage
  assertion would no longer be total over the gate's (now eight) return sites. Verified by enumeration:
  the nine rows reach all eight sites. The row carries `trailRunnerUnread()` like every other row, which
  is what keeps `trail_ptyrunner_composition_test.go:38`'s "every row carries `trailRunnerUnread()`"
  totality claim true and untouched.
- **The Detail sub-test widens from three inputs to four**, and each of the two new rows asserts both its
  own markers and the other arm's absence (`terminal_reason is empty` / `NOT DECIDED AT THIS ARM` /
  `NO LIVE REPRO EXISTS`) — so a row is red on its own when its own case misroutes, not merely when the
  two Details happen to differ.
- **A second sub-test on `TestTrailAdmissibilityRecordsCarryNoCapturedBytes`** — two hand-built rows
  (needed here specifically, since the needle has to *be* a key name, and `trailScan` reads names off
  real JSON) planting `trailNeedle` in `KeyNames`, one reaching each new arm, each asserting the arm
  marker before the no-captured-bytes check. The shipped sweep's gate row leaves `KeyNames` nil and
  reaches `trailGateUsable`, so it could never see this surface — key names are attacker-influenced,
  deliberately unbounded at this tier (`#1363`), and `trailGateResult` is published, while
  `trailScanResult` is not.
- **Eight count claims re-derived**, not adjusted by one, per the ticket's own inventory: arm count
  (seven → eight), the Detail sub-test's input/arm count (three → four), the carriage sweep's totality
  numbers (seven sites / eight rows → eight sites / nine rows), the `trailGateCases()` provenance split
  (four/four → six scan-produced / three hand-built, restated at two sites), and the two "eight
  rows"/"eight fixture rows" claims that move to nine with the added row. `trail_ptyrunner_composition_test.go:38`'s
  totality claim stays **unchanged** — true because the added row carries `trailRunnerUnread()`.

## Patterns established

- **Presence is a membership test over shipped key names, never the decoded scalar and never
  cardinality.** Two independent readings collapse the two shapes for two different reasons — the decoded
  value is always the same inside this branch, and cardinality miscounts a scan-produced absence as
  present because five other keys are still there. Both were mandated mutations, each verified sole-red
  under `go test -overlay`.
- **A discriminating fixture has to come from the real producer, not a hand-built lookalike.** The
  absence row's `KeyNames` had to be scan-produced (missing exactly one name out of six) rather than
  `nil`, because a `nil`-vs-`len>0` mutant cannot be caught by an input a `nil` check also gets right.
  Documented at the fixture's own doc comment so a future edit doesn't "simplify" it back to a literal.
- **Restoring a totality claim by coverage, not by softening it.** Splitting one arm into two, without
  adding a fixture row for the new arm, would have silently narrowed `TestTrailGateIgnoresTheRunnerPath`'s
  "the rows reach every return site" guarantee. The fix is an added row proven (by enumeration) to reach
  the previously-uncovered site, not a reworded comment.
- **A rendering-surface sweep is only as good as the arm its row reaches.** The shipped no-captured-bytes
  sweep's existing row never exercised either new arm (it reaches `trailGateUsable`), so a second,
  separately-preconditioned sub-test was required rather than widening the first — its premise (a
  well-formed input reaching the usable arm) doesn't hold for the new rows.
- **Count-word sweeps miss counts written as numerals.** Both the ticket's and the spec's re-derivation
  sweeps grepped for spelled-out numbers (`\b(three|four|seven|eight|nine)\b`); a clause reading "shrink
  40 comparisons to fewer" survived both, four lines from its already-corrected twin ("forty-five"), and
  was only caught by code review's numeral-form residual sweep (`^\s*//.*\b[0-9]{1,3}\b`). Fixed as
  `forty-five` (matching its twin) rather than `45`, since the numeral form was the reason it evaded
  detection in the first place.

## Lessons learned

From the PR body's own "Lessons learned" section (developer, verbatim, condensed):

- A rendering-surface sweep is only as good as the arm its row reaches — the shipped sweep's gate row
  carries `TerminalReason: "completed"` and `KeyNames` nil, landing on `trailGateUsable`, so it could
  never see a Detail that echoed a key name. The new rung asserts each row's arm marker before sweeping.
- Counting arms and counting values are different sweeps: `trailGateOutOfContract`'s own doc said "three
  sub-cases" and went false with the split, while three nearby "three"s (unrelated closed sets) correctly
  stayed true. A word-level number grep finds the candidates; only reading each hit's noun says which one
  moved.
- A count-word sweep cannot see a count written as a numeral (see above, "Patterns established").

From code review (two rounds — first FAIL on a MUST FIX, reworked, then PASS with a SHOULD FIX left open):

- **MUST FIX (fixed, 3ba545f):** `TestTrailGateIgnoresTheRunnerPath`'s two vacuity clauses named the same
  sweep size in one bullet list; clause B was correctly re-derived to "forty-five" but clause A, three
  lines above, was left at the stale "40". Root cause was the numeral-vs-word sweep gap above. Fixed by
  writing it as `forty-five`, the root-cause fix as well as the cosmetic one.
- **SHOULD FIX (left open, follow-up):** the new key-name leak rung has a truncation blind spot. The
  absence Detail renders at 480/512 bytes (32 bytes of headroom) against a 42-byte needle
  (`trailNeedle`); an echo appended at the *tail* of that Detail is cut by `reachCapCommand` before the
  needle completes, and `bytes.Contains` reports clean even though a truncated fragment of claude-derived
  text did cross into the published record. The rung has real teeth for an echo anywhere else (proved:
  head-of-absence-Detail and both positions in the present-and-empty Detail's wider 70-byte headroom all
  go correctly RED). The spec's own § 2 already named the fix (`!strings.HasSuffix(detail,
  reachTruncationMarker)` as a second non-vacuity precondition, alongside the arm-marker check) but it was
  not required for merge — recorded here so a future tightening of this rung's idiom doesn't have to
  re-derive the gap from scratch. **Applies beyond this ticket:** any future no-captured-bytes rung that
  plants a needle wider than a Detail's measured cap headroom needs the same `HasSuffix` guard, or a
  needle shorter than the headroom.
