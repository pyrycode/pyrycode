# Ticket #1575 — A newly-minted session starts at the operator's configured model and effort level

Both mint entry points handed `Pool.buildSession` the zero `SessionSettings`, so a client-minted session spawned with no `--model` / `--effort` and silently fell back to claude's own defaults. `Pool.mintSettings()` (`internal/sessions/pool.go`) now sources the operator's configured model and effort from the bootstrap's persisted settings, and `CreateIn` / `GetOrCreateIn` pass it. `Pool.Revive` is unaffected — it still passes the zero value, so a phone-granted bypass keeps failing to survive a daemon restart (#1487).

## Implementation

- `Pool.mintSettings()` reads `DefaultSettings()` and rebuilds a `SessionSettings` **field by field** from `Model` and `Effort` only — `YOLO` is excluded structurally, not by a clearing statement, so it can't be reintroduced by a later edit that copies the struct wholesale. Must be called with `p.mu` unheld (`DefaultSettings` takes `RLock`, non-reentrant); both call sites build the session before taking `p.mu`.
- `materialise` (`internal/sessions/get_or_create.go`) gained a `settings SessionSettings` parameter instead of deciding policy itself. This is the load-bearing choice: `materialise` is shared by `GetOrCreateIn` (must inherit) and `Revive` (must not, per #1487), so each caller now states its choice at its own call site rather than a one-line change inside `materialise` silently taking both paths with it.
- `TestPool_Revive_DoesNotInheritOperatorSettings` is the regression guard — confirmed via `go test -overlay` to redden specifically when `materialise` reads `mintSettings()` unconditionally, and only that test reddens under that mutant.
- The `#826b` zero-value comments at both mint sites and the fused mint+revive comment in `materialise` were split: the mint half deleted (no longer true), the #1487 fail-closed half moved verbatim to `Revive`'s call site.
- `docs/knowledge/features/sessions-package.md` (§ *Two spawn sites*, § `Pool.Revive`) was corrected in the same PR (not by this documentation phase) as part of AC 5.
- Ripple: `saveLocked` now persists `model`/`effort` for a minted session when the bootstrap carries them (`omitempty` previously dropped them) — wanted, since `Pool.UpdateSettings`'s live restart recomposes argv from the stored value.

## Deferred (code review NITs — not blockers)

- `docs/knowledge/features/sessions-package.md:32` — "no wire verb yet (setter: #826b, reader: #826c)" is stale: #845 landed the setter (`internal/relay/v2session_settings.go` `handleSetSessionSettings`, wired via `settingsUpdaterAdapter` in `cmd/pyry/main.go` to `Pool.UpdateSettings`). Out of this ticket's scope (AC 5 was about the *mint* path, not the wire verb) but worth a follow-up sweep replacing the never-filed `#826b` with #844 (wire vocab)/#845 (handler) wherever it still appears.
- The spec's security review treated the registry as "operator-trusted … for the bootstrap entry" as the premise that makes `mintSettings` safe. That's still true in effect, but the bootstrap's `Model`/`Effort` is also runtime-writable by the phone: `Pool.UpdateSettings` accepts any session id, including the bootstrap. The reason the conclusion still holds is that `handleSetSessionSettings` validates (`validModel`/`validEffort`) before persistence, so every value that can reach `mintSettings` is already boundary-checked. A future ticket touching this path should not assume "operator-only" as a starting premise — assume "validated-at-the-wire-boundary" instead.

## Lessons learned

(From the PR body's Lessons learned section.)

- A signature change was the cheap way to stop a shared helper from deciding policy. `materialise` had two callers with opposite contracts and no test pinning the difference; adding the `settings` parameter cost two edits and turned an invisible coupling into a compile-time question each caller has to answer.
- The overlay mutation proved AC 3, not the green run: `TestPool_Revive_DoesNotInheritOperatorSettings` passed on an unmodified tree *and* before any production change was made — only the mutant run discriminates it from a vacuous test.
- The `#826b` sweep wasn't exhausted by AC 5 (see Deferred, above) — the grep's own hit count doesn't tell you whether the survivors are in-scope or a different claim wearing the same stale issue number.
