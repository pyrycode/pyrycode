# Ticket #863 — daemon shutdown hangs while a control client is attached

A daemon stopped (SIGTERM / `pyry stop` / `pyry update`) while a control client was attached never exited on its own. `Bridge.Attach`'s input pump loops `in.Read(conn)` and only exits on a read error; nothing server-side ever closed the conn, so an idle client's read blocked forever, `handleAttach`'s detach-watcher never woke on `<-done`, `Serve`'s `streamingWG.Wait()` never returned, and the service manager escalated to SIGKILL. See [control-plane.md § Lifecycle](../features/control-plane.md#lifecycle) for where this sits in the shutdown sequence.

## Implementation

Two distinct block points live in the one pump goroutine, and each is unblocked by the layer that owns the resource it's parked on — no layer reaches across the frozen `Attach(in, out) (done, err)` signature:

| Layer | Owns | Block point it aborts | Trigger |
|---|---|---|---|
| `control.Server` | the `net.Conn` | `in.Read` (read-parked, idle client) | `Server.Close` closes every tracked streaming conn |
| `supervisor.Bridge` | `b.in` channel | `b.in <- chunk` (send-parked, child in restart backoff, buffer full) | new `Bridge.Shutdown()` closes a terminal `shutdownCh` the send selects on |
| `sessions.Session` | the `Bridge` handle + shutdown-vs-eviction knowledge | wires the two | `Session.Run` defers `Bridge.Shutdown()` |

- `Bridge.Shutdown()` (`internal/supervisor/bridge.go`) closes `shutdownCh` via `sync.Once` — idempotent, callable from any goroutine, no-op if nothing is attached. Deliberately **distinct** from the existing per-iteration `iterCancel` (closed + re-created on every child exit, including restarts): reusing `iterCancel` for the send-abort would tear the attach down on every routine restart backoff instead of only at terminal shutdown.
- `Session.Run` (`internal/sessions/session.go`) defers `s.bridge.Shutdown()` (guarded by `s.bridge != nil` — foreground sessions have no bridge) at the top of the function. `Run` returns only on permanent termination (outer ctx cancel or `Pool.Remove`); eviction stays inside the active↔evicted loop, so the defer fires exactly once and never on eviction. Placing the hook in `supervisor.Run` instead would be wrong — it also returns on eviction, which would poison the bridge for the next reactivation.
- `control.Server` (`internal/control/server.go`) adds a `streamConns map[net.Conn]struct{}` guarded by the existing `s.mu`. `handleAttach` registers the conn at handoff, reading `s.closed` in the same critical section — if shutdown already raced ahead (snapshotted the set before this handoff landed), the handler closes its own conn immediately instead of relying on `Close`. The detach-watcher deregisters after `<-done`. `Close` snapshots the set under `s.mu`, releases the lock, then closes each conn outside it — never holding `s.mu` across a `conn.Close()` avoids inverting lock order against the detach-watcher. Double-close (`Close` + detach-watcher, or handoff-race + `Close`) is safe and errors are discarded.

## Patterns established

- **Abort each block point on the resource its owning layer controls**, rather than inventing one shared cancellation mechanism that crosses package boundaries. Kept the frozen `Attach` signature untouched — changing it would have cascaded through `Bridge`, `Session`, the control `Session` interface, and ~5 test files (the #29 failure mode).
- **A closed `net.Conn` unblocks a blocked `Read`, not a blocked channel send.** Two different block shapes on the same pump need two different unblock primitives; conflating them (e.g. trying to make one signal cover both) doesn't work.
- **Terminal-vs-per-iteration signal separation**: when a bridge already has a per-iteration cancel channel, a *new* terminal shutdown signal must be a distinct field, not a reuse of the iteration one — the lifecycle semantics (closed-once-forever vs. closed-and-recreated-per-restart) are incompatible.
- **Lock-order rule for conn cleanup under a shared mutex**: snapshot/mutate the tracked set under the lock, always `Close()` conns after releasing it. Applies anywhere a `net.Conn` set is guarded by a mutex also taken by a per-conn cleanup goroutine.

## Lessons learned

(from the PR body)

- Closing a `net.Conn` interrupts a blocked `Read` but **not** a blocked channel send — the two pump block points needed two independent unblock mechanisms (conn close vs. a terminal signal the send selects on).
- The shutdown signal must be distinct from the per-iteration `iterCancel`: `iterCancel` closes on every child exit (restarts included), so reusing it for the send-abort would tear the attach down on every restart backoff.

Code review (PASS, no MUST/SHOULD-FIX) flagged one non-blocking NIT: `TestBridge_RestartDoesNotAbortAttach`'s comment overclaims what it guards (its pump is read-parked, not send-parked, so it wouldn't actually catch an `iterCancel`-keyed send bug) — `TestBridge_ShutdownUnblocksSendParkedPump` is the test that actually pins that property. Not corrected in code; noted here for anyone reading that test's comment at face value.
