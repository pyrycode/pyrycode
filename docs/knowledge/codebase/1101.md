# #1101 — `request_snapshot` degrades to `msgSnapshotOffline` on the stream-json path

**Size:** XS. One production file (`cmd/pyry/relay.go`, +17/-1 lines), one test file (`cmd/pyry/relay_test.go`, +42). No `internal/relay` change. Security-sensitive (existence-oracle ordering), verdict PASS.

## What shipped

A new unexported helper, `screenSnapshotterOrNil(sup *supervisor.Supervisor) relay.ScreenSnapshotter` in `cmd/pyry/relay.go`, used at the one call site that wires the `V2SessionConfig.Snapshotter` field:

```go
Snapshotter: screenSnapshotterOrNil(w.sup),  // was: Snapshotter: w.sup,
```

The helper returns a genuine `nil` when `sup == nil`, otherwise passes `sup` through unchanged. That's the entire fix — a ~4-line body plus doc comment.

## The bug

`Session.Supervisor()` type-asserts the stored `sessions.Runner` to `*supervisor.Supervisor` and returns `nil` on the stream-json bootstrap path (established by #1077; the stream-json runner is `*streamsup.Runner`, not `*supervisor.Supervisor`). Assigning that nil pointer directly to the `Snapshotter ScreenSnapshotter` interface field produces a **non-nil interface holding a nil pointer** — a classic Go typed-nil-in-interface trap. `handleRequestSnapshot`'s `m.cfg.Snapshotter == nil` guard (`internal/relay/v2session_replay.go:66`) then evaluates false, the handler falls through to call `ScreenSnapshot()` on the nil receiver, and `supervisor.ScreenSnapshot()` panics dereferencing `s.sessMu` on its first line.

The panic was latent in production: `sessions.New` is constructed with no `RunnerFactory`, so `w.sup` is always a real, non-nil supervisor today. This ticket is the preparatory guard for when the stream-json toggle lands and `w.sup` can actually be nil at request time.

## Why no `internal/relay` change

`handleRequestSnapshot` already had the right control flow — `KnownConversation` gate first (`v2session_replay.go:59`), then a nil-`Snapshotter` arm (line 66) returning `msgSnapshotOffline` / `CodeServerBinaryOffline`. The gap was purely in `cmd/pyry`'s wiring: it needed to hand the handler a *genuine* nil, not a typed one. Routing into the existing post-gate offline arm — rather than inventing a pre-gate short-circuit — is also what keeps the security property intact (below).

## Security: gate-before-degrade

The reason this XS ticket carries `security-sensitive`: a naive fix that short-circuited the offline reply *ahead of* the `KnownConversation` gate would leak a conversation-existence oracle to a remote, unauthenticated-for-that-conversation caller (foreign id → offline instead of not-found → "this conversation exists but has no live screen"). The fix here doesn't touch the gate or add any pre-gate branch — it only changes what value flows into the *existing* post-gate `Snapshotter == nil` check. Pinned by the pre-existing `"foreign conversation rejected"` test (`internal/relay/v2session_test.go:3790`), which uses a **live** snapshotter and still asserts `CodeConversationNotFound`, proving the gate runs first regardless of Snapshotter state.

## Patterns established

- **Convert typed-nil-in-interface at the wiring boundary, not at the consumer.** When a concrete-typed value that can be a nil pointer (here, `*supervisor.Supervisor` from `Session.Supervisor()`) is about to be assigned into an interface field, add a tiny `xOrNil` helper at the assignment site rather than teaching the consumer (`handleRequestSnapshot`) to special-case a typed nil. Keeps the fix in the one file that owns the interface conversion and leaves the consumer's `== nil` check meaningful.
- **Sibling wiring sites with the same trap, deliberately left unguarded.** `cmd/pyry/relay.go`'s `SessionStarter: w.sup` and the modal resolver's `w.sup` argument assign the same typed-nil-prone value and would panic on the stream-json path today if exercised. Out of scope for this ticket (Scope Discipline — this ticket touches only the `Snapshotter` seam); future stream-json integration slices (#1078 family) need the same `xOrNil` treatment before those verbs can safely reach the stream path. See the [sessions-package.md typed-nil-in-interface note](../features/sessions-package.md#runner-interface--runnerfactory-1077) for the general trap description.
- **Test the interface-nil property, not the assignment.** `TestScreenSnapshotterOrNil` asserts `got == nil` / `got != nil` on the helper's return value — the property a direct `Snapshotter: w.sup` assignment would fail — rather than asserting anything about `w.sup` itself. This is the shape of test that would have caught the bug before it shipped.

## Lessons learned

From the PR body (#1128):

- Typed-nil-in-interface trap: `Session.Supervisor()` returns a typed nil for stream-json runners; wrap it at the interface boundary (`x == nil → return nil`) so the consumer's optional-seam nil-check fires. The genuine-nil assertion (`got == nil`) is what a direct assignment fails.

Otherwise the implementation matched the architect's design (helper name, signature, call site) exactly, and the existing `internal/relay` test coverage (`v2session_test.go:3790`, `:3835`) was sufficient to pin both ACs without any new relay-level test.
