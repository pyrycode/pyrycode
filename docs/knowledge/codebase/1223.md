# Ticket #1223 — Deterministic trigger for a claude background handle under `pyry agent-run`

Adds `internal/e2e/realclaude/background_trigger_probe_test.go`, an opt-in evidence
probe (`PYRY_PROBE_BACKGROUND_TRIGGER=1`) that settles which lever deterministically
makes claude return a background handle under `pyry agent-run`. **The answer:
`BASH_DEFAULT_TIMEOUT_MS` set low, 7/7 identical fires on claude 2.1.220.**
#1224–#1227 are all natively blocked-by this ticket and are specified against this
trigger instead of the model's discretion. No production code changes — the
deliverable is evidence (posted on the issue) plus the kept probe file.

## Implementation

- **The test owns the in-flight window instead of hoping claude picks a slow
  command.** `holdProbeFIFO` `mkfifo`s a FIFO and blocks a goroutine in
  `os.OpenFile(path, os.O_WRONLY, 0)`; claude's `Bash → cat <fifo>` blocks on the
  read end. Both opens rendezvous with no poll lag, and the command **cannot
  complete on its own** — the write end is released only in `t.Cleanup` and never
  leaves the helper (never returns the `*os.File`). So a `tool_result` matching the
  tracked `tool_use`, observed while the write end is still held, is a **structural**
  signal that claude ended the call itself — not a match against claude's result
  prose, which is the fixture treadmill #563 and #1219 each paid for once. The same
  property removes the timing race from AC5's `ps` snapshot: taken synchronously at
  the observation point, with pyry still running.
- **Liveness is a `cmd.Wait` channel, not `Signal(0)`.** The spec offered
  `Signal(syscall.Signal(0))` as the cheaper option; a `Signal(0)` on an
  exited-but-unreaped direct child reports success (a zombie answers it), which
  would have silently evidenced "snapshot taken during the turn" for a run that had
  already ended — the exact AC5 property being asserted. `probeWaitForDirectChild`
  and the wait-goroutine close a channel instead.
- **Row table, one env delta per row, `t.Run` subtest per rep:** `default-only`
  (`BASH_DEFAULT_TIMEOUT_MS=5000`, 3 reps), `max-only` (`BASH_MAX_TIMEOUT_MS=5000`
  alone, 1 rep), `both` (both set, 3 reps), `disabled` (both +
  `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`, 1 rep — the free negative control), and
  `run-in-background` (no env; prompts the model for `run_in_background: true`, the
  AC4 comparison target, not a determinism candidate since the model fills it in).
  Each subtest gets its own `t.TempDir()`, `t.Setenv`, and FIFO — no sharing.
- **Three-valued classification, no prose matching:** `fired-background` (matching
  `tool_result` while the write end was held, and `cat` present in the `ps`
  snapshot as a live descendant), `fired-other` (matching `tool_result`, `cat`
  absent — claude bounded and killed the call), `did-not-fire` (no matching
  `tool_result` within the deadline). `command-never-ran` is a separate outcome for
  "the model never issued the Bash call."
- **Env-arrival control, model-free.** `probeReadLeverEnv` reads the three lever
  variable names out of the claude child's own environment via `ps -Eww -p
  <claudePid>` (never the model), separating "the variable never reached claude"
  from "claude ignored it" without spending a live turn. This is what makes
  `max-only`'s `did-not-fire` interpretable as attribution evidence rather than a
  tooling gap: the OS-level read confirmed `BASH_MAX_TIMEOUT_MS=5000` *was* in
  claude's environment.
- **Redaction is structural, not a reviewer's judgment call.** `probeLeverVars` is
  an explicit three-name allowlist; the claude child's real environment carries
  `CLAUDE_CODE_OAUTH_TOKEN`/`ANTHROPIC_API_KEY`, so the helper extracts by name and
  never dumps the environment wholesale. Same discipline for the workdir listing
  (names only) and pyry stdout/stderr captures (`truncate`d).
- **Every helper is probe-local by design**, including near-duplicates of
  `sigterm_mid_tool_use_test.go` helpers (`syncBuffer`, the descendant walk, the
  session-id poll) — that file was being rewritten by PR #1222 (open at
  implementation time), so ~40 LOC of deliberate duplication bought branch
  independence rather than a merge collision with zero benefit to this probe.

## The answer

`BASH_DEFAULT_TIMEOUT_MS` set low, alone, is the deterministic trigger: **7/7
firing reps** across every row that carries it (`default-only` 3/3 + `both` 3/3 +
1 dev-run rep), all identical (`fired-background`, `toolUseResult.timedOutAfterMs:
5000`, `backgroundTaskId` present). `BASH_MAX_TIMEOUT_MS` alone does **not** fire —
it caps what the model *may* set, and the model set no `timeout` field in any of
the ten-plus live turns run across the whole ticket. That `did-not-fire` is the
attribution evidence for AC2: it confirms the ticket body's "neither variable alone
covers both branches" reading over the #1219 architect's "the ceiling is the one to
test" conclusion — the default is exactly what applies in the no-model-`timeout`
branch, and that branch is the one that broke determinism on 2026-07-28.

The negative control (`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`) **split the
mechanism rather than confirming it**: the 5s timeout still expired, but the
command was SIGTERMed (`Exit code 143`, `is_error: true`, no `backgroundTaskId`,
`cat` gone from the process tree) instead of backgrounded. So "the timeout expires"
and "the command is moved to the background" are two separately observable steps,
and the env var under test drives only the first.

**AC4 — the two background paths are distinguishable, but only on one surface.**
Timeout-expiry and model-set `run_in_background` produce an identical
`backgroundTaskId`, identical `tool_result` structured fields
(`is_error: false`/stdout/stderr/interrupted), and a byte-identical
`pyry → claude → zsh → cat` detached-group process tree. Only
`toolUseResult.timedOutAfterMs` separates them — `5000` on the expiry path,
absent on the model-set path — alongside the `run_in_background: true` flag's
presence/absence in `tool_use.input`, which corroborates it from the request side.
This is the one line #1224–#1227 need:

```
toolUseResult.timedOutAfterMs == 5000   →  expiry path
toolUseResult.timedOutAfterMs  absent   →  model asked for it
```

**AC5 — one operator-run `ps -axo pid=,ppid=,pgid=` snapshot, taken during the
turn** (`snapshot_taken_during_turn: true`, self-evidenced from the `cmd.Wait`
channel), shows the backgrounded `cat` as a live descendant two process-group
levels below pyry, detached from claude's own group — the #565 shape. Recorded
without conclusion; #1224 reads the process table, #1225 the turn accounting,
#1226 the output file location, #1227 the interactive surface.

Full envelopes, per-lever table, and the complete AC1–AC5 record are posted on the
issue: [results](https://github.com/pyrycode/pyrycode/issues/1223#issuecomment-5109558101),
[AC4 comparison](https://github.com/pyrycode/pyrycode/issues/1223#issuecomment-5109558371),
[operator live-gate PASS](https://github.com/pyrycode/pyrycode/issues/1223) (final
comment, 2026-07-29).

## Patterns established

- **Invert who owns the in-flight window to get a structural (not prose-matched)
  discriminator for "did claude end this call on its own."** Ported from #1219's
  fixture design and now proven reusable across two tickets: hold a FIFO's write
  end open so the command the model runs cannot complete except by the test's own
  release. Any observation that happens *before* release is therefore attributable
  to claude, not to the command finishing. Reach for this shape whenever a probe
  needs to observe claude's behaviour on a still-running subprocess without racing
  a model-chosen timeout.
- **A negative control can split a mechanism into two observable steps instead of
  just confirming one.** `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` was specced as a
  yes/no check; it came back showing "timeout expiry" and "backgrounding
  disposition" are separable, which only became visible because the classifier
  read the **process tree**, not just the `tool_result` text. When designing a
  negative control, instrument enough surfaces that a partial effect is
  distinguishable from no effect.
- **A `Signal(0)` liveness probe is unsound for "still running" on a direct child**
  that may be unreaped — it answers success for a zombie. Prefer a `cmd.Wait`
  goroutine closing a channel when the liveness result is itself load-bearing
  evidence (here, AC5's "during the turn" claim), not just a convenience check.
- **When a design gate depends on a fact about production routing that can change
  underneath the ticket, verify it doesn't silently invalidate the gate.** The
  `both-streamjson` fallback row was gated to run only if the terminal-path rows
  came back `did-not-fire`, on the assumption that `pyry agent-run`'s default is
  the ptyrunner (terminal) path. That assumption held at spec time but the
  dispatcher forks switched to the headless stream path on 2026-07-25, before the
  operator's live run. The operator ran the fallback row anyway despite the gate
  saying not to, and it fired identically — worth checking whether a probe's
  internal gating logic still matches the surface it is meant to protect before
  trusting a "not attempted" state.

## Lessons learned

From the PR body (#1228) and code review (PASS, 0 MUST FIX / 2 SHOULD FIX / 4 NIT):

- **A `Signal(0)` liveness probe reports an unreaped direct child as alive.** The
  spec's cheaper suggestion would have falsified the very "snapshot taken during
  the turn" property AC5 exists to evidence. Fixed with a `cmd.Wait` goroutine +
  channel before this shipped — see § Patterns established above.
- **A negative control can split a mechanism rather than confirm it.**
  `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` still let the 5s timeout expire but
  changed the disposition from background to SIGTERM — visible only because the
  classifier read the process tree in addition to the `tool_result`.
- **The `did-not-fire` row is what makes the firing rows mean something.**
  `max-only` not firing is the evidence that the *default*, not the *ceiling*, is
  the operative lever — interpretable as attribution (not ambiguity) only because
  the env-arrival control confirmed the variable had reached claude's environment.
- **`backgroundTaskId` does not discriminate the two background paths;
  `toolUseResult.timedOutAfterMs` does.** Both paths produce an identical handle
  and an identical detached-group process tree.
- **Two SHOULD FIX findings shipped unfixed, deliberately, under the 3-finding
  merge threshold** (code review PR #1228#issuecomment-5109769378) — worth reading
  before #1224–#1227 re-stage this probe under different prompts, which is where
  both gaps are most likely to bite:
  - `probeWaitForBashToolUse` (`:762`) returns the **first** `tool_use` with
    `Name == "Bash"`, regardless of `input.command`. If the model issues any other
    Bash call before the FIFO `cat` (a path check, a retry), its fast-returning
    `tool_result` is misclassified as `fired-background` with nothing actually
    backgrounded. The only guard today is a system-prompt nudge ("use the Bash
    tool exactly once") — a stochastic protection for a claim the design's whole
    point is to make structural. `rec.FIFOPath` is already available at the call
    site; gating on `strings.Contains(command, fifoPath)` was identified as the
    fix but not applied (ten live reps never hit it).
  - `probeReadLeverEnv`'s `if !hit` fallback (`:1030-1044`) collapses to
    `<unread>` (a *read-failure* report) in exactly the case — no lever variable
    present in the `ps` output at all — that the doc comment (`:1000-1001`)
    promises reports as `<absent>` (a *finding*). The `run-in-background` row
    (which sets no lever env) always takes this path and always reports
    `<unread>` even though the read succeeded. A future forwarding regression that
    silently drops a variable would misread as tooling failure instead of the
    diagnosis. Fix identified (key the "did the read succeed at all" check off a
    variable guaranteed present — `HOME=`/`PATH=` — rather than off any lever
    name) but not applied.
- **`docs/knowledge/features/e2e-realclaude.md`'s Max-plan token extraction recipe
  was used and then deliberately discarded** — the developer stashed the extracted
  OAuth token at mode `0600` for the live rows and deleted it afterward, swept
  artifacts to confirm it never reached an issue comment or stdout capture.
