# Ticket #1343 — Probe rig: assemble the eight-field staging record from the transcript reading and the rig's facts, and return its gate's decision

The join that had no name. `finTranscriptFill` (#1304) already reads three of
`finOutcomeStaging`'s eight fields from a run's transcript; the pin reduction
(#1338) and the staged-command declarations (#1342) already supply the
material for the other five. Nothing called all of it in one place — the only
thing filling those five today was `finTranscriptStagedCaller`, a #1304 test
fixture whose hardcoded `PinMatchCount: 1, PinWantCount: 1` is correct for its
own file and wrong for the rig, whose real expectation is `finLivePinWantRows
= 2`. An assembly that inherited that `1` would send every correctly-staged
live run to `finOutcomePinCountUnexpected`, burning a live claude turn per
attempt. This ticket ships `finLiveAssembleStaging`, the one function that
closes that gap, and one offline test proving the join forwards its inputs
rather than re-deriving or fixing them.

New file only: `internal/e2e/realclaude/finding_live_assembly_test.go`
(`//go:build e2e_realclaude`, 428 lines). No existing file edited, no
production code, no live run, no `pyry` spawn, no real claude, no `ps` exec,
no FIFO. Imports `testing` and `time` only.

## Implementation

- **`finLiveAssembleFacts`** — the five caller-side fields of
  `finOutcomeStaging`, and only those five: `StagedCommand`, `RendezvousDone`,
  `PinScanErrored`, `PinMatchCount`, `PinWantCount`. It is `finTranscriptReading`'s
  (#1304) mirror image — 3 + 5 = 8, visible from both sides — and is a struct
  rather than five flat parameters specifically because a call site
  transposing two adjacent bools (`RendezvousDone` / `PinScanErrored`) would
  otherwise compile and silently report the wrong outcome for a correctly
  staged run. No JSON tags, the rule `finTranscriptReading` and
  `finOutcomeStaging` both state at themselves: it carries `StagedCommand`,
  which embeds a `t.TempDir()`-derived path on a live run.
- **`finLiveAssembleStaging(t, workdir, sessionID string, facts
  finLiveAssembleFacts, toolUseTimeout, resultTimeout time.Duration)
  finOutcomeResult`** — calls `finTranscriptFill` with `facts.StagedCommand`
  as the *only* source of the staged string (closing the two-consumer drift
  hazard between the gate's identity arm and the fill's own `call.Command ==
  staged` guard structurally rather than by care), builds `finOutcomeStaging`
  as one keyed composite literal with all eight fields present and every
  right-hand side either `r.X` or `facts.X` — no literal anywhere — and
  returns `finOutcomeStagingGate`'s result unchanged. Not pure: it inherits
  `*testing.T`, a filesystem read and a poll-to-deadline from
  `finTranscriptFill`; `finOutcomeStagingGate` itself is the pure half.
  Returns `finOutcomeResult` only, not the eight-field record — handing a
  caller the record would carry two captured strings past the one publishable
  type in this family for no stated need.
- **`finLiveAssembleContractWant = finLivePinWantRows + 1`** — a want no live
  driver ever emits, derived rather than written as a literal so it can never
  coincide with `finLivePinWantRows`. Backs the one test row that catches an
  assembly that forwards the match count but fixes the want internally —
  every other row lets that mis-assembly through.
- Neither `finLivePinReduce` nor `finLivePinWantRows` appears in the
  assembly's body (both are #1340's, the driver, to call); `finLivePinWantRows`
  appears only as a row value in the test. `finTranscriptStagedCaller`,
  `finOutcomeStagedBase` and `finOutcomeGateCases` are called nowhere in the
  file — calling any of them would make this a copy of an already-shipped
  test.

## Tests

`TestFinLiveAssembleStagingForwardsTheCounts` (AC2) — one correctly-staged
synthetic transcript, built once in the parent from the shipped
`finTranscriptBashBlock` / `finTranscriptAssistantLine` / `finTranscriptResultLine`
and `finLiveStageCommand(finLiveStageFixtureFIFOPath)` (#1342's real staged
literal, not the gate's `sh -c … ; exit 0` stand-in), read by all four rows so
"the counts are the only thing that varies" is literal rather than asserted.
Four rows, writing `w` for `finLivePinWantRows` and `c` for
`finLiveAssembleContractWant`:

| row | match | want | expected | sole kill |
|---|---|---|---|---|
| 1 | `w` | `w` | ready | an assembly that drops the counts entirely |
| 2 | `w-1` | `w` | unexpected | an assembly inheriting the fixture's `1, 1` |
| 3 | `0` | `0` | unexpected | an assembly substituting its own `match == want` for the gate |
| 4 | `c` | `c` | ready | an assembly that forwards the match but fixes the want internally |

Every assertion reads `finLiveAssembleStaging`'s return value; none goes to
`finOutcomeStagingGate` directly, since `finOutcomeGateCases` (#1284) already
ships the `2/2 → ready`, `1/2 → unexpected`, `0/0 → unexpected` mapping and
re-asserting it here would be a second copy under a new prefix. `t.Errorf`
names the two counts and the two outcome values freely and prints the staged
command in no form — the lengths-only house rule doesn't even apply, since no
message here needs to refer to the command at all.

Verification: `make e2e-realclaude` green; `go test -race -tags e2e_realclaude
-run '^TestFinLiveAssemble' -v` — all four subtests PASS, none SKIP; `go vet
-tags e2e_realclaude ./internal/e2e/realclaude/` clean (untagged `make check`
never analyses this file). Mutation evidence via `go test -overlay` — five
mis-assemblies, each producing exactly its predicted REDs: inherits the
fixture's `1, 1` (RED on rows 2+3); ignores its inputs, both counts zeroed
(RED on rows 1+4); copies the want into the match count (RED on row 2);
forwards the match, fixes the want internally (RED on row 4); substitutes its
own `match == want` for the gate (RED on row 3). Rows 1 and 4 reaching
`finOutcomeReadyToClassify` also proves the composition is non-vacuous — that
value is unreachable unless every upstream gate arm cleared, so the rows
prove the transcript is genuinely read through the fill rather than passing
on a broken read.

## Patterns established

- **A caller-side facts struct as the transcript-reading type's mirror
  image**, sized so the two together equal the record's full field count and
  named field-for-field with it. Makes an eight-field composite literal
  auditable by three mechanical rules (all keys present, no literal RHS,
  name-for-name) instead of by inspection.
- **A non-producible test row's constant is derived from the real one it must
  never equal (`real + 1`), not written as an independent literal.** The
  derivation is the guard: it makes "never coincides with the driver's value"
  structural, so a later edit that "fixes" the row by pinning it to the real
  constant is caught by inspection rather than silently deleting the only
  check that a forwarded value actually travels.
- **Two mis-assemblies structurally unreachable by any value-only test — a
  count swap inside the literal, and hardcoding the read-side fields at their
  staged values — are stated in the file's own header as accepted, with the
  reason, rather than chased with duplicate rows the ticket's own AC forbade
  reproducing.** A reader who later "discovers" the gap is told up front why
  the obvious fix (copying `TestFinTranscriptFill`'s decoy/wrong-command rows)
  is exactly what this ticket was scoped not to do.
- **`WithWorktree`'s containment role is stated as "both ends of this file's
  I/O resolve `HOME`", not just "we write a transcript".** The security
  review's MUST FIX on the first draft was exactly the gap between those two
  framings — the correct one names the bad outcome (`writeFixtureLines`
  landing in the operator's real `~/.claude/projects/…` tree) rather than
  asserting a narrower true-but-incomplete claim ("no environment is read").

## Lessons learned

(From the PR body; see PR #1345.)

- **The mutation matrix was worth running rather than reasoning about.** It
  is what confirms rows 2, 3 and 4 are each some mutant's *sole* RED, so no
  row is decorative. Row 1 shares its REDs with row 4 and is kept for a
  different reason — it is the only input a live driver produces, and the
  only row proving the eight-field composition reaches the pass-through at
  all.
- **`go test ./internal/e2e/realclaude/` (untagged, package named explicitly)
  fails with `build constraints exclude all Go files`** — every file in the
  package is behind `e2e_realclaude`. Under `./...` the package is skipped
  silently, so `make check` is unaffected. Pre-existing, and worth knowing
  before reading that error as a regression caused by this ticket.
- **Code review flagged one NIT, non-blocking:** `finLiveAssembleStaging`'s
  `toolUseTimeout, resultTimeout time.Duration` are two adjacent,
  transposable parameters of the same type — the one instance in this file of
  the hazard class its own header argues against when justifying
  `finLiveAssembleFacts` over five flat parameters. Kept anyway because it
  mirrors `finTranscriptFill`'s shipped signature field-for-field and
  diverging would be worse. Live, a transposition would swap a 30 s and a
  45 s deadline; offline both rows pass the same `finTranscriptTestDeadline`,
  so no row here can catch it. Recorded so a future edit to this signature
  knows the asymmetry was seen and accepted, not missed.
