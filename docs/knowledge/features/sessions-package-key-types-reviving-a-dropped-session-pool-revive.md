# Reviving a dropped session: `Pool.Revive` (#1487)

`Pool.New` materialises exactly one `*Session` from `sessions.json` — the bootstrap (`pickBootstrap` is the only reader of `reg.Sessions`). Every other entry is parsed and held in `Pool.dormant` rather than materialised; before #2448 it was discarded outright and erased by the first `saveLocked`, which is what made a restart-then-touch revive start from nothing. A conversation whose `CurrentSessionID` points at one of them is left with a healthy binding onto a session the pool does not have, until something touches it.

```go
func (p *Pool) Revive(id SessionID, label, spawnDir string) (*Session, error)
```

**No `context.Context` — that absence is the API contract.** `Revive` registers the session and returns; it never spawns claude and never blocks. The returned `*Session` is at `stateEvicted` with an open `activeCh` and a closed `evictedCh`, which is byte-for-byte the shape an idle-evicted session has, so it respawns on the next `Pool.Activate` through the **existing** lazy-respawn path. Reviving introduces no new lifecycle path; the caller owns the `Activate`.

**Shared core with `GetOrCreateIn`.** Both route through the unexported `materialise(id, label, spawnDir string, settings settingsSource) (*Session, took bool, error)`, which holds the whole `ValidID` → build → register → `saveLocked` → skip-set → `runGroup` guard → `g.Go` sequence described under [§ Pool.GetOrCreate](#poolgetorcreate-13b) — including every rollback. `settings` used to be a value the caller evaluated as an argument; since #2492 it is a closure `materialise` calls itself, which is what lets it read the source a second time inside the critical section that retires the dormant entry — see the next section. Since #2448, registering an id inside `materialise` also **retires** any `Pool.dormant` entry for it, so the pool holds exactly one source of truth per id. This is why the retire lives in `materialise` rather than only in `Revive`: `GetOrCreateIn` reaches the same code with a caller-supplied id (#1518) and can land on one that is dormant, so a session minted through `GetOrCreateIn` onto a previously-dropped id must retire that id's dormant entry too, or it would sit alongside the now-live session and reappear on a later save after the session was removed. Both of `materialise`'s rollback paths restore the entry they retired, so a failed registration leaves the registry byte-identical to before the call — see `pool_dormant_entries_test.go`, under Tests below. Exactly **two** things differ between the two callers. The first is what happens after: `GetOrCreateIn` calls `Activate` on the register path (and, per its long-standing contract, *not* on the take path), `Revive` calls it never. That take/register split became the `took` flag rather than an inline early return, so `TestPool_GetOrCreate_Take_DoesNotActivate` pins it — a `Revive`d session is the only fixture that can hold a registered-but-never-activated session to assert against. The second is the `settings` argument, below.

**Model and effort restored, posture still zeroed (#2448).** `materialise` takes the settings as a `settingsSource` and calls it itself, twice, rather than forwarding a value the caller computed — the caller still makes the policy decision (which source to hand over), `materialise` only decides *when* it is read. The first read is provisional, under a brief `Pool.mu.RLock`, and seeds `buildSession`'s construction argv; the second is authoritative, inside the same `Pool.mu.Lock` critical section that retires the dormant entry (#2492), and on the rare path where a concurrent `Pool.UpdateDormantSettings` makes the two disagree, its value replaces the built session's stored settings and installed argv before the session is published. See [sessions-package-concurrency.md](sessions-package-concurrency.md) for the lock-scope argument. `Revive` is the caller, and since #2448 it passes `Pool.revivedSettings(id)` rather than the zero value: a **field-by-field** literal carrying `id`'s own dropped `registryEntry.Model` and `.Effort` and nothing else — built the same shape as `mintSettings` above, for `mintSettings`' own reason. Excluding `YOLO` and `PermissionMode` structurally, by never naming them in the literal, means the posture cannot leak by a later edit deleting a clearing statement, and a field added to `registryEntry` in future is not inherited until someone opts it in. So a revived session's argv still carries no `--dangerously-skip-permissions` even if the dropped entry persisted `yolo: true` — a phone-set permission bypass still does not survive a daemon restart, exactly as before #2448 — but `--model` and `--effort` now reflect what the channel was visibly set to, instead of falling back to claude's defaults. An id with no dormant entry, or an entry that persisted neither field, revives to the zero value exactly as every revive did before #2448.

Restoring model and effort needed no read of a discarded `registryEntry`, because #2448 stopped discarding it: `Pool.dormant` keeps every entry `loadRegistry` returned that the pool did not materialise, `saveLocked` writes it back beside the live sessions, and `materialise` retires the entry it takes over (both of its rollback paths restore it, so a failed revive leaves the registry byte-identical). This is the amendment to [ADR 035](../decisions/035-lazy-revive-not-registry-rehydrate.md), which had decided a revived session carries zero settings outright — narrowed to say the posture only, not model and effort, which carry no privilege.

That parameter is also what keeps `Revive` off the mint path's inheritance (#1575): `GetOrCreateIn` passes `Pool.mintSettings` (the bootstrap's model and effort), `Revive` passes `revivedSettings` (the id's own persisted model and effort, never the bootstrap's) — so each caller states its choice where the contract justifying it already lives, and a revived session still never inherits settings it was not itself set to. Reading `mintSettings` *inside* `materialise` would be a one-line change that silently hands a revived session the bootstrap's model and effort — a third behaviour with its own security reasoning to redo. `TestPool_Revive_DoesNotInheritOperatorSettings` reddens under exactly that mutation (verified via `go test -overlay`), and it and the two `runner_config_posture_test.go` revive arms revive ids with no persisted entry, so #2448 left them passing unchanged.

**`spawnDir` is opaque here too.** Same contract as `CreateIn` / `GetOrCreateIn`: used verbatim, never validated, canonicalised, or trust-checked pool-side; empty falls back to `tpl.WorkDir`. The caller supplies a pre-resolved `$HOME`-confined realpath. SECURITY: it is a phone-influenced workspace path, so `Revive` must not log it. The consumer — `sessionRouter.revive` in `cmd/pyry` — re-runs `resolveSpawnDir` at revive time rather than trusting the recorded value, because a path valid at mint time can become an escape before the restart; see [conversation-session-binding.md § Restart scope](conversation-session-binding.md#edge-cases--limitations).

Since [#1475](conversation-session-binding.md#edge-cases--limitations), `resolveSpawnDir` has a second caller taking the identical posture: `activeSessionStarter.resolveSpawnDir` re-runs it when a `new_session` rotation reads the same conversation's recorded `Cwd`, wiring the result onto `(*streamsup.Runner).SetSpawnWorkDir` rather than into a `Revive` call — a live session never goes through `Revive` again. `Revive` and rotation are now the two production readers of a conversation's recorded workspace; see [the `new_session` seam's workspace re-read](v2-session-manager-state-machine-inbound-new-session-sessionstarter-seam.md#workspace-re-read-on-rotation-1475).

**Tests** (`pool_revive_test.go`): registers-without-spawning (Lookup pointer identity, `ChildPID == 0`, on-disk `lifecycle_state: "evicted"`), activates-normally (the child does come up), take-path-returns-existing, `spawnDir` threading both legs, `ErrPoolNotRunning` with a **byte-level** registry-unchanged assertion (the rollback re-persists), and `ErrInvalidSessionID`. That `ErrPoolNotRunning` assertion revived an id with no persisted entry for its whole life, so it was vacuous — nothing was in the registry for a rollback to corrupt. `pool_dormant_entries_test.go` (#2448) adds the dormant-id sibling, the first version of that assertion able to fail, and it did fail before `materialise`'s retire restored the entry on rollback. A byte-level "unchanged" assertion is only as strong as the fixture it runs against.
