# Drift detectors

The v1 type list appears three times: in the `Type*` constants block (`codes.go`), in the `inboundAppTypeSet` map literal (`envelope.go`), and in two test slices (`compat_test.go`). The triple-copy is **deliberate** — explicit drift detectors fail loudly in CI when a new constant lands without the corresponding map entry:

- `TestIsKnownAppType` — runs every v1 `Type*` constant through `IsKnownAppType` and asserts `nil` (catches "added a v1 `Type*` const, forgot the map").
- `TestInboundAppTypeSet_CoversAllExportedTypeConstants` — asserts every v1 application `Type*` constant is keyed in `inboundAppTypeSet`.
- `TestTypeConstants_V1V2Partition` (#454, extended #607/#617/#638/#647/#656/#701/#720/#707/#812/#813/#831/#844/#1007/#1074/#1393/#1386/#1405/#1616/#1704/#1726/#1752/#1962/#1895) — every exported `Type*` constant must be in `inboundAppTypeSet` **OR** in the test-local `v2OnlyTypes` allowlist; never both, never neither. The allowlist holds 44 entries and `inboundAppTypeSet` holds the 23 v1 application types (grew from #967's post-backfill-removal count with the four #887/#888 workspace-folder types), so the partition size assertion is `len(inboundAppTypeSet) + len(v2OnlyTypes) == 23 + 44 == 67`. Both counts move with every new v2 type or v1 addition — re-derive from `compat_test.go` rather than trusting a cached number here; this doc's own count has already drifted more than once (last corrected against #1895's landed `compat_test.go`). **This test does not itself fail on an unpartitioned constant — confirmed on #2052, not assumed.** `all` and `v2OnlyTypes` are hand-maintained literal slices, not derived from the source: a brand-new `Type*` constant added to `codes.go` and left off both lists moves the size assertion nowhere, so `TestTypeConstants_V1V2Partition` stays green. What actually reddens the build is the second, independent detector below — `cmd/pyry/relay_guard_test.go`'s `TestEveryInboundV2TypeHasHandler` Assertion #3, which walks every exported `Type*` constant from the AST of `codes.go` rather than a hand-written list. The `v2OnlyTypes` literal lives in the test rather than as an exported production symbol so production callers cannot accidentally import it for dispatch logic — v2 dispatch switches on individual constants, not on partition membership. **A second, independent drift detector lives outside this package**: `cmd/pyry/relay_guard_test.go`'s `TestEveryInboundV2TypeHasHandler` classifies every `Type*` constant into a handler bucket or `excludedTypes`; most outbound-only pushes get `"push"`, but the label column is free text checked only for membership (Assertion #3), so a type that doesn't fit — `TypeHello`'s `"handshake"`, `TypeAttachmentChunk`'s `"pending handler (#1744)"` — carries its own true reason instead of a borrowed one. #1074's spec named only the `compat_test.go` trio, and the developer had to discover this second detector at build time — see [codebase/1074.md](../codebase/1074.md) § Lessons learned. #1393 registered its three types in both detectors from the start; #1386 added its `excludedTypes["TypeThinkingProgress"] = "push"` entry in the same commit as the constant; #1405, #1616, #1704, #1726, #1752, #1962 and #1895 did the same for their own constants, each mandatory from the moment the constant exists rather than from the moment a later ticket emits it.

**None of the three `compat_test.go` registries can catch a wire-*string* typo — only a committed fixture can, confirmed by mutant run on #1895 rather than assumed.** All three (`TestIsKnownAppType`'s cases, `v2OnlyTypes`, and `TestTypeConstants_V1V2Partition`'s `all` slice) key on the constant's Go *symbol*. Mutating `TypeAttachmentStored`'s value from `"attachment_stored"` to `"attachment_saved"` moves consistently through all three and reddens none of them, because each one references the identifier and never re-derives the literal it holds. Only `TestAttachmentStoredPayload_RoundTrip`, reading the committed `testdata/attachment_stored.json`, catches a wire-string typo — a ticket that adds the three registry entries and skips a fixture round trip ships a type whose wire *value* nothing checks, even though its *membership* (v2-only, never in `v1TypeSet`, rejected by `IsKnownAppType`) is fully pinned.

**A complete-key-set test outlives a fixture regeneration that a round trip does not.** `TestAttachmentStoredPayload_WireKeys` marshals a freshly populated struct and asserts its key set is exactly `{attachment_id}` — it never reads a fixture. Adding an undeclared field to the payload reddens both it and `TestAttachmentStoredPayload_RoundTrip` the moment the field lands, but regenerating the fixture under that same change turns the round trip green again (the new field is now baked into the expected bytes) while the key-set assertion stays red. That is what makes a key-set pin, not a round trip, the right home for a "this payload exposes no host path" guarantee — the guarantee then survives whoever next regenerates the golden file without noticing what changed. See [Envelope types § v2 attachment-chunk vocabulary](protocol-package-constants-codes-go-envelope-types.md) for the sibling frame this reply answers.

**The `excludedTypes` classification key is whether a handler exists, not which direction the frame travels.** `TypeAttachmentChunk`'s case read as an exception while it sat in `excludedTypes["pending handler (#1744)"]`, because it's bidirectional; #1983's `TypeQuestionAnswer` / `TypeQuestionRefused` confirmed it's the general rule while they waited — both are genuinely, exclusively inbound, and still couldn't go in `inboundTypes`, because that bucket's Assertion #1 requires a live `dispatchAppFrame` case and #1983 shipped none (interception was #1984's). Filing a handler-less inbound type there fails by construction; filing it under `excludedTypes["push"]` would be false in the other direction, since it *is* inbound. Both sat in `excludedTypes` with their own true reason, `"pending handler (#1984)"`, following `TypeAttachmentChunk`'s precedent rather than the `"push"` block's — and, like `TypeAttachmentChunk` did once #1897 landed its case, both moved to `inboundTypes` as `"switch-intercepted"` once #1984 landed theirs. `TypeAttachmentChunk` itself moved from `excludedTypes` to `inboundTypes` when #1897 gave `dispatchAppFrame` its case, closing the example this paragraph used to cite in the present tense. See [Envelope types § v2 question-batch vocabulary](protocol-package-constants-codes-go-envelope-types.md) and [Question-batch payload § `QuestionAnswerPayload` / `QuestionRefusedPayload`](protocol-package-question-batch-payload.md#questionanswerpayload--questionrefusedpayload-1983).
- `TestErrorCode_Constants_MatchSpec` — exact-string match for each `Code*` constant against the spec's dotted string. Catches the "fat-fingered `protocol.unkown_type`" regression at the lowest possible cost.
- `TestCapability_Constants_MatchSpec` (`handshake_test.go`, #2020) — the same pattern applied to `Capability*` constants (`CapabilityInteractive`, `CapabilityQuestion`), added when the second one landed. Motivated by a real vacuity, not a hypothetical one: every existing capability-negotiation test in `internal/relay` passes the constant symbolically on both the advertise side and the expect side, so a fat-fingered wire value (e.g. `"questoin"`) would be internally self-consistent and green in all of them while breaking the cross-repo contract silently. A capability string is compared against a literal outside this module (the client repo, the spec table), which is what makes the drift detector worth its cost here even for a two-member set. See [handshake / control payloads § `Capabilities`](protocol-package-handshake-control-payloads.md) and [ADR 037](../decisions/037-capability-strings-not-version-numbers.md).

Reflection over `go/types` was considered and rejected — heavier than explicit assertions for a closed set. If the v1 type set ever grows past ~50 entries (no plausible path under the protocol's versioning policy), revisit.

**`go test -overlay` cannot mutation-test any guard in `cmd/pyry/relay_guard_test.go`'s `parseGoFile` family (#1980).** `TestEveryInboundV2TypeHasHandler` and every AST-reading structural guard built on the shared `parseGoFile` helper call `parser.ParseFile` against the file on disk at test runtime — the overlay JSON only rewrites what the *compiler* reads when building the test binary, so a mutant written into `relay.go` under an overlay is invisible to these guards even while `go build` sees it. #1980's own guard mutants "passed" clean under an overlay before anything was wrong with them; the false green was only caught by writing each mutant over the real file and restoring it in the same shell invocation. Any future guard added to this family inherits the same property — mutation-test it by editing and restoring the real file, never by overlay.

**The classic per-type `env`-round-trip test cannot pin a tag-level property on the payload struct, and this is invisible by reading — confirmed by overlay mutant on #2036.** The pattern most of this package's `*_test.go` files use — unmarshal `raw` into `Envelope`, unmarshal `env.Payload` into the typed payload, assert fields, re-marshal `env`, compare bytes against `raw` — never calls `json.Marshal` on the *payload* struct at all: `env.Payload` is `json.RawMessage`, so `json.Marshal(env)` re-emits the fixture's own untouched bytes, and every one of the payload's struct tags (`omitempty`, a renamed key, a dropped field) goes completely unexercised. #2036 wrote exactly this comment as fact in `SendMessagePayload`'s plan before checking it, then found by `go test -overlay` (not by reading) that dropping `omitempty` from `AttachmentIDs` reddens `TestSendMessagePayload_ZeroValue_KeyAbsent` alone — `TestSendMessagePayload_RoundTrip`'s byte comparison stays green throughout. Only a test that itself calls `json.Marshal`/`json.Unmarshal` on the bare payload — `roundTripEnvelope` (`interactive_test.go`), a `WireKeys` key-set assertion, or a dedicated `ZeroValue` case — exercises the tags. Do not cite an `env`-round-trip fixture test as evidence for a payload's wire-shape properties (`omitempty`, key renames, field drops) without checking which helper it actually calls; mutation-test the specific claim rather than assuming the family's most common test shape covers it.

**A multi-fact structural guard should run its message-bearing check before any check whose helper must `Fatal`.** #1980's guard ties three facts together with one `t.Helper()` returning a name (`soleRegistryMint`, which must `Fatal` on a shape mismatch since it has no fallback value to return) and two that report via `t.Errorf` and keep going. Ordered with the `Fatal`-capable check first, a mutant that breaks two facts at once only ever surfaces the least diagnostic message — arithmetic on a call count — because the test aborts before the second check runs. Ordering the `Errorf`-based checks first lets both facts speak on a mutant that breaks both, and the `Fatal`-only check stays as the backstop.
