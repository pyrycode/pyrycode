# Attachment envelope types

Split out of [Envelope types](protocol-package-constants-codes-go-envelope-types.md) — the `attachment_chunk` / `attachment_stored` / `request_attachment` family, split into its own document once the parent crossed the 50000-byte search-chunking cap.

**v2 attachment-chunk vocabulary** (#1752; cap + both-direction fixtures #1753, published contract #1751, reassembly #1741, storage #1743, dispatch #1897 (split from #1744), retrieval #2052/#2053/#2054, split from #1746):

```go
type AttachmentChunkPayload struct {
    ConversationID string `json:"conversation_id"`
    AttachmentID   string `json:"attachment_id"`
    Index          int    `json:"index"`
    TotalChunks    int    `json:"total_chunks"`
    Filename       string `json:"filename"`
    MimeType       string `json:"mime_type"`
    Size           int64  `json:"size"`
    SHA256         string `json:"sha256"`
    Data           []byte `json:"data"`
}
```

`ConversationID` (#2142) is meaningful on the upload leg only — the conversation the client means the bytes to land in. #2143 wired the validation: `internal/relay`'s `handleAttachmentChunk` gates it through the `KnownConversation` membership seam on every chunk, before it ever reaches `internal/attachments` or becomes a path component — see [Inbound `attachment_chunk`](v2-session-manager-state-machine-inbound-attachment-chunk-attachmentintake-seam.md) § "The conversation gate runs before the seam, on every chunk". Outbound (retrieval) it is emitted empty and a receiver ignores it, the same reason `AttachmentStoredPayload` and `HistoryPagePayload` carry none: a retrieval chunk is already correlated by `InReplyTo` to a `RequestAttachmentPayload` that named the conversation. It replaces a four-ticket-old published security argument — that the frame carried no `conversation_id` at all, so a client could not steer bytes into another conversation — which cost two operator-visible misfiles ([pyrycode-desktop#1076](https://github.com/pyrycode/pyrycode-desktop/issues/1076): an attachment added before a conversation's first message could never be stored; and send-in-A/send-in-B/return-to-A-and-attach filed the bytes under B). The trust level does not move: a paired client could already name any conversation on `send_message` and already fetch any conversation's file via `RequestAttachmentPayload`, so what the omission bought was never isolation between conversations, only the absence of a field. Confinement stays where it already was — registry validation plus `attachments.EnsureDir` refusing an escaping directory — and naming a conversation is still not authorization.

`TypeAttachmentChunk = "attachment_chunk"` is the first `Type*` constant in this package that is genuinely **bidirectional**: upload (client → daemon) and retrieval (daemon → client) ride the same frame, the settled anti-drift decision — one shape, not two built months apart against each other. `AttachmentChunkPayload` lives in the new `attachments.go` (the package's one-file-per-concern convention; `attachments_test.go` — cap constant and both-direction fixtures — is sibling #1753). No completion peer of `DebugBundleDonePayload`: `TotalChunks` rides every chunk, so a receiver knows the expected count from the first one, earlier than the bundle stream (whose chunks carry only `Seq` and need a terminal frame to learn a count at all).

- **The `SECURITY:` doc block is the deliverable, not a courtesy** — six blocked slices code against it because a single Go type here carries client-authored data inbound and daemon-authored data outbound and cannot itself say which. `Filename`/`Size`/`SHA256` are the claims a reader expects; `AttachmentID`/`Index`/`TotalChunks` are the ones whose falsification costs something (accumulator sizing, buffer placement, and the upload's storage key respectively) and had to be named explicitly rather than left implied.
- **Never allocate from a claim.** `TotalChunks` and `Size` are attacker-chosen integers — `make([][]byte, TotalChunks)` on a claimed 2³¹−1 is a multi-gigabyte allocation from one ~60 KB frame — so a receiver range-checks both before sizing anything. The doc block states that check as a **strict equality**, `TotalChunks == max(1, ceil(Size / bound))`, raw-over-raw against `MaxAttachmentChunkBytes` (§ below): only the equality bounds `TotalChunks` from above, since a maximum chunk size gives a *lower* bound on the honest chunk count and `TotalChunks >= ceil(Size/bound)` caps nothing; the `max(1, …)` is what resolves `Size == 0`, where the bare `ceil` gives 0 against the documented `TotalChunks >= 1`. The zero-byte question resolved to [`attachments-package.md`](attachments-package.md)'s #1769 — one chunk carrying zero bytes is complete and yields zero bytes, not an error and not permanently incomplete. **The equality form itself is now enforced, by `attachments.CheckDeclaration` (#1776, see [`attachments-package.md`](attachments-package.md) § "Admission layer")** — the price is accepted: a client whose own stride yields a conforming count is fine, but one that declares a count its stride can't produce is refused, which is not a regression given every non-final chunk is already obliged to carry exactly `bound` raw bytes.
- **`AttachmentID` is validated for canonical shape before it becomes a path component** (`conversations.ValidID` is the precedent named) and is explicitly **not a capability** — not secret, not unguessable, never the sole gate standing between a caller and a file. **`SHA256` is integrity, not authenticity**: the same party supplies bytes and digest, so a match proves the transfer wasn't corrupted and nothing about content safety; it must never become a content-addressed access token.
- **`Index`/`TotalChunks`, not `Seq`/`Total`.** `DebugBundleChunkPayload.Seq` carries a strict-succession contract the bundle receiver enforces (next `Seq` must equal the count already seen); this frame's receiver addresses by index and rejects duplicates/out-of-range instead of requiring succession, so reusing the name `Seq` would have imported a contract that isn't true here. `TotalChunks` rather than `Total` because a bare "total" beside a "size" on the same struct reads as a byte count.
- **`Data` never aliases a reused connection read buffer** — `encoding/json` allocates a fresh slice decoding a base64 field, so #1741 may retain `Data` without copying. A non-obvious contract worth stating once here rather than each consumer rediscovering it (surfaced by code review, not in the shipped doc block itself).

`excludedTypes["TypeAttachmentChunk"] = "pending handler (#1744)"` in `cmd/pyry/relay_guard_test.go` was the first entry whose label was neither `"push"` nor `TypeHello`'s `"handshake"` — proof the label column really is free text (Assertion #3 checks membership, never the value), not a closed enum a new entry must fit. The `"push"` neighbours all justify themselves with *this slice declares no inbound request verb*, which was **false** for `TypeAttachmentChunk` — the upload leg is inbound — so copying that reason would have shipped a false statement past a green `make check`. Filing it in `inboundTypes` instead would have failed Assertion #1 (no `Handlers`/`dispatchAppFrame` entry shipped with the vocabulary). It sat in `excludedTypes` under its own reason — the inbound leg had no handler yet — with a written handoff that #1897 (split from #1744) fulfilled: the entry now reads `inboundTypes["TypeAttachmentChunk"] = "switch-intercepted"`, beside the twelve other case-selector-backed entries. Any future bidirectional or not-yet-wired type should follow this entry's interim shape or `TypeHello`'s, never the `"push"` block. See [Inbound `attachment_chunk`](v2-session-manager-state-machine-inbound-attachment-chunk-attachmentintake-seam.md) for the handler.

**The cap + both-direction fixtures (#1753).** `attachments.go`'s new `const` block publishes `MaxAttachmentChunkBytes = 45000` — raw, pre-base64 bytes of `Data`, the first exported byte bound in this package — plus byte ceilings for the three metadata strings the doc block above leaves unbounded (`MaxAttachmentIDBytes = 64`, `MaxAttachmentFilenameBytes = 255` at POSIX `NAME_MAX`, `MaxAttachmentMimeTypeBytes = 255` at RFC 6838 §4.2). All four are declared contracts with no validator in this package, same posture as the payload type; #1741 enforces inbound, #1897 outbound — the retrieval reject path (`attachment.not_found` / `attachment.stream_aborted`) is #2054's.

- **Why this constant is exported where `maxV2AppEnvelope` (test-local, `interactive_test.go`) is not: enforcement location, not importance.** `maxV2AppEnvelope` measures a cap the *transport* enforces, so exporting it would claim an enforcement this package doesn't perform. `MaxAttachmentChunkBytes` is a producer-side contract every client must obey to chunk a file at all — readable from outside the package is the whole point, even though nothing here checks it either. The distinction to carry forward: exportedness tracks who must read the number, not whether this package verifies it.
- **A length ceiling is not a safety property, and `MaxAttachmentIDBytes` is the concrete case.** 64 bytes sits above `conversations.ValidID`'s 36-char UUIDv4 form so #1741/#1743 can choose the canonical shape without this constant constraining them — but 64 bytes also accommodates `../../../../etc/passwd` several times over, so it does nothing about the traversal hazard the canonical-shape check (not this bound) is responsible for. Worth re-stating whenever a byte-length constant sits next to a field the doc block also calls a path component: the two obligations don't imply each other.
- **Tracing a worst-case test fill to a *declared* bound, not a number invented in the test.** `TestAttachmentChunkPayload_FitV2EnvelopeCap` fills every unbounded field to its published constant, but two fills go beyond what the field's own contract allows and both are declared as such in the test's header rather than silently: `SHA256` is filled with 64 `<` rather than 64 hex characters (hex never escapes, so the honest worst case is 64 B, not the 384 B a hostile fill costs — the extra 320 B buys a proof that holds for a length-respecting non-hex value, which is what an inbound attacker actually sends), and `Index`/`TotalChunks`/`Size` are filled at `math.MinInt64` even though the doc block says `Index >= 0` etc — because nothing enforces that yet, and the *declared Go type* is the bound this fill traces to. A test that fills past a field's stated contract needs to say why in its own header, not leave a reader to wonder whether the fill is a mistake.
- **A byte guard's own source literal can silently lose the escape it exists to prove, and the round trip won't catch it.** The upload fixture's `Filename` (a `report ` + less-than-sign + `draft` + greater-than-sign + `.pdf`-shaped string) is the one place the committed bytes demonstrate `encoding/json`'s `SetEscapeHTML` default: the less-than sign becomes the six-byte sequence backslash-u-0-0-3-c on the wire. Writing that field's raw less-than-sign literal through an editing tool silently substituted the six-byte escaped form into three source-code spots meant to hold the raw character (a struct-literal want, a byte guard, and a comment), and every test still passed, because each assertion was internally consistent with whichever form it actually held — no fixture in the diff was wrong, only the test's *source* literals were. `roundTripEnvelope` proves the fixture round-trips; it proves nothing about whether the test's own Go-source literal is the character the test claims to be asserting against. After writing a character that JSON escapes into a Go source file, grep the file for the six-byte escape sequence to confirm none leaked into a spot meant to hold the raw byte, rather than trusting a green test run.
- **A sole-redness claim about an `,omitempty` mutant depends on which regeneration state you measured, and the two states can disagree.** As committed, the `index` field's `,omitempty` mutant reddens both `TestAttachmentChunkPayload_Upload_RoundTrip` (its fixture's `index` happens to be `0`, the field's own zero value) and `TestAttachmentChunkPayload_ZeroValue_RoundTrip`'s byte guard. Regenerate both fixtures under that same mutant and the upload round trip goes **green** — the mutant elides `index` from the regenerated upload JSON too, and decoding an absent `index` back to `0` still round-trips clean — while the zero-value byte guard, checking for the literal `"index":0`, stays red because that key is elided from the regenerated zero fixture as well. The upload round trip's coverage of `index` was real only pre-regeneration; only the byte guard survives both states. A "this test is the only one that catches mutant X" comment has to name *which* state — as-committed or post-regeneration — it was measured against, extending the sole-redness discipline [Slash-command-list payload](protocol-package-slash-command-list-payload.md) already records: re-run rather than predict, and now re-run in both states. **`ConversationID` (#2142) is the second field to earn this shape, and by a different route**: its retrieval fixture is committed *empty by design* (the field is upload-leg-only), so under the same mutant the retrieval round trip — not the upload one — goes red once fixtures are regenerated, because eliding an already-empty key changes nothing about `""` decoding back to `""`, while the zero-value guard reddens as before. A directional fixture earns directional mutant coverage regardless of which field or which leg carries it; don't assume `index` is a one-off.
- **A grep-based sweep for a reversed or superseded argument does not reach a test that encodes the same claim as a bare count.** #2142's sweep for the literal phrase "steer bytes" and for `conversation_id`'s absence, across `docs/protocol-mobile.md` and Go doc comments, missed `internal/relay`'s `TestAttachmentEnvelopes_AllEightFieldsAndCorrelation` entirely — its redness (`"payload carries 9 keys, want exactly 8"`) surfaced only because the gate *compiled and ran* the dependent package, not because anything in it matched either grep. The same shape hit `TestAttachmentChunkPayload_FitV2EnvelopeCap`'s header, which said "the three metadata bounds this fills to" and stayed green either way once a fourth field filled to one of those same three constants — AC-3's warning about that specific test, generalized: any assertion or comment that counts fields, keys or bounds rather than quoting the argument's prose is invisible to a prose sweep and has to be found by compiling and running every dependent package, not by widening the grep.
- **Adding a field to this frame's byte-budget arithmetic moves two rows, not one.** #2142's own back-of-envelope check (spare bytes minus the new field's value bound: `1333 − 384 = 949`) undercounted the true new spare figure (928) by exactly 21 bytes, because it accounted for the new value bound but not the "payload braces, keys, quotes, colons, commas" structural row, which also grows — the new key's own length (`conversation_id` is 15 bytes) plus its two quotes, colon, separating comma and the value's two quotes. `TestAttachmentChunkPayload_FitV2EnvelopeCap`'s measured total (64591) is what caught the discrepancy; a predicted total would not have. The next field added to this frame has to recompute both rows, not extend the value-bound row alone.

**The published client contract (#1751): `docs/protocol-mobile.md` § Attachments.** #1752/#1753 landed the Go above with nothing published for the mobile/desktop clients that code against the spec, not the Go — the doc actively contradicted the landed code in two places (§ Application-envelope size cap claimed chunking was "out of scope"; § Scope listed attachments as out of scope outright). #1751 published the section — the eight-field table, the sender's chunking arithmetic (`total_chunks = max(1, ceil(size / 45000))`), the receiver's index-addressed reassembly (deliberately weaker than `debug_bundle_chunk`'s strict `seq` succession — the neighbouring rule a reader would otherwise copy), retrieval's two terminal signals, and the trust/content-hygiene obligations — corrected both stale claims, and added the seven `attachment.*` codes documented above. Two lessons from that ticket generalize past it:

- **A `**bold**` paragraph lead is not a heading, and a markdown link to it renders as a dead anchor with nothing in this repo's build checking it.** `make cite-guard` only scans `//`-comment citations in Go source; a `[text](#some-bold-lead)` link inside `docs/protocol-mobile.md` itself is invisible to CI. Before linking to a spot in this document that isn't a `###`/`####` heading, check it actually has one — the § Application-envelope size cap paragraph this ticket linked to is a bold lead inside § Wire shapes, not its own heading.
- **A code-review SHOULD FIX against prose (not code or tests) can get deferred to "the documentation pass" instead of a rework lap, and if so it has to actually land here, not just get noted.** #1751's review flagged the § Application message types row's claim "the table's only bidirectional entry" as false — three rows (`ack`, `error`, `rekey_request`) are already `either` — and marked it non-blocking, explicitly for correction at the documentation stage. Verify a deferred-to-docs finding against the live file rather than assuming a PASS verdict means every finding landed.
- **Inserting a new `####` frame subsection mid-section re-parents whatever `#####` children already sit under the frame it displaces — confirmed on #2052.** § Attachments' `##### The attachment_id shape` and `##### Naming a message's attachments` sit under `#### attachment_stored`. Placing a new frame's subsection where it would read best — grouped next to the chunk/stored frames rather than at the section's end — would silently move both under a frame neither belongs to, since markdown heading depth is positional, not declared. Append a new frame subsection at the end of the section instead; it costs nothing, since every reference to it is by anchor rather than by position.

**The upload leg's success reply, `TypeAttachmentStored` (#1895, split from #1744), ships in the same const block area but stays wire vocabulary only.** `AttachmentStoredPayload{AttachmentID}` in `attachments.go` is a single field — the client's own id, echoed back — correlated via `Envelope.InReplyTo` rather than a payload field, filed `"reply"` in `excludedTypes` on the `TypeSessionSettingsUpdated` precedent — unaffected by #1897 landing, since a reply type's classification tracks whether it's an inbound request verb, not whether anything emits it yet. #1897 is what now constructs and emits it, from the completing chunk of an upload. See [Drift detectors](protocol-package-drift-detectors.md) for what its type-classification registries do and don't catch, and `docs/protocol-mobile.md` § `attachment_stored` for the published `attachment_id` shape.

**The retrieval request verb, `TypeRequestAttachment` (#2052), closes the hole this section named out loud for a full ticket cycle — split from #1746 into #2052 this verb, #2053 the outbound stream, #2054 the handler.** `RequestAttachmentPayload{ConversationID, AttachmentID}` in `attachments.go` is phone → binary **only** — unlike `AttachmentChunkPayload` it never rides the daemon → phone leg, so every field is an unverified claim, always, with nothing to infer from direction. `ConversationID` is a lookup key validated against the daemon's registry before it reaches a path join, never a value trusted as sent — naming a conversation is not authorization, the property `send_message`'s `attachment_ids` already states for itself (§ Naming a message's attachments). `AttachmentChunkPayload` carries a same-shaped field too since #2142, but the two still differ in what the value *does*: here it selects which conversation's file to read; there (since #2143) it gates whether the chunk is admitted at all, through the same `KnownConversation` seam. Both ids are documented against `conversations.ValidID`'s lowercase-UUIDv4 shape. A hostile or truncated payload decodes to two empty strings rather than an error, since every JSON key is optional to `encoding/json` — the concrete silent-failure shape a decoder must not fall into is `filepath.Join(base, "", "")` returning `base`, the conversation directory root, rather than an error.

No request-id key: correlation rides `Envelope.InReplyTo`, reusing `AttachmentStoredPayload`'s decision rather than re-litigating it — and the fixture pins the reuse in bytes rather than only in prose. `request_attachment.json`'s envelope id (`91`) is exactly the `in_reply_to` the already-committed `attachment_chunk_retrieval.json` carries, so the two fixtures describe one retrieval rather than two independently-chosen ones, the same tie `attachment_stored.json` made for the upload leg. Between #2052 and #2054 it sat in `excludedTypes` as `"pending handler (#2054)"`, on `TypeQuestionAnswer`'s #1983→#1984 precedent: `inboundTypes` would have failed Assertion #1 with no `dispatchAppFrame` case, and `"push"` would have been false for a frame that is genuinely, exclusively inbound. See [Drift detectors](protocol-package-drift-detectors.md) for what actually reddens the build on an unpartitioned `Type*` constant (not the registry a reader would guess), and `docs/protocol-mobile.md` § `request_attachment` for the published field table.

**The handler, #2054, has landed** — `internal/relay`'s `handleRequestAttachment`, reached from a new `dispatchAppFrame` case; the entry above moved from `excludedTypes` to `inboundTypes["TypeRequestAttachment"] = "switch-intercepted"`, exactly as `TypeAttachmentChunk` did ahead of it. It answers with the stored file's bytes (via `StreamAttachment`, #2053) or with one of the two codes this document already published: every no-bytes cause — an undecodable payload, an absent/empty id, an unknown conversation, a resolver miss, or a pre-emission read failure — collapses to `CodeAttachmentNotFound`, and a failure after `StreamAttachment` has begun pushing chunks answers `CodeAttachmentStreamAborted` instead, partitioned on the returned error's *identity* since the function's signature carries no count of what it enqueued. See [Inbound `request_attachment`](v2-session-manager-state-machine-inbound-request-attachment-attachmentresolve.md) for the seven-step ordering and the two lessons this ticket's code review surfaced.

**The outbound stream, #2053, has landed** (`internal/relay`'s `StreamAttachment` — see [Outbound attachment stream](v2-session-manager-state-machine-outbound-attachment-stream-streamattachm.md)) — shipped unwired, ahead of the #2054 handler, exactly as `StreamBundle` shipped ahead of #813. It settled where three of the eight fields on the retrieval leg come from: `size`/`sha256` from the stored bytes and `mime_type` from `http.DetectContentType`, never from anything a client declared, since nothing a client declared is stored. That finding corrected `docs/protocol-mobile.md` § Attachments, whose trust paragraph, `mime_type` field row, and `attachment_stored` restatement all previously said the two fields "arrive attacker-chosen at upload time, are stored, and are echoed back verbatim" — none of which is true (`mime_type` is never stored at all; `filename` is stored *sanitised*). **A fourth instance of the identical wrong claim was found in this very document's own doc block** — `AttachmentChunkPayload`'s SECURITY comment called the outbound fields "daemon-authored and trustworthy," a stronger and more dangerous form than any of the three sentences the #2053 AC named. #2053 scoped its correction to `docs/protocol-mobile.md` alone, so this instance was filed and corrected separately: the SECURITY block, both field-contract bullets and both matching struct trailing comments now state both legs, citing § Attachments as the authority rather than restating it as though new. A doc-correction AC that names specific sentences to fix does not imply it found every instance of the claim; grep the corrected phrase across the repo — including production doc comments, not only the document the AC named — before treating a correction as complete.

**`TypeReadWorkspaceFile` (#2598) declares and serves in one slice — the first member of this family with no declare-then-implement gap, unlike every type above it.** `ReadWorkspaceFilePayload{ConversationID, Path}` in `attachments.go` is phone → binary only, same posture as `RequestAttachmentPayload`: both fields are unverified claims, no `omitempty`, `ConversationID` a registry-validated lookup key and never authorization. It answers with `RequestAttachmentPayload`'s own vocabulary — an `attachment_chunk` stream correlated by `in_reply_to`, or `CodeAttachmentNotFound` / `CodeAttachmentStreamAborted` — but the bytes never touch the attachment store: `Path` is read live off the conversation's recorded `Cwd` on every request, confined by the same `confineFile`/`readChecked` pair `cmd/pyry`'s `attachment.file` control verb established for a **model**-named path (#2164) — this is the first wire path a **paired client** names instead. Filed straight into `inboundTypes["TypeReadWorkspaceFile"] = "switch-intercepted"`; nothing sits in `excludedTypes` for it, since the handler is this type's only consumer and shipped in the same ticket. See [Inbound `read_workspace_file`](v2-session-manager-state-machine-inbound-read-workspace-file-workspacefileread.md) for the handler, the seam, and the double markdown-extension check (requested leaf, then resolved leaf — confinement follows symlinks, a markdown-only check on the requested name alone does not), and `docs/protocol-mobile.md`'s `read_workspace_file` section for the published contract.

**The announcement frame, `TypeAttachmentOffered` (#2082, producer #2083), declares the vocabulary only — a fourth attachment-family type publishing before anything emits it, on the same declare-then-implement footing as `attachment_stored` and `request_attachment` above.** `AttachmentOfferedPayload{ConversationID, AttachmentID, Filename}` in `attachments.go`, filed `"push"` (not `"reply"` — nothing solicits it, so `Envelope.InReplyTo` carries nothing and the label never moves to `inboundTypes`). Correlation is `conversation_id` alone, on `ModalShownPayload`'s precedent: no `turn_id`, because it is private state on the interactive emitter while this frame originates on the control-server handler goroutine instead — the same lane `modal_shown` already broadcasts from — so a field a reader reaches for first is not reachable at all, and publishing it would mean building a seam nobody has asked for. Two design moves this ticket ruled out, so a later one doesn't re-propose them:

- **Widening `MessagePayload` to carry the announcement was the obvious move and the wrong one.** Its one producer, #2115's `newOperatorMessageHistory`, hands the value to `appendConversationHistory` — a write to the durable history log, not a push — so widening it would have announced nothing at the moment the file appears, and would also have changed a record shape `history_page` decoders already read. See [Messaging payloads](protocol-package-types-messaging-payloads.md).
- **A blanket per-frame provenance verdict, copied from `attachment_stored`'s one-row table, does not hold here.** `filename` is the first string in this family that originates from `claude` rather than the daemon or the client, so the published table states provenance per field (§ Question's rule) rather than one verdict for the frame — publishing it as daemon-asserted would have handed a reader trusted chrome for an attacker-shaped string (caught as a MUST FIX in this ticket's own security review, not downstream). For the same reason, this frame is **not** safe to log whole, unlike `attachment_stored` (which ships no filename) — the sibling a reader reaches for as the template gives the wrong answer here.

**Reusing a blanket outbound-trust sentence verbatim across a wider field set ships a new false claim, not just a fix.** § Attachments' "outbound every field is daemon-authored, and none is a stored client string echoed back verbatim" is scoped in its home document to the content metadata it had just enumerated (`size`, `sha256`, `mime_type`, `filename`). Copying it whole into `AttachmentChunkPayload`'s SECURITY block — which enumerates all eight fields — would have made it false of `AttachmentID`: nothing daemon-side mints one, the client supplies it on every chunk, `EnsureDir` makes it a directory name, and retrieval echoes it back byte-identical (`attachmentEnvelopes` copies what `StreamAttachment` is handed). The landed fix states the outbound half as daemon-authored *except* `AttachmentID`, which is the client's own id echoed back under the same canonical-shape check a receiving client must apply too — rather than borrowing the source sentence unmodified. Before reusing a trust or provenance sentence in a block that enumerates a wider field set than the one it was written for, check it against every field the new block names, not just the fields that motivated the original wording.
