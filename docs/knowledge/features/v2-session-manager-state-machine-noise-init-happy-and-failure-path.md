# `noise_init` happy-and-failure path

1. JSON-decode inner frame, validate `Version == 2` and `Type == "noise_init"`, base64-decode `Data` (size-cap 65535).
2. Lazy-construct `noise.Responder` from `cfg.StaticPriv` (one per session).
3. `Responder.ReadInit(data)` → early-data bytes. **On err: close(4426)** (MAC fail / wrong static pubkey / malformed IK message 1; no CipherStates exist, no AEAD-sealed error possible).
3a. **Capture `s.peerStatic = s.resp.PeerStatic()`** (#452) — the initiator's static pub, pinned for the session's lifetime at the earliest authenticated point. By the time `ReadInit` returns nil, flynn has MAC-verified and DH-decrypted the static; the value is authentic regardless of whether subsequent steps accept the hello. Set exactly once per `V2Session`; a future re-key (added in #453) MUST NOT overwrite it. The field is inert in the current code (no production reader); #453's `handleRekeyInit` will compare a fresh-handshake initiator's `PeerStatic()` against it via `bytes.Equal` and reject mismatches at WS close code 4426.
4. Decode early-data as a `protocol.Envelope`; require `Type == "hello"`. On decode failure or wrong type: **close(4421)** (handshake-layer protocol violation; CipherStates still don't exist).
5. Decode `Envelope.Payload` as `protocol.HelloClientPayload`. On decode failure: close(4421).
6. Compute the capability intersection the daemon will echo. An unsupported or repeated phone claim cannot enter this daemon-authored slice.
7. **Registry reload (#782).** If `cfg.DevicesPath != ""`, call `cfg.Devices.Reload(cfg.DevicesPath)` so a device paired via `pyry pair` after daemon startup authenticates here without a restart (and a `pyry pair revoke` stops being accepted). On a reload error: log at Warn (`v2.devices.reload_failed`, `conn_id` + `path` + static reason — **never** the wrapped `err`, which can carry a `token_hash` from a corrupt file) and proceed against the retained in-memory set (fail closed — accept set not widened, loaded devices not lost). See [`features/devices-registry.md`](devices-registry.md) § Reload and [ADR 029](../decisions/029-devices-registry-reload-at-handshake.md).
8. Call `cfg.Devices.Validate(hello.Token)` before constructing the ack. Only `ValidateAccepted` resolves `workspaceRoot()` and places the result in `HelloAckPayload.WorkspaceRoot`; a resolution error, empty/non-absolute home or either token-rejection result leaves it empty, so `omitempty` removes the raw key. This ordering is load-bearing: Noise has authenticated the initiator's static key by now, but a rejected initiator can still decrypt the response early data. Host metadata therefore requires device-token authorization as a separate gate. Resolution is a lexical `filepath.Join` only; it does not inspect, resolve through or create the reported directory, and neither the path nor a resolution error is logged.
9. Marshal `HelloAckPayload{ProtocolVersion: "v2", ServerID: cfg.ServerID, ConnID: env.ConnID, Capabilities: negotiated, WorkspaceRoot: root}` into an `Envelope{ID: 1, Type: hello_ack, InReplyTo: &hello.ID}`. `Responder.WriteResp(ackEnvJSON)` produces response bytes and `(send, recv)` CipherStates. **On err: close(4426)** (practically unreachable under correct flynn/noise; defensive). The complete ack remains inside Noise response early data and never enters the relay-visible `RoutingEnvelope` or a log field.
10. Persist `send` / `recv` on the session. **State → `V2StateHandshakeComplete`** (the externally-observable substate, even though step 11 immediately advances or rejects), then marshal an `InnerFrameV2{Type: noise_resp, Data: base64(respMsg)}`.
11. Apply the three-way `ValidateResult` captured in step 8:
    - **`ValidateAccepted`**: emit `RoutingEnvelope{ConnID, Frame: noiseRespFrame}` via `Outbound`. **Redemption persist (#1528):** `recordRedemption(connID, dev)` runs next, best-effort — if `dev.RedeemBy` carries a deadline, it clears it and persists `devices.json` inside `devices.WithLock` (`Reload` → `ClearRedeemBy` → `Save`, bounded by a 250ms `redemptionLockWait`); a record with no deadline costs nothing, not even a lock acquisition. Placed *after* the accept envelope so the phone never waits on the lock, and *before* the state transition below so tests can synchronise on it via `waitConnOpen`. Every failure (lock busy, in-region reload, save) is logged (`v2.devices.redeem_persist_failed`, no plain token/hash/name) and swallowed — the handshake has already succeeded. See [`features/devices-registry.md`](devices-registry.md) § `ClearRedeemBy` for the registry side and its two-writer-clobber update. Publish the matched device and negotiated interactive decision, then **state → `V2StateOpen`**. Log `v2.handshake.accept` with `conn_id` + `device_name`.

      `recordRedemption`'s own doc comment describes `handleNoiseInit` as running on "the session's Run goroutine" and names `pyry pair`/`pyry pair revoke`/the push-token handler as peers holding "sub-millisecond regions" of the same lock. Neither claim matches this document: per [§ Concurrency](v2-session-manager-concurrency.md) there is exactly **one** `Run` loop per manager, shared across every open conn, so a stall here is a stall for every session's frame processing, not just this one's — and per `devices-registry.md`'s clobber-guard update, none of those three peers call `WithLock` yet; `recordRedemption` is presently the primitive's only production caller. Code review flagged this as a SHOULD FIX on #1528 and it shipped undefended. The 250ms bound itself isn't wrong, just its stated justification — read the two linked sections for the actual model rather than the comment at the call site.

      **Client-version persist (#2577):** `recordClientVersion(connID, dev, hello.ClientVersion)` runs immediately after `recordRedemption`, same best-effort contract — the reported version is admitted through `sessions.AdmitClientVersion` (a refusal stores `""`), compared against the snapshot `Validate` returned, and only a change takes the lock: `WithLock` → `Reload` → `SetClientVersion` → conditional `Save`, bounded by the same `redemptionLockWait`. See [`features/devices-registry.md`](devices-registry.md) § `SetClientVersion`. **Accepted double lock/fsync on a device's first redemption that also reports a new version:** the two writes are separate `WithLock` regions, so that hello takes the devices lock and fsyncs twice back to back — flagged as a NIT on code review rather than merged into one region, since it is bounded by `redemptionLockWait` and reachable only once per device (the first hello after mint). Worth merging if a third accept-time devices write ever joins them.
    - **`ValidateUnknownToken`** and **`ValidateWindowElapsed`** (#1529) share ONE reject body wholesale: emit `noise_resp` first (so the AEAD channel exists on the wire), then AEAD-seal an `Envelope{Type: error, Payload: ErrorPayload{Code: auth.invalid_token, Message: MsgInvalidToken, Retryable: false}}` under `send`, wrap as an `InnerFrameV2{Type: noise_msg, Data: base64(ciphertext)}`, and emit one `RoutingEnvelope{ConnID, Frame: noiseMsgFrame, CloseCode: 4401}`. The rejected peer can decrypt the ack, which is why step 8 must leave its `workspace_root` absent. **State → `V2StateClosed`**, session deleted. The *only* thing that varies between the two results is which log `event` string is selected before falling into that shared body: `v2.handshake.reject.invalid_token` for an unmatched hash, `v2.handshake.reject.redemption_window_elapsed` for a matched-but-expired one — both with `conn_id` only (NO device-name, NO token, NO hash — anti-enumeration, mirrors `auth.go:129-132`).

      Selecting only the event string and falling into one shared body — rather than branching into a second reject body — is what makes "rejected identically" (AC-3) true by construction instead of by two code paths that happen to agree today. A distinct close code or error code here would turn the handshake into an oracle confirming that a captured token was once real, which is the specific thing #1529 exists to prevent: an attacker holding an elapsed token must see the same wire response as an attacker guessing at random. `internal/e2e/relay_v2_handshake_test.go` drives both cases through one shared assertion helper so the two cannot drift apart without failing for both. See [`features/devices-registry.md`](devices-registry.md) § `Validate` for the registry-side predicate and its own security discipline (the window check runs strictly before the `LastSeenAt` stamp, so a rejected attempt — either reason — mutates nothing at all).

### The client-version reject arm (#2578)

The version check runs between step 8's `Validate` call and step 11's arms, but only fires as a fourth outcome *after* the `ValidateUnknownToken`/`ValidateWindowElapsed` arm above has had its chance to return: `checkClientVersion(helloPayload.ClientVersion)` is called only when `tokenResult == devices.ValidateAccepted`, so an invalid token's reject arm never parses `client_version` and its bytes and timing never vary with it (`docs/protocol-mobile.md` § Compatibility calls this out explicitly). Its verdict gates `workspace_root` the same way a rejected token does — `root` stays `""` whenever the token is rejected OR the version is.

A rejected version — `reason` is `"unparsable"` (no minimum matched the parsed app, or the string didn't parse as `<app>/<MAJOR>.<MINOR>.<PATCH>` at all) or `"below_minimum"` (a parsed app whose minimum the parsed version doesn't clear) — takes the token arm's exact shape: `noise_resp` first, then ONE routing envelope carrying the sealed `client.update_required` error (`Retryable: false`, `MinClientVersion` set only on `below_minimum`) and close `StatusClientUpdateRequired` (4412), or a close-only fallback at 4412 if sealing fails — same atomicity argument as the paragraph below. **State never reaches `V2StateOpen`**: no `recordRedemption`, no `recordClientVersion`, `s.device`/`s.clientName`/`s.clientVersion` stay unset. The log event is `v2.handshake.reject.client_update_required`; `app` and `min_client_version` are added only on `below_minimum` (the parsed app is grammar-restricted, the minimum is daemon-authored) — the raw `client_version` is never logged, on either reason.

**With no minimum set for any app, `checkClientVersion` returns the zero value unconditionally** — a hello reporting `"1.0"`, `""` or any other free text is accepted exactly as it was before this ticket. Each daemon release carries its own minimums as build constants (`relay.MinMobileClientVersion` / `relay.MinDesktopClientVersion`, both empty as shipped) rather than operator configuration, so a staged rollout can leave different hosts enforcing different minimums, or none, at once — see `docs/protocol-mobile.md` § Compatibility.

**Lesson: a manager built only from hand-written test values can pass while the shipped constant is broken.** `NewV2SessionManager` parses every `MinClientVersions` entry and fails construction on one that doesn't parse as `<app>/MAJOR.MINOR.PATCH`, so a malformed minimum can never silently read as "no minimum". That guard only reddens `make check` because one test builds a manager from `ShippedMinClientVersions()` itself (`TestNewV2SessionManager_MinClientVersions`) rather than only from synthetic values invented for the test — without that, the constructor's validation would exist but never actually run against the real build constant until the daemon started. The same shape applies to any future config field sourced from a build constant: exercise the constructor against the production accessor, not only against values the test made up.

The AEAD-error-then-close path emits the error frame AND the close code in a **single** outbound routing envelope — atomic at the wire layer. This is what guarantees the spec's MUST: the phone observes the error envelope *before* the WS close (`docs/protocol-mobile.md` § Failure modes line 436). Two-call sequencing (`Send` then `CloseConn`) would race the relay's output paths.

### `noise_msg` in `V2StateHandshakeComplete` — the gating row

Today the natural inbound-frame flow never reaches this cell: state transitions through `handshakeComplete` atomically inside the `noise_init` handler. The cell exists for two reasons:

- **Future-proofing.** If a later slice introduces deferred token validation (e.g. network-backed registry lookup), `handshakeComplete` becomes observable to incoming frames between handshake completion and validation completion. The transition row defines the behaviour for that future world today.
- **Same-package unit-test verifiability.** A gating test in `v2session_test.go` directly assigns `s.state = V2StateHandshakeComplete` and injects a hand-rolled `(send, recv)` pair to drive this row deterministically — the **structural** proof that the handler chain is unreachable from `handshakeComplete`. AC #4's load-bearing invariant.

The implementation tries AEAD-decrypt-then-decode-as-`Envelope`. Decrypt failure → close(4421). Decrypt success → seal `auth.invalid_token` under the live `send` CipherState, emit + close(4401), regardless of envelope type. The handler chain in `internal/relay/handlers/` is **not** reached.
