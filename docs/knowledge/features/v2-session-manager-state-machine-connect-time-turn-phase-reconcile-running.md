# Connect-time turn-phase reconcile (#2712) — `RunningTurnPhases` seam + `reconcileTurnPhases` + `turnPhaseSnapshot`

`security-sensitive` — the seventh Mode B instance of the reconcile-on-connect mechanism (umbrella #829). A freshly interactive-open conn is unicast the current `thinking`/`responding` `turn_state` of every running turn, so a phone that reconnects mid-turn shows the right phase immediately instead of reading idle until the turn ends — `turn_state` otherwise travels only on the Mode A event stream, which a reconnect replays from a cursor, and the live stream itself sends nothing new for a long single-phase turn because `interactiveTurnEmitterV2.transitionTo` deduplicates the projected conversation phase.

**Structural divergence from its six twins, until #2739: the producer was a snapshot of the emitter's own state, not an enumeration over a registry or pool.** `RetainedBackgroundTaskRosters` and its five siblings all resolve a daemon-wide collection keyed by `conversation_id`. This seam's `cmd/pyry` producer, `turnPhaseSnapshot` (`cmd/pyry/interactive_turn_v2.go`), was a `sync.Mutex`-guarded `(conversationID, state turnbridge.TurnState)` pair — one value, because `interactiveTurnEmitterV2` held at most one open turn (only the active conversation's events reached it). `running()` already returned `[]protocol.TurnStatePayload` rather than at most one payload, to keep the seam's contract "every conversation with a turn running" rather than "the one conversation" — a decision that paid off directly when #2739 gave the emitter one turn **per conversation**: `turnPhaseSnapshot` is now a `map[string]turnbridge.TurnState` behind the same mutex, `publish`/`clear` key on `conversationID` instead of overwriting the one pair, and `running()` copies the map under the lock, sorts the conversation ids for determinism, and builds one payload per entry — the seam's shape (`[]protocol.TurnStatePayload`) and its callers did not have to change at all. The zero value (map lookup miss) still means "no turn with a sent phase," which is also what an open turn reads as before its first transition — `startTurnIfNeeded` publishes nothing, so a phase that was never sent is never derived (ticket requirement, not an incidental gap).

**Retain source lifecycle, project one conversation phase (#2981).** The emitter
can retain several producing sessions in one conversation after rotation or an
agent switch. `runningPhase` selects the most recent retained main-phase event
from a still-running source. Child activity and turns with no sent phase do not
contribute. `transitionTo` updates ownership before deduplication, even for
repeated events in the same phase. The snapshot remains one phase per
conversation, shared by live delivery and reconnect reconciliation.

A delayed predecessor's `TurnEnd` must preserve a running successor's snapshot.
When the phase owner ends, the latest remaining running phase is restored;
any emitted `turn_state` uses that retained source's history provenance, while
`turn_end` keeps the ending source's provenance. Only the last running phase
ending clears the snapshot. `endTurn` resets the selected source alone;
conversation-wide `closeForConversation` closes older phases first to publish
one final idle. Per-source deduplication alone would let an old end erase the
successor's snapshot and leave its subsequent same-phase chunks unable to
repair it. `TestInteractiveProvenancePhaseProjection` checks both agent
rotations and switches, either source ending, continued same-phase activity,
close, live phases and reconnect snapshots alongside warm/reopened history.
See [history producers](history-package-producers.md#producers-2114-2115) and
[retained emitter state](streamsup-package-draining-turnevents-into-the-interactive-emitter.md).
No session field is added to the reconnect wire payload.

**The one placement that is NOT beside its twins, and why.** `reconcileTurnPhases` is called from `handleNoiseInit`'s success tail *after* `replayMissed`, where the other six reconciles are grouped earlier in the same tail. The six twins' data doesn't change while a handshake is in flight; a turn's phase can — a turn may end between the moment this conn starts handshaking and the moment it finishes. The emitter publishes a transition to the snapshot *before* `emit`, and `emit` appends to the event ring *before* it asks the relay's `Run` goroutine for `ActiveConns`. `replayMissed` (on `Run`) sets `s.replayThrough` from the ring before the reconcile reads the snapshot. That ordering means: if the reconcile observes a running phase, any `idle` that closes it was appended to the ring *after* `replayThrough` was captured, so it is not in the replay tail and is not deduped by `forwardEnvelope`'s `EventID <= replayThrough` check — it arrives live, behind the reconciled frame. Reading the snapshot *before* `replayMissed` breaks this: an `idle` appended in the gap would ride the replay tail (which drains first), have its live copy deduped away, and leave the reconciled running phase as the last word on the wire. This is AC2's guarantee, and it depends on all three of: publish-before-emit, ring-append-before-`ActiveConns`, and reconcile-after-`replayMissed`. Any one of those three reordered reopens the race.

**That ordering guarantee is enforced only by a comment today, not a test — the verifier's PASS still flagged it as a SHOULD FIX.** `TestTurnPhaseSnapshot_PublishedBeforeFanOut` pins the producer half (publish happens before the emitter's fan-out) but no `internal/relay` test fails if a future refactor moves the `reconcileTurnPhases` call back up beside its six twins, ahead of `replayMissed`. A test closing this gap would need a replay source that appends an `idle` to the ring between the handshake's `replayMissed` step and the reconcile's read, and assert the reconciled `thinking` never outlives the live `idle` on the wire — not yet written as of #2712.

**The composition-root wiring in `cmd/pyry/relay.go:startRelayV2` is also untested end to end.** Two lines connect the pieces: `RunningTurnPhases: runningTurnPhases` on the `V2SessionConfig` literal, and `emitter.phases = turnPhases` assigned after construction (the same post-construction-assignment idiom `emitter.waker` and `emitter.hist` use, because the `V2SessionConfig` seam is built before the emitter exists). Dropping either line compiles cleanly and leaves every existing unit test green — the reconcile silently sends nothing. The six twins' pattern of proving this with a fake-daemon end-to-end test (`internal/e2e/relay_v2_stream_background_task_roster_reconcile_test.go` for the roster reconcile) has no counterpart here yet.

**The edge case this section used to note is gone, because #2739 removed what caused it.** Until then, the follow-active switch at the top of `interactiveTurnEmitterV2.Handle` ended the *prior* conversation's turn whenever the cursor moved, by calling `endTurn` (which clears the snapshot) without emitting an `idle` for it — so a conn already open when the switch fired kept whatever phase it last received for the abandoned conversation, with no live `idle` ever correcting it. #2739 deleted that switch: a conversation's turn now only ends on its own `TurnEnd`, its own externally-abandoned close (`closeForConversation`), or its own session's exit — never because some other conversation's cursor moved. Every path that clears a conversation's snapshot entry now does so because its last running main phase ended or the conversation was closed, so the stale-phase window described here no longer exists.

**Security review verdict: PASS** (`docs/specs/architecture/2712-*.md` § Security review). The payload carries only a server-minted `conversation_id` and a phase from `turnbridge`'s closed vocabulary — no claude-authored text reaches it, so the marshal-failure and push-failure log lines never echo `err` or payload content, matching the six twins' content-free posture. `EventID` is left `nil`: the frame never enters the replay ring or the durable history, and `forwardEnvelope`'s `last_event_id` dedup is inert for it, so re-sending it is harmless and the client's match-and-replace on `conversation_id` is what makes repeats idempotent. The capability gate is `s.interactive`, and a Codex conversation's phase is still withheld from a conn without `multi_agent` through the same `withheldFromConn` path that withholds the live copy. The reconcile enqueues via `Push`, never seals directly, so no Noise send-nonce is spent on a frame `drainOnce` cannot yet deliver (the #874 posture the twins share).

Tests: `cmd/pyry/interactive_turn_v2_phase_test.go` (snapshot lifecycle, publish-before-fan-out ordering, nil-receiver safety, unchanged emission when the snapshot is read), `internal/relay/v2session_turnphasereconcile_test.go` (delivery, unicast-only-to-the-opening-conn, non-interactive and nil/empty-seam no-op cases).
