# Inbound peer-close notice (#2601) — `handlePeerClose` + the `closeWith`/`teardown` split

The relay↔binary leg had no per-phone disconnect notice: a backgrounded or dropped phone was invisible to the manager until the [idle sweep](v2-session-manager-state-machine-idle-session-teardown-per-session-idle.md) reaped it, up to 15 minutes later. pyrycode-relay#152 adds one — a `{conn_id, close_code}` routing envelope with no `frame`, sent the instant that phone's own WebSocket ends. This ticket makes the binary act on it.

**Ordering in `handleFrame` is the whole contract.** A `CloseCode != 0` envelope is routed to `handlePeerClose` and returned from immediately after the empty-`ConnID` guard — ahead of both the lazy `m.sessions` create and the `lastActivityAt` stamp. That ordering is why a notice for a `conn_id` the manager holds nothing for creates no session (it never reaches the lazy-create line) and why `Frame` is never decoded (the branch returns before the AEAD/JSON path). `handlePeerClose` itself does one map lookup: on a miss it logs `v2.peer_close.unknown` at Debug and drops the notice; on a hit it logs `v2.peer_close.teardown` at Info and calls `teardown`.

**`closeWith` split into a publish-free `teardown(s) bool` plus the original `closeWith`.** Every close path before this ticket ended with `closeWith` doing cleanup *and* publishing a close-only envelope back to the relay in one call — right for a close the binary itself decides (idle sweep 4408, AEAD failure 4421, rekey failure 4426, ...), wrong here, since the phone is already gone and there is no one to notify. `teardown` is that cleanup verbatim — stop+nil `rekeyTimer`/`rekeyReplyTimer`/`idleTimer`, close `s.done` (stops the app-frame worker), `AttachmentIntake.ReleaseConn`, nil the replay queue, delete from `m.sessions`, delete from `m.queues` under `pushMu` — returning `false` without doing anything when `s.state` is already `V2StateClosed`. `closeWith` now reads `if !m.teardown(s) { return }` and then builds and sends its close envelope exactly as before. No existing `closeWith` caller changed: the double-teardown guard and the publish still work identically, because `closeWith` *is* `teardown` plus one more step. `handlePeerClose` calls `teardown` directly and publishes nothing.

**No new capability for the relay.** The relay is already able to end any open session today: an envelope for that `conn_id` whose `Frame` fails AEAD reaches the existing 4421 close path, and the relay can also just stop forwarding a phone's frames and let the idle sweep reap it. The close notice does the identical teardown with less log noise and no wasted AEAD attempt — it does not let the relay (or anyone who can inject on that leg) do anything it could not already do by other means. A phone cannot set `close_code` on its own envelope to affect another phone's session; enforcing that the relay only ever sets it for its own WebSocket's own end is the relay's responsibility (pyrycode-relay#152), out of scope here.

**Relation to the idle sweep.** The two share the same `teardown`, so "in any session state" collapses to the same reachable case the idle sweep already covers — a session only persists in `V2StateOpen` (every handshake state either reaches open or closes within one frame), so there is no state check beyond `teardown`'s own closed guard. A relay that never sends the notice (any relay before pyrycode-relay#152, or one that chooses not to) leaves every existing path unchanged: the idle sweep stays the only reaper, at its usual 15-minute bound.

**Why this matters for push wake.** `cmd/pyry`'s `pushWaker` (see [`relay-package.md` § Push-wake surface](relay-package.md#push-wake-surface-sendpushwake-2564)) wakes a device only when it is *absent* from `ActiveConns`. Before this ticket, a phone that had just backgrounded stayed listed as an open session until the idle sweep fired, so a turn ending or a modal appearing while the phone was briefly away sent no wake at all. The close notice makes that absence appear the instant the phone's WebSocket actually ends, closing that gap without changing `pushWaker`'s own absence-based trigger.
