# Inline reply seals gated behind `transportDown()` (#1526)

`security-sensitive` — the fourth application of [the #874 transport-down hold](#transport-down-hold-on-the-push-drain-874--connected-probe--transportdown), after [#912](#scheduled--manual-rekey-emit-gated-behind-transportdown-912) and [#1525](#app-reply-seal-gated-behind-transportdown-1525). Six replies on `Run` call `forwardEnvelope` directly, outside both the push drain and the per-conn worker's `forwardAppReply` path: `handleRequestSnapshot` and `snapshotReplyError` (screen snapshot, `v2session_replay.go`), `emitResync` (`v2session_replay.go`), `handleSetSessionSettings` and `settingsReplyError` (`v2session_settings.go`), and `debugBundleReplyError` (`v2session_debugbundle.go`). Each now calls the unexported `dropInlineReplyIfDown(s, event) bool` helper immediately before its own `forwardEnvelope`, and returns without sealing when it reports `true`. `event` is a fixed per-site slug (e.g. `v2.snapshot.dropped_transport_down`) — never one shared slug — which is what lets a table test's per-row log wait prove each site guards independently rather than one row masking five unguarded ones.

**Placement is call-site, not primitive, like #912 — not #1525's shape.** `forwardEnvelope` is shared with `drainOnce` and `drainReplayOnce`, and `drainReplayOnce` reads a transport-down-shaped return from `forwardEnvelope` as a reason to abandon its whole replay tail (`s.replayQueue = nil`). Putting the guard inside `forwardEnvelope` would make every blip on any of these six sites throw away in-flight replay state that has nothing to do with the reply being dropped. #1525 could gate inside `forwardAppReply` because that function has exactly one caller and nothing diverges after the check; these six have divergent callers sharing the one primitive, so the guard sits at each call site instead, the same reasoning as #912's two `emitRekeyRequest` callers.

**`debugBundleReplyError`'s widened window is why this ticket stopped being deferrable.** Five of the six sites run microseconds after their inbound frame, on `Run`, the same narrow window #874 originally deferred as low-risk. `debugBundleReplyError` is also reached from `handleBundleReady`, fired asynchronously after the bundle assembly completes off-`Run` — the same shape of widening that made #1525 worth doing once #965 moved handler execution off `Run` entirely. No live repro exists for any of the six; the fix shipped on the strength of the pattern, not an observed failure.

**Dropped, not parked — identical posture to #1525.** A reply sealed while the leg is down was already undeliverable (`m.send` discards the `Outbound` error at Debug), so the guard only stops paying a nonce for a non-delivery that was already happening. Side effects that precede the reply are unaffected: a settings update still persists even when its ack is dropped, and `handleBundleReady`'s deferred marker-clear still runs. `emitResync`'s dropped marker costs nothing extra either — the phone re-derives the need for one from its still-out-of-range `last_event_id` on the next handshake. (`handleRequestSnapshot` has had no side effect to preserve here since #2540 deleted its render arm — every reply on this path is now an error.)

**Two existing tests asserted the defect this ticket fixes, and had to change.** `TestV2Session_DebugBundle_RejectsSecondWhileQueued` and `TestV2Session_DebugBundle_PerConnIsolation` (`bundleGatedManagerFor`) hold `Connected` false to keep a bundle queued, and — before this ticket — expected the busy-reject `debugBundleReplyError` to be sealed and delivered anyway despite the leg being down. That is exactly the burned-nonce AC1 forbids, so "every existing test passes unmodified" and "no nonce spent while down" could not both hold; the ticket's own scope note (transport-up / nil-seam only) resolves the conflict in AC1's favor. Both tests now observe the busy reject through its `v2.bundle.err_dropped_transport_down` drop line instead of decrypting a sealed reply; the wire shape itself (code, message, retryable, `InReplyTo`) stays pinned by `TestV2Session_DebugBundle_RejectsSecondWhileAssembling`, which runs with the leg up. **Before reusing this guard shape again, check whether a test's `Connected` seam and its `Outbound` recorder already disagree on purpose** — that disagreement is itself a sign the test is depending on a since-fixed nonce-burning seal.

**Log line:** one Debug line per site on the down path — `event=<site slug>`, `conn_id`, `reason=transport_down` — no payload, `InReplyTo`, ciphertext, plaintext, settings values, or key bytes (#833). At `handleRequestSnapshot` and `emitResync` the drop is checked *before* the `served`/`resync` Info line, so a dropped reply is never logged as delivered; at `handleSetSessionSettings` the drop is checked *after* the existing `v2.settings.updated` Info line, because the update genuinely did persist.

**TOCTOU and byte-identity, same posture as #874/#912/#1525.** All six sites run on `Run`, the single owner of `s.send`; the probe is a plain read of `m.cfg.Connected`, needing no lock. The residual single-frame up→down race carries over unchanged and is not defended further. `transportDown()` reads "up" when `Connected` is nil, so every pre-existing test that doesn't wire the seam is byte-identical to pre-#1526 behavior.

**Security review verdict: PASS** (run after the code, recorded in `docs/specs/architecture/1526-inline-reply-transport-down.md` § Security review — the ticket carries `security-sensitive` and the pass initially shipped late, which twice failed verification on that ground alone before the plan was corrected). Same class as #874/#912/#1525: the change only ever skips a seal, so it cannot cause nonce reuse. The review also surfaced four more direct `forwardEnvelope` callers on `Run` with no probe — `newSessionReplyWorkspaceRefused` (`v2session_modal.go`, also reached from the #2477 `LateSessionStarter` callback, the widest of the four), `emitSystemPromptReply` (`v2session_systemprompt.go`), and `emitModelListReply` + `modelListReplyError` (`v2session_modelrequest.go`) — filed as [#2530](https://github.com/pyrycode/pyrycode/issues/2530) rather than fixed here, since they are outside this ticket's six named sites.

**The `session_settings` report is not one of the six.** `handleRequestSessionSettings` was in this ticket's original scope but now runs on the per-conn worker and returns through `forwardToRun` → `forwardAppReply`, which #1525 already guards; it dropped out of #1526 before the plan was written. `settingsReplyError` (reached from `handleSetSessionSettings`, still `Run`-side) remained in scope.

Tests: new `internal/relay/v2session_inlinereply_test.go` — `TestV2Session_InlineReply_TransportDown_BurnsNoNonce`, one row per site, each waiting on its own drop slug before asserting the `Outbound`-attempt count is unchanged, then recovering and decrypting the next frame under the phone's unchanged `initRecv` (the nonce oracle, the same shape as `TestV2Session_AppReply_TransportDown_BurnsNoNonce`). Isolation was confirmed by mutation: disabling one site's guard at a time failed exactly that site's row, six of six; making the helper log-then-seal-anyway failed every row on the AEAD MAC check, showing the oracle isn't vacuous.
