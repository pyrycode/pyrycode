# Connect-time question reconcile (#1979) — `OutstandingQuestions` seam + `reconcileQuestions`

`security-sensitive` — the fourth Mode B instance of the reconcile-on-connect mechanism (umbrella #829), a structural twin of [modal](#connect-time-modal-reconcile-877--outstandingmodals-seam--reconcilemodals), [queue](#connect-time-queue-reconcile-878--outstandingqueues-seam--reconcilequeues) and [model-list](#connect-time-model-list-reconcile-1863--retainedmodellists-seam--reconcilemodellists) reconcile above. `question_shown` is broadcast once, at raise time (#1973's `streamApprovalBridge.Surface`), to whoever is connected at that instant; `EventID` is nil so it never enters the #647/#777 turn-event replay ring, and there is no other path to it. `reconcileModals`' twist applies here unchanged: the daemon counts an approval answerable while *any* interactive conn is open, so a reconnected client that never received the batch re-arms the approval window at every expiry while being structurally unable to answer it.

**`OutstandingQuestions func() []protocol.QuestionShownPayload`** is the fourth optional `V2SessionConfig` seam (nil ⇒ no reconcile, byte-identical to pre-#1979). Same closure-not-pointer idiom as the other three: `internal/relay` imports neither `internal/questionbridge` nor `internal/modalbridge`, and `internal/protocol` is already a direct import. This slice's own seam is a fake returning a fixed slice; **#1980 bound the production closure**, `cmd/pyry/relay.go`'s `OutstandingQuestions: questionReg.Snapshot`, over the same daemon-singleton the surfacer records into. **Enumerate-all, not conversation-keyed** — `V2Session` carries no conversation id — same reasoning as `RetainedModelLists`.

**The production binding is pinned structurally, not by a test of `startRelayV2` itself.** `startRelayV2` has no test and cannot cheaply get one, so #1980 added `TestOutstandingQuestionsWiredToSurfacerRegistry` to `cmd/pyry/relay_guard_test.go` — the first guard on any of this family's four wiring assignments; none of `OutstandingModals`/`OutstandingQueues`/`RetainedModelLists` is pinned at its assignment even now. It reads `relay.go`'s AST rather than constructing the manager, and ties three facts together (the seam binds a plain-identifier method value whose method is `Snapshot`; `questionbridge.New()` is called exactly once in the file; the surfacer's question arm is fed that same identifier) because bare key-presence alone stays green against a freshly-minted second, always-empty registry. See [protocol-package-drift-detectors.md](protocol-package-drift-detectors.md) for two things this guard's construction surfaced that generalise to the rest of that file's AST-guard family: `go test -overlay` cannot mutation-test any of them (they parse the file from disk at test runtime, past what the overlay rewrites), and a multi-fact guard should run its `Errorf`-based checks before any check whose helper must `Fatal`.

**The pattern recurred, unfixed, in #2460.** `startRelayV2` also builds one `contextUsageRecorder` and assigns it into both `resolver.rec` and `emitter.usageRec` (see [`features/v2-session-manager-concurrency.md`](v2-session-manager-concurrency.md) § `request_context_usage` and [`features/conversations-registry-crud.md`](conversations-registry-crud.md) § `SetLastContextUsage`) — a fifth and sixth unguarded assignment in the same function, following the same after-construction-field shape as `hist` and this family's four. Code review flagged it SHOULD FIX rather than MUST FIX for the same reason each prior instance shipped anyway: the code as written is correct, and deleting either assignment leaves every new test green while silently reintroducing the staleness the ticket exists to prevent (the registry keeps filling from whichever producer's wiring survives, so the failure is invisible rather than a crash). No guard was added. A `TestOutstandingQuestionsWiredToSurfacerRegistry`-shaped AST check — one `contextUsageRecorder` literal in the file, both fields assigned from that same identifier — is the deterministic net this family still lacks for six assignments across two features now, not one.

**`reconcileQuestions(ctx, s)`** is `reconcileModelLists`'s structural twin, `protocol.TypeQuestionShown`/`QuestionShownPayload` substituted, keyed by `question_batch_id`, never by position: `Snapshot` walks a map with an unspecified order, so a reconciled batch must be looked up by id in both production logic and tests.

**Call site:** `handleNoiseInit`'s success tail, beside the modal reconcile and *before* the queue reconcile — a deliberate placement, not the model-list reconcile's "last, order is immaterial" default. An outstanding question batch rides the same approval-window time-sensitivity that put the modal reconcile first in the family; the ordering argument is the modal doc's, reapplied here rather than re-decided.

**No cardinality cap on outstanding batches, and it's the registry's gap, not this path's.** `questionbridge.Parse` bounds a single batch (1-4 questions, 2-4 options, `maxInputBytes` on the raw tool input), but nothing in `questionbridge.Registry` bounds how many batches can be outstanding at once — `Snapshot`'s length is bounded only by claude's own ask concurrency and by #1973 retiring a batch on every terminal path. `reconcileQuestions` deliberately adds no cap of its own (a second place deciding the limit could silently disagree with the first); the real backstop on this path is `pushQueue`'s byte ceiling, which drops rather than growing unbounded. Flagged SHOULD FIX in #1979's security review as a `questionbridge`-side obligation, not #1979's or #1980's — carry this into whichever ticket eventually caps `Registry.outstanding`.

**Testing pitfall found in this ticket: a conversation-keyed test cannot catch a conversation-keyed reconcile bug.** The model-list analogue this slice's test file copies *is* conversation-keyed by design (`RetainedModelLists` reconciles per-conversation model lists), so a `reconcileQuestions` miswrite that keyed lookups on `conversation_id` instead of `question_batch_id` is a one-word typo away from the copied test passing unchanged — two batches never share a conversation in the naive fixture set, so per-conversation and per-batch-id keying are indistinguishable. The delivery table carries an explicit two-batches-in-one-conversation row for exactly this mutant; any future reconcile in this family that copies a same-shaped sibling's test needs the same check — does *this* family's correlation key differ from the copied one's, and if so, does the fixture set actually exercise that difference.

**Pure read, isolation confirmed at both nesting levels.** `Snapshot`'s `cloneQuestions` clones the question slice and then each question's `Options` ([questionbridge-package.md](questionbridge-package.md)), so a reconciled payload shares no backing array with live registry state — AC3's "changes nothing it read" holds at both nesting levels, not just the outer one. This slice's own seam is a fake, so its tests assert the property against the fake's backing payloads rather than depending on `Snapshot`'s guarantee directly; #1980 is where the real property becomes observable end to end.

**Security review verdict: PASS** (`docs/specs/architecture/1979-question-connect-reconcile.md` § Security review), aside from the cardinality-cap SHOULD FIX above. Same two gates as the other three — authentication (post-handshake, post-token-validation) and capability (`!s.interactive`) — plus the same never-log-`err`-on-marshal-failure discipline as the siblings (`encoding/json` quotes input bytes; a batch's claude-authored text must not reach a log line).

Tests: `internal/relay/v2session_questionreconcile_test.go` — `v2session_modelreconcile_test.go`'s pattern (table-driven, one file per reconcile), including its recorded decision not to test the unreachable marshal branch (`QuestionShownPayload`'s closed field set cannot fail to marshal). The three no-frame rows (nil seam, zero-payload seam, non-interactive conn) need the same second-interactive-conn control the model-list doc's guard note describes, for the same `!s.interactive`-mutant reason.

\#1980 landed the daemon-side producer wiring (`questionbridge.Registry.Snapshot` → the seam), its structural guard, and the client contract note in `docs/protocol-mobile.md` § Question and § Reconnect / Backfill semantics' Mode B list.
