# Fanning `channel.post` out: `assistant_delta` live delivery (#2498)

A successful `channel.post` now fans the same content it appends to a channel's durable log to every interactive-capable client as one `assistant_delta` per chunk, so a cron's daily question reaches an operator's open desktop client without a reconnect. `channelPostEmitterV2` (`cmd/pyry/channel_post_v2.go`) is a deliberate copy of `conversationUpdateEmitterV2`'s shape rather than a resemblance — same origin (a host-side control verb broadcast from the control-server handler goroutine), so it is the delivery semantics a client already reasons about: a leaf mutex over a per-emitter envelope-id counter, the #607 interactive-capability gate, and a `Push` loop that logs and skips a torn-down conn rather than stopping. It is wired as `startRelayV2`'s seventh return value and reaches `channelPoster` the way `channelCreator`'s announce hook does — nil when the relay leg is off, called last, its result never consulted, so a fan-out failure can never turn a recorded post into a refusal.

`assistant_delta` is otherwise produced only by a supervised claude turn (`interactiveTurnEmitterV2`); `channelPostEmitterV2` is its second producer and the first that is not one. The two must stay distinguishable at the daemon boundary even though the wire frame is identical, which is why `docs/protocol-mobile.md`'s v2 type table records both.

**A fresh `turn_id` per post, and no turn lifecycle frame at all.** `newChannelPostTurnID` mints one per post from `conversations.NewID` (the same `crypto/rand` UUIDv4 mint `newChannelPostMessageID` used), and the emitter sends `assistant_delta` alone — no `turn_state`, no `turn_end`. A delta alone renders and a fresh `turn_id` starts a fresh bubble, so neither lifecycle frame is needed for the content to appear, and both would be claims this verb cannot make: `TurnEndPayload` carries four claude-authored strings and four numbers nothing here reported, and a channel is an ordinary bound conversation in which the operator can be mid-turn — a synthetic `turn_end` would close that turn rather than the post's own.

**The id's failure contract follows what it addresses, not what the old code called it.** `newChannelPostMessageID` fell back to `""` on an rng failure, correctly — a dedupe key nobody reads degrades harmlessly. `newChannelPostTurnID` refuses the post instead: a `turn_id` is the address a client groups chunks by, and every post minting `""` would coalesce into a single bubble with every other one, breaking the "one post is one rendering" property outright rather than degrading a field nobody reads.

**Chunking is a precondition of delivery, not a refinement.** `MaxChannelPostBytes` (64 KiB) and the v2 application envelope's cap (`maxV2AppEnvelope`, 65519 B) are unrelated numbers that nothing in the build joins — a producer that marshals one straight into the other compiles and passes every short-fixture test, and only fails against a real maximum-size message on a real conn. `encoding/json`'s escaping can cost up to six bytes per input byte, which is the arithmetic `maxDeltaTextBytes`' own doc block records and the reason a single-frame 64 KiB post would blow the envelope cap by roughly an order of magnitude. The poster splits with `splitDeltaText(text, maxDeltaTextBytes)` — the same call `flushDelta` makes — sharing one `turn_id` across chunks with `Seq` advancing from 0, so every chunk is a substring and concatenation reproduces the post byte-for-byte. `TestChannelPoster_MaximumPostFitsEnvelopeCap` measures this directly rather than trusting the constant: a `MaxChannelPostBytes`-sized, `<`-filled (worst-case escape) post, with every marshalled `protocol.Envelope` checked against `maxV2AppEnvelope` — if it ever fails, the fix is lowering `maxDeltaTextBytes`, not raising the measurement's tolerance.

**Live-only, like `conversation_updated` and `attachment_offered` — no outstanding-post registry, no connect-time replay.** The difference from both is that this frame has a durable half: `channelPoster` writes the identical payload to the conversation's log before the emitter is ever called, which is what makes live-only acceptable for a type that is also the single droppable class in `pushQueue.enqueue` and `convRing.evictOldest`. A client that was disconnected, or whose delta was evicted under backpressure, reads the post back out of history through its existing delta-rendering path — no replay path specific to this frame is needed. `EventID` is left unset for the same reason `conversation_updated` and `attachment_offered` leave it unset: this emitter owns no `eventring`, and the durable log already serves the reconnecting client.
