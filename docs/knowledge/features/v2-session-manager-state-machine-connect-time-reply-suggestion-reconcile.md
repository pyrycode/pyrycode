# Connect-time reply-suggestion reconcile (#2830) — `ReplySuggestions` seam + `reconcileReplySuggestions` + the `forwardEnvelope` revision guard

`security-sensitive` — the eighth Mode B instance of the reconcile-on-connect mechanism (umbrella #829), structurally [turn-phase reconcile](v2-session-manager-state-machine-connect-time-turn-phase-reconcile-running.md)'s twin with the payload type substituted. A freshly interactive-open conn is unicast the producer's current `reply_suggestion` state so a reconnect shows the suggestion that stands now, never one another device already cleared. The seam ships unwired — #2831 still owes the `cmd/pyry` producer — so today this mechanism sends nothing in production; everything below is checkable by calling `Push` directly, as the test file does.

**A cleared conversation is a payload, not an absence — the roster twin's exception, not the majority rule.** `ReplySuggestions func() []protocol.ReplySuggestionPayload` must return an entry with `SuggestedReply == nil` for a conversation whose suggestion was cleared, the same "empty state is itself the signal" posture [background-task-roster reconcile](v2-session-manager-state-machine-connect-time-background-task-roster-reconcile-retain.md) adopted for `Tasks == nil` and for the identical reason — `ReplySuggestionPayload.SuggestedReply` has no `omitempty`, so a nil marshals to a literal `"suggested_reply":null`, and a client's clear contract depends on seeing that null rather than the conversation simply going missing from the seam's return. Most of this family's other twins (model lists, slash-command menus) instead treat an empty aggregate as nothing-to-send and filter it out before it reaches the seam; a future reconcile copying this file as its own twin should re-derive which rule applies from its own payload's semantics rather than pattern-matching either precedent, exactly as the roster doc already warns.

**A `reply_suggestion` that fails to decode is delivered unchanged, not dropped — settled deliberately, not an oversight.** `replySuggestionStale` treats "not `TypeReplySuggestion`" and "payload doesn't decode" identically: neither is stale, neither is recorded, and `forwardEnvelope` falls through to send it as-is, the same `pushedConversationID` posture already gives any pushed frame whose shape its own guards don't recognise. The alternative — silently dropping a frame the relay cannot parse — was raised and rejected: the producer builds this payload from its own DTO, so a malformed frame is a producer bug, and dropping it silently would hide that bug from the client too, leaving a stale suggestion on screen with no signal that anything went wrong.

**The revision guard lives in `forwardEnvelope`, not in the reconcile, because that is the one seal path every pushed frame takes — queue drain and replay alike.** Putting the check there, rather than in `reconcileReplySuggestions` or in `Push`, is what lets one comparison order a reconciled snapshot frame against a live frame pushed through the ordinary fan-out, with neither caller aware of the other. The state it compares against, `V2Session.replySuggestionRevisions map[string]uint64`, follows the `replayThrough` regime exactly: Run-owned, read and written only inside `forwardEnvelope`, no lock, allocated lazily, and reset to empty on every fresh handshake — a new `V2Session` per connection, so a reconnect is never blocked by revisions an earlier connection saw.

**The watermark is recorded only after `m.send`, deliberately later than the guard's own pass/fail decision.** Recording at the moment `replySuggestionStale` returns `stale == false` would let a frame that was then withheld by `withheldFromConn`, or one that failed later at `s.send.Encrypt`, advance the conn's watermark for a revision the client never actually received — silently muting the next real delivery for that conversation, since a genuine later revision would then test as not-newer than a revision that was never sent. Recording after the frame is actually on the wire is what keeps "delivered" and "watermark advanced" the same fact.

**The race this guard exists to close needs no cross-component ordering invariant — unlike its nearest twin.** [Turn-phase reconcile](v2-session-manager-state-machine-connect-time-turn-phase-reconcile-running.md)'s correctness depends on three things happening in a specific order across two packages (publish-before-emit, ring-append-before-`ActiveConns`, reconcile-after-`replayMissed`), pinned today only by a comment, not a test. This guard needs none of that: it is a pure comparison against data already inside the envelope, so it is correct regardless of where `reconcileReplySuggestions` sits in `handleNoiseInit`'s tail or how it is ordered against `replayMissed` — the Technical Notes call this out explicitly, and the test suite proves it by forcing the harder of the two interleavings rather than relying on one. Whichever of a stale snapshot or a newer live frame reaches the shared per-conn queue first, the one that drains first is recorded first and the other is then judged against it; the losing order (an older revision draining after a newer one already recorded) is exactly the drop this guard performs, and the winning order (older drains first, newer drains after) delivers both, correctly leaving the newer one as the client's last word either way.

**Forcing the harder interleaving in a test needs the live push issued from inside the seam call itself.** `ReplySuggestions` runs synchronously on the Run goroutine before the snapshot frames it returns are enqueued, so a push issued from inside that same call is guaranteed to land in the per-conn queue ahead of them — there is no other way to make "the clear reaches the queue before the snapshot drains" deterministic rather than a hoped-for race. The helper doing that push must report a failure with `t.Errorf`, never `t.Fatalf`: it executes on the manager's Run goroutine, not the test's own, and `Fatal`'s `runtime.Goexit` there would abandon Run instead of failing the test.

**`withheldFromConn` needed no code change, only a test, because it already keys on the envelope's own `conversation_id`.** `pushedConversationID` reads that field generically for any pushed frame, so the Codex-withholding gate inherited automatically once `reconcileReplySuggestions` and the live path both produce envelopes shaped like every other pushed frame. The one thing this slice had to prove rather than assume: a conn without `multi_agent` gets neither the reconciled nor the live copy of a Codex conversation's suggestion, while a conn with it gets both — and no log line, including the withhold log line itself, carries `suggested_reply` text.

**The per-conn revision map's lifetime was the security review's one open point, closed by keeping it off any manager-level structure.** `replySuggestionRevisions` lives on `V2Session`, never on `V2SessionManager` keyed by `connID` — so it is bounded by the number of conversations one connection actually received a suggestion for, and it is freed the same moment the session itself is torn down, with nothing to leak across reconnects or sessions. A future twin needing per-conn state should default to the session, not the manager, for the same reason.

**What stays #2831's job.** This slice gates only the *reconciled* snapshot on `s.interactive`. Filtering a *live* `reply_suggestion` to interactive conns only is the producer's responsibility, the same as every other `cmd/pyry` broadcaster — it walks `ActiveConns` (which already carries each conn's `Interactive` flag) and calls `Push` only for the conns it means to reach. Nothing in `forwardEnvelope` enforces that filter generically; a producer that pushes to a non-interactive conn directly would not be caught here.

**Security review verdict: PASS** (`docs/specs/architecture/2830-reply-suggestion-reconcile.md` § Security review). No client-authored byte reaches the frame or the guard — the client's only input is the capability set judged once into `s.interactive`/`s.multiAgent`; the payload and its `revision` both come from the daemon's own seam and envelope. `suggested_reply` is claude-derived text and is never logged on any branch: the marshal-failure arm logs `event`, `conn_id`, `conversation_id` only, the push-failure arm logs only `Push`'s sentinel `err`, and a stale drop or a successful send logs nothing at all.

Tests: `internal/relay/v2session_replysuggestionreconcile_test.go` — delivery (single and multi-conversation, a literal `"suggested_reply":null` for the clear, no `event_id`), the no-frame cases (nil seam, empty result, capability not negotiated), a reconnect reading only the current state, the forced two-conn/two-conversation interleave proving the watermark is per conn and per conversation, and the Codex-withhold pair.
