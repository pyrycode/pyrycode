# Claude account source — token files, 1Password and OS secret stores (#2824, #2825, #2839, #2815, `security-sensitive`)

`cmd/pyry/claude_account.go` lets one daemon instance draw its Claude account from an owner-only token file, a 1Password reference, or an OS secret-store item, instead of inheriting `CLAUDE_CODE_OAUTH_TOKEN` from the process environment — so daemon usage doesn't have to draw on an operator's interactive `claude` account. All three sources use the same accessor and streamsup gate, backoff and wiring. The wire contract for client visibility — `request_claude_account` / `claude_account` — is answered by `handlers.RequestClaudeAccount`, with an optional operator `label` and the read-ordering guarantee below. User-facing behaviour (flags, the file format, precedence, failure/recovery) is documented in [`guide.md` § Claude account source](../../guide.md#claude-account-source) and [`deployment.md` § Claude account source](../../deployment.md#claude-account-source); this page covers the design and its durable lessons.

## Shape

- `resolveClaudeAccountSource(flagValue, envValue, instanceDir) (source, origin string, err error)` — first nonempty of the `-pyry-claude-account-source` flag, `$PYRY_CLAUDE_ACCOUNT_SOURCE`, then the `source` string in `<instanceDir>/claude-account.json` (`resolveInstanceDirPath(name)`, i.e. `~/.pyry/<name>/`), via the shared `readClaudeAccountField`. The file is opened only when the flag and env are both empty; a missing file or an absent `source` key means no source configured. `origin` names only where the value came from (`flag -pyry-claude-account-source`, `env PYRY_CLAUDE_ACCOUNT_SOURCE`, or the file's path) and every error is built from fixed text plus that origin — never the value itself, since it could be a token pasted into the wrong field.
- `newClaudeAccount(flagValue, envValue, opCLIFlag, opCLIEnv, instanceDir, logger) (*claudeAccount, error)` — empty source → not-configured accessor, `provider() == nil`, launch behaviour unchanged (this is the existing-callers-keep-compiling path #2823 required). A source starting with `op://` (longer than the prefix, no control byte) selects the 1Password reader; `keychain:<name>` selects the OS secret-store reader; an absolute path selects the file reader; anything else (a relative path, any other URI scheme) is refused. A keychain name must be nonempty, contain no control byte (DEL included), and not start with `-`; only darwin and linux are supported. Refusals name the origin, never the name. When the flag and env are both empty and a source was resolved from the file, it also reads that file's optional `label` key (#2839) via `readClaudeAccountField` and rejects one over 64 bytes, not valid UTF-8, or containing a control character (`unicode.IsControl`, so C1 controls count too, since clients render the label) with an origin-only error that never echoes the value. A flag or env source always reports label `""` and never opens the file for it.
- `readTokenFile(ctx, path)` opens the file afresh on every call (`O_RDONLY|O_NONBLOCK` — a FIFO at that path returns promptly instead of blocking the launch attempt), `fstat`s the opened descriptor, and refuses a non-regular file, a file owned by another UID, any `0o077` mode bit, content over 4096 bytes, or — after stripping one trailing LF/CRLF — empty content or a byte outside printable non-space ASCII (`parseTokenBytes`, shared with both subprocess sources below). Checking the descriptor actually read from (not a second `stat` on the path) closes the obvious check-then-use gap; a symlink is followed on purpose, and the checks land on whatever it resolves to.
- `readOpReference(ctx, cli, ref)` delegates to `runTokenCommand` with `[]string{"read", ref}` and `opReasons`. Output over the cap or failing `parseTokenBytes`'s shape is "1Password output invalid"; empty is "1Password output empty"; a non-zero exit or any other wait error is "1Password read failed"; a `Start` failure is "1Password CLI unavailable"; context expiry is "1Password read timed out" or "1Password read cancelled".
- `keychainCommand(goos, name)` returns `security` with `[]string{"find-generic-password", "-s", name, "-w"}` on darwin, or `secret-tool` with `[]string{"lookup", "service", name}` on linux. `newClaudeAccount` captures that tool and vector at construction, sets kind `os_keychain`, and calls `runTokenCommand` with `keychainReasons` on every read. Tools resolve through the daemon's `PATH`; there is no separate tool-path setting. The six reasons are "keychain tool unavailable", "keychain read failed", "keychain output empty", "keychain output invalid", "keychain read timed out" and "keychain read cancelled". A missing item, locked keyring or denied access refuses that launch with no cached-token or inherited-login fallback.
- `runTokenCommand(ctx, tool, args, reasons)` is shared by 1Password and OS secret stores: `exec.CommandContext` with no shell, each name/reference as one argv entry, `Stdin` nil, `Stdout` a `cappedBuffer` keeping only `maxAccountTokenBytes+1` bytes, `Stderr` nil (discarded), and `cmd.Env` built from `os.Environ()` with `CLAUDE_CODE_OAUTH_TOKEN` stripped (`withoutAccountToken`). Other environment entries, including `DBUS_SESSION_BUS_ADDRESS`, are retained. The child runs in its own process group (`Setpgid: true`); `cmd.Cancel` sends `SIGKILL` to the whole group, and `cmd.WaitDelay` (1s) bounds how long background `Wait` may linger for an escaped descendant holding stdout. The caller selects against `ctx.Done()`, returning at the bound whether or not the child has exited. `commandContextFailure` selects the source's fixed timeout/cancellation reason.
- `resolveClaudeAccountOpCLI(flagValue, envValue, instanceDir) (cli, origin string, err error)` — flag, then env, then the file's `op_cli` (via `readClaudeAccountField`), else `"op"`. It is called, and `validOpCLI` checked, **only** when the source is `op://`; file and keychain sources never read or validate `op_cli`, so a stray or malformed `op_cli` left in `claude-account.json` cannot break those instances. `validOpCLI` admits a bare name matching `[A-Za-z0-9._+-]+` other than `.`/`..` (looked up on `PATH`, never through a shell), or an absolute path with no control byte (spaces allowed, since it is still passed as a single `exec.Command` argv entry, never through a shell).
- `claudeAccount` is the instance-scoped accessor, one per daemon, shared by every Claude runner the instance creates. `provider()` is nil when not configured, else `a.read`. `prime(ctx)` is the one ten-second-bounded startup read (`runSupervisor`, after `checkDebugCapture`); its failure is logged, not fatal — the bootstrap session stays dormant until a turn needs it, so this priming read is what actually surfaces a boot-time misconfiguration before an operator sends anything. `status()` reports `{Kind, Label, State, Reason}` and never the token, the configured path, the 1Password reference, the keychain item name, or the tool's output.
- `(*claudeAccount).ClaudeAccount() protocol.ClaudeAccountPayload` (#2839) is `status()` mapped to the wire vocabulary for `handlers.RequestClaudeAccount`: internal kind `""` becomes `machine_login` and state `not-configured` becomes `not_configured`; `file`, `1password`, `os_keychain`, `ready`, `failed`, the label and the reason pass through unchanged. The mapping lives in `cmd/pyry`, deliberately — `internal/protocol` stays pure data and never computes a kind or state string itself. See [Claude account source frames](protocol-package-types-claude-account-payloads.md) for the wire pair this answers.
- `accountReadError`/`accountReadFailure` are the shared refusal type and constructor all three readers return: a fixed `reason` string, never wrapping an OS/exec error (which would carry the path, the tool, the reference or the item name).

## The selection file needed the same trust check as the secret it points to

The architect's plan's acceptance criteria asked only for the *token file* to be owner-only. The self-review added a second check the ticket didn't ask for: `claude-account.json` itself is refused unless it is owned by the daemon's user and carries no group/other write bit (`0o022`, checked on the opened descriptor, same shape as `readTokenFile`'s `0o077` check on the token file). The reasoning: this file doesn't hold the secret, but it *picks which file does* — a selection file another local user could write would let them redirect the daemon to read and hand Claude an unrelated single-line secret of the operator's, without ever touching the real token file's permissions. A pointer to a secret needs the same ownership/writability guard as the secret itself, or the guard on the secret is moot.

## Validating a JSON string field means checking the raw bytes, not the decoded string

`readClaudeAccountField` decodes a `claude-account.json` value with `json.Unmarshal` into a Go `string`. #2839's label validator (`validAccountLabel`) called `utf8.ValidString` on that decoded result and could never see invalid UTF-8: `encoding/json` silently replaces bad bytes inside a JSON string with U+FFFD while decoding rather than failing, so by the time the value is a Go string it is always valid UTF-8 by construction, whatever the source bytes were. The fix checks `utf8.Valid(raw)` on the undecoded `json.RawMessage` before ever unmarshalling it, with the field's existing `%q must be a string` origin-only wording. Because `readClaudeAccountField` is shared, this check now covers every key it reads — `source` and `op_cli` included, not just `label` — so a `source` or `op_cli` value with invalid bytes is now a startup error instead of surviving as a mangled path that could only fail later, at read time, somewhere harder to diagnose.

## Concurrency: the recorded state is the latest-started read's, not whichever finishes last

`claudeAccount.read` is called concurrently by every runner's own spawn path (first launch, a crash-loop retry, a respawn can all be in flight for different conversations at once). It used to record whichever outcome finished last — a slow failing read could overwrite a newer success. Harmless while `status()` had no reader, but #2816/#2838 gave it one: `handlers.RequestClaudeAccount` (#2839) now serves that snapshot to any paired client, so a stale "failed" obscuring a current "ready" (or the reverse) would be a real, client-visible lie rather than a latent risk.

\#2839 fixed it with a per-read sequence number rather than last-write-wins: `read` takes `mu`, increments `started` and keeps its own `seq`, then runs the actual read unlocked. On completion it takes `mu` again and records its outcome into `state`/`reason` only when `seq > recorded`, then sets `recorded = seq`. A read that started earlier but is still finishing when a later read's outcome is already recorded can never overwrite it — the mutex is taken twice per read (sequence assignment, outcome record) and never across the reader itself, so a slow 1Password CLI call doesn't block anyone else's read or their chance to record. The caller still always gets its own read's true result; only the *shared* `status()` snapshot is protected. `TestClaudeAccount_LaterReadWins` pins both orders — fail-after-success and success-after-fail — by blocking the earlier read on a channel, letting the later one complete, then releasing the first.

## The ten-second bound covers reads that return, not reads that hang

`prime`'s `context.WithTimeout` (and the per-attempt deadline `streamsup` applies on every later read) only cuts in once something inside `readTokenFile` actually checks `ctx.Err()` — before the open and after the read, not during either syscall. For a local file this is immediate either way. For a token file on a wedged FUSE or network mount, the blocking `open`/`read` syscall itself is not interrupted by the context, so the "ten-second startup bound" is not a hard ceiling on daemon startup time in that case. Documented as a known limit rather than fixed, since no production deployment puts the token file on anything but a local filesystem.

## A subprocess bound has to be enforced by returning on ctx.Done(), not by waiting on the child

The file reader's bound (above) is best-effort because nothing can interrupt a blocking syscall from the outside. A subprocess has no such excuse — the process itself can be killed — but `runTokenCommand` still can't enforce its bound by waiting for that kill to land, because `exec.CommandContext` only guarantees killing the *direct* child, and a token tool that forks a helper (deliberately or not) can leave that helper holding the stdout pipe open after the tool itself is dead. A test fixture makes this concrete: a fake `op` whose body is `sleep 30 & wait` detaches a `sleep` that outlives the parent shell entirely. Both 1Password and keychain reads use this runner, so neither an unlock prompt nor a hung helper can hold a launch past its deadline.

So the bound is enforced by the *read itself* giving up, not by the child's exit: `cmd.Wait()` runs in a goroutine that sends on a buffered channel, and the caller `select`s on that channel versus `ctx.Done()`, returning the moment `ctx.Done()` fires whether or not the child (or its escaped descendant) has actually exited. The process-group kill (`Setpgid` + `cmd.Cancel` sending `SIGKILL` to `-pid`) and `cmd.WaitDelay` only decide how fast the now-orphaned background goroutine itself exits — neither is on the path the launch waits for. Getting this backwards (waiting on `Wait` and treating the group kill as sufficient) is exactly the failure mode the ticket called out, and the hang-cut-by-deadline/cancel tests return in ~200ms specifically because the select, not the kill, is what unblocks them.

## Wiring is Claude-only, by construction rather than by filtering

`account.provider()` reaches the Claude runner factory through one new field, `streamApprovalConfig.account streamsup.AccountTokenProvider` ([`cmd/pyry/streamsup_runner.go`](streamsup-package-constructing-a-streamrunner-newstreamrunnerfacto.md)), set once in `runSupervisor`'s `streamApprovalConfig{...}` literal and read in exactly one place: `newStreamRunnerFactory`'s closure (`scfg.AccountTokenProvider = approval.account`). `codexHarness` receives the *same* `streamApprovalConfig` value but its own code only reads `registry`/`timeout`/`surface` off it — so a Codex child never sees this field, not because anything filters it out, but because nothing on that path looks at it. The same struct-carries-more-than-one-consumer-reads shape as `approval.stdio`/`registry`/`timeout`/`surface` generally (see [the factory's construction doc](streamsup-package-constructing-a-streamrunner-newstreamrunnerfacto.md)). No existing call site changed shape: 13 `newStreamRunnerFactory` callers and 8 `selectInteractiveRunner` callers at the ticket's base commit all passed a `streamApprovalConfig` literal already, so a new field on it is additive.

## Testing: driving a real spawn needs `sessions.new`, not a channel post

The plan's open question asked whether a channel post would drive a Claude child spawn in-process, cheaply enough for a startup-level test. It doesn't: `channel.new`/a channel post only records a host-authored message into the conversation history ([`control-plane.md`](control-plane.md)) — it never starts a turn, so nothing spawns. `control.SessionsNew` (the `sessions.new` control verb) mints and activates a session, which does spawn the child, and is the cheap in-process trigger to reach a real helper child from a test. `cmd/pyry/claude_account_startup_test.go` uses it to drive two named instances under one `HOME`, each with its own workdir and token file, to a real (stand-in) Claude helper child, and asserts each receives only its own token even with a conflicting `CLAUDE_CODE_OAUTH_TOKEN` inherited from the test process.

**A planted-secret leak scan over `HOME` needs to exempt the test's own scratch files, not just the operator's real ones.** The first version of this test wrote its helper's "token I received" marker inside `HOME`, where the same test's leak scan walked every file looking for the planted token. A second instance's helper writing its own `.tmp` sibling mid-`mv` could be caught by that walk and misread as the daemon leaking a token — a test-harness race, not a product defect, but one that failed about half the runs under `-race -count=10`. The fix: write the helper's own scratch output (`seen-token` and a per-child `seen-token.tmp.$$`) in a `t.TempDir()` *outside* `HOME`, through a final atomic `mv`, so the scan's only exemption stays the operator's token files and nothing it walks is the test's own in-flight write. See `TestClaudeAccount_TwoInstancesEachGetOwnToken`.

## Testing: secret-store fakes must exercise the intended failure

`TestReadKeychainItem` injects `claudeAccountGOOS` and fake tools on `PATH` to exercise both platforms on Linux. The fake checks the exact argument vector, using a service name with a space to catch splitting. Leak fixtures print the planted token and item name from literal script text to both stdout and stderr: copying the `op` fake's `$2` would print `-s` in the macOS vector, whose name is `$3`, and the item-name leak assertion would pass without exercising disclosure. See `writeFakeKeychainTool` and `assertNoKeychainLeak`.

For JSON-origin control-byte cases, build the fixture with `json.Marshal` and assert the fixed "malformed keychain item name" reason. `fmt.Sprintf("%q", value)` quotes a Go string and can emit `\x1b` or `\x7f`, which are invalid JSON escapes. An assertion that accepts any origin-bearing refusal can then stay green because JSON parsing rejected the fixture before name validation ran. The file-origin control-byte fixtures in `TestNewClaudeAccount_RefusesKeychainNameWithoutEchoingValue` illustrate this trap; its flag/env cases exercise the validator, while these JSON fixtures fail at parsing. See [the review finding](https://github.com/pyrycode/pyrycode/pull/2847#issuecomment-5998292349).

Hermetic fakes verify argv, bounded reads and disclosure behavior; they do not establish real keyring unlocking, macOS access-prompt approval, or service-session access. Those are [deployment requirements](../../deployment.md#claude-account-source). Do not use `Claude Code-credentials` as the daemon's item: it holds the interactive login, and its compact JSON can satisfy `parseTokenBytes`'s printable-byte check, so token-shape validation does not enforce that separation.
