# Claude account source — per-instance token files and 1Password (#2824, #2825, `security-sensitive`)

`cmd/pyry/claude_account.go` lets one daemon instance draw its Claude account from its own owner-only token file, or from a 1Password reference, instead of inheriting `CLAUDE_CODE_OAUTH_TOKEN` from the process environment — so daemon usage doesn't have to draw on an operator's interactive `claude` account. The token file was the first source kind (#2824); `op://` (#2825) is the second, built behind the same accessor so the streamsup gate, backoff and wiring are unchanged. Client visibility of the account state ([#2816](https://github.com/pyrycode/pyrycode/issues/2816)) and OS secret stores ([#2815](https://github.com/pyrycode/pyrycode/issues/2815)) still build on the source string and the accessor. User-facing behaviour (flags, the file format, precedence, failure/recovery) is documented in [`guide.md` § Claude account source](../../guide.md#claude-account-source) and [`deployment.md` § Claude account source](../../deployment.md#claude-account-source); this page covers the design and its durable lessons.

## Shape

- `resolveClaudeAccountSource(flagValue, envValue, instanceDir) (source, origin string, err error)` — first nonempty of the `-pyry-claude-account-source` flag, `$PYRY_CLAUDE_ACCOUNT_SOURCE`, then the `source` string in `<instanceDir>/claude-account.json` (`resolveInstanceDirPath(name)`, i.e. `~/.pyry/<name>/`), via the shared `readClaudeAccountField`. The file is opened only when the flag and env are both empty; a missing file or an absent `source` key means no source configured. `origin` names only where the value came from (`flag -pyry-claude-account-source`, `env PYRY_CLAUDE_ACCOUNT_SOURCE`, or the file's path) and every error is built from fixed text plus that origin — never the value itself, since it could be a token pasted into the wrong field.
- `newClaudeAccount(flagValue, envValue, opCLIFlag, opCLIEnv, instanceDir, logger) (*claudeAccount, error)` — empty source → not-configured accessor, `provider() == nil`, launch behaviour unchanged (this is the existing-callers-keep-compiling path #2823 required). A source starting with `op://` (longer than the prefix, no control byte) selects the 1Password reader; an absolute path selects the file reader; anything else (a relative path, any other URI scheme) is refused.
- `readTokenFile(ctx, path)` opens the file afresh on every call (`O_RDONLY|O_NONBLOCK` — a FIFO at that path returns promptly instead of blocking the launch attempt), `fstat`s the opened descriptor, and refuses a non-regular file, a file owned by another UID, any `0o077` mode bit, content over 4096 bytes, or — after stripping one trailing LF/CRLF — empty content or a byte outside printable non-space ASCII (`parseTokenBytes`, shared with the 1Password reader below). Checking the descriptor actually read from (not a second `stat` on the path) closes the obvious check-then-use gap; a symlink is followed on purpose, and the checks land on whatever it resolves to.
- `readOpReference(ctx, cli, ref)` runs `exec.CommandContext(ctx, cli, "read", ref)` — no shell, the reference is one argv entry (so it can never parse as an option), `Stdin` nil, `Stdout` a `cappedBuffer` that keeps only the first `maxAccountTokenBytes+1` bytes, `Stderr` nil (never captured), and `cmd.Env` built from `os.Environ()` with `CLAUDE_CODE_OAUTH_TOKEN` stripped (`withoutAccountToken`) so the CLI never inherits a credential it has no use for. The child runs in its own process group (`Setpgid: true`); `cmd.Cancel` sends `SIGKILL` to the whole group, and `cmd.WaitDelay` (1s) bounds how long the background `Wait` may linger for a descendant that escaped the group and still holds stdout. `Wait` runs in a goroutine selecting against `ctx.Done()`, so the caller returns at the bound whether or not the child has actually exited (see the note below). Output over the cap or failing `parseTokenBytes`'s shape is "1Password output invalid"; empty is "1Password output empty"; a non-zero exit or any other wait error is "1Password read failed"; a `Start` failure is "1Password CLI unavailable"; `ctx.Err()` is "1Password read timed out" or "1Password read cancelled" depending on which it is.
- `resolveClaudeAccountOpCLI(flagValue, envValue, instanceDir) (cli, origin string, err error)` — flag, then env, then the file's `op_cli` (via `readClaudeAccountField`), else `"op"`. It is called, and `validOpCLI` checked, **only** when the source is `op://`; a file source never reads or validates `op_cli`, so a stray or malformed `op_cli` left in `claude-account.json` cannot newly break an instance that worked before #2825 (the existing two-instance test exercises this with `"op_cli":"ignored"` on a file-source instance). `validOpCLI` admits a bare name matching `[A-Za-z0-9._+-]+` other than `.`/`..` (looked up on `PATH`, never through a shell), or an absolute path with no control byte (spaces allowed, since it is still passed as a single `exec.Command` argv entry, never through a shell).
- `claudeAccount` is the instance-scoped accessor, one per daemon, shared by every Claude runner the instance creates. `provider()` is nil when not configured, else `a.read`. `prime(ctx)` is the one ten-second-bounded startup read (`runSupervisor`, after `checkDebugCapture`); its failure is logged, not fatal — the bootstrap session stays dormant until a turn needs it, so this priming read is what actually surfaces a boot-time misconfiguration before an operator sends anything. `status()` reports `{Kind, State, Reason}` and never the token, the configured path, the 1Password reference, or the CLI's output.
- `accountReadError`/`accountReadFailure` are the shared refusal type and constructor both readers return: a fixed `reason` string, never wrapping an OS/exec error (which would carry the path, the CLI, or the reference).

## The selection file needed the same trust check as the secret it points to

The architect's plan's acceptance criteria asked only for the *token file* to be owner-only. The self-review added a second check the ticket didn't ask for: `claude-account.json` itself is refused unless it is owned by the daemon's user and carries no group/other write bit (`0o022`, checked on the opened descriptor, same shape as `readTokenFile`'s `0o077` check on the token file). The reasoning: this file doesn't hold the secret, but it *picks which file does* — a selection file another local user could write would let them redirect the daemon to read and hand Claude an unrelated single-line secret of the operator's, without ever touching the real token file's permissions. A pointer to a secret needs the same ownership/writability guard as the secret itself, or the guard on the secret is moot.

## Concurrency: the recorded state is whichever read finishes last, not whichever started last

`claudeAccount.read` is called concurrently by every runner's own spawn path (first launch, a crash-loop retry, a respawn can all be in flight for different conversations at once). The mutex covers only `state`/`reason`, never the read itself, so under concurrent spawns a slow failing read can overwrite a newer success's `ready` state if it finishes after it. This is harmless today — `status()` has no production reader yet, and each runner's own launch outcome is independent of what the accessor reports globally — but it stops being harmless the moment something surfaces `status()` to a client ([#2816](https://github.com/pyrycode/pyrycode/issues/2816)): that reader would need to either accept last-finisher semantics or have the accessor move to a per-read-attempt sequence number before trusting the snapshot.

## The ten-second bound covers reads that return, not reads that hang

`prime`'s `context.WithTimeout` (and the per-attempt deadline `streamsup` applies on every later read) only cuts in once something inside `readTokenFile` actually checks `ctx.Err()` — before the open and after the read, not during either syscall. For a local file this is immediate either way. For a token file on a wedged FUSE or network mount, the blocking `open`/`read` syscall itself is not interrupted by the context, so the "ten-second startup bound" is not a hard ceiling on daemon startup time in that case. Documented as a known limit rather than fixed, since no production deployment puts the token file on anything but a local filesystem.

## A subprocess bound has to be enforced by returning on ctx.Done(), not by waiting on the child

The file reader's bound (above) is best-effort because nothing can interrupt a blocking syscall from the outside. A subprocess has no such excuse — the process itself can be killed — but `readOpReference` still can't enforce its bound by waiting for that kill to land, because `exec.CommandContext` only guarantees killing the *direct* child, and a `1Password` CLI that forks a helper (deliberately or not) can leave that helper holding the stdout pipe open after the CLI itself is dead. A test fixture makes this concrete: a fake `op` whose body is `sleep 30 & wait` detaches a `sleep` that outlives the parent shell entirely.

So the bound is enforced by the *read itself* giving up, not by the child's exit: `cmd.Wait()` runs in a goroutine that sends on a buffered channel, and the caller `select`s on that channel versus `ctx.Done()`, returning the moment `ctx.Done()` fires whether or not the child (or its escaped descendant) has actually exited. The process-group kill (`Setpgid` + `cmd.Cancel` sending `SIGKILL` to `-pid`) and `cmd.WaitDelay` only decide how fast the now-orphaned background goroutine itself exits — neither is on the path the launch waits for. Getting this backwards (waiting on `Wait` and treating the group kill as sufficient) is exactly the failure mode the ticket called out, and the hang-cut-by-deadline/cancel tests return in ~200ms specifically because the select, not the kill, is what unblocks them.

## Wiring is Claude-only, by construction rather than by filtering

`account.provider()` reaches the Claude runner factory through one new field, `streamApprovalConfig.account streamsup.AccountTokenProvider` ([`cmd/pyry/streamsup_runner.go`](streamsup-package-constructing-a-streamrunner-newstreamrunnerfacto.md)), set once in `runSupervisor`'s `streamApprovalConfig{...}` literal and read in exactly one place: `newStreamRunnerFactory`'s closure (`scfg.AccountTokenProvider = approval.account`). `codexHarness` receives the *same* `streamApprovalConfig` value but its own code only reads `registry`/`timeout`/`surface` off it — so a Codex child never sees this field, not because anything filters it out, but because nothing on that path looks at it. The same struct-carries-more-than-one-consumer-reads shape as `approval.stdio`/`registry`/`timeout`/`surface` generally (see [the factory's construction doc](streamsup-package-constructing-a-streamrunner-newstreamrunnerfacto.md)). No existing call site changed shape: 13 `newStreamRunnerFactory` callers and 8 `selectInteractiveRunner` callers at the ticket's base commit all passed a `streamApprovalConfig` literal already, so a new field on it is additive.

## Testing: driving a real spawn needs `sessions.new`, not a channel post

The plan's open question asked whether a channel post would drive a Claude child spawn in-process, cheaply enough for a startup-level test. It doesn't: `channel.new`/a channel post only records a host-authored message into the conversation history ([`control-plane.md`](control-plane.md)) — it never starts a turn, so nothing spawns. `control.SessionsNew` (the `sessions.new` control verb) mints and activates a session, which does spawn the child, and is the cheap in-process trigger to reach a real helper child from a test. `cmd/pyry/claude_account_startup_test.go` uses it to drive two named instances under one `HOME`, each with its own workdir and token file, to a real (stand-in) Claude helper child, and asserts each receives only its own token even with a conflicting `CLAUDE_CODE_OAUTH_TOKEN` inherited from the test process.

**A planted-secret leak scan over `HOME` needs to exempt the test's own scratch files, not just the operator's real ones.** The first version of this test wrote its helper's "token I received" marker inside `HOME`, where the same test's leak scan walked every file looking for the planted token. A second instance's helper writing its own `.tmp` sibling mid-`mv` could be caught by that walk and misread as the daemon leaking a token — a test-harness race, not a product defect, but one that failed about half the runs under `-race -count=10`. The fix: write the helper's own scratch output (`seen-token` and a per-child `seen-token.tmp.$$`) in a `t.TempDir()` *outside* `HOME`, through a final atomic `mv`, so the scan's only exemption stays the operator's token files and nothing it walks is the test's own in-flight write. See `TestClaudeAccount_TwoInstancesEachGetOwnToken`.
