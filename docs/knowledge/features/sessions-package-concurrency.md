# Concurrency

`sync.RWMutex` on `Pool.sessions`:

- `Lookup` and `Default` take the read lock.
- `Run` takes the read lock once briefly to grab the bootstrap pointer and `claudeSessionsDir`.
- Writers: `RotateID` (1.2b-A; no production caller since #2137 retired its last one, kept for its ~40 test references), `RotateForNewSession` (#1125; re-key via the shared `rekeyLocked` + save, one `Pool.mu` critical section), `RotateBootstrapForSelfHeal` (#1165; same shared `rekeyLocked` + save — the "no skip-set register" divergence [ADR 033](../decisions/033-supervisor-self-heal-dedicated-rotation-no-skip-set.md) recorded no longer distinguishes it from its siblings, since #2137 deleted the skip-set from all of them), `AdoptAnnouncedID` (#2135/#2137; the announced-reset re-key, now the only one of these four with a production caller — see [`sessions-package-key-types-adoptannouncedid.md`](sessions-package-key-types-adoptannouncedid.md)), `persist` (1.2c-A; called from `Session.transitionTo`). Phase 1.1's `Pool.Add(SessionConfig)` plugs in the same way.

`sync.Mutex` on each `Session.lcMu` (1.2c-A): protects `lcState`, `attached`, `activeCh`, `lastActiveAt`, and (as of #866) `id`. **Lock order: `Pool.mu → Session.lcMu`**. `Session.transitionTo` releases `lcMu` *before* calling `Pool.persist` so `saveLocked`'s per-session re-acquire can't deadlock.

**`id` is a two-lock field (#866).** `rekeyLocked` (the mutation core shared by `RotateID`, `RotateForNewSession`, `RotateBootstrapForSelfHeal`, and `AdoptAnnouncedID`) writes `sess.id = newID` under **both** `Pool.mu` (W, via the caller's function-level `defer`) and `lcMu` — the write sits inside the same brief `lcMu` section held for `lastActiveAt`, so no new lock and no lock-order change. A read is race-clean while holding *either* lock: `Pool.mu`-holders (`List`, `ResolveID`, `Snapshot`, `saveLocked`, `Activate`) read `sess.id` directly; lifecycle-goroutine readers, which hold neither `Pool.mu` nor (before the read) `lcMu`, go through the unexported `(*Session).currentID()` helper (`sess.lcMu.Lock/Unlock`, return `id`). `Session.ID()` also routes through `currentID()` for the same reason, though it has zero production callers today. This replaced a stale invariant ("`RotateID` mutates `id` without `lcMu`; today's only callers run before any lifecycle goroutine begins observing it") that broke once #839 wired `RotateID` into the live fsnotify `/clear` watcher — that watcher goroutine ran concurrently with the per-session lifecycle goroutines and fired on every `/clear`, so the two lifecycle-goroutine reads of `sess.id` (the eviction-transition notify and the idle-eviction warn log) were a live, if latent, data race. See [codebase/866.md](../codebase/866.md).
**#2137 retired the watcher, and the invariant survived the deletion of its named justification** — a lesson worth stating on its own: `RotateID` itself has had no production caller since #2137 (the watcher was the last one; it stays only because ~40 tests across five files drive it, and removing it is a separate call), but the concurrent-reader hazard it documents did not go away — it moved. `AdoptAnnouncedID`'s re-key, which now carries every announced `/clear`, runs from the reset follower's decorator on the runner's parse goroutine ([`streamsup-package-announced-reset-follower.md`](streamsup-package-announced-reset-follower.md)), a different goroutine racing the same per-session lifecycle goroutines the watcher used to race. The tempting rewrite — "the watcher is gone, so there is no concurrent reader" — would restore precisely the bug #866 fixed. When correcting a comment that justifies an invariant by naming something you're deleting, check whether the invariant's *cause* (a concurrent goroutine touching the same state) is gone too, or whether only the name of the goroutine changed.

**Known residual gap (non-blocking, #866 code review).** `Pool.Activate`'s LRU-eviction path reads `sess.id`/`victim.id` as call arguments to `pickLRUVictim` while holding only `capMu` — `Pool.mu` is acquired *inside* `pickLRUVictim`, after Go has already evaluated those arguments, so this specific read is technically unguarded by either lock. It is pre-existing (unchanged by #866), and nil-impact today (the torn value is only used to exclude an already-known-inactive target from victim candidates), but it means "every `Pool.mu`-holder reads `id` race-clean" is not quite exception-free. Tracked as a follow-up, not yet filed as its own ticket.

**`Pool.materialise`'s settings evaluation sits inside the critical section that retires the dormant entry (#2492).** Both `settingsSource`s it can be handed — `Pool.mintSettings`, `Pool.revivedSettings` — are already-locked readers: MUST be called with `Pool.mu` held, the inverse of the contract they carried before this ticket, because `materialise` now reads them itself rather than taking a value its caller computed as an argument. It reads twice. A provisional read under a brief `Pool.mu.RLock`, released before `buildSession` runs (which stays off-lock — two file writes plus the injected `RunnerFactory` call-out), seeds the runner's construction argv. The obvious alternative — build at the zero value, always install the real settings afterward — was rejected: it makes that construction argv routinely wrong, and this package's argv assertions read it at construction (`recordingRunnerFactory`), so a runner whose construction argv is a placeholder is one missed install away from spawning the wrong model. Then an authoritative read, inside the same `Pool.mu.Lock` section that deletes the `p.dormant` entry, registers the session and calls `saveLocked` — this is what keeps the live/dormant partition total (every id is in exactly one of `p.sessions` / `p.dormant`, never both, never neither) even against a concurrent `Pool.UpdateDormantSettings` landing between the two reads. On the rare path where the two reads disagree, the authoritative value is stored on the session and installed on its runner (`Runner.SetSpawnArgs`, `Runner.SetSpawnPermissionMode`) *before* `p.sessions[id] = sess` and *before* `saveLocked` runs — above the registration so a same-id race's loser can never `Activate` on the stale argv, above the save so the persisted entry is never written from it either.

**That install is a new lock edge, `Pool.mu → runner-internal`, and it is safe only because the runner is unpublished at the point it fires — a placement fact, not a property of the installer's code.** `Pool.UpdateSettings` installs past its own unlock precisely because *its* runner is live and shared; taking a runner-internal lock under `Pool.mu` there could close a cycle against some other goroutine already holding that lock. `materialise`'s runner is a local this call built and has not yet been written into `p.sessions`, so no other goroutine can be holding its internal lock when the install runs — the edge cannot close a cycle against a runner nobody else can reach. That argument depends on *where* the install sits relative to the registration, not on anything the installer's own code says; moving the publish (`p.sessions[id] = sess`) ahead of the install would silently reopen the question `Pool.UpdateSettings`'s placement was chosen to avoid.

Goroutines introduced in this layer (1.2c-A):

1. **Per-Session lifecycle goroutine** — body of `Session.Run`, owns the `active ↔ evicted` state machine and idle timer.
2. **Per-active-period supervisor goroutine** — wraps `s.sup.Run(subCtx)` and pipes the result to `runErr`.
3. **Per-attach detach-watcher** — decrements `attached` when the bridge's done channel fires.

The PTY spawn / wait / backoff loop, the I/O bridge goroutines, and the SIGWINCH watcher all remain in their existing packages.
