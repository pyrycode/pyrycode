# App-reply seal gated behind `transportDown()` (#1525)

`security-sensitive` — extends [the #874 transport-down hold](#transport-down-hold-on-the-push-drain-874--connected-probe--transportdown) to `forwardAppReply`, the seal a per-conn handler's reply travels through on its way back to `Run`. #874 deliberately left this seal alone: a reply was sealed microseconds after its inbound frame arrived, too narrow a window for a blip to land inside. The #965 per-conn worker offload ([`codebase/965.md`](../codebase/965.md)) then widened that window to up to a full handler duration — as long as `createConversationMintTimeout` (30s) — wide enough to hold an entire reconnect blip, and the #874 deferral was never revisited against the new window. Before this ticket, a reply sealed while the relay leg was down burned a Noise send-nonce on a frame `send` silently dropped (swallowing the `Outbound` error at Debug); relay↔binary carries no per-connection disconnect frame, so the phone's recv `CipherState` stayed put, the next delivered frame failed AEAD, and a session that was never actually broken died at `StatusProtocolMismatch` (4421) with no self-heal.

**The guard sits inside `forwardAppReply`, not at its call site — the `drainOnce` shape, not the #912 shape.** #912 gated `emitRekeyRequest`'s two callers at their call sites because they diverge after the check (a timer re-arm vs. a returned error). `forwardAppReply` has exactly one caller (`Run`'s `m.appReply` arm) and nothing diverges after the decision — the reply is simply dropped, with no timer to re-arm and no error to report — so the call-site indirection #912 needed here buys nothing. The probe runs *after* the pre-existing `V2StateOpen` gate and *before* `s.send.Encrypt`: ordering is load-bearing exactly as in #912, so a session torn down mid-handler keeps hitting the not-open drop with its unchanged log line and text, in every transport state.

**Dropped, not parked.** The reply is undeliverable either way today — `send` already discards it — so the guard only stops paying a nonce for a non-delivery that was already happening; it does not make the reply arrive. Parking it for post-recovery delivery would need a new buffer, an eviction policy, and an ordering rule against the push queue, and was named out of scope by the ticket. Because nothing is held, the down→up edge needs no flush — the one structural difference from #874's held push head, which does need `Reconnect` to wake its drain.

**Log line:** one Debug line on the down path, `event=v2.app_reply.dropped_transport_down` + `conn_id` only — no payload, inner envelope type, `InReplyTo`, ciphertext, plaintext, or key bytes, matching `forwardEnvelope`'s no-AEAD-bytes-in-logs discipline.

**TOCTOU and byte-identity, same posture as #874/#912.** The probe is a plain read of `m.cfg.Connected`, an immutable-after-construction func field, executed on the `Run` goroutine — the single owner of `s.send` and sole writer of `s.state`. No lock, no atomic, no new goroutine. The residual single-frame up→down transition race carries over unchanged and is not defended further. `transportDown()` reads "up" whenever `Connected` is nil, so every existing `internal/relay` test that doesn't wire it is byte-identical to pre-#1525 behavior.

**Security review verdict: PASS.** Same class as #874/#912: the change only ever *skips* a seal, so it cannot cause nonce reuse — the failure mode it fixes is a nonce *gap*, and skipping a seal cannot create one. `transportDown()` is manager-global rather than per-conn, so a false reading suppresses replies on every conn, but the relay leg genuinely is shared — when it reads down, no conn's frame reaches anyone regardless, so there's no cross-conn amplification beyond what the transport already imposes. See `docs/specs/architecture/1525-appreply-transport-down-gate.md` § Security review for the full pass.
