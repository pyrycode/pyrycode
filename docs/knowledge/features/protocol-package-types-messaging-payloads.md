# Messaging payloads (#272)

Bodies of the two conversation-flow envelopes (`docs/protocol-mobile.md` § Message types → `send_message` / `message`). `send_message` is phone → binary; `message` is binary → phone. (This slice originally also shipped the v1 bulk-history backfill payloads — `BackfillSincePayload` / `MessageChunkPayload` / `BackfillDonePayload`, for `backfill_since` / `message_chunk` / `backfill_done` — but that flow had zero emitters and zero handlers on either v2 dispatch surface; removed as dead code in #967. The v2 reconnect path, `request_snapshot` + `hello.last_event_id` bounded-ring replay (ADR 025 / #646/#647), replaced it entirely. See [codebase/967.md](../codebase/967.md).)

```go
type SendMessagePayload struct {
    ConversationID string          `json:"conversation_id"`
    MessageID      string          `json:"message_id"`
    Text           string          `json:"text"`
    AttachmentIDs  []string        `json:"attachment_ids,omitempty"` // optional (#2036)
    ClientSentAt   json.RawMessage `json:"client_sent_at,omitempty"` // optional (#2704); raw, not string — see below
}

type MessagePayload struct {
    ConversationID string   `json:"conversation_id"`
    MessageID      string   `json:"message_id"`
    Role           string   `json:"role"`
    Text           string   `json:"text"`
    AttachmentIDs  []string `json:"attachment_ids,omitempty"` // optional (#2596)
    DeviceName     string   `json:"device_name,omitempty"`    // optional (#2704)
    ClientVersion  string   `json:"client_version,omitempty"` // optional (#2704)
    ClientSentAt   string   `json:"client_sent_at,omitempty"` // optional (#2704); daemon's own re-formatting, never the client's raw bytes
}
```

- **`MessagePayload.Role` stays `string`, not a named `Role` enum.** Spec defines a closed set (`"user"`, `"assistant"`, `"system"`) but the binary already treats role-strings as `string`-typed elsewhere; a typed `Role` would force a converter at every internal call site for no observable wire-format gain, and the closed-set guarantee belongs at the dispatcher. Matches `RegisterPushTokenPayload.Platform`'s rationale.
- **The three original required fields are non-pointer, no `omitempty`.** Encode-side absence surfaces as zero-value `""` on the wire; the dispatcher rejects malformed frames via shape validation. Empty `text` is wire-legitimate (semantic validation lives at the dispatcher).
- **`AttachmentIDs` (#2036) is the field's own departure, argued rather than assumed.** `send_message` is v1-compatible and inbound, so a shipping client predates the field and sends exactly the original three keys — the empty-case wire form has to be *decided*, not copied from a v2-only neighbour. `omitempty` makes the key absent for that client, which is why a plain `omitempty`-less field (the bullet above) is not this field's shape. The nil→`[]` `MarshalJSON` the package's five *outbound* slice payloads carry (`QuestionShownPayload`, `BackgroundTaskRosterPayload`, `ModelListPayload`, `ToolUsePayload`, `SlashCommandListPayload` — the code-review NIT on #2036's own enumeration, which the ticket's originating body inherited and #2036 corrected) is a shape precedent, not a placement one — publishing "always present" here would be false for every client that predates the field. A pointer-receiver `UnmarshalJSON` (via an unexported alias type, so no recursion) instead collapses all three empty wire forms — absent, `null`, `[]` — to `nil` on decode, since `len(x) == 0` agrees across the three but Go's `x == nil` does not (`encoding/json` decodes `[]` to an empty *non-nil* slice). No `MarshalJSON` is added: `omitempty` already elides `nil` and empty-non-nil alike, so the two directions are symmetric for free, and adding one by analogy with the outbound four would re-introduce the always-present key just rejected. An ill-typed `attachment_ids` is a decode **error**, propagated to `internal/relay/handlers`' `SendMessage` (answered `protocol.malformed`), never swallowed into an empty list. `MaxAttachmentIDsPerMessage = 32` (in this file) is a published bound — a producer-side contract in the `MaxAttachmentChunkBytes` idiom, not the receiver-configured-and-unpublished idiom `attachment.too_large` uses — counting elements, not distinct ids. Enforcement is `internal/relay/handlers.SendMessage`'s (#2038): the raw element count is checked before any dedup, so 33 copies of one id is still over bound, and this package itself still counts nothing. Every element is an unverified, client-authored claim that becomes both a directory component (validate via `conversations.ValidID` before any `filepath.Join`, never trust `MaxAttachmentIDBytes` for containment) and prompt content (§ Security model threat 1, joined to the prompt by #2038) — the doc block on the field itself carries this, not just `docs/protocol-mobile.md`, since the enforcing package reads the Go declaration first. Confinement to the message's own (session-derived, never client-asserted) conversation is what keeps the id from becoming a capability; the field must never be sold as safe *because* it's a UUIDv4.
- **`MessagePayload` has exactly one producer, and it is not a push.** `newOperatorMessageHistory` (#2115) is the only place this type is built, and it hands the value to `appendConversationHistory` — a write to the durable conversation-history log, not a broadcast to an attached client. The live assistant reply on the v2 interactive lane is a stream of `assistant_delta` closed by `turn_end`; a client learns a stored `message` only by asking with `request_history`. #2082 confirmed this while ruling out widening the type to announce a host-produced attachment: the obvious move, wrong for two reasons at once — it would announce nothing at the moment the event happens, and it would change a record shape `history_page` decoders already read. Before adding a field here for a live-notification use case, check whether a live push path calls this type at all; as of #2082 none does. See [Attachment envelope types](protocol-package-constants-codes-go-envelope-types-attachments.md).
- **`SendMessagePayload.ClientSentAt` (#2704) is `json.RawMessage`, not `string`, and that is load-bearing.** The AC is "an unparseable `client_sent_at` is dropped and the message is still accepted" — a `string`-typed field would fail the **whole envelope decode** on a wrongly-typed value (a number, an object), turning a client clock quirk into a refused `send_message`. Raw bytes let `json.Unmarshal` succeed regardless of shape, and the one parse — `internal/relay/handlers.parseClientSentAt` — decides content-validity on its own terms: a non-string, a string that isn't RFC 3339, or an RFC-3339 string whose **UTC** year falls outside 1..9999 all yield "no value", the same outcome as an absent key. The year check exists because `time.Parse(time.RFC3339, …)` accepts an offset that pushes the instant's UTC year out of 4-digit range (`"0001-01-01T00:30:00+01:00"` is year 0 once converted) — without it the daemon could try to store a value that is not itself valid RFC 3339. The raw bytes never leave that one function; the daemon stores only its own UTC re-formatting (`MessagePayload.ClientSentAt`), never the client's string, and never logs either form. See [`msgqueue-package.md`](msgqueue-package.md) and [`relay-package-handlers.md`](relay-package-handlers.md#send_message-grows-a-ninth-seam-sender-identity-and-tap-time-2704) for where the parsed value travels next.
- **`MessagePayload.DeviceName` / `ClientVersion` (#2704) are the stored operator turn's sender identity, set only on the `newOperatorMessageHistory` producer, like `AttachmentIDs`.** `DeviceName` is the paired device record's name (`dispatch.Conn.Auth().Name`) — never the hello's self-reported `device_name`, which `register_push_token` already documents as attacker-controlled. `ClientVersion` is the admitted value off the *connection's own* hello, not the device record's previously-persisted version — see [the stale-snapshot fix](v2-session-manager-state-machine-noise-init-happy-and-failure-path.md) in the handshake accept path. Both `omitempty`, so an entry from a connection with no device record, or a message predating this ticket, decodes byte-identical to before.
- **`AttachmentIDs` (#2596) widens the same one-producer type, and does not reopen #2082's rejection.** #2082 rejected widening `MessagePayload` for a *live-notification* use case — announcing a host-produced attachment at the moment it happens. #2596 widens it for the *stored-entry* case #2082 left open: the ids a `send_message` named, carried on the same `newOperatorMessageHistory`-built `role: "user"` entry the type already exists for, read back only via `request_history`. Same key and element shape as `SendMessagePayload.AttachmentIDs`; `omitempty` keeps every assistant emission and every attachment-less user entry byte-identical to before the field existed. The value is `msgqueue.QueuedMessage.AttachmentIDs` (see [msgqueue-package.md](msgqueue-package.md)), never anything derived from the delivery payload — the producer has no field to reach for that would leak a host path, by construction.
- **Pure DTOs: no methods, no constructors, no `Validate()`.** Still the posture for the three original fields and for `MessagePayload`, identical to `RegisterPushTokenPayload`. `SendMessagePayload.UnmarshalJSON` is a deliberate, named exception — normalisation of a parser-differential ambiguity at the decode boundary, not validation (nothing is checked or rejected on content). It is no longer the package's only decode hook: [`MintPairingPayload.UnmarshalJSON`](protocol-package-types-pairing-payloads.md) (#2126) widens the same departure one step further, to an outright content **reject**, and states the two conditions that earn a payload a hook rather than a doc-comment-only bound — no downstream consumer that would otherwise enforce the shape, and more than one concurrent implementation racing the same contract.

Golden round-trip tests in `messaging_test.go` decode each spec example through `Envelope` → `Envelope.Payload` → per-type struct and re-marshal byte-equivalently against the matching fixture. **That pattern alone cannot pin a tag-level property like `omitempty`** — see [Drift detectors](protocol-package-drift-detectors.md). `send_message.json` keeps its original three-key form as the absent-key regression fixture; the populated form is the paired `send_message_attachments.json` (the `question_shown.json` / `question_shown_empty.json` convention). The package's canonical `*string`-WITHOUT-`omitempty` "literal `null` on the wire" idiom is now `SessionTransitionPayload.WorkspaceCwd` (#656, below) — the original example, `BackfillSincePayload.ConversationID`, was removed with the rest of the backfill flow in #967.
