# Connect-time background-task-roster reconcile (#2078) — `RetainedBackgroundTaskRosters` seam + `reconcileBackgroundTaskRosters`

`security-sensitive` — the sixth Mode B instance of the reconcile-on-connect mechanism (umbrella #829), structurally [slash-command-list reconcile](v2-session-manager-state-machine-connect-time-slash-command-list-reconcile-retain.md)'s twin with the payload type substituted. A freshly interactive-open conn is unicast one `background_task_roster` per payload the seam returns, so a client attaching to a long-running daemon shows what is still running instead of an empty panel that only fills in when claude next changes the roster — which on a quiet session may never happen. Ships with the seam wired to nothing (`nil ⇒ no reconcile`), exactly as [slash-command-list reconcile](v2-session-manager-state-machine-connect-time-slash-command-list-reconcile-retain.md) shipped before #2007; the daemon-side producer is #2079.

**The one place a twin's answer is wrong here.** All five prior reconciles' producers filter an empty aggregate away before it reaches the seam. This family must not: `BackgroundTaskRosterPayload` with an empty `Tasks` is a *positive* statement that nothing is alive — the #1240 signal a client needs — not an absence to elide. So `reconcileBackgroundTaskRosters`'s loop carries no `len(p.Tasks) == 0 { continue }` guard, and `BackgroundTaskRosterPayload.MarshalJSON` exists specifically to guarantee that case serialises as `"tasks":[]` rather than `null`. The `len(retained) == 0` early return is a different thing entirely — that's the *seam* being empty (nothing retained daemon-wide), not one payload's roster being empty. A future reconcile copying this file as its own twin should re-derive this choice from its payload's own semantics rather than pattern-matching either precedent.

**The round-trip asymmetry this divergence creates is a test-authoring trap, not just a marshalling detail.** A seam payload with `Tasks: nil` marshals to `"tasks":[]` and decodes back as an empty, non-nil slice, so `reflect.DeepEqual` against the seam's own value is false for that case. `internal/relay/v2session_rosterreconcile_test.go`'s `wantRoster` helper normalises the **want** side (nil → `[]protocol.BackgroundTask{}`) rather than the got side, so the empty-roster case is compared honestly instead of being quietly excused from the table. Any test comparing a nil-slice-bearing payload across a JSON round trip should normalise the expectation, not relax the assertion.

**`internal/relay` importing `internal/sessions` transitively is not a violation of the "no new import" seam discipline.** The Technical Notes required declaring the seam where it is consumed rather than giving `internal/relay` a direct dependency on the daemon's session layer, and `RetainedBackgroundTaskRosters func() []protocol.BackgroundTaskRosterPayload` does that — no new import was added by this ticket. But `go list -deps ./internal/relay/...` already reports both `internal/sessions` and `internal/control` in the dependency graph (`internal/control` pulls in `internal/sessions`), which reads as a contradiction to a reviewer checking the claim with that command. It isn't one: the discipline being enforced is "no *direct* import for this seam's own sake," not "the package's transitive closure excludes sessions." Read `RetainedModelLists` / `OutstandingQuestions` / `RetainedSlashCommandLists` before trusting a `go list -deps` reading against this claim.

**Seam contract, shared with its five twins:** enumerate-all rather than conversation-keyed (`V2Session` carries no conversation id — each payload self-identifies via its own `conversation_id`), order not part of the contract, BOUNDED TIME on the Run goroutine, and already-bounded payloads only — the reconcile applies no cardinality or per-row text cap of its own; that bound is `internal/streamsup`'s (`maxTaskRosterEntries`, `maxTaskRosterDescription`) via `BackgroundTaskRosterPayload.DroppedTasks` / `BackgroundTask.TruncatedFields`, with `pushQueueByteCeiling` as the relay-side backstop. A second cap here would be a second place the limit is decided, able to disagree silently with the producer's.

**Error posture and the context-teardown test are carried forward unchanged from [slash-command-list reconcile](v2-session-manager-state-machine-connect-time-slash-command-list-reconcile-retain.md)** — same never-echo-`err` marshal branch (defensive, unreachable by fixture: the payload is a closed `string`/`[]BackgroundTask`/`int` struct), same `Push`-error-identity partition (`ctx` teardown stops the batch; `ErrConnNotFound` is structurally unreachable from this call site), same "count of `push_err` records, not envelope count" assertion for the teardown branch. Nothing new here; see the twin's own entry for the reasoning rather than re-deriving it per instance.

**Security review verdict: PASS** (`docs/specs/architecture/2078-background-task-roster-connect-reconcile.md` § Security review). All four `BackgroundTask` row fields (`task_id`, `task_type`, `description`, `truncated_fields`) are claude-authored untrusted text and never reach a log record on any branch — `description` is a literal command line for the `local_bash` task type, which `BackgroundTask`'s own doc grades as the more tempting shape of the family (a *list* of command lines), so even the marshal-failure branch must not echo `err` (`encoding/json` quotes its input). `conversation_id` is the one identifier logged, safe because it is server-minted. Same out-of-scope note as every enumerate-all seam in this family: no per-device confinement — belongs to the Mode B umbrella (#829), not to a sixth instance.

**Scope guard, matching #2010's repair for the slash-command-list family:** `docs/protocol-mobile.md` § `background_task_roster` and § Reconnect / Backfill's Mode B list are now stale (they still claim an envelope-level `event_id` and still name only five reconciles) — left untouched here on purpose, since correcting them would publish a capability not yet live (the seam ships nil until #2079) and would duplicate #2080's stated deliverable.
