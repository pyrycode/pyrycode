# Connect-time background-task-roster reconcile (#2078, #2079) — `RetainedBackgroundTaskRosters` seam + `reconcileBackgroundTaskRosters` + `resolveBoundBackgroundTaskRoster`/`retainedBackgroundTaskRosters`

`security-sensitive` — the sixth Mode B instance of the reconcile-on-connect mechanism (umbrella #829), structurally [slash-command-list reconcile](v2-session-manager-state-machine-connect-time-slash-command-list-reconcile-retain.md)'s twin with the payload type substituted. A freshly interactive-open conn is unicast one `background_task_roster` per payload the seam returns, so a client attaching to a long-running daemon shows what is still running instead of an empty panel that only fills in when claude next changes the roster — which on a quiet session may never happen. #2078 shipped the seam wired to nothing (`nil ⇒ no reconcile`); #2079 filled it with the daemon-side producer, so the path now runs end to end: `emitBackgroundTaskRoster` → `sessionBackgroundTaskHold.Sink` → `streamRunner.BackgroundTaskRoster` → `resolveBoundBackgroundTaskRoster` (conversation-keyed resolver, `cmd/pyry/session_background_task_list.go`) → `retainedBackgroundTaskRosters` (the registry enumeration, its sole consumer) → `relayWiring` → `V2SessionConfig.RetainedBackgroundTaskRosters` → `reconcileBackgroundTaskRosters`.

**The one place a twin's answer is wrong here.** All five prior reconciles' producers filter an empty aggregate away before it reaches the seam. This family must not: `BackgroundTaskRosterPayload` with an empty `Tasks` is a *positive* statement that nothing is alive — the #1240 signal a client needs — not an absence to elide. So neither `reconcileBackgroundTaskRosters`'s loop nor `retainedBackgroundTaskRosters`'s enumeration carries a `len(p.Tasks) == 0 { continue }` guard, and `BackgroundTaskRosterPayload.MarshalJSON` exists specifically to guarantee that case serialises as `"tasks":[]` rather than `null`. The `len(retained) == 0` early return is a different thing entirely — that's the *seam* being empty (nothing retained daemon-wide), not one payload's roster being empty. A future reconcile copying this file as its own twin should re-derive this choice from its payload's own semantics rather than pattern-matching either precedent.

**A twin's conclusion can be right while both its reasons are false, and here the conclusion itself flips.** `retainedModelLists` and `retainedSlashCommandLists` both omit a `len(...) > 0` filter because their empty case is unreachable — one type is documented "never empty", the other's producer has its own early return. `retainedBackgroundTaskRosters` omits the identical filter because the empty case is *the point*. The code is indistinguishable across all three; the divergence lives only in the comments, so a reader diffing the three sees no signal, and copying either neighbour's justification here states something false about this variant. Re-derive from the payload's own semantics — don't pattern-match a neighbour's reason even when its code and conclusion match.

**Proving the absent filter needed a fixture the twin's rig couldn't express.** Every other roster-bearing test builds non-empty rosters, so a `len(p.Tasks) == 0 { continue }` guard added to the enumeration is invisible to all of them while deleting the feature's entire payoff — it took a fixture that arms an *empty* roster distinguishably from an *unarmed* session to make that mutant sole-red. That's the one place `backgroundTaskRosterPlan` diverges from `slashCommandListPlan`, where map-presence and a non-empty inventory are the same thing and so can't tell the two states apart.

**The round-trip asymmetry this divergence creates is a test-authoring trap, not just a marshalling detail.** A seam payload with `Tasks: nil` marshals to `"tasks":[]` and decodes back as an empty, non-nil slice, so `reflect.DeepEqual` against the seam's own value is false for that case. `internal/relay/v2session_rosterreconcile_test.go`'s `wantRoster` helper normalises the **want** side (nil → `[]protocol.BackgroundTask{}`) rather than the got side, so the empty-roster case is compared honestly instead of being quietly excused from the table. Any test comparing a nil-slice-bearing payload across a JSON round trip should normalise the expectation, not relax the assertion.

**`internal/relay` importing `internal/sessions` transitively is not a violation of the "no new import" seam discipline.** The Technical Notes required declaring the seam where it is consumed rather than giving `internal/relay` a direct dependency on the daemon's session layer, and `RetainedBackgroundTaskRosters func() []protocol.BackgroundTaskRosterPayload` does that — no new import was added by this ticket. But `go list -deps ./internal/relay/...` already reports both `internal/sessions` and `internal/control` in the dependency graph (`internal/control` pulls in `internal/sessions`), which reads as a contradiction to a reviewer checking the claim with that command. It isn't one: the discipline being enforced is "no *direct* import for this seam's own sake," not "the package's transitive closure excludes sessions." Read `RetainedModelLists` / `OutstandingQuestions` / `RetainedSlashCommandLists` before trusting a `go list -deps` reading against this claim.

**Seam contract, shared with its five twins:** enumerate-all rather than conversation-keyed (`V2Session` carries no conversation id — each payload self-identifies via its own `conversation_id`), order not part of the contract, BOUNDED TIME on the Run goroutine, and already-bounded payloads only — the reconcile applies no cardinality or per-row text cap of its own; that bound is `internal/streamsup`'s (`maxTaskRosterEntries`, `maxTaskRosterDescription`) via `BackgroundTaskRosterPayload.DroppedTasks` / `BackgroundTask.TruncatedFields`, with `pushQueueByteCeiling` as the relay-side backstop. A second cap here would be a second place the limit is decided, able to disagree silently with the producer's.

**Error posture and the context-teardown test are carried forward unchanged from [slash-command-list reconcile](v2-session-manager-state-machine-connect-time-slash-command-list-reconcile-retain.md)** — same never-echo-`err` marshal branch (defensive, unreachable by fixture: the payload is a closed `string`/`[]BackgroundTask`/`int` struct), same `Push`-error-identity partition (`ctx` teardown stops the batch; `ErrConnNotFound` is structurally unreachable from this call site), same "count of `push_err` records, not envelope count" assertion for the teardown branch. Nothing new here; see the twin's own entry for the reasoning rather than re-deriving it per instance.

**Security review verdict: PASS** (`docs/specs/architecture/2078-background-task-roster-connect-reconcile.md` § Security review, `docs/specs/architecture/2079-background-task-roster-connect-producer.md` § Security review). All four `BackgroundTask` row fields (`task_id`, `task_type`, `description`, `truncated_fields`) are claude-authored untrusted text and never reach a log record on any branch — `description` is a literal command line for the `local_bash` task type, which `BackgroundTask`'s own doc grades as the more tempting shape of the family (a *list* of command lines), so even the marshal-failure branch must not echo `err` (`encoding/json` quotes its input); neither `resolveBoundBackgroundTaskRoster` nor `retainedBackgroundTaskRosters` takes a logger, for the same reason. `conversation_id` is the one identifier logged, safe because it is server-minted. Same out-of-scope note as every enumerate-all seam in this family: no per-device confinement — belongs to the Mode B umbrella (#829), not to a sixth instance.

**Two test-design traps worth carrying into any future reproduction of this family's refusal table or its enumeration:**
- Deleting the #678 empty-`CurrentSessionID` guard leaves the *empty-conversation-id* refusal row green — `conversations.Registry.Get("")` misses one step earlier, so the guard's sole red is the *unbound* row alone. A refusal-table reproduction that keeps the empty-id row while dropping the unbound one pins nothing.
- `conversations.Registry.Create` validates neither uniqueness nor non-emptiness of `c.ID`, and `Get` returns the first match. Not exploitable here — a duplicate id would resolve the first row's roster under the shared, confining id — but `retainedBackgroundTaskRosters`'s test helper (`indexRostersByConversation`) fails on a duplicated id, so registry id-uniqueness is a load-bearing assumption of the *tests*, not a guarantee the *code* enforces. Stated in that helper's header rather than added as a check on this path.
